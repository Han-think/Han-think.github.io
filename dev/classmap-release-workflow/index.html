1. 로컬 저장소 생성#

왜 이걸 보게 됐나#

처음 GitHub 저장소를 만들 때 로컬 저장소만 생성하면 된다고 생각했었는데, 온라인에 공개하려면 별도로 GitHub 웹사이트에서 레포지토리를 만들어야 한다는 걸 깨달았어. 이 개념을 알게 된 건 프로젝트 코드를 다른 사람과 공유하고 버전 관리 시스템을 제대로 활용하기 위해 필수적인 과정이라는 것을 이해하게 되면서였어. 앞으로는 이 과정을 통해 협업 효율성을 높이고 코드 관리에도 더 신경 쓸 수 있을 것 같아.

내가 헷갈린 지점#

처음 git init 명령어를 사용했을 때, GitHub에 바로 저장소 생성이 된다고 생각했어요. 실제로 커밋하는 건 알았는데, 어디에 올라가는지는 감이 안 잡혔죠. GitHub 웹사이트에서 레포지토리를 만들어 연결하는 과정이 필요하다는 걸 뒤늦게 알게 됐습니다.

시도한 코드 / 예시#

# 로컬 저장소 생성
git init

결과와 해석#

git init 명령어를 실행하면 내 컴퓨터에 로컬 저장소가 만들어지는 것을 확인했습니다. 이는 GitHub에 바로 연결되는 원격 저장소가 아니라, 프로젝트 파일을 관리할 수 있는 개인적인 작업 공간을 만드는 과정입니다. 이후 GitHub 웹사이트에서 새로운 레포지토리를 만들고, 로컬 저장소를 이 원격 저장소와 연결해야 실제로 코드를 공유하고 관리할 수 있습니다.

정리된 이해#

git init 명령은 로컬 저장소를 만들 뿐, GitHub에 실제 레포지토리를 생성하는 것이 아니라는 점을 알게 되었습니다. 로컬 저장소를 만든 후에는 GitHub 웹사이트에서 레포지토리를 생성하고 git remote add origin 명령으로 연결해야 원격 저장소와 연동할 수 있습니다. 이 과정을 통해 소스 코드 관리의 첫 단계를 제대로 이해하게 되었습니다.

2. 원격 저장소 연결#

왜 이걸 보게 됐나#

처음에는 로컬 저장소만 만들면 GitHub에 자동으로 연결될 줄 알았는데, 원격 저장소를 따로 만들어야 한다는 것을 깨닫고 제대로 연결하는 방법을 익히게 되었어. 프로젝트 릴리스 과정에서 GitHub에 코드를 올리려다 원격 저장소 연결 문제로 막혔을 때, 이 개념을 학습해야만 다음 단계로 나아갈 수 있었어. 앞으로 다른 프로젝트를 진행할 때도 이 연결 과정을 정확하게 이해하고 진행할 수 있도록 하는 것이 중요하다고 생각했어.

내가 헷갈린 지점#

처음에는 git init 명령어를 실행한다고 해서 바로 GitHub에 저장소가 만들어지는 줄 알았습니다. 로컬 저장소만 생성되는 것인지 몰랐고, 별도로 GitHub 웹사이트에서 레포지토리를 만들어 연결해야 한다는 점이 헷갈렸습니다. 또한, 이미 원격 저장소에 초기 커밋이 존재하는 상태에서 main 브랜치를 푸시하는 과정에서 오류가 발생할 수 있다는 점도 인지하지 못했습니다.

시도한 코드 / 예시#

git remote add origin https://github.com/your-username/your-repo.git

결과와 해석#

로컬 저장소를 만든 후, git remote add origin <GitHub_URL> 명령어를 사용하여 GitHub 레포지토리를 원격 저장소로 연결했습니다. 이렇게 하면 로컬에서 작업한 내용을 GitHub에 올리거나, GitHub에서 가져올 때 사용할 수 있게 됩니다. 이 과정을 통해 로컬과 원격 저장소 간의 연결을 성공적으로 구축했고, 이후 버전 관리를 위한 기반을 마련했습니다.

정리된 이해#

로컬 저장소는 단순히 파일들을 추적하는 공간이고, GitHub과 같은 원격 저장소는 코드를 온라인에 저장하고 공유하는 역할을 합니다. git remote add origin <GitHub_URL> 명령어를 통해 로컬 저장소를 원격 저장소와 연결하면, 코드 변경 사항을 GitHub에 업로드하거나 다운로드할 수 있습니다. 이를 통해 여러 개발자가 협업하고 코드 관리를 효율적으로 할 수 있습니다.

3. PyPI와 GitHub 역할#

왜 이걸 보게 됐나#

classmap-hanthink 프로젝트 릴리스 과정에서 GitHub 레포지토리를 만들고 PyPI에 패키지를 올리는 데 어려움을 겪으면서, 이 두 플랫폼의 역할을 명확히 이해해야 할 필요성을 깨달았습니다. GitHub는 코드를 관리하고, PyPI는 실제 사용자들이 패키지를 설치할 수 있도록 배포하는 공간이라는 것을 명확히 알게 되면서, 프로젝트 관리 및 배포 과정의 효율성을 높이기 위한 필수적인 지식임을 알게 되었습니다.

내가 헷갈린 지점#

처음에는 GitHub 저장소를 로컬 저장소 초기화 명령어로 바로 만들 수 있다고 생각했고, 원격 저장소의 존재를 잊고 main 브랜치를 푸시할 때 오류가 나는 이유를 몰랐습니다. 또한, PyPI에 패키지를 배포하려면 별도의 도구가 필요하다는 사실과, 그것이 프로젝트 내에 설치되어 있지 않으면 안 된다는 점을 간과했습니다.

시도한 코드 / 예시#

# classmap-hanthink CLI 사용법 예시
# 기본 출력
$ classmap examples/sample_classes.py

# 외부 base class 표시
$ classmap examples/sample_classes.py --show-external

결과와 해석#

GitHub는 코드 관리를 담당하고, PyPI는 최종 패키지를 배포하는 역할을 한다는 것을 확실히 알게 됐어. pyproject.toml의 버전 정보와 Git 태그를 일치시키는 것이 중요하다는 것도 명심해야겠어. 임시로 twine을 사용했던 경험을 바탕으로, 앞으로는 패키지 배포 전 필요한 도구 설치를 꼼꼼히 확인해야겠다고 다짐했어.

정리된 이해#

GitHub는 소스 코드의 버전 관리 및 이력 관리를 담당하고, PyPI는 파이썬 패키지를 배포하여 사용자들이 쉽게 설치할 수 있도록 돕는 역할을 합니다. 이 둘을 사용할 때에는 버전 정보, 커밋 메시지, 배포 파일 이름 등을 일관되게 유지하는 것이 중요합니다.

4. force push#

왜 이걸 보게 됐나#

원격 저장소에 이미 초기 커밋이 있었는데, 로컬 브랜치를 강제로 푸싱하려다 발생한 문제 때문에 ‘force push’ 개념을 알게 됐어. 초기에는 왜 푸시가 거절되는지 몰라서 당황했지만, 원격 저장소와 로컬 저장소의 관계를 이해하고, 상황에 따라 강제 푸싱을 사용할 수 있다는 것을 배우게 됐어. 하지만 강제 푸싱은 팀 협업에 영향을 줄 수 있다는 점도 인지하게 됐지.

내가 헷갈린 지점#

처음에 force push 명령어를 쓸 때, 혹시라도 다른 사람의 작업에 영향을 미치거나, 저장소의 기록을 덮어씌우는 건 아닌가 싶어서 굉장히 조심스러웠다. 특히, 협업하는 환경에서는 함부로 사용하면 안 된다고 생각했고, force push가 왜 위험한 명령어인지에 대한 이해가 부족했었다. 그래서 ‘강제’라는 단어 때문에 좀 꺼렸고, 어떤 상황에서 사용해야 하는지, 그리고 사용했을 때 어떤 영향을 미칠 수 있는지 더 명확히 알고 싶었다.

시도한 코드 / 예시#

git push -u origin main --force

결과와 해석#

git push -u origin main --force 명령은 로컬 main 브랜치의 변경 사항을 원격 저장소의 main 브랜치에 강제로 반영하는 명령어입니다. 원격 저장소에 이미 커밋이 있는 상태에서 로컬의 변경 사항을 덮어쓰기 때문에 다른 사람의 작업에 영향을 줄 수 있으므로, 팀원과 상의하거나 주의해서 사용해야 합니다. 이 명령어를 통해 나는 기존에 푸시 실패했던 문제를 해결하고 main 브랜치를 업데이트할 수 있었습니다.

정리된 이해#

force push는 원격 저장소에 이미 커밋이 있는 경우, 로컬 변경 사항을 강제로 업로드하는 명령어입니다. 신중하게 사용해야 하는데, 다른 사람과 협업하는 경우 혼란을 야기할 수 있기 때문입니다. 따라서 공개 저장소에는 가급적 사용하지 않는 것이 좋습니다.

총평#

오늘 전체에서 배운 것#

Git 저장소를 생성하고 원격 저장소와 연결하는 과정에서 GitHub 레포지토리 생성이 자동이 아니라는 점을 처음 깨달았습니다. 또한, PyPI 업로드 시 필요한 twine을 프로젝트에 설치하는 것을 잊지 말아야 하며, force push는 주의해서 사용해야 한다는 것을 알게 되었습니다.

다음에 조심할 것#

다음부터는 GitHub 레포지토리를 미리 생성하고 로컬 저장소와 연결하는 단계를 거쳐야 한다. PyPI 업로드 시 의존성 패키지 설치 여부를 꼼꼼히 확인하고, 강제 푸시 명령어 사용은 최대한 피해야겠다.

다음 복습 주제#

force push는 언제 어떤 상황에서 사용해야 하는지, 그리고 그 위험성을 좀 더 깊이 파악하고 싶다. PyPI 배포 과정에서 twine을 사용하는 방법, 그리고 빌드 시스템과의 연동을 좀 더 자세히 알아봐야겠다.
