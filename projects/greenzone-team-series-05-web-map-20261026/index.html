분석 결과를 화면에 연결한 구현#

분석 파일을 만들어 두는 것만으로 주민이나 관리자에게 결과가 전달되지는 않는다. 팀은 기존 FastAPI 앱과 화면을 바탕으로, 건물 검색에서 생활권·거점안 확인으로 이어지는 화면을 연결했다. 지도에는 집 위치, 생활권, 기존 후보, 신규 대안, 도로, 보호시설 같은 레이어를 나누어 표시한다.

이 화면의 역할은 분석을 다시 계산하는 것이 아니라, 준비된 결과를 사용자가 탐색하고 비교하는 것이다. 필터를 켜고 끄면 표시가 달라지지만, 그 조작이 Louvain이나 배정 분석을 새로 실행하지는 않는다.

보유 자료 기반 검색 구조#

검색 화면은 보유한 도로명·지번·건물명 자료에서 후보를 찾아 담당 생활권을 보여준다. Kakao Maps는 지도 화면과 위치 표시를 돕고, 프로젝트의 건물 연결 결과가 검색의 기준이 된다. 검색 결과를 외부 지오코딩으로 전부 다시 찾는 서비스라고 설명하지 않는다.

이 설계는 API 의존성을 줄이고 팀이 가진 데이터와 분석 결과를 같은 화면에 붙이는 데 유리했다. 대신 데이터에 없는 주소나 새로 지어진 건물은 검색되지 않을 수 있고, 자동완성·유사 주소 보완과 최신 주소 데이터는 별도 과제다. API 키는 공개 저장소에 넣지 않고 각자 로컬 설정으로 관리해야 한다.

Leaflet·Folium 지도 기능과 역할#

관리자 분석 지도에는 Leaflet과 Folium 두 가지 보기가 있다. Leaflet은 화면에서 필터를 빠르게 바꾸며 후보·생활권·도로를 탐색하기 좋다. Folium은 Python 분석 결과를 HTML 지도 보고서 형태로 만들어 검토하거나 공유할 때 편하다.

두 도구가 서로 다른 분석 결과를 만드는 것은 아니다. 같은 보유 데이터를 두 방식으로 표현한다. Leaflet은 브라우저에서 상호작용하는 탐색 화면이고, Folium은 분석 코드에서 HTML 지도를 구성하는 보고용 표현에 가깝다.

수거 경로 계산 기능과 한계#

경로 화면에서는 방문 거점을 고르고, 사용자가 순서를 직접 지정하거나 가까운 거점부터 자동 순서를 만들 수 있다. 두 경우 모두 저장된 도로 그래프의 구간 최단거리를 연결해 예상 경로를 표시한다.

이 경로는 실제 수거차 내비게이션이 아니다. 웹에는 팀 2차 분석에서 사용한 도로망 전체가 아니라 별도로 준비된 162개 도로 구간이 연결되어 있다. 일방통행, 차종, 회전 반경, 적재 상태, 시간대 정체, 실제 진입·정차 조건을 모두 반영하지 않는다. 분석 보고서에 나온 순회거리와 웹 계산 경로를 같은 값이라고도 할 수 없다.

화면 결과의 검증 범위와 다음 단계#

검색 결과와 지도는 “이 건물이 어느 제안 생활권에 연결되는가”를 보여준다. 안전한 장소가 확정되었다거나, 주민이 실제로 그곳을 이용한다거나, 수거차가 그 순서대로 운행한다는 증거는 아니다. 화면에는 운영 승인 전 제안이라는 경계를 계속 표시해야 한다.

이번 편의 정리#

이번 구현에서 중요한 건 도구를 여러 개 쓰는 것이 아니라 데이터 분석 → 검색 결과 → 지도 표시 → 경로안이 한 흐름으로 이어진 점이었다. 지도는 결과를 보여주는 창이고, 현장 검증을 대신하지 않는다.

다음 편에서는 폐기물 사진 후보, 사용자 확인, 공식 자료 검색, RAG와 평가를 살펴본다.
