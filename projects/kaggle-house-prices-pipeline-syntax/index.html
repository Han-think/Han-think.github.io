Kaggle House Prices 1: Pipeline 문법이 왜 중요했는가

강사님이 강조한 Pipeline 문법을 House Prices 프로젝트에서 왜 써야 했는지 정리
2026년 7월 6일 · 3 min

핵심 질문#

강사님이 pipeline 문법을 강조한 이유는 단순히 코드를 예쁘게 쓰기 위해서가 아니었다. Kaggle House Prices처럼 전처리, 결측치 처리, 인코딩, 스케일링, 모델 학습이 길게 이어지는 문제에서는 각 단계를 따로 실행하면 실수할 지점이 너무 많아진다.

이 프로젝트에서 pipeline은 세 가지 문제를 막아줬다.

  1. train/test 전처리 불일치
  2. fold 안팎의 데이터 누수
  3. 실험마다 달라지는 비교 조건

데이터 로딩과 경로 통일#

처음에는 Kaggle, Colab, 로컬 환경마다 경로가 달라서 코드가 흔들릴 수 있었다. 그래서 pathlib로 경로를 고정했다.

from pathlib import Path
import pandas as pd

DATA_DIR = Path('/mnt/data') if Path('/mnt/data/train.csv').exists() else Path('.')

train = pd.read_csv(DATA_DIR / 'train.csv')
test = pd.read_csv(DATA_DIR / 'test.csv')
sample_submission = pd.read_csv(DATA_DIR / 'sample_submission.csv')

경로를 먼저 통일하면 이후 pipeline은 입력 데이터만 바뀌고 구조는 유지된다.

의미 기반 결측치 처리#

House Prices의 결측치는 전부 같은 의미가 아니다. PoolQC, GarageType, BsmtQual 같은 값의 NaN은 누락이라기보다 시설 없음일 수 있다.

NONE_COLS = [
    'PoolQC', 'MiscFeature', 'Alley', 'Fence', 'FireplaceQu',
    'GarageType', 'GarageFinish', 'BsmtQual', 'BsmtCond',
    'BsmtExposure', 'BsmtFinType1', 'BsmtFinType2'
]

ZERO_COLS = [
    'GarageArea', 'GarageCars', 'BsmtFinSF1', 'BsmtFinSF2',
    'BsmtUnfSF', 'TotalBsmtSF', 'BsmtFullBath', 'MasVnrArea'
]

범주형 시설이 없으면 None, 면적이나 개수가 없으면 0, 실제 미기록 가능성이 높은 LotFrontage는 Neighborhood별 중앙값으로 대체했다. 이 정책을 함수나 transformer로 묶어야 train과 test에 같은 규칙을 적용할 수 있다.

EDA를 feature로 옮기기#

EDA에서 강하게 보인 변수는 OverallQual, GrLivArea, GarageCars, GarageArea, TotalBsmtSF, YearBuilt, Neighborhood였다. 그래프를 보고 끝내지 않고 파생변수로 옮겼다.

df['TotalSF'] = df['TotalBsmtSF'] + df['1stFlrSF'] + df['2ndFlrSF']
df['TotalBath'] = df['FullBath'] + 0.5 * df['HalfBath'] \
                  + df['BsmtFullBath'] + 0.5 * df['BsmtHalfBath']
df['HouseAge'] = df['YrSold'] - df['YearBuilt']
df['IsRemodeled'] = (df['YearBuilt'] != df['YearRemodAdd']).astype(int)
df['HasGarage'] = (df['GarageArea'] > 0).astype(int)
df['HasBsmt'] = (df['TotalBsmtSF'] > 0).astype(int)
df['OverallQual_TotalSF'] = df['OverallQual'] * df['TotalSF']

파생변수는 많이 만드는 것이 목적이 아니다. EDA에서 발견한 관계를 재현 가능한 코드 가설로 옮기는 것이 목적이다.

ColumnTransformer의 역할#

수치형과 범주형은 처리 방식이 다르다. 수치형은 결측치 대체와 scaling, 범주형은 결측치 대체와 one-hot encoding이 필요했다.

from sklearn.compose import ColumnTransformer
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import OneHotEncoder, RobustScaler
from sklearn.pipeline import Pipeline

numeric_pipe = Pipeline([
    ('imputer', SimpleImputer(strategy='median')),
    ('scaler', RobustScaler())
])

categorical_pipe = Pipeline([
    ('imputer', SimpleImputer(strategy='most_frequent')),
    ('onehot', OneHotEncoder(handle_unknown='ignore'))
])

preprocess = ColumnTransformer([
    ('num', numeric_pipe, numeric_features),
    ('cat', categorical_pipe, categorical_features)
])

handle_unknown='ignore'도 중요했다. test에 train에서 보지 못한 범주가 나와도 pipeline이 멈추지 않게 해준다.

Pipeline으로 모델까지 묶기#

최종적으로 전처리와 모델을 하나로 묶었다.

from sklearn.linear_model import LassoCV

model = Pipeline([
    ('preprocess', preprocess),
    ('model', LassoCV(
        alphas=np.logspace(-5, -2, 40),
        cv=5,
        max_iter=20000,
        random_state=42
    ))
])

이 구조의 장점은 cross-validation을 할 때 fold마다 전처리가 다시 fit된다는 점이다. 즉 검증 fold의 정보를 미리 본 상태로 imputer, scaler, encoder가 학습되는 위험을 줄인다.

이번 프로젝트에서 배운 pipeline의 의미#

Pipeline은 초보자에게 문법이 복잡해 보인다. 하지만 프로젝트가 커질수록 오히려 안전장치가 된다.

위험pipeline 없이 생기는 문제pipeline으로 얻은 효과
train/test 불일치test에 다른 전처리 적용같은 transformer 재사용
데이터 누수전체 데이터로 scaler fitfold 안에서만 fit
실험 비교 혼란모델마다 전처리 조건 다름같은 조건에서 모델 교체
재현성 부족셀 실행 순서에 의존하나의 객체로 재실행

강사님이 pipeline 문법을 중요하게 본 이유는 결국 이것이었다. 실험을 많이 하는 사람일수록, 코드를 짧게 쓰는 것보다 실험 조건을 고정하는 문법이 더 중요하다.
