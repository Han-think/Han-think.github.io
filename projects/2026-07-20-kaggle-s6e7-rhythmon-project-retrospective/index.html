1. 프로젝트의 출발점과 최종 결과#

무엇을 만들었나#

이 프로젝트는 Kaggle Playground Series S6E7의 학생 생활습관 데이터를 이용해 health_condition을 예측하는 다중 분류 문제에서 시작했다.

입력은 수면 시간, 심박수, BMI, 칼로리 소비량, 걸음 수, 운동 시간, 수분 섭취량과 같은 수치형 변수와 식습관, 스트레스 수준, 수면 품질, 활동 수준, 흡연·음주, 성별과 같은 범주형 변수로 구성됐다. 목표값은 다음 세 상태였다.

  • at-risk
  • fit
  • unhealthy

처음 목표는 단순했다.

기존 코드보다 Kaggle 점수를 더 높이는 것.

하지만 프로젝트가 진행될수록 목표는 점수만으로 설명하기 어려워졌다. 모델이 어떤 데이터를 보고 판단했는지, 검증 점수가 실제 제출 점수와 얼마나 일치하는지, 더 높은 점수가 반복 가능한지, 그리고 이 예측을 실제 서비스에 연결한다면 누가 최종 결정을 내려야 하는지까지 질문이 확장됐다.

최종적으로 프로젝트는 다음 네 층으로 완성됐다.

  1. 예측 모델: LightGBM과 CatBoost 기반 다중 분류
  2. 검증 체계: 5-fold OOF와 nested 검증
  3. 재현 체계: 실험 로그, 확률 캐시, 제출 이력, 모델 증적
  4. 서비스 제안: 청소년 건강 리듬 지원 앱 리듬ON

2. 문제 정의와 평가 지표부터 다시 잡기#

무엇을 배웠나#

이 데이터는 클래스가 심하게 불균형했다.

클래스 비율
at-risk 85.87%
unhealthy 8.36%
fit 5.77%

일반 Accuracy만 사용하면 모든 샘플을 다수 클래스인 at-risk로 예측해도 겉보기 점수가 높게 나올 수 있다. 그러나 이 모델의 목적은 세 상태를 모두 구분하는 것이므로, 각 클래스의 recall을 동일하게 반영하는 Balanced Accuracy가 적합했다.

Balanced Accuracy는 다음과 같이 계산된다.

Balanced Accuracy
= (Recall_at-risk + Recall_fit + Recall_unhealthy) / 3

예를 들어 at-risk recall이 매우 높아도 fit과 unhealthy를 거의 놓친다면 Balanced Accuracy는 낮아진다.

왜 이 지표가 중요했나#

이 문제에서 소수 클래스는 단순한 예외가 아니다. 오히려 모델이 놓치기 쉬운 상태다. 다수 클래스만 잘 맞히는 모델은 전체 정확도는 높아 보이지만 실제 분류 문제를 해결하지 못한다.

그래서 모델 개발 과정에서 다음을 함께 봤다.

  • 전체 Balanced Accuracy
  • 클래스별 recall
  • confusion matrix
  • fit → at-risk 오류
  • unhealthy → at-risk 오류
  • 보정 전후의 클래스별 변화

헷갈렸던 점#

초기에는 class_weight='balanced'를 사용하면 불균형 문제가 자동으로 해결된다고 생각하기 쉬웠다. 그러나 class weight는 학습 중 손실 함수에 영향을 주는 한 가지 방법일 뿐이다.

실제로는 다음이 모두 필요했다.

  1. 불균형을 반영한 학습
  2. 클래스별 성능을 반영한 평가
  3. OOF 확률 기반 후처리
  4. 클래스별 오류 방향 확인
  5. 제출 점수와 로컬 검증의 일치 확인

정리된 이해#

평가 지표는 결과를 채점하는 마지막 도구가 아니라 프로젝트의 방향을 결정하는 첫 번째 계약이다.

문제 정의
→ 지표 선택
→ 검증 방식
→ 모델 선택
→ 운영 KPI

Balanced Accuracy를 선택했기 때문에 모델 개발뿐 아니라 서비스 KPI에서도 상태별 누락을 따로 보게 됐다.

3. 첫 번째 전환점 수치형 변수를 문자열로 다루던 오류#

무엇을 발견했나#

기존 코드는 모든 컬럼을 문자열로 읽고, 모든 변수에 LabelEncoder를 적용하고 있었다.

train = pd.read_csv(train_path, dtype=str)

for col in X.columns:
    encoder = LabelEncoder()
    combined = pd.concat(
        [X[col].astype(str), X_test[col].astype(str)],
        axis=0
    )
    encoder.fit(combined)

    X[col] = encoder.transform(
        X[col].astype(str)
    ).astype(float)

이 방식은 범주형 변수뿐 아니라 수치형 변수까지 문자열 범주로 바꿨다.

예를 들어 수면 시간이 다음과 같다고 하자.

6.5, 7.0, 7.5, 8.0

이 값은 실제로 크기와 간격이 있는 연속형 수치다. 그러나 문자열 인코딩을 적용하면 모델에는 다음과 같은 임의의 번호로 들어갈 수 있다.

6.5 → 0
7.0 → 1
7.5 → 2
8.0 → 3

값이 단순할 때는 우연히 순서가 맞아 보일 수 있지만, 실제 고유값이 많고 소수점 표기가 복잡하면 원래의 수학적 거리와 의미가 깨진다.

수정 방식#

수치형과 범주형을 분리했다.

numeric_columns = [
    "sleep_duration",
    "heart_rate",
    "bmi",
    "calorie_expenditure",
    "step_count",
    "exercise_duration",
    "water_intake",
]

categorical_columns = [
    "diet_type",
    "stress_level",
    "sleep_quality",
    "physical_activity_level",
    "smoking_alcohol",
    "gender",
]

수치형은 실제 float로 유지했다.

for col in numeric_columns:
    X[col] = pd.to_numeric(
        X[col],
        errors="coerce"
    ).astype("float32")

범주형은 train과 test의 vocabulary를 일치시킨 뒤 category 타입으로 처리했다.

for col in categorical_columns:
    values = pd.concat(
        [X[col], X_test[col]],
        axis=0
    )

    categories = values.dropna().unique()

    X[col] = pd.Categorical(
        X[col],
        categories=categories
    )

    X_test[col] = pd.Categorical(
        X_test[col],
        categories=categories
    )

결측값도 무조건 0으로 채우지 않고 모델이 결측 분기 자체를 학습할 수 있도록 유지했다.

결과#

이 오류를 수정하고 LightGBM을 전체 데이터 5-fold OOF로 학습한 뒤, Public score는 약 0.93365까지 상승했다.

한 번의 고급 모델 추가보다 데이터 타입 오류 하나를 고친 효과가 더 컸다.

헷갈렸던 점#

머신러닝 프로젝트에서는 모델 이름이 화려할수록 성능이 좋아질 것처럼 느껴진다. 그러나 실제로는 입력 데이터가 잘못 표현되면 아무리 강한 모델도 잘못된 문제를 학습한다.

정리된 이해#

첫 번째 원칙은 다음과 같다.

모델을 바꾸기 전에 데이터가 모델에 어떤 형태로 들어가는지 확인한다.

이 프로젝트에서 가장 큰 초기 개선은 새 알고리즘이 아니라 데이터 의미를 복원한 데서 나왔다.

4. 검증 전략 OOF와 nested 검증을 분리한 이유#

OOF란 무엇인가#

OOF는 Out-of-Fold prediction의 약자다.

5-fold 교차검증에서는 데이터를 다섯 조각으로 나눈 뒤, 매번 네 조각으로 학습하고 남은 한 조각을 예측한다.

Fold 1: 2,3,4,5로 학습 → 1 예측
Fold 2: 1,3,4,5로 학습 → 2 예측
Fold 3: 1,2,4,5로 학습 → 3 예측
Fold 4: 1,2,3,5로 학습 → 4 예측
Fold 5: 1,2,3,4로 학습 → 5 예측

이렇게 하면 모든 학습 행에 대해 자신을 학습에 사용하지 않은 모델의 예측 확률을 얻는다.

oof_proba = np.zeros(
    (len(X), n_classes),
    dtype=np.float32
)

for fold, (train_idx, valid_idx) in enumerate(
    splitter.split(X, y)
):
    model.fit(
        X.iloc[train_idx],
        y[train_idx]
    )

    oof_proba[valid_idx] = model.predict_proba(
        X.iloc[valid_idx]
    )

왜 OOF 확률이 필요했나#

클래스별 확률 보정과 앙상블을 실험하려면 단순 예측 라벨이 아니라 클래스별 확률이 필요했다.

sample 1
at-risk: 0.61
fit: 0.37
unhealthy: 0.02

이 확률을 이용하면 모델을 다시 학습하지 않고도 다음을 시험할 수 있다.

  • 클래스별 가중치
  • 모델 간 확률 블렌드
  • calibration
  • threshold 변화
  • 클래스별 recall trade-off

nested 검증을 도입한 이유#

문제는 OOF 확률에서 최적 가중치를 찾고 같은 OOF에서 점수를 계산하면 결과가 낙관적으로 보일 수 있다는 점이다.

예를 들어 다음처럼 보정값을 찾았다고 하자.

best_weights = search_weights(
    y_true=y,
    oof_proba=oof_proba
)

그 뒤 같은 데이터에서 평가하면 탐색과 평가에 같은 정보를 사용한다.

pred = np.argmax(
    oof_proba * best_weights,
    axis=1
)

이를 줄이기 위해 OOF fold를 다시 나눠 보정 파라미터를 선택하는 영역과 평가 영역을 분리했다.

외부 Fold A
→ 나머지 Fold에서 보정값 탐색
→ Fold A에서 보정값 평가

외부 Fold B
→ 나머지 Fold에서 보정값 탐색
→ Fold B에서 보정값 평가

실제 관찰#

여러 라운드에서 nested 점수와 Public score가 약 ±0.001 안에서 반복적으로 일치했다.

이 일치는 단순히 점수가 높다는 것보다 중요했다. 로컬 검증이 실제 제출 방향을 제대로 반영하고 있다는 증거였기 때문이다.

정리된 이해#

검증은 단일 숫자가 아니라 신뢰 계층이다.

빠른 샘플 검증
→ 전체 OOF
→ nested 검증
→ Public score 확인
→ 반복 실행 확인

각 계층은 목적이 다르다.

  • 빠른 검증: 후보 압축
  • 전체 OOF: 최종 모델 비교
  • nested 검증: 후처리 과적합 점검
  • Public score: 외부 결과 확인
  • 반복 실행: 재현성 확인

5. 클래스별 확률 보정으로 불균형을 다루기#

오류 방향을 먼저 봤다#

초기 confusion matrix를 확인했을 때 오류는 무작위가 아니었다.

주요 오류는 다음 방향으로 몰렸다.

fit → at-risk
unhealthy → at-risk

반대로 fit ↔ unhealthy 혼동은 상대적으로 적었다.

즉 모델은 소수 클래스끼리 헷갈리는 것이 아니라, 애매한 샘플을 다수 클래스인 at-risk로 보내는 경향이 강했다.

클래스별 확률 가중치#

예측 확률에 클래스별 가중치를 곱한 뒤 가장 큰 값을 선택했다.

weighted_proba = proba * class_weights
prediction = np.argmax(
    weighted_proba,
    axis=1
)

예를 들어 원래 확률이 다음과 같다고 하자.

at-risk: 0.52
fit: 0.45
unhealthy: 0.03

fit에 조금 더 높은 가중치를 적용하면 경계 샘플의 결정이 바뀔 수 있다.

weights:
at-risk: 0.85
fit: 1.15
unhealthy: 1.10

보정 후:

at-risk: 0.442
fit: 0.5175
unhealthy: 0.033

최종 예측은 fit이 된다.

중요한 제한#

보정값을 크게 만들수록 소수 클래스 recall은 올라갈 수 있지만, 다수 클래스 recall은 내려간다.

실제로 보정 범위를 넓히면서 다음 현상이 나타났다.

  • fit recall 상승
  • unhealthy recall 상승
  • at-risk recall 하락
  • 전체 Balanced Accuracy는 일정 구간까지 상승
  • 이후 개선폭 감소

즉 보정은 공짜 성능 향상이 아니라 클래스 간 오류 비용을 재배분하는 과정이다.

수확체감#

보정 탐색 범위를 넓힐수록 개선폭이 줄었다.

초기 grid
→ 큰 개선

Nelder-Mead 확장
→ 추가 개선

더 넓은 범위
→ 작은 개선

과도한 범위
→ recall trade-off 증가

정리된 이해#

클래스별 보정은 모델을 속이는 기술이 아니다.

모델이 만든 확률을 문제의 평가 기준에 맞게 해석하는 의사결정 층이다.

모델 확률
→ 클래스별 비용 반영
→ 최종 결정

다만 이 층은 반드시 OOF와 nested 검증으로 선택해야 한다.

6. 모델 스크리닝과 후보 압축#

왜 여러 모델을 비교했나#

처음부터 CatBoost와 LightGBM만 선택하지 않았다. 다양한 알고리즘을 동일한 빠른 조건에서 비교해 데이터의 기본 구조를 파악했다.

대표적으로 다음 모델을 비교했다.

  • DummyClassifier
  • LogisticRegression
  • RidgeClassifier
  • SGDClassifier
  • GaussianNB
  • DecisionTreeClassifier
  • RandomForestClassifier
  • ExtraTreesClassifier
  • HistGradientBoostingClassifier
  • KNeighborsClassifier
  • LightGBM
  • XGBoost
  • CatBoost

빠른 스크리닝 조건#

전체 데이터와 최종 파이프라인을 모든 모델에 적용하면 비용이 너무 크다. 그래서 후보 압축 단계에서는 주로 다음 조건을 사용했다.

약 50,000행
3-fold CV
원본 13개 변수
공통 전처리
Balanced Accuracy

일부 모델은 메모리와 실행 시간 문제로 더 작은 샘플을 사용했다.

주의할 점#

HistGradientBoosting이 빠른 조건에서 가장 높았지만, 최종 전체 데이터 OOF에서는 CatBoost가 더 강했다.

이 차이는 다음 이유에서 발생할 수 있다.

  • 샘플 크기 차이
  • 범주형 처리 방식
  • 조기종료
  • 하이퍼파라미터
  • 최종 파생 피처
  • 전체 분포에서의 안정성

빠른 조건에서 오래 걸린 LightGBM과 CatBoost가 결국 최종 후보로 남았다는 점도 눈여겨볼 부분이다. 스크리닝 단계의 실행 시간과 최종 채택 여부는 별개의 기준으로 다뤄야 했다.

정리된 이해#

스크리닝의 목적은 최고 모델을 확정하는 것이 아니라 탐색 공간을 줄이는 것이다.

13개 모델 비교
→ 3~4개 후보
→ 전체 OOF
→ 오류 다양성 분석
→ 최종 앙상블

7. CatBoost와 LightGBM을 함께 사용한 이유#

CatBoost의 역할#

CatBoost는 범주형 변수를 네이티브하게 다룰 수 있고, ordered boosting을 통해 범주형 통계의 누수를 줄이는 데 강점이 있다.

이 프로젝트에서 CatBoost는 가장 강한 단일 모델이었다.

CatBoost OOF
≈ 0.9494

auto_class_weights='Balanced'를 사용해 불균형도 학습 단계에서 반영했다.

model = CatBoostClassifier(
    loss_function="MultiClass",
    iterations=6000,
    learning_rate=0.12,
    depth=7,
    l2_leaf_reg=6.54,
    random_strength=1.91,
    bagging_temperature=0.15,
    auto_class_weights="Balanced",
    random_seed=42,
    early_stopping_rounds=100,
    verbose=False,
)

CatBoost 범주형 결측 오류#

CatBoost에 범주형 NaN이 실수형 NaN으로 들어가면 오류가 발생했다.

잘못된 방식:

X[col] = X[col].astype(str)

pandas categorical 컬럼의 NaN이 환경에 따라 실제 float NaN으로 남을 수 있었다.

수정 방식:

X[col] = (
    X[col]
    .cat.add_categories(["__MISSING__"])
    .fillna("__MISSING__")
    .astype(str)
)

작은 샘플로 먼저 실행하는 smoke test가 없었다면 전체 데이터 학습을 시작한 뒤에야 오류를 발견했을 것이다.

LightGBM의 역할#

LightGBM 단독 OOF는 CatBoost보다 낮았다.

LightGBM OOF
≈ 0.9229

그럼에도 최종 모델에서 제외하지 않았다.

이유는 두 모델이 틀리는 패턴이 완전히 같지 않았기 때문이다.

앙상블에서는 단독 성능뿐 아니라 오류 다양성이 중요하다.

강한 모델 A
+ 조금 약하지만 다른 오류를 내는 모델 B
→ 일부 오류 상쇄 가능

동일 fold 사용#

두 모델의 OOF 확률을 블렌딩하려면 같은 샘플이 같은 fold 구조에서 예측돼야 한다.

그래서 한 모델이 생성한 fold ID를 저장하고 다른 모델이 그대로 재사용했다.

fold_id = np.load(
    "artifacts/fold_id.npy"
)

for fold in range(5):
    train_idx = np.where(
        fold_id != fold
    )[0]

    valid_idx = np.where(
        fold_id == fold
    )[0]

확률 블렌드#

두 모델의 확률을 가중 평균했다.

blended = (
    alpha * lgb_proba
    + (1 - alpha) * cb_proba
)

final_pred = np.argmax(
    blended * class_weights,
    axis=1
)

최종 fixed OOF Balanced Accuracy는 0.949873이었다.

CatBoost 단독보다 개선폭은 작지만, 반복 검증에서 유지되는 개선이었다.

30개 피처가 같은 fold 구조의 5-Fold OOF를 거쳐 두 모델로 나뉘고, 그 확률이 다시 하나로 blend된 뒤 클래스 보정을 통과하는 전체 흐름을 도식으로 남겨두면, 나중에 어느 단계를 손봐야 할지 훨씬 빨리 찾을 수 있었다.

XGBoost를 제외한 이유#

XGBoost도 세 번째 후보로 실험했다.

그러나 XGBoost raw OOF는 약 0.9236 수준이었고, 3모델 스태킹은 2모델 블렌드보다 오히려 낮았다.

이 결과는 중요한 negative result였다.

앙상블은 모델 수를 늘리는 기술이 아니라 서로 다른 유효한 정보를 합치는 기술이다.

8. 하이퍼파라미터 튜닝에서 배운 시간 관리#

튜닝 설계#

가장 강한 단일 모델인 CatBoost를 Optuna로 튜닝했다.

초기 설정은 다음과 같았다.

SAMPLE_ROWS = 150_000
TUNE_SPLITS = 3
TUNE_ITERATIONS = 800
N_TRIALS = 40

탐색 범위에는 다음이 포함됐다.

  • learning rate
  • depth
  • l2 leaf regularization
  • random strength
  • bagging temperature

시간 추정 실패#

초기에는 전체 실행이 20~40분 정도일 것으로 예상했다. 그러나 trial 13개에 약 56분이 걸렸다.

40개 trial을 모두 실행하면 약 3시간이 필요한 속도였다.

가장 큰 원인은 depth=10까지 허용한 것이었다.

CatBoost의 대칭 트리는 깊이가 증가할수록 리프 수가 지수적으로 늘어난다.

depth 8  → 256 leaves
depth 9  → 512 leaves
depth 10 → 1024 leaves

깊이 10은 깊이 8보다 단순히 25% 느린 것이 아니라 훨씬 더 큰 계산량을 요구할 수 있다.

튜닝 결과#

최적 조합은 대략 다음과 같았다.

{
  "learning_rate": 0.119849,
  "depth": 7,
  "l2_leaf_reg": 6.53864,
  "random_strength": 1.91416,
  "bagging_temperature": 0.145226
}

전체 데이터 재학습 결과 개선폭은 약 +0.000289였다.

튜닝 전 CatBoost OOF
0.949136

튜닝 후 CatBoost OOF
0.949425

무엇을 배웠나#

튜닝 자체보다 더 중요한 관찰은 trial 점수가 매우 좁은 구간에 몰려 있었다는 점이다.

약 0.947 ~ 0.9488

이는 모델이 이미 좋은 영역에 있었고 하이퍼파라미터보다 다른 요소의 개선 여지가 더 크다는 의미였다.

정리된 이해#

튜닝 전에 반드시 한 trial의 시간을 측정해야 한다.

1 trial 실행
→ 평균 시간 계산
→ 최대 시간 예산 결정
→ 탐색 공간 축소
→ 본 실행

그리고 결과 분포가 좁으면 튜닝을 계속 늘리기보다 피처나 검증 구조로 우선순위를 옮겨야 한다.

9. EDA 재검토가 만든 가장 큰 돌파구#

왜 다시 EDA를 했나#

모델과 보정을 여러 번 개선한 뒤 성능이 정체되기 시작했다.

처음에는 피처 엔지니어링의 기대효과를 낮게 봤다. 이미 다른 패키지에서 신호가 크지 않다고 정리돼 있었기 때문이다.

그러나 원본 데이터를 직접 다시 분석하면서 이 판단이 잘못됐음을 확인했다.

Mutual Information 결과#

주요 변수의 Mutual Information은 다음 순서였다.

변수 Mutual Information
sleep_duration 약 0.155
stress_level 약 0.143
physical_activity_level 약 0.056
bmi 약 0.032
exercise_duration 약 0.023
step_count 약 0.022
diet_type 약 0.0002
gender 약 0.0002

수면 시간과 스트레스 수준이 압도적으로 강했고, 식습관 유형과 성별은 이 데이터에서는 거의 신호가 없었다.

stress_level 단독 분포#

스트레스 수준별 클래스 비율에서 매우 강한 구조가 나타났다.

stress=high
→ unhealthy 비율 증가

stress=low
→ fit 비율 증가

stress=medium
→ 대부분 at-risk

특히 medium에서 at-risk 비율이 약 99% 수준이었다.

stress × activity 교차#

stress_level과 physical_activity_level을 결합했을 때 더 강한 패턴이 나타났다.

대표적으로:

low stress + active
→ fit 비율이 크게 증가

high stress + active/moderate/sedentary
→ unhealthy 비율이 증가

medium stress
→ 활동 수준과 관계없이 대부분 at-risk

이 구조는 단일 변수보다 상호작용 피처가 유효할 가능성을 보여줬다.

같은 방식으로 sleep_duration을 기준으로 조건부 신호를 다시 스캔했을 때도 비슷한 패턴이 나타났다. 단일 변수 중요도로는 잘 드러나지 않던 조합이, 조건을 걸고 보면 뚜렷한 임계값 후보로 나타났다.

효과크기#

통계 검정에서는 유의확률만 보지 않고 효과크기를 함께 봤다.

주요 결과:

sleep_duration
ε² ≈ 0.1947
large

stress_level
Cramér's V ≈ 0.3874
medium

데이터가 매우 크면 작은 차이도 통계적으로 유의할 수 있다. 그래서 실제 차이의 크기를 나타내는 효과크기가 더 중요했다.

정리된 이해#

EDA는 모델 전처리 단계에서 한 번 하고 끝나는 작업이 아니다.

초기 EDA
→ 모델 학습
→ 오류 분석
→ 가설 생성
→ 재EDA
→ 피처 실험

모델이 정체될 때 다시 원본으로 돌아가는 것이 가장 큰 돌파구가 될 수 있다.

10. 13개 원본 변수를 30개 피처로 확장한 방식#

원본 피처#

원본 입력은 수치형 7개와 범주형 6개, 총 13개였다.

수치형:

sleep_duration
heart_rate
bmi
calorie_expenditure
step_count
exercise_duration
water_intake

범주형:

diet_type
stress_level
sleep_quality
physical_activity_level
smoking_alcohol
gender

결측 플래그 13개#

각 변수의 결측 여부를 별도 피처로 추가했다.

컬럼별 결측률을 실제로 그려보면 stress_level(12.0%)과 sleep_duration(11.0%)이 가장 많이 비어 있었다. 하필 이 두 변수가 앞서 EDA에서 가장 강한 신호로 확인된 변수였기 때문에, 결측 여부 자체를 버리지 않고 신호로 남기는 것이 더 중요해졌다.

for col in raw_columns:
    X[f"{col}_missing"] = (
        X[col].isna()
    ).astype("int8")

값이 비어 있다는 사실 자체가 측정 환경이나 생활 패턴을 반영할 수 있기 때문이다.

예를 들어 다음 두 상황은 동일하지 않다.

수면시간이 0시간으로 기록됨
수면시간이 측정되지 않음

값을 대체하더라도 관측 여부는 따로 보존해야 했다.

교차 피처 1개#

EDA에서 확인한 스트레스와 활동 수준의 결합을 하나의 범주형 교차 피처로 만들었다.

X["stress_activity"] = (
    X["stress_level"].astype(str)
    + "_"
    + X["physical_activity_level"].astype(str)
)

해석 피처 3개#

도메인 의미를 반영한 파생 피처를 추가했다.

수면 편차#

X["sleep_deviation_8h"] = (
    X["sleep_duration"] - 8.0
).abs()

수면 시간이 많거나 적다는 단순 방향보다 8시간 기준에서 얼마나 벗어났는지를 표현했다.

활동 효율#

X["activity_per_minute"] = (
    X["step_count"]
    / (X["exercise_duration"] + 1.0)
)

걸음 수와 운동 시간을 함께 봐 활동 밀도를 표현했다.

BMI 대비 수분 섭취#

X["hydration_per_bmi"] = (
    X["water_intake"]
    / (X["bmi"] + 1e-6)
)

절대 수분 섭취량만 보지 않고 체격 지표와의 상대적 관계를 표현했다.

최종 계산#

원본 13
+ 결측 플래그 13
+ 교차 피처 1
+ 해석 피처 3
= 최종 30개 피처

중요한 원칙#

피처를 많이 만드는 것이 목적이 아니었다.

각 피처는 다음 절차를 통과해야 했다.

EDA 관찰
→ 가설
→ 피처 생성
→ OOF 비교
→ fold별 안정성 확인
→ 유지 또는 제거

실제로 원본 13개에 파생 피처를 다 얹은 30개 구성과, 신호가 약한 몇 개를 뺀 21개 선택 구성을 반복 교차검증으로 직접 비교했다. 두 구성의 Balanced Accuracy 차이는 오차범위 안이었고, 클래스별 recall도 거의 겹쳤다.

즉 피처를 더 많이 넣는다고 성능이 더 좋아지는 것도, 줄인다고 나빠지는 것도 아니었다. 이 결과를 보고 나서야 “30개를 그대로 쓴다"는 선택이 감이 아니라 확인된 결정이라고 말할 수 있었다.

정리된 이해#

좋은 피처 엔지니어링은 복잡한 수식을 만드는 것이 아니라 모델이 발견하기 어려운 구조를 명시적으로 표현하는 일이다.

11. 최종 모델과 점수 계보#

왜 점수 계보가 필요한가#

실험이 많아지면 어떤 파일이 어떤 모델에서 나왔는지 쉽게 잃어버린다.

그래서 다음을 별도로 저장했다.

  • OOF probability
  • test probability
  • fold ID
  • class mapping
  • 하이퍼파라미터
  • calibration result
  • submission file
  • Public score
  • 실행 시간
  • 실험 설명
  • 채택 여부

주요 단계#

단계 핵심 변화 OOF 또는 Public
초기 제출 잘못된 전체 LabelEncoding Public 0.88188
데이터 타입 수정 수치형 복원, 범주형 분리 Public 0.93365
클래스 보정 1 좁은 grid OOF 약 0.932
보정 확장 Nelder-Mead Public 약 0.945
넓은 보정 nested 검증 Public 약 0.948
CatBoost 추가 강한 단일 모델 OOF 약 0.9494
LGB + CB blend 오류 다양성 결합 Fixed OOF 0.949873
재현 제출 동일 파이프라인 Public 0.95005
대회 최적화 트랙 외부 anchor 및 일부 후처리 Public 0.95113

0.95113을 핵심 모델로 사용하지 않은 이유#

0.95113은 더 높은 Kaggle 표시 점수였다. 그러나 동일한 학습 파이프라인의 순수 산출물이라기보다 외부 anchor와 특정 행 단위 후처리에 의존했다.

이 결과는 대회 실험 기록으로는 가치가 있지만, 다음 기준에는 맞지 않았다.

  • 동일 코드로 재생성 가능한가?
  • 모델 버전과 입력이 명확한가?
  • 서비스에 배포할 수 있는가?
  • 결과를 설명할 수 있는가?
  • 다른 사람이 검증할 수 있는가?

그래서 두 트랙을 분리했다.

Competition track
→ 최고 표시 점수 0.95113

Reproducible core
→ Public 0.95005
→ Fixed OOF 0.949873

최종 선택#

프로젝트의 중심에는 재현 가능한 0.95005를 두었다.

이 선택은 점수를 포기한 것이 아니다.

점수의 출처와 생성 과정을 설명할 수 있는 결과를 선택한 것이다.

이 최종 blend가 실제로 어떤 오류를 남기는지도 fixed OOF로 확인했다.

at-risk 93.5%, fit 94.9%, unhealthy 96.5% — 세 클래스 모두 90%대 초반 이상으로 올라왔고, 초기에 가장 심했던 fit·unhealthy → at-risk 오분류도 각각 4.5%, 3.1%까지 줄었다. 3장에서 시작한 데이터 타입 수정부터 여기까지, 모든 단계가 실제로 이 대각선 숫자를 밀어 올리는 데 기여했다는 걸 눈으로 확인할 수 있는 지점이다.

12. 점수 경쟁을 서비스 설계로 바꾼 리듬ON#

예측 모델만으로는 부족했다#

Kaggle에서는 제출 파일을 만들면 프로젝트가 끝날 수 있다.

하지만 실제 서비스에서는 모델 예측이 행동으로 연결돼야 한다.

이 프로젝트에서 제안한 서비스는 리듬ON이다.

리듬ON은 청소년이 수면, 활동, 스트레스 기록을 확인하고 자신의 생활 리듬을 이해하며 작은 실천을 선택하도록 돕는 앱이다.

서비스 한 문장 정의#

생활 기록에서 변화 신호를 먼저 읽고, 기존 건강지원이 필요한 학생에게 더 적시에 닿도록 돕는다.

중요한 표현 전환#

모델의 출력은 진단이 아니다.

모델 출력
= 건강 상태 확정

이 아니라 다음과 같이 정의했다.

모델 출력
= 담당자가 다시 확인할 검토 후보

이 차이가 서비스의 책임 구조를 바꾼다.

서비스 흐름#

1. 생활 데이터 기록
2. 모델이 상태 확률 계산
3. 기관 담당자가 맥락 검토
4. 참여자가 지원 제안에 동의 또는 거절
5. 리듬ON에서 기록과 작은 행동 시작

상태별 코칭 강도와 비즈니스 액션#

모델의 세 클래스 출력을 그대로 서비스에 옮기면 안 된다는 것도 여기서 정리됐다. fit·at-risk·unhealthy는 진단 등급이 아니라, 코칭 강도와 리소스를 얼마나 투입할지를 정하는 기준으로 다시 번역해야 했다.

  • fit → Free / 유지: 저빈도 체크인, 습관 유지 콘텐츠
  • at-risk → Core 구독: 주 1~2회 코칭, 스트레스·활동 트래킹
  • unhealthy → Premium 개입: 고빈도 모니터링, 전문가 연계 권고

모델은 의료 진단이 아니라 생활습관 기반 웰니스 코칭의 우선순위를 지원하는 도구로만 쓰인다는 원칙은, 이 표를 만든 뒤에야 문장이 아니라 실제 운영 기준으로 자리 잡았다.

참여자 앱#

참여자 화면은 모델 클래스 이름을 직접 통보하는 대신 다음을 제공한다.

  • 오늘의 수면·활동·수분·스트레스 기록
  • 자신의 최근 기록과 익명화된 참고 범위 비교
  • 잘하고 있는 부분
  • 조금 더 관리할 부분
  • 오늘 선택할 한 가지 또는 두 가지 행동
  • 지원 정보 확인
  • 동의와 철회 기능

수면·심박·걸음·운동·수분을 하루치만 가볍게 입력하면, 또래 권장 기준과 나란히 놓고 “조금 더” 정도로만 알려준다. 숫자를 그대로 진단처럼 던지지 않고, 오늘 두 가지만 가볍게 시작해보라고 제안하는 톤을 화면 단계에서부터 지키려 했다.

기관 웹#

기관 담당자 화면은 다음을 제공한다.

  • 전체 변화 추이
  • 검토 대기량
  • 우선 검토 후보
  • 예측 확률
  • 데이터 최신성
  • 검토 사유
  • 승인·수정·보류
  • override 기록
  • 감사 로그

기관 현황 요약, 우선검토 큐, 개별 상세 화면 세 단으로 나눈 것도 의도적이다. 담당자가 전체 추이를 먼저 보고, 검토가 필요한 후보를 우선순위대로 좁힌 뒤, 개별 건에서만 승인·수정·보류를 결정하게 만들어 “일단 다 보고 판단"하는 부담을 줄이려 했다.

정리된 이해#

예측이 서비스가 되는 지점은 정확도 숫자가 아니라 책임이 다음 주체로 인계되는 지점이다.

모델
→ 담당자
→ 참여자
→ 서비스

13. 사람 중심 운영 구조와 안전 경계#

모델이 하지 않는 일#

리듬ON은 다음을 하지 않는다.

  • 의료 진단
  • 자동 지원 대상 확정
  • 자동 앱 설치
  • 개인에게 건강 책임 전가
  • 동의 없는 데이터 연결
  • 검증 전 무분별한 확대

단계 산출물 통제 주체

행동 기록·비교·작은 실천 리듬ON
감사 결정·변경 이력 운영 체계

Human-in-the-loop#

모델은 후보를 제안하지만 담당자가 다음 중 하나를 선택한다.

승인
수정
보류

이 기록은 모델 실패 사례를 발견하는 학습 데이터가 된다.

참여자 선택권#

참여자는 다음 권한을 가져야 한다.

  • 목적 확인
  • 데이터 범위 확인
  • 참여 수락
  • 참여 거절
  • 동의 철회
  • 기록 수정
  • 지원 안내 선택

각 단계에는 로그가 필요하다.

model_version
probability
decision
override_reason
consent_status
invite_expiry

로그는 감시를 강화하기 위한 것이 아니라 누가 어떤 근거로 결정을 내렸는지 추적하기 위한 장치다.

정리된 이해#

안전한 AI 서비스는 모델 정확도 위에 세워지지 않는다.

정확도
+ 사람 검토
+ 동의
+ 철회
+ 감사
+ 중단 기준

이 여섯 요소가 함께 있어야 한다.

파일럿의 목적#

실제 청소년과 기관이 이 흐름을 사용할 수 있는지 제한된 범위에서 검증하는 것이 목표다.

기간 검증 내용
1~2주 데이터 계약, 항목 정의, 동의문, 권한 구조

15. 실패한 시도와 남겨야 할 교훈#

클러스터링 기반 피처#

KMeans 거리와 클러스터 모델을 이용해 경계 사례를 분리하려 했지만, 전체 성능과 어려운 경계 구간에서 오히려 악화됐다.

교훈:

데이터가 군집 구조를 가진다고 해서 그 군집이 타겟 경계와 일치하는 것은 아니다.

XGBoost 추가#

세 번째 모델을 넣으면 앙상블이 더 좋아질 것으로 기대했지만, 3모델 스태킹은 2모델 블렌드보다 낮았다.

교훈:

약한 모델을 추가하는 것은 다양성을 늘리는 것이 아니라 신호를 희석할 수 있다.

과도한 보정#

클래스 가중치 범위를 계속 넓히면 Balanced Accuracy가 일정 구간까지는 올라갔지만, at-risk recall 손실이 커졌다.

교훈:

보정은 성능을 만드는 마법이 아니라 오류 비용의 이동이다.

튜닝 시간 추정#

CatBoost depth 범위를 넓게 잡은 채 40 trial을 실행해 예상보다 몇 배 긴 시간이 걸렸다.

교훈:

탐색 전에 trial 1개의 시간을 측정한다.

다른 자료의 EDA 결론을 그대로 믿은 것#

기존 패키지에서 신호가 약하다고 판단한 내용을 그대로 받아들여 피처 엔지니어링 우선순위를 낮췄다.

직접 EDA를 다시 하자 가장 강한 상호작용이 발견됐다.

교훈:

다른 분석의 결론은 참고 자료이지 원본 데이터에 대한 최종 답이 아니다.

더 높은 점수의 유혹#

0.95113을 프로젝트 대표 점수로 쓰는 것이 더 화려해 보였다. 그러나 재현성과 계보가 약했다.

교훈:

포트폴리오에서 중요한 것은 최고 숫자뿐 아니라 그 숫자의 출처를 설명할 수 있는가이다.

오늘 오후 전체에서 배운 것#

이번 프로젝트는 데이터 분석, 머신러닝, 검증, 실험 관리, 서비스 설계가 서로 분리된 일이 아니라 하나의 연속된 파이프라인이라는 점을 보여줬다.

가장 먼저 데이터 타입 오류를 수정하면서 모델보다 입력 표현이 중요하다는 것을 배웠다. 이후 OOF와 nested 검증을 통해 로컬 점수를 믿을 수 있는 조건을 만들었다. 클래스별 확률 보정에서는 불균형 문제를 단순 class weight 하나로 끝낼 수 없다는 것을 확인했다. CatBoost와 LightGBM을 결합하면서는 단일 성능과 오류 다양성이 서로 다른 기준이라는 것도 배웠다.

가장 큰 전환점은 EDA를 다시 한 것이었다. 이미 다른 분석에서 결론이 나왔다고 생각했던 원본 데이터를 다시 보면서 stress_level × physical_activity_level의 강한 상호작용과 수면 시간의 효과를 찾았다. 이 경험은 모델이 정체됐을 때 더 복잡한 알고리즘으로 가기 전에 원본 데이터로 돌아가야 한다는 교훈을 남겼다.

마지막으로 Kaggle 점수를 서비스로 연결하면서 모델 출력이 곧 행동이 되어서는 안 된다는 원칙을 세웠다. 모델은 신호를 만들고, 담당자는 검토하며, 참여자는 동의하고, 서비스는 작은 행동을 돕는다. 이 책임 분리가 리듬ON의 핵심이다.

다음에 조심할 것#

다음 프로젝트에서는 시작 단계부터 데이터 계약을 먼저 고정해야 한다.

수치형과 범주형, 결측 의미, 타겟 클래스, 평가 지표를 명확히 정의한 뒤 모델을 실행해야 한다. 빠른 실험과 최종 검증도 처음부터 구분해야 한다. 샘플 3-fold 결과와 전체 5-fold OOF를 같은 표에서 직접 비교하면 오해가 생길 수 있으므로 실험 목적을 반드시 기록해야 한다.

하이퍼파라미터 튜닝에서는 trial 하나의 시간을 먼저 측정하고 전체 시간 예산을 계산해야 한다. 앙상블은 모델 수를 늘리는 방향이 아니라 OOF 오류 상관을 분석한 뒤 추가해야 한다. 높은 Public score가 나오더라도 모델 계보와 재현 절차가 불명확하면 core 결과와 분리해야 한다.

서비스 연결에서는 합성 데이터의 분류 성능을 실제 건강 효과로 과장하지 않아야 한다. 진단, 자동 배정, 자동 설치를 금지하고 사람 검토, 명시적 동의, 철회, 감사 로그, 중단 기준을 먼저 설계해야 한다.

점수 뒤에 있었던 하루 — 처음 캐글을 해본 사람의 진짜 후기#

위 18개 챕터는 전부 “무엇을 왜 했는가"의 기록이다. 그런데 이 프로젝트를 실제로 겪은 하루 반나절의 느낌은 표와 숫자 뒤에 거의 남지 않았다. 마지막으로 그 이야기를 조금 더 솔직하게 적어둔다.

시작은 거창하지 않았다. “높은 점수를 받기 위한 코드로 결과물을 만들어내는 것을 해보자"는 말 한마디였다. 이게 나중에 강의 프로젝트라는 것도, 노트북과 비즈니스 액션플랜까지 필요하다는 것도 이 시점엔 전혀 몰랐다. 그냥 순수하게 점수를 올려보자는 마음으로 시작한 하루였다.

실행은 항상 직접 했다. 코드가 바뀔 때마다 배치 파일을 더블클릭하고, 콘솔에 찍히는 로그를 통째로 옮겨서 같이 확인하는 방식이 하루 종일 반복됐다. 첫 보정으로 점수가 오르자 “1.0 가즈아"를 외쳤고, 오후 내내 “0.9999는 가야지"라는 농담을 반복했다. 실제로는 0.951대 근처가 현실적인 천장이라는 답을 들었지만, 그 근거 없는 기대감 자체가 하루를 재미있게 만들었다.

밤에는 CatBoost 학습을 걸어두고 잠들었고, 다음 날 아침은 “일어나자마자 이어서” 시작됐다. XGBoost가 기대만큼 나오지 않았을 때도, 하이퍼파라미터 튜닝이 예상보다 몇 배 오래 걸린다는 걸 알았을 때도 크게 흔들리지 않았다. 그런데 딱 한 번, 진짜 불안했던 순간이 있었다. 스코어가 소폭 개선에 그치자 “이제 이걸로는 더 못 올리는 건가"라는 생각이 든 때였다. 신기하게도 그 불안이 오히려 EDA를 처음부터 다시 보게 만들었고, 그 결과가 이 프로젝트에서 가장 중요한 발견(stress_level × physical_activity_level)으로 이어졌다. 막힌 것 같던 순간이 실제로는 가장 큰 전환점이었다.

작은 사고도 몇 번 있었다. 캐시가 저장되지 않은 것 같아 걱정했던 순간(타임스탬프로 확인하니 멀쩡했다), 스모크 테스트 중 진짜 제출 폴더에 테스트 파일이 잠깐 섞여 들어갔던 일, CatBoost가 결측 범주형 값 때문에 갑자기 에러를 뱉었던 순간. 완벽하게 매끄러운 하루는 아니었지만, 매번 “일단 작게 돌려보고 실제로 나온 숫자만 믿는다"는 원칙 덕분에 큰 사고 없이 넘어갈 수 있었다.

최종 제출에서 Public LB 0.95005와 “Your Best Entry!” 배지, 랭킹 364등을 확인했을 때는 “이 정도면 충분하다, 수고했다"는 말이 자연스럽게 나왔다. 그런데 여기서 끝이 아니었다. 결과를 정리해달라는 요청 중에 이게 사실 강의 과제였고, 노트북과 비즈니스 액션플랜까지 필요하다는 게 뒤늦게 드러났다. 처음 제출한 노트북은 강사님 기준을 완전히 충족하지 못했다는 피드백을 받았다. Pipeline 함수, ConfusionMatrixDisplay, SHAP 해석이 빠져 있다는 지적이었다. 그래서 아래처럼 SHAP 기반 피처 기여도 분석을 뒤늦게 추가했다.

흥미롭게도 이 SHAP 결과는 앞서 Mutual Information으로 찾은 sleep_duration·stress_level 우선순위와 완전히 같지는 않았다. unhealthy 예측 하나만 놓고 보면 bmi가 가장 큰 기여를 했다. 전역 신호를 보는 방법과 개별 예측 기여를 보는 방법이 서로 다른 답을 줄 수 있다는 걸, 설명 자료를 억지로 끼워 맞추다가 몸으로 확인한 셈이다.

처음 Kaggle을 해보는 입장에서 이 프로젝트가 남긴 것은 점수도, 모델 이름도 아니었다. 오히려 숫자 하나에 흥분하고, 정체됐을 때 잠깐 불안해하고, 다시 데이터로 돌아가고, 뒤늦게 드러난 요구사항까지 다시 채워서 끝까지 완주한 그 하루 반나절의 과정 자체가 가장 크게 남았다. 다음 프로젝트에서는 이 경험을 발판 삼아, 시작 단계에서부터 데이터 계약과 평가 지표, 그리고 최종 산출물 형태까지 먼저 확인하고 들어가고 싶다.
