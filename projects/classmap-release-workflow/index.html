1. GitHub 레포 생성#

왜 이걸 보게 됐나#

classmap-hanthink 프로젝트 릴리스 과정에서 GitHub 레포지토리를 만들고 관리하는 기본적인 과정이 막막하게 느껴졌어요. 특히 로컬 저장소와 원격 저장소를 연결하는 방법을 제대로 이해하지 못해 푸시 과정에서 오류가 발생했고, 이 문제를 해결하면서 GitHub 레포 생성 및 연결 과정을 익히게 됐습니다. 이 경험을 통해 협업 환경에서 필수적인 Git 사용법의 기초를 다지게 되었습니다.

내가 헷갈린 지점#

처음 GitHub 레포지토리를 만들 때 git init만 하면 자동으로 원격 저장소가 만들어지는 줄 알았는데, 로컬 저장소만 생성되고 별도로 웹에서 레포를 만들어야 한다는 것을 깨달았습니다. 또한, 이미 초기 커밋이 있는 원격 저장소에 main 브랜치를 푸시할 때 바로 실패할 거라고 예상하지 못해서 당황했습니다.

시도한 코드 / 예시#

# GitHub 레포 생성 예시
# GitHub 웹사이트에서 새로운 레포지토리를 생성 후, 로컬 저장소와 연결합니다.
# <GitHub_URL> 은 생성된 레포지토리의 URL로 대체합니다.
git remote add origin <GitHub_URL>

결과와 해석#

처음에는 git init 명령어가 GitHub 저장소를 만들어 줄 거라고 생각했지만, 로컬 저장소만 생성되고 웹사이트에서 새로운 레포지토리를 만들어야 한다는 걸 깨달았습니다. GitHub 웹사이트에서 레포지토리를 만든 후 git remote add origin <GitHub_URL> 명령어로 로컬 저장소를 원격 저장소와 연결하는 과정을 통해 실질적인 레포 생성 방법을 익혔습니다.

정리된 이해#

GitHub 레포지토리는 로컬 저장소를 만든 후 웹사이트에서 직접 생성해야 하고, 로컬 저장소와 연결해야 원격 저장소에 코드를 올릴 수 있습니다. git init은 로컬 저장소를 만드는 명령어일 뿐, GitHub에 실제 레포지토리를 생성하는 것이 아니라는 점을 명확히 이해해야 합니다.

2. 메인 브랜치 푸시#

왜 이걸 보게 됐나#

처음에는 GitHub에 코드를 올릴 때 로컬 저장소만 만들면 된다고 생각했는데, main 브랜치를 원격 저장소에 푸시하는 과정에서 오류가 발생하면서 원격 저장소 연결 및 푸시 방식에 대한 이해가 필요하다는 것을 알게 됐어. 특히 기존 커밋이 있는 원격 저장소에 새로운 코드를 푸시할 때 어떻게 해야 하는지, 그리고 force push는 어떤 상황에서 사용해야 하는지 배우게 됐지.

내가 헷갈린 지점#

처음에는 로컬 저장소를 만든다고 해서 GitHub 레포지토리가 바로 생성되는 줄 알았습니다. 그래서 커밋 후 바로 git push를 시도했는데, 이미 원격 저장소에 초기 커밋이 있다는 이유로 푸시가 거절되는 상황에 당황했습니다. 좀 더 명확하게는, 로컬과 원격 저장소의 관계를 완전히 이해하지 못하고 있었던 것 같습니다.

시도한 코드 / 예시#

git push -u origin main --force

결과와 해석#

처음 git push를 할 때 main 브랜치 푸시가 거절되어 당황했는데, 기존 커밋이 이미 원격 저장소에 있기 때문이었습니다. git push -u origin main --force 명령어를 사용하여 강제로 푸시했지만, 이후에 다른 개발자와 협업할 때는 force push가 문제를 일으킬 수 있다는 점을 기억해야 합니다.

정리된 이해#

처음에는 로컬 저장소 생성만으로는 원격 저장소가 만들어지는 줄 알았지만, GitHub 웹사이트에서 레포지토리를 만들고 로컬 저장소와 연결해야 한다는 것을 깨달았습니다. 기존 커밋이 있는 원격 저장소에 main 브랜치를 푸시할 때는 강제 푸시를 신중하게 사용해야 하며, 버전 정보와 관련된 여러 요소들이 일관성을 유지하는 것이 중요합니다.

3. PyPI 역할#

왜 이걸 보게 됐나#

프로젝트를 배포하는 과정에서 패키지를 실제로 설치할 수 있도록 하는 곳이 필요해서 PyPI의 역할을 알게 됐어. classmap-hanthink 프로젝트를 PyPI에 올리려고 할 때, 관련된 명령어를 제대로 사용하지 못해서 오류가 발생했고, 그 과정에서 PyPI가 어떤 역할을 하는지 명확히 이해하게 됐지. 결국 패키지 배포를 성공시키기 위해서는 이 부분을 반드시 알아야 했어.

내가 헷갈린 지점#

PyPI가 단순히 코드 저장소를 생각하고 있었는데, 실제로 설치 가능한 패키지를 배포하는 역할이라는 것을 뒤늦게 알게 되었습니다. 소스 코드 관리에는 GitHub를 쓰고, 최종적으로 사용자가 설치할 수 있는 패키지를 만드는 곳이 PyPI라는 개념이 처음에는 잘 연결되지 않았습니다. 특히 twine을 사용해야 한다는 점을 놓쳐서 PyPI의 역할을 더욱 명확하게 이해하게 되었습니다.

시도한 코드 / 예시#

# classmap-hanthink CLI 사용법 예시
# 기본 출력
# $ classmap examples/sample_classes.py

# 외부 base class 표시
# $ classmap examples/sample_classes.py --show-external

결과와 해석#

PyPI는 내가 만든 파이썬 패키지를 다른 사람들이 쉽게 설치해서 사용할 수 있도록 배포하는 저장소 역할을 해. twine이라는 도구를 이용해서 dist 폴더에 만들어진 패키지 파일을 PyPI 서버에 업로드하는 과정을 거치게 되는데, 이 과정에서 버전 정보가 일치하는지 확인하는 것이 중요해. PyPI에 올린 패키지는 pip 명령어를 통해 다른 사람들이 설치할 수 있게 돼.

정리된 이해#

PyPI는 개발자들이 만든 파이썬 패키지들을 배포하는 저장소 역할을 합니다. 마치 앱 스토어처럼, 다른 사람들이 쉽게 우리 코드를 다운로드하여 사용할 수 있도록 해주는 곳이죠. 따라서 우리 프로젝트를 다른 사람들이 설치할 수 있도록 하려면 PyPI에 패키지를 업로드해야 합니다.

4. Git 명령어#

왜 이걸 보게 됐나#

이전에는 코드 변경 사항을 관리하고 협업하는 방식이 명확하지 않아 혼란스러웠다. classmap-hanthink 프로젝트 릴리스 과정에서 GitHub를 통한 버전 관리와 PyPI 배포를 직접 경험하며 Git 명령어의 필요성을 절감하게 되었고, 소스 코드 관리와 배포 프로세스 이해를 위해 학습하게 되었다. 이제는 코드 변경 이력을 체계적으로 관리하고 다른 사람과 함께 프로젝트를 진행할 때 필요한 기본적인 지식을 갖추고자 한다.

내가 헷갈린 지점#

git init 명령어가 저장소를 웹에 바로 생성해주는 줄 알았는데, 로컬 저장소만 만들어주는 것 같아서 당황했었어. 또, v0.1.0 태그를 만들고 푸시하려니까 거절당해서, 왜인지 몰랐다가 원격 저장소에 이미 초기 커밋이 있었다는 걸 알고 나서 어떻게 해결해야 할지 검색했지. Git에 익숙하지 않아서 푸시 과정에서 문제가 발생할까 봐 계속 조심스러웠어.

시도한 코드 / 예시#

# classmap-hanthink CLI 사용법 예시
# 기본 출력
# $ classmap examples/sample_classes.py

# 외부 base class 표시
# $ classmap examples/sample_classes.py --show-external

결과와 해석#

git init은 로컬 저장소를 만드는 명령어인데, GitHub에 레포지토리를 만드는 건 아니어서 별도로 웹에서 레포지토리를 생성하고 로컬 저장소와 연결해야 했어. git push --force는 기존 커밋이 있을 때 초기 브랜치를 푸시할 수 있게 해줬지만, 다른 사람의 작업에 영향을 줄 수 있으니 주의해야겠어. twine을 프로젝트에 설치하지 않아서 PyPI 업로드에 실패했는데, 임시로 실행하는 방법으로 문제를 해결했지만, 앞으로는 프로젝트에 확실히 설치해야겠어.

정리된 이해#

Git 명령어는 로컬 저장소를 생성하는 것 외에 원격 저장소를 GitHub 웹사이트에서 만들어 로컬 저장소와 연결해야 하고, 이미 원격 저장소가 존재하는 경우 강제 푸시를 해야 할 수 있다는 것을 알게 되었다. 특히 Git 태그는 버전 관리에 중요하며, 이와 관련된 정보는 PyPI 업로드 과정에서도 일관성을 유지해야 한다는 점을 명확히 이해하게 되었다.

총평#

오늘 전체에서 배운 것#

GitHub 레포지토리를 생성하고 메인 브랜치를 푸시하는 과정에서, 로컬 저장소 초기화와 원격 저장소 연결을 명확히 구분해야 한다는 것을 알게 되었습니다. 또한, PyPI를 통해 패키지를 배포하려면 twine을 설치하고 관련 정보들이 일관성을 유지하는 것이 중요하다는 것을 깨달았습니다.

다음에 조심할 것#

GitHub 레포 생성 시 로컬 저장소와 원격 저장소를 혼동하지 않도록 주의해야겠다. force push는 정말 필요한 경우에만 사용하고, 다른 사람에게 영향을 줄 수 있다는 것을 항상 염두에 두어야겠다. PyPI 업로드 전에 필요한 도구가 설치되어 있는지 다시 한번 확인하는 습관을 들여야겠다.

다음 복습 주제#

--force push 사용 시 발생할 수 있는 문제점과 안전한 대안을 좀 더 깊이 알아봐야겠다. PyPI 패키지 배포 과정에서 자동화된 CI/CD 파이프라인 구축 방법을 학습하고 싶다.
