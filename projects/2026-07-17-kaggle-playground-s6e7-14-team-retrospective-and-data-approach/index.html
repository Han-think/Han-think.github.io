팀 프로젝트가 개인 실험과 달랐던 점#

개인 실험에서는 원하는 만큼 모델을 바꾸고, 실패를 추적하고, 한 행의 예측까지 파고들 수 있었다. 팀 프로젝트에서는 그 결과를 다른 사람이 이해하고 검토할 수 있는 구조로 바꿔야 했다.

팀원들과 역할을 나눠 진행하면서 네 종류의 질문을 동시에 다뤘다.

  1. 분석 질문: 어떤 생활습관 신호가 상태와 함께 달라지는가?
  2. 모델 질문: 어떤 후보가 반복 검증에서도 성능을 유지하는가?
  3. 서비스 질문: 모델의 출력을 누가 보고 어떤 행동으로 바꾸는가?
  4. 책임 질문: 잘못됐을 때 누가 수정하고 중단할 수 있는가?

하나만 잘해서는 발표자료가 완성되지 않았다. 분석이 좋아도 서비스의 결정 주체가 없으면 적용할 수 없고, 화면이 좋아도 데이터와 검증 근거가 없으면 아이디어에 머문다.

함께 만들며 좋아진 네 가지#

1. 결과보다 근거의 계보가 선명해졌다#

팀 발표자료를 준비하며 0.95005와 0.95113을 같은 종류의 점수처럼 말할 수 없다는 결론에 도달했다.

  • 0.95005: 전체 학습 데이터와 고정 OOF로 다시 만들 수 있는 분석 코어
  • 0.95113: 외부 anchor와 특정 행 수정으로 얻은 대회 최적화 기록

둘 다 공개하되 사용 목적을 분리했다. 이 구분 덕분에 높은 점수를 포기한 것이 아니라, 설명·검증·운영 가능한 근거를 제품 기준으로 선택했다고 말할 수 있었다.

2. 완료와 제안을 구분했다#

완료된 것은 합성 데이터 분석, 모델 비교, OOF, Kaggle Public 확인이다. 기관 웹, 참여자 앱, 실제 지원 효과는 아직 제안과 프로토타입이다.

발표자료에서 [완료], [제안], 실사용 미검증을 분리하자 과장된 표현이 줄었다. 무엇을 이미 증명했고 무엇을 앞으로 확인해야 하는지가 훨씬 명확해졌다.

3. 모델 밖의 실패 조건을 보게 됐다#

개인 실험에서는 OOF 하락이나 Public 하락이 실패였다. 서비스 제안에서는 다음도 실패다.

  • 담당자가 검토할 시간이 너무 오래 걸림
  • 특정 집단의 recall이 크게 낮음
  • 참여자가 데이터 범위를 이해하지 못함
  • 거절하거나 철회하기 어려움
  • 결정 사유와 변경 기록이 남지 않음

정확도만으로 성공을 정의하면 이런 문제를 놓친다.

4. 발표자료 제작이 분석의 마지막 검증이 됐다#

팀원들과 결과를 설명하는 과정에서 불명확한 수치와 연결이 드러났다. 왜 이 모델인가, 왜 이 점수를 쓰는가, 누가 최종 결정하는가에 한 문장으로 답하지 못하면 분석이나 서비스 흐름을 다시 확인했다.

발표자료 제작은 결과를 예쁘게 포장하는 마지막 단계가 아니라, 전체 논리가 실제로 이어지는지 확인하는 최종 통합 테스트였다.

아쉬웠던 점과 남은 한계#

이번 프로젝트에는 분명한 한계가 있다.

  • Kaggle 데이터는 실제 청소년 기관의 운영 데이터가 아니라 합성 데이터다.
  • Public 점수는 건강지원 효과를 뜻하지 않는다.
  • 보호 집단별 공정성을 판단할 충분한 정보가 없다.
  • 결측이 실제 환경에서 같은 의미를 갖는지 알 수 없다.
  • 앱 참여가 생활습관 변화로 이어지는지 검증하지 않았다.
  • 개인정보 보호, 접근 권한, 보안 운영을 구현하지 않았다.

따라서 최종 결과는 완성된 건강 서비스가 아니다. 재현 가능한 분석을 책임 있는 지원 흐름으로 연결해 볼 수 있다는 파일럿 제안이다.

또한 팀 프로젝트의 모든 작업을 한 사람이 한 것처럼 기록하지 않는다. 개인 실험에서 만든 근거가 일부 포함됐지만, 최종 문제 정의와 서비스 흐름, 발표자료 구조는 팀원들과 검토하고 다듬은 공동 결과다.

처음 보는 데이터를 받았을 때의 접근 순서#

이번 경험을 바탕으로 새 데이터를 받았을 때 사용할 절차를 다음처럼 정리했다.

1. 목적과 결정 주체부터 적는다#

예측 대상보다 먼저 이 결과로 누가 무엇을 결정하는가를 쓴다. 같은 분류 문제라도 자동 처리, 담당자 검토, 단순 참고는 필요한 오류 기준이 다르다.

2. 데이터 계약을 만든다#

  • 행과 열의 의미
  • 수치형·범주형 구분
  • 목표값과 클래스 정의
  • 결측과 중복
  • 시간 기준과 누출 가능성
  • 학습·검증·테스트 분리

코드를 쓰기 전에 이 표를 만들면 잘못된 가정을 빨리 찾을 수 있다.

3. 지표의 비용을 계산한다#

Accuracy, F1, Balanced Accuracy는 같은 모델을 다르게 평가한다. 클래스 불균형이 있다면 각 클래스 recall과 오분류 비용을 함께 본다.

이번 문제에서는 다수 클래스가 약 85.9%였기 때문에 일반 Accuracy만 보면 소수 상태를 놓치는 모델도 좋아 보일 수 있었다. 그래서 클래스별 recall을 같은 비중으로 평균하는 Balanced Accuracy를 사용했다.

4. 단순 기준선을 먼저 만든다#

복잡한 모델보다 먼저 다음을 확인한다.

  • 다수 클래스 기준
  • 단순 선형 모델
  • 트리 기반 기준 모델
  • 고정된 교차검증
  • seed와 fold 기록

기준선이 있어야 새 피처나 모델의 이득을 말할 수 있다.

5. 탐색과 확인을 분리한다#

탐색에 사용한 fold에서 threshold, 피처, seed를 계속 고르면 점수가 낙관적으로 변한다. 후보를 고른 뒤에는 새 fold, 독립 표본, 전체 OOF 중 하나에서 다시 확인한다.

탐색 -> 후보 고정 -> 독립 확인 -> 전체 OOF -> 외부 확인

6. 최종 소비자를 평가한다#

단독 CatBoost를 개선했더라도 실제 제출이 LightGBM과의 Blend라면 Blend 점수로 판단한다. 피처가 한 모델에서 좋아도 최종 파이프라인에서 나빠질 수 있다.

7. 성공과 실패를 같은 형식으로 남긴다#

각 실험에는 다음을 기록한다.

  • 가설
  • 변경한 한 가지
  • 데이터와 fold
  • 기준 점수
  • 결과 점수
  • 클래스별 변화
  • 채택·기각 이유
  • 산출물 경로와 hash

실패를 지우지 않아야 같은 시도를 반복하지 않는다.

8. 적용 경계를 따로 검토한다#

모델 점수와 실제 적용 가능성은 별도 문제다.

  • 자동 결정해도 되는가?
  • 사람이 다시 봐야 하는가?
  • 당사자의 동의가 필요한가?
  • 잘못된 결정은 되돌릴 수 있는가?
  • 중단 조건과 감사 로그가 있는가?

실험을 멈추고 결론을 만드는 기준#

더 많은 실험이 항상 더 좋은 결론을 만들지는 않는다. 이번 프로젝트에서는 다음 조건이 겹칠 때 탐색을 멈추는 편이 낫다는 것을 배웠다.

  • 새 후보가 독립 확인에서 반복해서 이기지 못한다.
  • OOF 이득이 최종 Blend에서 사라진다.
  • Public 표시점수만 같아 변경의 효과를 식별할 수 없다.
  • 추가 실행 비용이 기대 개선보다 크다.
  • 이미 재현 가능한 기준선이 문제 해결에 충분하다.

멈춘 뒤에는 최고점만 남기지 않고 채택한 코어, 기각한 후보, 미실행 후보, 남은 한계를 함께 정리한다. 그래야 다음 프로젝트에서 처음부터 같은 길을 다시 걷지 않는다.

총평#

이번 팀 프로젝트에서 확인한 것은 합성 데이터에서 건강 상태를 분류할 가능성이다. 아직 확인하지 않은 것은 이 분석이 실제 청소년에게 안전하고 유용한 지원으로 이어지는가이다.

그래서 팀의 최종 선택은 다음과 같다.

  • 대회 최고점 0.95113은 대회 기록으로 남긴다.
  • 재현 가능한 0.95005 코어를 파일럿 근거로 사용한다.
  • 모델은 검토 후보만 제안한다.
  • 담당자가 맥락을 확인하고 사유를 기록한다.
  • 참여자가 동의, 거절, 철회를 선택한다.
  • 작은 파일럿에서 성능, 공정성, 운영, 동의를 함께 검증한다.

처음에는 모델 점수를 올리는 프로젝트로 시작했다. 마지막에는 점수를 어디까지 믿고, 누구에게 책임을 넘기며, 언제 멈출 것인가를 설계하는 프로젝트가 됐다.

팀원들과 함께 만든 가장 중요한 결과는 높은 숫자 하나가 아니라, 분석을 사람의 선택과 책임에 연결하는 기준이었다.
