관리자 운영 기능과 목표#

관리자 화면은 개발자가 코드를 수정하는 화면이 아니다. 프로젝트에서는 안내 자료의 원문·출처·확인일·시행일·사용 상태를 검토하고, 설명을 수정하거나 사용을 중지하며, 변경 이유와 이전·새 값을 이력으로 남기는 흐름을 구성했다.

수정 결과는 같은 서버의 로컬 SQLite에 저장되어 다음 조회부터 반영된다. 이 데이터는 Git을 통해 다른 팀원의 PC와 자동 동기화되는 운영 DB가 아니다. 사용자는 이미 열어 둔 결과가 바뀌지 않을 수 있어 다시 조회해야 한다. 따라서 관리자 기능을 설명할 때는 변경이 저장되는 위치와 적용 범위를 함께 말해야 한다.

실제 비밀번호나 키는 발표자료·스크린샷·공개 글에 넣지 않았다. 공개 예제에서는 변수 이름과 가짜 값만 보여주고, 각자 로컬 환경에서 설정해야 한다.

논리 ERD와 실제 DB 구조#

발표의 ERD는 서비스에서 필요한 데이터 관계를 설명하는 논리 그림이다. 후보, 생활권, 데이터 출처, 운영 기록처럼 개념을 넓게 표현할 수 있다. 하지만 그림에 엔터티가 11개 있다고 실제 SQLite에 테이블도 11개 있다는 뜻은 아니다.

제출 코드의 실제 SQLite에는 records, history, seeds 세 테이블이 있다. records는 종류별 현재 자료, history는 수정 전후와 이유, seeds는 초기 입력 여부를 관리한다. 논리 ERD는 향후 정규화한 DB 설계를 설명하는 자료이고, 실제 구현은 현재 코드에서 작동하는 구조라고 분리해야 했다.

확인된 기능과 검증 결과#

로컬 브라우저에서 사진 후보, 사용자 품목·규격 선택, 참고 금액 조회, 관리자 로그인, 자료 수정과 반영, 원복, 한국어 이력을 확인했다. 별도 HTTP 점검과 관리자 임시 DB 검사, RAG 핵심 검사도 수행했다.

이 숫자는 기능 계약이나 정해 둔 입력 검사의 결과다. 팀원이 처음 보는 질문으로 독립 평가한 결과, 현장에서 거점이 안전하다고 확인한 결과, 실제 주민이 이용한 결과와는 다르다. RAG의 14개 고정 질문도 전체 민원 질문을 대표하지 않으며, 반복 평가를 일반 정확도나 환각률로 바꾸면 안 된다.

제안 거점의 현장 안전과 부지 사용, 실제 수거차 운행, 거점별 실측 폐기물량, 예약·결제의 자체 처리, 다른 PC에서의 독립 실행은 이번 제출이 자동으로 증명하지 않는다. 필요한 협의·자료·장비를 확보한 뒤 별도로 확인해야 한다.

남은 운영 한계와 다음 단계#

이번 팀 프로젝트는 정해진 발표와 산출물을 제출했다. 그렇다고 양천구의 공식 수거 체계를 바꾸거나, 주민에게 실제 운영 거점을 확정해 안내하거나, 기관 시스템과 연동한 것은 아니다. 웹은 분석 결과를 보여주는 제안형 시제품이다.

이 경계를 명확히 하는 것이 프로젝트를 작게 보이게 하지 않았다. 오히려 무엇을 이미 만들었고, 무엇을 데이터·현장·기관 협의와 함께 해야 하는지 구체적으로 보이게 했다.

이번 편의 정리#

관리자 기능, ERD, 테스트 결과는 서로 다른 수준의 근거다. 화면에서 수정이 작동했다는 것과 실제 운영자가 여러 PC에서 장기적으로 서비스를 운영한다는 것은 다른 목표다.

이제 팀 제출 범위를 정리했으니, 다음 두 편에서는 내가 개인 통합판 C에서 더 완성하고 싶은 부분을 나누어 기록한다.
