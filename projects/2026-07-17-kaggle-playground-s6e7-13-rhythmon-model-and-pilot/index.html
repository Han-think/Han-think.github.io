Kaggle Playground S6E7 팀 프로젝트 - 13. 재현 모델과 리듬ON 파일럿 설계

팀 프로젝트에서 최고 표시점수와 재현 가능한 모델을 분리하고, 담당자 검토와 참여자 동의를 포함한 리듬ON 파일럿을 설계한 과정.
2026년 7월 17일 · 4 min

팀 프로젝트의 최종 선택은 가장 높은 표시점수를 제품에 붙이는 것이 아니었다. 다시 실행할 수 있는 분석 코어와 사람이 책임지는 운영 흐름을 함께 선택하는 일이었다.

목차#

  • 최고점과 제품 근거를 분리하다
  • 재현 가능한 모델을 고른 과정
  • 모델은 검토 후보까지만 제안한다
  • 리듬ON에서 참여자가 갖는 선택권
  • 8주 파일럿의 검증 게이트
  • 확대보다 중단 조건이 먼저다
  • 총평

최고점과 제품 근거를 분리하다#

개인 실험에서 Public 최고점은 0.95113이었다. 그러나 이 점수는 외부 anchor에 특정 행을 수정해 만든 대회 최적화 결과였다. 성과로는 남길 수 있지만, 같은 학습 파이프라인을 다시 실행해 얻는 모델은 아니었다.

팀 프로젝트에서는 두 점수의 역할을 분리했다.

구분 핵심 수치 사용 목적
재현 코어 Public 0.95005 파일럿 분석 근거
고정 전체 OOF 0.949873 내부 재현성 확인
Nested OOF 0.949763 선택 편향 점검
대회 최적화 Public 0.95113 별도 대회 기록

0.95113을 숨기거나 실패로 처리한 것이 아니다. 검증 조건이 다른 결과를 한 줄에 섞지 않은 것이다. 최종 발표자료에서는 0.95005를 중심에 두고 0.95113은 별도 기록으로 분리했다.

재현 가능한 모델을 고른 과정#

최종 모델을 고르는 과정은 다음 단계로 나뉘었다.

  1. Screen: 공통 조건에서 여러 모델을 빠르게 비교해 후보를 줄였다.
  2. Probe: 피처, 보정, 조합이 반복해서 이득을 내는지 확인했다.
  3. Confirm: 탐색에 쓰지 않은 fold나 독립 표본에서 다시 확인했다.
  4. Full OOF: 전체 690,088행의 5-fold OOF로 최종 선택했다.
  5. Public: Kaggle 점수로 외부 결과를 확인했다.

빠른 13개 모델 비교에서는 HistGradientBoosting이 0.9014로 가장 높았고 CatBoost는 0.8964였다. 하지만 quick screen은 50k 표본과 3-fold 중심의 후보 압축 단계였다. 최종 선택은 전체 데이터와 고정된 5-fold OOF에서 다시 했다.

최종 코어의 역할은 다음과 같았다.

  • CatBoost OOF 0.949408: 주력 성능
  • LightGBM OOF 0.922927: 다른 오류 패턴
  • 보정 Blend fixed OOF 0.949873: 두 모델의 오류 상쇄와 클래스별 결정 보정

단독 점수가 더 낮은 LightGBM도 최종 조합에서는 가치가 있었다. 좋은 앙상블은 강한 모델만 모으는 것이 아니라 서로 다르게 틀리는 모델을 결합하는 과정이라는 점을 다시 확인했다.

모델은 검토 후보까지만 제안한다#

서비스에서 모델이 담당하는 범위는 상태 확률과 검토 우선순위까지다. 이후 결정은 기관 담당자에게 넘어간다.

기관용 화면은 누구를 지원할 것인가를 자동 결정하는 대시보드가 아니다. 데이터 최신성, 상태 확률, 근거, 이전 검토 이력을 보고 누구를 먼저 다시 살펴볼 것인가를 정하는 화면이다.

담당자는 다음 선택을 할 수 있어야 한다.

  • 승인: 지원 안내가 필요하다고 판단
  • 수정: 모델이 놓친 맥락을 반영
  • 보류: 정보가 부족하거나 시점이 적절하지 않음
  • 사유 기록: 나중에 결정 과정을 감사할 수 있도록 보존

모델은 우선순위를 만들 수 있지만, 학생의 상황을 최종 판단할 수 없다. 이 책임 경계가 있어야 오분류가 곧바로 실제 개입으로 이어지는 위험을 막을 수 있다.

리듬ON에서 참여자가 갖는 선택권#

담당자의 검토가 끝나도 앱 연결은 자동으로 시작되지 않는다. 참여자는 목적과 데이터 범위를 확인한 뒤 동의, 거절, 철회를 선택한다.

리듬ON 앱의 역할은 상태 라벨을 통보하는 것이 아니다.

  • 수면, 활동, 스트레스 기록을 직접 확인하고 수정한다.
  • 센서값만으로 설명되지 않는 오늘의 맥락을 남긴다.
  • 현재 기록과 참고 기준을 이해하기 쉽게 비교한다.
  • 한 번에 한두 개의 작은 행동만 제안한다.
  • 목표는 참여자가 직접 선택하고 확정한다.

이 구조에서는 입력한 건강 기록이 바로 공개되거나 자동 지원으로 연결되지 않는다. 데이터는 참여자에게 먼저 피드백을 주고, 필요한 범위에서만 담당자 검토와 후속 상담의 맥락으로 사용된다.

8주 파일럿의 검증 게이트#

현재 리듬ON은 완성된 서비스가 아니라 검증할 제안이다. 그래서 팀원들과 8주 파일럿을 기능 개발 일정이 아니라 의사결정 게이트로 설계했다.

기간 확인할 것 실패 시
1~2주 데이터 계약, 수집 범위, 동의문 범위 재정의 또는 보류
3주 실제 개입 없는 shadow scoring 성능·drift 점검
4주 담당자 웹 검토와 사유 기록 화면·업무 흐름 수정
5~6주 동의한 소규모 참여자 앱 초대 초대 범위 축소
7~8주 KPI, 철회, 오류, 감사 로그 확대·수정·중단 결정

모델 KPI만으로는 파일럿을 평가할 수 없다.

  • 상태별 recall과 Balanced Accuracy
  • calibration과 drift
  • 보호 집단별 성능 차이
  • 데이터 최신성과 결측 패턴
  • 담당자 override 비율
  • 검토 시간과 불필요한 제안
  • 참여자의 동의, 거절, 철회
  • 결정과 변경의 감사 로그

정확도가 높아도 공정성, 동의, 보안, 운영 시간이 기준을 통과하지 못하면 확대하지 않는다.

확대보다 중단 조건이 먼저다#

이 프로젝트가 최종적으로 제안한 것은 전면 출시가 아니다. 담당자 검토형 소규모 파일럿이다.

Go 조건

  • 같은 조건에서 재현 코어를 다시 확인한다.
  • 담당자가 승인·수정·보류 사유를 기록한다.
  • 참여자의 명시적 동의와 철회를 보장한다.
  • 모든 결정과 변경을 감사할 수 있다.
  • 성능, 공정성, 검토 시간 KPI가 함께 통과한다.

No-go 조건

  • 모델 결과를 의료 진단처럼 사용한다.
  • 점수만으로 지원 대상을 자동 배정한다.
  • 동의 없이 앱이나 정보를 연결한다.
  • 보안 또는 개인정보 보호 기준을 위반한다.
  • 특정 집단의 성능 저하를 설명하거나 줄이지 못한다.

팀 프로젝트의 결론은 정확도가 높으니 출시한다가 아니었다. 분류 가능성은 확인했으니, 이제 사람을 실제로 도울 수 있는지 작은 범위에서 검증한다는 것이었다.

총평#

재현 가능한 모델을 고르는 일과 책임 있는 서비스를 설계하는 일은 따로 떨어져 있지 않았다. 다시 만들 수 없는 높은 점수는 제품 근거가 되기 어렵고, 사람의 검토와 참여자의 선택이 없는 정확한 모델은 안전한 지원 흐름이 되기 어렵다.

팀원들과 함께 선택한 것은 0.95005라는 숫자 하나가 아니라, 그 숫자를 같은 조건에서 다시 확인하고 필요하면 멈출 수 있는 파일럿 구조였다.
