LearningLog와 TableCard — 학습 기록을 프로젝트 구조로 만드는 법

수업 노트, PDF, 대화 기록이 쌓여도 흘려보내지 않기 위해 만든 학습 파이프라인. LearningLog와 TableCard의 역할 분리, 그리고 상태 장부 시스템에 대한 기록.
2026년 5월 28일 · 3 min

왜 폴더를 두 개로 나눴는가#

처음에는 TableCard 하나에 다 넣으면 될 것 같았다.

TableCard는 내가 만들고 있는 인간-AI 협업 방법론 구조다. 카드 기반 작업 분해, 외부 기억, 검증 게이트 같은 개념을 담고 있다.

여기에 수업 정리, 블로그 초안까지 전부 넣었더니 문제가 생겼다.

TableCard가 “내 수업 기록함"이 되어버렸다. 범용 방법론이 아니라 오늘 강의 노트 저장소가 된 것이다.

그래서 분리했다.

TableCard와 LearningLog의 역할 차이#

TableCard = 방법론 엔진#

TableCard가 다루는 질문:

작업을 어떻게 나눌 것인가?
AI는 어떤 역할을 맡는가?
인간은 어디서 판단하는가?
파일 시스템이 어떻게 외부 기억이 되는가?

이건 특정 수업 주제와 무관하다. Python을 배우든, 소설을 쓰든, 이 질문은 같다.

LearningLog = 콘텐츠 처리 공장#

LearningLog가 다루는 질문:

내가 오늘 뭘 배웠는가?
어디서 헷갈렸는가?
어떻게 다시 이해했는가?
블로그에 올릴 수 있는가?

이건 실제 학습 콘텐츠의 문제다.

학습 콘텐츠가 흘러가는 경로#

수업 자료나 대화 기록이 들어오면 이런 흐름으로 처리된다.

00_inbox (원본 투입)
→ 01_registry (등록 및 상태 관리)
→ 02_extracted (원본 기반 사실 추출)
→ 03_working_notes (내 이해 + 해석 포함)
→ 04_blog_drafts (Hugo 초안)
→ 05_ready_to_publish (검토 완료)
→ blog-source (명시 승인 후 이동)
→ 06_published (발행 기록)
→ 07_archive (소스 보관)

각 단계는 상태 장부(CSV)로 추적된다.

상태 장부가 필요한 이유#

처음에는 “폴더에 파일만 잘 넣으면 되지 않나?” 싶었다.

하지만 소스가 많아지면 이런 문제가 생긴다.

이 PDF 처리했나 안 했나?
이 노트 블로그 초안 만들었나?
이미 발행된 건 어느 것인가?

장부 없이는 같은 자료를 계속 다시 처리하게 된다.

내가 만든 장부:

파일 역할
source_registry.csv 어떤 자료가 들어왔는가
processed_ledger.csv 어디까지 처리됐는가
publish_ledger.csv 블로그에 올렸는가

이 구조는 나중에 로컬 모델 자동화에도 그대로 사용된다. 자동화 스크립트가 장부를 읽고, 이미 처리된 것은 건너뛰면 된다.

지금 당장 자동화하지 않는 이유#

장부가 생겼다고 바로 모든 것을 자동화하면 안 된다.

발행 자동화보다 처리 자동화를 먼저 해야 한다. 처리 자동화보다 구조를 먼저 안정화해야 한다.

지금은 기차를 사기보다 선로를 까는 단계다.

registry, ledger, 폴더 구조가 선로다. 로컬 모델은 나중에 붙이는 기차다.

이 구조를 만들면서 배운 것#

처음에는 “파일 시스템으로 이렇게까지 해야 하나?” 싶었다.

하지만 실제로 만들어보니 이 구조가 없으면:

  • 같은 자료를 두 번 처리하게 됨
  • 어떤 글이 발행 가능한지 알 수 없음
  • Claude에게 매번 전체 맥락을 다시 설명해야 함

장부와 상태 관리가 있으면 다음 대화부터 “SRC-025 상태가 working이니까 Hugo 초안을 만들면 된다” 같은 정확한 작업이 가능하다.

English Technical Summary#

Architecture Overview#

  • TableCard: reusable methodology engine (task decomposition, human-AI roles, verification gates)
  • LearningLog: content processing pipeline for learning materials

Pipeline Stages#

00_inbox → registered → extracted → working → drafted → ready → published → archived

Ledger System#

Three CSV files track pipeline state:

  • source_registry.csv: source intake tracking
  • processed_ledger.csv: processing progress
  • publish_ledger.csv: publication record

Design Principles#

  • Original source files in 00_inbox are never modified
  • Publish to blog-source only after explicit approval
  • Ledgers prevent duplicate processing and enable future automation
