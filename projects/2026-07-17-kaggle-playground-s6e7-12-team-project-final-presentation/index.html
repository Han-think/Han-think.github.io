Kaggle Playground S6E7 팀 프로젝트 - 12. 분석을 리듬ON 제안으로 연결한 최종 발표자료

팀원들과 Kaggle 건강 상태 분류 결과를 재현 가능한 분석, 사람의 검토, 참여자의 선택이 이어지는 리듬ON 서비스 제안으로 정리한 최종 발표자료 제작 기록.
2026년 7월 17일 · 4 min

1~11편이 개인 실험의 점수와 검증 과정을 기록했다면, 12편부터는 팀원들과 그 결과를 하나의 문제 정의와 서비스 제안으로 묶은 팀 프로젝트의 마무리를 기록한다.

이 글은 실제 발표 수행 기록이 아니라, 팀원들과 완성한 최종 발표자료와 그 제작 과정을 남기는 기록이다.

개인 실험에서 팀 프로젝트로#

이 프로젝트의 출발점은 Kaggle Playground Series S6E7의 학생 건강 상태 분류 문제였다. 입력은 수면, 활동, 스트레스 등 13개 생활습관 특성이었고, 목표는 at-risk, fit, unhealthy 세 상태를 구분하는 것이었다.

개인 실험에서는 모델과 피처, OOF, Public 점수를 끝까지 파고들었다. 하지만 팀 프로젝트의 최종 발표자료는 높은 점수를 얻은 과정을 그대로 나열하는 문서가 아니었다. 팀원들과 함께 다음 질문에 답해야 했다.

분류 점수를 실제 건강지원 흐름으로 연결한다면, 모델은 어디까지 하고 사람은 어디서 결정해야 할까?

그래서 최종 결과물의 중심을 정확한 분류 모델이 아니라 재현 가능한 신호를 사람이 안전하게 검토하는 과정으로 옮겼다. 서비스 이름은 청소년이 자신의 생활 리듬을 확인하고 작은 실천을 시작한다는 뜻을 담아 리듬ON으로 정했다.

결론부터 시작한 이유#

발표자료 첫 부분에서는 분석 과정을 시간순으로 설명하지 않고 최종 결론을 먼저 제시했다.

  • 합성 학습 데이터 690,088행을 사용했다.
  • 13개 원본 특성에서 결측, 교차, 해석 피처를 포함한 30개 신호를 구성했다.
  • 전체 데이터의 5-fold OOF로 최종 후보를 다시 검증했다.
  • 재현 가능한 제품 근거는 Public 0.95005, fixed OOF 0.949873인 코어로 정했다.
  • 모델은 지원 대상을 확정하지 않고 담당자가 먼저 검토할 후보만 제안한다.
  • 참여자는 안내를 받은 뒤 동의, 거절, 철회를 직접 선택한다.

개인 실험에서 기록한 0.95113은 더 높은 대회 점수였다. 그러나 외부 anchor와 특정 행 수정에 의존한 별도 최적화 트랙이었기 때문에 같은 파이프라인으로 다시 학습하고 배포할 수 있는 제품 근거와 분리했다.

좋은 발표자료는 가장 큰 숫자를 앞세우는 것이 아니라, 어떤 숫자를 무엇에 사용할 수 있는지를 먼저 밝혀야 한다는 것을 배웠다.

분석을 서비스로 잇는 다섯 고리#

팀 발표자료의 전체 흐름은 다섯 고리로 정리했다.

단계 산출물 통제 주체
생활 데이터 수면·활동·스트레스 신호 참여자
재현 분석 상태 확률과 검토 우선순위 모델
기관 확인 승인·수정·보류 담당자
참여자 선택 동의·거절·철회 참여자
리듬ON 기록·비교·작은 실천 서비스

이 구조에서 모델 점수는 행동의 결론이 아니다. 담당자가 다시 확인할 이유를 만드는 시작 신호다. 담당자의 검토와 참여자의 선택이 모두 통과된 뒤에야 리듬ON의 기록과 행동 제안이 시작된다.

다섯 고리 중 하나라도 빠지면 문제가 생긴다.

  • 분석만 있고 담당자 확인이 없으면 자동 판단이 된다.
  • 담당자 판단만 있고 참여자 동의가 없으면 강제 연결이 된다.
  • 앱만 있고 분석 근거가 없으면 일반적인 생활습관 콘텐츠에 머문다.
  • 점수만 있고 감사 기록이 없으면 나중에 결정 과정을 설명할 수 없다.

팀원들과 역할을 나눠 만든 결과#

이번 결과물은 혼자 완성한 프로젝트가 아니다. 팀원들과 역할을 나눠 분석 근거, 모델 비교, 서비스 흐름, 화면 제안, 발표자료의 논리를 서로 확인했다.

협업 과정에서 특히 중요했던 것은 각자 만든 결과를 단순히 한 문서에 붙이는 일이 아니었다. 서로 다른 작업을 같은 기준으로 다시 연결해야 했다.

  1. 분석 수치는 어떤 검증 조건에서 나온 것인지 확인했다.
  2. 모델의 출력이 실제 서비스에서 어떤 행동으로 이어지는지 정의했다.
  3. 완료된 분석과 아직 검증하지 않은 서비스 제안을 구분했다.
  4. 자동 진단이나 자동 배정으로 오해될 표현을 걷어냈다.
  5. 발표자료 전체를 문제, 근거, 서비스, 파일럿, 한계의 순서로 통일했다.

개별 이름이나 기여를 나열하기보다, 이 글에서는 팀원들과 함께 판단 기준을 맞추고 하나의 흐름을 만든 과정에 집중한다.

발표자료에 끝까지 담은 경계#

리듬ON은 의료 진단 서비스로 제안하지 않았다. 모델이 계산한 상태 확률만으로 지원 대상을 자동 배정하거나 앱을 자동 설치하는 구조도 아니다.

발표자료에는 다음 네 가지 금지선을 분명히 담았다.

  • 의료 진단을 대신하지 않는다.
  • 모델 점수로 지원 대상을 자동 배정하지 않는다.
  • 참여자의 동의 없이 앱이나 정보를 연결하지 않는다.
  • 개인에게 건강 문제의 책임을 돌리지 않는다.

또한 현재 확인된 범위도 제한했다. Kaggle 합성 데이터에서 분류 가능성과 재현성을 확인했지만, 실제 청소년 데이터의 대표성, 보호 집단별 공정성, 앱 사용 지속성, 개인정보 보호와 보안 운영은 아직 확인하지 않았다.

총평#

개인 실험에서는 왜 점수가 오르거나 떨어졌는가가 가장 큰 질문이었다. 팀 프로젝트에서는 질문이 한 단계 더 넓어졌다.

이 결과를 누가 보고, 어떤 결정을 내리며, 잘못됐을 때 누가 멈출 수 있는가?

팀원들과 발표자료를 만들면서 모델 성능, 서비스 화면, 운영 책임을 한 흐름으로 설명하는 법을 배웠다. 높은 점수는 좋은 출발점이지만, 실제 제안이 되려면 재현성, 사람의 검토, 참여자의 선택, 중단 기준까지 함께 있어야 했다.

다음 13편에서는 왜 0.95113이 아니라 재현 가능한 0.95005 코어를 제품 근거로 택했는지, 그리고 이를 8주 파일럿으로 어떻게 검증하려 했는지 정리한다.
