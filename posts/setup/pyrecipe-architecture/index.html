[도구] PyRecipe — 로컬 AI 환경 추천기 설계와 구현

로컬 LLM으로 Python 패키지 버전 조합을 추천하는 단일 HTML 도구 · 아키텍처 설계부터 JSON 파싱 엣지케이스 해결까지
2026년 5월 27일 · 7 min

왜 만들었는가#

로컬 AI를 세팅하다 보면 반드시 마주치는 벽이 있습니다.

pip install torch diffusers
→ ERROR: torch 2.x.x requires ...
→ ERROR: No module named 'triton'
→ ERROR: CUDA not available

문제는 패키지가 아닙니다. 버전 조합입니다.

Intel Arc GPU에서 PyTorch를 쓰려면 torch-directml을 써야 하고, IPEX를 얹으려면 정확히 맞는 버전이 필요하고, Python 3.12에서는 아직 안 되는 패키지가 수두룩합니다. 이 지식이 Stack Overflow 어딘가에 흩어져 있고, 2023년 글이 2026년에는 틀린 경우가 많습니다.

PyRecipe는 이 문제를 로컬 LLM으로 푸는 시도입니다.

전체 구조#

C:\Ollama-IPEX\PyRecipe\
├── index.html          ← 단일 파일 애플리케이션 (UI + 로직)
├── catalog/
│   ├── recipes.json    ← 검증된 레시피 8개 (패키지 조합 + 버전)
│   └── index.json      ← 키워드 → 레시피 ID 매핑
├── profiler.ps1        ← 로컬 환경 자동 감지 (GPU, Python, conda 등)
├── profile.json        ← profiler 실행 결과 (런타임 생성)
└── start.bat           ← Ollama + HTTP 서버 동시 기동

의존성은 없습니다. Node.js, React, Webpack — 전부 없습니다. 브라우저가 실행 환경 전체입니다.

세 개의 레이어#

1. Catalog — 검증된 지식 베이스#

{
  "id": "llm-ollama-ipex",
  "python": {
    "recommended": "3.11",
    "avoid": ["3.12"]
  },
  "packages": {
    "required": ["torch-directml", "intel-extension-for-pytorch"],
    "optional": ["accelerate"]
  },
  "gpu": "intel-arc",
  "notes": "Intel Arc → torch-directml 필수. IPEX는 torch 버전과 정확히 일치해야 함"
}

LLM의 학습 데이터는 낡습니다. moviepy==1.0.6처럼 존재하지 않는 버전을 자신 있게 출력하는 것을 이미 목격했습니다. Catalog는 LLM이 “기억에서 떠올리는” 것을 막고, 검증된 데이터를 context로 주입하기 위한 구조입니다.

const catalogSummary = catalog.map(r =>
  `Recipe: ${r.id}
Goals: ${r.goals.join(', ')}
Required: ${r.packages.required.join(', ')}
GPU: ${r.gpu}
Python: ${r.python.recommended} (avoid: ${r.python.avoid.join(',')})
Notes: ${r.notes}`
).join('\n---\n');

카탈로그 전체를 프롬프트에 넣는 방식입니다. 8개 레시피 기준으로 약 1,200 토큰. 컨텍스트 낭비처럼 보일 수 있지만, 이 방식이 모델이 잘못된 버전을 지어내는 것을 효과적으로 억제합니다.

2. Profiler — 환경 자동 감지#

profiler.ps1은 PowerShell로 작성된 환경 스캐너입니다.

# GPU 감지 — 단순 문자열 매칭으로는 실패하는 케이스가 있음
$gpuVendor = "unknown"
foreach ($g in $gpus) {
    if ($g -match "Intel.*Arc|Arc.*Graphics") { $gpuVendor = "Intel Arc" }
    elseif ($g -match "Intel.*Iris|Intel.*UHD|Intel.*HD") { $gpuVendor = "Intel Arc" }
    elseif ($g -match "NVIDIA|GeForce|Quadro|RTX|GTX") { $gpuVendor = "NVIDIA" }
    elseif ($g -match "AMD|Radeon|RX\s") { $gpuVendor = "AMD" }
}

초기에는 "Intel Arc" 단순 매칭을 썼는데, 실제 Win32_VideoController가 반환하는 이름은 "Intel(R) Arc(TM) Graphics"입니다. 정규식을 Intel.*Arc로 바꾸고 나서야 올바르게 감지되었습니다.

실행 결과는 profile.json으로 저장되고, 페이지 로드 시 자동으로 불러와 드롭다운을 채웁니다.

async function loadProfile() {
  const p = await fetch('./profile.json?' + Date.now()).then(r => r.json());
  if (gv === 'Intel Arc') {
    if (p.cpu?.includes('Ultra')) setSelectValue(gpuEl, 'Intel Arc + NPU');
    else setSelectValue(gpuEl, 'Intel Arc');
  }
}

Date.now() 캐시 버스터를 붙이는 이유는 Python HTTP 서버의 캐싱 동작 때문입니다. profiler를 재실행한 후 새로고침해도 이전 profile을 반환하는 경우가 있었습니다.

3. LLM Advisor — Ollama 스트리밍 연동#

브라우저에서 로컬 Ollama로 직접 요청을 보냅니다.

const resp = await fetch('http://127.0.0.1:11434/api/generate', {
  signal: AbortSignal.timeout(modelCfg.timeout),
  method: 'POST',
  body: JSON.stringify({
    model,
    system: SYSTEM_PROMPT,
    prompt: userPrompt,
    stream: true,
    options: { temperature: 0.3, top_p: 0.9, num_predict: modelCfg.num_predict }
  })
});

file:// 프로토콜에서 http:// 요청은 CORS로 막힙니다. 그래서 start.bat이 python -m http.server 8080으로 로컬 HTTP 서버를 띄우고, Ollama 측에는 OLLAMA_ORIGINS=*를 설정합니다. 이 두 조건이 동시에 충족되어야 브라우저 → Ollama 통신이 성립합니다.

모델 크기에 따라 타임아웃과 토큰 수를 다르게 설정합니다.

const MODEL_CONFIG = {
  'qwen3:4b-instruct': { num_predict: 900,  timeout: 180000 },
  'mistral24b_ablit':  { num_predict: 600,  timeout: 600000 },
};

24B 모델이 Intel Arc에서 생성하는 속도는 4B 모델과 비교할 수 없습니다. 타임아웃을 일률적으로 적용하면 24B 모델은 항상 실패합니다. 3분(180초) 제한에서 정확히 타임아웃되는 것을 서버 로그(3m0s)로 확인하고 모델별 설정을 분리했습니다.

LLM 출력 파싱 파이프라인#

가장 많은 시간을 쏟은 부분입니다.

LLM은 스키마를 지키지 않습니다. 모델마다 다른 방식으로 출력을 망가뜨립니다.

qwen3   → <think>...</think> 블록 + 잘못된 JSON 이스케이프
mistral → 잘못된 이스케이프 (\.  대신  \\.)
gemma   → ```json ... ``` 마크다운 코드블록으로 감쌈
일부    → warnings 필드를 배열 대신 문자열로 출력

파이프라인은 4단계로 구성됩니다.

1단계: 노이즈 제거#

const cleaned = accumulated
  .replace(/<think>[\s\S]*?<\/think>/gi, '')  // qwen3 thinking 블록
  .replace(/<think>[\s\S]*/gi, '')             // 닫히지 않은 think 태그
  .replace(/```json\s*/gi, '')                 // 마크다운 코드블록 시작
  .replace(/```\s*/g, '')                      // 마크다운 코드블록 끝
  .trim();

2단계: 균형 탐색으로 JSON 추출#

정규식으로 \{[\s\S]*\}을 매칭하는 것은 중첩된 {}가 있으면 오작동합니다. 대신 괄호 깊이를 추적하는 탐색으로 정확한 JSON 블록을 찾습니다.

function extractBalancedJson(text) {
  let start = -1, depth = 0, inStr = false, escape = false;
  for (let i = 0; i < text.length; i++) {
    const c = text[i];
    if (escape) { escape = false; continue; }
    if (c === '\\' && inStr) { escape = true; continue; }
    if (c === '"') { inStr = !inStr; continue; }
    if (inStr) continue;
    if (c === '{') { if (depth === 0) start = i; depth++; }
    else if (c === '}') {
      depth--;
      if (depth === 0 && start !== -1) return text.slice(start, i + 1);
    }
  }
  return null;
}

이 함수는 JSON 문자열 리터럴 안의 {}는 무시하고, 실제 객체 구조만 추적합니다.

3단계: 이스케이프 보정#

LLM이 Windows 경로를 출력할 때 자주 발생하는 문제입니다.

// LLM이 생성한 잘못된 JSON
"installCommands": [".\.venv\\Scripts\\Activate.ps1"]

// JSON 파서가 기대하는 형태
"installCommands": [".\\.venv\\Scripts\\Activate.ps1"]

JSON 명세에서 \ 뒤에 올 수 있는 문자는 ", \, /, b, f, n, r, t, u 뿐입니다. .은 허용되지 않습니다.

정규식으로 보정하면 \\. (유효한 이중 백슬래시 + 점)을 잘못 건드리는 문제가 발생합니다. 정규식 엔진이 \\.에서 두 번째 \ + .을 매칭해 \.을 만들어내는 역효과입니다. 그래서 문자 단위 처리로 구현했습니다.

function fixJsonEscapes(str) {
  const valid = new Set(['"','\\','/','b','f','n','r','t','u']);
  let out = '', inStr = false, i = 0;
  while (i < str.length) {
    const c = str[i];
    if (!inStr) {
      out += c;
      if (c === '"') inStr = true;
      i++;
    } else if (c === '\\') {
      const nx = str[i + 1] || '';
      if (valid.has(nx)) {
        out += c + nx;              // 유효한 이스케이프: 그대로
        i += (nx === 'u') ? 6 : 2; // \uXXXX는 6자
      } else {
        out += nx;                  // 잘못된 이스케이프: \ 제거
        i += 2;
      }
    } else {
      out += c;
      if (c === '"') inStr = false;
      i++;
    }
  }
  return out;
}

4단계: 방어적 렌더링#

LLM이 배열 필드를 문자열로 출력하는 경우를 처리합니다.

function toArr(v) {
  if (!v) return [];
  if (Array.isArray(v)) return v;
  if (typeof v === 'string') return v.split('\n').map(s => s.trim()).filter(Boolean);
  return [String(v)];
}

warnings 필드가 ["경고1", "경고2"] 대신 "경고1\n경고2" 형태로 오는 모델이 실제로 있었습니다. toArr는 둘 다 같은 방식으로 처리합니다.

레이아웃 안정성#

분석 중 UI가 흔들리는 문제에 시간을 많이 썼습니다.

원인은 세 가지였습니다.

1. 스트림 텍스트가 화면에 실시간 렌더링되면서 높이가 변함
→ 스트림 출력을 숨겨진 rawOutput 박스에만 저장. 분석 완료 후 토글 버튼으로 열람.

2. 결과 블록이 display:none → display:'' 전환 시 레이아웃 펄쩍 뜀
→ 구조화 결과 블록을 항상 표시. 분석 전에는 —로 placeholder. 결과 도착 시 텍스트만 교체.

3. 진행바 ease-in-out 트랜지션 + JS 타이머 오차 → 덜컹거림
→ JS 기반 width 업데이트를 완전히 제거. @keyframes scan으로 CSS 스캐너 애니메이션으로 교체.

@keyframes scan { 0%{left:-40%} 100%{left:110%} }
.progress-scanner {
  position: absolute;
  width: 40%;
  background: linear-gradient(90deg, transparent, var(--purple), transparent);
  animation: scan 1.6s linear infinite;
}

linear를 쓰는 이유는 ease-in-out이 끝에서 속도가 줄면서 루프 점프 시 시각적 충격이 커지기 때문입니다. gradient로 양 끝을 페이드하면 루프가 자연스럽게 이어집니다.

시스템 프롬프트 설계#

모델 출력 형식을 강제하는 가장 효과적인 방법은 시스템 프롬프트에 명시적으로 못 박는 것입니다.

OUTPUT RULES (STRICT):
* Start your response with { immediately
* End your response with }
* All array fields MUST be arrays [...], never plain strings
* Do NOT wrap in triple-backtick code blocks

그리고 하드웨어별 규칙을 명시합니다.

* Intel Arc → torch-directml (NOT regular torch+cuda)
* NVIDIA → torch+cu121 or cu118 depending on CUDA version
* CPU only → torch (cpu build)

이 규칙들이 없으면 Intel Arc에 CUDA 기반 torch를 추천하는 결과가 빈번하게 나왔습니다.

SYSTEM_PROMPT의 백틱 함정#

JavaScript 템플릿 리터럴(`)로 시스템 프롬프트를 작성하면서 만난 버그입니다.

const SYSTEM_PROMPT = `...
  * Do NOT wrap in \`\`\`json\`\`\` blocks  // 이렇게 이스케이프 필요
...`;

프롬프트 안에 “코드블록을 쓰지 말라"는 규칙을 설명하기 위해 ```를 그대로 넣으면, 템플릿 리터럴이 그 지점에서 닫힙니다. 이후의 모든 JavaScript가 파싱 실패합니다. 오류 메시지 없이 페이지 전체가 조용히 멈춥니다.

해결책은 단어로 대체하는 것입니다.

* Do NOT wrap in triple-backtick code blocks

한계와 다음 단계#

현재 PyRecipe가 가진 근본적인 한계는 카탈로그 커버리지입니다. 8개의 레시피로 커버할 수 없는 목표가 대부분입니다. 카탈로그 밖으로 나가면 LLM이 버전을 만들어냅니다.

다음으로 구현하고자 하는 것은 verified-versions.json입니다.

{
  "_verified": "2026-05-27",
  "torch-directml": "0.2.5.dev240914",
  "diffusers": "0.31.0",
  "transformers": "4.47.0",
  "moviepy": "1.0.3"
}

검증 날짜를 명시한 패키지 버전 목록을 LLM context에 추가로 주입하면, 카탈로그 밖의 목표에도 정확한 버전을 참조할 수 있게 됩니다.

마치며#

PyRecipe는 복잡한 프레임워크 없이, 단일 HTML 파일 안에서 로컬 LLM을 실용적인 도구로 만드는 실험이었습니다.

실제로 돌아가는 것을 만드는 과정에서 가장 많은 것을 배웠습니다. LLM이 JSON을 어떻게 망가뜨리는지, CSS 애니메이션이 JS 타이머보다 안정적인 이유, 정규식이 충분하지 않을 때 문자 단위 파서가 필요한 이유.
