1. React 리팩터링 흐름 복습: 초보자의 구조 이해하기#

무엇을 배웠나#

리팩터링은 화면을 바꾸는 것이 아니라, 같은 기능을 유지하면서 내부 구조를 개선하는 작업이라는 점을 명확히 이해했습니다. 특히 CSS Modules와 styled-components가 클래스 이름 격리나 JavaScript 템플릿 리터럴을 통해 스타일 관리의 방식을 어떻게 변화시키는지 구체적인 예시를 보며 체감할 수 있었습니다. 단순히 문법을 익히는 것을 넘어, 코드 관리 방식의 차이를 인지하는 연습이 무엇보다 중요하다고 느꼈습니다.

헷갈렸던 점#

처음에는 화면이 똑같아 보여서 리팩터링의 필요성을 즉시 체감하기 어려웠습니다. 특히 CSS Modules나 styled-components 같은 도구가 단순히 스타일 적용 방식뿐만 아니라 프로젝트 전체의 코드 관리 구조를 근본적으로 바꾸는 것인 줄 몰랐습니다. 결국 “같은 기능을 유지하면서 내부 구조를 개선하는 작업"이라는 정의 아래, 각 스타일링 기법이 가진 고유한 장단점과 관리 방식을 이해하는 과정이었음을 깨달았습니다.

정리된 이해#

리팩터링은 화면을 바꾸는 것이 아니라 같은 기능을 유지하면서 내부 구조를 개선하는 작업입니다. 일반 CSS, CSS Modules, styled-components는 스타일 관리 방식이 다를 뿐 최종적인 화면 표현은 비슷할 수 있습니다. 이 과정은 문법 암기보다 코드 관리 방식의 차이를 체감하는 연습에 가깝습니다.

// 1. 일반 CSS (HTML)
<button class="btn">클릭</button>

// 2. CSS Modules (JS import)
import styles from './Button.module.css';
<button className={styles.btn}>클릭</button>

// 3. styled-components (JS 템플릿 리터럴)
const Button = styled.button`
  background-color: blue;
  color: white;
`;
<Button>클릭</Button>

2. React Router 비동기 상태 관리 복습#

무엇을 배웠나#

오늘은 수많은 상태 관리 도구를 사용해보며, 단순히 화면이 비슷비슷하게 보이는 이유를 고민했습니다. 결국 각 도구가 필요한 이유는 ‘데이터 전달과 상태 변경의 책임’을 얼마나 명확히 나누느냐에 달려 있다는 생각이 들었습니다. 특히 Redux Toolkit 같은 툴이 boilerplate 코드를 줄여주어 진입 장벽을 낮춰준다는 점은 실무에서 효율성을 높이는 중요한 요소라고 느꼈습니다.

헷갈렸던 점#

useState와 useReducer, Context, Redux 등 다양한 도구를 사용해도 화면 결과가 비슷비슷해 ‘필요성’을 파악하기 어려웠다.

상태 관리 도구는 단순히 코드를 줄이기 위한 것이 아니라, 데이터 전달과 상태 변경의 책임을 명확히 나누기 위해 선택하는 것이다. 상태의 범위와 변경의 복잡도가 높을수록 더 체계적인 도구를 사용해야 한다.

정리된 이해#

도구를 교체하는 핵심 목적은 화면 표현이 아닌 데이터 전달과 상태 변경의 책임을 명확히 나누는 데 있습니다. useState부터 Redux Toolkit까지, 상태의 범위와 변경의 복잡도가 높을수록 더 체계적인 관리 도구가 필요합니다. 결국 개발자는 앱의 규모와 상황에 맞는 최적의 상태 관리 전략을 선택해야 합니다.

LearningLog 워킹 노트: React Router, 비동기 서비스, 상태 관리 진화 복습#

작성일: 2026-08-20 초보자 시점: 오늘도 수많은 개념들이 쏟아지니 머릿속이 복잡해지는 순간들입니다. 특히 “왜 이 도구를 쓰지?“라는 질문에 대한 답을 찾기 위해 코드를 이리저비 옮겨보았는데, 정작 중요한 건 ‘화면의 결과’가 아니라 ‘데이터가 어떻게 흐르는지’였습니다.

1. 무엇이 헷갈렸나#

오늘 가장 큰 혼란은 **“화면이 비슷비슷하게 나오는데, 내부 구조가 계속 바뀌니 왜 필요한지 감이 안 잡혔다”**는 점이었습니다. useState로 시작했다가 useReducer, Context, Redux… 차근차근 도구를 업그레이드해보니 코드의 양과 복잡도는 급격히 늘었는데, 정작 보이는 결과물은 비슷비슷해서 “이게 무슨 의미일까?“라는 의문이 들었습니다. 단순히 문법을 외우는 것이 아니라, 어떤 상황에서 어떤 도구가 필요한지를 감으로 잡는 과정이 필요하다고 느꼈습니다.

2. 정리된 이해#

도구를 바꾸는 가장 큰 목적은 **“화면 표현이 아니라 데이터 전달과 상태 변경의 책임을 더 명확히 나누기 위함”**이었습니다.

  • useState: 내 컴포넌트 안에서 간단하게 다룰 수 있는 로컬 상태
  • useReducer: 상태 변화의 규칙이 조금이라도 복잡해질 때 유용한 도구
  • Context: 컴포넌트 트리 사이에서 값을 공유해야 할 때, 중간 다리를 놓는 통로 역할
  • Redux: 앱 전체의 상태를 store라는 중앙 집중식 창고에 관리하고, 명확한 흐름으로 변경하고 싶을 때
  • Redux Toolkit: Redux를 시작할 때 겪게 되는 번거로운 boilerplate 코드를 줄여주어 진입 장벽을 낮춰주는 친구

결론적으로, **“상태의 범위와 변경의 복잡도”**가 높을수록 더 체계적인 도구를 선택하게 된다는 생각이 들었습니다.

3. 실습 예시 (오늘의 전환 과정)#

강사님께서 보여주신 방식은 정말 인상 깊었습니다. 같은 기능을 위해 useState로 관리하던 카운터를 useReducer로 리팩토링한 과정을 통해, 액션(Action)과 리듀서(Reducer)가 상태 변화를 어떻게 체계적으로 관리하는지 실감할 수 있었습니다. 특히 useReducer는 단순한 값의 변경이 아니라, ‘어떤 의도’로 상태가 변하는지를 명시할 수 있어 코드의 의도가 훨씬 명확해지는 것을 체감했습니다.

// useReducer를 활용한 카운터 예시
const initialState = { count: 0 };

function reducer(state, action) {
  switch (action.type) {
    case 'increment':
      return { count: state.count + 1 };
    case 'decrement':
      return { count: state.count - 1 };
    default:
      return state;
  }
}

const [state, dispatch] = useReducer(reducer, initialState);

// 버튼 클릭 시.dispatch({ type: 'increment' })와 같이 호출

핵심을 보여주는 코드 예시’만’ 백틱3개 코드블록으로 출력하라. 노트에 코드 근거가 없으면 아무것도 쓰지 마라.

3. 자동 채점 계약과 기능 구현의 균형#

무엇을 배웠나#

자동 채점 시스템은 코드의 기능적 완성도뿐만 아니라, starter code가 제시한 인터페이스와 DOM 구조 등 ‘계약’을 정확히 따르는지를 검증한다는 점을 깨달았다. 특히 import 경로나 태그 구조의 미세한 변경조차 테스트를 실패시킬 수 있어, 기능 구현 전 반드시 제공된 skeleton을 준수하는 것이 우선임을 느꼈다. 이를 통해 ‘더 좋은 코드’와 ‘채점 계약 사이의 균형’이 단순히 문법적 완성도가 아닌, 시스템 요구사항 충족 여부로 판단되어야 한다는 관점을 갖게 되었다.

헷갈렸던 점#

가장 큰 혼란은 “기능이 정상 작동해 보여도, DOM 구조의 작은 변화 하나가 채점을 실패하게 만든 경우"였습니다. 특히 코드를 더 깔끔하게 리팩토링했음에도 불구하고, <div> 태그 하나만 사라져도 XPath 기준의 자동 채점 시스템에서 테스트가 깨지는 경험을 했습니다.

또 한 가지는 “더 좋은 코드"를 작성하는 것과 “채점 계약(계약)“을 지키는 것 사이의 균형이었습니다. 기능상 완벽해 보여도, starter code와 요구사항에 명시된 import 경로, 파일 구조, DOM 계층 구조 등과의 불일치가 있으면 채점이 되지 않는다는 점이 처음에는 직관적이지 않았습니다.

자동 채점 문제는 단순히 “코드가 작동하는지"를 넘어, **“정해진 인터페이스와 구조를 정확히 맞추는 문제”**라는 점을 깨달았습니다. 기능 검증과 구조 준수는 별개의 문제이며, starter code의 구조를 보존하는 것이 자동 채점 환경에서 최우선 과제가 됩니다.

정리된 이해#

자동 채점 시스템은 코드의 기능적 완성도보다, starter code와의 인터페이스와 구조 일치 여부를 우선적으로 검증합니다. 따라서 기능을 구현하기 전에는 DOM 구조나 import 경로 등 ‘계약’을 정확히 맞추는 것이 최우선 과제가 되어야 합니다. 일단 테스트가 통과한 후에는 코드 리팩토링이나 개선이 가능하지만, 초기 단계에서는 강사님이 제시한 구조를 보존하는 것이 채점 실패를 막는 가장 안전한 방법입니다.

// React Testing Library와 채점 스켈레톤 민감도 복습을 위한 핵심 원칙 요약

/*
핵심 원칙:
1. 기능 검증(structural compliance)보다 DOM 구조/import 경로 등 '계약' 준수를 우선시
2. starter code의 디렉터리 구조, import 경로, 기본 DOM 레이아웃을 먼저 파악
3. 최소한의 변경으로 테스트 통과를 목표로 한 후, 리팩토링 검증
*/

4. 카카오 지도 SDK와 React의 연결 고리#

무엇을 배웠나#

React와 외부 SDK를 결합할 때 가장 중요한 것은 useRef를 통해 DOM 엘리먼트를 정확히 참조하고, 지도 객체 생성 시 그 컨테이너를 전달하는 것입니다. new kakao.maps.Map과 new kakao.maps.Marker는 각각 지도와 마커 객체를 생성하지만, 실제 화면에 나타나게 하려면 setMap(map) 메서드를 호출해 마커를 지도에 부착해야 합니다. 마지막으로 클릭 이벤트 리스너를 통해 evt.latLng로 좌표를 추출하면, 위도와 경도를 각각 getLat()와 getLng() 메서드로 손쉽게 분리할 수 있습니다.

헷갈렸던 점#

React와 외부 SDK(카카오맵)의 생명주기 차이로 인해 useRef를 직접 변형하려다 구조적 불일치가 발생했다. 특히 마커와 이벤트 객체가 React의 상태 관리와 어떻게 연결되는지 파악하는 것이 처음에는 직관적이지 않았다. 결국 핵심은 외부 SDK 객체를 React의 렌더링 주기에 맞게 연결하는 ‘고리’를 만드는 것이었다.

정리된 이해#

외부 SDK 객체와 React의 생명주기를 연결하는 것이 핵심입니다. useRef로 DOM을 참조하고, 지도 생성 시점에 setMap을 호출해 마커를 화면에 뿌려줍니다. 마지막으로 클릭 이벤트 리스너를 통해 evt.latLng로 좌표를 추출하여 상태와 연동하면 됩니다.

import { useEffect, useRef } from 'react';
import { Map, Marker } from '@kakao/maps-sdk';

export default function KakaoMap() {
  const mapContainer = useRef(null);
  const mapRef = useRef(null);

  useEffect(() => {
    // 1. SDK 로딩 및 지도 생성
    const map = new Map(mapContainer.current);
    mapRef.current = map;

    // 2. 마커 생성 및 추가
    const marker = new Marker({
      position: new kakao.maps.LatLng(37.5665, 126.9780),
    });
    marker.setMap(map);

    // 3. 클릭 이벤트 리스너 등록 (핵심)
    kakao.maps.event.addListener(map, 'click', function(mouseEvent) {
      const latlng = mouseEvent.latLng; // evt.latLng와 동일
      console.log('클릭 좌표 - 위도:', latlng.getLat(), '경도:', latlng.getLng());

      // 클릭한 위치에 마커 이동 예시
      marker.setPosition(latlng);
    });
  }, []); // 의존성 배열 비워두기 (컴포넌트 마운트 시 한 번만 실행)

  return <div ref={mapContainer} style={{ width: '100%', height: '500px' }} />;
}

5. React Bootstrap 버튼 UI 입문하기#

무엇을 배웠나#

React Bootstrap은 Bootstrap의 디자인 시스템을 React 컴포넌트 형태로 제공하는 라이브러리이며, 핵심 CSS를 import한 후 variant나 size와 같은 prop을 통해 스타일을 제어한다. 기존에 직접 CSS를 작성하던 방식과 달리, 사전에 정의된 속성을 활용해 빠르게 일관성 있는 UI를 구성할 수 있다는 점이 가장 큰 특징이다. 특히 import "bootstrap/dist/css/bootstrap.min.css"와 같이 Bootstrap의 기본 스타일을 최상위 컴포넌트에서 적용해야 React Bootstrap 컴포넌트가 제대로 작동한다는 점을 반드시 기억해야 한다.

헷갈렸던 점#

React Bootstrap에서 variant="primary"와 같은 prop을 주는 방식이 기존 HTML class 적용과는 다른 개념이며, 스타일이 실제로 적용되는지 처음에는 의심이 들었다.

또, import "bootstrap/dist/css/bootstrap.min.css"와 { Button } from "react-bootstrap"가 섞여 있어, 핵심 CSS와 React 전용 컴포넌트의 출처를 구분하기 어려웠다.

정리된 이해#

React Bootstrap은 Bootstrap의 디자인 시스템을 React 컴포넌트 형태로 제공하는 라이브러리이며, 핵심 CSS를 import한 후 variant와 같은 prop을 통해 스타일을 제어하여 빠른 구성과 일관된 디자인을 실현한다.

import React from 'react';
import { Button, ButtonToolbar } from "react-bootstrap";
import "bootstrap/dist/css/bootstrap.min.css";

function App() {
  return (
    <div>
      {/* variant prop을 통해 스타일 선택 */}
      <Button variant="primary">Primary</Button>

      {/* size prop으로 크기 조절 가능 */}
      <Button variant="secondary" size="lg">Large Secondary</Button>

      {/* ButtonToolbar로 버튼 그룹화 */}
      <ButtonToolbar>
        <Button variant="success">Success</Button>
        <Button variant="danger">Danger</Button>
      </ButtonToolbar>
    </div>
  );
}

export default App;

6. Next.js Link, 차트 페이지 라우팅 구성하기#

무엇을 배웠나#

Next.js의 Link 컴포넌트는 React Router의 그것과 네이밍이 같아 혼란스러울 수 있지만, 실제로는 Next.js의 파일 시스템 라우팅과 연동되어 페이지 이동을 담당한다는 점을 명확히 했다. 단순히 URL을 전환하는 것을 넘어, 클라이언트 사이드에서 부드러운 네비게이션을 제공하며 next/link를 사용하는 것이 핵심임을 깨달았다.

헷갈렸던 점#

React Router와 Next.js 모두 Link라는 동일한 컴포넌트 이름을 사용하지만, import 경로가 react-router-dom인지 next/link인지에 따라 완전히 달라져 코드 작성 시 실수가 잦았다.

특히 “페이지 이동"이라는 개념은 같지만, 그 주체가 React Router인지 Next.js의 디렉토리 구조인지 구분이 가지 않아 라우팅 시스템의 작동 원리를 혼동하기 쉬웠다.

정리된 이해#

Next.js에서 Link는 페이지 이동을 담당하며, 실제 라우팅은 Next.js의 디렉토리 구조가 관리한다. next/link를 사용하면 단순 리프레시 없이 클라이언트 사이드에서 부드럽게 전환되며, 정의된 경로대로 자동 매핑된다. 따라서 개발자는 Link를 통해 URL을 선언적으로 제어하고, 시스템은 파일 기반 라우팅으로 페이지를 연결한다.

import Link from "next/link";

export default function Navigation() {
  return (
    <nav>
      <ul>
        <li><Link href="/">Home</Link></li>
        <li><Link href="/bar">Bar Page</Link></li>
        <li><Link href="/line">Line Page</Link></li>
      </ul>
    </nav>
  );
}

7. MUI X Charts 핵심 prop 분류와 학습 포인트#

무엇을 배웠나#

MUI X Charts를 공부하면서 JSX 문법과 데이터 구조가 결합되는 부분이 가장 어려웠습니다. 특히 배열과 객체가 중첩된 series={[{ data: [...], label: "..." }]} 형태에서 닫는 기호의 위치를 파악하는 데 애를 먹었습니다. 핵심은 series, xAxis 같은 prop이 데이터를 표현하고, barLabel나 stack 같은 prop이 스타일링과 상호작용을 담당한다는 점으로 정리했습니다.

헷갈렸던 점#

JSX 문법에서 대괄호와 중괄호가 섞여 있어 }]나 }} 어디서 닫혀야 할지 감이 잡히지 않았다.

특히 />(자 closing 태그)를 빼먹었을 때 에러 메시지가 추상적이어서 코드 어디가 잘못된지 찾기 어려웠고, stack, area, highlightScope 같은 prop들이 어떤 역할을 하는지 데이터 흐름 전체를 한 번에 파악하기 힘들었다.

정리된 이해#

MUI X Charts는 데이터 표현(series, xAxis), 스타일링(barLabel, area), 상호작용(onLineClick)을 구분하여 이해해야 한다. 특히 JSX의 중괄호와 대괄호 조합에 익숙해지는 것이 가장 중요한 첫걸음이다.

MUI X Charts: BarChart와 LineChart 구성 및 이벤트 (초보자 워킹 노트)#

📌 핵심 요약#

MUI X Charts에서 가장 큰 어려움은 JSX 문법과 데이터 구조의 결합이었습니다. 특히 series prop에 사용되는 대괄호([])와 중괼호({})의 조합, 그리고 컴포넌트 닫기(/>) 위치가 혼동을 주었습니다.

🔑 핵심 prop 분류#

카테고리 주요 prop 의미
데이터 표현 series 실제 차트에 표시할 데이터 묶음 (라벨 포함)
xAxis x축의 카테고리/스케일 정의
grid 격자 선의 방향 및 스타일
스타일링 barLabel 막대 위에 값 표시 여부
borderRadius 모서리의 둥근 정도
area 라인 차트 아래 영역 채우기
stack 같은 이름끼리 막대를 누적 표시
상호작용 onAreaClick, onLineClick 사용자가 차트를 클릭했을 때 실행되는 함수

💡 문법의 요령#

  • JSX 닫기: 컴포넌트는 중첩된 {와 } 그리고 [와 ]를 정확히 맞물려 닫아야 합니다.
  • 닫는 기호 확인: />(자 closing 태그)를 빼먹었을 때 에러 메시지가 추상적이므로, 대괄호와 중괄호의 개수를 꼼꼼히 확인하는 습관이 필요합니다.

📊 핵심 코드 예시#

import * as React from 'react';
import { BarChart, LineChart } from '@mui/x-charts';

const data = [
  { month: 'Jan', uv: 400, pv: 300 },
  { month: 'Feb', uv: 300, pv: 200 },
  { month: 'Mar', uv: 200, pv: 250 },
];

// BarChart 예시
<BarChart data={data} margin={{ top: 20, right: 30, left: 0, bottom: 0 }}>
  <XAxis dataKey="month" />

  {/* series는 데이터 표현을 담당하며, 대괄호와 중괄호가 섞여 있음 */}
  <Bar dataKey="uv" fill="#8884d8" barLabel />
  <Bar dataKey="pv" fill="#82ca9a" barLabel />
</BarChart>

// LineChart 예시
<LineChart data={data} margin={{ top: 20, right: 30, left: 0, bottom: 0 }}>
  <XAxis dataKey="month" />

  {/* series 구성: [{ dataKey, type, ... }] 형태 */}
  <Line type="monotone" dataKey="uv" stroke="#8884d8" activeDot={{ r: 8 }} />
  <Line type="monotone" dataKey="pv" stroke="#82ca9a" activeDot={{ r: 8 }} />
</LineChart>

총평#

오늘 오전 전체에서 배운 것#

React 리팩터링과 상태 관리, 그리고 자동 채점 시스템의 ‘계약’ 개념을 통해 코드를 단순히 기능적으로 완성하는 것을 넘어 구조와 인터페이스의 중요성을 재인식했습니다. 특히 외부 SDK와의 연동이나 UI 라이브러리 사용 시 제공된 스켈레톤 준수의 필연성을 깨닫고, 문법적 완성도보다 시스템 요구사항 충족을 최우선으로 하는 개발 관점을 갖게 되었습니다.

다음에 조심할 것#

  1. 자동 채점 시스템은 코드의 완성도보다 제공된 인터페이스와 DOM 구조를 정확히 따르는 것이 최우선이므로, skeleton 코드를 임의로 수정하기보다는 기능을 구현하는 순서를 재고해야 한다.
  2. React Bootstrap 등 외부 라이브러리를 사용할 때는 CSS 파일을 최상위 컴포넌트에서 반드시 import하여 스타일 시트가 로드된 상태여야지만 컴포넌트가 정상적으로 작동한다는 점을 간과하지 말아야 한다.
  3. MUI X Charts와 같은 차트 라이브러리에서는 데이터 구조(series, xAxis 등)와 닫는 괄호 위치에 각별히 주의해야 하며, JSX 문법과 데이터 결합 시 실수가 발생하기 쉬우니 코드 작성을 신중히 검토해야 한다.

다음 복습 주제#

React와 외부 SDK 연동 시 useRef를 통한 DOM 참조와 객체 부착(setMap)의 필수 과정을 명확히 이해했다. 또한, 자동 채점 시스템에서 ‘인터페이스 계약 준수’가 기능 구현 그 이상으로 중요한 검증 기준임을 인지하고 실무 적용에 임하겠다.

다음 학습 주제로는 React 상태 관리의 핵심인 useEffect와 useReducer의 동작 원리, 그리고 Next.js와 연동된 데이터 페칭 전략을 복습하여 화면 전환 시 발생하는 비동기 처리 이슈를 해결하는 방법을 심화하고자 한다.
