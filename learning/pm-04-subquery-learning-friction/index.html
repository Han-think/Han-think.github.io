1. 메인쿼리 접근 방식#

왜 이걸 보게 됐나#

처음에는 문제를 풀 때 자연스럽게 단서를 찾고 해결해 나가는 방식에 익숙했기에, 서브쿼리를 사용할 때 메인 쿼리부터 접근해야 한다는 개념이 굉장히 어색하고 거꾸로 느껴졌습니다. 특히 서브쿼리의 결과값을 미리 넣는 듯한 느낌 때문에, 문제 해결의 논리적 흐름을 파악하기 어려웠던 거죠. 그래서 이 접근 방식을 이해하게 되면서 쿼리 작성 과정의 흐름을 잡을 수 있었습니다.

내가 헷갈린 지점#

서브쿼리를 처음 접했을 때 메인 쿼리부터 접근해야 한다는 점이 너무 이상하게 느껴졌다. 문제 해결에 익숙한 내게는 쿼리를 거꾸로 작성하는 것 같았고, 어떤 숫자나 조건을 미리 넣어버리는 것처럼 보였던 기억이 난다. 전체적인 흐름을 파악하기 전에 특정 값에 먼저 집중해야 한다는 점이 이해하기 어려웠다.

시도한 코드 / 예시#

SELECT Name
FROM tracks
WHERE AlbumId = 4;

결과와 해석#

처음에는 WHERE AlbumId = 4 와 같이 특정 값을 쿼리 내에 바로 넣는 방식이 어색했지만, 서브쿼리 접근법을 따라 단서를 먼저 파악하고 필요한 값을 서브쿼리로 뽑아내는 과정을 거치니 메인쿼리가 어떤 데이터를 가르키는지 더 명확하게 이해하게 되었다. 이 방법을 통해 문제 해결의 전체적인 흐름을 파악하고, 쿼리 작성의 순서를 체계화할 수 있었다.

정리된 이해#

처음에는 문제 해결을 위한 단서를 먼저 찾는 나에게 메인쿼리부터 접근하는 서브쿼리 방식이 거꾸로 느껴졌지만, 최종 출력 항목과 테이블을 명확히 하고 필요한 정보를 단서로 활용하는 방식으로 접근하면 쿼리 작성 과정이 체계적으로 정리된다는 것을 깨달았다. 이 방법을 통해 쿼리가 어떤 결과를 보여줘야 하는지 명확히 파악하고 필요한 정보를 연결하여 효율적으로 문제를 해결할 수 있게 되었다.

2. 테이블 및 컬럼 연결#

왜 이걸 보게 됐나#

처음에는 문제에서 주어진 정보와 테이블 간의 연결고리가 잘 안 보여서, 어떤 컬럼을 어디에서 가져와야 하는지 혼란스러웠다. 결국 테이블 구조와 각 컬럼의 역할을 정확히 이해하고, 문제의 단서가 어떤 테이블과 컬럼에 해당하는지 파악하는 과정이 필요하다는 것을 깨달았다. 이 부분에 대한 이해가 부족하면 쿼리가 돌아가지 않거나 예상치 못한 결과가 나오기 때문에 중요했다.

내가 헷갈린 지점#

처음에는 테이블과 컬럼들이 서로 어떻게 연결되는지, 특히 문제에서 요구하는 조건이 어떤 테이블의 어떤 컬럼과 연관되는지 파악하는 데 어려움을 느꼈습니다. 예를 들어, 고객 정보와 지원 담당자 정보를 연결해야 할 때 어떤 컬럼이 어떤 테이블에 있는지, 그리고 그 컬럼들이 어떻게 조건을 형성하는지 즉시 떠올리기 어려웠습니다. 단순한 테이블 목록을 암기하는 것만으로는 해결되지 않아, 쿼리의 논리적 흐름을 이해하고 테이블 간의 관계를 파악하는 것이 중요하다는 것을 깨달았습니다.

시도한 코드 / 예시#

SELECT Name
FROM tracks
WHERE AlbumId = 4;

결과와 해석#

테이블과 컬럼을 정확하게 연결하는 연습을 위해 customers 테이블의 SupportRepId와 employees 테이블의 EmployeeId가 어떻게 연결되는지 확인하는 간단한 조인 쿼리를 작성해 보았는데, 예상대로 출력이 제대로 나오지 않았다. 테이블 구조를 다시 확인하고 컬럼 이름을 정확하게 입력하니 원하는 결과를 얻을 수 있었고, 테이블 간의 관계를 시각적으로 정리하는 것이 중요하다는 것을 깨달았다. 컬럼 이름만 정확히 아는 것보다 테이블 간의 관계를 이해하는 것이 더 중요했다.

정리된 이해#

테이블과 컬럼 연결이 어려웠던 이유는 문제에서 제시된 단서를 바탕으로 전체적인 흐름을 파악하는 데 집중하다 보니, 필요한 테이블이나 컬럼의 정확한 이름을 떠올리는 데 어려움이 있었습니다. 쿼리 작성 순서를 먼저 정하고, 문제에서 주어진 정보를 단계별로 템플릿에 적용하는 방식으로 접근하니 필요한 테이블과 컬럼을 연결하는 과정이 훨씬 수월해졌습니다.

3. 서브쿼리 접근법#

왜 이걸 보게 됐나#

처음 서브쿼리를 접했을 때 문제 해결의 논리적인 흐름과 맞지 않아 어려움을 겪었기 때문에, 쿼리 작성 순서를 체계적으로 접근하는 방법을 배우게 되었어. 단순히 쿼리 작법을 익히는 것을 넘어, 복잡한 조건들을 파악하고 논리적으로 연결하는 능력을 키우기 위해 이 접근법이 필요했어. 이제는 이 템플릿을 활용하여 서브쿼리를 보다 자신 있게 다룰 수 있게 되었어.

내가 헷갈린 지점#

처음에는 메인 쿼리부터 시작해야 한다는 기존의 문제 해결 방식과 달리, 서브쿼리는 거꾸로 접근해야 한다는 점이 너무 헷갈렸어요. 특히 미리 숫자를 넣어서 조건으로 사용하는 부분이 이해가 안 되어서, 어떻게 접근해야 할지 막막했습니다. 서브쿼리가 어떤 값을 반환해야 하는지, 그리고 그 값이 메인쿼리에 어떻게 영향을 주는지 파악하는 데 어려움을 겪었습니다.

시도한 코드 / 예시#

SELECT albums.Title
FROM albums
WHERE albums.AlbumId IN (SELECT tracks.AlbumId FROM tracks WHERE tracks.GenreId IN (SELECT GenreId FROM genres WHERE genres.Name = 'Rock'));

결과와 해석#

위에서 정리한 서브쿼리 접근법은 문제를 단계별로 분해하여 쿼리를 작성하도록 돕는 효과적인 방법이었다. 예를 들어, 특정 장르의 앨범 제목을 찾기 위해, 최종 출력(앨범 제목)부터 시작하여 필요한 조건과 테이블을 연결하는 방식으로 쿼리를 구성할 수 있었다. 이 방식 덕분에 복잡한 쿼리도 논리적으로 접근하여 작성할 수 있게 되었다.

정리된 이해#

서브쿼리는 문제 해결을 위해 전체 쿼리를 거꾸로 생각하며 접근해야 한다는 점이 핵심이었고, 이를 위해 최종 출력부터 시작하여 필요한 정보를 단계별로 정의하는 템플릿을 활용하여 어려움을 극복했습니다. 이 템플릿을 통해 서브쿼리가 어떤 값을 반환해야 하는지 명확히 파악하고, 이를 메인 쿼리에 어떻게 연결할 수 있는지 이해할 수 있었습니다.

4. 서브쿼리 반환 값#

왜 이걸 보게 됐나#

처음 서브쿼리를 접했을 때, 어떤 값이 들어가야 할지 막막해서 쿼리가 제대로 작동하지 않았어요. 특히 메인 쿼리의 조건에 필요한 값을 어떻게 알아내야 할지 몰라, 서브쿼리가 어떤 값을 반환해야 하는지 명확히 정의하는 개념이 필요하게 됐습니다. 그래서 ‘서브쿼리 반환 값’을 이해하는 것이 쿼리 작성의 핵심이라는 것을 깨닫게 됐죠.

내가 헷갈린 지점#

서브쿼리가 어떤 값을 반환해야 하는지 이해하는 부분이 가장 어려웠다. 처음에는 서브쿼리가 단순하게 어떤 컬럼 값을 가져오는 것 이상으로, 메인 쿼리에 어떤 의미를 전달해야 하는지 파악하는 데 어려움을 느꼈다. 특히, 서브쿼리의 결과가 단일 값인지, 아니면 여러 개의 값으로 구성된 목록인지 판단하는 기준이 불분명했다.

시도한 코드 / 예시#

SELECT tracks.AlbumId

결과와 해석#

서브쿼리가 어떤 값을 반환해야 하는지 명확히 하는 과정에서, 예를 들어 tracks.AlbumId가 여러 개의 AlbumId 목록을 반환해야 한다는 것을 깨달았을 때, IN 연산자를 사용할 수 있다는 아이디어가 떠올랐다. 이는 서브쿼리의 결과를 메인 쿼리의 조건에 활용하는 중요한 연결고리라는 것을 이해하게 해주었다. 이러한 작은 실습을 통해 서브쿼리가 단순한 조작이 아닌, 복잡한 데이터를 효율적으로 다루는 핵심 요소임을 알게 되었다.

정리된 이해#

서브쿼리 반환 값은 메인 쿼리의 조건으로 사용될 데이터, 즉 쿼리가 최종적으로 어떤 값을 계산하거나 비교하기 위해 필요한 정보를 의미한다. 이 값은 단일 값이 될 수도 있고, 여러 값을 포함하는 목록이 될 수도 있으며, 메인 쿼리의 조건절에 적절한 연산자와 함께 사용되어 최종 결과를 도출하는 데 중요한 역할을 한다.

총평#

오늘 전체에서 배운 것#

서브쿼리를 작성할 때 메인 쿼리부터 접근하는 것이 어렵게 느껴졌지만, 단계별 템플릿을 활용하여 구조화된 접근법을 익혔다. 테이블 및 컬럼 연결에 어려움을 겪었지만, 쿼리 작성 과정을 체계화하여 문제 해결 능력이 향상되었다.

다음에 조심할 것#

테이블과 컬럼 이름 연결에 더 신경 써서, 자주 사용하는 테이블 관계를 빠르게 떠올릴 수 있도록 노력해야겠다. 서브쿼리의 반환 값 형태(단일 값 vs 목록)를 정확히 파악하는 것이 쿼리 작성의 핵심이라는 점을 잊지 말아야겠다.

다음 복습 주제#

서브쿼리 결과 형태가 단일 값인지 목록인지 판단하는 기준을 더 명확히 해야 할 것 같다. IN 연산자 외 다른 연산자를 사용할 때 서브쿼리의 반환 값 형태가 결과에 어떤 영향을 미치는지도 알아봐야겠다.
