1. 오프라인 평가와 데이터셋의 구분: RAG 실험 버전 관리#

무엇을 배웠나#

오프라인 평가는 실제 서비스 출시 전, 고정된 데이터셋을 기준으로 RAG 시스템의 답변 품질을 Judge LLM이 평가하는 과정입니다. 단순히 기대출력과 비교하는 것이 아니라, Hallucination과 AnswerRelevance 같은 기준을 통해 모델의 응답 내용과 문맥 적절성을 점검합니다. 이를 통해 프롬프트나 검색 설정을 변경했을 때 시스템 성능 변화를 실험적으로 비교할 수 있습니다.

헷갈렸던 점#

오프라인 평가에서 데이터셋에 정답이 등록되어 있어도, 시스템은 단순히 기대출력과 제출 답안을 비교하지 않습니다. 대신 Hallucination과 AnswerRelevance 같은 Judge LLM이 모델의 답변 내용과 문맥을 자체적으로 평가하여 점수를 매깁니다.

오프라인 평가는 실제 서비스 배포 전, 고정된 시험지(Dataset) 기준으로 RAG 시스템의 응답을 비교하는 과정입니다. 검색 기반 답변 생성 함수와 Judge LLM을 조합해 실험명(Experiment)으로 버전 관리하며, 프롬프트나 검색 설정을 변경했을 때 시스템이 어떻게 변하는지를 확인할 수 있게 해줍니다.

정리된 이해#

오프라인 평가는 실제 서비스 배포 전, 고정된 데이터셋을 기준으로 RAG 시스템의 답변 품질을 Judge LLM이 Hallucination과 AnswerRelevance 관점에서 평가하는 과정이다. 기대출력이 등록된다고 해서 자동 채점이 이루어지는 것이 아니라, 시스템이 문맥과 출력을 비교해 점수를 매기는 방식이다. 이를 통해 프롬프트나 검색 설정을 변경했을 때 시스템의 성능 변화를 비교 실험할 수 있다.

# [핵심 실습 예시: Opik을 이용한 RAG 오프라인 평가 구조]

from opik import Opik
from opik.evaluation import evaluate

# 1. 실험 환경 초기화 (트래킹 서버 연결)
client = Opik()

# 2. 데이터셋 정의 (질문과 기대컨텍스트 쌍)
dataset_name = "rag_offline_test"
data = [
    {"input": "What is the capital of France?", "expected_context": ["Paris history", "France geography"]},
    {"input": "Explain quantum computing basics", "expected_context": ["Qubit", "Superposition"]}
]
# 데이터셋 생성 또는 가져오기
get_or_create_dataset(client, dataset_name, data)

# 3. 평가 함수 정의 (Judge LLM 설정)
def task(item):
    # RAG 파이프라인 실행 (검색 + 답변 생성)
    answer, source_nodes = run_rag_pipeline(item["input"])

    return {
        "answer": answer,
        "source_nodes": source_nodes,
        "expected_context": item["expected_context"]
    }

# Hallucination과 AnswerRelevance를 평가할 Judge 모델 설정
judge_model = LiteLLMChatModel(model="gpt-4o-mini")

evaluate(
    client=client,
    task=task,
    dataset=dataset_name,
    model="nemotron", # 실제 배포된 RAG 모델명
    scores=["Hallucination", "AnswerRelevance"],
    judge_model=judge_model,
    experiment_name="rag_regression_test_v1"
)

2. Online Evaluation의 실제 운영과 피드백 관리#

무엇을 배웠나#

수업 전에는 LLM 답변 생성과 평가가 같은 과정으로 생각했으나, 실제로는 서로 다른 호출(call)을 통해 진행된다는 점을 깨닫고 혼란스러웠습니다. 특히 CPU 환경에서 두 번의 처리가 모두 지연되어 “답이 나왔는데 왜 기다리지?“라는 의문이 들곤 했습니다. 또한 Trace 대시보드에서 피드백을 검색할 때 점수 표시 이름이 달라지면 찾기 어려워지므로, 이름 관리의 중요성을 느꼈습니다. 온라인 평가는 정해진 데이터셋이 아닌 실제 사용자 질의에 대한 실행 경로 위에 결과를 붙여나가며 실시간 품질을 모니터링하는 방식이라는 점을 명확히 이해했습니다.

헷갈렸던 점#

강사님이 보여주신 04_online_eval.py 코드를 보며, LLM이 답을 생성하고 화면에 출력되는 과정이 전부라고 생각했습니다. 하지만 실제로는 답을 만든 LLM과 그 답변을 심사하는 Judge(평가자)가 서로 다른 호출(call)을 한다는 사실이 낯설었습니다.

또 한 가지는 강사님 코드에서 사용하는 'hal_online'이나 'rel_online' 같은 점수 표시 이름이 제 개인 수정본에서는 hall_online으로 바뀌어 있었습니다. 단순히 오타인 줄 알았는데, Trace 대시보드에서 나중에 이 피드백을 검색할 때 이름이 달라지면 찾기 어려워질 수 있어 신중해야 한다는 점을 깨닫고 혼란스러웠습니다.

정리된 이해#

온라인 평가는 사용자의 질문이 들어올 때마다 LLM이 답을 생성하고, 별도의 Judge가 그 결과를 평가하여 Trace에 피드백을 붙이는 실시간 모니터링 방식입니다. 오프라인 평가와 달리 정해진 데이터셋이 아닌 실제 상호작용 흐름상 점수가 매겨지며, 이때 호출 횟수와 피드백 이름 관리가 중요합니다.

# 1. LLM이 질문에 답변을 생성합니다.
response = query_engine.query(question)

# 2. Judge(평가자)가 답변을 검토하고 점수를 매깁니다.
feedback = judge.evaluate(response, question)

위 코드는 Online Evaluation의 핵심 구조를 보여줍니다. query_engine이 답을 만든 후, 별도의 judge 과정을 통해 Trace에 피드백이 기록됩니다.

3. Judge 모델 접속 오류와 환경별 URL 정리#

무엇을 배웠나#

RAG 답변용 LLM과 Judge(채점)용 LLM은 별도의 API 클라이언트라는 점이 핵심입니다. 모델명만으로는 기본 주소를 사용하지만, api_base를 명시해야 특정 포트나 환경에 정확히 연결됩니다. 또한 Windows에서 Docker 게시 포트와 컨테이너 내부 포트의 네트워크 경계를 명확히 이해하지 못하면 접속 오류를 디버깅하는 데 시간을 낭비하기 쉽습니다.

헷갈렸던 점#

Judge LLM과 RAG 답변 LLM은 별도의 API 클라이언트이며, 모델명만으로는 연결되지 않아 api_base를 명시해야 특정 포트에 접속할 수 있습니다. Windows 환경에서 Docker 컨테이너 내부 통신을 위해서는 호스트와 컨테이너의 포트 매핑 관계를 정확히 이해하는 것이 필수적입니다.

정리된 이해#

RAG 답변용 LLM과 Judge용 LLM은 별도의 API 클라이언트이며, 모델명만으로는 연결되지 않으므로 api_base를 명시적으로 지정해 주어야 특정 포트나 환경에 올바르게 연결됩니다. Windows Docker 환경에서는 호스트와 컨테이너 간의 포트 매핑(11435→11434) 관계를 정확히 이해해야만 접속 오류를 방지할 수 있습니다.

# ✅ 권장되는 Judge 모델 생성 방식 (강사님 03번 스타일)

from commons import OLLAMA_URL

judge_model = LLM(
    model_name="gemma4:e4b",
    api_base=OLLAMA_URL  # Windows 환경에서는 "http://localhost:11435" 등 환경별로 조정 필요
)

4. 공통 Judge 팩토리의 등장#

무엇을 배웠나#

강사님의 코드 업데이트에 대한 초기 혼란은, 로컬 환경 차이를 고려한 의도적인 설계였음을 깨닫고 해소되었다. 핵심 개념인 팩토리 패턴을 통해 모델 생성을 한곳에 집중함으로써 코드의 중복을 줄이고 일관성을 유지할 수 있게 되었다. 특히 기존 코드와 새 함수를 혼용하지 않아야 시스템 안정성이 확보된다는 점을 명확히 이해했다.

헷갈렸던 점#

강사님의 코드 업데이트 시 로컬 환경과 반드시 일치해야 한다는 막연한 두려움이 있었습니다. 하지만 commons.py를 통째로 복사하는 대신, 모델 주소나 포트 등 학습자마다 차이가 나는 파라미터는 개별적으로 관리하도록 설계된 것을 깨닫고 안도했습니다. 결국 기존 코드와 새 팩토리 함수를 혼용하면 시스템 안정성에 악영향을 줄 수 있다는 점을 명확히 이해하게 되었습니다.

정리된 이해#

공통 Judge 팩토리 함수는 모델 생성 시 필요한 파라미터를 한곳에 모아두는 ‘공장’ 역할을 하며, 각 실습 파일에서 반복되는 설정 코드를 호출하는 것만으로 대체할 수 있게 해준다. 특히 기존 LiteLLMChatModel 등 기존 코드와 새 factory 함수를 섞어 쓰지 않도록 주의해야 시스템 안정성을 유지할 수 있다.
