1. 테이블 연결 표#

왜 이걸 보게 됐나#

ERD 그림만 보니까 테이블 간 관계를 파악하기가 너무 어려워서, 어떤 테이블을 어떻게 연결해야 할지 막막했어. 테이블 연결 표를 사용하니까, 각 테이블이 어떤 컬럼으로 연결되는지 한눈에 보여서 훨씬 이해하기 쉬워졌어. 이제는 복잡한 테이블 관계도 명확하게 파악할 수 있게 됐어.

내가 헷갈린 지점#

처음에는 테이블 간의 관계를 ERD만 보고 파악하려고 했더니, 컬럼이 잘려 보여서 어떤 컬럼을 연결해야 할지 막막했습니다. 테이블 간의 연결 조건을 명확히 보여주는 테이블 연결 표가 있었다면 훨씬 쉽게 이해할 수 있었을 것 같았습니다. 또한, 어떤 테이블이 ‘중간’ 테이블인지, 어떤 테이블을 기준으로 연결해야 하는지 파악하는 데 어려움을 겪었습니다.

시도한 코드 / 예시#

- tracks.MediaTypeId = media_types.MediaTypeId
- invoices.CustomerId = customers.CustomerId
- playlists.PlaylistId = playlist_track.PlaylistId
       |                                  |
       |                                  |
       ↓                                  ↓
    tracks                                tracks

결과와 해석#

테이블 연결 표는 복잡한 ERD를 단순화하여 각 테이블 간의 관계를 명확하게 보여주기에, 어떤 컬럼을 JOIN에 사용해야 할지 빠르게 파악할 수 있게 도와줬습니다. 특히 여러 테이블을 연결할 때 어떤 순서로 테이블을 조인해야 하는지 시각적으로 보여주어, JOIN 조건 설정 오류를 줄여주었습니다. 덕분에 테이블 관계를 이해하는 데 훨씬 시간을 덜 쓰게 되었습니다.

정리된 이해#

테이블 연결 표는 복잡한 ERD를 이해하는 것보다 테이블 간의 관계를 명확하게 보여주어 어떤 컬럼을 어떻게 연결해야 할지 쉽게 파악할 수 있도록 도와줍니다. 이 표를 활용하면 테이블 간의 연결 과정을 시각적으로 보여주어 JOIN 구문을 작성하는 데 훨씬 도움이 됩니다. 특히 테이블이 여러 개일수록 그 효과가 더욱 두드러집니다.

2. 서브쿼리 선택 기준#

왜 이걸 보게 됐나#

처음에는 JOIN과 서브쿼리를 구분해서 사용할 때가 언제인지 감이 잘 안 잡혔어요. 어떤 문제를 해결할 때 어떤 방식을 선택해야 할지 막연하게 느껴져서, 서브쿼리 선택 기준을 명확히 이해하고 싶었습니다. 이를 통해 SQL 쿼리 작성 능력을 향상시키고 싶었습니다.

내가 헷갈린 지점#

처음에는 서브쿼리가 단순한 쿼리 안에서 또 다른 쿼리를 돌리는 것 이상으로 어떤 의미를 가지는지, 그리고 왜 필요한 건지 감이 잘 안 잡혔다. 단일 행과 다중 행 서브쿼리의 차이점도 무엇이 중요한 기준인지 파악하기 어려웠고, 쿼리를 작성할 때 JOIN과 서브쿼리 중 어떤 것을 선택해야 할지 판단하는 것이 버거웠다.

시도한 코드 / 예시#

SELECT FirstName, LastName, Email
FROM customers
WHERE CustomerId IN (SELECT CustomerId FROM invoices WHERE BillingCountry = 'Brazil');

결과와 해석#

평균 매출을 초과하는 인보이스를 조회하는 서브쿼리를 작성해보니, 평균 매출을 구하는 서브쿼리가 전체 쿼리의 WHERE절에서 조건을 걸어주는 역할을 한다는 것을 명확히 알 수 있었다. IN 연산자를 사용한 서브쿼리는 여러 개의 값을 비교할 때 유용하다는 것을 확인했고, FROM절에 서브쿼리를 사용하면 복잡한 분석을 위한 임시 테이블을 만들 수 있음을 깨달았다. 이러한 예제들을 통해 서브쿼리의 활용 범위와 역할에 대한 이해가 깊어졌다.

정리된 이해#

단일 값 비교에는 단일 행 서브쿼리를, 목록 조회에는 다중 행 서브쿼리를 사용하면 됩니다. 필요에 따라 서브쿼리를 임시 테이블처럼 활용할 수도 있습니다. JOIN과 서브쿼리 모두 데이터 추출을 위한 강력한 도구이지만, 상황에 따라 적절한 것을 선택하는 것이 중요합니다.

3. FROM 절 서브쿼리#

왜 이걸 보게 됐나#

FROM 절 서브쿼리는 JOIN으로 표현하기 복잡하거나, 테이블을 임시적으로 만들어 다른 쿼리에서 활용해야 할 때 유용하다는 것을 알게 되면서 배우게 되었습니다. 특히 복잡한 관계를 가진 데이터를 분석하거나, 집계된 결과를 기반으로 또 다른 쿼리를 실행해야 할 때 필요한 기술이라는 것을 깨달았습니다. JOIN만으로는 해결하기 어려운 상황에서 데이터를 효율적으로 다루는 방법을 배우고 싶어서 FROM 절 서브쿼리를 학습하게 되었습니다.

내가 헷갈린 지점#

처음에는 FROM 절 서브쿼리가 단순히 SELECT문의 일부라고 생각했는데, 실제로는 쿼리 실행 결과가 테이블처럼 사용되는 임시 테이블을 만드는 역할을 한다는 것을 이해하는 데 시간이 걸렸습니다. 마치 VIEW를 정의하는 것과 유사하지만, 명시적으로 VIEW를 생성하지 않고 쿼리 내에서만 사용하는 점이 낯설었습니다. 이 임시 테이블을 활용하여 복잡한 쿼리를 단순화할 수 있다는 점이 흥미로웠습니다.

시도한 코드 / 예시#

SELECT BillingCountry, total_sales
FROM (
    SELECT BillingCountry, SUM(Total) AS total_sales
    FROM invoices
    GROUP BY BillingCountry
) AS country_sales;

결과와 해석#

FROM 절 서브쿼리는 마치 임시 테이블을 만드는 것과 같습니다. 서브쿼리에서 계산된 값을 외부 쿼리에서 마치 테이블 컬럼처럼 활용할 수 있어서, 국가별 총 매출을 계산해서 보여주는 것처럼 복잡한 로직을 구현할 때 유용합니다. 이 서브쿼리를 통해 데이터를 가공하고 정리하는 과정을 SQL 쿼리 내에서 더 깔끔하게 처리할 수 있습니다.

정리된 이해#

FROM 절 서브쿼리는 쿼리 결과로 임시 테이블을 만들어서, 이를 마치 일반 테이블처럼 다른 쿼리에서 사용할 수 있도록 해줍니다. 이를 통해 복잡한 연산을 수행하거나, 기존 테이블에 없는 새로운 가상 테이블을 만들 수 있습니다. 특히, 여러 테이블을 조인하기 전에 중간 결과를 저장하거나, 집계 결과를 기준으로 추가적인 분석을 진행할 때 유용합니다.

4. 단일/다중 행 서브쿼리#

왜 이걸 보게 됐나#

JOIN과 서브쿼리를 배우면서 데이터를 효율적으로 연결하고 원하는 정보를 추출하는 방법을 익혀야 했는데, 헷갈리는 상황에서 어떤 쿼리 방식을 선택해야 할지 판단하기 어려웠어요. 단일 행과 다중 행 서브쿼리의 차이점을 명확히 이해해야 복잡한 쿼리도 논리적으로 작성할 수 있다는 것을 깨달았습니다.

내가 헷갈린 지점#

처음에는 서브쿼리가 항상 JOIN과 동일한 역할을 하는 것처럼 생각해서, 서브쿼리를 사용해야 할지 JOIN을 사용해야 할지 판단하기 어려웠다. 특히 다중 행 서브쿼리가 무엇을 의미하는지, 그리고 어떻게 활용해야 하는지 감이 잘 안 잡혔다. 어떤 조건을 만족하는 여러 개의 값을 가져올 때 IN을 사용해야 한다는 것을 나중에야 알게 되었다.

시도한 코드 / 예시#

SELECT FirstName, LastName, Email
FROM customers
WHERE CustomerId IN (SELECT CustomerId FROM invoices WHERE BillingCountry = 'Brazil');

결과와 해석#

단일 행 서브쿼리는 결과가 딱 하나의 값으로만 나오기 때문에 =, >, < 와 같은 비교 연산자를 사용해서 조건을 검사할 때 활용돼요. 반면 다중 행 서브쿼리는 여러 개의 값을 반환하기 때문에 IN이나 NOT IN과 같이 목록을 비교하는 데 사용하며, 특정 조건에 맞는 여러 행을 추출할 수 있습니다. 예를 들어, 브라질 고객이 발행한 인보이스의 고객 정보를 조회할 때 다중 행 서브쿼리를 사용해서 고객 ID 목록을 얻고, 이를 바탕으로 고객 정보를 가져오는 식으로 활용할 수 있습니다.

정리된 이해#

단일 행 서브쿼리는 비교 연산자를 통해 단 하나의 값과 비교하는 데 사용하고, 다중 행 서브쿼리는 여러 개의 값을 반환하여 목록과 비교할 때 활용합니다. 어떤 서브쿼리를 선택할지는 필요한 결과의 형태에 따라 결정되며, 복잡한 조건이나 목록 조회를 다룰 때 유용합니다. JOIN과 서브쿼리는 비슷한 결과를 낼 수 있지만, 가독성이나 성능을 고려하여 상황에 맞게 선택하는 것이 중요합니다.

총평#

오늘 전체에서 배운 것#

테이블 연결 표를 활용하여 복잡한 ERD를 이해하는 데 도움을 받았고, 서브쿼리의 종류에 따른 선택 기준을 명확히 구분할 수 있게 되었다. 특히 FROM 절 서브쿼리를 활용하여 임시 테이블을 생성하는 방법을 익혀, 복잡한 데이터 분석 쿼리를 작성하는 데 필요한 역량을 키웠다.

다음에 조심할 것#

ERD를 맹신하지 말고 테이블 연결 표를 활용해서 테이블 간의 관계를 명확하게 파악해야겠다. 서브쿼리의 단일/다중 행 여부를 결정할 때, 비교 연산자의 종류를 기준으로 판단하는 연습을 꾸준히 해야겠다. FROM 절 서브쿼리는 복잡한 쿼리를 단순화하는 강력한 도구이지만, 성능에 영향을 줄 수 있다는 점을 항상 염두에 두어야겠다.

다음 복습 주제#

FROM 절 서브쿼리의 성능 이슈와 최적화 방법에 대해 더 깊이 알아보고, 복잡한 JOIN 쿼리를 분석하고 튜닝하는 실습을 해보고 싶다. 또한, 서브쿼리와 JOIN의 성능 차이를 비교 분석하여 상황에 맞는 효율적인 쿼리 작성 방법을 익혀야겠다.
