1. express-08-board통합분석#

무엇을 배웠나#

처음에는 각 기능이 어느 단계에서 왔는지 구분하기 어려웠지만, 08_board가 05~07의 통합 프로젝트임을 깨닫고 나니 MongoDB, JWT, Express가 어떻게 어우러지는지 명확해졌습니다. 특히 mongoose-sequence 패키지를 통해 단순히 기능을 쓰는 것을 넘어, 밑바탕이 되는 라이브러리의 버전 관리까지 신경 써야 한다는 점을 새롭게 알게 되었습니다. 게시글 목록 조회 시 sort와 skip/limit를 활용한 페이지네이션, 상세보기에서 findOneAndUpdate로 조회수(bHit)를 동시 증가시키는 코드를 통해 실전 적용력을 기를 수 있었습니다.

헷갈렸던 점#

처음에는 08_board 폴더 안에 이전 단계(05~07)의 코드가 뒤섞여 있어, 각 기능이 어디서 왔는지 구분하기 어려웠습니다. 특히 mongoose-sequence 패키지를 보면서 단순히 기능을 사용하는 것을 넘어, 그 아래 깔린 라이브러리의 버전 관리까지 신경 써야 한다는 점이 초보자에게 진입장벽이 되었습니다.

정리된 이해#

08_board는 MongoDB, JWT, Express가 통합된 최종 프로젝트 단계로, 그동안 분산되었던 기능이 하나의 게시판 시스템에 집약됩니다. 핵심은 sort, skip, limit을 활용한 페이지네이션과 findOneAndUpdate를 통한 조회수 증가 구현입니다. 이를 통해 의존성 관리와 통합된 라우팅 구조의 전체 흐름을 이해하게 되었습니다.

// list 라우터 및 컨트롤러 내부
const list = async (req, res) => {
    const page = parseInt(req.query.page) || 1;
    const limitNum = 5; // 한 페이지당 게시물 수

    const posts = await boardModel
        .find({})
        .sort({ idx: -1 })      // idx 내림차순 정렬 (최신글 우선)
        .skip((page - 1) * 5) // 페이지 건너뛰기
        .limit(limitNum);     // 한 페이지당 5개 제한

// 게시글 상세보기 컨트롤러 내부
const detail = async (req, res) => {
    const { idx } = req.params;

    // findOneAndUpdate를 통해 조회수 증가와 동시에 데이터 조회
    const post = await boardModel.findOneAndUpdate(
        { idx: Number(idx) },
        { $inc: { bHit: 1 } },
        { new: true }
    );
};

2. 이미지 업로드와 CRUD 확장: 멀티미디어 기능 보강 journey#

무엇을 배웠나#

multer를 사용한 파일 업로드 방식이 단순한 URL 저장보다 복잡하지만, 실제 파일을 서버에 보관해야 할 때 필수적임을 이해했습니다. Express와 MongoDB를 연동하여 이미지 경로 문자열만 DB에 저장하고, 실제 파일은 uploads 폴더에 물리적으로 보관하는 구조를 설계했습니다. 쿼리 필터와 $inc 같은 연산자를 활용해 기분과 좋아요 수 기능을 직관적으로 구현할 수 있는 방법을 구체화했습니다.

헷갈렸던 점#

처음에는 이미지 업로드를 단순히 “서버에 파일 저장하기"로만 생각하여, multipart/form-data와 multer 같은 새로운 개념들이 연달아 등장하면서 진입 장벽이 높았습니다. 특히 DB에 이미지 데이터 자체를 저장해야 하는지, 아니면 경로 문자열만 저장하면 되는지 감 잡지 못해 막막했습니다. 결국 기존 CRUD와 JWT 지식을 확장하여, 업로드된 파일의 이름을 문자열로 MongoDB에 저장하는 방식으로 방향을 설정했습니다.

정리된 이해#

이미지 업로드를 위해서는 multipart/form-data 전송 방식과 multer 미들웨어를 활용해 클라이언트에서 선택한 파일을 서버의 uploads/ 폴더에 저장하고, 실제 이미지 파일 자체는 보관하지 않고 경로 문자열만 MongoDB에 저장하는 방식으로 진행한다.

// 1. 미들웨어 설정 (multer 사용)
const multer = require('multer');
const upload = multer({ dest: 'uploads/' });

// 2. 게시글 생성 라우트 (이미지 업로드 포함)
router.post('/', upload.single('image'), async (req, res) => {
  try {
    const newPost = new Post({
      title: req.body.title,
      content: req.body.content,
      image: `/uploads/${req.file.filename}`, // DB에 경로 문자열 저장
      mood: req.body.mood,
      author: req.user._id
    });
    await newPost.save();
    res.status(201).json(newPost);
  } catch (err) {
    res.status(400).json({ message: err.message });
  }
});

// 3. 게시글 목록 조회 (pagination 및 mood 필터링)
router.get('/', async (req, res) => {
  const page = parseInt(req.query.page) || 1;
  const limit = parseInt(req.query.limit) || 10;
  const skip = (page - 1) * limit;

  const filter = {};
  if (req.query.mood) filter.mood = req.query.mood;

  const posts = await Post.find(filter)
    .skip(skip)
    .limit(limit)
    .sort({ createdAt: -1 });

  const total = await Post.countDocuments(filter);

  res.json({
    data: posts,
    currentPage: page,
    totalPages: Math.ceil(total / limit),
    totalPosts: total
  });
});

3. 페이지네이션 UI 흐름과 조건 로직#

무엇을 배웠나#

처음에는 DB의 skip와 limit만으로 페이지네이션이 끝나는 줄 알았지만, 마지막 페이지인지 판단하기 위해 totalPages를 알아야 UI 버튼을 제어할 수 있다는 점에서 큰 혼란이 있었다. 페이지네이션은 단순히 데이터를 잘라오는 것을 넘어, 백엔드에서 계산한 정보를 API가 전달하고 UI가 버튼의 활성화 여부를 결정하는 3층 구조라는 점을 깨달았다. 특히 [다음]이나 [끝] 버튼을 구현할 때, 단순히 page + 1을 하는 것이 아니라 전체 페이지 수와의 비교 로직이 필수적이라는 점이 가장 중요한 통찰이었다.

헷갈렸던 점#

처음에는 DB에서 skip와 limit만 잘 적용하면 페이지네이션이 끝나는 것으로 생각했습니다. 하지만 실제로는 마지막 페이지인지(totalPages) 확인해야지만 UI 버튼을 활성화하거나 비활성화할 수 있다는 점이 가장 큰 혼란이었습니다. 데이터를 잘라오는 것과 전체 구조를 파악하는 것은 완전히 다른 차원의 문제였습니다.

정리된 이해#

페이지네이션은 DB에서 데이터를 슬라이싱하는 것을 넘어, Backend가 계산한 전체 개수와 페이지 수를 API로 전달하고 UI가 이를 기반으로 버튼의 활성화 상태를 제어하는 3층 구조입니다. 특히 [끝]이나 [이전] 버튼처럼 현재 위치와 전체 범위를 비교하여 로직을 적용해야만 올바른 네비게이션이 가능해집니다.

페이지네이션 핵심 로직 (Backend → API → UI)#

1. Backend Layer (DB 계산)#

// MongoDB 예시: skip, limit, countDocuments를 통한 전체 개수 및 데이터 범위 계산
const page = parseInt(req.query.page) || 1;
const limit = parseInt(req.query.limit) || 10;
const skip = (page - 1) * limit;

const [articles, totalCount] = await Promise.all([
  Article.find().skip(skip).limit(limit),
  Article.countDocuments()
]);

const totalPages = Math.ceil(totalCount / limit);

return {
  list: articles,
  page,
  pageSize: limit,
  totalCount,
  totalPages
};

2. API Layer (정보 전달)#

{
  "list": [...],           // skip((page-1)*limit) ~ limit(5)의 결과 데이터
  "currentPage": 2,      // 클라이언트가 요청한 현재 페이지 번호
  "pageSize": 5,         // 한 페이지에 표시할 아이템 수
  "totalCount": 47,      // 전체 데이터 개수
  "totalPages": 10       // 전체 페이지 수 (Math.ceil(47/5))
}

3. UI Layer (버튼 제어 로직)#

// 페이지 네비게이션 버튼 활성화/비활성화 상태 결정 함수
const paginationControls = {
  hasPrevPage: currentPage > 1,
  hasNextPage: currentPage < totalPages,

  // [처음] 버튼: 현재 페이지가 1이면 비활성화
  isFirstDisabled: currentPage === 1,

  // [끝] 버튼: 현재 페이지가 전체 페이지 수면 비활성화
  isLastDisabled: currentPage === totalPages,

  // [이전] 버튼: 1 미만이면 비활성화 (경계값 처리)
  isPrevDisabled: currentPage <= 1,

  // [다음] 버튼: 전체 페이지 수를 초과하면 비활성화
  isNextDisabled: currentPage >= totalPages
};

💡 핵심 통찰#

단순히 page + 1을 연산하는 것이 아니라, [끝] 버튼은 항상 totalPages까지 이동해야 하며, [이전]은 페이지 번호가 1 미만이 되면 자동으로 비활성화되어야 한다는 조건 로직이 필수적입니다.

총평#

오늘 오후 전체에서 배운 것#

오늘은 express-08-board 통합 분석을 통해 MongoDB, JWT, Express가 어우러지는 구조를 명확히 이해했으며, 특히 mongoose-sequence 패키지를 통한 버전 관리와 실전 페이지네이션 구현의 중요성을 새롭게 인식했습니다. 또한 멀티미디어 기능 보강 과정에서 multer를 활용한 파일 업로드 구조를 설계하고, 쿼리 필터와 $inc 연산자를 통해 직관적인 기능을 구현하는 방법을 구체화했습니다. 마지막으로 LearningLog와 Project의 역할을 명확히 구분함으로써 코드의 목적과 위치를 정확히 분리할 수 있게 되었습니다.

다음에 조심할 것#

오늘은 코드의 목적과 위치를 명확히 구분하는 것이 무엇보다 중요하다는 점을 뼈저리게 느꼈다. 특히 LearningLog와 Project의 역할 혼동은 향후 개발 속도를 저해하는 큰 요인이 될 수 있어, 앞으로는 반드시 ‘배운 기술인지, 실행 가능한 코드인지’를 먼저 확인하고 폴더 구조를 잡아야겠다. 또한 페이지네이션 구현 시 단순히 DB 쿼리만 신경 쓰는 것이 아니라, 전체 페이지 수를 기반으로 한 UI 제어 로직까지 꼼꼼히 설계하지 않으면 버튼이 먹통이 되는 치명적인 버그를 낳을 수 있음을 명심하고 다음 단계로 넘어가야겠다.

다음 복습 주제#

다음에 복습할 주제#

  2. 미디어 업로드 및 스토리지 관리: multer를 활용한 파일 업로드의 전체 흐름과, 서버에 물리적인 파일을 보관할 때 경로 문자열만 DB에 저장하는 구조의 장단점을 명확히 이해했습니다. 향후 실제 서비스 배포 시 용량 관리와 백업 전략을 어떻게 연계해야 하는지 복습하겠습니다.
