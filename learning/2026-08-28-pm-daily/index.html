1. 회원 CRUD 패턴 통찰과 적용 과정#

무엇을 배웠나#

오늘 드디어 회원 CRUD 기능을 모두 완성했습니다. 그동안 각 기능이 독립된 것처럼 느껴졌지만, 알고 보니 모두 같은 Router → Model → DB 흐름 안에서 동작한다는 점을 깨닫고 이해가 깊어졌습니다. 이제 Create, Read, Update, Delete의 패턴을 익혀서 실무에서 바로 적용할 수 있게 되었습니다.

헷갈렸던 점#

처음에는 각 기능이 독립된 것처럼 보여서 혼란스러웠지만, 알고 보니 모두 같은 Router → Model → DB 흐름 안에서 동작한다는 점을 깨닫는 데 시간이 걸렸습니다. 특히 HTTP Method가 CRUD의 의미를 결정짓는다는 부분과, req.body를 꺼내 Model에 전달하는 과정이 모든 기능에서 반복된다는 점이 처음에는 낯설었습니다.

정리된 이해#

모든 CRUD 기능은 요청을 받아 값을 꺼내고 Model로 DB 작업을 수행한 뒤 결과를 반환하는 동일한 패턴 안에서 동작한다. 오전에 만든 MongoDB와 Mongoose 연결 ‘뼈대’ 위에 회원가입, 조회, 수정, 삭제 기능을 추가하면서, 각 기능이 독립된 것이 아니라 같은 Router → Model → DB 흐름 안에서만 동작 방식이 다르다는 것을 깨달았다.

// 1. Create - 회원가입 (POST)
router.post('/', async (req, res) => {
  const newUser = new User(req.body);
  await newUser.save();
  res.json({ success: true });
});

// 2. Read - 회원조회 (GET)
router.get('/', async (req, res) => {
  const users = await User.find();
  res.json(users);
});

// 3. Update - 수정 (PUT)
router.put('/:id', async (req, res) => {
  await User.findByIdAndUpdate(req.params.id, req.body);
  res.json({ success: true });
});

// 4. Delete - 삭제 (DELETE)
router.delete('/:id', async (req, res) => {
  await User.findByIdAndDelete(req.params.id);
  res.json({ success: true });
});

2. JWT 인증 흐름과 return 제어의 중요성#

무엇을 배웠나#

JWT 인증은 요청이 들어오면 토큰을 먼저 검사하는 ‘인증 게이트’ 역할을 하며, 토큰이 유효하지 않으면 즉시 응답을 보내고 함수를 종료해야 한다. return 키워드 없이 인증 실패 응답을 보낸 경우, 아래 코드가 계속 실행되어 중복된 응답이나 에러가 발생할 수 있다. 따라서 JWT 검증 로직 뒤에는 반드시 함수 실행을 중단하는 return이 따라와야 안전하다.

헷갈렸던 점#

JWT 인증 로직이 들어가면 토큰 유무에 따라 실행 경로가 갈라지는데, return 키워드 없이 응답을 보내면 아래 코드가 계속 실행되어 중복된 응답이나 에러가 발생할 수 있다는 점이 가장 헷갈렸다. 특히 인증 실패 시 401 응답을 보낸 뒤에도 return이 없으면 다음 비즈니스 로직이 실행되어 의도치 않은 결과가 나오기 쉽다. 따라서 JWT 검증 후 반드시 함수를 종료하는 return이 따라와야만 안전하게 흐름을 제어할 수 있다.

정리된 이해#

JWT 인증은 요청이 들어오면 토큰을 먼저 검사하는 ‘인증 게이트’ 역할을 하며, 유효하지 않을 경우 즉시 응답을 보내고 함수를 종료해야 한다. return 키워드는 인증 실패 시 아래 코드가 실행되어 중복된 응답이나 에러가 발생하는 것을 방지하기 위해 반드시 따라와야 한다. 따라서 토큰 검증 로직 뒤에는 항상 함수 실행을 중단하는 return이 필수적으로 위치해야 한다.

// 미들웨어 함수
const authenticateToken = (req, res, next) => {
  const authHeader = req.headers['authorization'];
  const token = authHeader && authHeader.split(' ')[1];

  if (!token) {
    return res.status(401).json({ message: '토큰이 없습니다.' });
  }

  jwt.verify(token, process.env.ACCESS_TOKEN_SECRET, (err, user) => {
    if (err) {
      return res.status(403).json({ message: '토큰이 유효하지 않습니다.' });
    }

    req.user = user;
    next(); // 다음 미들웨어로 이동
  });
};

3. Express 프로젝트 구조 이해하기#

무엇을 배웠나#

Express 기본 프로젝트에서 파일 이름은 그 역할을 설명하는 것보다, 해당 파일이 서버 구성에서 어떤 위치에 있는지(역할)를 먼저 파악하는 것이 핵심입니다. app.js, db.js 등 각 파일의 기능보다는 “지금 이 코드가 서버에 어떤 영향을 미치는가?“를 먼저 생각하면 자연스럽게 파일의 위치와 기능을 이해할 수 있습니다. 오늘 실습에서는 서버 시작점인 app.js부터 데이터베이스 연결(db.js), Schema 정의(models), API 라우팅(routers)까지 순차적으로 연결하며 전체 흐름을 확인했습니다.

헷갈렸던 점#

수업 중 가장 혼란스러웠던 부분은 ‘파일 이름’과 ‘역할’의 매칭이었습니다. app.js, db.js, model.js 같은 파일명을 보고 대충 감을 잡으려 했으나, 실제로 어떤 기능을 담당하는지 순식간에 오가다 보니 어느 순간 “이 파일이 서버를 켜는 건지, 데이터를 저장하는 건지” 구분이 안 되곤 했습니다.

핵심은 파일의 이름보다는 그 파일이 서버 구성에서 어떤 위치에 있는지(역할)를 먼저 파악하는 것입니다. Express 기본 프로젝트는 크게 ‘실행/조립’, ‘데이터 연결’, ‘데이터 규칙’, ‘API 제공’, ‘테스트’, ‘인증’의 6가지 역할로 나뉘며, 파일 이름을 외우려 애쓰기보다 “지금 이 코드가 서버에 어떤 영향을 미치는가?“를 먼저 생각하면 자연스럽게 파일의 위치와 기능이 눈에 들어오게 됩니다.

정리된 이해#

Express 기본 프로젝트에서 파일 이름은 그 파일의 역할을 설명하기보다, 서버 구성에서의 위치를 파악하는 데 집중해야 한다. 각 파일이 서버에 어떤 영향을 미치는지(실행, 데이터 연결, 규칙 정의, API 제공 등)를 먼저 이해하면 자연스럽게 기능과 위치가 눈에 들어온다. 따라서 app.js를 시작점으로 하여 db.js, 모델, 라우터 등이 순차적으로 서버를 완성하는 흐름을 파악하는 것이 핵심이다.

// app.js - 서버의 시작점 (Entry Point)
// Express 애플리케이션 인스턴스 생성 및 미들웨어/라우터 연결
const express = require('express');
const app = express();
const port = 3000;

// 기본 미들웨어 설정 (JSON 파싱 등)
app.use(express.json());

// 라우터 파일 연결 (기능별 모듈화)
const userRouter = require('./routers/user'); // ./routers/user.js
const postRouter = require('./routers/post'); // ./routers/post.js

app.use('/users', userRouter);  // /users 경로 아래에서 userRouter 실행
app.use('/posts', postRouter);  // /posts 경로 아래에서 postRouter 실행

// 서버 시작 (리스닝)
app.listen(port, () => {
  console.log(`서버가 http://localhost:${port} 에서 실행 중입니다.`);
});

// models/User.js - 사용자 스키마 정의
const mongoose = require('mongoose');

const userSchema = new mongoose.Schema({
  username: {
    type: String,
    required: [true, '사용자 이름은 필수입니다.'],
    unique: true,
    trim: true,
    minlength: [3, '이름은 최소 3글자 이상이어야 합니다.']
  },
  email: {
    type: String,
    required: [true, '이메일은 필수입니다.'],
    unique: true,
    lowercase: true,
    match: [/^\w+([\.-]?\w+)*@\w+(\.\w+)+$/, '올바른 이메일 형식이 아닙니다.']
  },
  password: {
    type: String,
    required: [true, '비밀번호는 필수입니다.'],
    minlength: [6, '비밀번호는 최소 6자리 이상이어야 합니다.'],
    select: false // 비밀번호를 조회 시 기본적으로 제외
  },
  createdAt: {
    type: Date,
    default: Date.now
  }
});

// 인스턴스 메서드: 비밀번호 비교 (로그인 시 사용)
userSchema.methods.comparePassword = async function(candidatePassword) {
  return candidatePassword === this.password; // 실제 프로젝트에서는 bcrypt 사용 권장

// 스태틱 메서드: 이메일 중복 확인

  return this.findOne({ email: email });

module.exports = mongoose.model('User', userSchema);

// routes/auth.js - 인증 관련 라우터
const express = require('express');
const router = express.Router();
const User = require('../models/User');

// POST /api/auth/register - 회원가입
router.post('/register', async (req, res) => {
  try {
    const { username, email, password } = req.body;

    // 이메일 중복 확인
    const existingUser = await User.findByEmail(email);
    if (existingUser) {
      return res.status(409).json({ message: '이미 가입된 이메일입니다.' });
    }

    // 새 사용자 생성
    const user = new User({
      username,
      email,
      password // 실제 프로젝트에서는 해시화(password hashing) 필수!
    });

    await user.save();

    res.status(201).json({
      message: '회원가입이 성공적으로 완료되었습니다.',
      user: {
        id: user._id,
        username: user.username,
        email: user.email
      }
    });
  } catch (error) {
    console.error('❌ 회원가입 오류:', error);
    res.status(500).json({ message: '서버 내부 오류가 발생했습니다.' });
  }
});

module.exports = router;

오늘은 이전 실습으로 만든 UI 코드를 새로 짜야 할지 고민하다가, 결국 1일차에 구축한 Express API와 연동하는 통합 단계임을 깨달았습니다. 프론트엔드 화면에 실제 데이터가 흐르는 연결 고리를 놓는 것이 이번 과제의 핵심 목표였습니다. 이를 통해 백엔드와 프론트엔드를 HTTP API 계약으로 연결하는 실전적인 경험을 쌓을 수 있었습니다.

오늘은 ‘새로운 문법을 배우는 날’인지, ‘이미 만든 화면과 실제 서버를 연결하는 날’인지 구분이 가지 않아 혼란스러웠습니다.

결국 핵심은 1일차에 만든 Express API를 UI에서 실제로 사용하는 통합 단계였으며, 단순히 화면을 꾸미는 것을 넘어 데이터가 오가는 관문을 만드는 작업이 목표였습니다.

정리된 이해#

오늘은 Next.js UI 코드를 새로 짜는 것이 아니라, 기존에 만든 Express API와 화면을 연결하는 통합 단계였습니다. 핵심은 프론트엔드와 백엔드를 HTTP API 계약으로 잇는 ‘데이터 흐름’을 만드는 과정입니다. 실습 순서는 API 정상 작동 확인부터 시작해 목록 조회, 글 작성, 로그인 토큰 전달, 라우팅 연결까지 진행하는 것이 목표입니다.

// 1. API 엔드포인트 정의 (Express 서버 side)
const express = require('express');
const app = express();
app.use(express.json());

let articles = []; // 메모리 DB

// GET: 목록 조회 (데이터 연결 시작점)
app.get('/api/articles', (req, res) => {
  res.json(articles);
});

// POST: 글 작성 (데이터 전송)
app.post('/api/articles', (req, note) => {
  const newArticle = { id: Date.now(), title: req.body.title };
  articles.push(newArticle);
  res.status(201).json(newArticle);
});

app.listen(3000, () => console.log('Server running on port 3000'));

// 2. Next.js 페이지에서 API 연결 (useEffect + axios)
import { useState, useEffect } from 'react';
import axios from 'axios';

function ArticleList() {
  const [articles, setArticles] = useState([]);
  const [loading, setLoading] = useState(true);

  // GET 요청: 서버로부터 데이터 불러오기
  useEffect(() => {
    async function fetchArticles() {
      try {
        const response = await axios.get('http://localhost:3000/api/articles');
        setArticles(response.data);
      } catch (error) {
        console.error(error);
      } finally {
        setLoading(false);
      }
    }
    fetchArticles();
  }, []);

  if (loading) return <p>로딩 중...</p>;

  return (
    <ul>
      {articles.map((article) => (
        <li key={article.id}>{article.title}</li>
      ))}
    </ul>
  );
}

export default ArticleList;

총평#

오늘 오후 전체에서 배운 것#

오늘은 Express와 MongoDB를 활용한 회원 CRUD 기능을 완성하며, 라우터-모델-DB 흐름이 일관되게 동작한다는 패턴을 확실히 익혔습니다. JWT 인증 로직에서 return 키워드의 위치가 함수 종료와 중복 응답 방지에 결정적임을 깨닫고, 안전한 코드 작성의 중요성을 체감했습니다. 마지막으로 구축한 Express API와 Next.js 프론트엔드를 연동하여, 백엔드와 프론트엔드가 HTTP API 계약으로 유기적으로 연결되는 실전적인 흐름을 경험했습니다.

다음에 조심할 것#

  • return 키워드를 인증 로직 뒤 반드시 사용하여, 토큰 검증 실패 시 즉시 함수 종료와 응답 전송을 보장하고 아래 코드 실행으로 인한 중복 에러를 방지해야 한다.
  • Express 프로젝트에서 파일명보다는 해당 파일이 서버 흐름상 어떤 역할을 수행하는지(라우팅, DB 연결 등)를 먼저 파악하여 전체적인 구조를 이해하는 것이 중요하다.

다음 복습 주제#

오늘은 Express와 MongoDB, JWT 인증을 연계한 전체적인 흐름을 이해하는 데 집중했습니다. 특히 회원 CRUD가 하나의 일관된 패턴으로 동작한다는 점과, JWT 검증 시 return 문의 위치가 얼마나 중요한지 명확히 깨달았습니다. 이제 각 기능이 독립적이지 않고 Router → Model → DB로 이어지는 연결 고리 안에서 작동한다는 사실을 바탕으로 실무 프로젝트에서 적용할 수 있는 기반을 다졌습니다.

다음 복습 주제는 다음과 같습니다. 첫째, JWT 인증 미들웨어 내에서 return 문의 필수성을 다시 확인하고, 토큰이 없을 경우와 유효하지 않을 경우의 분기 로직을 구체적으로 정리하여 실무에서 발생할 수 있는 에러를 예방하는 방법을 익히겠습니다. 둘째, Express 프로젝트 구조에서 파일별 역할보다는 요청 흐름(라우팅 → 컨트롤러 → 모델 → DB) 중심으로 디렉터리를 구성하고 설계하는 연습을 하여, 코드의 위치와 기능을 직관적으로 파악할 수 있는 안목을 기르겠습니다.
