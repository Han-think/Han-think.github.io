1. 질문 변환과 검색의 차이, Multi-Query와 HyDE#

무엇을 배웠나#

질문 자체가 검색을 방해할 수 있다는 점을 깨닫고, Multi-Query와 HyDE가 단순히 다른 표현이 아니라 recall과 semantic similarity를 높이는 서로 다른 접근법임을 명확히 이해했습니다. 특히 query transformation이 retrieval pipeline에서 핵심적인 역할을 한다는 점이 가장 인상적이었습니다.

헷갈렸던 점#

처음에는 LLM이 답변을 만드는 과정과 검색을 위한 질의 변환 과정이 어떻게 다른지 분간하기 어려웠습니다. 특히 HyDE가 ‘LLM이 가짜 답변을 만들어내는 것 아닐까’라는 걱정을 했습니다.

또 한 가지 헷갈린 점은 Multi-Query와 HyDE의 차이점이 명확하지 않다는 점이었습니다. 질문의 관점을 여러 개 만드는 것인지, 가상의 문서를 만드는 것인지 구별이 안 되었던 것입니다.

핵심적으로 ‘질문 자체가 검색에 방해가 될 수 있다’는 점을 이해할 수 있었습니다. 짧고 모호한 질문은 벡터 검색조차도 정답을 놓칠 수 있다는 사실이 인상적이었습니다.

가장 중요했던 깨달음은 “검색이 안 되면 무조건 임베딩 모델부터 바꾸기보다, 질문이 너무 짧거나 추상적인 것은 아닌지 먼저 점검해야 한다"는 점이었습니다. query transformation은 retrieval pipeline의 중요한 단계가 될 수 있습니다.

정리된 이해#

질문 자체가 검색을 방해할 수 있다는 점을 깨닫고, 임베딩 모델 변경 전 항상 질문 길이를 점검하는 습관을 들였습니다.

Multi-Query는 다양한 표현의 질문을 추가 생성해 recall을 높이고, HyDE는 가상의 답변을 만들어 의미적 유사성을 통해 더 나은 문서를 찾는 방식입니다.

# Multi-Query 예시 (강사님 common.py 기준)
original_question = "한번 더 거르기"
transformed_questions = multi_query(original_question)

2. 두 단계 검색의 원리: retriever와 reranker roles#

무엇을 배웠나#

벡터 검색은 넓은 범위에서 빠르게 후보군을 발굴하는 역할을 하고, 크로스 인코더는 그 후보들 사이의 순서를 정밀하게 재배치하여 가장 관련성 높은 문서를 최상위로 끌어올리는 역할을 한다. 두 단계 구조는 빠른 retriever와 비싼 reranker의 장점을 결합해 효율적으로 정확도를 높이는 전략이다. 특히 1차 검색에서 정답이 하위권에 밀려 있어도, reranker가 이를 상위로 끌어올릴 수 있다는 점은 검색 성능 최적화의 핵심임을 확인할 수 있었다.

헷갈렸던 점#

벡터 검색은 넓은 범위에서 대략적인 관련성을 판단해 후보를 발굴하는 역할이고, 크로스 인코더 리랭커는 이미 선정된 후보들 사이의 순서를 정밀하게 조정하는 과정이라는 점이 핵심이었다. 1차 검색에서 정답이 하위에 밀려 있어도, 리랭커가 이를 상위로 끌어올려 최종 결과를 결정한다는 점을 이해하는 데 시간이 걸렸다.

정리된 이해#

벡터 검색은 넓은 범위에서 후보군을 빠르게 확보하는 역할을 수행하고, 크로스 인코더 리랭커는 이미 선정된 후보들 사이의 순서를 정밀하게 재조정하여 가장 관련성이 높은 문서를 최상위로 끌어올리는 과정이다. 이 두 단계 구조는 빠른 retriever와 비싼 reranker의 장점을 결합해 검색 효율과 정확도를 동시에 높이는 전략이다.

# 1차 검색: 넓은 후보군 확보
candidates = vector_search(query, k=6)
# [문서3, 문서1, 정답_문서7, 문서5, 문서2, 문서8]

# 2차 reranking: 정밀한 순위 조정
reranked = cross_encoder.rerank(query, candidates)
# [정답_문서7, 문서3, 문서1, 문서5, 문서2, 문서8]

3. retrieval pipeline 통합: 기법별 k값 의미와 단계별 목적 정리#

무엇을 배웠나#

오늘은 검색 기법들이 하나의 파이프라인에서 어떻게 순차적으로 연결되는지 이해하는 데 집중했습니다. 각 단계별로 k 값이나 목적 등이 달라 혼란스러웠지만, 오후에 보여진 파이프라인 흐름을 통해 각 기법의 역할이 명확해졌습니다. 특히 Multi-Query와 Vector Search, RRF, Re-Rank가 어떻게 후보를 넓히고 정제하는지 구체적인 순서와 목적을 익힐 수 있었습니다.

헷갈렸던 점#

처음에는 k 값이 각 단계에서 다른 의미를 가지는지 구분하기 어려웠고, 여러 검색 기법이 따로 배워진 이유를 전체적인 흐름 속에서 연결 짓기 힘들었습니다. 하지만 파이프라인 구조를 통해 각 기법이 후보 생성, 융합, 재정렬 순서로 명확한 역할을 담당한다는 사실을 깨닫고 이해가 되었습니다.

정리된 이해#

오늘은 검색 기법들이 하나의 파이프라인 안에서 순차적으로 연결되어 검색 품질을 개선하는 패턴을 이해했습니다. Multi-Query, Vector Search, BM25, RRF, Re-Rank 등 각 단계는 목적과 대상이 다르며, k 값 또한 단계별로 의미가 달라 혼동 없이 설정해야 합니다. 결국 이러한 기법들을 조립하여 최종적으로 LLM이 근거가 있는 답변을 생성할 수 있도록 후보 문서를 선별하는 것이 핵심입니다.

# 06_pipeline.py (핵심 파이프라인 구조)

from typing import List, Dict

class RetrievalPipeline:
    def __init__(self, k_multi_query: int = 3, k_vector: int = 50,
                 k_bm25: int = 100, k_rrf: int = 60, k_rerank: int = 20):
        """
        파이프라인 초기화 시 각 단계별 k 값의 역할을 명확히 구분합니다.

        - k_multi_query: Multi-Query 단계에서 질문 변형 개수
        - k_vector: Vector Search 후보 수 제한
        - k_bm25: BM25 후보 수 제한
        - k_rrf: RRF 융합 전후 후보 수 관리
        - k_rerank: Re-Rank 최종 상위 선택 수
        """
        self.k_multi_query = k_multi_query
        self.k_vector = k_vector
        self.k_bm25 = k_bm25
        self.k_rrf = k_rrf
        self.k_rerank = k_rerank

    def run(self, query: str, vector_store, bm25_index, reranker, llm):
        """
        전체 검색 파이프라인을 실행합니다.
        """
        # 1. Multi-Query: 질문을 변형하여 다양한 관점에서 검색
        queries = self._generate_multi_queries(query, self.k_multi_query)

        # 2. Vector + BM25: 의미적 검색과 키워드 검색 동시에 수행
        vector_results = self._vector_search(queries, vector_store, self.k_vector)
        bm25_results = self._bm25_search(query, bm25_index, self.k_bm25)

        # 3. RRF: 서로 다른 검색 방식의 결과를 융합
        fused_results = self._rrf_fusion(vector_results, bm25_results, self.k_rrf)

        # 4. Re-Rank: 후보들을 정밀하게 재정렬
        reranked_results = self._rerank(fused_results, query, reranker, self.k_rerank)

        # 5. LLM: 최종 context를 바탕으로 답변 생성
        answer = self._generate_answer(query, reranked_results, llm)

        return answer

4. 에이전트 RAG, 판단의 순간: 초보자의 혼란과 기댓값#

무엇을 배웠나#

나는 강사님의 Git에 올라온 12_search 폴더의 retrieval pipeline을 통해, 검색 과정이 Multi-Query → Hybrid → Rerank → LLM의 순서로 고정되어 있음을 확인했다. 그리고 Agentic RAG는 이 흐름에 ‘상태를 판단해 다음 행동을 스스로 선택하는 단계’가 추가된다는 점을 개인적으로 정리했다. 아직 실제 코드는 확인되지 않았지만, 후보 생성→평가→다음 단계 구조 안에 판단이 개입된다고 생각하면 진입이 수월할 것 같다.

헷갈렸던 점#

  1. ‘에이전트’가 단순히 정해진 순서를 따르는 것이 아니라, 현재 검색 상태를 판단하여 다음 행동을 스스로 결정한다는 점이 가장 큰 차이점이었다.
  2. 기존 retrieval pipeline에서 부족한 결과를 보완하는 주체가 인위적인 흐름이 아닌, 스스로 판단하는 에이전트라는 점에 혼란을 느꼈다.
  3. 강사님의 실제 구현 코드가 아직 공개되지 않아, 이론과 실제 적용 사이의 간극을 어떻게 메울지 감이 잡히지 않았다.

정리된 이해#

나는 오늘 LearningLog 파이프라인에서 ‘에이전틱 RAG’라는 개념을 마주했으나, 강사님의 Git에는 아직 해당 관련 코드가 없어 막연한 혼란에 빠졌다. 그럼에도 불구하고 나는 기존의 12_search 폴더 retrieval pipeline이 사람이 정해진 순서(Multi-Query → Hybrid → Rerank → LLM)로 동작한다는 사실만 확신할 수 있다. 그리고 에이전트 RAG는 이 흐름 속에 검색 결과를 보고 스스로 판단하여 다음 행동을 선택하는 단계를 추가한 개념이라고 해석하고 있다.

# Agentic RAG의 핵심: 상태 기반 판단 루프 (가상/예비 구현)
# 아직 강사님의 실제 소스는 확인되지 않았지만, 개념적 구조를 정리한 예시입니다.

from typing import Literal, Optional

StepResult = Literal["continue", "answer", "search"]

def agentic_rag_loop(query: str, max_iterations: int = 3) -> str:
    """
    Agentic RAG의 기본 흐름.
    1. 검색 → 2. 평가 → 3. 판단(계속/답변)으로 반복
    """
    iteration = 0
    context = []

    while iteration < max_iterations:
        iteration += 1

        # 1. Search (검색)
        # 실제 구현에서는 retriever나 tool이 호출됨
        new_docs = retrieve_documents(query, context)
        context.extend(new_docs)

        # 2. Evaluate (평가)
        relevance_score = assess_relevance(query, context)

        # 3. Judge (판단) - 다음 단계 결정
        decision: StepResult = decide_next_step(relevance_score, iteration)

        if decision == "answer":
            # 답변 생성
            answer = generate_answer(query, context)
            return answer
        elif decision == "search":
            # 더 검색 계속
            continue
        else:
            break

    # 반복 종료 시 기본 답변 반환
    return generate_answer(query, context)


def retrieve_documents(query: str, existing_context: list) -> list:
    """검색 도구 호출 예시 (가상)"""
    # 실제로는 벡터 DB 검색 등 수행
    return []

def assess_relevance(query: str, context: list) -> float:
    """관련성 점수 산출 (가상)"""
    return 0.8

def decide_next_step(score: float, iteration: int) -> StepResult:
    """다음 단계 판단 로직 (가상)"""
    if score < 0.5 or iteration >= 3:
        return "answer"
    return "continue"

def generate_answer(query: str, context: list) -> str:
    """LLM 기반 답변 생성 (가상)"""
    return f"질문 '{query}'에 대한 답변입니다."

총평#

오늘 오후 전체에서 배운 것#

오후에는 검색 파이프라인 전체가 어떻게 유기적으로 연결되는지 이해하는 데 집중했습니다. retriever와 reranker의 역할 분담과 각 단계별 k값 및 목적의 차이를 명확히 하여, 단순한 검색 기법 나열을 넘어 최적화된 pipeline 구조를 파악할 수 있었습니다. 특히 Multi-Query부터 RRF, Re-Rank까지 후보를 넓히고 정제하는 구체적인 흐름을 통해, 검색 성능 향상이 어떻게 단계적으로 이뤄지는지 전체적인 그림이 그려졌습니다.

다음에 조심할 것#

오늘은 검색 파이프라인 전체가 하나의 유기적인 흐름으로 연결된다는 점을 명확히 이해했습니다. 특히 retriever와 reranker가 각자의 역할을 수행하며 후보군을 선별하고 정제하는 과정이 중요하다고 느꼈습니다. 앞으로는 단순히 검색 결과를 나열하는 것이 아니라, 왜 특정 기법이 사용되는지 그 목적을 가지고 파이프라인을 설계하는 습관을 들일 것입니다.

다음 복습 주제#

오늘은 검색 파이프라인 전체가 하나의 흐름으로 연결된다는 점을 확실히 이해할 수 있었다. retriever와 reranker가 각자의 역할을 충실히 수행하며, Multi-Query 같은 기법들이 후보군을 얼마나 넓히느냐에 따라 이후 단계의 성패가 갈린다는 점이 인상 깊었다. 특히 검색 과정 안에 ‘판단’이 개입되는 Agentic RAG 구조가 어떻게 작동할지, retrieval pipeline 내에서의 순서와 목적 관계를 명확히 짚어두고 다음 복습을 준비해야겠다.

다음 복습 주제는 검색 단계별 k값과 후보군 관리 전략이다. retriever에서 가져오는 초기 개수(k), RRF나 Re-Rank 과정에서 어떻게 임계치를 조절하는지, 그리고 LLM에 전달할 최종 문서 수를 어떻게 결정하는지가 파이프라인 성능의 핵심 열쇠가 된다는 점을 정리하고 싶다.

다음 복습 주제는 Agentic RAG의 판단 로직과 상태 전이이다. 단순히 검색을 반복하는 것이 아니라, 현재 retrieved된 문서들이 LLM의 질문에 얼마나 부합하는지 판단하고 다음 단계(재검색, 요약, 종료 등)를 스스로 결정하는 메커니즘이 어떻게 설계되는지가 핵심 포인트가 될 것이다.

다음 복습 주제는 하이브리드 검색(Retrieval)의 실제 적용 시나리오다. keyword 기반과 vector search의 장단점을 어떻게 조합해 RRF 점수를 매기는지, 그리고 특정 도메인이나 질문 유형에 따라 가중치를 두는 전략이 retrieval precision에 미치는 영향을 구체적으로 살펴보고 싶다.
