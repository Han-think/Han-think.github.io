1. MongoDB·Express·Next.js 동시 실행하기#

무엇을 배웠나#

웹 애플리케이션이 정상 동작하려면 MongoDB, Express 백엔드, Next.js 프론트엔드 등 모든 요소가 동시에 실행되어야 한다는 점을 명확히 이해하게 되었다. 특히 프론트엔드만 구동된 상태에서는 화면은 표시되지만 실제 기능인 로그인이나 게시글 조회가 작동하지 않는다는 사실을 깨닫고, 백엔드의 역할을 데이터 연결 고리로 인식할 수 있게 되었다. 실습을 통해 mongod 명령어로 MongoDB를 실행한 뒤 Express와 Next.js를 순차적으로 구동하는 과정을 경험하며, 세 구성 요소의 필수적인 상호작용 관계를 체감했다.

헷갈렸던 점#

처음에는 코드 자체에 오류가 있는 줄 알았는데, 실제로는 백엔드나 데이터베이스가 실행되지 않아 API 요청이 처리되지 않는 경우가 많았습니다. 특히 프론트엔드만 켜져 있어도 화면은 뜨지만 로그인이나 게시글 조회 같은 기능은 작동하지 않아서 혼란스러웠습니다. 웹 애플리케이션을 동작시키려면 MongoDB, Express 백엔드, Next.js 프론트엔드가 모두 실행된 상태여야 한다는 점을 깨닫게 되었습니다.

정리된 이해#

웹 애플리케이션이 정상 동작하려면 MongoDB, Express 백엔드, Next.js 프론트엔드의 세 가지 요소가 모두 실행 중이어야 한다. 특히 CRUD 기능 등 실제 기능을 사용하려면 백엔드가 반드시 켜져 있어야 하며, 프론트엔드는 UI만 그리는 ‘그림’에 불과하다. 따라서 개발 전 필수적으로 모든 프로세스를 동시에 구동해야 서비스가 완성된다.

MongoDB · Express · Next.js 동시 실행하기#

🔍 무엇이 헷갈렸나 (Confusion Point)#

처음에는 프로젝트의 모든 파일이 준비되어 있는데 화면이나 기능이 동작하지 않으면, **“코드 자체에 오류가 있는 것 아닐까?”**라는 생각이 들었습니다. 특히 Next.js 프론트엔드만 실행해도 페이지는 뜨는데, 로그인이나 게시글 조회 같은 기능이 작동하지 않을 때 저는 “백엔드 코드가 잘못된 건가?” 혹은 “데이터베이스 연결에 문제가 생긴 건가?” 하며 불안해했습니다.

가장 큰 혼란은 **“파일이 다 있는데 왜 안 되지?”**라는 기대와 “실행 중인 프로세스가 없는 상태” 사이의 간격이었습니다. 백엔드나 데이터베이스가 켜져 있지 않으면 API 요청이 공중분해되는 줄 알았는데, 프론트엔드는 그냥 에러 화면이나 로딩 상태로 멈춰있으니 뭔가 이상하다고 느꼈습니다.

📚 정리된 이해 (Corrected Understanding)#

웹 애플리케이션이 제대로 동작하려면 세 가지 요소가 모두 살아있는 상태여야 합니다.

  1. MongoDB: 데이터가 저장되고 읽히는 저장소
  2. Express 백엔드: 비즈니스 로직을 처리하고 MongoDB와 통신하는 다리
  3. Next.js 프론트엔드: 사용자 인터페이스를 보여주고 사용자의 요청을 백엔드로 전달

구조적으로는 아래와 같이 연결되어 있습니다.

MongoDB  ↔  Express  ↔  Next.js  ↔  Browser

특히 중요한 점은, 프론트엔드만 실행해도 화면은 열릴 수 있지만, 로그인, 게시글 조회, 글쓰기 같은 실제 기능(CRUD)을 사용하려면 백엔드가 반드시 켜져 있어야 한다는 점이었습니다. 프론트엔드는 UI만 그리는 ‘그림’이고, 백엔드는 그 그림에 데이터를 채워주는 ‘내부 장치’와 같았습니다.

💡 실습 예시 (Practice Example)#

실제 수업 시간에 따라한 실행 과정입니다.

1. MongoDB 실행 터미널에서 mongod 명령어를 통해 데이터베이스 서버를 켰습니다.

2. Express 백엔드 실행 백엔드 폴더로 이동하여 npm run dev 혹은 node index.js 명령어로 서버를 구동했습니다.

3. Next.js 프론트엔드 실행 프론트엔드 폴더에서 npm run dev 명령어로 개발 서버를 시작했습니다.

이 세 가지가 모두 실행된 상태에서야 비로소 브라우저에서 애플리케이션을 사용하고 API 요청이 MongoDB에 도달하여 데이터를 주고받을 수 있었습니다.

2. WebStorm 터미널 경로 중복 입력 오류 정리#

무엇을 배웠나#

CLI 명령어는 현재 위치를 기준으로 상대적인 이동을 수행한다는 점을 이해했습니다. WebStorm 터미널은 이미 프로젝트 폴더 경로를 자동으로 설정해 주기 때문에, 상위 폴더 이름을 다시 입력하면 중복된 경로가 생성되어 오류가 발생합니다. 따라서 현재 위치에서 바로 하위 폴더로 이동하는 . 접두사 사용이 핵심임을 깨달았습니다.

헷갈렸던 점#

CLI에서 cd 명령어는 현재 위치를 기준으로 상대적인 이동을 수행한다는 점을 간과하고, 단순히 문법만 외우려다 보니 상위 폴더 이름이 중복되어 경로가 엉뚱하게 해석되는 혼란이 발생했습니다. WebStorm 터미널은 프로젝트 폴더를 열면 자동으로 해당 경로를 가리키므로, 별도의 루트 이동 없이 cd .\폴더명만으로도 충분하다는 점을 깨닫고 나서야 상대경로와 절대경로의 차이를 정확히 이해할 수 있었습니다.

정리된 이해#

CLI에서 cd 명령어는 현재 위치를 기준으로 상대 경로를 해석하므로, 상위 폴더 이름을 중복 입력하면 시스템이 “현재 위치 + 입력한 경로"를 합쳐 의도치 않은 깊이 있는 폴더로 이동하게 된다. WebStorm 터미널은 프로젝트 폴더를 열면 자동으로 해당 폴더 경로를 현재 위치로 설정해 주기 때문에, 상위 폴더 이름을 다시 붙이지 않고 .\폴더명만 입력하면 정확히 원하는 하위 폴더로 이동할 수 있다.

# 상황: WebStorm 한 창에서 `express` 폴더를 열고, 백엔드와 프론트엔드를 각각 실행하는 경우.

1.  **WebStorm 구성**:
    *   프로젝트 트리: `express/` 아래에 `project_web(백엔드)`, `project_front(프론트엔드)`가 있음.

2.  **터미널 1 (Backend)**:
    *   현재 위치 확인: `D:\shared_study\express`
    *   명령어: `cd .\project_web` (현재 폴더 기준 project_web로 이동)

3. EADDRINUSE 포트 충돌 해결하기#

무엇을 배웠나#

EADDRINUSE 에러는 서버가 켜지지 않은 장애가 아니라, 이미 실행 중인 포트 충돌 상황을 알리는 상태 보고서라는 점을 깨달았습니다. 기존에 실행된 Next.js dev server가 백그라운드에서 종료되지 않고 남아있는지 확인하는 것이 우선이며, 브라우저로 localhost 접속해 화면이 보이는지 확인한 후 재실행하는 순서를 따르는 것이 중요합니다.

헷갈렸던 점#

처음에는 에러 메시지가 ‘서버가 켜지지 않았다’는 장애 신호로 직관적으로 느껴져 당황했으나, 실제로는 이미 실행 중인 서버가 포트를 점유하고 있는 상태였습니다. 따라서 단순히 재시도하거나 코드를 수정하기보다, 기존 백그라운드 프로세스가 살아있는지 확인하는 것이 우선이었습니다.

정리된 이해#

EADDRINUSE 에러는 서버가 이미 실행 중이라는 상태 보고서이며, 이를 해결하려면 먼저 백그라운드에서 동작하는 기존 Next.js 서버를 종료한 뒤 재실행해야 한다.

# EADDRINUSE 오류 해결을 위한 실습 예시

# 1. 기존 서버 종료 (이미 실행 중일 경우)
pkill -f "next dev"  # 또는 Ctrl+C

# 2. 포트 확인 및 강제 종료 (필요 시)
lsof -i :3000       # 3000번 포트를 점유한 프로세스 찾기
kill -9 <PID>     # 해당 프로세스 강제 종료

# 3. 서버 재실행
npm run dev

4. 요청 흐름 따라 디버깅하기#

무엇을 배웠나#

연결 순서대로 문제를 파악하는 디버깅 사고방식이 가장 큰 도움이 되었습니다. 무작위 수정이 아닌, 요청 흐름을 따라가며 어디서 끊겼는지 pinpointing 하는 습관이 생겼습니다. 특히 문제 유형별로 404, 401, 500 등 각각의 의미를 명확히 구분하여 진단할 수 있게 되었습니다. 앞으로 새로운 기능을 추가할 때도 Frontend부터 Database까지 순차적으로 확인하며 효율적으로 문제를 해결할 수 있을 것입니다.

헷갈렸던 점#

처음에는 에러가 발생하면 모든 시스템이 잘못된 줄 알았고, 화면이나 데이터가 안 보일 때 frontend, backend, database를 두루 의심하다 정작 문제 지점을 찾는 데 시간이 오래 걸렸습니다. 핵심은 무작위 수리가 아니라 요청 흐름(User → Frontend → Backend → Database)을 따라가며 어디서 끊겼는지 pinpointing 하는 순서 확인이었습니다.

정리된 이해#

디버깅은 무작위 수정이 아닌 요청 흐름(User → Frontend → Backend → Database)을 따라가며 문제 지점을 정확히 파악하는 과정입니다. 특히 오류 유형별로 화면 표시 여부, 상태 코드, 인증 관련 이슈를 구분해 확인하면 해결 속도가 크게 빨라집니다.

# LearningLog 워킹 노트: 전체 요청 흐름과 디버깅 순서

🔍 무엇이 헷갈렸나 (Confusion Point)#

처음에는 “에러가 나면 모든 게 잘못된 줄 알았습니다.” 가장 큰 혼란은 **‘어디부터 손을 대야 할지’**였습니다. 브라우저에서 화면이 안 뜨거나 데이터가 안 보이면, Next.js 코드 문제인가 싶다가도, API 서버(Express) 문제가 아닐까 하고 전전긍긍하다가 결국 데이터베이스(MongoDB) 연결 문제인 경우도 많았죠. 세 영역(Frontend, Backend, Database)을 두루 의심하다 보니, 정작 문제가 나는 지점을 찾는 데 시간이 오래 걸리고 방황하게 되었습니다.

📌 정리된 이해 (Corrected Understanding)#

핵심은 **“연결 순서대로 확인하는 것”**이었습니다. 무작위로 고치는 것이 아니라, 요청이 흐르는 경로(User → Next.js → Express → MongoDB → 역순)를 그대로 따라가며 어디에서 끊겼는지 pinpointing 하는 것입니다.

특히 문제 유형별 기준을 두니 매우 실용적이었습니다.

  • 화면 자체가 안 뜸: Frontend 문제 (스타일, 컴포넌트 오류 등)
  • 404: 경로(Route)나 URL 설정 문제
  • 401: 인증(JWT/Token) 관련 문제
  • 500: Backend 또는 DB 실행 오류
  • CORS: Frontend와 Backend 사이의 통신 연결 문제
  • EADDRINUSE: 포트 충돌로 인한 시작 실패

“안 된다"는 하나의 문제가 아니라, “어디까지 되는가? 어디서부터 끊기는가?“를 먼저 확인하는 사고방식이 생긴 것이 가장 큰 수확입니다.

💡 실습 예시 (Project Connection)#

오늘 배운 디버깅 순서는 단순히 이번 과제에만 국한되지 않습니다. login, image upload, mood filter, pagination 등 이후 진행하게 될 모든 기능의 디버깅에도 그대로 적용할 수 있습니다. MongoDB 실행 확인부터 API 직접 테스트까지의 흐름을 몸에 익혀두면, 새로운 기능을 추가했을 때 훨씬 빠르게 문제를 해결할 수 있을 것 같습니다.

5. 파일 트리와 실행 프로세스의 분리#

무엇을 배웠나#

폴더 트리와 실행 프로세스는 별개의 개념이라는 점을 명확히 이해하게 되었다. 파일 구조가 프로그램의 동작 상태를 의미하지 않는다는 사실에 큰 혼란을 느꼈고, 이를 해결하기 위해 실제 터미널에서 서비스를 직접 실행해보는 과정을 거쳤다. 그 결과 MongoDB, Express, Next.js 각각이 다른 포트에서 실행되는 것을 확인하고, 브라우저 접속을 통해 전체 시스템이 정상 동작함을 검증할 수 있었다.

헷갈렸던 점#

폴더에 파일이 존재한다는 것과 프로그램이 실제로 실행되어 포트를 열고 있는 것은 완전히 다른 개념이다. 특히 윈도우 환경에서 MongoDB, Express, Next.js가 각각 다른 포트에서 동작하는지 확인하는 것이 어려웠다.

‘폴더 트리(Folder Tree)‘는 코드의 조직 구조를 보여주는 시각적 레이아웃이지만, ‘실행 프로세스(Process Tree)‘는 메모리에 올라가 실제 서비스를 수행하고 있는 프로그램의 상태다. “프로젝트가 정상 동작한다"는 것은 단순히 파일이 존재하는 것이 아니라, MongoDB와 Express, Next.js가 모두 실행 중이며 HTTP 통신이 이루어지고 있어야 한다는 것을 깨달았다.

정리된 이해#

폴더 트리는 코드 조직도를 의미하며, 실행 프로세스는 메모리에 올라가 포트를 여는 실제 프로그램 상태를 뜻한다. 프로젝트가 정상 동작한다는 것은 MongoDB, Express, Next.js 등 모든 의존 서비스가 실제로 실행 중이며 HTTP 통신이 이루어지고 있음을 의미한다.

# 폴더 트리 vs 실행 프로세스

파일 구조 (Folder Tree)#

  • app.js, db.js 등 코드가 존재하는 디렉토리 layout
  • “파일이 존재한다"는 것만으로는 프로그램 구동 여부 불명확

실행 상태 (Process Tree)#

  • 메모리에 올라간 실제 프로그램 인스턴스들
  • 포트(27017, 80, 3000) 점유 여부로 확인 가능

동작 조건 (All Must Be True)#

  1. MongoDB 프로세스 구동 (mongod 또는 서비스 실행)
  2. Express 백엔드 구동 (node app.js)
  3. Next.js 프론트엔드 구동 (npm run dev)
  4. HTTP 통신 정상 여부 확인 (localhost:3000)

6. 콘솔 로그, 개발자의 ‘관찰 도구’ as-is (as is)#

무엇을 배웠나#

console.log()는 프로그램 실행 결과를 보여주는 출력이 아니라, 개발자가 코드 내부를 들여다보는 ‘관찰 도구’라는 점을 깨달았다. 처음에는 불필요한 방해 요소로 느껴졌지만, 자동차 계기판처럼 내부 상태를 점검하는 필수적인 기능임을 이해했다. 핵심은 의심 가는 지점에만 찍고 문제를 해결한 뒤 정리를 하는 것이다.

헷갈렸던 점#

처음에는 console.log()가 프로그램 실행 시 화면에 보여지는 최종 결과물로 오해했습니다. 그래서 코드 곳곳에 값을 찍는 행위가 최종 결과물을 흐트러뜨리는 방해 요소라고 생각했죠. 하지만 로그의 위치와 의미를 명확히 구분하지 못해 “언제, 왜 찍어야 하는지” 감을 잡지 못했던 것이 진짜 혼란의 원인이었습니다.

정리된 이해#

console.log()는 사용자에게 보여주는 최종 결과물이 아니라, 개발자가 코드 내부를 들여다보는 ‘관찰 도구’다. 자동차 계기판처럼 프로그램 실행 중 발생하는 내부 상태를 확인하는 용도로 활용해야 한다. 따라서 로그의 의미를 명확히 설명하는 앞부분 문자열을 작성하고, 문제 해결 후에는 불필요한 출력을 정리하는 습관이 중요하다.

// 데이터를 보내기 전 상태 확인
console.log('보내기 전 데이터', data);

// Express 라우트 진입 직후 확인
console.log('req.body', req.body);

// DB 조회 결과 확인
console.log('조회 결과', result);

// 올바른 사용 예시
console.log('login body', req.body);  // 무엇을 확인하는지 명시
console.log('token', token);

7. 서버 재시작, ‘상태 맞춤’을 위한 필수 과정#

무엇을 배웠나#

재시작은 단순한 전원 공급이 아니라, 현재 실행 중인 프로세스가 수정된 코드를 읽고 있는지 확인하는 ‘상태 맞춤’ 과정임을 깨달았다. 수정 내용과 대상 프로세스를 먼저 질문한 뒤, 자동 리로드 환경인지 판단하여 적절히 재시작하거나 반영해야 한다는 점에서 이전의 무조건적인 restart 습관을 교정할 수 있었다.

헷갈렸던 점#

“재시작"이 단순히 전원을 껐다 켜는 행위인지, 코드 변경 사항을 반영하는 작업인지 구분하지 못해 혼란스러웠습니다. 특히 Next.js와 Express 같은 프레임워크에 따라 자동 갱신 여부가 달라져, 언제 다시 시작해야 할지 타이밍을 잡기 어려웠습니다. 또한 문제 발생 시 무조건 재시작하는 습관이 debugging의 일부인지 단순히 문제를 덮는 행위인지 구분되지 않아 고민이 컸습니다.

정리된 이해#

재시작은 단순한 전원 공급이 아니라, 현재 실행 중인 프로세스가 수정된 코드를 읽고 있는지 확인하는 작업이다. 수정 내용과 대상 프로세스, 자동 리로드 여부를 먼저 판단한 뒤 반영 상태를 점검해야 한다.

8. 프로젝트 상태와 원인을 묻는 AI 활용법#

무엇을 배웠나#

AI에게 단순히 기능을 요청하는 것보다, 현재 프로젝트의 상태와 오류 원인을 정확히 설명하는 것이 훨씬 효과적입니다. 특히 디버깅이나 기능 추가 시, 실패한 단계와 기대 결과 및 실제 결과를 구조적으로 묻는 것이 정답에 빠르게 도달하는 핵심입니다.

헷갈렸던 점#

AI에게 코드를 짜달라고 하기보다 현재 상태와 원인을 묻는 방식이 훨씬 효과적이라는 점을 깨닫게 된 계기입니다.

처음에는 AI가 “코드를 만들어주는 도구"라는 생각에 단순히 기능만 요청했습니다. 하지만 프로젝트를 진행하면서 내 프로젝트의 기존 라우팅 구조, 데이터베이스 스키마, 설정된 포트 번호 등 ‘상황’을 고려하지 않은 코드가 돌아와 충돌이 발생했습니다. AI가 “할 수 있다"고 말하는 것과, 내 프로젝트 전체에서 “적절하다"는 판단은 다르다는 점을 깨닫고 나니, 단순히 기능을 달라는 질문보다 현재의 상태를 정확히 설명하는 것이 중요하다고 생각하게 되었습니다.

AI 활용의 핵심은 **“생성"이 아니라 “상태 전달과 원인 규명”**에 있습니다. AI에게 코드를 짜달라고 하기 전에, 현재 내가 어떤 상태에 있는지, 어디가 문제인지 명확히 전달하는 과정이 필요합니다. 특히 디버깅이나 기능 추가 요청 시, 무작정 “해결해줘"라는 식의 질문보다는 **‘어떤 단계에서 실패했는지’, ‘기대한 결과와 실제 결과는 무엇인지’**를 구조적으로 묻는 것이 훨씬 효과적입니다. AI도 전체 맥락을 모르고 추측하기 때문에, 사용자가 프로젝트의 제약 조건과 현재 상태를 먼저 알려주면 훨씬 정합성 있는 답변을 얻을 수 있습니다.

처음에는 헷갈렸거나 오해했던 점을 2~3문장으로 요약하면 다음과 같습니다.

AI가 만들어주는 코드가 내 프로젝트와 잘 맞지 않아 당황한 적이 많았습니다. 단순히 기능만 요청하면 AI는 최신 트렌드나 일반적인 패턴을 반영하지만, 내 프로젝트의 기존 라우팅 구조, 데이터베이스 스키마, 현재 설정된 포트 번호 등 ‘상황’을 고려하지 않은 경우가 많아 충돌이 발생했습니다. AI가 “할 수 있다"고 말하는 것과, 내 프로젝트 전체에서 “적절하다"는 판단은 다른 것이라는 점을 깨닫고 나니, 단순히 기능을 달라는 식의 질문보다 현재의 상태를 정확히 설명하는 것이 무엇보다 중요하다는 생각이 들었습니다.

정리된 이해#

AI에게 코드를 짜달라고 요청하기보다, 현재 프로젝트의 상태와 구체적인 오류 상황을 먼저 설명하는 것이 정답에 도달하는 가장 빠른 길입니다.

9. 기능 구현 전, 목적에 맞는 범위 조절하기#

무엇을 배웠나#

“할 수 있다"는 가능성은 무수히 많지만, 그것이 프로젝트의 목적에 부합하는지는 별개의 문제다. 따라서 기능 구현 전 전체 시스템의 정합성과 목적을 먼저 확인하고, 목적에 맞지 않는 기능을 과감히 배제해야 한다.

정리된 이해#

가능성은 기술적 구현 가능성을 뜻하지만, 적합성은 프로젝트의 목적과 현재 학습 범위와의 일치 여부를 의미한다. 따라서 무조건 작은 것부터 시작하기보다 전체 시스템의 정합성과 목적을 해치지 않는 선에서 필요한 최소 단위를 선택해 scope를 조절하는 것이 핵심이다.

# 핵심 요약

🟢 초보자 시점, 학습자의 혼란#

처음 들었을 때 이 문장은 참으로 따뜻하고 현실적인 조언처럼 들렸다. “작은 것부터 시작해서 하나씩 쌓아가자"는 의미였으니까. 하지만 막상 코드를 쓰려니 모든 기능이 “구현 가능"하다는 사실이 발목을 잡았다. 게시판 한 개 만들려고 해도 이미지 업로드, 좋아요, 댓글, 검색, 채팅… 목록은 끝이 없다. “할 수 있다"는 말이 너무 포괄적이어서, 가능성만으로 기능을 계속 추가하다 보면 어느새 거대한 엉키기 쉬운 시스템이 되어버릴 것 같은 공포가 들었다. 핵심적인 혼란점은 “능력(가능성)“과 “적합성(필요성)“을 구분하지 못한 채 진행하면 안 된다는 점이었다.

📌 정리된 이해#

강사님의 말씀을 단순히 “작게 시작하라"는 뜻으로만 받아들이면 위험하다. 가능성은 문법적이든 기술적이든 무수히 많지만, 그것이 프로젝트의 전체 목적에 부합하는지는 별개의 문제이기 때문이다. 그래서 **“전체 틀을 먼저 본 뒤, 그 안에서 필요한 최소 단위를 선택해서 작게 구현한다”**는 원칙으로 보강했다. 핵심은 기능 하나하나가 성공하는 것이 아니라, 전체 시스템의 정합성과 목적을 해치지 않는 선에서 시작해야 한다는 점이다.

🛠️ 실습 예시: Photo Mood 게시판#

현재 진행 중인 프로젝트에서도 이 딜레마를 겪었다. 기능별로 가능 여부를 따져보니 음악, AI 추천, 채팅, 검색 등 화려한 기능들이 즐비했다. 하지만 프로젝트의 목적과 현재 학습 범위를 고려해 이미지, mood, 좋아요, pagination 네 가지로 범위를 확 좁혔다. 단순히 “못 해서 안 한 것"이 아니라, **“목적에 맞지 않는 기능을 과감히 배제(scope를 조절한 것)”**이라는 점이 무엇보다 중요했다.

10. 개발 디버깅의 ‘흐름’과 ‘관찰#

무엇을 배웠나#

나는 개발이 단순히 문법을 외우는 것이 아니라, **‘어디를 봐야 하는지 아는 것’**과 **‘에러 발생 시 무엇을 확인해야 하는지’**의 방향성 잡기에 있음을 깨달았다.

특히 console.log()의 타이밍과 ‘할 수 있는 것부터’라는 접근 방식에 대한 고민을 통해, 전체 구조를 무시한 채 기능만 구현하면 나중에 정합성 문제가 생긴다는 점을 이해하게 되었다. 결국 각 단계는 하나의 반복된 루프로 연결되며, 문제를 해결하는 순서를 파악하는 것이 핵심임을 배웠다.

헷갈렸던 점#

  1. console.log()가 단순히 문법일 뿐 아니라, 데이터 흐름을 파악하기 위한 ‘시점 조절’ 도구라는 점을 깨닫는 데 시간이 걸렸다.
  2. “작은 것부터 한다"는 말이 전체 구조를 무시하는 것은 아닌지 걱정했지만, 실제로는 문제 발생 시 복구를 위한 필수적인 순서임을 체감했다.
  3. 각 메모가 따로 보면 추상적이었지만, 프로젝트 경험을 통해 이들이 ‘디버깅을 위한 반복 루프’로 연결된다는 사실에 가장 큰 확신을 가졌다.

정리된 이해#

개발은 코드 문법 외에 ‘어디를 봐야 하는지’ 파악하는 것이 핵심이며, 디버깅은 전체 구조 확인부터 작은 단위 구현까지 반복되는 루프로 작동한다.

1. [전체 구조 확인]: FE → app.js → router
2. [문제 위치 파악]: 에러 메시지, 콘솔 로그, 스택 트레이스 분석
3. [데이터 흐름 추적]: 변수 값 변경, API 응답, 상태 관리(State Management)
4. [해결책 적용 및 검증]: 코드 수정, 테스트 실행, 결과 확인
5. [반복 및 최적화]: 로그 레벨 조정, 디버거 사용법 숙지, 리팩토링

총평#

오늘 오후 전체에서 배운 것#

오후에는 MongoDB, Express, Next.js가 서로 어떻게 상호작용하며 전체 시스템을 구동하는지 이해하고, 터미널 경로 오류와 포트 충돌 해결법을 학습했습니다. 특히 console.log()를 단순한 출력이 아닌 개발자의 관찰 도구로 활용하고, 무작위 수정보다는 요청 흐름을 따라 문제를 파악하는 디버깅 사고방식을 확립하여 효율적인 문제 해결 능력을 기를 수 있었습니다.

다음에 조심할 것#

  1. 터미널 경로 입력 시 절대 경로가 아닌 현재 위치 기준의 상대 이동(.)을 사용해 중복 오류를 방지한다.
  2. 서버 재시작 전 기존 프로세스가 종료되지 않았는지 확인하고, 자동 리로드 환경인지 판단하여 불필요한 restart를 피한다.

다음 복습 주제#

  1. 실행 환경과 디버깅의 기초: MongoDB, Express, Next.js 등 각 컴포넌트가 독립적인 포트에서 실행되며, 이들의 순차적 구동과 경로 관리(상대경로 vs 절대경로) 오류 해결법을 숙지해야 한다.

  2. 문제 해결을 위한 체계적 사고: EADDRINUSE 같은 에러는 포트 충돌 상태를 의미하며, 무작위 수정보다는 요청 흐름(요청→응답→DB)을 따라가며 로그를 관찰하는 습관이 효율적인 디버깅의 핵심이다.
