1. AWS EC2와 Linux OS 개념 분리하기#

무엇을 배웠나#

AWS 인프라와 Linux OS를 ‘어디에 있는가’ 기준으로 분리하여 개념을 정리할 수 있었습니다. 특히 EC2, Security Group, Storage 등 인프라 요소와 yum, timedatectl 같은 OS 명령어를 명확히 구분하니 흐름이 이해되었습니다. 이를 통해 서버 생성 후 OS 준비, 그리고 애플리케이션 실행이라는 순서대로 학습 진행 방향이 잡혔습니다.

헷갈렸던 점#

AWS 인프라와 Linux OS가 섞여 보여서, 명령어가 어디서 실행되는지 분간이 안 됐습니다.

특히 yum upgrade 같은 명령어가 EC2 서버 위에서 실행되는 것인지, 로컬 컴퓨터에서 실행하는 것인지 구분이 되지 않아 막막했습니다. Security Group나 Storage 용어 앞에서 “네트워크 문제인가, 하드디스크 문제인가” 하며 Linux 공부를 해야 할지 인프라 설정을 해야 할지 혼란스러웠습니다.

결국 서버를 켜는 것과 OS를 다루는 과정이 동시에 진행되는 느낌이라, ‘어디에 있는 것인가’에 초점을 맞춰 개념을 분리해야 했습니다.

정리된 이해#

AWS EC2는 ‘서버 하드웨어’를, Linux OS는 그 안에 설치된 ‘소프트웨어 환경’으로 구분하여 생각해야 한다. Security Group 같은 보안 설정은 서버 자체의 문제이며, yum 같은 명령어는 OS 내부에서 실행되는 작업이다. 결국 서버를 생성한 뒤 OS를 준비하고 그 위에 애플리케이션을 올리는 순서로 흐름을 이해하면 된다.

sudo yum upgrade -y

2. EC2 Python 가상환경 FastAPI 실행 정리#

무엇을 배웠나#

리눅스 명령어는 시스템 전체를 관리하는 OS 레벨 도구이며, 파이썬 관련 툴은 격리된 애플리케이션 레벨에서 동작한다는 점이 명확해졌다. 특히 yum으로 리눅스에 Python을 설치한 뒤, venv로 환경을 격리시켜 pip나 uv로 라이브러리를 관리하는 이중 구조를 이해하게 되었다. 이를 통해 서버 구성 시 OS 레벨과 애플리케이션 레벨의 역할을 분리하여 사고할 수 있게 되었다.

헷갈렸던 점#

리눅스 명령어와 파이썬 패키지 관리자가 모두 ‘설치’라는 점에서 역할 구분이 어려웠고, venv로 만든 가상환경을 source로 활성화하는 리눅스 환경의 동작 원리가 감이 안 잡혔다.

정리된 이해#

리눅스 명령어는 시스템 전체를 관리하는 OS 레벨 도구이며, yum은 리눅스 자체 패키지를 설치하고 python3.x는 런타임을 실행한다. 반면 venv, pip, uv 등은 Python 애플리케이션 내부를 격리하여 라이브러리를 관리하는 Python 레벨의 도구이다. 따라서 서버에 Python을 설치한 뒤 가상환경을 생성하고 패키지를 설치하는 순서대로 진행하면 된다.

EC2에 Python 가상환경과 FastAPI 실행 기반 만들기#

🔍 무엇이 헷갈렸나 (What Confused Me)#

처음에는 yum, pip, uv, venv가 모두 “설치"와 “환경” 관련 도구인 것처럼 느껴졌다. 특히 리눅스 명령어(yum)와 파이썬 패키지 관리자(pip, uv)의 경계가 모호했다. 서버에 무언가를 설치한다는 점에서 비슷하게 느껴져서, 각각이 어떤 계층(OS 레벨 vs Python 레벨)에서 작동하는지 구분하기 어려웠다. 또한 venv로 가상환경을 만든 후 source로 활성화시키는 과정이 리눅스 환경에서 어떻게 동작하는지 감이 안 잡혔다.

📌 정리된 이해 (Corrected Understanding)#

명령어/용어 역할 계층
pwd / ls / mkdir / cd Linux 파일 및 디렉터리 탐색 및 생성 OS 레벨
yum Linux 시스템 전체 패키지 설치 (OS 관리) OS 레벨
python3.14 Python 런타임 실행 환경 OS 레벨
venv Python 격리된 가상환경 생성 Python 애플리케이션 레벨
pip / uv Python 패키지 다운로드 및 설치 Python 애플리케이션 레벨
FastAPI Web API 프레임워크 (코드 로직) 애플리케이션 레벨
uvicorn ASGI 서버 (실제 요청 처리) 인프라 레벨

핵심은 **“리눅스는 시스템 전체를 관리하고, Python은 격리된 환경 안에서 패키지를 관리한다”**는 점이다. yum으로 리눅스에 Python 자체를 설치하고, 그 안에서도 venv로 환경을 격리시킨 뒤 pip나 uv로 필요한 라이브러리를 채우는 구조다.

🛠️ 실습 예시 (Practice Example)#

# 1. 리눅스 기본 이동 및 폴더 생성
pwd
ls -
mkdir fastapi_project
cd fastapi_project

# 2. Python 가상환경 생성 및 활성화
python3 -m venv .venv
source .venv/bin/activate

# 3. 패키지 설치 (uv 사용 예시)
uv pip install fastapi uvicorn

# 4. 간단한 FastAPI 앱 생성 후 실행
cat > main.py << 'EOF'
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def read_root():
    return {"message": "Hello World"}
EOF

uvicorn main:app --host 0.0.0.0 --port 8000

총평#

오늘 오전 전체에서 배운 것#

AWS EC2와 Linux OS를 ‘위치’ 기준으로 분리하여 인프라 요소와 OS 명령어를 명확히 구분했다. 이를 통해 서버 생성 후 OS 준비, 애플리케이션 실행이라는 자연스러운 학습 흐름을 잡을 수 있었다. 특히 리눅스 시스템 관리 도구와 파이썬 가상환경의 이중 구조를 이해하여, 서버 구성 시 OS 레벨과 애플리케이션 레벨의 역할을 분리해 사고할 수 있게 되었다.

다음에 조심할 것#

리눅스 명령어와 파이썬 툴을 구분하지 않고 섞어 사용하면 서버 구성에 오류가 발생할 수 있으므로, 항상 ‘OS 레벨’과 ‘애플리케이션 레벨’의 경계를 명확히 인지해야 한다.

EC2 생성 후 OS 설치와 환경 설정 단계를 건너뛰고 바로 애플리케이션을 실행하려 하면 의존성 문제로 인해 서비스가 정상 동작하지 않을 수 있으므로, 반드시 yum으로 시스템 환경을 먼저 준비한 뒤 venv 등으로 격리된 공간에서 개발해야 한다.

다음 복습 주제#

리눅스 OS 레벨과 파이썬 가상환경 등 애플리케이션 레벨의 역할 분리를 명확히 이해한 만큼, 실제 서버 운영 시 이 두 영역이 어떻게 상호작용하는지 심화 학습하고 싶습니다.

특히 yum으로 시스템 전체에 Python을 설치한 뒤, 왜 굳이 venv나 uv 같은 가상환경 도구가 필요한지 그 필요성과 동작 원리를 심층적으로 파악하여, 서버 구성 시 발생할 수 있는 의존성 충돌 문제를 효과적으로 해결하는 방법을 익히고 싶습니다.
