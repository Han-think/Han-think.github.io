1. FastAPI 회원가입 DB 연결 및 INSERT 흐름 정리#

무엇을 배웠나#

FastAPI와 SQLAlchemy를 활용한 DB 연결 흐름을 get_conn() → SQL 작성 → execute() → 결과 fetch 순서로 파악했다. 특히 /overlay와 /join 엔드포인트가 SELECT/INSERT 차이 외에는 구조가 동일하다는 점을 이해하는 것이 핵심이었다. 또한 quote_plus()는 비밀번호 특수문제로 인한 URL 파싱 오류를 방지하기 위한 보안 처리임을 명확히 했다.

헷갈렸던 점#

처음에는 get_conn(), text(), execute() 등 다양한 메서드들이 난무해 전체 흐름이 하나의 연결된 과정인지 개별 기능인지 구분하기 어려웠습니다. 특히 quote_plus 같은 함수가 DB 접속과 무슨 연관이 있는지 의아해했으며, 이것이 실제 접속 실패로 이어질지 몰랐습니다. 가장 큰 혼란은 지난주 병원 일정으로 인해 09_db_conn과 10_member_join 사이의 연결 고리를 놓쳐, 여러 메서드들이 독립적으로 튀어나온 것처럼 느껴졌던 점입니다.

정리된 이해#

FastAPI에서 DB 연결은 get_conn()을 통해 시작되며, 이후 text()로 SQL을 작성하고 execute()로 실행한 뒤 mappings().fetchone() 또는 fetchall()로 결과를 받아오는 표준 흐름을 반복합니다. 특히 /overlay는 중복 체크를 위한 SELECT, /join은 데이터 생성을 위한 INSERT를 수행하지만, 이 두 엔드포인트의 전체적인 요청→응답 경로는 구조적으로 동일합니다. URL 구성 시 비밀번호에 특수문자가 포함될 경우 발생할 수 있는 파싱 오류를 방지하기 위해 quote_plus() 함수가 사용된다는 점도 반드시 기억해야 합니다.

# FastAPI DB 연결 및 중복 체크 흐름 (SELECT)
@app.get("/overlay")
def check_overlay(id: str):
    conn = get_conn()  # 1. DB 연결 획득
    sql = text("SELECT id FROM member WHERE id = :id")  # 2. SQL 작성 (파라미터 바인딩)
    result = conn.execute(sql, {"id": id}).mappings().fetchone()  # 3. 실행 및 결과 fetch
    return {"exists": result is not None}  # 4. JSON 응답 반환

# FastAPI INSERT 흐름 (가입 처리)
@app.get("/join")
def join_member(id: str, pwd: str):
    conn = get_conn()  # 1. DB 연결 획득
    sql = text("INSERT INTO member (id, pwd) VALUES (:id, :pwd)")  # 2. SQL 작성
    conn.execute(sql, {"id": id, "pwd": pwd})  # 3. INSERT 실행 (commit은 별도 또는 세션 종료 시 자동)
    return {"message": "가입 완료"}

2. 트랜잭션과 bcrypt 해시 처리 이해하기#

무엇을 배웠나#

execute()는 SQL 문을 실행하고, commit()으로 변경사항을 DB에 영구 저장하며, rollback()은 오류 발생 시 이전 상태로 되돌리는 것이다. bcrypt는 비밀번호를 해시하여 복구가 불가능하게 만들지만, 로그인 시 입력한 평문과 저장된 해시 값을 비교해 인증을 수행한다. transaction의 commit과 rollback을 통해 데이터 일관성을 유지하고, hash 함수의 특성을 이해함으로써 비밀번호 처리 메커니즘을 정확히 파악할 수 있게 되었다.

헷갈렸던 점#

execute()는 단순히 SQL을 실행하는 것뿐만 아니라, commit()을 통해야 비로소 데이터베이스에 영구적으로 반영된다는 점이었습니다. 또한 bcrypt가 비밀번호를 복호화하여 확인하는 것이 아니라, 입력한 평문과 저장된 해시 값을 비교하는 일방향 함수라는 점에서 처음에는 원문의 재생성 여부가 불투명했습니다.

정리된 이해#

execute()는 SQL 문을 데이터베이스에 실행하는 것이고, commit()을 통해야 비로소 변경 사항이 영구적으로 저장된다. bcrypt는 비밀번호를 복호화할 수 없는 일방향 해시 함수로, 로그인 시 입력한 평문과 저장된 해시 값을 비교하여 인증을 수행한다.

# 트랜잭션 흐름 예시 (SQLAlchemy 기반)
try:
    # 1. SQL 실행 (INSERT, UPDATE 등)
    result = conn.execute(sql, info)
    row = result.rowcount

    # 2. 성공 여부 확인 후 확정
    if row > 0:
        conn.commit()  # 변경사항 DB에 저장
except Exception as e:
    # 3. 오류 발생 시 롤백
    logger.error(e)
    conn.rollback()
finally:
    # 4. 연결 종료 (필요시)
    pass

# bcrypt 비밀번호 검증 예시
import bcrypt

# 회원가입 시: 평문 비밀번호를 해싱하여 저장
hashed_pw = bcrypt.hashpw(plain_password.encode('utf-8'), bcrypt.gensalt())
# DB에 hashed_pw (바이트 형태) 저장

# 로그인 시: 입력된 비밀번호와 stored_hash 비교
if bcrypt.checkpw(input_password.encode('utf-8'), stored_hash):
    # 인증 성공
    pass
else:
    # 인증 실패
    pass

3. bcrypt 비밀번호 검증 흐름 이해하기#

무엇을 배웠나#

회원가입 시 비밀번호를 해시화해 DB에 저장하고, 로그인 단계에서는 사용자가 입력한 평문과 DB에 있는 해시를 비교하여 일치 여부만을 판별한다는 사실을 깨달았다. 처음에는 함수 이름이 달라서 비밀번호 복호화 과정인지 혼란스러웠지만, 서버가 비밀번호를 원래 상태로 되찾는 것이 아니라 단순히 검증하는 역할임을 이해하니 흐름이 단순해졌다.

헷갈렸던 점#

비밀번호를 ‘복호화’하는 게 아니라, 입력값과 DB 해시를 단순히 ‘비교’한다는 점이 가장 혼란스러웠습니다. 회원가입 시 비밀번호를 해시로 변환해 저장한다는 건 알았지만, 로그인 단계에서 왜 또 다른 함수(matches)가 필요한지 감이 안 잡혔습니다.

정리된 이해#

회원가입 시 평문 비밀번호를 해시로 변환해 DB에 저장하고, 로그인은 사용자가 입력한 값을 DB에 있는 해시와 비교해 일치 여부만 판별하는 방식입니다. 서버는 비밀번호를 복호화하거나 원래 상태로 되돌리지 않으며, 단순히 인증 과정을 거쳐 접근을 허가합니다.

총평#

오늘 오전 전체에서 배운 것#

FastAPI와 SQLAlchemy를 활용한 DB 연결 흐름과 트랜잭션 제어 메커니즘을 정리했다. 특히 비밀번호 보안 처리를 위해 quote_plus()를 사용하고, bcrypt를 통해 해시화된 비밀번호를 검증하는 로직의 차이를 명확히 이해하였다.

다음에 조심할 것#

  1. DB 연결 및 트랜잭션 관리: get_conn()을 통해 DB 세션을 확보한 후, SQL 실행 전 반드시 commit()으로 영구 저장 여부를 확인하고 예외 발생 시 rollback()로 데이터 무결성을 유지하는 흐름을 명확히 해야 한다.
  2. 비밀번호 보안 처리: bcrypt를 이용한 해시화와 검증 과정은 복호화가 아닌 일치 여부 판별임을 인지해야 하며, URL 연결 시 특수문제 이슈를 방지하기 위해 quote_plus() 사용을 필수로 체크해야 한다.
  3. 엔드포인트 구조 통일성: /overlay(SELECT)와 /join(INSERT)의 코드 구조가 유사하므로, 쿼리 작성 부분만 차별화하여 중복된 흐름을 효율적으로 관리하고 실수 없이 구현하는 습관을 들여야 한다.

다음 복습 주제#

FastAPI와 SQLAlchemy를 활용한 CRUD 흐름에서 commit()과 rollback()의 시점 차이점을 확실히 구분하는 것이 중요하다. 특히 트랜잭션 처리 중 예외가 발생했을 때 데이터 무결성을 해치지 않기 위해 rollback()을 언제 호출해야 하는지 연습해 볼 필요가 있다.

비밀번호 보안과 관련하여 bcrypt와 같은 해시 함수의 원리와 특성을 정확히 이해하는 것이 필요하다. 비밀번호를 평문 상태로 저장하지 않고 해싱하는 과정뿐만 아니라, 로그인 시 입력값과 stored hash를 비교하는 검증 로직이 어떻게 동작하는지 흐름도를 그려보며 숙지해야 한다.

FastAPI 라우트 설계 시 엔드포인트별로 수행되는 SQL 문의 종류(SELECT vs INSERT 등)와 파라미터 전달 방식을 명확히 구분하는 연습을 해야 한다. 특히 quote_plus()와 같은 인코딩 함수가 URL 파싱 오류를 예방하는 역할을 한다는 점을 실제 코드에서 직접 확인하며 적용해 보는 것이 좋다.
