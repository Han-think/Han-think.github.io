1. 질문과 답변의 유해성 점수화#

무엇을 배웠나#

Moderation 점수화는 질문과 답변을 각각 독립적으로 평가한다는 점이 핵심이다. 사용자의 입력 위험도와 모델의 출력 위험도를 separately 측정함으로써, 부적절한 요청에 대해 적절히 거절하는 경우를 안전하게 구분할 수 있다. 실제 서비스에서는 이 두 점수를 바탕으로 차단 또는 수정 로직을 동반해야 한다. 이러한 접근 방식은 ‘나쁜 말만 걸러내는 것’을 넘어 입력 의도와 출력 대응의 적절성을 동시에 파악하는 것이다.

헷갈렸던 점#

처음에는 Moderation.score() 함수가 질문(input)뿐만 아니라 답변(output)만으로 위험도를 평가하는지 의아해했다. 특히 실제 서비스에서는 높은 위험도가 감지되었을 때 차단하거나 수정하는 로직이 필수적일 텐데, 강사님의 방식은 단순히 점수를 매기는 것에 그쳐 적용 가능성에 대한 궁금증이 들었다.

핵심 개념은 질문과 답변이 각각 독립적인 유해성 점수를 가진다는 것이다. score(output=question)는 사용자 질문의 위험도를, score(output=answer)는 모델의 답변 위험도를 평가하며, 부적절한 요청을 받았음에도 챗봇이 적절히 거절했다면 입력은 고위험이지만 출력은 저위험이라는 조합이 가능하다는 점이 특히 인상 깊었다.

정리된 이해#

Moderation 점수는 질문(입력)과 답변(출력)이 각각 독립적인 위험도를 가지며, 입력의 위험도가 높더라도 출력이 적절히 거절했다면 전체적으로 안전한 상호작용으로 판단할 수 있다. 이는 유해성 평가가 단순히 금지된 단어를 걸러내는 것이 아니라, 사용자의 의도와 모델의 대응 태도를 별도로 측정하는 과정임을 의미한다. 따라서 실제 서비스 적용 시에는 이 두 점수를 기반으로 차단 여부나 수정 로직을 결정하는 추가적인 판단 기준이 필요하다고 이해할 수 있다.

# 질문과 답변 각각에 대해 moderation 점수 매기기
input_res = m_metric.score(output=question)  # 사용자 질문의 위험도
out_res = m_metric.score(output=answer)      # 모델 답변의 위험도

# Opik 트레이스에 피드백으로 기록
opik_context.update_current_trace(feedback_scores=[
    {"name": "mod_input", "value": input_res.value, "reason": input_res.reason},
    {"name": "mod_output", "value": out_res.value, "reason": out_res.reason}
])

2. Compliance Risk Judge: 위험한 확언 탐지하기#

무엇을 배웠나#

Compliance Risk Judge는 답변의 사실 여부를 판단하는 것이 아니라, 금융이나 의료와 같은 분야에서 사용자에게 위험을 초래할 수 있는 근거 없는 보장이나 개인정보 노출 등을 식별하는 데 초점을 맞춘다는 점이다. 입력 형식에 [사용자질문]과 [챗봇대답] 라벨을 붙이는 것은 Judge가 질문과 답변의 역할을 구분하여 평가하도록 돕기 위한 구조화 과정이었다. 실습을 통해 점수와 평가 사유를 반환받는 기본적인 사용법을 익혔으며, 낮은 점수가 반드시 법적·의학적 완벽함을 보장하지 않으므로 수동 검토가 필수임을 인지하게 되었다.

헷갈렸던 점#

처음에는 score() 함수가 질문과 답변을 어떻게 결합해야 할지 레이아웃이 낯설었습니다. 특히 라벨링이 왜 필요한지 처음에는 직관적이지 않았습니다. 또한, 단순한 사실 여부 판단보다 ‘근거 없는 보장’이나 ‘위험한 확언’을 잡아내는 세밀하고 민감한 평가가 필요하다는 점이 새롭게 다가왔습니다.

정리된 이해#

Compliance Risk Judge는 LLM 답변의 사실 여부를 확인하는 평가가 아니라, 사용자에게 위험을 초래할 수 있는 근거 없는 보장이나 잘못된 정보(예: 금융·의료 오류, 개인정보 노출)를 식별하는 데 초점을 맞춘다. 따라서 단순한 텍스트 입력이 아닌, ‘무엇을 평가하는가’에 따라 질문과 답변을 [사용자질문] / [챗봇대답] 형식으로 구조화하여 입력해야 한다. 또한 점수가 낮다고 해서 해당 답변이 완벽하다는 뜻은 아니므로, 평가 결과는 맹신하기보다는 수동 검토와 문맥 확인이 반드시 필요하다.

# 기본적인 사용법
judge_model = get_judge_model()
cr_metrics = ComplianceRiskJudge(model=judge_model)
result = cr_metrics.score(
    output=f"[사용자질문]\n{question}\n\n[챗봇대답]\n{answer}"
)
# result.value: 점수, result.reason: 평가 이유

3. LLM 평가와 서비스화 사이의 간극: FastAPI 적용 경계#

무엇을 배웠나#

강사님의 PDF 교안을 통해 LLM 운영 전 과정을 이해하는 데 큰 어려움이 없었으나, ‘서비스화’ 단계로 넘어가면서 평가 완료와 서비스 완성 사이의 간극이 명확히 느껴졌다. 실제 서비스는 HTTP 요청·응답 사이클과 동시성 처리 등 추가적인 요소가 필요하기 때문에, 평가가 잘된다고 해서 서비스가 자동으로 완성된다는 생각은 버려야 한다. 현재는 강사님이 언급한 04_online_eval.py를 FastAPI 서비스에 연동하는 작업을 진행 중이며, 평가와 서비스 구현을 분리하여 접근하고 있다.

헷갈렸던 점#

평가 결과가 좋다고 해서 서비스가 자동으로 완성된 것은 아니며, 실제 서비스에는 HTTP 요청·응답 사이클과 예외 처리 등 고려해야 할 요소가 많습니다. FastAPI 엔드포인트 구현 자체는 아직 미완료 과제로 남아 있으며, CLI 기반 평가 환경과는 다른 실무적인 요소들이 필요합니다.

정리된 이해#

LLM 운영은 평가와 서비스가 별개임을 명확히 했으며, FastAPI를 통한 HTTP 기반 서비스 구현과 온라인 평가를 연동하는 것이 실제 적용의 핵심 과제임을 깨달았다.

총평#

오늘 오후 전체에서 배운 것#

질문과 답변을 독립적으로 평가하여 안전성을 판단하고, Compliance Risk Judge를 통해 근거 없는 위험 선전을 식별하는 방법을 습득했다. 또한, 평가 결과가 서비스 완성도를 보장하지 않으며 FastAPI 등 추가적인 구현이 필요하다는 점을 인식하게 되었다.

다음에 조심할 것#

평가 점수와 실제 서비스 로직은 별개로 관리해야 한다는 점을 명확히 인지하고, 평가 결과에 과신하지 않고 수동 검토를 병행하는 습관을 기르겠다.

FastAPI 등 외부 프레임워크와의 연동 과정에서 발생할 수 있는 동시성 및 요청 응답 처리 문제를 충분히 고려하여, 평가 모듈을 서비스에 안정적으로 적용할 수 있도록 신중히 준비하겠다.

다음 복습 주제#

LLM 서비스 구현 시, 평가 점수와 실제 서비스 로직은 별개로 관리해야 한다는 점을 명확히 인지했다. 단순히 모델이 잘 답변하는지를 넘어, 입력과 출력의 위험도를 동시에 판단하여 안전하게 차단하거나 수정하는 구조가 필수적임을 이해했다. 또한, 평가 툴의 결과가 좋더라도 FastAPI를 통한 HTTP 요청 처리와 동시성 관리 등 실제 서비스 인프라 요소를 별도로 구현해야 한다는 점을 인식하고 있다.
