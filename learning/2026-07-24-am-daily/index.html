1. 파이썬 코드 스타일 가이드: 컨벤션과 네이밍 규칙#

무엇을 배웠나#

로컬 임포트는 직접 작성한 코드뿐 아니라 조직 내에서 공유되는 패키지도 포함하는 개념이라는 것을 알게 되었고, 케이스 표기법은 코드 실행에 영향을 미치는 것이 아니라 코딩 스타일 가이드라인이라는 것을 명확히 이해했습니다. 특히 파이썬에서도 대소문자 구분이 중요하며, snake_case는 대소문자를 구분하여 사용해야 한다는 점을 다시 한번 확인했습니다. 이러한 규칙들을 통해 코드의 가독성과 유지보수성을 높일 수 있다는 것을 깨달았습니다.

헷갈렸던 점#

처음에는 local import가 무엇을 의미하는지 명확하게 이해하지 못했고, 케이스 표기법이 코드 실행에 영향을 미치는 줄 알았습니다. 또한 SQL 경험 때문에 snake_case는 대소문자 구분이 없는 방식이라고 잘못 생각했습니다.

정리된 이해#

로컬 임포트는 프로젝트 내에서 관리하는 코드, 즉 직접 작성한 코드와 조직 내에서 공유되는 패키지를 모두 포함하는 개념이다. 케이스 표기법은 코드 스타일을 나타낼 뿐 실행 결과에 영향을 주지 않으며, snake_case는 파이썬에서 대소문자 구분을 명확하게 해야 하는 규칙을 따르는 방식이다. dunder 메소드는 파이썬에서 특별한 역할을 수행하는 메소드를 지칭하는 용어이다.

2. 함수 컨벤션과 테스트 가능성 이해#

무엇을 배웠나#

함수 인자 관리에서 *와 ** 문법의 역할을 명확히 이해하게 되었고, 여러 인자를 다룰 때 튜플과 딕셔너리를 활용하는 방법을 알게 되었다. 테스트 가능성이 단순히 테스트 코드 작성을 넘어 전체 시스템의 효율성과 오류 추적 능력을 향상시키는 중요한 요소임을 깨달았다. 이제는 코드를 작은 단위로 나누어 테스트 가능한 함수를 설계하는 것이 필요하다는 점을 알게 되었다.

헷갈렸던 점#

함수 인자 관리에서 *와 **의 차이와 활용법을 명확히 이해하지 못했고, 특히 가변 인자를 사용하는 상황에서 혼란이 컸습니다. 테스트 가능성이라는 개념을 단순히 테스트 코드 작성을 의미하는 것으로만 생각하여, 실제 코드의 유지보수성과 디버깅 효율성에 미치는 영향에 대해 충분히 인지하지 못했습니다.

정리된 이해#

*는 여러 개의 위치 인자를 튜플로 묶어 함수에 전달하고, **는 키워드 인자를 딕셔너리로 묶어 전달하는 방법이 명확해졌습니다. 테스트 가능성을 높이기 위해서는 함수를 작게 나누어 각자의 역할을 분리하고, 독립적으로 테스트할 수 있도록 설계하는 것이 중요하며, 이를 통해 코드의 안정성과 유지보수성을 높일 수 있습니다. 앞으로는 테스트 가능성을 고려하여 함수를 설계하는 습관을 들여야겠습니다.

무엇을 배웠나#

주석, 독스트링, 핸드북의 역할을 명확히 구분하게 되었고, 특히 독스트링이 코드 인터페이스 문서화의 역할을 한다는 것을 알게 되었다. 타입 힌트는 변수 타입을 명시하는 문법이지만 런타임 타입 검사를 강제하지 않는다는 점도 이해했다. 또한 dict와 같은 자료형 표기 오류도 인지하여 앞으로는 정확한 표기를 사용하도록 노력해야겠다.

헷갈렸던 점#

4. 프로젝트 구조와 모듈 분리, 효율적인 코드 관리를 위한 고민#

무엇을 배웠나#

프로젝트 규모가 커질수록 파일 분리가 항상 좋은 것은 아니며, 파일 수보다는 각 파일의 역할과 책임 경계가 명확한 모듈화가 중요하다는 점을 깨달았습니다. 파일의 역할 설명 가능성, 입력/출력 명확성, 독립적인 검증 가능성 등의 질문을 통해 모듈화 수준을 판단할 수 있음을 알게 되었습니다. 현재 진행 중인 프로젝트에 적용 가능한 코드 전수조사, 결손/충돌 탐지, 변경 영향 분석 등의 체계를 구축하여 프로젝트 구조를 개선해야겠다는 방향을 잡았습니다.

헷갈렸던 점#

프로젝트 파일이 너무 많아서 과도하게 분리하는 것이 오히려 비효율적일까 봐 걱정이었고, 프로젝트 규모가 커질수록 관리하기가 더 어려워지는 것 같아서 혼란스러웠다. 코드와 데이터의 복잡한 관계 때문에 전체적인 그림을 파악하기 힘들고, 통제 불능 상태로 이어질까 봐 불안했다.

정리된 이해#

프로젝트 규모가 커질수록 파일 분리가 무조건 좋을 수 없으며, 각 파일의 역할과 책임을 명확히 하는 모듈화 수준이 중요함을 깨달았습니다. 각 파일이 독립적으로 검증 가능하고 수정 시 영향 범위를 예측할 수 있도록 설계해야 효율적인 코드 관리가 가능하며, 현재 진행 중인 체계적인 분석을 통해 이를 달성할 수 있습니다.

5. Python 패키지 관리: PyPI, pip, requirements.txt 활용법#

무엇을 배웠나#

PyPI는 패키지 저장소이고, pip는 그 패키지를 설치하고 관리하는 도구라는 것을 명확히 이해하게 되었어. requirements.txt는 Python 패키지 의존성을 기록하는 파일이며, IDE와 상관없이 터미널에서 pip를 통해 관리할 수 있다는 것도 알게 되었어. 또한, 프로젝트에서 필요한 모든 것을 다 포함하는 파일은 아니라는 점도 인지하게 됐어.

헷갈렸던 점#

강사님이 PyCharm을 쓰시는 모습만 보니까 pip와 requirements.txt가 PyCharm에서만 작동하는 게 아닌가 싶었고, 프로젝트 의존성을 requirements.txt가 전부 포함하는지 확신이 없었습니다. 실제로 터미널에서 pip 명령어를 사용해보고, requirements.txt가 Python 패키지 버전 정보만 담는다는 것을 알게 되었습니다.

정리된 이해#

PyPI는 파이썬 패키지 저장소이고, pip는 이 패키지를 설치하고 관리하는 도구인데, 이 둘은 IDE와 상관없이 터미널에서 사용할 수 있습니다. requirements.txt는 주로 파이썬 패키지와 버전을 기록하며, 프로젝트의 스크립트나 데이터 파일 등은 포함하지 않습니다.

# pandas 패키지 설치
pip install pandas

# 특정 버전 설치
pip install pandas==1.4.1

# 현재 환경의 패키지 목록을 requirements.txt로 내보내기
pip freeze > requirements.txt

6. 수업 보조 자료 링크 관리 및 접근 가이드#

무엇을 배웠나#

수업 보조 자료 링크는 일반 공개가 아닌 수강생 전용 자료이므로 접근 시 권한을 확인해야 한다는 점을 알게 되었다. 링크 입력 오류 가능성을 염두에 두고, 접근이 안 될 경우 수업 게시판에서 직접 링크를 재확인하는 것이 중요하며, 자료의 공개 가능 여부와 출처를 기록하는 습관을 들여야겠다. 이 내용을 바탕으로 자료 관리를 더욱 체계적으로 할 수 있을 것 같다.

헷갈렸던 점#

화면 캡처해서 링크를 입력하는 과정에서 글자가 제대로 인식되지 않을까 봐 걱정되었고, 혹시 링크가 개인 계정에 연결되어 있어서 다른 사람들이 접근하지 못할까 봐 불안했어요. 수업 자료인지, 아니면 일반 공개된 자료인지도 헷갈렸습니다.

정리된 이해#

제공된 링크들은 일반적인 공개 자료가 아니므로, 수업 내부 보조 자료로만 활용해야 합니다. 링크 접근에 문제가 발생하면 수업 게시판에서 다시 확인하는 것이 가장 확실한 방법이며, 자료의 공개 가능 여부와 출처를 명확히 기록하는 것이 중요합니다.
