1. 토크나이저, ‘단어’를 넘어 ‘subword’로 쪼개다#

무엇을 배웠나#

토크나이저가 ‘단어’ 단위로 텍스트를 자르는 것이 아니라, 사전에 등록된 규칙에 따라 **subword(부분 단어)**로 쪼개서 ID로 변환한다는 점을 명확히 인식하게 되었다. 특히 한글 단어와 조사·어미가 ##으로 시작하는 subword로 분리되는 모습이나, 슬래시(/)까지 토큰의 일부가 되어버리는 사례를 보며 ‘토큰 = 단어’라는 직관적인 기대가 무너지는 과정이 가장 인상 깊었다. 또한 encode() 함수를 통해 토큰 ID 앞에 ``나 뒤에 `

헷갈렸던 점#

처음 tokenizer 코드를 실행했을 때 가장 큰 충격은 **“사람이 보는 단어와 기계가 보는 토큰이 전혀 다르다”**는 점이었습니다.

특히 다음과 같은 부분에서 혼란이 컸습니다.

  • 한글 단어의 단위 분할: "상승했지만" 같은 자연스러운 한글 문장도 "상승" + "##했" + "##지만"처럼 쪼개어졌습니다. 조사와 어미가 ##로 시작하는 subword로 분리되는 모습이 낯설었습니다.
  • 기호와 영문의 분할: "GPU/XPU"가 "GP" + "##U" + "/" + "XP" + "##U"로 나뉘는 것을 보고, slash(/)까지 토큰의 일부가 되어버리는 것에 놀랐습니다.

결국 **“토큰 = 단어”**라는 직관적인 기대를 버리는 과정이 가장 헷갈리고 재밌었던 포인트였습니다.

정리된 이해#

토크나이저는 우리가 흔히 생각하는 ‘단어’ 단위로 텍스트를 자르는 것이 아니라, 사전에 등록된 vocabulary와 규칙에 따라 **subword(부분 단어)**로 쪼개서 고유의 ID로 변환하는 과정입니다. 특히 한글이나 특수문자의 경우, 조사와 어미가 ##으로 시작하는 subword로 분리되어 기계가 문맥을 파악하도록 돕습니다. 또한 encode() 함수를 통해 토큰 ID 앞에 ``, 뒤에 `

2. Padding과 EOS의 차이점 이해하기#

무엇을 배웠나#

처음에는 PAD와 EOS가 같은 개념인 줄 알았지만, 실제로는 배치 정렬용 자리 채우기와 생성 중단 신호로 역할이 완전히 달랐다. Truncation은 모델이 잘라낸 사실을 인지하지 못해 중요한 맥락이 끊어질 위험이 있다는 점이 가장 인상 깊었다. 특히 대화 이력이 다음 입력에 포함될 경우, 간접적으로 truncation 문제와 연결된다는 점도 새롭게 깨달았다.

헷갈렸던 점#

처음에는 EOS가 단순히 ‘자리 채우기’용 padding인지, 아니면 생성을 멈추는 기능적인 신호인지 구분이 안 되었습니다. 또한 truncation이 단순히 길이를 줄이는 행위일 뿐 아니라, 모델이 잘라낸 사실을 모른 채 중요한 맥락이 끊어지며 오해를 일으킬 수 있다는 점을 간과했습니다. finally, 대화 이력이 다음 입력의 context에 포함될 경우, truncation 문제와 연쇄적으로 영향을 미칠 수 있음을 깨닫는 데 시간이 걸렸습니다.

정리된 이해#

PAD는 배치 크기를 맞추기 위한 자리 채우기로, 실제 의미 없는 영역이며 attention mask로 무시된다. EOS는 시퀀스 종료를 알리는 신호로서 생성 중단을 유도하는 기능적 목적이 있다. Truncation은 입력 길이 초과 시 발생하며, 모델이 잘라낸 사실을 인지하지 못해 중요한 정보가 손실될 위험이 있다.

# Padding (PAD)
padding_token_id = tokenizer.pad_token_id  # 보통 EOS token과 동일하거나 별도 설정
attention_mask = torch.ones(batch_size, seq_len)  # 실제 토큰은 1, 패딩은 0으로 마스크

# End of Sequence (EOS)
eos_token_id = tokenizer.eos_token_id
generated_ids = model.generate(input_ids, eos_token_id=eos_token_id)  # EOS token이 생성되면 중단

# Truncation (잘라내기)
truncated_input = input_ids[:, :max_length]  # 최대 길이 초과 시 앞부분 또는 뒷부분 잘라냉

3. XPU 환경 감성분석 실습 및 오해 정리#

무엇을 배웠나#

XPU 환경에서는 PyTorch 코드에 “cuda"가 하드코딩되어 있어도 자동으로 XPU로 전환되지 않으며, 장치를 명시적으로 선택해야 한다. 또한 classification score는 모델이 해당 class를 예측할 때의 confidence이지 감정 강도를 백분율로 나타낸 값은 아니다.

헷갈렸던 점#

처음에는 PyTorch가 설치되어 있으면 CUDA 코드가 자동으로 XPU로 대체될 것처럼 느꼈다.

또 classification score는 모델이 해당 class를 예측할 때의 confidence이지, 감정의 강도를 백분율로 나타낸 값은 아니라는 점도 명확히 했다.

정리된 이해#

XPU 환경에서 PyTorch 코드를 실행하려면 torch.cuda.is_available() 대신 torch.xpu.is_available()를 사용하여 장치를 명시적으로 선택해야 하며, classification score는 모델의 confidence가 감정 강도를 백분율로 나타낸 값은 아니라는 점을 명확히 했다.

XPU 환경에서 감성분석 모델 구동하기#

import torch
from transformers import AutoTokenizer, AutoModelForSequenceClassification

# 1. 장치 자동 선택 로직
if torch.cuda.is_available():
    device = "cuda"
elif torch.xpu.is_available():
    device = "xpu"
else:
    device = "cpu"

print(f"Using device: {device}")

# 2. 모델 및 tokenizer 로드
model_name = "nlptown/bert-base-multilingual-uncased-sentiment"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForSequenceClassification.from_pretrained(model_name).to(device)

# 3. 입력 전처리 및 추론
text = "It works exactly as advertised, but somehow I still regret buying it."
inputs = tokenizer(text, return_tensors="pt").to(device)
outputs = model(**inputs)
predicted_class_id = outputs.logits.argmax().item()

print(f"Sentiment: {predicted_class_id} (Negative)")

4. FastAPI와 Jinja2: 역할과 템플릿의 구분#

무엇을 배웠나#

FastAPI에서 Jinja2는 HTML 렌더링을 위한 선택적 도구이며, API 전용 사용 시 필수 요소가 아닙니다. 반면 Chat Template은 LLM이 입력 형식을 인식하도록 Role을 구조화하는 프로MPT 설계의 핵심 요소입니다. 이 두 개념은 목적과 적용 영역이 완전히 다르며, 혼동되지 않도록 구분해야 합니다.

헷갈렸던 점#

FastAPI에서 Jinja2가 필수적인지, HTML 렌더링 도구인지에 대한 경계가 모호했습니다. 또한 Chat Template이 단순히 문자열을 채우는 툴인지, 모델의 입력 형식을 결정하는 핵심 장치인지를 구분하기 어려웠습니다.

정리된 이해#

Chat Template은 LLM이 입력 형식을 인식하도록 Role을 포맷팅하는 핵심 장치이며, Jinja2는 FastAPI 선택과 무관하게 UI 렌더링을 담당하는 웹 템플릿 엔진이다.

# Chat Template: Role을 모델 입력 형식으로 변환하는 핵심 장치
messages = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "Hello!"}
]

# Jinja2: FastAPI에서 HTML 렌더링에 사용하는 템플릿 엔진 (FastAPI 필수 아님)
from fastapi import FastAPI
from fastapi.responses import HTMLResponse

app = FastAPI()

@app.get("/")
async def get():
    return HTMLResponse(content="<h1>Hello</h1>", status_code=200)

5. Intel XPU로 Gemma 2 2B IT 모델 준비하기#

무엇을 배웠나#

XPU 환경에서는 device_map="xpu" 인자와 함께 bfloat16 정밀도 설정이 필수적이며, 모델 로드 전 입력 텐서를 반드시 XPU 장치로 이동시켜야 한다. 또한 단순히 코드를 실행하는 것을 넘어, 시스템 부하와 메모리 사용량을 직접 확인하며 내 하드웨어에서의 실제 동작을 검증하는 과정이 중요하다.

헷갈렸던 점#

가장 먼저 든 의문은 device_map="xpu" 인자 하나만으로 모델을 올릴 수 있는지, 그리고 float32 정밀도를 그대로 사용해도 되는지에 대한 불안감이었습니다. 단순히 코드를 복사하는 것을 넘어 ‘내 하드웨어에서 실제로 어떻게 동작하는지’를 확인하는 과정이 필수적이라고 생각했습니다. 특히 bfloat16 사용에 대해 명확해졌는데, FP32 대비 파라미터당 저장 크기가 절반이므로 모델 weight 메모리 부담을 크게 줄일 수 있지만, 전체 메모리 사용량은 weight 외 activation, buffer 등도 포함하므로 신중하게 설정해야 합니다.

정리된 이해#

XPU 환경에서 모델을 로드할 때는 device_map="xpu" 인자 사용 여부와 bfloat16 정밀도 설정이 핵심이며, 단순히 코드를 실행하는 것을 넘어 실제 하드웨어에서의 메모리 점유율과 부하를 직접 확인하는 과정이 필수적입니다.

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_id = "google/gemma-2-2b-it"

# 토크나이저 생성
tokenizer = AutoTokenizer.from_pretrained(model_id)

# 대화 내용 정의
msg_list = [
    {"role": "user", "content": "파이썬에서 변수는 뭐야?"},
    {"role": "assistant", "content": "변수는 데이터를 저장하는 상자와 같습니다."},
    {"role": "user", "content": "그럼 리스트는 뭐야?"},
]

prompt = tokenizer.apply_chat_template(msg_list, tokenize=False)

총평#

오늘 오후 전체에서 배운 것#

오후에는 토크나이저가 ‘단어’가 아닌 ‘subword’로 텍스트를 쪼개 ID로 변환한다는 점과, PAD와 EOS가 배치 정렬과 생성 중단이라는 서로 다른 역할을 한다는 점을 명확히 이해할 수 있었다. 또한 XPU 환경에서 PyTorch 코드가 자동으로 장치를 인식하지 못해 명시적인 device 설정이 필요하며, classification score는 감정 강도가 아닌 모델의 예측 confidence임을 정리했다. 마지막으로 FastAPI와 Jinja2의 역할 구분, 그리고 Gemma 2 모델을 XPU에 올릴 때 device_map과 bfloat16 설정, 텐서 이동의 중요성을 실습을 통해 체득할 수 있었다.

다음에 조심할 것#

오늘 학습한 핵심 내용은 토큰화가 ‘단어’가 아닌 ‘subword’ 단위로 작동하며, ##이나 / 같은 문자가 토큰에 포함될 수 있다는 점이다. 또한 PAD는 배치 정렬을 위한 자리 채우기이고 EOS는 생성을 멈추라는 신호라는 구분과, XPU 환경에서는 코드에 “cuda"가 있어도 자동 전환되지 않아 장치 설정을 반드시 확인해야 한다는 점을 새롭게 인식했다. 다음에는 토큰 분리의 원리를 정확히 이해해 오류를 줄이고, 장치 이동 코드를 습관적으로 점검하여 모델 로딩 시 불필요한 에러를 방지하도록 노력하겠다.

다음 복습 주제#

토큰화 과정에서 ‘단어’라는 직관적 개념이 무너지고 subword 단위로 쪼개지는 원리를 확실히 이해하는 것이 다음 단계다. 특히 한글 어미가 ##으로 시작하거나 슬래시(/)까지 포함되는 사례를 통해 토큰화가 어떻게 작동하는지 재점검해야 한다. 또한 Padding과 EOS의 기능 차이를 명확히 구분하고, Truncation이 모델에 미치는 영향(특히 이력 연장 시)을 짚어보는 것이 중요하다.

XPU 환경에서 PyTorch 코드에 하드코딩된 “cuda"가 자동으로 전환되지 않는다는 점을 반드시 기억해야 한다. classification score는 감정 강도 백분율이 아닌, 해당 클래스를 예측한 모델의 confidence 값임을 명확히 구분해야 한다. FastAPI와 Jinja2의 역할 차이, 그리고 Chat Template이 LLM 입력 형식을 구조화하는 핵심 요소라는 점도 다시 한번 확실하게 인지해 두어야 한다.

XPU 환경에서 Gemma 2 모델을 로드할 때는 device_map="xpu"와 bfloat16 설정이 필수적이며, 입력 텐치를 반드시 XPU 장치로 이동시켜야 한다. 단순히 코드를 실행하는 것을 넘어 시스템 부하와 메모리 사용량을 직접 확인하며 내 하드웨어에서의 실제 동작을 검증하는 과정이 무엇보다 중요하다.
