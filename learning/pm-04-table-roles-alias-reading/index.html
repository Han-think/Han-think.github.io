1. 별칭 활용#

왜 이걸 보게 됐나#

복잡한 테이블 간의 관계를 파악하고 쿼리를 작성할 때 테이블 이름이 너무 길거나 반복적으로 사용되어서 쿼리 자체가 가독성을 잃어버리는 경우가 많았어. 별칭을 사용하면 테이블 이름을 줄여서 쿼리를 간결하게 만들 수 있고, 테이블 간의 조인 조건을 명확하게 표현할 수 있어서 쿼리 이해도와 효율성을 높일 수 있겠다는 생각을 하게 됐어.

내가 헷갈린 지점#

처음에는 별칭이 왜 테이블 이름 뒤에 덧붙여지는지, 그리고 SELECT 문에서 이 별칭을 어떻게 활용해야 하는지 잘 몰랐습니다. 테이블 이름이 너무 길 때만 별칭을 쓰는 줄 알았고, 별칭을 사용하지 않으면 쿼리가 작동하지 않을 것이라고 생각했습니다. 별칭이 단순히 짧게 줄여쓰기 위한 것 이상이라는 것을 깨닫지 못했습니다.

시도한 코드 / 예시#

SELECT ii.TrackId, g.Name AS GenreName, SUM(ii.UnitPrice * ii.Quantity) AS Revenue
FROM invoice_items AS ii
INNER JOIN tracks AS t ON ii.TrackId = t.TrackId
INNER JOIN genres AS g ON t.GenreId = g.GenreId

결과와 해석#

음악 매출 쿼리에서 tracks 테이블을 중심으로 invoice_items와 genres 테이블을 조인하여 특정 장르별 매출을 계산해봤습니다. tracks 테이블의 별칭 t를 통해 조인 조건을 명확히 하고, genres 테이블의 Name 컬럼을 GenreName이라는 별칭으로 선택하여 쿼리 결과를 더 쉽게 이해할 수 있도록 했습니다. 이처럼 별칭을 사용하면 쿼리 복잡도를 줄이고 가독성을 높일 수 있었습니다.

정리된 이해#

별칭은 테이블 이름을 줄여서 편하게 사용하기 위한 임시 이름표인데, FROM이나 JOIN절에서 정의해서 쿼리 전체에서 일관되게 사용해야 합니다. 테이블 역할과 중심 테이블을 파악하는 것이 쿼리 작성의 핵심이며, 쿼리의 목적에 따라 중심 테이블을 찾고 테이블 간의 연결 관계를 이해해야 효율적인 쿼리를 작성할 수 있습니다.

2. 테이블 역할#

왜 이걸 보게 됐나#

ERD가 복잡해질수록 어떤 테이블이 핵심이고, 어떤 테이블들이 서로 어떻게 연결되는지 파악하는 게 어려웠거든. 테이블 간의 관계를 명확히 이해하지 못하면 쿼리를 제대로 작성할 수 없을 것 같아서, 테이블 역할을 배우게 됐어. 결국 쿼리의 목적에 맞춰 테이블의 역할을 이해하는 게 효율적인 쿼리 작성을 위한 첫걸음인 것 같아.

내가 헷갈린 지점#

처음에는 테이블 간의 관계를 ERD에서 보는 것 자체가 어려웠고, 쿼리 작성 시 어떤 테이블이 핵심이고 어떤 테이블이 보조 역할을 하는지 파악하는 데 시간이 오래 걸렸습니다. 특히 여러 테이블이 조인되는 쿼리에서는 각 테이블이 어떤 정보를 담고 있으며, 쿼리 목적에 따라 어떤 테이블이 중심이 되는지 혼란스러웠습니다.

시도한 코드 / 예시#

SELECT ii.TrackId, g.Name AS GenreName, SUM(ii.UnitPrice * ii.Quantity) AS Revenue
FROM invoice_items AS ii
INNER JOIN tracks AS t ON ii.TrackId = t.TrackId
INNER JOIN genres AS g ON t.GenreId = g.GenreId

결과와 해석#

음악 매출 쿼리를 작성하면서 invoice_items 테이블을 중심으로 tracks와 genres 테이블을 연결하는 과정을 이해할 수 있었다. invoice_items 테이블이 중심이 되어 어떤 트랙이 얼마만큼 팔렸는지, 그리고 그 트랙의 장르는 무엇인지 알아낼 수 있게 되었다. 테이블 간의 관계를 파악하고 중심 테이블을 기준으로 쿼리를 구성하는 연습이 중요함을 깨달았다.

정리된 이해#

쿼리에서 각 테이블이 어떤 역할을 하는지 파악하는 것이 중요하며, 특히 쿼리의 목적을 고려하여 중심 테이블을 찾아야 전체적인 구조를 이해하기 쉽습니다. 중심 테이블은 쿼리의 핵심 데이터가 위치하는 곳이며, 다른 테이블과의 관계를 통해 필요한 정보를 가져옵니다.

3. 중심 테이블#

왜 이걸 보게 됐나#

쿼리를 작성하다 보면 여러 테이블을 연결해서 필요한 정보를 뽑아내야 하는데, 각 테이블이 어떤 역할을 하는지 명확히 이해하지 못하면 어떤 테이블이 핵심이고 어떤 테이블을 연결해야 할지 막막해졌어. 그래서 테이블 간의 관계를 파악하고 쿼리의 목적에 맞춰 중심 테이블을 찾을 수 있게 되면서 더 효율적으로 쿼리를 작성할 수 있게 됐어.

내가 헷갈린 지점#

처음에는 여러 테이블이 연결된 쿼리에서 어떤 테이블이 가장 중요한 역할을 하는지, 즉 ‘중심 테이블’을 찾기가 어려웠다. ERD를 보면 모든 테이블이 서로 관련되어 보여서 어느 테이블을 기준으로 쿼리를 설계해야 할지 혼란스러웠고, 중심 테이블이 쿼리 결과에 가장 큰 영향을 미치는 테이블이라는 개념을 제대로 이해하지 못했다. 쿼리 목적에 따라 중심 테이블이 달라질 수 있다는 점도 인지하지 못하고 있었다.

시도한 코드 / 예시#

tracks (중심) → albums → artists → genres

결과와 해석#

쿼리의 목적에 따라 중심 테이블을 찾으면 어떤 테이블이 핵심 데이터 역할을 하는지 알 수 있어요. 예를 들어 음악 매출 쿼리에서는 tracks 테이블이 중심이 되어 다른 테이블들과 연결되면서 음악 데이터와 관련된 정보를 효과적으로 가져올 수 있습니다. 이를 통해 쿼리 작성의 방향성을 잡고 테이블 간의 관계를 더 명확하게 이해할 수 있었습니다.

정리된 이해#

쿼리의 목적을 가장 잘 반영하는 테이블을 중심으로 테이블 간의 관계를 파악해야 합니다. 중심 테이블을 찾으면, 어떤 테이블들이 중심 테이블과 연결되어 있는지, 그리고 그 연결이 어떤 의미를 가지는지를 더 쉽게 이해할 수 있습니다. 이를 통해 복잡한 ERD를 단순화하고 효율적인 쿼리를 작성할 수 있습니다.

4. 쿼리 목적#

왜 이걸 보게 됐나#

복잡한 데이터베이스에서 원하는 정보를 찾으려면, 어떤 테이블이 핵심적인 역할을 하는지 파악해야 효율적으로 쿼리를 작성할 수 있어요. 단순히 테이블 간의 연결만 보는 게 아니라, 어떤 정보를 얻고 싶으냐에 따라 중심 테이블이 달라지기 때문에, 쿼리 목적을 이해하는 것이 데이터 분석의 첫걸음이라고 생각하게 됐습니다. 그래야 불필요한 테이블을 거치지 않고 원하는 결과를 빠르게 얻을 수 있겠죠.

내가 헷갈린 지점#

처음에는 쿼리 목적을 파악하는 것이 가장 어려웠다. 단순히 테이블 간의 관계를 보는 것 이상으로, 어떤 정보를 얻고 싶어서 쿼리를 작성하는지에 따라 중심 테이블이 달라질 수 있다는 점을 이해하는 데 시간이 걸렸다. 쿼리가 무엇을 보여주어야 하는지에 대한 질문에 답하는 것이 테이블 역할과 별칭을 제대로 활용하는 데 핵심이라는 걸 뒤늦게 깨달았다.

시도한 코드 / 예시#

SELECT ii.TrackId, g.Name AS GenreName, SUM(ii.UnitPrice * ii.Quantity) AS Revenue
FROM invoice_items AS ii
INNER JOIN tracks AS t ON ii.TrackId = t.TrackId
INNER JOIN genres AS g ON t.GenreId = g.GenreId

결과와 해석#

쿼리 목적은 어떤 정보를 얻고 싶은지 명확하게 정의하는 것인데, 예를 들어 ‘음악 매출’을 구하는 쿼리는 ‘invoice_items’ 테이블을 중심으로 어떤 테이블과 연결되어 있는지 파악해야 합니다. 이를 통해 ‘invoice_items’ 테이블에서 시작하여 ’tracks’, ‘genres’ 테이블을 연결하는 쿼리를 작성하여 매출 정보를 얻을 수 있었습니다. 쿼리 목적에 따라 중심 테이블과 연결되는 테이블이 달라지므로, 목적에 맞게 테이블 간의 관계를 이해하는 것이 중요합니다.

정리된 이해#

쿼리 목적을 명확히 하는 것이 테이블 간의 관계를 이해하고 어떤 테이블이 중심이 되는지 파악하는 데 가장 중요합니다. 중심 테이블은 쿼리가 어떤 정보를 얻어내기 위해 사용되는 핵심 테이블이며, 다른 테이블들은 이 중심 테이블과 연결되어 필요한 데이터를 제공합니다. 따라서 쿼리를 작성하기 전에 어떤 정보를 얻고 싶은지를 먼저 생각해야 중심 테이블을 찾고 쿼리를 설계할 수 있습니다.

총평#

오늘 전체에서 배운 것#

SQL 쿼리에서 테이블 이름을 짧게 줄여주는 별칭은 FROM이나 JOIN절에서 정의하며, 쿼리의 목적에 따라 중심 테이블을 파악하는 것이 중요합니다. 특히 ERD를 볼 때 각 테이블의 역할과 중심 테이블을 명확히 구분하는 연습이 필요했습니다.

다음에 조심할 것#

별칭이 FROM 절에 어디서 정의되는지, 그리고 쿼리 목적에 따라 중심 테이블을 정확히 파악하는 연습을 꾸준히 해야겠다. ERD를 보면서 테이블 간의 관계와 쿼리 목적을 연결하는 훈련이 필요해 보이고, 실제 쿼리를 작성하면서 각 테이블의 역할을 더욱 명확하게 이해해야 할 것 같다.

다음 복습 주제#

INNER JOIN genres AS g ON t.GenreId = g.GenreId GROUP BY ii.TrackId, g.Name ORDER BY Revenue DESC;


다음에 좀 더 복잡한 JOIN 조건과 서브쿼리를 활용하여 쿼리를 작성해보고, 성능에 미치는 영향도 분석해봐야겠다. ERD의 테이블 간 관계를 시각적으로 표현하는 방법을 익혀서 테이블 역할을 더 빠르게 파악할 수 있도록 해봐야지.
