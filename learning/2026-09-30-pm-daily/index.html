1. LLM 코드 재사용과 그래프 시각화 확장 (LearningLog)#

무엇을 배웠나#

오전과 동일한 executor 구조를 활용해 LLM이 Python 코드를 생성하고 실행하는 패턴을 재사용할 수 있음을 깨달았다. 핵심은 새로운 기술 습득이 아니라, ‘prompt 목적’만 변경하여 기존 worker를 그래프 생성 작업에 적용하는 재사용성이었다. 이를 통해 LangGraph와 같은 프레임워크에서 node/worker로 기능을 묶는 기반 구조를 이해하게 되었다.

헷갈렸던 점#

오전 수업에서 배운 DataFrame 기반 코드 실행 파이프라인 구조와 오늘 주제인 그래프 생성 흐름이 거의 동일하여, 새로운 기술을 배우는 것이 아니라 기존 패턴을 재사용하는 방법에 집중하게 되었습니다. 핵심은 LLM이 자연어 요청을 Python/Matplotlib 실행 단계로 변환하며, 공통 executor와 task-specific prompt를 분리하면 LangGraph 같은 프레임워크에서 각 기능을 노드/워커로 묶는 기반이 된다는 점이었습니다. 무엇보다 “새로운 실행 기술” 자체가 아니라, **“같은 패턴을 재사용 가능한 워커로 만드는 과정 자체”**가 학습의 대상였다는 점이 가장 큰 깨달음이었습니다.

정리된 이해#

오전 학습한 DataFrame 기반 코드 실행 파이프라인의 핵심 패턴을 재사용하는 것이 목표였으며, LLM에게 자연어를 Python/Matplotlib 코드로 변환하게 한 뒤 executor를 통해 그래프를 생성하는 구조임을 이해했습니다. 특히 기존의 executor와 task-specific prompt를 분리하여 구성하면 LangGraph와 같은 프레임워크에서 각 기능을 node/worker로 효율적으로 묶을 수 있다는 점에 주목했습니다.

2. LangGraph 핵심 개념과 비유 정리#

무엇을 배웠나#

LangGraph의 핵심 개념을 ‘작업 가방’, ‘처리 모듈’, ‘연결선’ 등 구체적인 비유로 환원하여 추상적인 문법과 전체 흐름을 분리해서 이해할 수 있었다. 특히 compile()와 invoke()가 설계도와 실제 실행의 차이라는 점을 명확히 인식하여, 노드와 라우팅 로직이 어떻게 데이터 흐름 속에서 상호작용하는지 전체적인 그림을 그릴 수 있게 되었다.

헷갈렸던 점#

처음에는 상태, 함수, 라우팅 로직이 같은 코드 블록에 섞여 있어 각 요소의 역할 분간이 어려웠습니다. 또한 Python 함수와 LangChain/Graph 개념이 동시에 등장하면서 데이터와 처리 로직, 연결 고리의 경계가 불분명했습니다. 이러한 혼란을 해소하기 위해 ‘작업 가방’, ‘처리 모듈’, ‘연결선’ 등의 비유를 먼저 머릿속에 그린 뒤 문법을 익힌 것이 가장 큰 도움이 되었습니다.

정리된 이해#

LangGraph는 상태, 노드, 엣지를 각각 데이터 용기, 처리 함수, 연결 로직으로 분리하여 생각해야 한다. 전체 흐름을 설계하는 compile()까지 완료한 뒤 invoke()로 실행하면, 파이프라인처럼 순차적으로 결과를 도출할 수 있다.

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, END

# 1. 상태 정의 (작업 가방)
class AgentState(TypedDict):
    input: str
    output: str

# 2. 노드 정의 (처리 모듈)
def node_a(state: AgentState) -> dict:
    # LLM이나 계산 로직이 들어가는 곳
    return {"output": f"Processed: {state['input']}"}

def router(state: AgentState) -> str:
    # 판단자 역할
    if "error" in state.get("output", ""):
        return "error_handler"
    return END

# 3. 그래프 컴파일 (일자리 초대장)
graph = StateGraph(AgentState)
graph.add_node("process", node_a)
graph.add_conditional_edges("process", router)
graph.set_entry_point("process")

app = graph.compile()

# 4. 실행 (업무 시작)
result = app.invoke({"input": "Hello LangGraph"})
print(result["output"])

3. LLM Router와 Worker의 그래프 통합 이해하기#

무엇을 배웠나#

Router는 답변을 생성하는 것이 아니라, 어떤 Worker에게 일을 시킬지 결정하는 classifier 역할이라는 점을 이해하게 되었다. 또한 conditional edge가 routing label과 실제 node를 연결해주는 고리라는 점도 명확해졌다. 현재 시스템은 통합 완성본보다 routing graph의 골격만 만든 단계로 보는 것이 정확하다.

헷갈렸던 점#

Router가 답을 생성하는 것이 아니라, 어떤 Worker에게 일을 시킬지 결정하는 classifier 역할이라는 점이 가장 핵심적인 전환점이었습니다.

특히 conditional edge는 routing label과 실제 node를 매핑해주는 연결 고리 역할을 한다는 점도 명확해졌습니다.

정리된 이해#

Router는 답변을 생성하는 것이 아니라, 어떤 Worker에게 일을 시킬지 결정하는 classifier 역할입니다. conditional edge는 routing label과 실제 node를 매핑해주는 연결 고리 역할을 합니다. 현재 시스템은 통합 완성본보다 routing graph 골격을 만드는 단계로 이해해야 합니다.

LearningLog 워킹 노트: LLM Router로 plain·excel·vector worker를 하나의 그래프로 묶기#

🔍 무엇이 헷갈렸나 (Confusion Point)#

오늘 가장 패닉이 온 부분은 **“부품 사이의 control flow가 새로 등장해 책임 경계가 안 보인다”**는 점이었습니다.

RAG

State

LangGraph

이 모든 것이 한 화면에 합쳐졌을 때, 기존에 알고 있던 부품들이 낯설게 느껴진 것은 부품을 모르해서가 아니라, 어떤 부품이 어떤 역할을 하며 어떻게 연결되는지(control flow)의 책임 경계가 명확하지 않았기 때문입니다.

특히 Router라는 decision component가 단순히 질문의 종류를 분류하는 것을 넘어, State 관리와 Worker 실행의 orchestration 역할을 하게 되면서 전체 시스템의 구조를 이해하기 어려웠습니다. “이전 거 융합하는 건 알겠는데 짬뽕처럼 보여서 패닉"이라는 생각이 들었던 지점은 바로 이 control/orchestration layer가 새로 올라온 부분이었습니다.

📚 정리된 이해 (Corrected Understanding)#

헷갈리던 부분을 3층 구조로 나누니 단순해졌습니다.

Decision Layer       → Router → 무슨 능력이 필요한가?
Worker Layer         → plain / excel / vector → 실제 작업 수행
State Layer          → question / data / code / context / generation → 결과 운반

핵심은 Router가 답변을 생성하는 것이 아니라, 어떤 Worker에게 일을 시킬지 결정하는 classifier 역할이라는 점이었습니다. 또한 conditional edge는 routing label과 실제 node를 매핑해주는 연결 고리 역할을 한다는 점도 명확해졌습니다.

현재 Git 상태는 통합 완성본보다 routing graph 골격을 만드는 단계로 보는 것이 정확합니다. Prompt와 code에서 key name이({"route":"plain"} vs result['router']) 맞지 않거나, router가 실제 결과를 사용하지 않고 "plain"으로 고정되어 있는 등 중간 구현 상태라는 점도 이해하는 데 도움이 되었습니다.

수업에서 다룬 기본적인 라우팅 흐름은 다음과 같습니다.

  1. 사용자 질문 입력: “오늘 날씨는 어때?”
  2. Router 결정: {"route": "plain"} (날씨 조회 능력이 필요하다고 판단)
  3. Worker 실행: plain worker가 API 호출 수행
  4. State 업데이트: 결과가 State에 저장되어 다음 단계로 전달

핵심을 보여주는 코드 예시’만’ 백틱3개 코드블록으로 출력하라. 노트에 코드 근거가 없으면 아무것도 쓰지 마라.

from langgraph.graph import StateGraph, END
from typing_extensions import TypedDict

# State Layer: 데이터가 흐르는 그릇
class AgentState(TypedDict):
    question: str
    route: str  # Router의 결정 결과 ("plain", "excel", "vector")
    answer: str

# Decision Layer: 어떤 Worker에게 일을 맡길지 결정
def router(state: AgentState) -> dict:
    """
    질문의 의도를 분석하여 적절한 worker 경로를 결정합니다.
    """
    q = state["question"].lower()

    # 간단한 키워드 기반 라우팅 로직 (실제로는 LLM이 수행)
    if any(word in q for word in ["날씨", "기온", "습도"]):
        route = "plain"
    elif any(word in q for word in ["엑셀", "표", "데이터 분석"]):
        route = "excel"
    else:
        route = "vector"  # 기본적으로 벡터 검색 등 사용

    return {"route": route}

    """plain worker: 간단한 질의응답 또는 API 호출"""
    # 실제 구현에서는 날씨 API 등을 호출합니다.
    answer = f"날씨 관련 답변: '{state['question']}'에 대한 정보를 처리했습니다."
    return {"answer": answer}

오늘 오후 전체에서 배운 것#

LLM 코드 재사용과 LangGraph 핵심 개념을 통해, 기존 worker 구조를 프롬프트 목적 변경만으로 그래프 생성 작업에 적용할 수 있음을 깨닫고, compile()와 invoke()가 설계도와 실행의 차이라는 점을 명확히 이해했다. 특히 Router가 답변이 아닌 Worker 할당을 결정하는 classifier 역할을 하고, conditional edge가 routing label과 node를 연결해주는 고리라는 점은 시스템 통합의 골격임을 확인할 수 있었다.

다음에 조심할 것#

  • LangGraph에서 compile()와 invoke()를 설계도와 실제 실행으로 구분하여, 노드 간 데이터 흐름과 라우팅 로직이 어떻게 상호작용하는지 전체적인 그림을 먼저 파악한 뒤 구체적인 코드에 착수해야 한다.
  • Router가 답변 생성 자체가 아니라 Worker 할당이라는 classifier 역할임을 명확히 인지하고, conditional edge가 routing label과 실제 node를 연결해주는 고리라는 점을 항상 상기하여 불필요한 로직 중복을 방지해야 한다.
  • 기존 LLM 코드 재사용 경험을 바탕으로 새로운 프레임워크 적용 시 ‘prompt 목적’만 변경하면 worker를 효율적으로 재사용할 수 있음을 전제로 하되, 시스템 통합 완료보다는 routing graph의 골격부터 단계별로 검증하며 진행해야 한다.

다음 복습 주제#

LangGraph의 핵심 구조가 단순히 코드 작성법이 아니라, ‘어떤 작업을 누가 어떻게 연결하는지’에 대한 설계 사고임을 재정립해야 한다.

특히 compile()와 invoke()의 차이를 명확히 이해하고, 라우팅 로직이 데이터 흐름 속에서 노드를 제어하는 메커니즘으로 작동한다는 점을 심화 학습해야 한다.

현재 시스템에서 router와 worker가 유기적으로 연결된 완전한 그래프가 아니라, routing 레이어의 골격과 실제 실행 흐름을 분리하여 설계·검증하는 연습을 이어가야 한다.
