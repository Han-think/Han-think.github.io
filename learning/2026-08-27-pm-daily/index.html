1. Express 요청 데이터와 Middleware 이해하기#

무엇을 배웠나#

URL 경로, 쿼리 문자열, 요청 본문이 각각 어떤 위치에서 데이터를 받는지 명확히 구분할 수 있게 되었다. 특히 req.body 사용 전 반드시 거쳐야 할 미들웨어의 역할을 이해하여 데이터가 전달되지 않는 문제를 해결하는 데 도움이 되었다. next()를 통해 미들웨이드의 흐름을 제어한다는 개념은 라우트 처리 순서를 디버깅하는 핵심적인 기준점이 되었다. 이제 URL 구조와 데이터 형태에 따라 적절한 속성을 선택해 요청값을 안전하게 추출할 수 있게 되었다.

헷갈렸던 점#

URL 경로와 쿼리 문자열이 비슷해서 어디서 데이터가 오는 건지 구분하기 어려웠습니다. 특히 req.params와 req.query가 모두 URL과 관련이 있어 헷갈렸습니다. 또한 express.json() 없이 req.body를 사용하려다 데이터를 확인하지 못해 고생했습니다.

정리된 이해#

req.params, req.query, req.body는 데이터가 들어온 위치(URL 경로, 물음표 뒤, 요청 본문)로 구분하면 혼동이 사라집니다. 특히 req.body는 기본적으로 보이지 않으므로 express.json() 미들웨어를 반드시 거쳐야 합니다. 미들웨어 흐름에서 next()를 호출해야 다음 단계로 넘어가므로, 데이터가 전달되지 않을 때는 이 연결 고리를 확인하는 것이 디버깅의 핵심입니다.

// 1. params: URL 경로 값
app.get('/rest/:id/:pw', (req, res) => {
    const { id, pw } = req.params;
    res.json({ params: { id, pw } });
});

// 2. query: 물음표 뒤의 문자열
app.get('/search', (req, res) => {
    const { q } = req.query;
    res.json({ query: { q } });
});

// 3. body: POST 등으로 보낸 데이터 본문
// express.json() 미들웨어를 거쳐야 보임
app.post('/login', (req, res) => {
    const { id, pw } = req.body;
    res.json({ body: { id, pw } });
});

2. [워킹노트] NoSQL CAP Sharding Vector Graph DB, State Control Layer의 필요성#

무엇을 배웠나#

수업 초반에는 DB 기술 자체가 목인 줄 알았지만, 실제로는 데이터의 최신성이나 신뢰도를 보장하는 ‘상태 관리’가 더 중요하다는 점을 깨달았습니다. 특히 Vector DB는 의미적으로 가까운 데이터를 찾는 것이지, 그것이 현재 유효한 정보인지 자동으로 보장해주지는 않는다는 사실을 이해했습니다. 결국 기술적 저장 방식과 별개로, 데이터의 최신성과 권위 여부를 판단하는 별도의 계층이 필요하다고 정리했습니다.

헷갈렸던 점#

수업 내용이 ‘저장 방식’에 집중해 있어, 실제 서비스에서 데이터의 최신성과 신뢰도를 보장하는 ‘상태 관리’ 부분에 대한 구체적인 방법이 부족하다고 느꼈습니다.

특히 Vector DB가 의미적으로 가까운 데이터를 찾는다는 점은 이해했지만, 그 데이터가 현재 유효한 정보인지, 권위 있는 정보인지를 판단하는 기준이 별도 시스템에서 관리되어야 한다는 점이 명확하지 않아 혼란스러웠습니다.

정리된 이해#

수업 내용은 DB 기술 자체가 목이 아니라 데이터 저장·검색을 위한 도구에 불과하다는 점을 강조했습니다. 특히 Vector DB와 Graph DB는 ‘유사성’과 ‘정확성/최신성’을 구분해야 하며, 실제 서비스에서는 별도의 State Control Layer를 통해 데이터의 신뢰도와 최신성을 관리해야 한다는 점을 정리했습니다.

# State Control Layer: 데이터의 최신성 및 권위 관리 예시

class DataStateManager:
    def __init__(self):
        self.stale_threshold = 300  # 초 (5분)
        self.authority_scores = {}  # 소스별 권한 점수

    def check_validity(self, record):
        """
        Vector/Graph DB에서 찾은 데이터가 현재 사용 가능한지 검증
        """
        is_fresh = (record.timestamp > time.time() - self.stale_threshold)
        has_authority = self.authority_scores.get(record.source, 0) > 50
        return is_fresh and has_authority

    def update_state(self, record, new_data):
        """
        새로운 데이터가 도착했을 때 상태 업데이트
        """
        if new_data.confidence > record.confidence:
            record.update(new_data)
            self.authority_scores[record.source] = new_data.weight

# Vector/Graph Search vs State Control Layer 예시

def retrieve_with_context(query_embedding, db):
    # 1. 의미적 유사도 검색 (Vector DB 역할)
    candidates = db.vector_search(query_embedding, k=20)

    # 2. 상태 관리 레이어에서 필터링
    valid_results = []
    for candidate in candidates:
        if manager.check_validity(candidate):
            valid_results.append(candidate)

    # 3. 권한 점수 기반 정렬 (Graph DB 관계 탐색 보완)
    return sorted(valid_results, key=lambda x: x.authority_score, reverse=True)[:5]

3. 상태 관리와 정합성의 미묘한 균형#

무엇을 배웠나#

처음에는 검색 결과 반환과 상태 관리가 같은 차원이라고 생각했지만, 실제로는 정합성 유지가 모델의 창작 능력을 억제할 수 있다는 점을 깨닫게 되었다. 특히 Canonical State와 Projection의 구분, 그리고 HARD·SOFT·FREE 제약 강도의 개념을 통해 ‘정확함’과 ‘창의성’ 사이의 균형을 어떻게 조절해야 할지 명확한 기준을 세울 수 있었다. 무엇보다 정합성을 유지하는 것이 목적이 되면 오히려 모델의 자율성이 제한되어 창의력이 위축된다는 사실을 이해하게 되었다.

헷갈렸던 점#

검색 결과 반환과 상태 관리가 같은 선상에 있다고 생각했으나, 실제로는 정합성 관리와 창작 영역이 완전히 다른 차원이라는 점이 가장 큰 혼란이었다.

Canonical State와 Projection의 차이가 단순히 ‘내부 상태와 전달 정보의 분리’ 정도로만 여겨졌으나, 프로젝트 적용 시 어떻게 구분하고 활용해야 할지 구체적인 감이 잡히지 않았던 점이다.

정합성을 강제하는 것이 모델의 자율성을 억제하여 창의력을 저해한다는 점을 간과하다가, 정확함과 창의성 사이의 미묘한 균형 조절이 핵심이라는 사실을 깨닫게 되었다.

정리된 이해#

내부 정본은 상세히 유지하고, 작업에 필요한 정보는 최소한으로 선택해 전달하는 것이 핵심입니다. 정합성 유지가 목적이 되면 모델의 자율성이 억제되어 오히려 창의력이 저하될 수 있음을 인지해야 합니다. Canonical State와 Projection을 명확히 구분하여 시스템의 ‘진실’과 사용자나 작업에 맞는 정보 흐름을 분리하는 것이 중요합니다.

# Canonical State vs Projection Example

class SystemState:
    def __init__(self, canonical_data):
        # 내부 정본 (Canonical State): 충분히 상세하게 유지
        self.canonical = canonical_data  # {"user_id": 1, "preferences": {...}, "history": [...], "metadata": {...}}

# 프로젝션 (Projection): 현재 작업에 필요한 최소한만 선택해 전달
def get_user_projection(state, user_role):
    if user_role == "admin":
        return {
            "user_id": state.canonical["user_id"],
            "is_active": state.canonical.get("is_active"),
            # 관리자에게는 민감하지 않은 기본 정보만 노출
        }
    elif user_role == "viewer":
        return {
            "display_name": state.canonical.get("display_name"),
            # 시청자에게는 더 필터링된 정보 전달
        }
    # FREE 영역: 모델이 선택할 창작 영역 (예술적 자유, 상상력)
    # 정합성 유지가 목적이 되면 모델의 자율성이 억제되어 창의력이 저하됨

# HARD/SOFT/FREE 제약 강도 예시
def apply_constraints(data, constraint_type):
    if constraint_type == "HARD":
        # 반드시 지켜야 할 사실 (데이터 정합성, 보안 등)
        return {k: v for k, v in data.items() if not k.startswith("_")}
    elif constraint_type == "SOFT":
        # 참고해야 할 맥락 (추가 정보, 힌트 등)
        return {k: v for k, v in data.items() if k in ["hints", "context"]}
    elif constraint_type == "FREE":
        # 모델이 선택할 창작 영역
        return data  # 모든 가능성 열림

4. Smart App Control에 의해 차단된 MongoDB 실행 파일 해결 과정#

무엇을 배웠나#

Smart App Control가 신뢰하지 않은 실행 파일을 차단하는 Windows 보안 기능이었으며, MongoDB 실행을 막는 주된 원인이 되었다. 나는 처음에는 ‘관리자 권한’ 문제로만 생각했으나, 실제로는 프로그램 실행 시점에 정책이 발동한다는 사실을 깨닫고 해결했다. ZIP 파일 직접 실행 등 다양한 방법을 시도해보았지만, 결국 해당 기능을 끄거나 예외 처리를 해야 정상 작동한다.

헷갈렸던 점#

나는 “설치 단계에서 에러가 나면 무조건 관리자 권한 문제"라고 가정했지만, 실제로는 설치 자체는 성공한 뒤 실행(Running)하는 순간에 터진 일이었다.

결국 Windows의 ‘Smart App Control’ 기능이 MongoDB 실행 파일을 신뢰할 수 없는 프로그램으로 간주해 차단한 것이 원인이었다.

정리된 이해#

Windows의 ‘Smart App Control’ 기능이 MongoDB 실행 파일(mongod.exe)을 신뢰할 수 없는 프로그램으로 간주해 차단하여, 설치 후 즉시 종료되는 현상이 발생했다. 실제로는 권한 문제가 아니라 Windows 보안 정책에 의해 프로그램이 자동으로 차단된 것이 원인이었다.

# MongoDB 실행 및 Smart App Control 해결 과정

문제 상황#

  • MongoDB 설치 파일 실행은 성공했으나, mongod.exe 실행 시 즉시 종료되거나 접속 불가
  • 관리자 모드 실행 시에도 동일한 증상 발생

원인 분석#

Windows의 Smart App Control 기능이 mongod.exe를 신뢰할 수 없는 실행 파일로 간주하여 차단함.

해결 방법#

  1. Smart App Control 비활성화:

    • Windows 설정 > 개인정보 및 보안 > Windows 보안 > 바이러스 및 위협 방지 > 관리자 설정 열기
    • “SmartAppControl” 항목에서 사용 안 함 선택 후 재부팅

  2. MongoDB 서비스 재시작 또는 mongod.exe 직접 실행 시 정상 동작 확인

5. ES6 핵심 문법, 헷갈림과 정리의 시간#

무엇을 배웠나#

ES6는 새로운 언어가 아니라 기존 JavaScript를 더 간결하고 효율적으로 만든 업그레이드 버전이라는 점을 깨달았다. 특히 let과 const를 통해 변수의 재할당 가능성을 명확히 구분하고, 화살표 함수와 템플릿 리터럴을 사용하면 코드를 훨씬 짧고 읽기 쉽게 작성할 수 있다. 또한 객체 구조 분해와 같은 문법은 문맥에 따라 다른 의미를 가지므로, 사용 목적과 상황을 정확히 이해하는 것이 중요하다고 느꼈다.

헷갈렸던 점#

ES6가 새로운 언어가 아니라 기존 JavaScript를 더 간결하게 다듬은 업그레이드 버전임을 깨닫는 순간이 반복됐다.

특히 {} 기호가 문맥에 따라 구조 분해와 함수 파라미터 기본값 등 완전히 다른 의미를 갖는다는 점에 혼란을 느꼈다. “또 중이야?“라는 생각이 들 정도로 구별하는 데 집중해야 했다.

정리된 이해#

ES6는 기존 JavaScript 문법을 더 간결하고 효율적으로 다듬은 업그레이드된 버전이며, let/const, 템플릿 리터럴, 화살표 함수 등의 핵심 구문을 통해 코드의 가독성과 작성 편의성을 크게 높일 수 있다.

const person = { name: '철수', age: 25 };

// 구조 분해 할당 (객체에서 값 꺼내기)
const { name, age } = person;
console.log(name); // 철수

// 화살표 함수
const add = (a, b) => a + b;
console.log(add(3, 4)); // 7

// 템플릿 리터럴
const sentence = `${name}는 ${age}살입니다.`;
console.log(sentence); // 철수는 25살입니다.

6. 비동기 패턴 이해를 위한 핵심 정리: callback, promise, async/await, Promise.all#

무엇을 배웠나#

비동기 프로그래밍에서 await를 두 번 쓰는 것은 앞선 결과가 뒤에 필요한 순차적 의존 관계를 의미하며, Promise.all()은 독립적인 작업들을 동시에 실행해 전체 소요 시간을 단축시킨다는 점을 명확히 이해하게 되었다. 특히 callback, Promise, async/await가 각각 어떤 역할을 하는지 구분하고, 상황에 따라 순차 처리와 병렬 처리를 적절히 조합하는 것이 핵심이라는 사실을 깨달았다.

헷갈렸던 점#

await를 두 번 쓰는 것과 Promise.all()을 사용하는 것의 차이를 단순히 ‘동시성’과 ‘순차성’으로만 구분하다가, 실제로는 결과값이 다음 단계에 필요한지 여부가 핵심임을 깨닫는 데 시간이 걸렸습니다. 특히 여러 비동기 작업을 시작할 때, 앞선 작업의 결과물이 뒤에 필요 없는 독립적인 경우 Promise.all()을 써야 효율적이라는 점을 명확히 이해하는 것이 아직도 중요합니다.

정리된 이해#

비동기 프로그래밍에서 await를 두 번 쓰는 것은 앞선 결과가 뒤에 필요한 순차적 의존 관계이며, Promise.all()은 별도의 계산 결과가 필요 없는 독립적인 작업의 병렬 실행에 사용된다는 점을 명확히 구분하는 것이 핵심입니다.

// async/await + Promise.all 패턴 (병렬 실행)
async function main(a, b, c, d) {
  // 독립적인 두 덧셈 작업을 동시에 시작
  const [r1, r2] = await Promise.all([
    adder_promise(a, b),
    adder_promise(c, d),
  ]);

  // 결과를 합치는 순차적 처리
  return r1 + r2;
}

7. commonjs-module-export와-require의-이해#

무엇을 배웠나#

require 시점에 한 번 계산된 결과값이 그대로 반환되며, 이후 호출해도 값이 변하지 않는다는 점이 핵심입니다. 함수 형태를 export할 경우, require한 결과에 ()를 붙여야만 실제 함수가 실행됩니다. 또한 ./module과 같은 경로 생략 규칙을 통해 import 구문을 간소화할 수 있습니다.

헷갈렸던 점#

require() 호출 시점에 계산된 결과값이 그대로 반환되며, 이후 재호출해도 값이 변하지 않는다는 점이 가장 큰 혼란이었습니다. 또한 함수를 export할 경우 ()를 붙여야만 실행된다는 개념이 부족해, 함수 자체만으로는 결과를 얻을 수 없다는 점을 학습했습니다.

정리된 이해#

require()는 모듈을 처음 로드할 때 한 번만 실행되며, 그 결과를 캐싱해 반환합니다. 따라서 export된 값이 함수든 문자열이든, require한 즉시 고정된 결과가 돌아오므로 이후 호출에서는 값이 변하지 않습니다. 함수를 export하려면 반드시 module.exports = () => { ... } 형태로 정의하고, 외부에서 사용 시 require(...)( )처럼 괄호를 붙여 실행해야 합니다.

// counter.js - 값 export 예시 (count는 한 번 계산된 후 고정됨)
let count = 0;
module.exports = count += 1; // 첫 require 시점에 1이 되어 export됨

// index.js
const a = require('./counter');
console.log(a); // 1 (두 번째 require해도 값은 여전히 1)
