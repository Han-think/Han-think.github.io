1. AutoTokenizer와 AutoModel 직접 연결 이해하기#

무엇을 배웠나#

pipeline()는 전처리부터 후처리까지 자동화된 편리한 인터페이스이며, AutoTokenizer와 AutoModelForCausalLM을 직접 연결하면 device 설정나 dtype 제어 등 모델의 세부 파라미터를 자유롭게 관리할 수 있다. 두 방식은 wrapper와 그 내부의 부품 관계에 있으며, 특수 하드웨어 환경에서는 직접 연결 방식을 통해 backend와의 인터페이스를 잡아주는 과정이 필수적이다.

헷갈렸던 점#

처음에는 pipeline()가 모든 과정을 자동으로 처리한다고 생각하여, 직접 AutoTokenizer와 AutoModelForCausalLM을 연결할 때 단계가 복잡하게 느껴졌습니다. 특히 텐서 디바이스 이동과 attention mask 생성 등 세부적인 메커니즘이 pipeline() 내부에서 숨겨져 있어 코드를 작성할 진입점이 막막했습니다.

혼란을 겪은 후, 두 방식의 역할 분담이 명확해졌습니다. pipeline()는 전처리부터 후처리까지 자동으로 처리하는 ‘올인원’ 인터페이스이며, AutoTokenizer와 AutoModelForCausalLM은 device 설정나 dtype 제어 등 모델 세부 파라미터를 직접 관리해야 할 때 필요한 ‘직접 연결’ 방식입니다. 결국 pipeline()는 wrapper이고 AutoModel은 그 안의 부품이라고 이해하게 되었습니다.

정리된 이해#

pipeline()는 전처리부터 후처리까지 자동화된 편리한 인터페이스이며, AutoTokenizer와 AutoModelForCausalLM을 직접 연결하면 device 설정 및 dtype 제어 등 모델 세부 파라미터를 사용자가 직접 관리할 수 있다.

🟢 2. 정리된 이해 (Corrected Understanding)#

핵심 내용#

pipeline()는 빠른 프로토타입 작성과 일반적인 추론에 최적화된 ‘올인원’ 인터페이스입니다. 전처리부터 후처리까지 자동으로 처리해 주므로, 모델의 동작 원리에 깊게 관여하지 않고도 결과를 빠르게 얻을 수 있습니다.

반면 AutoTokenizer + AutoModelForCausalLM는 device 설정, dtype 제어, attention 구현 등 모델의 세부 파라미터를 직접 관리해야 할 때 필요한 ‘직접 연결’ 방식입니다. Intel XPU나 특정 하드웨어 환경에서 최적화를 수행할 때는 이 방식을 통해 backend와의 인터페이스를 직접 잡아줘야 합니다.

결국 pipeline()는 wrapper이고, AutoModel은 그 안의 부품이라고 이해하면 됩니다. 특수 백엔드를 쓸 때는 wrapper를 벗겨내고 내부 stage를 직접 만져주는 과정이 필수적이죠.

🟠 3. 실습 예시 (Personal Interpretation & Example)#

코드 예시: AutoTokenizer + AutoModelForCausalLM 직접 연결#

from transformers import AutoTokenizer, AutoModelForCausalLM
import torch

# 1. 모델과 토크나이저 로드
model_name = "meta-llama/Llama-3.2-1B-Instruct"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype="auto",  # 자동 dtype 설정 (float16 등)
)

# 2. 입력 텍스트 토크나이징 (입력 전처리)
inputs = tokenizer("Hello, my name is", return_tensors="pt")

# 3. 텐서를 모델이 있는 디바이스(device)로 이동
inputs = {k: v.to(model.device) for k, v in inputs.items()}

# 4. 모델을 통한 텍스트 생성 (핵심 추론 과정)
# generate 메서드는 attention mask를 내부적으로 처리합니다.
generated_ids = model.generate(**inputs, max_new_tokens=50)

# 5. generated IDs를 텍스트로 디코딩 (출력 후처리)
output_text = tokenizer.decode(generated_ids[0], skip_special_tokens=True)

print(output_text)

코드 근거#

  • AutoTokenizer.from_pretrained: 모델과 동일한 토크나이저를 로드하여 텍스트를 ID 시퀀스로 변환합니다. (note_date: 2026-09-04, model: nvidia-nemotron-3.5-lightning-30b-a3b)
  • return_tensors="pt": PyTorch 텐서 형태로 반환하여 downstream 연산에 바로 사용 가능하게 합니다.
  • model.generate(): Causal LM 추론의 핵심 함수로, 입력된 토큰을 기반으로 다음 토큰을 자동 반복 생성합니다. attention mask는 모델 내부에서 inputs_embeds나 position_ids를 바탕으로 자동 생성되어 **inputs와 함께 전달됩니다.
  • tokenizer.decode(): 모델이 출력한 token ID 시퀀스를 사람이 읽을 수 있는 문자열로 변환합니다. skip_special_tokens=True로 special tokens (BOS/EOS 등)은 제거하고 실제 의미 있는 텍스트만 추출합니다.

위 내용은 학습 노트 SRC-20260905-001의 3. 실습 예시 섹션을 요약한 것입니다.

2. Qwen XPU 실행 시 TextStreamer·Chat Template 핵심 정리#

무엇을 배웠나#

TextStreamer를 사용하려면 단순히 클래스를 생성하는 것만으로는 충분하지 않으며, generate() 메서드에 인자로 전달해야 실시간 토큰 출력이 가능하다.

핵심적인 학습 포인트는 프롬프트를 message 리스트 형태로 구조화한 뒤 apply_chat_template()을 호출하여 모델이 기대하는 대화 형식으로 변환한 다음, tokenizer에 입력해야 한다는 점이다. chat template가 적용되지 않은 상태로 tokenizer에 직접 입력을 하면 모델이 예상하지 못한 형식을 받게 되어 오류가 발생할 수 있다.

헷갈렸던 점#

TextStreamer를 별도로 생성해두는 것만으로는 실시간 출력이 되지 않으며, 반드시 generate() 함수에 인자로 전달되어야 토큰이 스트리밍된다.

특히 chat template가 적용된 message 리스트를 tokenizer에 직접 입력하면 모델이 기대하지 못한 형식의 입력을 받게 되어 오류가 발생할 수 있다.

정리된 이해#

TextStreamer는 generate() 함수에 인자로 전달될 때만 토큰을 실시간으로 출력하며, 단순히 클래스를 생성해두는 것만으로는 효과가 없다. 핵심은 프롬프트를 메시지 리스트로 구조화한 뒤 apply_chat_template()를 호출하여 모델이 기대하는 대화 형식으로 변환한 후 토크나이저에 입력하는 것이다.

from transformers import AutoModelForCausalLM, AutoTokenizer, TextStreamer
import torch

model_id = "Qwen/Qwen2.5-7B-Instruct"

# 1. 모델과 토크나이저 로드
model = AutoModelForCausalLM.from_pretrained(model_id, dtype=torch.bfloat16)
model = model.to("xpu")
tokenizer = AutoTokenizer.from_pretrained(model_id)

# 2. chat 구조 생성 및 template 적용
messages = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "Hello!"}
]
prompt = tokenizer.apply_chat_template(messages, tokenize=False)

# 3. 토큰화 및 XPU로 이동
inputs = tokenizer(prompt).to(model.device)

# 4. TextStreamer 생성 및 generate 실행
streamer = TextStreamer(tokenizer, skip_prompt=True, skip_special_tokens=True)
_ = model.generate(**inputs, streamer=streamer)

3. SDPA와 EAGER 속도 비교 실험 (XPU 환경)#

무엇을 배웠나#

SDPA와 EAGER 속도 차이를 단순히 실행 결과로 비교하면 안 되며, XPU 환경에서는 첫 실행 시 하드웨어 초기화 비용이 섞이기 때문에 warm-up 과정을 반드시 거쳐야 정확한 측정이 가능하다. 또한 CUDA용 torch.cuda.synchronize() 대신 XPU 환경에 맞게 torch.xpu.synchronize()를 사용해야 하며, 내 하드웨어 백엔드에 맞는 최적의 구현체를 직접 측정하여 검증하는 것이 이론을 외우는 것보다 훨씬 실용적이다.

헷갈렸던 점#

첫 실행 결과가 실제 속도와 다르다는 점에 당황했으며, XPU 환경에서 synchronize 함수를 어떻게 호출해야 할지 막막했습니다. 단순히 숫자 비교를 넘어 하드웨어별 최적화된 파이프라인의 차이를 이해하는 데 집중해야 했습니다.

정리된 이해#

SDPA와 EAGER는 하드웨어 초기화 비용과 커널 준비 시간 차이로 인해 첫 실행 결과가 실제 속도와 다를 수 있으므로, 반복 실험 후 평균을 내어 검증하는 과정이 필수적입니다. 특히 XPU 환경에서는 torch.cuda.synchronize() 대신 torch.xpu.synchronize()를 사용해야 정확한 성능 측정이 가능합니다. 결국 중요한 것은 특정 하드웨어에 최적화된 구현체를 직접 측정하여 검증하는 실용적인 접근입니다.

from transformers import AutoModelForCausalLM, AutoTokenizer
import torch

# Qwen2.5-1.5B-Instruct 모델 로드 (XPU 환경용)
model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen2.5-1.5B-Instruct",
    device_map="xpu",  # Intel XPU 지정
    attn_implementation="sdpa"  # sdpa로 설정 후 측정
)

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-1.5B-Instruct")

총평#

오늘 오전 전체에서 배운 것#

AutoTokenizer와 AutoModel 직접 연결은 device 설정 등 모델 파라미터를 자유롭게 제어할 수 있어 편리하며, Qwen XPU 실행 시 TextStreamer 사용을 위해서는 generate() 메서드에 인자로 반드시 전달해야 한다. 또한 XPU 환경에서 속도 측정을 할 때는 warm-up 과정을 거쳐야 하고 torch.xpu.synchronize()를 사용해야 정확한 비교가 가능하다.

다음에 조심할 것#

  • torch.xpu.synchronize()를 정확히 호출하여 XPU 환경의 동기화 비용을 반드시 보정해야 정확한 속도 측정이 가능하다.
  • generate() 메서드에 TextStreamer 인자를 직접 전달하지 않으면 실시간 토큰 출력이 작동하지 않으므로, 파이프라인 구성 시 이 점을 간과하지 않도록 주의해야 한다.
  • 첫 실행 전 warm-up 과정을 거치지 않고 단순 비교를 진행하면 하드웨어 초기화 오차가 섞여 SDPA와 EAGER의 실제 성능 차이를 정확히 판단할 수 없다.
