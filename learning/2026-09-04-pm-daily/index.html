1. XPU 호환성과 라이브러리 버전 충돌 극복기#

무엇을 배웠나#

처음에는 XPU 호환성 문제라고 생각했으나, 실제로는 diffusers, transformers, huggingface-hub 라이브러리 간의 버전 불일치로 인한 dependency conflict였습니다. 텍스트 생성보다 이미지 생성이 환경 궁합에 민감하므로, XPU 사용 시 기존 성공했던 설정이나 버전을 그대로 유지하는 것이 가장 중요하다는 점을 깨달았습니다.

헷갈렸던 점#

처음에는 XPU 호환성 문제로 생각했지만, 실제로는 diffusers, transformers, huggingface-hub 라이브러리 간의 버전 불일치(dependency conflict) 때문이었다.

에러 메시지가 XPU 관련인 것처럼 보여서 실제 원인이 라이브러리 로드 단계의 호환성 문제임을 파악하는 데 시간이 걸렸다. 텍스트 생성보다 이미지 생성은 환경 궁합이 민감하므로, 기존에 성공했던 설정이나 버전을 건드리지 않는 것이 가장 중요하다.

정리된 이해#

XPU 환경에서 이미지 생성 시 라이브러리 버전 호환성 문제가 가장 큰 장애물이 되며, torch.bfloat16 지정과 xpu 디바이스 이동 순서가 핵심적인 성공 요인이다.

import torch
from diffusers import StableDiffusionPipeline

# 모델 로드 (기본적으로 float16 또는 bfloat16 권장)
pipe = StableDiffusionPipeline.from_pretrained(
    "runwayml/stable-diffusion-v1-5",
    torch_dtype=torch.bfloat16
)

# XPU 디바이스로 이동 (핵심 단계)
pipe.to("xpu")

# 추론 실행
image = pipe("a photo of an astronaut riding a horse on mars").images[0]

# 이미지 저장
image.save("astronaut.png")

2. 프롬프트 구조화와 steps 활용법, 네거티브 프롬프트의 필요성#

무엇을 배웠나#

긴 프롬프트는 단순히 길이가 중요한 것이 아니라, ‘주인공·배경·분위기·스타일’로 구조화해야 결과 관리가 쉬워진다는 점을 깨달았습니다. steps 수를 늘리면 이미지가 정교해지지만, 무조건 높이는 것은 시간 비용 증가와 아티팩트 위험을 가져오므로 가이던스 스케일과 균형을 맞춰 조절해야 한다는 점을 이해했습니다.

헷갈렸던 점#

프롬프트가 길수록 좋은 결과가 나오는 줄 알았는데, 오히려 요소가 섞여 엉뚱한 결과가 나와서 ‘문장 길이’가 아니라 구조와 역할이 중요하다는 것을 깨달았습니다.

steps 수를 늘리면 이미지가 더 정교해진다는 설명을 들었지만, 구체적으로 어떤 점이 개선되는지 감이 안 잡혔고, 너무 많이 늘리면 발생할 부작용에 대해서도 몰랐습니다.

정리된 이해#

프롬프트는 문장 길이가 아니라 ‘주인공·배경·분위기·스타일’로 구분해 구조화하는 것이 효과적이며, steps 수는 증가할수록 결과가 정교해지지만 과도하면 아티팩트가 발생할 수 있으므로 가이던스 스케일과 균형을 맞춰야 한다.

# 프롬프트 구조화 예시 (SD 1.5 기준)
prompt = "(masterpiece, best quality), " \
         "subject: a young woman, " \
         "background: rainy city street at night, " \
         "atmosphere: cyberpunk, neon lights, " \
         "style: anime style, detailed illustration, " \
         "details: glowing eyes, wet pavement reflection"

# Steps와 Guidance Scale 조절 예시
steps = 20
guidance_scale = 7.5

# 네거티브 프롬프트 예시
negative_prompt = "(worst quality, low quality:1.4), blurry, deformed hands, extra digits, malformed limbs, watermark, text"

3. Ollama Windows 설치와 모델 저장소 분리#

무엇을 배웠나#

Ollama 설치 시 PowerShell 위치가 System32로 보였지만, 실제로는 현재 작업 디렉터리일 뿐 시스템 폴더에 영향을 주지 않는다. 모델 저장소 경로는 프로그램 설치와 별개로 환경 변수 OLLAMA_MODELS를 설정해 원하는 드라이브로 분리할 수 있다.

헷갈렸던 점#

Ollama 설치 명령어를 실행할 때 irm과 iex가 각각 웹 스크립트 다운로드와 즉시 실행을 의미한다는 점을 정확히 이해했습니다.

기본 프로그램 설치 경로는 시스템 폴더와 무관하게 현재 작업 디렉터리에서 진행되며, 모델 저장소 경로는 별도의 환경 변수(OLLAMA_MODELS)를 설정해 원하는 드라이브로 분리가 가능하다는 사실을 명확히 했습니다.

정리된 이해#

Ollama 프로그램 설치와 모델 저장소 경로는 별개의 개념이다. 기본적으로 프로그램을 깔면 시스템 폴더에 등록되지만, 환경 변수 OLLAMA_MODELS를 설정하면 원하는 드라이브로 모델 저장 위치를 분리할 수 있다. 이를 통해 C드라이브 용량을 절약하고 관리 효율을 높일 수 있다.

Ollama Windows 설치와 모델 저장소 분리#

🟡 초보자 시점, 학습자의 혼란#

오늘은 로컬 LLM 환경 구축의 첫걸음인 Ollama Windows 설치를 진행했습니다. 강사님의 PowerShell 기반 설치 명령어부터 시작해 모델 저장소 경로 분리까지의 과정을 기록합니다.

가장 먼저 든 생각은 “설치가 시스템 폴더에 되는 건가?“라는 막연한 불안감이었습니다. irm https://ollama.com/install.ps1 | iex 명령어를 보고, irm이 Invoke-RestMethod, iex가 Invoke-Expression이라는 설명을 들으며 차근차근 이해해 나갔습니다. 그런데 “PowerShell 위치가 C:\Windows\System32>이면 설치가 System32에 되는 것처럼 보인다"는 수업 내용에 살짝 멘붕이 왔습니다. 현재 작업 디렉터리일 뿐인데, 시스템 폴더인 줄 알고 걱정했던 제 모습이 웃기면서도, 초보자가 환경 변수와 경로 설정을 할 때 얼마나 쉽게 혼란스러울지 실감하게 된 계기가 되었습니다.

📌 정리된 이해#

핵심은 **“Ollama 프로그램 자체의 설치와 모델 저장소의 위치는 별개”**라는 점이었습니다. 기본적으로 프로그램을 깔고, 그다음에 환경 변수 OLLAMA_MODELS를 설정해 모델이 저장될 경로를 원하는 드라이브로 분리하는 방식입니다. Hugging Face를 쓰는 Python 가상환경과는 독립적으로 운영된다고 하니, 두 환경을 혼동하지 않고 각각의 원칙을 세우는 것이 중요하겠습니다.

🛠️ 실습 예시#

1. Ollama 설치 (PowerShell)#

irm https://ollama.com/install.ps1 | iex
  • irm: Invoke-RestMethod (웹에서 스크립트 다운로드)
  • iex: Invoke-Expression (스크립트 즉시 실행)

2. 모델 저장소 경로 분리 (CMD 또는 PowerShell)#

setx OLLAMA_MODELS "E:\ollama\models"
echo %OLLAMA_MODELS%

또는 PowerShell에서는:

echo $env:OLLAMA_MODELS

4. Vulkan 감지와 실제 GPU 오프로드의 간극#

무엇을 배웠나#

Vulkan 감지가 실제 GPU 오프로드를 보장하지 않으며, 로그의 표시와 모델 실행 여부는 별개라는 점을 명확히 구분할 수 있게 되었다. 특히 작은 용량 모델은 CPU만으로도 빠른 속도를 내므로, 초보자는 성능 향상의 증거로 GPU 활용도를 오해하기 쉽다. 결국 ollama run 명령어 하나로는 현재 어떤 백엔드가 실제로 동작하는지 판단하기 어렵다는 한계를 깨닫게 되었다.

헷갈렸던 점#

처음에는 Ollama의 ‘Vulkan 감지’ 로그가 GPU 오프로드 활성화로 직관적으로 해석되었습니다. 특히 작은 모델(2.4B)에서는 CPU 처리 속도가 빨라 실제 GPU 사용 여부와 관계없이 반응이 빨라 보였기 때문입니다. 그러나 OLLAMA_IGPU_ENABLE 설정에도 불구하고 CPU 점유율이 100% 유지되는 상황을 겪으며, ‘감지’와 ‘실제 실행’ 사이에는 분명한 간극이 있음을 깨닫게 되었습니다.

정리된 이해#

Vulkan 감지는 시스템 내 GPU가 인식된 사실을 의미하지만, 모델 추론에 실제로 사용되는 것은 아닙니다. exaone3.5:2.4b와 같이 작은 용량의 모델은 CPU만으로도 충분한 속도를 보여주어, 초보자는 GPU 활용 여부를 오해하기 쉽습니다. 따라서 로그의 감지 사실과 실제 실행 백엔드 사이의 간극을 정확히 구분하는 것이 중요합니다.

# Ollama Vulkan 감지와 CPU 실행 경계

🟡 무엇이 헷갈렸나 (Confusion Point)#

처음 Ollama를 접했을 때 가장 혼란스러웠던 점은 “Vulkan 감지"와 “실제 GPU 오프로드(Offload)“가 같을 것이라고 가정했던 것입니다.

ollama ps 명령어를 통해 모델이 실행되는 모습을 보니 100% CPU라고 표시되어 있었음에도, 반응 속도가 꽤 빨라서 **“아, GPU가 잘 작동하는구나”**라고 직관적으로 해석했습니다. 특히 로그에 OLLAMA_VULKAN:true와 Intel Arc 감지 문구가 함께 뜨니, 자연스럽게 “Vulkan이 활성화되어 GPU로 처리가 되는 것"으로 이해했던 것이죠.

하지만 정작 OLLAMA_IGPU_ENABLE=1을 강제로 설정해도 여전히 CPU 100%가 유지되는 상황을 마주하면서, “감지된 것"과 “실제 사용된 것” 사이에는 분명한 간극이 있다는 사실을 깨닫게 되었습니다. 작은 2.4B 모델의 특성상 CPU만으로도 충분히 빠른 속도가 나오기 때문에, 초보자인 저는 성능 향상의 증거로 GPU 활용도를 오해하기 쉬웠던 것입니다.

📌 정리된 이해 (Corrected Understanding)#

현재 제 상황은 다음과 같이 정리가 됩니다.

  1. Vulkan 감지 ≠ 실제 GPU Offload: Ollama가 Intel Arc와 같은 Vulkan 지원 GPU를 시스템에서 인식하고 있다는 사실은 맞지만, 그것이 반드시 모델 추론에 사용되는 것은 아닙니다.
  2. 모델 규모의 영향: exaone3.5:2.4b와 같이 작은 용량의 모델은 CPU만으로도 처리 속도가 빨라, 사용자로서는 GPU가 작동하는 것처럼 느껴질 수 있습니다.
  3. 명령어의 투명성 부족: ollama run 명령어 하나로는 현재 어떤 백엔드(Vulkan, Metal, GGML 등)가 실제로 동작하고 있는지, 그리고 연산이 CPU에서 이뤄지는지 GPU에서 이뤄지는지를 판단하기 어렵습니다.

결론적으로 “로그가 Vulkan을 감지했다"는 사실은 맞지만, “모델 실행이 GPU를 사용한다"는 해석은 섣부른 추측이었다.

총평#

오늘 오후 전체에서 배운 것#

XPU 환경에서는 라이버리 버전 충돌이 호환성 문제로 오해되기 쉽지만, 실제로는 diffusers와 transformers 등 간의 의존성 불일치가 주된 원인이라는 점을 명확히 했다. 프롬프트 작성의 핵심은 길이의 누적이 아니라 ‘주인공·배경·분위기·스타일’로의 구조화이며, steps 조절 시 가이던스 스케일과의 균형을 통해 시간 비용과 아티팩트 위험을 최소화해야 한다는 원칙을 세웠다. 마지막으로 Ollama 모델 경로는 환경 변수 OLLAMA_MODELS를 활용해 설치 위치와 분리할 수 있으며, Vulkan 감지가 실제 GPU 오프로드를 보장하지 않는다는 점을 구분하여 성능 해석의 오류를 방지하는 것이 중요하다는 사실을 확인했다.

다음에 조심할 것#

XPU 환경에서는 기존 검증된 라이브러리 버전을 그대로 유지하는 것이 가장 중요하며, 프롬프트는 ‘주인공·배경·분위기·스타일’로 구조화하여 관리 효율을 높여야 한다. 또한 steps 수를 늘릴 때는 가이던스 스케일과 균형을 맞춰 시간 비용 증가와 아티팩트 위험을 방지해야 한다.

다음 복습 주제#

다음에 복습할 주제는 다음과 같습니다.

XPU 환경에서 안정적인 모델 구동을 위해서는 라이브러리 버전 호환성보다 기존 검증된 설정 유지보수가 핵심임을 재확인하고, diffusers 및 transformers 관련 의존성 관리 전략을 심화 학습할 계획입니다. 또한 Ollama를 활용한 로컬 AI 환경 구성 시 모델 저장소 경로 분리 방법과 실제 GPU 오프로드 여부를 정확히 판단하는 방법을 검증하여, 불필요한 성능 오해 없이 효율적인 추론 환경을 구축하는 노하우를 습득하고자 합니다.

Qwen XPU 실행 시 TextStreamer·Chat Template 핵심 정리: TextStreamer를 사용하려면 단순히 클래스를 생성하는 것만으로는 충분하지 않으며, generate() 메서드에 인자로 전달해야 실시간 토큰 출력이 가능하다. 핵심적인 학습 포인트는 프롬프트를 message 리스트 형태로 구조화한 뒤 apply_chat_template()을 호출하여 모델이 기대하는 대화 형식으로 변환한 다음, tokenizer에 입력해야 한다는 점이다. chat template가 적용되지 않은 상태로 tokenizer에 직접 입력을 하면 모델이 예상하지 못한 형식을 받게 되어 오류가 발생할 수 있다. SDPA와 EAGR 속도 비교 실험 (XPU 환경): SDPA와 EAGER 속도 차이를 단순히 실행 결과로 비교하면 안 되며, XPU 환경에서는 첫 실행 시 하드웨어 초기화 비용이 섞이기 때문에 warm-up 과정을 반드시 거쳐야 정확한 측정이 가능하다. 또한 CUDA용 `torch.cuda.synchronize()` 대신 XPU 환경에 맞게 `torch.xpu.synchronize()`를 사용해야 하며, 내 하드웨어 백엔드에 맞는 최적의 구현체를 직접 측정하여 검증하는 것이 이론을 외우는 것보다 훨씬 실용적이다.
