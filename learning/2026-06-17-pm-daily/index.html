1. 데이터 정규화: 일관성과 정확성을 위한 설계 사고#

무엇을 배웠나#

정규화는 데이터를 단순히 분리하는 것이 아니라, 데이터의 일관성과 정확성을 확보하기 위한 설계 방식임을 이해하게 되었다. 특히, 삽입, 수정, 삭제 시 발생하는 이상 현상을 방지하고 데이터 관리의 효율성을 높이는 데 중요한 역할을 한다는 것을 알게 되었다. 공유 킥보드 서비스 예시를 통해 테이블 설계 과정을 직접 실습하면서 정규화의 개념을 더 명확하게 체감할 수 있었다.

헷갈렸던 점#

처음에는 데이터를 한 테이블에 묶어두는 것이 조회하기 편할 것 같았고, 여러 테이블로 나누는 과정이 오히려 더 복잡하게 느껴졌다. 기준 정보만 추가하는 것이 어렵게 느껴졌고, 테이블을 미리 만들어야 한다는 부담감도 있었다. 테이블 분리 과정이 필요한 이유가 불명확하게 느껴졌다.

정리된 이해#

정규화는 데이터의 중복을 줄이고 수정 및 삭제 시 발생하는 문제를 방지하기 위한 데이터 설계 방식이며, 테이블을 분리하여 데이터의 일관성을 유지하는 것을 목표로 한다. 단순히 데이터를 나누는 것이 아니라, 데이터의 논리적인 관리 단위를 정의하고 각 테이블 간의 관계를 명확히 하는 과정이다. 이를 통해 데이터의 정확성을 높이고, 유지보수를 용이하게 만들 수 있다.

CREATE TABLE Customer (
    CustomerID INT PRIMARY KEY,
    Name VARCHAR(100),
    Email VARCHAR(100)
);

CREATE TABLE Kickboard (
    KickboardID INT PRIMARY KEY,
    Brand VARCHAR(50),
    BaseFee DECIMAL(10, 2)
);

CREATE TABLE Rental (
    RentalID INT PRIMARY KEY,
    CustomerID INT,
    KickboardID INT,
    RentalDate DATE,
    FOREIGN KEY (CustomerID) REFERENCES Customer(CustomerID),
    FOREIGN KEY (KickboardID) REFERENCES Kickboard(KickboardID)
);

2. 데이터 정규화: 원자값, 복합키, 함수 종속 이해하기#

무엇을 배웠나#

정규화를 공부하면서 원자값, 복합키, 그리고 함수 종속성들의 관계를 이해하는 데 어려움을 겪었지만, 예시를 통해 개념을 명확하게 정리할 수 있었습니다. 특히 부분 함수 종속과 이행 함수 종속의 경우, 데이터 간의 결정 관계를 파악하는 것이 중요함을 알게 되었습니다. 이 노트를 통해 데이터베이스 설계 시 발생할 수 있는 문제점을 예방하고 효율적인 테이블 구조를 만들 수 있을 것 같습니다.

헷갈렸던 점#

원자값이 데이터가 단일 값을 가져야 한다는 것을 이해하는 데 시간이 걸렸고, 부분 함수 종속과 이행 함수 종속이 어떤 상황에서 발생하는지 감이 잘 잡히지 않았어요. 복합키는 여러 컬럼을 묶어서 사용한다는 건 알겠는데, 언제 그리고 왜 사용해야 하는지 명확하게 이해하기 어려웠습니다.

정리된 이해#

데이터 정규화는 데이터를 효율적으로 저장하고 중복을 줄이기 위한 과정인데, 특히 원자값은 한 컬럼에 단일 값만 넣어야 한다는 점을 기억해야 합니다. 복합키는 여러 컬럼을 묶어 고유하게 식별하는 역할을 하며, 부분 함수 종속과 이행 함수 종속은 특정 컬럼들이 다른 컬럼의 값을 결정하는 관계를 파악하는 데 중요한 개념입니다. 이 개념들을 제대로 이해하면 데이터베이스 설계 시 오류를 줄이고 성능을 향상시킬 수 있습니다.

-- 원자값 적용 예시
student_id | course_id | grade
1         | CS101     | A
1         | CS102     | B

-- 복합키 사용 예시
PRIMARY KEY (student_id, course_id)

-- 부분 함수 종속 예시
student_id → student_name

3. 킥보드 예제를 통한 데이터 정규화 이해#

무엇을 배웠나#

공유 킥보드 예제를 통해 비정규화된 테이블의 편리함 뒤에 숨겨진 데이터 일관성 문제를 깨달았다. 특히, 데이터 수정 시 여러 행을 일일이 업데이트해야 하는 번거로움과 오류 가능성이 있다는 점을 알게 되었다. 정규화를 통해 데이터 중복을 줄이고, 수정 및 추가 작업의 안전성을 높일 수 있다는 것을 이해하게 되었다.

헷갈렸던 점#

처음에는 테이블 하나에 모든 정보를 담는 비정규화 방식이 간단하고 조회하기 편해 보였는데, 데이터가 바뀌거나 추가될 때 문제가 생길 수 있다는 점을 제대로 몰랐다. 특히 여러 곳에서 같은 데이터가 반복될 때 수정이 어렵고, 실수로 누락될 가능성이 있다는 사실을 간과했었다. 정규화를 통해 데이터를 효율적으로 관리하고 일관성을 유지하는 것이 중요하다는 것을 깨달았다.

정리된 이해#

처음에는 비정규화된 테이블이 편리해 보였지만, 데이터 변경 시 일관성 문제를 야기할 수 있다는 것을 알게 되었다. 정규화를 통해 데이터 중복을 줄이고 각 테이블을 명확하게 분리함으로써, 데이터 관리의 안정성과 효율성을 높일 수 있다는 것을 깨달았다. 앞으로는 데이터 모델링 시 정규화의 중요성을 항상 염두에 두고 설계해야겠다.

CREATE TABLE customer_unnormalized (
       customer_id INT,
       customer_name VARCHAR,
       rental_time DATE,
       rental_location VARCHAR,
       brand VARCHAR,
       model_year INT,
       price_per_min DECIMAL,
       basic_price

UPDATE customer_unnormalized
SET price_per_min = 120
WHERE brand = 'boardkick';

4. 데이터 이해와 활용: 생성부터 분석까지#

무엇을 배웠나#

데이터는 복잡한 분석을 위한 것이 아니라, 간단히 분류하고 반복적으로 활용할 수 있는 기록이라는 것을 깨달았다. 내가 직접 생성하는 소설 장면이나 이미지 프롬프트 같은 것들도 데이터로 분류될 수 있다는 점을 이해하게 되었고, 데이터 척도에 따라 데이터를 어떻게 분류하고 활용할 수 있는지 실습을 통해 경험했다. 이제 데이터 생성자와 분석자라는 이분법적인 구분보다는, 데이터 파이프라인의 한 부분으로서 데이터 생성과 관리를 수행하는 사람이라고 생각할 수 있게 되었다.

헷갈렸던 점#

데이터 분석이라는 단어를 들으면 항상 외부에서 정보를 가져와 분석하는 과정이라고 생각했는데, 제가 직접 생성하는 소설 장면이나 이미지 프롬프트 같은 것들도 데이터로 간주해야 한다는 점이 처음에는 이해가 잘 안 되었습니다. 특히 제가 데이터를 만드는 사람인지, 분석하는 사람인지에 대한 역할 구분이 모호하게 느껴졌습니다. 데이터가 거창한 무엇인가라고 생각했지만, 기록 가능한 정보라는 점을 명확히 이해하게 되었습니다.

정리된 이해#

데이터는 복잡한 것이 아니라, 분류하고 반복적으로 활용할 수 있는 정보의 기록 자체를 의미한다. 나는 데이터를 만들기도 하고 분석하기도 하는데, 내가 만드는 것도 결국은 분석을 위한 데이터가 될 수 있다는 점을 이해하게 되었다. 메타데이터를 꼼꼼히 기록하면서 데이터의 종류에 따른 척도를 적용하는 연습을 꾸준히 해야겠다.

5. 개인 콘텐츠 파이프라인: 소설 중심 통합 데이터 관리#

무엇을 배웠나#

내 생성 콘텐츠 파이프라인을 소설 본문을 핵심 축으로 두고 모든 자산과 운영 데이터를 관리하는 구조로 이해하게 되었다. 소설을 중심으로 이미지, 영상, 음악 등의 파생 자산을 생성하고, 검수 및 수정 과정을 기록하며, 최종적으로 공개 가능한 산출물을 별도로 관리해야 한다는 점을 명확히 알게 되었다. 이를 통해 혼란스러웠던 역할과 목표가 정리되고 앞으로의 작업 방향을 설정하는 데 도움이 될 것이다.

헷갈렸던 점#

처음에는 소설을 중심으로 다양한 미디어를 통합하는 작업이 제 역할과 목표를 흐릿하게 만드는 것 같았어요. 특히 내부 운영 데이터와 공개 데이터의 경계가 명확하지 않아, 창작 방향이나 설정이 노출될까 봐 걱정했습니다. 소설이 모든 콘텐츠의 기준점이라는 것을 명확히 인지하고, 운영 데이터와 공개 데이터를 분리하는 과정이 필요하다는 것을 깨달았습니다.

정리된 이해#

내 작업은 소설 본문을 최우선으로 두고, 이를 기반으로 이미지, 영상, 음악 등 다양한 미디어를 생성하는 파이프라인입니다. 생성되는 콘텐츠는 내부 운영 데이터로 관리되며, 최종적으로는 공개 가능한 결과물만 별도로 추출됩니다. 소설 본문을 중심으로 구조를 명확히 하고, 각 자산 생성 및 검수 과정을 체계적으로 관리하는 것이 중요합니다.

- 소설 구조화:
   - 각 회차(Episode)와 장면(Scene)을 명확하게 분류하고 문서화합니다.

   - 예시: `C:\Ollama-IPEX\Content\Assets\Episode1\Scene1_ImageAsset.png`

오늘 오후 전체에서 배운 것#

데이터 정규화를 통해 데이터 관리의 중요성을 깨닫고, 데이터 간의 관계를 정확히 파악하는 것이 효율적인 테이블 설계를 위해 필수적임을 알게 되었다. 또한, 데이터는 단순 분석 도구로 쓰이는 것이 아니라, 반복적인 활용을 위한 기록이라는 점을 이해하고, 나만의 콘텐츠 파이프라인을 구축하여 데이터 관리의 효율성을 높일 수 있을 것이다.

다음에 조심할 것#

데이터 정규화 시 함수 종속성, 특히 이행 함수 종속을 파악하는 데 더 주의해야겠다. 복합키 개념을 완벽하게 이해하고 실제 설계에 적용하는 연습을 꾸준히 해야겠다. 개인 콘텐츠 파이프라인 구축 시, 소설 중심의 통합 관리라는 큰 틀을 잊지 않고 각 단계별 데이터 관리 프로세스를 꼼꼼하게 설계해야겠다.

다음 복습 주제#
