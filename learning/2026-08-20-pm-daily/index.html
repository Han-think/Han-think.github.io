1. MUI X Charts 데이터 변환과 라벨 처리 정리#

무엇을 배웠나#

차트의 핵심은 ‘원본 데이터’를 라이브러리가 요구하는 특정 구조로 변환하는 과정임을 깨달았다. arcLabel 함수를 통해 라벨과 값의 의미가 화면에 어떻게 표시되는지 명확히 구분할 수 있게 되었다. 또한, map()을 활용해 객체 배열을 시리즈별로 분리하는 데이터 가공 로직이 체계적으로 정리되었다.

헷갈렸던 점#

PieChart 라벨 표시 문제에서 label과 value가 무엇을 의미하는지, 그리고 화면에 어떻게 반영되는지 명확히 구분하지 못해 혼란스러웠다.

ScatterChart 데이터 구조 매핑 시 원본 데이터의 필드명(x1, y1 등)을 차트가 요구하는 x, y 프로퍼티로 변환하는 과정에서 객체와 배열이 중첩되며 줄맞춤과 괄호 처리에 어려움을 겪었다.

colorMap 방식인 piecewise와 continuous의 논리적 차이를 이해하지 못해, 특정 상황에서 어떤 방식을 적용해야 하는지 기준을 세우지 못했다.

정리된 이해#

차트 라이브러리에서 가장 중요한 것은 원본 데이터를 차트가 이해할 수 있는 특정 구조로 변환하는 전처리 과정이다. series와 data prop에 맞춰 필드명을 매핑하고, label과 value의 의미를 구분하여 표시하는 것이 핵심이며, 색상 매핑 방식은 데이터의 분포 특성에 따라 piecewise 또는 continuous 방식을 선택해야 한다.

// PieChart 라벨 표시 수정 예시
arcLabel: function (item) {
    return `${item.label}: ${item.value}`;
}

// ScatterChart 데이터 구조 매핑 예시
{label:'A', data:data.map(d => ({x:d.x1, y:d.y1}))}
{label:'B', data:data.map(d => ({x:d.x2, y:d.y2}))}

2. 서버 데이터 정확히 확인하기#

무엇을 배웠나#

서버 응답 데이터의 필드명을 정확히 확인하는 것이 얼마나 중요한지 뼈저리게 느꼈습니다. data.totalPage와 data.pages 같은 작은 차이 하나로 화면이 깨지거나 에러가 발생하기 쉽다는 점을 깨닫고, 실제 API 구조를 꼼꼼히 검증해야겠다고 다짐했습니다. 또한 MUI Pagination의 count prop에 전체 페이지 수를 정확히 전달하고, onChange 이벤트를 통해 원하는 페이지 번호를 받아오는 흐름을 확실히 정리할 수 있었습니다.

헷갈렸던 점#

처음에는 서버에서 넘어오는 데이터 구조를 정확히 파악하지 못해 큰 혼란을 겪었습니다. 콘솔 창에 뜬 데이터를 보고 data.totalPage라고 추측했는데, 실제로는 data.pages라는 필드명이 사용되고 있었기 때문입니다. 이 작은 차이 하나 때문에 페이지가 1개만 보였거나, 에러가 발생하거나 화면이 깨지는 경험을 했습니다.

가장 중요한 교훈은 **“서버 응답을 추측하지 말고 실제 필드명을 정확히 확인해야 한다”**는 점입니다. React의 문법 자체는 익숙했지만, 어떤 데이터를 state에 담아야 하는지(데이터 계약 확인)에 대한 부분이 가장 막막했습니다. let [pages, setPages] = useState(1);으로 페이지 상태를 관리하고, 서버로부터 받은 전체 페이지 수(data.pages)를 setPages(data.pages)로 업데이트해야 MUI Pagination의 count prop에 올바른 값이 전달됩니다.

정리된 이해#

서버 응답 데이터의 실제 필드명(data.pages)을 정확히 확인하는 것이 가장 중요합니다. useState로 관리한 페이지 상태를 MUI Pagination의 count prop에 직접 연결해야지만, 사용자가 페이지를 전환해도 올바른 게시글이 로드됩니다. finally, onChange 이벤트에서 전달된 페이지 인자를 받아 해당 데이터를 요청하는 함수를 호출하면 목록이 업데이트됩니다.

// useState로 페이지 상태 관리 (초기값 1)
const [pages, setPages] = useState(1);

// MUI Pagination 컴포넌트 사용
<Pagination
  count={pages} // state에 담긴 전체 페이지 수를 prop으로 전달
  component="nav"
  variant="fullWidth"
// 페이지가 변경될 때 호출되는 함수
  onChange={(event, value) => {
    callList(value); // value는 클릭한 페이지 번호
  }}
/>

3. React 데이터 공유: Prop Drilling에서 Context로 (초보자 시점)#

무엇을 배웠나#

Context를 통해 Props 전달의 번거로움을 해결할 수 있다는 점을 배웠습니다. 특히 Provider가 감싸고 있는 범위 안에서 자식 컴포넌트가 직접 데이터를 가져올 수 있어 트리 구조와 상관없이 데이터 공유가 가능해졌습니다. 또한 Context의 초기값이 단순히 placeholder 역할을 한다는 사실과, useContext를 통해 언제든 해당 값에 접근할 수 있다는 점을 명확히 이해하게 되었습니다.

헷갈렸던 점#

React 컴포넌트 트리를 타고 데이터를 전달하는 ‘Prop Drilling’ 과정은 중간 자식 컴포넌트가 어떤 Props를 받는지 파악하기 어렵고, Context의 기본값이 빈 문자열로 설정된 점을 타이밍 차이로 혼동하기 쉽습니다.

정리된 이해#

Context는 Props처럼 컴포넌트 간의 명시적인 연결 고리 없이, Provider가 감싸고 있는 범위 안에서 필요한 위치에서 바로 데이터를 사용할 수 있게 해준다. 핵심은 createContext로 객체를 생성하고, Provider로 값을 공급한 뒤, useContext 훅을 통해 해당 범위 내의 데이터를 직접 가져오는 세 단계 흐름으로 이루어진다. 이를 통해 중간 컴포넌트들이 불필요하게 Props를 전달하는 번거로움 없이, 트리 구조 상 어디에 있든 Context 값에 접근할 수 있다.

import React, { createContext, useContext } from 'react';

// 1. Context 생성 (초기값: 빈 문자열)
const DataContext = createContext('');

// 2. Provider 컴포넌트 (데이터를 공급하는 역할)
const DataProvider = ({ children }) => {
  const value = '공유하고 싶은 데이터'; // 실제 전달할 값

  return (
    <DataContext.Provider value={value}>
      {children}
    </DataContext.Provider>
  );
};

// 3. 데이터를 사용하는 컴포넌트 (어디서든 접근 가능)
const DataConsumer = () => {
  const data = useContext(DataContext);

  return <div>{data}</div>;
};

4. Context 실험: 값 변경 시 재렌더링 확인하기#

무엇을 배웠나#

Context는 컴포넌트 트리 전체에 데이터를 전달할 수 있는 전역 상태 관리 기능이지만, 값이 변경되면 소비하는 모든 컴포넌트가 다시 렌더링된다는 단점이 있다.

오늘 실험을 통해 Context의 변화가 특정 컴포넌트에만 국한되지 않고 트리 전체에 영향을 미치는지 확인하며, 단순히 ‘전역 상태’라고 생각하기보다 어떤 컴포넌트가 값 변경을 감지하는지 주의 깊게 살펴봐야 한다는 점을 깨달았다.

헷갈렸던 점#

Context를 배우기 전에는 상태 관리가 useState 하나라고 생각했었는데, Context가 ‘전역 상태’라는 개념과 함께 ‘값이 변하면 자식 컴포넌트가 모두 다시 그린다(Re-rendering)‘는 부작용을 동반한다는 점을 바로 이해하기 어려웠습니다. 특히 강의에서 바로 실험 코드를 작성해 재렌더링 발생 여부를 확인하려다 보니, Context가 단순히 데이터를 전달하는 기능인지, 상태 관리 도구인지를 구분하는 것이 혼란스러웠습니다. 결국 오늘 만든 기본 구조가 실제 서비스용 코드인지 실험용 스캐폴드인지도 구별하기 어려워, Context의 동작 원리를 파악하는 것보다 렌더링이 몇 번 일어나는지 확인하는 과정 itself에 집중하게 된 점이 가장 큰 오해였습니다.

정리된 이해#

Context는 컴포넌트 트리 전체에 데이터를 전달할 수 있는 전역 상태 관리 기능이지만, 값이 변경될 때 소비하는 모든 컴포넌트가 다시 렌더링된다는 단점이 있다. 따라서 단순히 “전역 변수처럼 사용하면 된다"는 생각보다는, 어떤 특정 컴포넌트가 값의 변화를 감지하고 재렌더링되는지 주의 깊게 관찰해야 한다. 오늘 실험을 통해 Context의 편리함과 함께 불필요한 렌더링 비용이 발생할 수 있음을 인지하게 되었다.

5. 수업 중 디버깅 원칙: 원본 보존과 안전한 진행#

무엇을 배웠나#

수업 중에는 강사님의 원본 코드를 그대로 유지하는 것이 최우선이며, 논리 수정은 복습 시간에 따로 진행해야 한다.

특히 주석을 삭제하지 않고 들여쓰기만 정돈하여 코드의 의도를 명확히 보존하는 것이 중요하며, 실행 확인 후 가장 가까운 에러 한 군데만 수정한 뒤 다음 단계로 넘어가야 한다.

헷갈렸던 점#

오늘은 JSX 구조와 강의 코드를 쫓아가는 과정에서 괄호 누락과 컴포넌트 생략으로 인해 화면이 깨지는 경험을 했습니다. 특히 API 데이터 필드명 추측으로 발생한 에러와, 내 수정 방향이 강사 코드와 달라져 흐름이 끊긴 점이 가장 혼란스러웠습니다. 이를 통해 수업 중에는 원본 코드를 보존하고 주석을 삭제하지 않는 것이 무엇보다 중요하다는 점을 명확히 했습니다.

정리된 이해#

강사님의 원본 코드를 그대로 사용하고, 주석을 삭제하지 않는 것이 최우선입니다. 수업 중에는 논리 수정보다는 들여쓰기 등 가벼운 정돈에 집중하고, 실행 여부를 먼저 확인한 뒤 가장 가까운 에러 한 군데만 신중하게 수정해야 합니다.

LearningLog 워킹 노트: 빠른 실습 수업에서 원본을 보존하는 디버깅 기준#

🟢 초보자 시점: 오늘의 혼란과 발견#

오늘 오후 반복 문제의 대부분은 ‘차트나 Context 개념’이 아니라, JSX 구조 자체와 강의 코드를 쫓아가는 과정에서 발생했습니다. 강의 속도가 빨라 한 번 놓친 코드가 이후 전체 흐름을 따라가기 어려웠고, 작은 오류가 연쇄적으로 생겨 당황했던 경험이 있습니다.

📌 오늘 내가 헷갈렸던 점#

  1. /> 누락 및 괄호 혼란: 배열/객체 중첩 괄호를 여닫을 때 실수가 잦았습니다.
  2. 컴포넌트 누락: 필요한 컴포넌트를 빠뜨려 화면이 깨지는 경우를 경험했습니다.
  3. 서버 응답 필드명 추측: 실제 API 데이터 구조와 다른 이름을 사용하려다 에러가 납니다.
  4. 강사 코드와의 이질감: 내 수정 방향이 강사님 코드와 달라져 흐름이 끊깁니다.
  5. 주석 소실: 주석이 사라지면 나중에 코드의 의도를 추적하기 어렵습니다.

🧹 정리된 이해 (핵심 요약)#

수업 중에는 **“원본을 보존하는 것”**이 최우선입니다. 더 좋은 코드 리팩토링은 복습 시간에 따로 진행해야 합니다.

안전하고 빠른 수업 진행 순서:

  1. 강사님 원본 유지: 강사가 보여준 코드를 그대로 사용합니다.
  2. 주석 보존: 코드의 의도를 위해 주석을 삭제하지 않습니다.
  3. 들여쓰기만 정리: 가독성을 위해 들여쓰기는 정돈하지만 논리는 건드리지 않습니다.
  4. 실행 확인: 일단 코드가 실행되는지 확인합니다.
  5. 에러 한 곳만 수정: 문제가 있다면 가장 가까운 에러 한 군데만 수정하고 진행합니다.
  6. cleaner approach는 복습 때: 수업 시간에는 원본 흐름을 유지하다가, 나중에 시간이 될 때 개선된 코드를 따로 작성합니다.

오후에는 MUI X 차트 데이터 변환과 서버 API 필드 검증, 그리고 React Context를 통한 데이터 공유에 대해 정리했습니다. 특히 차트의 경우 원본 데이터를 라이브러리 구조로 변환하는 과정의 중요성을 깨닫고, 서버 응답 시 totalPage와 pages 같은 필드명 차이로 인한 화면 오류 가능성을 경계하게 되었습니다. 또한 Context를 통해 Props 전달의 번거로움을 해결할 수 있지만, 값 변경 시 트리 전체 컴포넌트가 재렌더링된다는 점을 확인하며 신중한 상태 관리의 필요성을 체감했습니다.

다음에 조심할 것#

오늘 배운 내용은 데이터 관리와 상태 공유의 중요성을 다시 한번 체감하게 된 소중한 시간이었습니다.

MUI X Charts를 다루면서 가장 크게 느낀 점은 **‘원본 데이터를 라이브러리에 맞게 변환하는 과정’**이 얼마나 꼼꼼해야 하는지였습니다. 특히 arcLabel 함수를 통해 라벨과 값의 역할을 명확히 구분하고, map()을 활용해 시리즈별로 데이터를 분리하는 로직을 정리하니 차트 구성에 대한 감이 잡혔습니다. 데이터 변환 실수는 시각적 결과로 바로 드러나기 때문에, 다음 단계에서는 원본 구조를 보존하면서 라이브러리에 최적화된 형태로 가공하는 연습을 해야겠습니다.

서버 데이터 확인 부분은 ‘작은 차이가 큰 결과를 만든다’는 교훈을 얻었습니다. data.totalPage와 data.pages 같은 필드명 차이 하나로 화면이 깨질 수 있다는 점을 깨닫고, 실제 API 구조를 검증하는 습관을 들여야겠다고 다짐했습니다. MUI Pagination의 count prop과 onChange 이벤트 흐름을 확실히 정리한 것도 큰 수확입니다.

React에서의 데이터 공유 학습도 매우 유익했습니다. Prop Drilling에서 Context로 넘어오면서 Props 전달의 번거로움이 해결되고, Provider 범위 안에서 자식 컴포넌트가 직접 데이터를 가져올 수 있다는 점이 인상적이었습니다. Context가 단순히 placeholder 역할을 한다는 점과 useContext를 통해 언제든 값에 접근할 수 있는 명확한 이해가 되었습니다.

마지막으로 Context 실험을 통해 값이 변경되면 트리 전체가 다시 렌더링된다는 사실을 확인했습니다. ‘전역 상태’라고 생각하기보다, 어떤 컴포넌트가 값을 감지하는지 주의 깊게 살펴봐야 한다는 점을 깨달았습니다. 오늘 수업 중 강조된 원본 코드 보존과 에러 수정은 한 군데만, 그리고 들여쓰기 정돈으로 의도 보존의 중요성을 새겨두었습니다.

다음 복습 주제#

Context는 전역 상태 관리에 유용하지만, 값이 변경되면 트리 전체 컴포넌트가 재렌더링되는 부작용을 반드시 인지해야 한다. 따라서 Context를 도입할 때는 어떤 컴포넌트가 값을 의존하고 있는지 신중하게 분석하여 불필요한 렌더링을 방지하는 것이 중요하다.

React의 상태 관리 방식인 Prop Drilling과 Context 사이에서 프로젝트의 규모와 복잡도에 맞는 적절한 방법을 선택하는 연습이 필요했다. 특히 작은 규모에서는 불필요한 Context 사용이 오히려 코드를 복잡하게 만들 수 있으므로, 상태가 필요한 범위와 깊이를 고려하여 Props 전달과 Context 중 더 효율적인 방식을 결정해야 한다.
