1. pm-01-data-definition-erd-map#

무엇을 배웠나#

ERD는 테이블 간 관계를 보여주는 지도이고, 데이터 정의서는 각 컬럼의 의미를 설명하는 문서라는 것을 깨달았다. 복잡한 ERD 구조에서 핵심 경로를 파악하고, 데이터 정의서를 활용하면 SQL 쿼리 작성에 도움이 된다는 점을 알게 되었다. 특히, 문제 해결 시 어떤 경로를 따라가야 하는지 이해하는 것이 중요하다는 것을 배웠다.

헷갈렸던 점#

처음에는 ERD가 복잡해서 테이블 간의 관계를 파악하는 것 자체가 어려웠고, 여러 테이블에 동일한 이름의 컬럼이 있어서 그 의미가 무엇인지 혼동되기도 했습니다. 특히 데이터 정의서가 없어서 각 컬럼의 역할이 정확히 무엇인지 추론하기 힘들었습니다.

정리된 이해#

ERD는 테이블 간의 관계를 보여주는 지도이고, 데이터 정의서는 각 테이블과 컬럼의 의미를 자세히 설명하는 문서라는 것을 이해했다. 핵심 경로를 파악하고 데이터 정의서를 활용하면 복잡한 ERD도 쉽게 이해하고 활용할 수 있을 것 같다. 문제를 풀 때 어떤 경로를 따라야 할지, 어떤 테이블과 컬럼을 참고해야 할지 명확하게 판단할 수 있게 되었다.

    tracks.TrackId → albums.AlbumId → albums.Title

2. pm-02-subquery-basic-single-multi#

무엇을 배웠나#

서브쿼리는 평소 문제 해결 방식과 달리, 최종 결과를 먼저 생각하고 메인 쿼리를 작성하는 방식으로 접근해야 한다는 점을 알게 되었습니다. 메인 쿼리는 결과를 담을 틀을 만들고, 서브쿼리는 메인 쿼리가 필요로 하는 기준값을 제공하는 역할을 한다는 것을 이해하게 되었습니다. 이 과정을 통해 서브쿼리의 역할 분담을 명확히 파악하고 활용할 수 있게 되었습니다.

헷갈렸던 점#

평소 문제 해결 방식을 SQL 서브쿼리 작성 방식으로 바꾸는 게 너무 어려웠습니다. 직관적으로 앨범 ID를 먼저 찾는다고 생각했는데, SQL에서는 트랙 이름 기준으로 메인 쿼리를 먼저 작성해야 한다는 점이 헷갈렸습니다. 전체적인 문제 해결 흐름이 역전되는 느낌이었습니다.

정리된 이해#

서브쿼리는 메인 쿼리에서 필요한 정보를 미리 계산해서 제공하는 보조 쿼리라는 점을 이해해야 합니다. 문제 해결 과정에서 최종 결과를 먼저 생각하고, 그 기준값을 서브쿼리를 통해 찾아 메인 쿼리에 적용하는 역순 사고방식이 중요합니다. 이렇게 하면 메인 쿼리는 결과 데이터의 틀을 만들고, 서브쿼리는 필요한 조건을 제공하여 전체적인 쿼리가 효율적으로 작동합니다.

SELECT Name
FROM tracks
WHERE AlbumId IN (SELECT AlbumId FROM albums WHERE GenreId IN (SELECT GenreId FROM genres WHERE Name = 'Rock'));

3. pm-03-join-vs-subquery-choice#

무엇을 배웠나#

JOIN과 서브쿼리가 같은 결과를 얻을 수 있지만, 접근 방식이 완전히 다르다는 것을 알게 되었다. 서브쿼리는 필요한 값을 먼저 찾아 조건을 적용하고, JOIN은 테이블을 연결하여 데이터를 통합한다는 점이 가장 큰 차이점이다. 앞으로는 상황에 따라 적절한 방법을 선택하여 SQL 쿼리를 작성할 수 있을 것 같다.

헷갈렸던 점#

처음에는 서브쿼리와 JOIN이 결국 같은 정보를 가져다주는데 왜 다른 방식으로 접근해야 하는지 이해하기 어려웠다. 특히 서브쿼리는 최종 테이블에서 시작해서 하위 테이블을 거쳐 조건을 찾는 방식이고, JOIN은 연결할 테이블부터 시작하는 점이 헷갈렸다. 결과적으로 두 방식의 차이를 이해하고, 어떤 상황에 어떤 방식을 사용하는 것이 더 효율적인지 파악하는 것이 중요했다.

정리된 이해#

서브쿼리는 먼저 필요한 값을 찾아 조건을 설정하고, JOIN은 테이블들을 직접 연결하여 데이터를 추출한다는 점에서 접근 방식이 달라요. 서브쿼리는 조건이나 목록을 빠르게 찾는 데, JOIN은 여러 테이블의 데이터를 통합하여 보여주는 데 더 적합하다고 이해했습니다. 앞으로는 상황에 따라 적절한 방법을 선택해서 사용해야겠어요.

-- 서브쿼리 예제: 특정 평균 판매 금액 이상의 제품 찾기
-- (판매 금액의 평균을 먼저 구해 그 평균보다 높은 판매 금액을 가진 제품을 찾습니다.)
SELECT ProductName
FROM Products
WHERE SalesAmount > (SELECT AVG(SalesAmount) FROM Products);

4. pm-04-subquery-learning-friction#

무엇을 배웠나#

서브쿼리 학습 초반에는 메인 쿼리부터 접근해야 한다는 점이 헷갈렸지만, 고정된 템플릿을 활용하면서 문제 해결 과정을 체계적으로 정리할 수 있게 되었다. 쿼리 작성 시 최종 출력, 테이블, 조건 컬럼 등을 명확히 정의하는 것이 중요하며, 이를 통해 복잡한 쿼리를 효과적으로 구성할 수 있다는 것을 알게 되었다. 이번 경험을 바탕으로 앞으로 더욱 효율적인 쿼리 작성을 할 수 있을 것이다.

헷갈렸던 점#

쿼리를 거꾸로 접근해야 한다는 점이 처음엔 매우 헷갈렸고, 필요한 조건값을 미리 넣어 계산해야 하는 방식이 직관적이지 않았다. 또한, 테이블과 컬럼 간의 정확한 연결 관계를 기억하는 데 어려움을 느껴 쿼리 작성이 막혔다.

정리된 이해#

서브쿼리는 문제 해결의 단서를 먼저 파악하는 것이 아니라, 먼저 어떤 결과를 보여줄지 명확히 한 후 필요한 정보를 테이블에서 찾아 쿼리를 역으로 작성해야 한다는 것을 깨달았습니다. 최종 출력과 테이블을 먼저 정하고, 필요한 정보가 어디에 있는지 추적하며 서브쿼리의 역할을 명확히 하는 것이 중요합니다.

SELECT Name
FROM tracks
WHERE AlbumId = 4;

SELECT Name
FROM tracks
WHERE AlbumId = 4;

총평#

오늘 오후 전체에서 배운 것#

ERD와 데이터 정의서를 활용하여 복잡한 관계를 이해하고, 서브쿼리를 통해 문제 해결의 기준값을 먼저 설정하는 접근 방식을 익혔습니다. JOIN과 서브쿼리의 차이점을 이해하며 상황에 맞는 쿼리 작성 방법을 고민하게 되었고, 템플릿을 활용하여 복잡한 쿼리 작성 과정을 체계적으로 정리하는 방법을 배웠습니다. 앞으로는 더욱 효율적인 SQL 쿼리 작성에 도움이 될 것입니다.

다음에 조심할 것#

서브쿼리를 사용할 때 메인 쿼리부터 접근하는 방식이 익숙해져서 오히려 복잡한 쿼리에서 길을 잃지 않도록 주의해야겠다. JOIN과 서브쿼리 중 어떤 방식을 선택해야 할지 판단하는 기준을 명확하게 세우고, 다양한 상황에서 연습하며 실력을 키워야겠다. 쿼리 작성 전 최종 출력, 테이블, 조건 컬럼을 꼼꼼히 정의하는 습관을 꾸준히 유지해야 더 효율적인 쿼리를 작성할 수 있을 것 같다.

다음 복습 주제#

서브쿼리를 활용한 문제 해결 방식에 익숙해지고, 다양한 상황에서 JOIN과 서브쿼리 중 어떤 방법을 선택해야 할지 판단하는 연습을 좀 더 해야 할 것 같아요. 특히, 서브쿼리의 역할 분담을 명확히 이해하고 적용하는 능력을 키우는 데 집중해서 복습할 예정입니다.
