1. 대화 이력을 State에 누적하기 — end_point와 message history#

무엇을 배웠나#

State가 단순한 중간값 전달을 넘어, 다음 실행에서도 이어질 수 있는 대화 이력을 담아가는 저장소 역할을 한다는 점을 이해하게 되었습니다. 특히 end_point_answer() 함수에서 HumanMessage와 AIMessage를 만들어 context에 저장하는 방식이, 답변을 단순히 텍스트로 저장하는 것을 넘어 conversation의 맥락을 다음 질문에도 전달하여 연속성을 유지하게 한다는 점이 인상 깊었습니다. 각 worker가 답변을 내고 나면 end_point에서 history를 통합적으로 관리함으로써 중복 코드를 줄이고 시스템 전체의 일관성을 높일 수 있다는 구조적 이점도 명확히 파악했습니다.

헷갈렸던 점#

처음에는 end_node가 왜 필요한지 이해되지 않았습니다. 이전까지는 각 worker가 질문을 받아 답을 내고 바로 종료되는 것으로 알았기 때문입니다. 특히 end_point_answer() 함수에서 message 객체를 만들어 context에 저장하는 과정이 왜 필요한지 감이 잡히지 않았습니다.

핵심은 State가 단순한 중간값 전달을 넘어, “다음 실행에서도 이어질 수 있는 이력"을 담아가는 확장된 개념이라는 점입니다. 기존에는 한 질문의 처리 중간값만 전달했다면, 오늘 learned 것은 State가 현재 작업 상태와 이전 대화 이력을 함께持ち去도록 설계된다는 것입니다. context는 이전 사용자/AI message의 목록이며, 모든 worker가 끝난 뒤 공통 end_point에서 history를 저장하면 중복 코드를 줄이고 conversation의 연속성을 유지할 수 있습니다.

정리된 이해#

State는 단순한 중간값 전달을 넘어, 다음 실행에서도 이어질 수 있는 대화 이력을 담아가는 역할을 한다. context에 HumanMessage, AIMessage를 저장함으로써 각 worker가 끝난 뒤 공통된 end_point에서 중복 코드 없이 대화의 맥락을 지속적으로 유지할 수 있다. 이는 단순히 답변을 저장하는 것을 넘어, 다음 질문에도 이전 대화를 재사용하여 연속성을 보장한다.

context.append(
    HumanMessage(content=state["question"])
)

context.append(
    AIMessage(content=state["generation"])
)

2. 대화 흐름을 잇는 체크포인트: thread_id와 MemorySaver#

무엇을 배웠나#

thread_id는 대화 단위를 구분하는 핵심 키이며, MemorySaver와 checkpointer를 사용하면 같은 스레드에서 연속된 invoke 호출 사이에 그래프의 상태가 자동으로 복원되어 문맥을 이어갈 수 있습니다. 또한 context는 애플리케이션 데이터인 반면 MemorySaver는 LangGraph 런타임이 상태를 보존하는 저장 메커니즘이라는 점을 명확히 구분해야 합니다.

헷갈렸던 점#

context는 실제 대화 내용(메시지 등)이지만, MemorySaver는 LangGraph 런타임이 상태를 보존하는 저장 메커니즘이라는 점이 가장 헷갈렸습니다. 또한 thread_id가 단순히 대화 이름을 뜻한다고 생각했는데, 실제로는 graph 실행 흐름을 구분하고 state를 이어주는 핵심적인 key라는 점을 이해하는 데 시간이 걸렸습니다. checkpointer 없이서는 이전 invocation의 state가 다음 invocation에서 복원되지 않으므로, state 지속성을 위해서는 이 세 요소가 함께 작동해야 한다는 점이 명확하지 않았습니다.

정리된 이해#

thread_id는 한 대화를 구분하는 고유 식별자이며, MemorySaver와 checkpointer를 사용하면 같은 thread_id를 통해 여러 번의 graph 실행 사이에서 상태가 지속되어 대화 맥락을 이어갈 수 있습니다. context는 애플리케이션 데이터이고 MemorySaver는 LangGraph 런타임이 상태를 보존하는 저장 메커니즘이라는 점을 명확히 구분해야 합니다.

from langgraph.checkpoint.memory import MemorySaver
import uuid

# 1. MemorySaver 인스턴스 생성 (상태를 보존하는 저장소)
memory = MemorySaver()

# 2. 그래프 컴파일 시 checkpointer로 memory 전달
app = wf.compile(checkpointer=memory)

# 3. 대화 식별자를 위한 thread_id 설정 (configurable에 포함)
config = {
    "configurable": {
        "thread_id": uuid.uuid4()  # 고유한 conversation ID 생성
    }
}

# 4. 첫 번째 invoke: 초기 상태 전송
response1 = app.invoke("안녕하세요!", config)

# 5. 두 번째 invoke: 이전 thread의 state가 자동으로 복원되어 이어짐
response2 = app.invoke("오늘 날씨 어때?", config)

3. history를 프롬프트에 다시 연결하기#

무엇을 배웠나#

MemorySaver 같은 도구는 과거 대화를 저장하는 역할만 수행하며, 자동으로 LLM 프롬프트에 연결되지 않습니다. 따라서 저장된 history를 다음 inference input으로 다시 명시적으로 연결해야 모델이 이전 맥락을 참고할 수 있습니다. message ordering가 실제 응답 문맥에 직접적인 영향을 미친다는 점을 이해해야 합니다.

헷갈렸던 점#

처음에는 MemorySaver 같은 도구가 과거 대화를 자동으로 다음 프롬프트에 연결해줄 것이라 생각했습니다. 하지만 실제로는 저장된 상태가 LLM 입력에 직접 삽입되지 않으면 모델이 이전 내용을 참고할 수 없다는 점을 가장 크게 혼동했습니다. 결국 ‘저장’과 ‘사용’은 별도의 단계이며, message ordering를 통해 과거 대화를 프롬프트에 다시 연결해야만 모델이 이를 참조할 수 있습니다.

정리된 이해#

MemorySaver 같은 도구는 과거 상태를 복원하는 역할만 수행하며, LLM이 자동으로 이전 대화를 읽어쓰지는 않습니다. 따라서 저장된 history를 다음 inference input의 프롬프트 메시지 리스트에 명시적으로 다시 연결해야 모델이 문맥을 이해할 수 있습니다. message ordering은 실제 응답 문맥에 직접적인 영향을 미치므로, context를 먼저 넣고 현재 질문을 마지막에 추가하는 패턴을 반드시 따라야 합니다.

# 1. 저장된 history를 message list의 선두에 확장
msg_list.extend(context)

# 2. 현재 질문을 리스트의 가장 마지막에 추가
msg_list.append(
    HumanMessage(content=question)
)

총평#

오늘 오후 전체에서 배운 것#

State를 통해 대화 이력을 누적함으로써 다음 실행에서도 맥락을 이어갈 수 있게 되었고, end_point에서의 통합 관리로 시스템 일관성을 높일 수 있었습니다. 또한 thread_id와 MemorySaver를 활용해 그래프 상태를 자동 복원하여 연속성을 유지할 수 있으며, 저장된 history는 명시적으로 프롬프트에 연결해야 모델이 이전 맥락을 참고할 수 있다는 점을 명확히 했습니다.

다음에 조심할 것#

  • end_point 함수에서 history를 누적 저장하더라도, 자동으로 LLM 프롬프트에 포함되지 않으므로 다음 inference 시 반드시 explicit하게 message history를 연결해 주어야 연속성이 유지됨을 유의해야 한다.
  • thread_id와 MemorySaver를 활용한 상태 복원과 달리, prompt에 이력을 연결하는 작업은 개발자가 직접 구현해야 하므로, 실수로 인해 이전 대화 맥락이 무시되지 않도록 코드 흐름을 꼼꼼히 검증할 필요가 있다.

다음 복습 주제#

다음에는 MemorySaver와 checkpointer를 활용한 대화 흐름 유지 기법과, 저장된 history를 LLM 프롬프트에 명시적으로 연결하는 구체적인 구현 방법을 중점적으로 복습할 예정입니다. 특히 어떤 순서로 message를 배치해야 모델이 이전 맥락을 가장 효과적으로 참고할 수 있는지 실험해보는 시간을 갖겠습니다.
