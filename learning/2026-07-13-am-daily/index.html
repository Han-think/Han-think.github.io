1. Pipeline으로 Kaggle 베이스라인 완주하기#

무엇을 배웠나#

오전 수업에서는 Kaggle 프로젝트를 처음부터 제출까지 한 번 완주하는 표준 흐름을 확인했다.

문제 정의
-> 데이터 확인
-> 독립변수와 종속변수 분리
-> 전처리 Pipeline 구성
-> 베이스라인 모델 학습
-> Balanced Accuracy 확인
-> 테스트 데이터 예측
-> submission.csv 생성
-> Kaggle 제출 및 점수 확인

처음부터 최고 점수를 노리는 것보다, 같은 입력에서 같은 결과를 다시 만들 수 있는 기준선부터 완성하는 것이 중요했다. 기준선이 있어야 이후의 피처 엔지니어링이나 앙상블이 실제 개선인지 비교할 수 있다.

헷갈렸던 점#

강사님의 제출 코드는 짧았고, 개인 프로젝트에서 만든 앙상블과 보정 코드는 훨씬 복잡했다. 그래서 코드가 짧으면 분석이 단순한 것인지, 내 방식이 필요 이상으로 복잡한 것인지 헷갈렸다.

정리된 이해#

제출 코드가 짧은 이유는 전처리와 모델이 이미 final_pipeline 안에 묶여 있기 때문이다. 중요한 것은 마지막 세 줄의 길이가 아니라, 학습할 때 적용한 전처리가 테스트 데이터에도 같은 순서로 적용된다는 점이다.

test_pred = final_pipeline.predict(X_test_kaggle)

submission = pd.DataFrame({
    id_col: test_ids,
    target_col: test_pred
})

submission.to_csv("submission_1th.csv", index=False)

Pipeline 문법은 코드를 예쁘게 줄이는 장치가 아니다. 전처리 누락과 데이터 누수를 줄이고, 학습과 예측의 절차를 하나의 재현 가능한 객체로 고정하는 장치다.

2. EDA를 변수 선택의 근거로 사용하기#

무엇을 배웠나#

EDA는 발표용 그래프를 만드는 단계가 아니라 어떤 변수를 왜 사용하고 어떻게 가공할지 결정하는 근거를 만드는 과정이었다.

Variable Selection
-> Issues with Data
-> Feature Engineering
-> EDA
-> Statistical Analysis

실제 작업에서는 이 단계들이 한 방향으로만 흐르지 않는다. EDA에서 이상한 분포를 발견하면 데이터 문제를 다시 확인하고, 새로운 관계가 보이면 파생 변수를 만든 뒤 통계와 모델 점수로 다시 검증한다.

헷갈렸던 점#

처음에는 EDA를 결과 보고서에 넣기 위한 시각화 정도로 생각했다. 그러나 수업 사례에서는 EDA가 변수 선택, 점수 설계, 클러스터링, 최종 우선순위까지 이어졌다.

정리된 이해#

각 단계의 역할은 다음처럼 구분할 수 있다.

단계 확인하는 것
EDA 데이터의 분포, 이상치, 변수 간 관계
상관분석 선형 관계와 중복 가능성
통계 검정 관찰한 차이가 우연일 가능성
Feature Engineering 관찰과 가설을 모델 입력으로 변환
모델링 만든 정보가 예측에 실제로 도움이 되는지 확인

개인 Kaggle 프로젝트에서 stress_level과 physical_activity_level의 관계를 다시 살펴보고 교차 피처를 만든 과정도 같은 흐름이었다. 그래프에서 끝내지 않고 모델 입력과 검증 점수까지 연결해야 EDA가 의사결정 근거가 된다.

3. 점수 설계와 검증 가능한 의사결정 구조#

무엇을 배웠나#

수업 사례에서는 알고리즘 결과만 보여주는 것이 아니라 우선순위 점수가 어떻게 구성되고 검증되는지 전체 과정을 다뤘다.

점수 구성 요소 선정
-> 방향성 통일
-> 단위 정규화
-> 가중치 산정
-> 클러스터링
-> 군집별 특성 분석
-> 최종 점수 계산
-> 민감도 분석
-> 현장 적용

서로 단위가 다른 값을 바로 더할 수 없고, 값이 클수록 좋은 변수와 나쁜 변수를 같은 방향으로 맞춰야 한다. 가중치도 단순한 감으로 정하기보다 왜 그 비중을 사용했는지 설명하고, 가중치가 조금 달라져도 결론이 유지되는지 확인해야 한다.

헷갈렸던 점#

처음에는 모델이나 클러스터링 알고리즘을 사용했다는 사실 자체가 전문성을 보여준다고 생각했다. 하지만 알고리즘 이름만으로는 입력이 어떻게 결과와 액션으로 이어졌는지 설명할 수 없었다.

정리된 이해#

검증 가능한 결과물에는 다음 연결이 남아야 한다.

입력 데이터
-> 정제 규칙
-> 변수와 방향성
-> 점수 또는 모델
-> 검증 결과
-> 해석
-> 실제 액션

좋은 분석은 “모델을 돌렸더니 이런 숫자가 나왔다”에서 멈추지 않는다. 입력과 규칙을 바꾸면 결과가 어떻게 달라지는지 추적할 수 있어야 하고, 최종 사용자가 그 결과를 어떤 판단에 사용할 수 있는지도 설명해야 한다.

4. 수업 베이스라인과 개인 최적화의 역할 구분#

무엇을 배웠나#

수업의 베이스라인은 표준 Pipeline으로 전체 흐름을 완주하는 데 목적이 있었고, 개인 프로젝트는 그 기준선 이후에 성능을 개선하고 검증을 강화하는 작업이었다.

수업 베이스라인 = 재현 가능한 전체 과정 학습
개인 최적화 = 기준선 이후 성능 개선과 검증 강화

강사님의 기본 제출에서 확인한 점수와 개인 프로젝트 점수는 사용한 특성, 모델, 보정, 검증 조건이 다르다. 따라서 숫자만 나란히 두고 어느 모델이 절대적으로 우수하다고 결론 내리면 안 된다. 비교할 때는 데이터, metric, split, 전처리와 제출 조건을 먼저 맞춰야 한다.

헷갈렸던 점#

개인 프로젝트를 너무 복잡하게 만든 것은 아닌지 걱정했다. 하지만 기준선과 최적화의 목적이 다르다는 점을 구분하자, 주말에 진행한 실험은 수업과 동떨어진 작업이 아니라 수업의 다음 단계를 먼저 경험한 것이었다.

정리된 이해#

기존 프로젝트를 처음부터 다시 만들 필요는 없다. 먼저 이미 존재하는 코드, 실험 결과, 그래프와 제출 기록을 조사하고, 수업의 분석 항목에 맞춰 재배치하면 된다. 없는 증빙만 추가하고, 조건이 다른 점수는 직접 비교하지 않으며, 모델을 다시 학습할 때는 그 이유와 기대 효과를 먼저 정해야 한다.

총평#

오늘 오전 전체에서 배운 것#

Kaggle 프로젝트는 높은 점수 하나를 만드는 활동이 아니라 문제 정의부터 제출까지 재현 가능한 흐름을 세우고, 기준선 이후의 개선을 검증하는 과정이라는 점을 배웠다. Pipeline, EDA, 통계, 점수 설계와 모델링은 따로 떨어진 기술이 아니라 하나의 판단 경로를 구성한다.

다음에 조심할 것#

조건이 다른 점수를 숫자만으로 비교하지 않는다. 새로운 피처나 앙상블이 좋아 보이더라도 같은 검증 조건에서 기준선을 넘는지 확인하고, 탐색에 사용하지 않은 fold나 표본에서도 결과가 유지되는지 다시 확인한다.

다음 복습 주제#

개인 Kaggle 프로젝트의 실험 원장을 기준으로 각 피처와 모델이 어떤 가설에서 시작됐고 어떤 검증에서 채택되거나 기각됐는지 연결해 본다. 이후 발표자료에서는 점수보다 문제 정의, 판단 근거와 재현 가능한 흐름이 먼저 보이도록 구성한다.
