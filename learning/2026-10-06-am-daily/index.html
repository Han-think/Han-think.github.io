1. RAG 파이프라인: 검색과 생성의 분리#

무엇을 배웠나#

오늘 RAG 파이프라인의 핵심 구조를 명확히 이해할 수 있었다. 검색기와 질문 엔진으로 나뉘는 두 단계가 단순히 문서를 찾는 것을 넘어, 점수 기반의 근거 확인과 답변 생성의 역할을 한다는 점이 인상 깊었다. 특히 검색된 결과의 점수를 통해 LLM이 어떤 부분을 참고했는지 추적하는 과정이 중요하다는 점을 깨닫고 실무에 적용해보고자 한다.

헷갈렸던 점#

검색된 문서의 점수만 보고 답변의 신뢰성을 판단하면 안 된다는 사실을 간과하고 있었다. 실제로는 점수가 낮은 문서를 근거로 LLM이 환각을 일으킬 수 있어, 검색 품질과 생성 품질을 분리해서 봐야 한다는 점을 깨닫지 못했다. Retriever 모드에서 source_nodes를 통해 어떤 문서가 답변의 근거가 되는지 추적하는 과정이 낯설고 중요하게 느껴졌다.

정리된 이해#

RAG 파이프라인에서 검색 품질과 생성 품질은 분리되어야 하며, 검색된 문서의 점수는 LLM이 답변을 생성할 때 환각을 막는 중요한 근거가 된다. Retriever는 질문의도에 맞는 상위 문서를 찾고 유사도 점수를 제공하며, Query Engine은 검색 결과를 바탕으로 답변을 생성하지만 이 과정에서 어떤 문서를 근거로 했는지 추적하는 것이 중요하다.

# Retriever 설정 예시
retriever = vector_store.as_retriever(
    similarity_top_k=5  # 상위 5개 문서 검색
)

# Query Engine 설정 예시 (검색 + 생성 통합)
query_engine = vector_store.as_query_engine()

2. Chroma 영속 저장과 Chat Engine 연결 흐름 — LlamaIndex 서비스화 여정#

무엇을 배웠나#

오늘 가장 크게 느낀 점은 ‘저장된 데이터’와 ‘최신 문서’가 반드시 일치하지 않는다는 사실이었습니다. 단순히 ChromaDB에 벡터가 존재한다는 것만으로는 그 내용이 최신 상태인지 보장할 수 없기 때문에, 실제 서비스에서는 갱신 정책을 반드시 고려해야 한다는 점을 깨달았습니다.

그리고 LlamaIndex에서 Chat Engine를 활용해 대화형 인터페이스를 구현하는 과정이 단순히 질문을 받는 것을 넘어, condense_plus_context 모드를 통해 이전 대화를 문맥으로 유지하며 답변한다는 점이 인상적이었습니다. 이는 RAG 시스템을 한 번 실행하는 도구를 넘어, 지속적으로 사용자가 상호작용할 수 있는 서비스로 진화시키는 핵심적인 전환점이 되었습니다.

헷갈렸던 점#

오늘 가장 크게 헷갈렸던 부분은 “저장되어 있다"는 것이 “데이터가 최신 상태다"라는 뜻이 아니다라는 점이었습니다.

강사님 방식에서 if coll.count() == 0: 조건을 보고 처음에는 “아, 데이터가 있으면 다시 안 읽어오네?” 정도로만 생각했습니다. 하지만 ‘문서가 수정되었거나 삭제된 경우’를 고려하지 않는 단순 카운트 기반의 skip 로직은, 실제 서비스에서는 치명적인 함정이 될 수 있겠다는 생각이 들었습니다.

특히 “이미 색인된 데이터가 있어도, 그 안에 들어있는 내용이 바뀌었다면?“이라는 질문이 들었는데, 강사님 코드에서는 그런 갱신 정책이 빠져 있었습니다. “데이터가 있다"와 “문서가 최신이다"는 완전히 다른 차원의 문제였습니다.

정리된 이해#

오늘 ChromaDB 영속 저장 방식의 핵심은 **“데이터가 존재한다는 것과 문서 내용이 최신이라는 것은 별개의 문제”**라는 점이었습니다. 단순히 count()로 색인 여부를 판단하면, 파일 내용이 수정되었음에도 이전 데이터가 그대로 사용되어 답변 정확도가 떨어질 수 있습니다.

따라서 실제 서비스에서는 저장된 데이터를 재사용하기 전, 문서 변동 이력을 확인하거나 강제 재색인과 같은 갱신 정책을 별도로 설계하는 것이 중요합니다.

from llama_index.core import VectorStoreIndex, StorageContext
from llama_index.vector_stores.chroma import ChromaVectorStore
import chromadb

# 1. ChromaDB 영속 클라이언트 설정 (이전 데이터 재사용을 위한 필수 단계)
persist_dir = "./chroma_db"
client = chromadb.PersistentClient(path=persist_dir)

# 2. 기존 컬렉션 불러오기 (이미 색인된 문서가 있다면 재임베딩 방지)
collection = client.get_collection("my_documents")
vector_store = ChromaVectorStore(chroma_collection=collection)
storage_context = StorageContext.from_defaults(vector_store=vector_store)

# 3. 저장된 벡터 스토어로부터 Index 복원 (이미 존재한다면 재처리 불필요)
index = VectorStoreIndex.from_vector_store(
    vector_store,
    storage_context=storage_context
)

# 4. Chat Engine 생성 (대화형 Q&A를 위한 설정)
chat_engine = index.as_chat_engine(
    chat_mode="condense_plus_context",
    verbose=True
)

# 5. 대화 실행 예시
response = chat_engine.chat("이 문서에 대해 무엇을 알고 싶어?")
print(response.response)

총평#

오늘 오전 전체에서 배운 것#

RAG 파이프라인의 검색기와 질문 엔진으로 이원화된 구조를 이해하고, 점수 기반 근거 확인을 통해 LLM의 답변 신뢰성을 높이는 방법을 학습했다. 또한 ChromaDB에 저장된 벡터가 항상 최신 문서를 반영하지 않을 수 있음을 인식하고, 서비스 운영 시 갱신 정책의 필수성을 체감했다. 마지막으로 Chat Engine를 활용해 condense_plus_context 모드를 적용, 이전 대화를 유지하며 지속적인 사용자 상호작용이 가능한 대화형 서비스로 시스템을 진화시킨 핵심 원리를 파악했다.

다음에 조심할 것#

오늘 학습한 내용을 바탕으로 다음에 조심해야 할 점을 정리해 본다.

먼저, 검색된 문서의 점수와 메타데이터를 반드시 확인하여 LLM이 근거로 삼는 정보가 최신 상태인지 검증하는 습관을 들여야 한다. 단순히 벡터가 존재한다는 사실만으로는 내용의 신빙성을 보장할 수 없으므로, 실제 서비스 환경에서는 데이터 갱신 정책을 철저히 점검해야 한다.

둘째, Chat Engine를 활용한 대화형 인터페이스를 구현할 때는 condense_plus_context 모드의 동작 원리를 정확히 이해하고 적용해야 한다. 이전 대화를 문맥으로 유지하는 기능은 시스템의 복잡성을 높일 수 있으므로, 대화 흐름을 설계할 때 사용자의 의도와 시스템의 상태가 일치하는지 지속적으로 검증하는 것이 중요하다.

다음 복습 주제#

RAG 파이프라인에서 검색된 결과의 점수 기반 근거 확인과 답변 생성의 분리 중요성을 다시 한번 강조하고 싶다.

ChromaDB에 벡터가 존재한다고 해서 그 내용이 최신 상태임을 보장할 수 없으므로, 실제 서비스 적용 시 데이터 갱신 정책을 반드시 고려해야 한다는 점을 명확히 인지해야 한다.
