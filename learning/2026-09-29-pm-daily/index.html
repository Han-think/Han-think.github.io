1. 다중 PDF RAG 구현 시 메타데이터 활용하기#

무엇을 배웠나#

오늘 ‘소설 한 권 RAG’에서 ‘여러 PDF RAG’로 범위를 넓혔을 때, 코드 자체는 반복되는 패턴이었지만 데이터 관리 방식이 근본적으로 달라진 것을 깨달았다. 핵심 알고리즘의 변화가 아니라, 입력 자료의 단위가 하나에서 여러 개로 확장되면서 각 청크에 과목 메타데이터를 부착하고 필터링 조건을 거는 방식으로 검색 범위를 정밀하게 조절할 수 있게 되었다. 특히 where 조건을 활용해 특정 과목만 선별적으로 검색하는 로직이 어떻게 작동하는지 감이 잡히는 좋은 계기가 되었다.

헷갈렸던 점#

오전과 오후 코드 구조가 거의 동일해 ‘확장된 것인가?‘라는 의문이 들었다.

핵심 알고리즘 자체는 반복되었지만, 데이터 단위가 ‘하나’에서 ‘여러 개’로 바뀌면서 각 청크에 과목 메타데이터를 부착하고 where 조건을 걸어 필터링하는 방식이 추가되었다.

정리된 이해#

오늘 ‘소설 한 권 RAG’에서 ‘여러 PDF RAG’로 범위를 확장했을 때, 코드 자체는 반복되는 패턴이었지만 핵심 로직은 변화하지 않았다. 중요한 차이는 입력 자료의 단위가 하나에서 여러 개로 늘어났고, 이를 구분하고 필터링하기 위해 각 청크에 ‘과목(subject)’ 메타데이터를 부가했다는 점이다. 결국 기존 알고리즘을 유지한 채 데이터 범위를 관리하는 방식이 확장된 것이었다.

lecture = (
    path
    .split("/")[1]
    .rsplit(".", 1)[0]
    .lower()
)

2. LangChain RAG 추상화와 직접 구현 비교#

무엇을 배웠나#

LangChain을 사용하면 RAG 파이프라인 전체를 코드 한 줄로 연결할 수 있다는 점이 가장 큰 장점이었다. RunnablePassthrough 같은 추상화 요소가 처음에는 낯설었지만, 결국 질의를 전달하고 결과를 파싱하는 단순한 역할임을 깨닫고 이해가 쉬어졌다. 직접 구현할 때보다 component별 역할을 분리해 정의함으로써 코드의 가독성과 유지보수성이 크게 향상된 것을 느꼈다.

헷갈렸던 점#

LangChain의 추상화된 컴포넌트들이 단순히 기능이 추가된 것이 아니라, 기존 RAG 흐름에서 각 단계를 독립적인 객체로 분리하고 파이프라인으로 연결하는 방식이라는 점이 처음에는 직관적이지 않았다.

특히 retriever가 단순한 검색 기능을 넘어 파이프라인 전체의 입구 역할을 하며, RunnablePassthrough가 질의를 전달해주는 장치라는 개념이 기존의 직관적인 코드 작성 흐름과 달라 혼란을 느꼈다.

정리된 이해#

LangChain은 RAG 파이프라인 각 단계(검색, 프롬프트 구성, LLM 호출, 결과 파싱)를 독립적인 component로 분리하고, 이들을 연결하는 LCEL(LangChain Expression Language)만 정의하면 되므로 코드 작성 복잡도가 크게 줄어든다. 핵심 기능은 직접 구현한 코드와 동일하지만, RunnablePassthrough 같은 추상화 장치를 통해 질의 전달과 컨텍스트 주입을 자동화하여 파이프라인 흐름을 명시적으로 제어할 수 있다. thus, “어떻게(Retrieval → Prompt → Generation)“가 아니라 “무엇을(Component 조합)“에 집중하여 RAG를 구현할 수 있게 된다.

from langchain_core.runnables import RunnablePassthrough
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# 1. retriever: 검색 및 컨텍스트 추출 (직접 구현의 query() 역할)
retriever = vectorstore.as_retriever()

# 2. RunnablePassthrough: 질의를 그대로 전달하는 장치
#    (직접 구현에서 context join 전 단계에 해당)

# 3. ChatPromptTemplate: 프롬프트 구성 (직접 구현의 prompt 문자열 생성 역할)
prompt = ChatPromptTemplate.from_template(
    "Use the following pieces of context to answer the question at the end. "
    "If you don't know the answer, just say that you don't know. Don't try to make up an answer.\n\n"
    "{context}\n\nQuestion: {question}"
)

# 4. LLM 호출 (직접 구현의 ollama.generate() 역할)
llm = ChatOllama(model="nvidia-nemotron-3.5-lightning-30b-a3b", temperature=0)

# 5. StrOutputParser: 출력 파싱 (직접 구현의 결과 반환 역할)

# 전체 파이프라인 정의 (LCEL)
rag_chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | prompt
    | llm
    | StrOutputParser()
)

3. RAG를 FastAPI 웹 서비스로 옮기기 — 업로드 화면, 채팅 화면, service 분리#

무엇을 배웠나#

오늘은 기존 RAG 알고리즘을 FastAPI 웹 서비스에 통합하는 과정을 시작했다. 파일 업로드와 라우팅 등 웹 프레임워크 특유의 개념이 섞이며 코드 구조 잡기에 집중했다. 핵심은 RAG 로직 자체를 새로 만든 것이 아니라, 기존 기능을 웹으로 연결하기 위한 ‘포장’과 ‘분리’ 작업에 있었다.

헷갈렸던 점#

처음에는 RAG 알고리즘 자체를 다시 짜는 줄 알았는데, 기존 로직을 FastAPI 위에 얹는 ‘포장’ 작업이었음을 깨닫고 혼란스러웠다. 특히 file_upload 함수 같은 경우 빈 껍데기만 만들고 return값도 False로 초기화해두니, 실제 서비스에서 어떻게 동작할지 감조차 잡히지 않았다. 파일 업로드, Form 데이터 처리, StaticFiles 마운트 등 웹 프레임워크 특유의 개념들이 섞이다 보니, RAG 로직 자체를 공부하던 때보다 더 막막함을 느꼈다.

정리된 이해#

오늘은 기존 RAG 알고리즘을 FastAPI 웹 서비스에 통합하는 과정을 시작했다. 핵심은 알고리즘 자체를 새로 만든 것이 아니라, main.py와 service/ 디렉토리를 기반으로 한 skeleton을 구성하여 PDF 업로드 및 채팅 엔드포인트의 뼈대를 잡는 것이었다. 기존 학습 패턴을 유지하며 RAG 로직을 웹 프레임워크 위에 포장하는 데 집중했다.

총평#

오늘 오후 전체에서 배운 것#

오늘은 다중 PDF RAG 구현 시 메타데이터를 활용해 검색 범위를 정밀하게 조절하는 방법을 배웠고, LangChain의 추상화 요소를 통해 코드의 가독성과 유지보수성을 크게 높일 수 있음을 체감했다. 또한 기존 RAG 알고리즘을 FastAPI 웹 서비스에 통합하면서, 핵심 로직을 그대로 둔 채 ‘포장’과 ‘분리’ 작업을 통해 시스템 구조를 재정비하는 과정을 시작했다.

다음에 조심할 것#

  1. 메타데이터 부착과 필터링 로직이 RAG 검색 정밀도에 미치는 영향을 간과하지 않도록 주의한다.
  2. 웹 서비스 이관 시 기존 알고리즘을 ‘포장’하는 데 집중하다가, 실제 서비스 운영에 필요한 예외 처리와 보안 관리를 소홀히 하지 않도록 한다.
  3. LangChain 추상화의 편의성에 익숙해져 직접 구현 시 component 역할 분리의 필연성을 간과하지 않도록 한다.
