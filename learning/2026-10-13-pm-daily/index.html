1. Docker Ollama와 LangChain 스트리밍 연결하기#

무엇을 배웠나#

Docker Ollama 환경에서는 기본 포트와 다른 포트를 사용 중이더라도 base_url 파라미터를 정확히 지정함으로써 모델 연결을 해결할 수 있었다. 또한 Uvicorn 실행 시 파일 경로와 옵션을 명확히 구분해두는 것이 실시간 서버 구축의 안정성을 높이는 핵심임을 깨달았다. 마지막으로 API 레벨에서의 스트리밍이 실제 UI 렌더링 속도와는 별개라는 점을 이해하여, 클라이언트 측 처리 로직의 중요성도 함께 인식하게 되었다.

헷갈렸던 점#

Docker Ollama가 사용하는 포트(예: 11435)와 강사님이 가정했던 기본값(11434)이 달라 연결이 안 되어 혼란스러웠습니다. 모델 이름만 바꾸면 되는 줄 알았지만, 실제로는 base_url을 수정해 서버 위치를 지정해야 한다는 사실을 깨닫고 나서야 흐름이 이해되었습니다. Uvicorn 실행 명령어의 세부 옵션들이 섞여 정확히 어떤 파일을 가리켜야 할지 불안했던 점을 정리했습니다.

정리된 이해#

학습 노트 내용을 바탕으로, Docker Ollama 환경에서 FastAPI와 LangChain을 연동할 때 서버 위치(base_url), 모델 이름(model), 그리고 웹 서버 실행 옵션을 명확히 분리하여 관리하는 것이 핵심입니다. 특히 기본값인 localhost:11434가 아닌, 실제 Docker 컨테이너가 사용하는 포트(예: 11435)를 base_url에 정확히 명시해야만 모델 호출이 정상적으로 작동합니다.

from langchain_ollama import ChatOllama
from fastapi import FastAPI
from langchain_core.outputs import LLMResult

# Ollama 서버 위치(base_url)와 모델명(model)을 분리하여 설정
llm = ChatOllama(
    model="gemma4:e4b",  # 사용할 모델 이름
    base_url="http://localhost:11435"  # Docker 환경에서 실제 실행 중인 포트
)

app = FastAPI()

@app.get("/stream")
async def stream_response():
    async def generate():
        # 스트리밍 방식으로 응답 생성
        async for chunk in llm.astream({"input": "Hello"}):
            yield chunk.content

    return StreamingResponse(generate(), media_type="text/event-stream")

2. FastAPI 개발을 위한 Docker 바인드 마운트와 패키지 설치 정리#

무엇을 배웠나#

Docker 컨테이너와 호스트 파일 시스템은 bind mount를 통해 직접 연결되며, 파일을 복사하는 것이 아니라 실시간으로 연동된다는 점을 이해했습니다. Python 실행 환경만 제공하는 기본 이미지는 웹 서버 패키지가 포함되어 있지 않으므로, 필요한 라이브러리는 개별적으로 설치해야 합니다. 컨테이너 진입 후 pip install과 uvicorn 명령을 순차적으로 실행하면 FastAPI 프로젝트를 손쉽게 구동할 수 있습니다.

헷갈렸던 점#

Docker 실습 초기에 호스트 폴더와 컨테이너 경로 연결 방식이 파일 복사와 혼동되었습니다. python:3.14-slim 이미지는 Python 환경만 제공할 뿐 FastAPI나 Uvicorn 같은 서버 패키지가 기본 포함되지 않아, 별도 설치가 필요하다는 점이 명확하지 않았습니다.

정리된 이해#

Docker 컨테이너는 호스트 폴더와 경로를 연결하는 바인드 마운트를 통해 실시간으로 파일을 공유하며, python:3.14-slim 이미지는 기본적으로 FastAPI나 Uvicorn을 포함하지 않으므로 필요한 패키지는 별도로 설치해야 한다.

# Dockerfile 예시 (컨테이너 환경 설정)
FROM python:3.14-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY . .

CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]

3. Docker 네트워크와 404 디버깅: localhost 오해 풀기#

무엇을 배웠나#

FastAPI 컨테이너 내 localhost는 컨테이너 자체를 의미하며, 호스트와의 연결을 위해서는 Docker 포트 매핑(-p)이 필수적입니다. 반면 Ollama와 같은 다른 컨테이너에는 host.docker.internal를 통해 호스트 네트워크에 접속해야 합니다. 또한 Ctrl+C는 서버 중지 명령이지 요청 취소 명령이 아니라는 점도 확인했습니다.

헷갈렸던 점#

컨테이너 내부에서 localhost는 자기 자신을 의미한다는 사실을 간과하여, 다른 컨테이너(예: Ollama)에는 접근할 수 없다고 잘못 생각했습니다. 또한 서버가 시작되지 않았을 때 호스트와 컨테이너 간의 연결 실패로 단정하기보다, 실제로는 404 에러가 발생하며 요청은 도달하고 있음을 확인했습니다. 마지막으로 Ctrl+C가 Uvicorn 프로세스를 중지하는 명령이지, 조회를 취소하는 명령어는 아니라는 점을 간과했습니다.

정리된 이해#

컨테이너 내부에서 localhost는 자기 자신을 의미하므로, 다른 컨테이너나 호스트에 직접 접속할 수 없습니다. 따라서 호스트와 컨테이너 간 통신에는 Docker의 포트 매핑(-p)이 필수적이며, 서로 다른 컨테이너 간 연결은 host.docker.internal과 같은 특수한 도메인을 통해 호스트를 경유해야 합니다.

# Uvicorn 실행 예시
uvicorn main:app --host 0.0.0.0 --port 8000

# Docker 포트 매핑으로 호스트 접속 시
docker run -p 80:8000 <이미지명>

4. RAG 웹서비스 재사용 핵심 이해하기#

무엇을 배웠나#

RAG 시스템은 PDF 업로드 후 텍스트를 청킹하고 임베딩하여 벡터 DB에 저장한 뒤, 질의 시 유사한 문서를 검색해 답변을 생성하는 구조다. 핵심 개념인 청킹, 임베딩, ChromaDB가 어떻게 연동되는지 이해하면 코드 작성 시 데이터 흐름을 명확히 파악할 수 있다. 특히 상대 경로와 모델 변경 시 기존 데이터가 영향을 받을 수 있다는 점을 주의해야 한다.

헷갈렸던 점#

처음 RAG를 접했을 때는 단순한 질문-응답 서비스라고 생각했으나, PDF 업로드부터 텍스트 분할, 벡터 데이터베이스 저장까지 연관된 개념들이 한 번에 등장해 감이 잡히지 않았다. 특히 chromadb나 langchain-chroma 같은 추가 패키지가 왜 필요한지, 임베딩 모델을 변경하면 기존 데이터는 어떻게 되는지 이해하는 데 어려움이 있었다. 또한 강사님의 코드를 그대로 사용하더라도 Docker 환경에서 경로가 변하거나 모델이 달라지면 시스템 전체가 꼬일 수 있어, 상대경로인 ./store가 실행 위치에 따라 데이터를 잃을 위험이 있다는 점이 가장 결정적인 혼란 요소였다.

정리된 이해#

RAG 시스템은 PDF 업로드를 통해 텍스트를 추출하고 적절한 크기로 청킹한 뒤, 임베딩 모델을 이용해 벡터 형태로 변환하여 ChromaDB에 저장한다. 사용자의 질의와 가장 유사한 벡터를 검색해 답변을 생성하는 방식으로, 패키지 설치뿐만 아니라 경로 설정과 모델 호환성 관리가 필수적이다.

# PDF 업로드 및 텍스트 전처리 (청킹)
from langchain_community.document_loaders import PyPDFLoader
from langchain.text_splitter import RecursiveCharacterTextSplitter

loader = PyPDFLoader("경로/파일명.pdf")
documents = loader.load()

text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,     # 청크 크기 (예: 150자 ~ 500자)
    chunk_overlap=50, # 문맥 유지를 위한 겹치는 구간
    separators=["\n", " ", ""]
)
chunks = text_splitter.split_documents(documents)

# 임베딩 및 ChromaDB 저장
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

embeddings = OpenAIEmbeddings(model="text-embedding-3-large") # 또는 bge-m3 등
vectordb = Chroma.from_documents(
    documents=chunks,
    embedding=embeddings,
    persist_directory="./store" # 상대경로 주의
)

# 질문 시 유사 문서 검색 및 답변 생성
from langchain.chains import RetrievalQA
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model_name="gpt-4o-mini", temperature=0)
retriever = vectordb.as_retriever(search_kwargs={"k": 5}) # 상위 5개 청크 검색

qa_chain = RetrievalQA.from_chain_type(
    llm=llm,
    chain_type="stuff",
    retriever=retriever
)

result = qa_chain.invoke({"query": "사용자 질문 내용"})
print(result["result"])

5. 컨테이너 자동화와 쉘 문법 이해하기#

무엇을 배웠나#

파일명에 현혹되지 않고 실제 명령어의 성격과 실행 환경을 구분하는 것이 중요하다는 점을 배웠다. sh -c 옵션이 붙은 Docker 명령어는 리눅스/bash 환경에서 동작하며, Windows PowerShell에서는 구조적 오류가 발생할 수 있다. 또한 네트워크 주소는 고정값이 아니므로 내 로컬 환경의 구성에 맞게 대안을 검토해야 한다는 점을 깨달았다.

헷갈렸던 점#

05_command.sh 파일명이 Bash 환경을 의미한다고 잘못 가정하여, Windows PowerShell에서 sh -c 구문을 그대로 실행하려다 구조적 오류에 빠질 뻔했다.

Docker 컨테이너 내부와 외부 네트워크 환경 간의 주소 매핑(172.17.0.1:11435)이 로컬 구성에 따라 달라진다는 점을 간과하여, 단순히 IP를 복사하기보다는 실제 네트워크 구성을 이해하려 노력해야 한다는 점을 깨달았다.

컨테이너 실행 명령어에서 -w, sh -c, &&와 같은 옵션들이 각기 다른 기능(작업 디렉터리 지정, 셸 전달, 전제 조건 충족 시 다음 명령어 실행)을 수행한다는 사실을 명확히 구분하여 이해해야 한다.

정리된 이해#

sh -c 옵션은 파일 확장자가 .sh인 것과 상관없이 셸 환경에서 문자열을 실행하도록 지시하는 역할이며, && 연산자는 전 단계 명령어의 성공 여부에 따라 다음 명령을 이어서 수행하여 컨테이너 내부 작업 흐름을 제어한다.

sh -c "pip install -r requirements.txt && uvicorn main:app --host 0.0.0.0 --port 8000"

6. Docker 네트워크와 localhost 오해 정리#

무엇을 배웠나#

Docker 컨테이너 내부와 호스트 머신의 localhost가 별개의 네트워크 공간을 가지므로, 포트 번호가 같아도 접속 주소가 달라져 404 에러 등 연결 실패를 유발한다는 점을 명확히 이해하게 되었다. 또한 EXPOSE나 -p 옵션만으로는 실제 서비스 접근 경로가 결정되지 않으며, 호스트 측 네트워크 환경과 컨테이너 내부 설정이 어떻게 결합되는지 꼼꼼히 확인해야 한다는 사실도 깨달았다. 지금까지의 과정은 모델 API와의 end-to-end 연동 검증은 진행되지 않은 상태였지만, 실패 과정을 보존하고 정리하는 것이 학습에 큰 도움이 된다는 점을 깨닫게 되었다.

헷갈렸던 점#

Docker 컨테이너 내부와 호스트 머신의 localhost가 별개의 네트워크 공간을 가지므로, 익숙한 127.0.0.1:8000 주소를 입력하면 연결되지 않아 서버 오류로 오해하기 쉽습니다. 또한 Dockerfile의 포트 매핑이 있어도 실제 접근 경로는 호스트 환경과 컨테이너 내부 설정이 결합된 결과이므로, “같은 포트번호라도 주소가 다르다"는 사실이 가장 중요한 버그 포인트가 되었습니다.

정리된 이해#

Docker 컨테이너 내부와 호스트 머신의 localhost는 별개의 네트워크 공간을 가지므로, 포트 번호가 같아도 접속 주소가 달라집니다. 따라서 Docker 기반 학습에서는 컨테이너 내 서비스 접근 시 호스트 IP와 포트 매핑 설정을 정확히 확인하는 것이 가장 중요한 버그 포인트가 됩니다.

# Docker 컨테이너 내부 FastAPI 실행 시 호스트 접속을 위한 설정 예시

from fastapi import FastAPI

app = FastAPI()

@app.get("/")
async def root():
    return {"message": "Hello from Docker Container"}

if __name__ == "__main__":
    # Docker 내부에서는 0.0.0.0으로 바인딩해야 외부(호스트) 접속 가능
    import uvicorn
    uvicorn.run(app, host="0.0.0.0", port=8000)

총평#

오늘 오후 전체에서 배운 것#

Docker 환경에서는 컨테이너 내부와 호스트 네트워크가 분리되어 localhost 개념이 달라지므로, 포트 매핑과 base_url 설정 등 정확한 네트워크 경로 설정이 필수적임을 깨달았다. 또한 기본 이미지에 포함되지 않은 패키지를 개별 설치하고, 파일 시스템을 실시간으로 연동하는 바인드 마운트의 특성을 이해하여 개발 환경을 효율적으로 구축할 수 있었다. 마지막으로 RAG 시스템의 데이터 흐름과 컨테이너 명령어의 실행 환경 차이를 정확히 구분하는 것이 향후 프로젝트 적용 시 중요한 기준점이 되었다.

다음에 조심할 것#

Docker 환경에서는 컨테이너 내부 localhost와 호스트 네트워크를 명확히 구분하여 포트 매핑 여부를 반드시 확인해야 하며, 파일 경로와 옵션을 정확히 분리해두는 것이 서버 구축의 안정성을 높인다. 또한 RAG 시스템 구축 시 상대 경로와 모델 변경이 기존 데이터에 미칠 영향을 검토하고, sh -c 명령어 사용 시 운영체제별 구조적 차이를 반드시 인지해야 한다.
