1. custom model head와 backbone의 역할 분담 and [CLS] 벡터 흐름 이해#

무엇을 배웠나#

처음에는 pipeline() 한 줄이 어떻게 동작하는지 막막했지만, 모델 내부 구조를 분해해 보니 Head는 단순히 붙이는 것이 아니라 Backbone이 만든 벡터를 가공하는 공정이라는 점을 깨닫게 되었다. 특히 [CLS] 토큰을 통해 문장 전체의 의미를 대표하는 벡터로 추출하는 과정이 핵심임을 이해하게 되었고, 코드 한 줄 안에 숨겨진 데이터 흐름을 정확히 파악할 수 있게 되어 모델 구조에 대한 감이 잡혔다.

헷갈렸던 점#

  1. Head는 단순히 모델 위에 얹히는 부품이 아니라, Backbone이 만든 벡터를 가공하여 최종 결과를 도출하는 별도의 처리 공정이다.
  2. return self.custom_head(cls_vec) 한 줄 안에는 데이터가 Backbone을 통과한 후 Head로 이동하는 흐름과 결과 반환이라는 두 단계가 압축되어 있어, 데이터의 이동 경로가 불명확했다.
  3. 모델 구조를 이해하려면 Backbone이 원재료를 가공하는 ‘공장 본체’이고, Head는 최종 상품을 만들어내는 ‘마지막 공정’으로 구분하여 생각하는 것이 정확하다.

정리된 이해#

Backbone은 입력 텍스트를 특징 벡터로 가공하는 공장이며, Head는 그 벡터를 바탕으로 최종 분류 결과를 도출해내는 마지막 공정이다. Backbone이 만든 대표 벡터([CLS] 토큰)를 Head에 전달해야만 사용자 정의 로직에 따라 정확한 결과가 출력된다.

# [CLS] 토큰 추출 및 Custom Head 통과 흐름 (코드 기반)

# 1. Backbone을 통한 특징 벡터 추출
# last_hidden_state shape: (batch_size, sequence_length, hidden_dim)
last_hidden_state = backbone(input_ids=input_ids, attention_mask=attention_mask).last_hidden_state

# 2. [CLS] 토큰의 마지막 히든스테이트만 추출하여 문장 전체 벡터로 활용
# [:, 0, :]는 시퀀스의 첫 번째 토큰([CLS])을 의미합니다.
cls_vec = last_hidden_state[:, 0, :]

# 3. Custom Head를 통과시켜 최종 분류 결과(Logits) 도출
output = custom_head(cls_vec)

2. config로 정의한 라벨의 의미와 학습 과정 구분#

무엇을 배웠나#

config 설정을 통해 모델의 출력 구조를 정의하는 것과, 실제 가중치를 조정하며 학습하는 과정은 별개라는 점을 명확히 이해할 수 있었습니다. 특히 num_labels와 id2label이 모델 내부 지식 습득을 자동으로 유도하지는 않으며, 단순히 결과 해석을 위한 규격만 설정한다는 사실을 깨닫고 코딩 시 자동완성 오류에 휘말리지 않고 정확한 용어를 사용하는 중요성을 느꼈습니다.

헷갈렸던 점#

config 설정을 바꾸는 것만으로 모델이 긍정과 부정 개념을 저절로 습득하는 것처럼 느껴져서, 설정과 학습의 경계를 구분하기 어려웠습니다.

또 자동완성 기능에 의존하다가 input_ides, max_lengeth 등 의도치 않은 오타가 코드 실행에 방해가 되어, 정확한 용어 사용의 중요성을 실감했습니다.

핵심은 ‘규격 정의’와 ‘학습 과정’을 분리하는 것입니다. config.num_labels = 2는 모델 출력 레이어의 스펙을 정하는 것이고, 실제 학습은 문장을 보고 가중치를 조정하여 긍정과 부정을 구분하는 별도 과정이기 때문입니다.

정리된 이해#

config는 모델이 긍정과 부정이라는 개념을 스스로 학습하게 하는 것이 아니라, 출력 레이어가 2개라는 규격(스펙)을 정의하고 각 숫자가 NEG와 POS 중 무엇을 의미하는지 이름표를 붙이는 역할입니다. 실제 학습은 문장을 보고 가중치를 조정하여 긍정과 부정의 차이를 구분하는 별도 과정이며, config 설정을 했다고 모델이 즉시 지식을 습득하는 것은 아닙니다.

# 1. config에 라벨 규격 정의
config.num_labels = 2
config.id2label = {0: "NEG", 1: "POS"}
config.label2id = {"NEG": 0, "POS": 1}
config.problem_type = "single_label_classification"

# 2. Head 레이어는 config와 연결
nn.Linear

3. Softmax와 확률의 오해, 그리고 모델의 한계#

무엇을 배웠나#

Softmax는 모델이 이미 학습한 점수의 질을 확률 형태로 변환할 뿐, 정답 확률을 높여주지는 않는다는 점을 깨달았다. 특히 logits가 거의 비슷할 때 argmax 결과가 달라 보여도, 실제 점수 차이가 크지 않다는 사실을 통해 Softmax의 본질을 정확히 이해할 수 있었다. 모델이 아직 NEG와 POS를 구분할 패턴을 학습하지 못했다면, 아무리 헤드를 조정해도 Softmax는 단순히 점수를 재분배하는 수준에 그칠 것임을 깨닫게 되었다.

헷갈렸던 점#

Softmax는 모델이 이미 결정한 점수를 확률 형태로 변환할 뿐, 정답을 맞히게 만들어주지 않는다는 점을 깨달았습니다. 특히 두 문장의 점수가 51:49로 엎치락뒤치락하자, 모델이 잘못 판단한 줄 알았지만 실제로는 학습된 패턴의 차이였습니다. 결국 argmax가 선택한 라벨이 정답인지는 logits의 격차에 달려 있으며, Softmax는 그 결과를 해석하는 도구일 뿐 결정적인 요인이 되지 않습니다.

정리된 이해#

Softmax는 모델이 이미 결정한 점수(logits)를 0~1 사이의 확률 형태로 변환할 뿐, 점수의 질 자체를 높여주거나 정답을 보정해주는 함수가 아니다. 따라서 Softmax를 통과한 확률 값이 5:5 수준이라도, 해당 클래스가 실제로는 더 높은 점수를 받았음을 의미하며 argmax 결과가 틀린 경우 모델의 학습 부족으로 인한 분류 오류임을 이해해야 한다.

# Softmax 적용 전의 원시 점수 (Logits)
logits = torch.tensor([[0.1, -0.2]])  # 예: NEG와 POS에 대한 원시 점수

# Softmax를 통과하여 확률로 변환
probabilities = torch.nn.functional.softmax(logits, dim=1)

# 가장 높은 점수를 가진 클래스 선택 (ArgMax)
predicted_class_id = torch.argmax(probabilities, dim=1).item()

print(f"Logits: {logits.tolist()}")
print(f"Probabilities: {probabilities.tolist()}")
print(f"Predicted Class ID: {predicted_class_id}")  # 결과: 0 또는 1

4. 앙상블 기법의 이해: Soft Voting과 Weighted Average#

무엇을 배웠나#

Soft Voting은 모든 모델을 동등하게 취급해 점수를 평균내는 방식이며, Weighted Average는 신뢰도에 따라 가중치를 부여해 결과에 반영한다는 점이 가장 큰 차이점이다. 특히 가중치의 기준을 어디에 두느냐가 결과의 정확도를 결정짓는 핵심 열쇠라는 점을 깨닫고, 단순히 다수결이 아님을 명확히 이해하게 되었다. 아직 모델 간의 우열을 객관적으로 판단하는 기준이 부족해 가중치 부여에 시행착오를 겪을 수 있지만, 신뢰도 조절의 중요성을 깊이 새긴 계기가 되었다.

헷갈렸던 점#

Soft Voting은 모델들이 모두 틀려도 평균값이 도출된다는 점에서 단순한 다수결과 다르며, Weighted Average는 신뢰도에 따른 가중치 부여가 결과에 직접적인 영향을 미쳐 어떤 모델을 우대할지가 관건임을 깨달았다.

정리된 이해#

Soft Voting은 모든 모델을 동등하게 취급해 점수를 평균내는 방식이며, Weighted Average는 신뢰도에 따라 가중치를 부여해 각 모델의 기여도를 다르게 반영하는 방법이다.

# Soft Voting: 모든 모델을 동등하게 평균내는 방식
soft_voting_result = (pred_1 + pred_2 + pred_3) / 3

# Weighted Average: 신뢰도(가중치)가 다른 모델들의 점수를 비율에 맞게 가산하는 방식
weighted_avg_result = (pred_1 * w_1 + pred_2 * w_2 + pred_3 * w_3) / (w_1 + w_2 + w_3)

총평#

오늘 오전 전체에서 배운 것#

[CLS] 토큰을 통한 문장 의미 추출과 Backbone이 만든 벡터를 가공하는 Head의 역할 분담을 명확히 이해했으며, num_labels 설정은 결과 해석을 위한 규격일 뿐 자동 학습을 유도하지 않는다는 점을 깨닫고 용어 사용에 신중하게 임하게 되었다. 또한 Softmax가 점수 재분배 수준임을 인지하고, 모델이 아직 구분 패턴을 학습하지 못했다면 헤드 조정만으로는 한계가 있음을 깨닫고 신뢰도를 고려한 가중치 조절의 중요성을 새롭게 인식하였다.

다음에 조심할 것#

  • [CLS] 벡터 추출 과정을 단순 연결이 아닌, 백본이 만든 특징을 가공하는 핵심 단계로 인식하고 코드 흐름을 정확히 따라가야겠다.
  • num_labels나 id2label 설정이 모델 학습 자체를 자동으로 보장하지 않는다는 점을 명확히 인지하여, 라벨 정의와 학습 파라미터 설정을 별개로 관리해야 한다.
  • Softmax가 점수를 재분배하는 역할임을 기억하고, 아직 패턴을 학습하지 못한 모델에 헤드만 의존하면 한계에 부딪힐 수 있음을 인지해 데이터 품질과 모델의 학습 상태를 먼저 점검해야겠다.

다음 복습 주제#

  1. Backbone과 Head의 데이터 흐름 재정리: [CLS] 벡터가 어떻게 Backbone에서 추출되어 Head로 전달되는지, 그리고 Head 내부에서 어떤 연산을 거쳐 최종 출력이 만들어지는지 전체적인 파이프라인 시각화를 통해 다시 한번 점검한다.

  2. 라벨 매핑과 모델 학습의 관계 이해: num_labels나 id2label 설정이 모델의 실제 학습 능력에 직접적인 영향을 미치지 않는다는 점을 명확히 인지하고, 라벨 정의는 결과 해석을 위한 사후 작업임을 확실히 하여 코딩 시 혼동을 피하는 습관을 기른다.

  3. Softmax와 확률 해석의 정확성: Softmax가 점수를 재분배하는 과정임을 인식하고, 모델이 아직 학습하지 못한 클래스 간의 구분이 확실하지 않을 경우 argmax 결과가 달라 보여도 실제 점수 차이가 미미할 수 있음을 감안하여 확률 값을 맹신하지 않고 신중하게 해석하는 안목을 기른다.
