1. 청킹은 검색 단위를 설계하는 일#

무엇을 배웠나#

청킹은 문서를 단순히 잘게 쪼개는 절단 작업이 아니라, 검색 단위를 설계하는 설계 과정입니다. 청크 크기가 너무 크면 여러 문맥이 뒤섞여 노이즈가 되고, 너무 작으면 필요한 정보가 하나의 청크에 들어가지 못해 검색 실패로 이어질 수 있습니다. 따라서 적절한 청크 크기와 오버랩은 데이터와 질문 유형에 따라 실험을 통해 검증해야 하는 critical한 단계입니다.

헷갈렸던 점#

청킹은 단순히 문서를 잘게 쪼개는 절단 작업이 아니라, 검색 단위를 설계하는 설계 과정입니다. 핵심은 적절한 청크 크기가 데이터와 질문 유형에 따라 달라진다는 점이며, 정답 크기는 존재하지 않으므로 실험을 통해 검증해야 합니다. overlap은 경계에서의 문맥 끊김을 막기 위한 완충지대 역할을 합니다.

정리된 이해#

청킹은 문서를 단순히 자르는 절단 작업이 아니라, 검색 결과가 담아야 할 문맥의 범위를 설계하는 과정입니다. 청크 크기는 데이터와 질문 유형에 따라 달라지며, 너무 크면 노이즈가 되고 너무 작으면 필요한 정보가 검색되지 않을 수 있습니다. 따라서 적절한 청크 크기와 오버랩 설정을 통해 검색 품질을 최적화해야 합니다.

from langchain.text_splitter import RecursiveCharacterTextSplitter

# 문서 로드 (예시)
documents = [
    "인공지능은 현대 기술의 핵심입니다. 머신러닝과 딥러닝을 통해 다양한 문제를 해결합니다.",
    "자연어 처리(NLP)는 컴퓨터가 인간의 언어를 이해하고 처리하도록 돕습니다.",
    "검색 증강 생성(RAG)은 언어 모델에 외부 지식을 제공하여 정확도를 높이는 기법입니다."
]

# 청킹 설정 (토큰 수 기준 approximate)
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,  # 청크 크기: 토큰 약 350-400개 수준
    chunk_overlap=50, # 오버랩: 인접 청크 간 문맥 연결을 위한 버퍼
    separators=["\n\n", "\n", " ", ""]
)

# 청킹 적용
chunks = text_splitter.split_documents(documents)

print(f"원본 문서 수: {len(documents)}")
print(f"청크 수: {len(chunks)}")
for i, chunk in enumerate(chunks):
    print(f"- 청크 {i+1}: {chunk.page_content[:80]}...")

2. 임베딩과 top-k, 검색 품질을 좌우하는 두 가지 레버#

무엇을 배웠나#

임베딩 모델은 검색 기준이 되는 의미적 거리를 결정하고, top-k는 그 결과를 몇 개까지 다음 단계로 넘길지를 정하는 서로 다른 두 개의 레버라는 점을 명확히 이해했습니다. k를 늘리는 것은 단순히 좋은 문서를 더 찾는 것이 아니라, 관련성이 약한 후보까지 섞일 위험이 있다는 점도 함께 인식하게 되었습니다.

헷갈렸던 점#

임베딩 모델은 ‘무엇을 의미상으로 가깝게 볼지’를 결정하는 기준이지만, top-k는 가져올 후보의 개수를 조절하는 역할이며, k를 늘리는 것만으로 검색 품질이 자동 좋아지는 것은 아니다.

정리된 이해#

임베딩 모델은 검색 기준을 결정하고, top-k는 가져올 후보의 수를 조절하는 서로 다른 역할을 합니다. k를 늘리면 더 많은 문서를 확보할 수 있지만 정답률이 자동으로 높아지는 것은 아닙니다. 임베딩 모델과 top-k는 검색 품질을 각각 다른 방식으로 조정하는 두 개의 레버입니다.

# top-k 비교 실험 (동일 모델 내)
results_k1 = search(query, k=1)  # 상위 1개만 반환
results_k3 = search(query, k=3)  # 상위 3개 반환

# 임베딩 모델 비교 실험 (k=1 고정)
results_model_a = search(query, k=1, model="intfloat/multilingual-e5-small")
results_model_b = search(query, k=1, model="sentence-transformers/all-MiniLM-L6-v2")

3. BM25와 벡터 검색의 융합, RRF 알고리즘 이해하기#

무엇을 배웠나#

BM25와 벡터 검색은 단순한 결합을 넘어, 서로 다른 매커니즘을 가진 두 방식이 어떻게 상호 보완되는지를 이해하는 것이 핵심이었다. 특히 k라는 기호가 검색 결과 수와 RRF 가중치 조절이라는 완전히 다른 역할을 한다는 점은 혼동을 줄 만한 대목이었다. 또한 BM25가 단순히 단어 매칭을 넘어 토큰화 전략, 특히 한국어 형태소 분석의 필요성을 요구한다는 점이 lexical search의 섬세함을 보여주었다. finally, Hybrid Search는 두 검색 결과를 단순히 나열하는 것이 아니라 RRF 같은 공식으로 순위를 통합하는 정교한 구조임을 명확히 할 수 있었다.

헷갈렸던 점#

처음에는 k라는 기호가 검색 결과 수와 점수 보정 상수를 모두 뜻한다는 점이 가장 큰 혼란이었습니다. 또한 BM25를 단순한 ‘단어 맞추기’로 생각하다가, 한국어 사용을 위해 형태소 분석이 필요하다는 점을 간과하고 있었습니다. 마지막으로 Hybrid Search를 단순히 두 방식을 동시에 돌리는 것으로 오해했으나, 실제로는 결과를 융합하는 정교한 구조라는 사실을 새롭게 깨달았습니다.

정리된 이해#

BM25는 정확한 단어 일치에 강점을 보이는 lexical search이며, Vector Search는 의미적 유사성을 기반으로 한 semantic search입니다. Hybrid Search는 이 두 방식의 결과를 RRF 같은 공식으로 융합하여 검색 성능을 보완하는 구조입니다.

# BM25와 Vector Search를 결합한 Hybrid Search (RRF) 예시

# 1. 개별 검색 결과 가져오기
bm25_results = bm25_retriever.search(query, top_k=10)
vector_results = vector_store.similarity_search(query, k=10)

# 2. RRF (Reciprocal Rank Fusion) 점수 계산
def rrf_fusion(results_list, k=60):
    """
    results_list: 검색 방식별 결과 리스트 [(doc_id, rank), ...]
    k: RRF 보정 상수 (기본값 60)
    """
    score_map = {}

    for rank, (doc_id, _) in enumerate(results_list, start=1):
        # RRF 공식: 1 / (k + rank)
        score = 1 / (k + rank)
        if doc_id not in score_map:
            score_map[doc_id] = 0.0
        score_map[doc_id] += score

    # 점수 기준으로 정렬
    fused_results = sorted(score_map.items(), key=lambda x: x[1], reverse=True)
    return fused_results

# 3. 결과 융합 및 최종 반환
fused = rrf_fusion([bm25_results, vector_results])
final_doc_ids = [doc_id for doc_id, _ in fused[:top_k]]

총평#

오늘 오전 전체에서 배운 것#

청킹은 문서를 단순히 잘게 쪼개는 것이 아니라, 검색 단위를 설계하는 중요한 과정이며 적절한 크기와 오버랩을 찾는 것은 데이터와 질문 유형에 따라 실험을 통해 검증해야 합니다. 임베딩 모델과 top-k는 의미적 거리와 결과의 범위를 결정하는 서로 다른 두 레버로서, k를 늘리는 것은 관련성이 약한 후보까지 섞일 위험이 있다는 점을 인지하게 되었습니다. BM25와 벡터 검색은 각기 다른 매커니즘을 가지며 RRF 알고리즘을 통해 통합 순위가 산출되며, 특히 한국어 형태소 분석 등 정교한 전처리가 lexical search의 성능을 좌우한다는 점을 이해할 수 있었습니다.

다음에 조심할 것#

청킹은 단순한 단절이 아니라 검색 성능을 결정짓는 설계 과정임을 명심하고, 데이터와 질문 유형에 맞춰 크기와 오버랩을 실험적으로 최적화해야 합니다. 또한 임베딩 모델과 top-k 파라미터가 의미적 거리와 결과의 양을 각각 조절하는 레버 역할을 한다는 점을 인식하여, k값 증가가 단순히 많은 결과를 가져오는 것이 아니라 노이즈를 유발할 수 있음을 항상 경계해야 합니다.

다음 복습 주제#

청킹 전략이 검색 성능에 미치는 영향을 구체적으로 이해하는 것이 시급합니다. 단순히 문서를 쪼개는 수준을 넘어, 질문의 의도와 데이터 특성에 맞는 최적의 청크 크기와 오버랩 설정을 어떻게 실험하며 검증할지 방법을 고민해야 합니다.

임베딩 모델과 top-k 파라미터가 검색 품질에 미치는 미묘한 영향을 명확히 구분하는 연습이 필요합니다. k 값을 조정했을 때 관련성이 높은 문서뿐만 아니라 노이즈가 섞이는 현상을 어떻게 제어하고 균형을 잡을지, 실제 검색 결과에서 어떤 트레이드오프가 발생하는지 시뮬레이션해보는 과정이 필요합니다.

BM25와 벡터 검색의 장점을 효과적으로 융합하기 위한 구체적인 하이브리드 검색 구현 로직을 심화해야 합니다. RRF 알고리즘의 작동 원리와 파라미터 설정, 그리고 한국어 처리를 위한 형태소 분석 등 lexical search의 세부 사항이 검색 정확도에 미치는 영향을 체계적으로 정리하고 적용해보는 연습을 이어가야 합니다.
