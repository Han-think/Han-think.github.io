1. 파일명 충돌 방지, 확장자 점(.) 처리하기#

무엇을 배웠나#

오늘 FastAPI 파일 업로드 실습을 진행하며, 확장자 처리 시 점(.) 포함 여부가 파일명 생성 로직에 직접적인 영향을 미친다는 점을 명확히 깨달았습니다. ext 변수에 점이 이미 포함되어 있어 UUID와 합칠 때 중복되지 않도록 주의해야 한다는 사실을 깨닫고 코드를 수정했습니다. 이러한 작은 문자열 조합 실수가 실제 파일 경로 처리에서 오류의 원인이 된다는 점을 인지하고, 앞으로는 확장자 처리에 더욱 신중을 기할 것입니다.

헷갈렸던 점#

파일명 생성 시 확장자 앞에 점(.)이 이미 포함되어 있는지 확인하지 않아, UUID와 합쳐질 때 중복된 점이 발생하거나 파일명이 깨지는 오류를 범했다.

확장자를 분리하는 과정 자체가 간단해 보여도, 그 변수에 포함된 문자열의 형태가 실제 파일 경로 생성 로직에 직접적인 영향을 미친다는 점을 간과한 것이 실수의 근본 원인였다.

작성 당시에는 ‘점 찍기’가 당연한 습관으로 여겼으나, 시스템 관점에서 확장자 처리 방식이 파일 인식에 결정적 변수가 된다는 사실을 깨닫고 나니 단순한 문자열 조합에도 신중을 기해야 한다는 교훈을 얻었다.

정리된 이해#

파일 업로드 시 확장자 앞에 점이 포함되어 있는지 반드시 확인해야 하며, UUID와 확장자를 점 없이 연결해 파일명을 생성해야 충돌을 방지하고 정상적인 저장이 가능하다. FileResponse를 활용한 다운로드 구현과 Axios를 통한 동적 HTML 생성을 통해 파일 목록의 조회, 삭제, 다운로드 기능을 완성할 수 있다.

# ✅ 수정된 코드 (점 없이 바로 연결)
f'{uuid.uuid4()}{ext}'   # 결과: "a1b2c3.jpg"

2. APScheduler Job 제어: Scheduler와 Job의 생명주기 분리#

무엇을 배웠나#

APScheduler는 전체 스위치가 아닌 ‘전체’와 ‘개별 Job’을 분리해 관리하는 구조라는 점을 명확히 이해할 수 있었다. 특히 shutdown()이 완전 종료가 아니라 재시작이 필요한 해체 작업임을 깨닫고, 일시정지 제어를 위해 pause()와 resume_job()를 적절히 사용해야 한다는 가이드를 얻었다. 마지막으로 date와 interval 표현식이 예약의 지속 시간과 빈도를 구분한다는 점도 중요한 학습 포인트가 되었다.

헷갈렸던 점#

Scheduler 전체를 제어하는 start()와 stop()이 아닌, 개별 Job을 일시정지·재개할 수 있는 pause_job()와 resume_job() 메서드가 존재한다는 점이 가장 큰 혼란 포인트였습니다.

특히 shutdown()이라는 메서드 이름이 주는 함정이 컸는데, “멈추다"라는 직관적인 의미와 달리 실제로는 Scheduler를 완전히 해체하는 종료 동작이었으며, 재개를 위해서는 다시 start()를 호출해야 한다는 점이었습니다.

크론 표현식에서 date는 단발성 예약(한 번만 실행), interval은 주기적 반복(정해진 간격마다 실행)을 의미한다는 점도 중요한 구분 요소였습니다.

정리된 이해#

APScheduler는 전체 스위치가 아닌 ‘무대’와 ‘배역’으로 구분해 관리한다. start()로 스케줄러를 켜고, pause()와 resume_job()으로 개별 작업의 가동을 제어할 수 있다. 특히 shutdown()은 완전 종료가 아니라 재시작을 전제로 한 해체이므로, 일시정지는 pause()를 사용하는 것이 정확하다.

from apscheduler.schedulers.background import BackgroundScheduler

scheduler = BackgroundScheduler()

# Scheduler 시작 (전체 스위치)
scheduler.start()

# 특정 Job 일시정지 (개별 스위치)
scheduler.pause_job(job_id='task_1')

# 특정 Job 재개
scheduler.resume_job(job_id='task_1')

# Scheduler 전체 종료 (완전 종료)
scheduler.shutdown()

3. shutdown pause resume recreate 이해하기#

무엇을 배웠나#

start, stop, shutdown은 단순히 실행과 중단의 대칭 관계가 아니라, lifecycle(수명 주기)의 차이를 의미합니다. pause와 resume는 scheduler 인스턴스를 유지한 채 일시정지와 재개를 반복하는 반면, shutdown은 인스턴스를 완전히 소멸시켜 /start 버튼을 눌러도 기존 객체가 살아나지 않습니다. 따라서 shutdown 후 scheduler를 다시 작동시키려면 전역 변수 등을 통해 새로운 객체를 생성하는 패턴이 필수적입니다.

헷갈렸던 점#

pause와 shutdown이 단순히 실행과 중단의 차원이 아니라, scheduler 인스턴스를 유지하는가 소멸시키는가의 문제라는 점이 가장 큰 혼란 포인트였습니다. /stop 버튼을 누른 뒤 /start를 다시 눌렀는데 scheduler가 살아나지 않아 “버그인가?“라고 생각했던 것이 결정적인 계기가 되었습니다. 결국 shutdown은 인스턴스를 완전히 없애는 행위이므로, 재실행 시 기존 객체를 재생성하는 코드 패턴이 반드시 필요하다는 점을 깨닫게 되었습니다.

정리된 이해#

pause/resume는 scheduler 인스턴스를 유지하며 일시정지했다가 재개하는 방식이지만, shutdown은 인스턴스를 완전히 소멸시킨다. 따라서 /start를 다시 실행하려면 기존 객체를 재생성하는 과정이 반드시 필요하다.

sch = None  # 전역 변수로 scheduler 인스턴스 관리

def create_scheduler():
    # 새로운 scheduler 객체 생성 및 Job 등록 등 초기화 로직
    return sch_start()

@app.get("/start")
async def start():
    global sch

    # sch가 None(없음)라면 새로 생성하고, 이미 있다면 resume
    if sch is None:
        sch = create_scheduler()
        sch.start()
    else:
        sch.resume()

    return {"msg": "scheduler 실행"}

@app.get("/stop")
async def stop():
    global sch

    # sch가 존재하면 shutdown 후 None으로 초기화
    if sch is not None:
        sch.shutdown()
        sch = None

    return {"msg": "scheduler 종료"}

4. GitHub commit 흐름과 강의 자료 일치 확인하기#

무엇을 배웠나#

오늘은 PDF 순서와 GitHub commit 이력이 일치하지 않아 코드 진행 상황을 파악하는 데 혼란이 있었습니다. 이를 해결하기 위해 개념 흐름(PDF)과 실제 코드 변화(GitHub)를 함께 확인하며 수업을 따라가야 한다는 점을 명확히 했습니다. 특히 scheduler 관련 수정 사항을 실시간으로 확인한 것이 이론보다 훨씬 구체적으로 이해되는 계기가 되었습니다.

헷갈렸던 점#

PDF 페이지 순서와 GitHub commit 번호가 일치하지 않아 현재 실습 단계 파악에 어려움이 있었습니다.

특히 수업 진행이 빠를 경우, “지금 코드가 최종본인지 중간 과정인지"를 판단하기 어렵고 혼란스러웠습니다.

commit 흐름을 PDF 개념 흐름과 대조해 보니 강의 자료와 실제 코드 이력이 잘 맞닿아 있음을 확인했습니다.

정리된 이해#

오늘은 단순히 PDF 내용을 읽는 것을 넘어, 강사님의 GitHub commit 이력을 함께 보며 실습이 어떻게 완성되는지 확인하는 시간을 가졌습니다. 가장 큰 혼란은 페이지 순서와 Git 번호가 1:1로 매칭되지 않아 현재 코드가 어느 단계인지 파악하기 어려웠던 점입니다. 앞으로는 PDF(개념 흐름)와 GitHub(실제 코드 이력)를 함께 참고하여 수업의 진행 상황과 다음 단계를 정확히 파악하는 것이 중요하다고 느꼈습니다.

→ 파일 업로드 / 이름변경

→ 사진 업로드 완성
→ 파일리스트 / 삭제 / 다운로드

→ 스케줄러 보강

5. LM Studio와 LangChain: provider-independent 구조 이해하기#

무엇을 배웠나#

LangChain은 CLI와 달리 LLM 애플리케이션을 구성하는 오케스트레이션 레이어로, 핵심 구조는 provider에 상관없이 동일하다는 점이 가장 큰 깨달음입니다. LM Studio를 사용해도 강사님의 Ollama 기반 코드 흐름을 그대로 따라갈 수 있으며, base_url과 모델 식별자만 조정하면 되므로 공급자 독립적인 학습이 가능합니다. 특히 LangChain 코드 자체는 런타임 제공층에 크게 의존하지 않으므로, 실제 사용 툴을 LM Studio로 교체해도 상위 구조의 이해에는 지장이 없습니다.

헷갈렸던 점#

처음에는 LangChain이 CLI(명령줄 인터페이스)와 비슷하다고 생각했지만, 실제로는 LLM 애플리케이션을 구성하는 오케스트레이션 레이어였습니다. 또한 Ollama를 사용하지 않아도 LM Studio로 런타임을 교체해도 코드의 상위 구조는 동일하다는 점을 깨닫고 안도했습니다. 핵심은 base_url과 모델 식별자만 달리 주면 LangChain 코드가 provider에 독립적으로 동작한다는 점입니다.

정리된 이해#

LangChain은 CLI와 달리 LLM 애플리케이션을 구성하는 오케스트레이션 및 어댑터 레이어로, 핵심 로직은 동일하게 유지하면서 base_url과 모델 식별자만 LM Studio 환경에 맞게 조정하면 Ollama 코드와 유사한 흐름을 적용할 수 있다.

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    base_url="http://localhost:1234/v1",
    api_key="lm-studio",
    model="local-model"
)

총평#

오늘 오후 전체에서 배운 것#

오늘은 FastAPI 파일 업로드 시 확장자 점(.) 처리가 로직에 미치는 영향을 파악하고, APScheduler에서 shutdown이 인스턴스 소멸임을 명확히 이해했습니다. 또한 LangChain의 provider-independent 구조를 통해 도구 교체 용이성을 확인하며, 코드 진행 상황을 위해 PDF와 GitHub 이력을 병행 확인하는 습관을 들였습니다.

다음에 조심할 것#

  • 확장자 처리 시 점(.) 포함 여부를 반드시 확인하고, UUID와 합칠 때 중복되지 않도록 문자열 조합 로직을 검증하는 습관을 들일 것이다.
  • APScheduler의 shutdown은 인스턴스를 소멸시키는 작업이므로, 재사용을 위해서는 전역 변수 등을 통해 새로운 객체를 생성하는 패턴을 반드시 적용할 것이다.

다음 복습 주제#

LangChain과 LM Studio 연동 시 provider 구조에 대한 이해가 깊어져, 실제 툴을 교체해도 핵심 로직이 유지된다는 자신감이 생겼습니다.

APScheduler의 lifecycle(수명 주기) 개념이 명확히 정리되어, 단순 on/off 스위치가 아닌 ‘재시작’과 ‘일시정지’의 차이를 정확히 구분하여 설계할 수 있게 되었습니다.

GitHub 이력과 PDF 흐름을 실시간으로 대조하며 수업 내용을 파악하는 습관을 들이면, 개념 혼동 없이 코드 진행 상황을 효율적으로 관리할 수 있을 것입니다.
