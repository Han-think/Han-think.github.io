1. Gemma 2 Intel XPU 장치 이동 및 temperature 파라미터 정리#

무엇을 배웠나#

강사님의 CUDA 코드를 그대로 따라 하려다가 장치 관리와 파라미터 용도에 대한 이해 부족으로 혼란을 겪었다. device_map="auto"는 XPU 환경에서는 자동 분산이 아닌 model.to("xpu")를 통한 명시적 이동이 필요했으며, temperature는 모델 생성 옵션임이 확인되었다. 결국 최소한의 수정만으로도 XPU에서 Gemma 2를 성공적으로 구동할 수 있었다.

헷갈렸던 점#

CUDA 코드를 그대로 따라 하려다가 XPU 환경과의 호환성 차이로 막막함을 느꼈다. 특히 device_map="auto" 옵션이 XPU에서도 유효한지, 그리고 temperature가 파이썬 임포트인지 생성 파라미터인지가 명확하지 않아 혼란스러웠다. 강사님의 CUDA 흐름을 유지하면서 model.to("xpu")로 장치를 명시적으로 이동시키고, temperature가 generate() 함수 옵션임을 파악했다.

정리된 이해#

XPU 환경에서는 model.to("xpu")를 통해 모델과 텐서를 명시적으로 같은 장치에 올리는 것이 핵심이며, temperature는 generate() 함수 내부의 생성 파라미터로서 답변의 일관성이나 다양성을 조절하는 역할을 한다.

# 장치 이동 전략: 모델을 Intel XPU에 명시적으로 올리는 방식
model.to("xpu")

# generate 시 temperature 파라미터 사용 예시
outputs = model.generate(
    **inputs,
    max_new_tokens=256,
    temperature=0.7,
    do_sample=True
)

2. 입력과 답변을 분리하는 slicing 과정#

무엇을 배웠나#

생성된 전체 결과에서 입력 프롬프트를 잘라내어 답변을 추출하는 것은 모델이 답변만 생성한 것이 아니라, post-processing 과정을 통해 가능하다는 점을 깨달았습니다. shape[1]을 활용해 입력 토큰의 길이를 정확히 파악하면, 생성 결과의 경계를 명확히 구분할 수 있습니다. 또한 skip_special_tokens=True 옵션은 decode 과정에서 불필요한 특수 문자를 제거하여 가독성 높은 문자열로 변환하는 역할을 한다는 점을 이해했습니다.

헷갈렸던 점#

처음에는 model.generate()가 답변을 생성하는 것인지, 아니면 전체 출력을 반환하는지 구분하지 못해 혼란스러웠습니다. 특히 outputs[0]에서 입력 토큰을 제거하고 답변만 slice하는 과정이 모델의 동작 방식 변화인지, 단순히 결과물의 전처리인지를 파악하기 어려웠습니다. 또한 skip_special_tokens=True가 토큰 ID를 문자열로 변환하는 과정인지, 아니면 답변을 걸러내는 필터 역할인지 initially 명확하지 않았습니다.

정리된 이해#

model.generate()는 모델이 답변을 생성하는 단계이며, outputs[0]은 입력 토큰과 생성된 답변 토큰이 결합된 전체 결과입니다. 따라서 “답변만 출력한다"는 것은 모델의 출력을 직접 수정하는 것이 아니라, input_length를 기준으로 outputs[0][input_length:]로 입력을 잘라내고, 남은 토큰을 tokenizer.decode()로 문자열 변환하는 전처리 과정입니다.

# 토크나이저를 통해 PyTorch Tensor 형태로 입력 받기
inputs = tokenizer(
    prompt,
    return_tensors="pt"
)

# 현재 입력 토큰의 길이 구하기 (shape 활용)
input_length = inputs["input_ids"].shape[1]

# 모델 생성 실행
outputs = model.generate(**generate_kwargs)

# 생성된 전체 결과에서 입력 프롬프트를 잘라내고 답변 부분만 선택
answer_tokens = outputs[0][input_length:]

# 선택된 token ID를 사람이 읽을 수 있는 문자열로 변환
answer_text = tokenizer.decode(answer_tokens, skip_special_tokens=True)

3. no_grad와 Sampling 파라미터의 연결 이해#

무엇을 배웠나#

torch.no_grad()는 가중치를 사용하지 않는다는 뜻이 아니라, 추론 과정에서 불필요한 그래디언트 계산을 막아 메모리 효율을 높이는 역할을 한다는 점을 명확히 이해할 수 있었다. 또한 temperature가 확률 분포의 날카로움을 조절하여 무작위성과 정답 사이의 균형을 맞춘다는 구체적인 원리를 통해, 파라미터가 모델 행동에 미치는 영향을 직관적으로 파악할 수 있게 되었다. 마지막으로 generate 메서드에서 이러한 sampling 파라미터를 함께 설정하는 것이 어떻게 효율적인 텍스트 생성을 가능하게 하는지 실전 예시를 통해 확인할 수 있었다.

헷갈렸던 점#

torch.no_grad()는 가중치 자체를 끄는 것이 아니라, 그 파라미터를 업데이트하는 그래디언트 계산을 추적하지 않음을 의미합니다. temperature는 토큰 확률 분포의 날카로움을 조절하여 무작위성과 정답 사이의 균형을 맞추는 값이며, 높을수록 창의적이고 낮아질수록 정확해지는 효과가 있습니다.

정리된 이해#

torch.no_grad()는 가중치를 사용하지 않는다는 뜻이 아니라, 추론 과정에서 불필요한 그래디언트 계산을 차단해 메모리 절약과 속도 향상을 이뤄낸다. temperature는 토큰 확률 분포의 날카로움을 조절하는 값으로, 높일수록 무작위성이 증가하고 낮출수록 정답에 가까워지는 결과를 낳는다. 따라서 추론 시에는 no_grad와 함께 temperature, do_sample 등 sampling 파라미터를 적절히 설정해 모델의 생성 성능을 최적화해야 한다.

# 추론 시 불필요한 그래프 생성을 막는 경우
with torch.no_grad():
    outputs = model.generate(
        **inputs,
        max_new_tokens=256,
        temperature=0.7,
        do_sample=True
    )

4. Hugging Face 모델 파일 구조와 샤딩 이해하기#

무엇을 배웠나#

Sharding은 거대한 가중치 파일을 여러 조각으로 나누어 저장하는 방식이며, index.json는 각 shard가 어디에 있는지 매핑해주는 안내서입니다. Model Parallelism은 나뉘어진 shard를 실제 연산을 위해 서로 다른 장치에 배치하는 것이고, device_map="auto"는 이 과정에서 모델 레이어를 자동으로 GPU에 분배해주는 기능입니다.

헷갈렸던 점#

처음에는 safetensors 파일이 단순히 여러 개로 쪼개진 저장 방식인지, 샤딩이 연산 분산 개념인지 구분하기 어려웠습니다. 특히 device_map="auto"가 단순한 장치 선택 설정이 아니라 모델 레이어 배치까지 관여한다는 사실을 알게 되어 전체적인 실행 흐름을 파악하는 데 혼란을 겪었습니다. 핵심은 거대한 가중치를 여러 조각으로 나누는 저장 구조(Sharding)와 실제 연산을 위해 파라미터를 GPU에 분배하는 연산 방식(Model Parallelism)을 분리하여 이해해야 한다는 점이 가장 크게 와닿았습니다.

정리된 이해#

Sharding은 거대한 가중치 파일을 여러 조각으로 나누어 저장하는 방식이며, index.json는 각 shard가 어디에 있는지, 어떤 키를 가지고 있는지를 매핑해주는 안내서 역할을 합니다. 반면 Model Parallelism은 이미 나뉘어진 shard들을 실제 연산을 위해 서로 다른 장치(GPU 등)에 배치하는 것이고, device_map="auto"는 이 과정에서 모델의 레이어와 파라미터를 자동으로 GPU에 분배해주는 지능형 매핑 기능입니다.

from transformers import AutoModelForCausalLM, AutoTokenizer

# 모델과 토크나이저 로딩 (sharding 구조 이해)
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.2-1B",
    low_cpu_mem_usage=True,
    device_map="auto"
)

5. KoBART XPU 파이프라인 이해하기#

무엇을 배웠나#

pipeline()가 토크나이저, 모델 추론, 디코딩 과정을 자동으로 연결해 주는 고수준 API라는 점을 명확히 이해하게 되었습니다. torch.distributed.pipelining.pipeline과 같은 저수준 분산 엔진과의 이름 혼동을 피하기 위해 용도를 정확히 구분하는 연습을 했습니다. 입력 길이와 max_length, max_new_tokens 파라미터 간의 상호작용과 우선순위를 파악하여 경고를 효과적으로 해결하는 방법을 배웠습니다.

헷갈렸던 점#

Hugging Face 공식 pipeline API와 PyTorch 분산 훈련용 torch.distributed.pipelining.pipeline은 이름만 같을 뿐 용도가 완전히 달라서 혼동되기 쉽습니다.

입력 문장이 42토큰뿐인데 max_length=60을 주니 “입력이 최대 길이를 초과한다"는 경고가 뜬 뒤, 모델 기본값인 max_new_tokens=256과 충돌나서 어느 파라미터가 우선되는지 파악하는 데 시간이 걸렸습니다.

정리된 이해#

pipeline()는 토크나이저, 모델 추론, 디코딩 과정을 자동으로 연결해 주는 고수준 API이며, Intel XPU 환경에서는 device="xpu" 문자열을 직접 지정하여 하드웨어를 정확히 제어할 수 있다.

from transformers import pipeline

summ = pipeline(
    task="summarization",
    model="EbanLee/kobart-summary-v3",
    device="xpu"
)

result = summ("짧은 입력 문장", max_length=60)
print(result[0]["summary_text"])

총평#

오늘 오전 전체에서 배운 것#

Gemma 2 XPU 구동을 위해 device_map="auto" 대신 명시적 이동과 파라미터 조정이 필요하다는 점을 확인했으며, 생성된 결과에서 입력 프롬프트를 잘라내어 답변을 추출하는 slicing 과정과 temperature 같은 sampling 파라미터가 확률 분포를 조절하여 텍스트 생성을 제어한다는 원리를 이해했다.

다음에 조심할 것#

XPU 환경에서는 device_map="auto" 대신 명시적인 model.to("xpu") 이동이 필수적이며, temperature는 모델 생성 옵션임을 반드시 확인해야 한다.

생성된 결과에서 답변을 추출할 때는 입력 프롬프트의 토큰 길이를 정확히 파악한 뒤 slicing 해야 하며, decode 시 skip_special_tokens=True 옵션을 활용해 가독성을 높여야 한다.

다음에 복습할 주제#

XPU 환경에서 device_map="auto" 대신 명시적인 model.to("xpu") 이동이 필수적임을 재확인하고, 토크나이저와 모델 출력을 분리할 때 shape[1]을 활용해 입력 프롬프트 길이를 정확히 파악하는 slicing 기법을 심화 학습한다. 또한 temperature 파라미터가 확률 분포의 날카로움을 조절하여 무작위성과 정답 사이의 균형을 어떻게 맞추는지에 대한 수학적 원리를 복습하고, torch.no_grad()가 그래디언트 계산 억제를 통해 메모리 효율을 높이는 핵심 역할을 하는지 검증한다.
