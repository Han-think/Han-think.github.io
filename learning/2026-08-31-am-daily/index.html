1. Express 프로젝트 기준선 잡기 (05를 뼈대로 06·07 연결하기)#

무엇을 배웠나#

오늘은 프로젝트의 기준선을 잡기 위해 식별자와 토큰의 역할을 명확히 구분하는 시간을 가졌다. 특히 Member.id, MongoDB _id, JWT가 각각 다른 목적을 가진다는 점을 정확히 이해했다. 05_mongodb를 뼈대로 하여 06·07을 연결하는 핵심 흐름을 정리하며, 기본 CRUD에 집중하는 것이 중요하다고 느꼈다.

헷갈렸던 점#

가장 큰 혼란 요소는 식별자(ID)와 토큰(JWT)의 구분이었습니다. Member.id, _id, 게시글 고유값, 그리고 JWT token까지 모두 ‘무언가를 찾는 값’처럼 보여서 용도가 헷갈렸습니다. 특히 08_board 예제에서 JWT, 페이지네이션, 자동 증가 ID가 한 번에 나오다 보니 각 요소가 어디서 왔는지, 어떤 역할을 하는지 놓치기 쉽었습니다.

핵심 흐름은 Node.js → npm Express 설치 → express() → middleware → router → Mongoose model → MongoDB → response이며, 각 용어의 정확한 의미는 다음과 같습니다. Member.id는 사용자 로그인 아이디(예: 이메일 또는 username), MongoDB _id는 document 자체 식별자(JWT는 로그인 인증을 증명하는 서명된 문자열)이며, 게시글 식별자는 CRUD에서 특정 게시글을 찾기 위한 값(_id 혹은 custom 필드)입니다. 결론적으로 id와 _id와 JWT는 각각 다른 목적을 가진 고유한 개념입니다.

정리된 이해#

오늘은 프로젝트의 기준선을 잡는 시간이었습니다. 핵심 흐름은 Node.js와 Express를 설치한 뒤 미들웨어와 라우터를 거쳐 Mongoose 모델로 MongoDB에 접근하고 응답을 반환하는 순서입니다. 가장 큰 혼란 요소였던 식별자(ID)와 토큰(JWT)은 각각 다른 목적을 가집니다: Member.id는 사용자 로그인 아이디, _id는 데이터베이스 문서 고유값, JWT는 인증을 증명하는 문자열입니다. 이를 명확히 구분하여 프로젝트의 기본 골격을 세우는 것이 중요합니다.

// 05_mongodb를 뼈대로 하는 핵심 흐름 (Express 프로젝트 기준선)

// 1. Express 설치 및 기본 설정
const express = require('express');
const app = express();

// 2. 미들웨어 설정 (body-parser 등)
app.use(express.json());

// 3. 라우터 분리 (router 활용)
const router = express.Router();

// 4. Mongoose 모델 연결 (MongoDB와의 통신)
// Member, Board 등 각 도메인별 Model 정의
const Post = require('./models/Post'); // 예시 모델

// 5. CRUD 라우팅 설정
router.get('/', async (req, res) => {
  const posts = await Post.find(); // MongoDB 조회
  res.json(posts);
});

router.post('/', async (req, res) => {
  const post = new Post(req.body); // 데이터 생성
  await post.save();
  res.status(201).json(post);
});

// 6. 라우터 적용
app.use('/api', router);

// 7. MongoDB 연결 및 서버 실행
mongoose.connect('mongodb://localhost:27017/mydb')
  .then(() => {
    app.listen(3000, () => console.log('Server running on port 3000'));
  });

2. 서버 구현 핵심 흐름 이해하기#

무엇을 배웠나#

Express와 MongoDB를 연결할 때 파일 구조보다 요청이 어떻게 흐르는지가 더 중요하다는 점을 깨달았다. node app.js 방식과 Express generator 방식을 구분하는 것보다, 라우터와 미들웨어를 거쳐 모델로 가는 연결 고리를 파악하는 것이 핵심이었다. 특히 회원가입과 글쓰기 시나리오를 통해 요청이 DB까지 도달하고 돌아오는 전체 흐름을 이해하게 되어 실무 적용에 대한 감을 잡을 수 있었다.

헷갈렸던 점#

Express와 MongoDB를 연결할 때 bin/www 방식과 node app.js 방식이 동시에 존재해 “어떤 코드가 정석인지” 구별하기가 힘들었다.

핵심은 단순히 파일을 만드는 것이 아니라, 요청이 어떤 경로를 거쳐 DB로 가고 다시 돌아오는지 전체적인 흐름을 파악하는 것이었다. 파일 구조보다 요청이 지나가는 경로가 더 중요하다.

처음에는 shortId나 nanoid 같은 라이브러리가 섞여 있어 “어디까지 내가 만든 건지” 막막했지만, 회원가입과 글쓰기 시나리오를 통해 Request → app.js → Router → Middleware → Model → MongoDB → Response라는 논리적 흐름을 이해하는 것이 무엇보다 중요했다.

정리된 이해#

핵심은 요청이 app.js를 거쳐 라우터와 미들웨어, 모델을 통해 MongoDB로 흐르고 다시 응답으로 돌아오는지 파악하는 것이다. 단순히 파일을 만드는 것보다 요청의 경로를 읽는 것이 중요하며, 현재 구현된 백엔드는 향후 Next.js UI로부터 fetch 요청을 받아 데이터를 처리하게 될 예정이다.

// app.js (핵심 진입점)
const express = require('express');
const app = express();
const port = 80;

// DB 연결 및 미들웨어 설정 생략
app.listen(port, () => {
  console.log(`Server running on port ${port}`);
});

// routes/member.js (라우터 미들웨어)
const express = require('express');
const router = express.Router();
const memberModel = require('../models/member');

router.post('/join', async (req, res) => {
  try {
    const newMember = new memberModel(req.body);
    await newMember.save();
    res.status(201).json({ message: '가입 성공', data: newMember });
  } catch (error) {
    res.status(400).json({ error: error.message });
  }
});

module.exports = router;

// models/member.js (DB 모델)
const mongoose = require('mongoose');
const Schema = mongoose.Schema;

const memberSchema = new Schema({
  username: { type: String, required: true, unique: true },
  email: { type: String, required: true },
  createdAt: { type: Date, default: Date.now }
});

module.exports = mongoose.model('Member', memberSchema);

3. API 식별자와 JWT 인증 흐름 정리#

무엇을 배웠나#

가장 큰 혼란은 ‘ID’라는 용어가 문서 고유번호, 게시글 번호, 로그인 정보 등 다양한 의미로 섞여 사용될 때 발생했습니다. 이를 해결하기 위해 **“무엇을 찾는 값”**과 **“누가 요청했는지 증명하는 값”**을 분리하여 생각해야 한다는 점을 깨달았습니다. id나 postId는 대상을 식별하는 역할을 하고, JWT는 인증 주체임을 명확히 구분하면 백엔드 흐름이 논리적으로 정리된다는 결론에 도달했습니다.

헷갈렸던 점#

처음에는 id, _id, postId 같은 용어가 모두 ‘식별자’라는 점에서 혼동이 되었습니다. 특히 게시글 번호와 사용자 ID가 섞여 있어 어떤 상황에서 무엇을 써야 할지 감을 잡기 어려웠습니다.

핵심은 **“무엇을 찾는 값"과 “누가 요청했는지 증명하는 값”**을 분리해서 생각해야 한다는 점이었습니다. 단순히 ‘ID’라고 통칭하기보다는, 문서 내에서 어떤 역할을 하는지에 따라 네이밍이 달라진다는 것을 이해하니 백엔드 흐름이 논리적으로 정리된 것 같습니다.

정리된 이해#

핵심은 **“무엇을 식별하는 값"과 “누가 요청했는지 증명하는 값”**을 분리하여 생각하는 것입니다.

id, postId, idx는 게시글이나 대상을 찾기 위한 고유 번호이며, JWT는 사용자의 신원을 검증하기 위한 인증 토큰입니다. 이 두 가지를 명확히 구분하면 백엔드 흐름이 논리적으로 정리됩니다.

🛠️ 실습 예시 (학습 내용 기반)#

1. 로그인 흐름 (인증)#

POST /member/login
- 아이디/비밀번호 확인
- jwt.sign(...)으로 토큰 생성
- token을 클라이언트에 반환

핵심: 이 과정에서 비밀번호는 JWT 페이로드에 넣지 않아야 합니다. (다음 복습 주제)

2. 보호된 요청 흐름 (인가)#

Authorization: Bearer <token>
→ jwt.verify(...) 검증
→ req.user 에 사용자 정보 부착
→ next()로 실제 작업 수행

다음에 조심할 것#

다음에는 id와 JWT가 혼용될 경우 발생하는 혼란을 방지하기 위해, 무엇을 식별하는 값인지와 누가 요청한 것인지 증명하는 값을 명확히 구분하여 사고의 오류를 최소화해야 한다.

JWT와 ID(게시글 번호 등)의 개념적 혼동을 해소하고, ‘무엇을 식별하는지’와 ‘누가 요청했는지 증명하는지’를 명확히 구분해 논리적인 흐름을 완성하는 연습이 필요합니다.
