1. 데이터베이스 설계: ERD, 스키마, 제약조건 완벽 이해#

무엇을 배웠나#

오늘 수업을 통해 ERD는 데이터베이스 설계를 위한 큰 그림이고, 스키마는 이 ERD를 바탕으로 실제 테이블 구조를 정의하는 것을 알게 되었습니다. 또한, 데이터의 정확성과 일관성을 유지하기 위한 제약조건의 종류와 역할을 이해하게 되어 데이터베이스 설계 과정에서 각 단계의 목적과 연관성을 파악하는 데 도움이 되었습니다. 특히 ERD 설계, 스키마 정의, 그리고 제약조건 적용 사이의 관계를 명확하게 이해하게 된 점이 중요합니다.

헷갈렸던 점#

ERD는 그림이고, 스키마는 그 그림을 코드로 옮기는 과정인 줄 알았는데, 실제 테이블 생성 명령어들과의 연결이 잘 안 되는 느낌이었어요. 특히 중간 테이블이 왜 필요한지, 그리고 제약 조건들이 정확히 어떤 역할을 하는지 이해하기가 좀 어려웠습니다. 전체적인 흐름 속에서 각 요소들의 역할이 명확하게 연결되지 않는 느낌이었어요.

정리된 이해#

ERD는 데이터베이스를 설계할 때 테이블과 관계를 시각적으로 보여주는 설계도이고, 스키마는 이 ERD를 바탕으로 실제 테이블 구조를 정의하는 것을 의미합니다. 제약조건은 데이터의 정확성과 일관성을 유지하기 위한 규칙들로, 테이블 간의 관계를 명확히 하고 데이터 오류를 방지하는 역할을 합니다.

-- 예시: Department 테이블 생성 (간략화)
CREATE TABLE Department (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(255) NOT NULL
);

-- 예시: Professor 테이블 생성 (간략화)
CREATE TABLE Professor (
    professor_id INT PRIMARY KEY,
    department_id INT,
    professor_name VARCHAR(255) NOT NULL,
    FOREIGN KEY (department_id) REFERENCES Department(department_id)
);

-- 예시: Course 테이블 생성 (간략화)
CREATE TABLE Course (
    course_id INT PRIMARY KEY,
    course_name VARCHAR(255) NOT NULL,
    credits INT DEFAULT 3
);

2. 학교 데이터베이스 제약조건 완벽 이해하기#

무엇을 배웠나#

학교 데이터베이스 제약조건을 이해하는 과정에서 테이블 구조의 핵심 테이블과 부가 테이블 구분이 어려웠지만, 각 예제의 목적과 핵심 제약조건을 정리하면서 이해도가 높아졌습니다. 특히 복합 기본키나 제약 조건 수정/삭제 과정, 개체 무결성과 참조 무결성 개념에 대한 명확한 이해가 필요했습니다. 앞으로는 예제별 목적과 제약조건을 연결하여 테이블 구조를 더욱 체계적으로 분석해야겠습니다.

헷갈렸던 점#

처음에는 테이블들이 어떤 역할을 하는지 파악하기 어려웠고, 특히 복합 기본키가 어떻게 작동하는지 이해하는 데 시간이 오래 걸렸습니다. 또한, SQLite에서 제약 조건을 수정하거나 삭제하는 과정이 복잡하게 느껴져서 막연하게 느껴졌던 점도 있습니다. 개체 무결성과 참조 무결성의 차이점을 명확히 구분하는 데 어려움을 겪었습니다.

정리된 이해#

학교 데이터베이스 제약조건을 이해하는 과정에서 테이블 구조를 구분하고 각 제약조건이 어떻게 작동하는지 파악하는 데 어려움이 있었지만, 예제별 목적과 핵심 개념을 명확히 구분하면서 실질적인 작동 방식을 이해할 수 있게 되었습니다. 특히, 복합 기본키와 개체/참조 무결성은 추가적인 학습이 필요하지만, 기본적인 제약조건의 역할과 중요성은 숙지하게 되었습니다. SQLite에서 제약조건을 수정하거나 삭제하는 부분은 좀 더 실습을 통해 숙달해야겠습니다.

-- 예제 2: NOT NULL 확인
CREATE TABLE users (
    id INTEGER NOT NULL,
    name TEXT,
    email TEXT NOT NULL
);

-- 예제 3: 이메일 중복 방지
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    name TEXT,
    email TEXT UNIQUE
);

-- 예제 5: 기본값 설정 확인
CREATE TABLE products (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  price REAL DEFAULT 0.0
);

-- 예제 6: 학점 범위 검사
CREATE TABLE courses (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  credits INTEGER CHECK (credits BETWEEN 1 AND 5)
);

-- 예제 10: 학생 ID 중복 방지
CREATE TABLE students (
    student_id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    grade INTEGER
);

-- 예제 12: 복합 기본키 테스트
CREATE TABLE enrollment (
    student_id INTEGER,
    course_id INTEGER,
    PRIMARY KEY (student_id, course_id)
);

3. Good vs Bad DB 제약조건 비교 실습 요약#

무엇을 배웠나#

데이터베이스 제약조건 설계 시, 사용자 경험을 고려하는 것이 얼마나 중요한지 깨달았습니다. bad.db를 통해 과도한 제약조건이 오히려 사용자 불편을 초래할 수 있다는 점을 실감했고, good.db는 실용적인 제약조건 설계의 좋은 예시임을 알게 되었습니다. 이 실습을 통해 데이터베이스 설계 시, 적절한 수준의 제약조건 적용의 중요성을 배우게 되었습니다.

헷갈렸던 점#

처음에는 bad.db의 복잡한 제약조건이 왜 데이터 입력을 막는지 이해하기 어려웠고, 앱의 목적이 단순히 ERD 시각화가 아니라 제약조건의 적절성을 비교하는 데 있다는 것을 파악하는 데 시간이 걸렸습니다. 특히 bad.db의 과도한 CHECK 조건이 사용자 입력에 얼마나 큰 영향을 미치는지 명확히 알지 못했습니다.

정리된 이해#

Good DB는 실용적인 제약조건을 통해 사용자 입력을 쉽게 할 수 있도록 설계되었고, Bad DB는 과도한 제약조건으로 인해 정상적인 입력도 실패하게 되는 상황을 보여줍니다. 실습을 통해 좋은 제약 조건과 나쁜 제약 조건의 차이를 명확히 이해할 수 있었습니다. 중요한 것은 데이터 무결성을 유지하면서도 사용자 경험을 고려하는 균형 잡힌 설계입니다.

4. SQLite 이해와 DBMS 선택 가이드#

무엇을 배웠나#

오늘 수업에서 SQLite에 대한 이해가 부족했던 부분을 명확히 파악하고, SQLite, PostgreSQL, Oracle DBMS의 특징과 적합한 사용 상황을 구분하게 되었습니다. 특히 SQLite는 가벼운 개인 프로젝트에 적합하고, 팀 프로젝트나 대규모 서비스에는 PostgreSQL이나 Oracle과 같은 서버형 DB가 더 적합하다는 점을 알게 되었습니다. 실습을 통해 제약조건 설정과 같은 SQLite의 기본적인 사용법도 익혔습니다.

헷갈렸던 점#

SQLite를 처음 접하면서, PRAGMA foreign_keys = ON을 잊으면 참조 무결성이 지켜지지 않는다는 점이 당황스러웠고, 테이블 구조를 수정할 때 ALTER TABLE의 제약이 많다는 것도 답답했습니다. 또한 ERD 도구와 SQLite 스키마의 호환성 문제 때문에 데이터베이스 구조를 시각적으로 명확하게 표현하기 어려웠습니다.

정리된 이해#

SQLite는 파일 기반으로 가볍고 설치가 간편하여 개인 프로젝트나 로컬 테스트에 적합하며, 다른 DBMS와 달리 제약 조건 관리에 있어 약간의 주의가 필요합니다. 팀 프로젝트나 대규모 데이터 관리가 필요한 경우에는 PostgreSQL과 같은 서버형 데이터베이스를 선택하는 것이 더 적합합니다. SQLite의 제약 조건은 PRAGMA 명령어를 통해 명시적으로 활성화해야 하며, 테이블 수정 시 제약 조건 변경이 까다롭다는 점을 기억해야 합니다.

PRAGMA foreign_keys = ON;
CREATE TABLE Users (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    FOREIGN KEY (id) REFERENCES Contacts(id)
);

총평#

오늘 오전 전체에서 배운 것#

데이터베이스 설계 과정에서 ERD, 스키마, 제약조건의 역할과 상호 연관성을 명확히 이해하게 되었고, 특히 데이터베이스 제약조건 설계 시 사용자 경험을 고려하는 것이 중요하다는 것을 깨달았습니다. 또한, SQLite를 포함한 다양한 DBMS의 특징을 파악하여 프로젝트 규모와 목적에 맞는 데이터베이스를 선택할 수 있게 되었습니다.

다음에 조심할 것#

앞으로는 ERD 설계, 스키마 정의, 제약 조건 적용 사이의 관계를 더욱 명확히 연결하며 테이블 구조를 분석하는 연습을 꾸준히 해야겠습니다. 또한, 데이터베이스 설계 시 사용자 경험을 고려하는 실용적인 제약 조건 설계에 더욱 집중해야 할 것 같습니다. 마지막으로, 다양한 DBMS의 특징을 고려하여 프로젝트의 규모와 목적에 맞는 데이터베이스를 선택하는 능력을 키워야겠습니다.
