1. 공공 API 크롤링, 요청 인자 이해하기#

무엇을 배웠나#

Open API 기반 크롤링을 처음 이해할 때 인증 관련, 응답 형식, 데이터 대상, 범위 지정 등 다양한 인자를 혼동했었는데, API가 외부 데이터에 접근하는 통로라는 것을 명확히 이해하게 되었습니다. 공공 데이터 API와 LLM API의 차이점을 이해하고, API 문서를 통해 필요한 인자를 파악하는 연습이 중요함을 알게 되었습니다. 실제 식품안전나라 레시피 API 실습을 통해 API 호출 구조와 데이터 처리 과정을 익혔습니다.

헷갈렸던 점#

API를 처음 접했을 때, 어떤 인자가 필수이고 어떤 인자가 선택적인지 파악하는 게 어려웠습니다. 특히 공공 데이터 API와 LLM API의 차이점을 명확히 구분하지 못해서 API가 단순히 모델을 호출하는 것 이상으로 외부 데이터에 접근하는 역할을 한다는 것을 이해하는 데 시간이 걸렸습니다.

정리된 이해#

API는 단순히 모델을 호출하는 것이 아니라 외부 데이터에 접근할 수 있도록 해주는 중요한 통로라는 점을 이해하게 되었다. 요청 인자들을 역할에 따라 분류하고, 각 인자가 API 요청에 어떤 영향을 미치는지 명확히 파악하는 것이 중요하다. 특히 공공 데이터 API를 사용할 때는 공식 문서를 꼼꼼히 확인하고, 인증키와 데이터 형식을 정확하게 입력해야 원하는 데이터를 얻을 수 있다.

import requests
import json

api_key = "YOUR_API_KEY"  # 실제 API 키로 대체
url = f"https://api.foodsafetykorea.go.kr/api/1/recipe/{api_key}/json/RECIPE_SERVICE/0/10"

response = requests.get(url)

if response.status_code == 200:
    data = response.json()
    print(json.dumps(data, indent=2, ensure_ascii=False))
else:
    print(f"API 요청 실패: {response.status_code}")

2. JSON과 XML 선택 및 로컬 데이터 관리 전략#

무엇을 배웠나#

JSON과 XML의 선택은 프로젝트의 요구사항과 환경에 따라 달라져야 하며, JSON의 편리함과 XML의 엄격한 검증 능력을 모두 고려해야 한다는 점을 알게 되었습니다. 자주 사용하는 데이터는 외부 API 호출 대신 로컬 데이터베이스에 저장하여 효율적인 접근성을 확보하는 것이 중요하다는 것을 배웠습니다. 앞으로는 데이터 형식 선택 시, 단순히 최신 기술 여부를 판단하는 것이 아니라, 프로젝트의 목적과 데이터 특성에 맞는 최적의 방식을 선택해야겠습니다.

헷갈렸던 점#

처음에는 JSON을 최신 기술로만 생각하고 XML을 오래된 형식으로 여겨 JSON을 무조건적으로 선호했지만, XML의 계층 구조와 데이터 검증 능력이 중요함을 깨달았습니다. 또한 매번 API를 호출할지, 로컬에 저장할지 결정하는 데 어려움을 겪었으며, 효율적인 데이터 관리 방법에 대한 이해가 부족했습니다.

정리된 이해#

프로젝트의 필요에 따라 JSON과 XML을 선택하되, JSON은 Python과의 연동이 용이하여 우선적으로 고려합니다. 자주 사용되는 데이터는 외부 API 호출 대신 로컬 데이터베이스에 저장하여 효율성을 높이고, 원본 데이터 형식은 보존하여 필요시 활용합니다. XML은 여전히 엄격한 데이터 검증이 필요한 환경에서 유용하게 사용될 수 있습니다.

import requests
import pandas as pd

# JSON 예시
response = requests.get('API_URL', timeout=30)
response.raise_for_status()
payload = response.json()
rows = payload["서비스명"]["데이터열"]
df = pd.DataFrame(rows)

import xml.etree.ElementTree as ET

# XML 예시
root = ET.fromstring(response.text)
xml_data = {child.tag: child.text for child in root}

3. 멀티스레딩과 API 사용 시 성능과 제한 사항 이해#

무엇을 배웠나#

멀티스레드를 사용한다고 해서 항상 성능이 일정 비율로 향상되는 것은 아니라는 것을 알게 되었다. 요청 수와 서버 응답 시간에 따라 멀티스레드의 효과가 달라지고, 무료 공공 API는 다양한 제한 사항이 있다는 것도 깨달았다. 이러한 점들을 고려하여 API 호출 설계를 해야겠다.

헷갈렸던 점#

멀티스레드가 항상 일정한 비율로 성능 향상을 가져온다고 생각했고, 공공 API는 제한 없이 자유롭게 사용할 수 있다고 잘못 이해했습니다. 실제로 멀티스레드 성능은 요청 수와 응답 시간에 따라 달라지고, 공공 API는 다양한 제한 사항이 존재했습니다.

정리된 이해#

멀티스레드를 사용하면 네트워크 요청의 개수와 서버 응답 시간에 따라 성능 향상이 커지지만, 요청 수가 적거나 응답 시간이 길면 효과가 제한적일 수 있습니다. 무료 공공 API는 무제한으로 사용할 수 있는 것이 아니라, 호출 횟수, 페이지 크기, 인증 등 다양한 제한 사항을 준수해야 합니다. 이러한 점들을 고려하여 스레드 수를 조절하고 API 사용 계획을 세워야 효율적인 데이터 수집이 가능합니다.

import concurrent.futures
import requests

def fetch_data(url):
    try:
        response = requests.get(url)
        response.raise_for_status() # HTTP 에러 발생 시 예외 발생
        return response.json()
    except requests.exceptions.RequestException as e:
        print(f"Error fetching {url}: {e}")
        return None

4. 랜덤 포레스트 이해와 하이퍼파라미터 튜닝 워크노트#

무엇을 배웠나#

Random Forest가 단순히 여러 트리의 결과를 평균내는 것이 아니라, 다수결 투표 방식으로 예측을 결정한다는 점을 명확히 이해하게 되었다. 또한, 모델 학습 과정에서 사용되는 무작위성이 데이터 샘플링과 특성 선택에 활용된다는 것을 알게 되었고, 하이퍼파라미터와 학습 파라미터의 구분에도 대한 개념을 제대로 갖추게 되었다. 이러한 이해를 바탕으로 Random Forest 모델을 더 효과적으로 다룰 수 있을 것 같다.

헷갈렸던 점#

처음에는 Random Forest의 예측이 여러 트리의 결과를 단순 평균내는 거라고 생각했고, ‘random’이라는 단어가 데이터 임의 채워넣는 걸 의미한다고 착각했습니다. 또한, 모델 내부 파라미터와 사람이 설정하는 하이퍼파라미터의 차이를 명확히 구분하지 못해 어려움을 겪었습니다.

정리된 이해#

Random Forest는 여러 트리의 예측 결과를 투표로 결정하며, 무작위성은 데이터 샘플링과 특성 선택 과정에서 활용됩니다. 하이퍼파라미터는 모델 학습 전에 사용자가 직접 설정하는 값이며, 트리의 깊이나 트리의 수를 조절합니다. 이러한 이해를 바탕으로 Random Forest 모델을 더 효과적으로 활용할 수 있을 것입니다.

# Random Forest 예측 방식 예시 (Python)
import numpy as np

def majority_vote(predictions):
    """다수결 투표를 통해 최종 예측 결정"""
    counts = np.bincount(predictions)
    return np.argmax(counts)

# 예측 결과 (각 트리의 예측)
tree_predictions = np.array(['생존', '사망', '생존', '생존', '사망', '생존'])

# 다수결 투표를 통해 최종 예측 결정
final_prediction = majority_vote(tree_predictions)
print(f"최종 예측: {final_prediction}")

5. 에러 수정 및 개인 PC 자원 맞춤 학습 전략#

무엇을 배웠나#

작은 오타 하나로도 파이프라인 실행이 중단될 수 있다는 점을 깨달았고, n_jobs=-1과 같은 무분별한 병렬 처리가 오히려 자원 과다 사용으로 이어질 수 있다는 점을 알게 되었다. 개인 PC 자원을 고려하여 각 단계별 병렬 처리 전략을 세우는 것이 중요하며, 특히 API 수집, 랜덤 포레스트, 그리드 서치CV의 병렬화 방식 차이를 이해해야 한다는 것을 배웠다. 앞으로는 코드를 꼼꼼히 검토하고, 자원 사용량을 고려하여 병렬 처리 단계를 조정해야겠다.

헷갈렸던 점#

실습하다가 ColumnTransformer나 random_state 같은 사소한 오타 때문에 파이프라인이 멈추는 경우가 많았고, n_jobs=-1을 어디에나 적용하면 좋을 거라고 생각했지만 오히려 자원 낭비가 될 수 있다는 점을 제대로 이해하지 못했습니다. 특히 개인 PC의 자원을 고려해서 병렬 처리 전략을 어떻게 세워야 할지 막막했습니다.

정리된 이해#

작은 오타와 문법 오류가 코드 실행에 큰 영향을 미칠 수 있다는 점을 깨달았고, 병렬 처리 시 각 단계별 목적과 주의사항을 명확히 이해해야 과도한 자원 사용을 막을 수 있다는 점을 알게 되었다. 특히 개인 PC의 자원을 고려하여 각 단계에 적합한 병렬화 수준을 설정하는 것이 중요하다는 점을 확인했다.
