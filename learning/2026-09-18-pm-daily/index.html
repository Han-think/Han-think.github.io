1. CONCAT과 TRUNCATE의 정확한 구분하기#

무엇을 배웠나#

SELECT 문을 통해 데이터를 단순히 꺼내는 것을 넘어, 사람이 읽기 쉬운 형태로 가공하는 방법을 배웠다. CONCAT() 함수는 문자열이나 값을 이어 붙여 하나의 문자열로 만드는 반면, TRUNCATE()는 숫자의 소수점 이하를 지정한 자리 수만큼 잘라내는 숫자 함수다. 특히 TRUNCATE()와 테이블을 지우는 TRUNCATE TABLE 명령어는 목적과 대상이 완전히 다르다는 점을 명확히 구분하는 것이 중요하다.

헷갈렸던 점#

CONCAT과 TRUNCATE가 동시에 등장하면서 문자열 함수와 숫자 함수의 역할 경계가 모호해 순간적으로 “이건 함수야, 아니면 명령어야?” 하는 혼동을 느꼈다.

특히 TRUNCATE라는 단어는 테이블을 지우는 DDL 명령어인 TRUNCATE TABLE과 발음도 비슷하고 용어도 겹쳐서, 함수와 명령어의 구분이 momentarily 섞였다. 하지만 수업을 통해 TRUNCATE(숫자, 자리수)는 숫자의 소수점 자릿수를 정리하는 순수 함수이며, 테이블을 비우는 구조 변경 명령어와는 완전히 별개라는 점을 명확히 할 수 있었다.

정리된 이해#

SELECT 문을 통해 데이터를 단순히 꺼내는 것을 넘어, 사람이 읽기 쉬운 형태로 가공하는 방법을 배웠다. CONCAT() 함수는 문자열이나 값을 이어 붙여 하나의 문자열로 만들며, TRUNCATE() 함수는 숫자의 소수점 이하를 지정한 자리 수만큼 잘라낸다. 특히 TRUNCATE()는 숫자 함수이며 TRUNCATE TABLE은 테이블을 비우는 명령어와 완전히 별개라는 점을 명확히 구분하는 것이 중요하다.

SELECT
    CONCAT(family_name, ' ', first_name) AS full_name,
    TRUNCATE(price, 2) AS truncated_price
FROM products;

2. SQL 조건 검색 핵심 요약#

무엇을 배웠나#

SELECT 문에서 원하는 데이터를 추출하는 핵심 요소들을 정리했습니다.

DISTINCT는 선택한 컬럼 전체 조합이 같아야 중복으로 간주된다는 점을 명확히 했습니다. 또한 IN 연산자는 여러 개의 OR 조건을 하나의 식으로 효율적으로 대체할 수 있다는 규칙을 익혔고, LIKE 연산자의 % 기호가 문자열의 앞, 뒤, 가운데에 각각 다른 패턴 매칭 효과를 낸다는 점을 이해했습니다.

헷갈렸던 점#

SELECT 절에서 여러 컬럼을 지정했을 때, DISTINCT는 ‘선택한 모든 컬럼 값이 일치하는 행’에 대해서만 중복을 제거한다는 점을 명확히 했다. IN 연산자는 OR 조건의 나열을 대체할 수 있지만, 단순히 문법을 외우는 것을 넘어 실제 데이터가 어떻게 매핑되는지 연습하지 않으면 바로 생각이 나지 않는 패턴이다. LIKE에서 % 기호는 앞, 뒤, 양쪽에 모두 사용 가능하며, 가운데 위치할 경우 문자열의 어디에든 해당 패턴이 포함되어 있으면 조건을 만족한다는 점을 정확히 이해했다.

정리된 이해#

WHERE 절을 통해 기본적인 조건 필터링을 수행하고, AND/OR 연산자를 활용해 여러 조건을 조합하여 데이터를 추출합니다. DISTINCT는 선택한 컬럼 전체의 조합이 동일할 경우 중복을 제거하며, IN 연산자는 여러 OR 조건을 간결하게 표현하는 대체 구문으로 사용됩니다.

-- WHERE 조건 검색 기본 예시
SELECT * FROM employees
WHERE salary > 5000 AND department = 'Sales';

-- DISTINCT: 선택한 컬럼 조합의 중복 제거 (family_name + salary 기준)
SELECT DISTINCT family_name, salary FROM employees;

-- IN 연산자: 여러 OR 조건을 하나로 압축
SELECT * FROM employees
WHERE family_name IN ('김', '이', '박');

-- LIKE 패턴 검색 예시
SELECT * FROM employees
WHERE family_name LIKE 'ze%';      -- ze로 시작하는 이름
SELECT * FROM employees
WHERE family_name LIKE '%com';     -- com으로 끝나는 이름
SELECT * FROM employees
WHERE family_name LIKE '%se%';     -- 가운데에 se가 포함된 이름

-- ORDER BY: 결과 정렬 (ASC 오름차순, DESC 내림차순)
SELECT * FROM employees
ORDER BY salary DESC;

3. 그룹화와 통계 필터링의 차이: GROUP BY vs HAVING#

무엇을 배웠나#

GROUP BY는 단순히 데이터를 묶는 것이 아니라, 집계 함수와 결합해 의미 있는 통계를 도출하는 핵심 도구라는 점을 깨달았습니다. WHERE은 그룹화 전 원본 행을 걸러내고, HAVING은 GROUP 이후의 결과에 조건을 적용한다는 명확한 순서 구분 덕분에 쿼리 작성 시 혼란이 해소되었습니다. 특히 별칭 사용 가능 여부에 따라 문법적 번거로움이 있다는 점은, 안전하게 함수 자체를 기술하는 습관을 들이는 것이 중요하다고 느꼈습니다.

헷갈렸던 점#

GROUP BY는 단순히 데이터를 뭉치는 과정이 아니라, 집계 함수와 결합했을 때 각 그룹별로 통계값을 산출하는 핵심적인 역할을 한다는 점이 가장 크게 와닿았습니다.

WHERE은 원본 행 단위로 조건을 걸지만, HAVING은 GROUP BY 이후에 발생한 집계 결과(합계나 평균 등)에만 조건을 적용한다는 점에서 시점와 대상이 명확히 구분된다는 사실이 이해하는 데 큰 도움이 되었습니다.

정리된 이해#

GROUP BY는 집계 함수(합계, 평균 등)를 적용하기 전, 기준이 되는 컬럼을 기준으로 데이터를 묶어주는 역할을 합니다. WHERE은 그룹화 전에 개별 행을 걸러내고, HAVING은 GROUP BY 이후 계산된 결과값에 조건을 붙여 최종 결과를 필터링합니다. 특히 HAVING에서는 별칭 대신 집계 함수를 직접 명시하는 것이 안전합니다.

-- WHERE: GROUP BY 전에 개별 행을 필터링 (예: 부서코드가 'D10'인 행만 선택)
SELECT dept_id, SUM(salary) AS total_salary
FROM employees
WHERE dept_id = 'D10'
GROUP BY dept_id;

-- HAVING: GROUP AFTER 그룹화된 결과에 조건을 걸기 (예: 부서별 급여 합계가 10000 이상인 경우)
SELECT dept_id, SUM(salary) AS total_salary
FROM employees
GROUP BY dept_id
HAVING SUM(salary) >= 10000;

4. 트랜잭션과 자동 커밋의 관계#

무엇을 배웠나#

Transaction은 단순한 데이터 변경이 아니라, ‘All or Nothing’ 원칙을 따르는 논리적 업무 단위다. AUTOCOMMIT 설정 여부에 따라 SQL 실행 후 즉시 확정되거나, 직접 COMMIT해야 한다는 점이 핵심이었다. 특히 AUTOCOMMIT 0(Off) 상태에서는 ROLLBACK을 통해 이전 상태로 되돌릴 수 있다는 점을 명확히 이해했다.

헷갈렸던 점#

SQLite에서는 자동으로 변경 사항이 확정되는 동작을 보였지만, 표준 SQL 환경에서는 COMMIT 명령어가 필수적이라는 점이 가장 큰 혼란 요소였다.

특히 AUTOCOMMIT 설정값(1 또는 0)이 트랜잭션의 확정 여부를 결정한다는 점을 간과하다가, SELECT @@AUTOCOMMIT;로 현재 모드를 확인해야 한다는 사실을 깨닫고 이해하게 되었다.

정리된 이해#

트랜잭션은 ‘성공 시 확정, 실패 시 전체 취소’하는 논리적 업무 단위이며, AUTOCOMMIT 설정 여부에 따라 SQL 실행 즉시 확정되거나 수동 COMMIT 전까지 변경 사항이 유보된다. 따라서 데이터의 일관성을 보장하려면 Commit과 Rollback의タイ밍을 AUTOCOMMIT 상태와 함께 정확히 파악해야 한다.

-- AUTOCOMMIT OFF 상태에서의 Transaction 흐름 예시

-- 1. AUTOCOMMIT 비활성화 (OFF)
SET AUTOCOMMIT OFF;

-- 2. 데이터 변경 (아직 확정되지 않음, ROLLBACK 가능)
DELETE FROM employees WHERE id = 100;

-- 3. 작업 취소 (변경 사항 원상 복구)
ROLLBACK;

-- 4. 현재 상태 확인 (데이터가 복구된 것을 확인)
SELECT * FROM employees WHERE id = 100;

5. 테이블당 1개의 기본키, 컬럼의 자유로운 조합#

무엇을 배웠나#

PRIMARY KEY는 테이블 내 각 행을 유일하게 식별하는 기준이며, 중복과 NULL이 허용되지 않는 것이 핵심 규칙입니다. 테이블당 하나의 PRIMARY KEY 제약조건만 존재하지만, 이를 구성하는 컬럼의 개수는 단일 컬럼에서 여러 개의 복합키까지 자유롭게 설정할 수 있습니다. 특히 복합키의 경우 각 컬럼 값은 반복되어도 전체 조합이 중복되지 않아야 한다는 점이 중요합니다.

헷갈렸던 점#

강사님의 설명을 그대로 따라 적다 보면 컬럼이 하나여야 한다고 오해하게 되었고, ‘컬럼 조합 16개 가능’이라는 표현을 컬럼 개수 제한으로 잘못 해석했습니다.

특히 ‘테이블당 1개의 제약조건’ 규칙은 PRIMARY KEY라는 이름의 규칙은 하나만 존재한다는 뜻이지, 컬럼의 개수를 제한하는 것은 아니라는 점을 명확히 구분하지 못해 혼란스러웠습니다.

정리된 이해#

PRIMARY KEY는 테이블 내 각 행을 유일하게 식별하는 기준이며, 중복과 NULL 값을 허용하지 않는 것이 핵심 규칙입니다. 테이블당 하나의 PRIMARY KEY 제약조건만 존재하지만, 이는 단일 컬럼이나 여러 컬럼의 조합(복합키)으로 구성될 수 있습니다. 특히 복합키의 경우 전체 조합이 유일해야 하므로 각 컬럼 값은 반복되어도 문제되지 않습니다.

-- 단일 컬럼 기본키 (emp_no)
CREATE TABLE employees (
    emp_no INT PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50)
);

-- 복합기본키 (student_no + subject_no 조합)
CREATE TABLE enrollments (
    student_no INT,
    subject_no INT,
    grade CHAR(1),
    PRIMARY KEY (student_no, subject_no)
);

총평#

오늘 오후 전체에서 배운 것#

CONCAT과 TRUNCATE는 문자열 연결과 숫자의 소수점 절삭이라는 전혀 다른 기능을 수행한다는 점을 명확히 구분하는 것이 중요했습니다. 또한 GROUP BY와 HAVING의 순서 차이를 이해하여 WHERE이 원본 행을 걸러내고 HAVING이 집계 결과에 조건을 적용한다는 점은 쿼리 작성 시 큰 도움이 되었습니다. 마지막으로 트랜잭션의 ‘All or Nothing’ 원칙과 AUTOCOMMIT 설정 여부에 따른 Commit/Rollback의 관계를 통해 논리적인 업무 단위 관리의 중요성을 깨달았습니다.

다음에 조심할 것#

TRUNCATE 함수와 테이블 삭제 명령어를 혼동하지 않도록 주의해야 합니다. 또한 WHERE 절과 HAVING 절의 적용 시점을 명확히 구분하여 쿼리 작성 오류를 방지하는 것이 중요합니다. 마지막으로 AUTOCOMMIT 설정 여부에 따라 데이터 변경 사항을 즉시 확정하거나 되돌릴 수 있으므로, 트랜잭션 관리에 항상 주의를 기울여야 합니다.

다음 복습 주제#

다음 학습에서는 JOIN을 통해 여러 테이블 간의 데이터를 통합하고, 이를 효율적으로 필터링하는 방법을 중점적으로 공부할 예정이다. 특히 INNER JOIN, LEFT JOIN 등 다양한 조인 유형별 동작 원리와 결과 차이점을 명확히 이해하여 복잡한 쿼리 작성 능력을 키우겠다. 또한 INDEX와 같은 성능 최적화 기법에 대해서도 기본적인 개념을 짚어보며, 실무에서 자주 발생하는 데이터 중복 문제 해결 방안에 대해서도 고민해보겠다.
