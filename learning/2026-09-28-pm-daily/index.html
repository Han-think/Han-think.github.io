1. JWT 기반 로그인 인증 연결하기#

무엇을 배웠나#

JWT는 로그인 자체를 처리하는 것이 아니라, 로그인 후 후속 요청에서 사용자가 인증된 상태임을 증명하기 위한 토큰입니다. 서버는 로그인 직후의 상태를 자동으로 기억하지 않기 때문에, 이후 모든 요청에 token을 Authorization 헤더에 실어 재검증을 받아야 합니다. 실습을 통해 token은 Python으로 secret key로 암호화해 생성하고, 브라우저에서는 sessionStorage에 저장한 뒤 다음 요청 시 header에 실어 보내는 흐름을 확인했습니다.

헷갈렸던 점#

로그인을 한 번 했다고 서버가 자동으로 인증 상태를 유지하지 않으며, 이후 요청마다 token을 Authorization 헤더에 실어 재전송해야 한다는 점이 가장 헷갈렸다. 특히 token이 로그인 자체의 결과물이 아니라, 다음 요청에서 ‘인증된 사용자’임을 증명하기 위한 증명서 역할을 한다는 개념이 명확히 잡히지 않아 token, payload, header 등의 용어가 동시에 등장했을 때 감을 잃었다.

정리된 이해#

JWT는 로그인 완료 후 서버에 전달된 사용자 정보를 증명하는 인증 토큰이며, 이후 요청 시 Authorization 헤더에 실어 보내야 서버가 이를 검증하여 접근을 허락한다. 로그인을 한 번 했다고 해서 서버가 자동으로 다음 요청을 기억하지 않기 때문에, 매번 token을 포함해 인증 과정을 반복해야 한다. 따라서 JWT는 단순히 발급되는 값이 아니라, 서버와 클라이언트 사이에서 지속적인 인증 상태를 유지하기 위한 핵심 수단이다.

JWT 기반 로그인 인증 연결하기#

💻 실습 예시#

1. JWT 생성 (Python)#

def get_token(data: dict) -> str:
    expire_time = ...  # 만료 시간 계산
    data.update({"exp": expire_time})
    return jwt.encode(
        data,
        "<secret>",      # 실제 secret 값은 보안에 유의하여 관리
        algorithm="HS256"
    )

2. 브라우저 저장 (JavaScript)#

로그인 성공 후 sessionStorage에 저장:

sessionStorage.setItem("id", param.id);
sessionStorage.setItem("token", data.token);

3. Authorization 헤더 전송 (다음 요청)#

axios.get(
    `/list/1?id=${id}`,
    {
        headers: {
            Authorization: token  // token을 header에 실어 보냄
        }
    }
);

4. FastAPI에서의 인증 확인#

서버는 query parameter의 ID, client IP, Authorization header의 token을 가져와 verify_token()으로 payload를 검증한다.

def verify_token(token: str):
    return jwt.decode(
        token,
        "<secret>",
        algorithms=["HS256"]
    )

2. RAG와 Vector DB, 개념 정리의 핵심#

무엇을 배웠나#

오늘 FastAPI 인증 수업 후 갑자기 바뀐 RAG와 Vector DB 주제로 인해 용어가 기존 SQL 개념과 겹쳐 혼란스러웠습니다. 특히 모델 재훈련이 아닌 문서 검색 과정임을 이해하는 데 시간이 걸렸지만, get()와 query()의 차이를 통해 ID 기반 조회와 의미 유사성 검색의 기능을 명확히 구분할 수 있었습니다. Vector DB는 모델을 다시 훈련시키는 것이 아니라, 미리 저장해둔 문서를 의미적으로 찾아주는 통로라는 점이 가장 핵심적인 깨달음이었습니다.

헷갈렸던 점#

처음에는 RAG가 모델을 다시 훈련하는 과정인 줄 알았지만, 이미 만든 문서를 DB에 저장하고 검색하는 ‘검색’ 과정임을 명확히 했다. SQL로만 보아왔던 get()와 query()의 차이도 처음에는 ID 찾기와 의미 찾기의 미세한 차이로 느껴져 구분하기 어려웠으나, 결국 전자는 정확한 ID 조회, 후자는 질문과의 유사도 검색이라는 점을 이해했다.

정리된 이해#

Vector DB는 모델을 재학습시키는 것이 아니라, 저장된 문서를 의미적으로 검색하는 통로라는 점이 핵심입니다. get()은 정확한 ID를 통해 특정 문서를 조회하고, query()는 질문과 의미가 비슷한 문서를 찾아주는 것이 주요 기능입니다. 오늘 배운 내용을 바탕으로 Vector DB가 단순히 데이터를 저장하는 곳이 아니라, 질문에 답하기 위해 관련 정보를 끄집어내는 필터 역할임을 명확히 이해했습니다.

# 02_CRUD.py 핵심 로그 (노트 기반 요약)

from chromadb import PersistentClient

client = PersistentClient(path="./chroma_db")

collection = client.get_or_create_collection(name="user_guide")

# 1. 추가 (Create)
collection.add(
    documents=["로그인 방법", "비밀번호 찾기 안내", "다크모드 설정 가이드"],
    ids=["doc_001", "doc_002", "doc_003"]
)

# 2. 특정 ID 조회 (Read - get)
doc = collection.get(ids=["doc_001"])
print(doc)  # ['로그인 방법'] 반환

# 3. 의미 기반 검색 (Read - query)
results = collection.query(
    query_texts="비밀번호가 기억나지 않아요",
    n_results=2
)
print(results)  # 질문과 의미가 비슷한 문서들 반환

3. metadata 조건 검색과 upsert 데이터 관리#

무엇을 배웠나#

나는 where와 query_texts가 단순한 검색 조건이 아니라, 후보군을 좁히는 필터와 의미 검색을 수행하는 두 단계 과정임을 이해하게 되었다. 특히 where로 메타데이터를 걸러놓은 상태에서 query_texts가 의미를 파악한다는 점이 핵심이었다. 이를 통해 벡터 DB가 단순히 벡터 유사도만 계산하는 것이 아니라, 구조화된 조건과 의미 검색을 결합하여 정교한 결과를 도출한다는 사실을 깨달았다.

헷갈렸던 점#

처음에는 where와 query_texts가 중복된 것처럼 보여 혼란스러웠습니다. 하지만 핵심은 두 단계의 필터링 과정이라는 점이었습니다. where는 메타데이터로 후보를 좁히고, query_texts는 남은 후보 안에서 의미적으로 가장 가까운 문서를 찾는 역할을 한다는 점을 이해하는 데 시간이 걸렸습니다.

정리된 이해#

where는 메타데이터 조건으로 후보 풀을 좁히고, query_texts는 남은 후보들 사이에서 의미적으로 가장 가까운 문서를 찾는 두 단계 필터링 과정입니다. where가 없으면 전체 DB에서 검색하고, query_texts가 없으면 메타데이터 조건에만 맞는 빈약한 결과가 나오므로 둘 다 필요합니다.

coll.add(

    ],
    metadatas=[
        {"lang": "python", "level": "beginner", "version": 3.19},
        {"lang": "java", "level": "advanced"}
    ]

총평#

오늘 오후 전체에서 배운 것#

JWT는 로그인 자체를 처리하는 것이 아니라, 이후 인증된 상태임을 증명하기 위해 Authorization 헤더에 토큰을 실어 재검증을 받아야 한다는 흐름을 확인했습니다. RAG와 Vector DB에서 모델 재훈련이 아닌 기존 문서를 의미적으로 검색해주는 통로라는 점을 핵심으로 이해했으며, where 메타데이터 필터와 query_texts 의미 검색이 결합하여 정교한 결과를 도출한다는 사실도 정리했습니다.

다음에 조심할 것#

오늘은 JWT가 로그인을 처리하는 것이 아니라, 이후 인증 상태를 증명하는 토큰임을 명확히 했다. 또한 Vector DB가 단순히 벡터 유사도 계산에 그치지 않고, where와 query_texts를 결합해 의미 검색과 메타데이터 필터링을 정교하게 수행한다는 점을 이해했다. 다음에는 인증 흐름에서 토큰이 Authorization 헤더에 올바르게 실리는지, 그리고 벡터 검색 시 메타데이터 필터와 의미 검색이 어떻게 상호작용하는지 반드시 확인할 것이다.

다음 복습 주제#

JWT 인증 흐름에서 토큰이 브라우저와 서버 사이에서 어떻게 주고받으며 유효성을 검증하는지, 그리고 sessionStorage를 활용한 상태 관리의 구체적인 구현 방법을 다시 한 번 점검해 볼 필요가 있다.

RAG와 Vector DB의 핵심 개념인 ‘의미적 검색’과 ‘ID 기반 조회’의 차이를 명확히 이해하기 위해, 벡터가 단순히 숫자 배열이 아니라 문맥을 담은 의미 표현임을 재정의하고, get()과 query() 메서드가 어떻게 다른 목적을 수행하는지 비교 정리해야 한다.

Vector DB에서 where 조건과 query_texts를 활용한 두 단계 필터링 과정의 작동 원리를 정확히 파악하여, 구조화된 메타데이터 필터링이 의미 검색 결과에 어떻게 영향을 미치는지 시뮬레이션해 볼 수 있는 연습을 이어가야 한다.
