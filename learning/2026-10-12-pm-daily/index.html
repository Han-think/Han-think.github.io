1. 영상 프레임 추출과 로컬 자동 후보 수집 workflow#

무엇을 배웠나#

영상 프레임 추출 과정에서 수동 저장과 자동 모델 검출 사이에서 균형을 잡는 것이 데이터 다양성을 확보하는 핵심임을 깨달았습니다. 단순히 일정 간격으로 프레임을 캡처하는 것만으로는 의도치 않은 편향이 발생할 위험이 있어, 원본 영상을 기준으로 한 후보 수집 후 사람이 직접 검수하는 워크플로우가 필요하다고 판단했습니다. 또한 저장 해상도와 미리보기 해상도를 분리하여 관리하면 원본 변형을 최소화하면서도 효율적인 데이터 전처리가 가능하다는 점을 이해하게 되었습니다.

헷갈렸던 점#

수동 저장 방식은 프레임 선택에 대한 통제력을 주지만, 영상 전체를 일일이 확인해야 해 시간이 많이 걸리는 단점이 있었습니다. 반면 자동 추출은 시간 간격 설정에 따라 원하는 프레임이 실제로 캡처되지 않아 데이터가 편중될 위험이 있어 균형 잡힌 접근이 필요했습니다. 특히 모델이 이미 잘 아는 대상만 수집하게 되면 학습 데이터의 다양성이 떨어져 새로운 대상 탐지에 취약해질 수 있다는 점이 가장 큰 우려였습니다.

정리된 이해#

영상 속 모든 프레임을 일정 간격으로 추출하면, 모델이 이미 잘 아는 대상만 편향적으로 수집되는 것을 방지할 수 있어 데이터의 다양성을 확보하는 데 유리하다. 다만 실제 저장 간격이 영상의 FPS와 정확히 맞지 않을 경우 의도치 않은 시간 간격 차이가 발생할 수 있으므로, 이후 사람에 의한 검수 과정을 통해 오탐과 미탐을 걸러내는 것이 필수적이다. 따라서 자동으로 후보를 먼저 확보한 뒤, 사람이 직접 라벨링을 검토하는 워크플로우가 좋은 학습 데이터를 만드는 핵심적인 방법이다.

# 영상 프레임 추출 및 자동 후보 수집을 위한 핵심 로직

import cv2
import os
from pathlib import Path

def extract_frames_auto(video_path, output_dir, interval_sec=1.0):
    """
    주어진 영상에서 일정 시간 간격으로 원본 해상도 프레임을 추출합니다.

    Args:
        video_path (str): 입력 영상 경로
        output_dir (str): 저장할 디렉토리 경로
        interval_sec (float): 프레임 추출 간격(초)
    """
    cap = cv2.VideoCapture(video_path)
    if not cap.isOpened():
        print(f"Error: Cannot open video {video_path}")
        return

    # 영상 정보 가져오기
    fps = cap.get(cv2.CAP_PROP_FPS)
    frame_interval = int(fps * interval_sec)  # 초 단위를 프레임 수로 변환

    os.makedirs(output_dir, exist_ok=True)
    saved_count = 0
    frame_count = 0

    while True:
        ret, frame = cap.read()
        if not ret:
            break

        # 간격에 맞는 프레임만 저장 (원본 해상도 유지)
        if frame_count % frame_interval == 0:
            filename = os.path.join(output_dir, f"frame_{saved_count:04d}.jpg")
            cv2.imwrite(filename, frame)  # 원본 품질로 저장
            saved_count += 1

        frame_count += 1

    cap.release()
    print(f"Extracted {saved_count} frames from {video_path}")

# 사용 예시

2. YOLO Detection/Segmentation 분리 학습 핵심 정리#

무엇을 배웠나#

YOLO 모델 선택과 라벨 형태를 반드시 매칭해야 하며, data.yaml의 클래스 정의가 모델 입력과 일치해야 한다. Detection은 박스(BBox), Segmentation은 폴리곤/마스크 라벨을 사용하며, 사전학습 weight도 detect와 seg 버전이 따로 존재한다. epochs나 batch 같은 하이퍼파라미터는 장치 환경에 따라 학습 속도와 안정성에 직접적인 영향을 주므로, 내 XPU 환경에서는 값을 조정하는 것이 중요하다.

헷갈렸던 점#

가장 큰 혼란은 라벨 형태(박스 vs 폴리곤)와 가중치 종류(detect vs seg)가 서로 다른 모델에 적용될 경우 학습이 꼬일 수 있다는 점이었습니다. 특히 mouse와 같은 세부 카테고리가 섞이면 클래스 수가 어떻게 변하는지, 기존 사전학습 weight와 호환되는지 감조차 잡히지 않았습니다. 결국 핵심은 내가 가진 라벨 형태에 정확히 맞는 모델과 task를 매칭하는 것이 무엇보다 중요하다는 점을 깨닫게 되었습니다.

정리된 이해#

YOLO Detection과 Segmentation은 라벨 형식(박스 vs 폴리곤)과 가중치 종류가 다르므로, 사용 중인 데이터 형태에 맞는 모델을 정확히 매칭하는 것이 가장 중요하다. data.yaml의 클래스 정의 순서와 개수는 모델 입력과 반드시 일맞춰야 학습이 올바르게 진행된다. 또한 epochs, batch, workers 등 하이퍼파라미터는 사용자의 장치 환경(CUDA 등)에 따라 학습 속도와 안정성에 직접적인 영향을 미치므로 적절히 조정해야 한다.

3. 웹캠 테스트에서 모델 성능 검증의 함정#

무엇을 배웠나#

모델이 화면에 박스를 그리는 것만으로는 성능 검증이 되지 않는다는 점을 명확히 깨달았습니다. 단순히 탐지가 이루어졌는지 확인하는 것보다, model.names를 통해 클래스 매핑을 정확히 확인해야 모델이 무엇을 예측했는지 알 수 있습니다. 또한 best.pt와 last.pt의 차이를 이해하고, 다양한 조명과 배경 조건에서 모델이 robust하게 작동하는지 검증하는 것이 중요하다는 점을 배웠습니다.

헷갈렸던 점#

처음에는 모델이 영상에 박스를 그려주면 “아, 학습된 거구나” 하고 쉽게 판단하려 했습니다. 하지만 ‘박스가 뜬다 = 성능이 검증됐다’는 등식이 성립하지 않는다는 점이 가장 큰 혼란이었습니다. 특히 classes=[0, 1] 파라미터가 무엇을 의미하는지, 그리고 COCO 사전학습 모델의 숫자와 동일하다고 가정하면 안 된다는 점은 제 머릿속에 명확한 매핑을 만들기 어려웠습니다. “모델이 mouse를 예측했다"는 사실만으로 그 예측이 정확한 것인지, 아니면 클래스 ID 혼동 때문에 그런 것인지 구별하는 것이 쉽지 않았죠.

정리된 이해#

웹캠 화면에 박스가 그려진다고 해서 모델이 다양한 현장 조건에서 검증된 성능을 보장한 것은 아닙니다. 모델이 예측한 클래스 라벨을 확인하려면 model.names나 results[0].names를 반드시 확인해야 합니다. 또한, 학습된 모델의 성능과 신뢰도를 판단할 때는 best.pt와 last.pt의 차이를 명확히 구분하는 것이 중요합니다.

4. 데이터 정리와 Git 경계: 중복과 재현성의 구분#

무엇을 배웠나#

SHA-256 해시가 같다는 것이 픽셀 단위의 완전 identical를 의미한다는 점을 깨닫고, 화면이 같아도 시간이 흐르면 해시가 달라진다는 점에 충격을 받았다. 단순히 중복을 제거해 용량을 줄이는 것보다, 원본 영상을 보존하면서 후보 데이터만 선별하고 annotation된 dataset으로 단계적으로 관리하는 것이 재현성과 검증의 관점에서 중요하다는 점을 이해했다. 특히 .gitignore로 데이터를 숨기는 것과 실제 파일 관리는 별개이며, 과거 커밋 이력이 자동으로 사라지지 않는다는 점은 데이터 관리에서의 중요한 경계가 되었다.

헷갈렸던 점#

SHA-256 해시가 같다는 것이 픽셀 단위의 완전 identical를 의미한다는 점과, 이웃한 영상 프레임이 시간이 조금만 흘러도 해시가 완전히 달라질 수 있다는 점 사이에서 ‘화면이 똑같을 수 있다’는 직관적 이해와 충돌했던 점이 가장 헷갈렸습니다. 또한 best.pt 파일명 하나로 여러 학습 run의 결과를 식별하기 어렵다는 점과, 파일명을 통해 학습의 출처를 한눈에 파악할 수 없다는 점에서 메타데이터 관리의 중요성을 새롭게 인식하게 되었습니다.

정리된 이해#

SHA-256 해시가 같다는 것은 픽셀 단위의 완전 identical를 의미하지만, 화면이 똑같다는 뜻은 아니므로 데이터 삭제 시 재현성과 검증 가능성을 우선해야 한다.

완전 일치와 지각적 유사성을 구분하여 원본 영상을 보존하면서 후보 데이터만 선별하고 annotation된 dataset으로 단계적으로 관리하는 것이 중요하다. 특히 .gitignore로 데이터를 숨기는 것과 실제 파일 관리는 별개이며, 과거 커밋 이력이 자동으로 사라지지 않는다는 점은 중요한 경계점이다.

import hashlib
from pathlib import Path

def find_and_remove_duplicates(folder_path):
    folder = Path(folder_path)
    hashes = {}  # 해시 -> [파일경로 리스트]

    # 1. 모든 이미지 파일 순회하며 SHA-256 해시 계산
    for img_path in folder.rglob("*.jpg"):  # 확장자에 맞게 조정
        with open(img_path, 'rb') as f:
            file_hash = hashlib.sha256(f.read()).hexdigest()

        if file_hash not in hashes:
            hashes[file_hash] = []
        hashes[file_hash].append(img_path)

    removed_count = 0
    # 2. 중복된 해시를 가진 파일들 처리
    for file_hash, paths in hashes.items():
        if len(paths) > 1:
            # 첫 번째 파일은 보존하고, 나머지는 삭제
            # (라벨 파일도 동일 논리로 삭제한다고 가정)
            keep_path = paths[0]
            for dup_path in paths[1:]:
                dup_path.unlink()  # 파일 삭제
                removed_count += 1
                print(f"Removed duplicate: {dup_path}")

    return removed_count

# 실행 예시
if __name__ == "__main__":
    count = find_and_remove_duplicates("dataset/mouse2/train")
    print(f"\nTotal files removed: {count}")

5. Docker Desktop과 WSL2의 실제 관계와 명령어 흐름 정리#

무엇을 배웠나#

Docker Desktop과 WSL2는 별개의 개념이며, Docker Desktop은 자체적으로 docker-desktop이라는 WSL 배포판을 생성하지만 사용자가 설치한 Ubuntu와는 역할이 다르다. 주요 명령어인 search, pull, run의 용도와 실행 흐름을 명확히 이해하게 되었다.

헷갈렸던 점#

Docker Desktop 설치 시 WSL2 백엔드와 사용자가 별도로 다운로드한 Ubuntu 배포판이 같은 것인지 구분되지 않아 혼란스러웠다.

docker images, docker search, docker pull, docker run 등 명령어들이 각각 다른 기능을 수행한다는 점에서, 검색과 다운로드, 실행을 하나의 흐름으로 연결하기 어려웠다.

Docker Image는 컨테러너를 실행하는 청사진이고, Container는 이를 실제로 실행한 격리된 인스턴스이며, Docker Desktop은 Windows/Mac에서 Engine을 구동하게 해주는 GUI 프로그램이라는 점에서 WSL2와 사용자 Ubuntu의 역할 차이를 명확히 구분해야 했다.

정리된 이해#

Docker Desktop은 Windows 시스템 위에 WSL2라는 리눅스 환경을 구축하여 Docker Engine을 실행하게 되며, 이때 사용자가 별도로 설치한 Ubuntu와는 목적과 역할이 다르다. 이미지 검색(docker search)은 원격 저장소에서 후보를 찾는 조회 명령이며, 실제 다운로드(docker pull)와 실행(docker run)은 별도의 단계로 나뉘어 수행된다.

다음에 조심할 것#

  1. YOLO 모델과 라벨 형태를 반드시 매치하고, data.yaml 클래스 정의가 입력과 일치하는지 확인해 실수 없는 학습을 진행한다.
  2. 단순히 탐지가 되었는지 확인하기보다 model.names로 클래스를 정확히 매핑하고, 다양한 환경에서 모델이 robust하게 동작하는지 검증하여 실제 성능을 판단한다.
  3. 데이터는 SHA-256 해시로 식별하되, 화면이 같아도 시간이 흐르면 해시가 달라질 수 있음을 인지해 원본 영상을 보존하면서 후보 데이터만 단계적으로 관리한다.

다음 복습 주제#

  • YOLO 모델 구조와 라벨링 포맷(박스/폴리곤)의 필수 매칭 규칙, 그리고 데이터 증강 시 클래스 정의와 weight 버전(detect/seg) 관리의 중요성을 재정립한다.
  • Docker Desktop과 WSL2의 독립적인 아키텍처 차이점을 명확히 이해하고, docker-desktop 배포판과의 상호작용을 통해 명령어 흐름(pull, run)을 안정적으로 제어하는 방법을 숙지한다.
  • 영상 데이터 관리에서 SHA-256 해시 기반의 완전 identical 판별 한계와, 시간 경과에 따른 파일 변동 추적의 필요성을 인식하여, 원본 보존과 후보 선별을 분리한 단계적 데이터 관리의 틀을 구축한다.
