1. LangChain Agent의 도구 판단 및 인자 구성 과정#

무엇을 배웠나#

LangChain Agent는 LLM이 질문의 의도를 파악해 적절한 도구를 선택하고 인자를 구성하는 ‘판단력 있는 실행자’ 역할을 수행합니다. 핵심은 LLM이 도구 사용을 결정하고, 실제 연산이나 검색 등 구체적인 작업은 Tool이 담당한다는 책임 분담 구조입니다. 오늘 혼란스러웠던 함수 구현 오류와 흐름의 주체 전환을 이해하며, LLM과 Tool이 협업하는 시나리오를 자연스럽게 파악할 수 있었습니다.

헷갈렸던 점#

가장 큰 혼란은 도구의 기능과 인자에 대한 부분이었습니다. 어제 작성한 코드에서 모든 함수가 a * b로 되어 있어, 이것이 정말 더하기 함수인지 나누기 함수인지 기능에 대한 의문이 들었습니다. 또한 LLM이 단순히 답을 주는 것을 넘어, 어떤 도구를 쓸지 판단하고 인자를 결정하는 과정으로 주체가 이동한다는 흐름이 처음에는 복잡하게 느껴졌습니다.

정리된 이해#

LangChain Agent는 LLM이 질문의 의도를 파악하여 적절한 도구를 선택하고 인자를 구성한 뒤, 도구 실행 결과를 받아 최종 답을 제시하는 ‘판단력 있는 실행자’ 구조입니다. 핵심은 LLM이 판단과 계획을 담당하고, Tool이 실제 연산을 수행한다는 책임 분담에 있습니다. 이를 통해 단순한 텍스트 완성 기능을 넘어 실질적인 계산이나 검색 등 다양한 외부 작업을 수행할 수 있게 됩니다.

# LangChain Agent Tool Call Flow Example

from langchain.agents import initialize_agent, Tool
from langchain.tools.tool import Tool as ToolClass
from langchain_openai import ChatOpenAI
from langchain.schema import SystemMessage

# 1. 도구(Tool) 정의: 실제 연산 기능을 수행
def plus(a: int, b: int) -> int:
    return a + b

def minus(a: int, b: int) -> int:
    return a - b

def divide(a: int, b: int) -> float:
    if b == 0:
        raise ValueError("0으로 나눌 수 없습니다.")
    return a / b

# 각 도구의 메타데이터 정의 (LLM이 인자를 이해하도록 함)
tools = [
    Tool(
        name="plus",
        func=plus,
        description="두 숫자를 더합니다. 인자는 정수여야 합니다."
    ),
    Tool(
        name="minus",
        func=minus,
        description="첫 번째 숫자에서 두 번째 숫자를 뺍니다."
    ),
    Tool(
        name="divide",
        func=divide,
        description="첫 번째 숫자를 두 번째 숫자로 나눕니다. 0으로 나누면 오류가 납니다."
    )
]

# 2. LLM(대형 언어 모델) 초기화
llm = ChatOpenAI(model_name="gpt-4o-mini", temperature=0)

# 3. Agent 초기화: LLM + Tool 설정
agent = initialize_agent(
    tools,
    llm,
    agent_type="zero-shot-react-description",
    verbose=True
)

# 4. 질문 실행: "15와 7의 차이는?"
print("--- Question: '15와 7의 차이는?' ---")
result = agent.invoke({"input": "15와 7의 차이는?"})
print(f"Final Answer: {result['output']}\n")

# 5. 질문 실행: "20을 4로 나누면?"
print("--- Question: '20을 4로 나누면?' ---")
result = agent.invoke({"input": "20을 4로 나누면?"})
print(f"Final Answer: {result['output']}\n")

# 6. 질문 실행: "10과 5를 더한 후 3을 빼면?"
print("--- Question: '10과 5를 더한 후 3을 빼면?' ---")
result = agent.invoke({"input": "10과 5를 더한 후 3을 빼면?"})
print(f"Final Answer: {result['output']}")

2. LLM Agent와 Tool의 역할 분리를 통한 FastAPI 웹 서비스 구축#

무엇을 배웠나#

LLM에게 직접 계산하게 하는 것이 아니라, LLM이 판단하고 Tool이 실제 작업을 수행하는 역할 분리가 핵심임을 깨달았다. 단순히 계산을 빠르게 하려는 목적보다는, 자연어 입력에 대한 Agent의 도구 선택 및 orchestration 흐름을 이해하는 것이 실습의 본질이었다. FastAPI를 통해 웹 요청이 LLM 판단과 Tool 실행으로 이어지는 전체 과정을 직관적으로 경험할 수 있었다.

헷갈렸던 점#

LLM이 단순한 덧셈 같은 기본 산술 연산을 직접 수행하는 것보다, Agent와 Tool 구조를 통해 자연어 입력을 분석하고 적절한 도구를 선택하게 하는 전체 orchestration 흐름을 이해하는 것이 실습의 핵심 목적임을 직관적으로 느꼈다.

단순 계산 서비스의 경우 컴퓨터가 직접 계산하는 것이 압도적으로 빠르고 정확하므로, 이번 실습의 본질은 계산기의 효율성이 아니라 LLM에게 도구를 사용하게 하여 자연어 입력을 분석하고 Tool을 실행하는 역할 분리의 전체 과정임을 깨달았다.

정리된 이해#

LLM에게 도구를 사용하게 하는 전체 orchestration 흐름을 이해하는 것이 실습의 핵심이며, Agent는 판단하고 Tool은 실제 작업을 수행하는 역할 분담 구조를 가졌다. 단순 계산이 목적이라면 직접 Python 연산이 빠르지만, 자연어 기반의 복합 요청이나 Tool 선택이 필요한 상황에서는 LLM이 도구를 활용해 추론하는 과정이 의미가 있다.

# agent_service.py (Agent 실행 감싸기)
def calc_tool(msg: str):
    # LLM이 판단하여 Tool 선택 및 실행
    return agent_executor.invoke({"input": msg})

# main.py (FastAPI 웹 서비스 연결)
@app.post("/calc")
async def calculate(request: Request):
    form = await request.form()
    user_msg = form.get("msg", "")

    # 자연어 프롬프트 생성 후 Agent 호출
    result = calc_tool(user_msg)
    return {"response": result["output"]}

3. lmstudio agent service adaptation 이해하기#

무엇을 배웠나#

핵심은 ‘Provider 교체가 전체 구조를 흔드는가’에 대한 고민이었지만, 결론은 ‘구조는 그대로 connector만 교체하면 된다’였습니다. ChatOllama를 ChatOpenAI로 바꾸는 것만으로도 LangChain 프레임워크 자체를 수정하지 않고 내 환경에 맞게 변환할 수 있었습니다. 이를 통해 강의 의도는 보존하면서 실제 local LLM 환경을 실용적으로 적용할 수 있다는 확신을 얻었습니다.

헷갈렸던 점#

처음에는 provider 교체가 전체 코드 구조를 흔드는 것 아닐까 걱정했습니다. 특히 base_url과 api_key를 직접 지정해야 한다는 점이 낯설었고, 표준 사용법인지 의문이 들었습니다. 그러나 핵심은 구조 자체를 바꾸지 않고 connector 부분만 교체하면 된다는 점이 가장 크게 와닿았습니다.

정리된 이해#

강사님의 ChatOllama 구조를 유지하면서, 환경 차이로 인해 ChatOpenAI로 모델 연결 부분을 교체하는 방식으로 코드를 변환했습니다. 핵심 파일인 main.py, agent_service.py, view/chat.html는 수정하지 않고, 모델 인스턴스 생성 부분만 교체하여 LangChain 프레임워크의 구조적 의도를 그대로 살렸습니다. 이를 통해 provider 변경이 전체 리팩토링을 요구하는 것이 아니라, ‘connector’ 수준에서의 교체로 충분하다는 점을 실감하며 수업을 진행할 수 있었습니다.

# agent_service.py - Provider 교체 예시

from langchain_openai import ChatOpenAI  # 강사님: ChatOllama 사용
from langchain_community.chat_models import ChatOllama

# --- 강사님의 구조 ---
# model = ChatOllama(model="llama2", temperature=0.7)

# --- 변환된 내 환경 구조 ---
model = ChatOpenAI(
    model_name="local-model",  # LM Studio에 연결할 모델명
    openai_api_key="sk-...",   # LM Studio용 가짜 키 (필수 항목)
    openai_api_base="http://localhost:1234/v1",  # LM Studio 기본 주소
    temperature=0.7
)

4. LLM 스트리밍과 HTTP 연결 고리 이해하기#

무엇을 배웠나#

LLM 스트리밍과 HTTP 스트리밍을 연결하는 핵심은 yield를 통해 청크를 전달한 뒤, FastAPI의 StreamingResponse가 이를 실시간 HTTP 응답으로 변환한다는 점이다. 이전 챕터에서 이미 StreamingResponse 패턴을 사용했으므로, agent_service에서도 동일한 흐름으로 LLM의 토큰이 브라우저까지 도달하도록 구현하면 된다. 특히 Python 서버와 브라우저 클라이언트 사이에서 ReadableStream, TextDecoder 같은 기술들이 어떻게 데이터를 주고받으며 실시간 UI로 렌더링되는지 이해하는 것이 다음 단계의 핵심이다.

헷갈렸던 점#

LLM이 생성한 토큰이 콘솔에만 출력되어 HTTP 응답으로 전달되지 않아, 브라우저로 실시간 데이터가 흐르는 전체적인 연결 고리가 불분명했습니다.

특히 Python 서버와 브라우저 클라이언트 사이에서 generator yield가 어떻게 StreamingResponse를 거쳐 ReadableStream로 변환되고 처리되는지, 그리고 그 과정에서 markdown-it 같은 라이브러리가 어떻게 UI에 렌더링되는지에 대한 메커니즘이 명확하지 않았습니다.

정리된 이해#

LLM이 생성한 토큰 청크를 yield로 유지하면서 FastAPI의 StreamingResponse를 통해 HTTP 스트리밍으로 변환하면, 브라우저 측에서 ReadableStream과 TextDecoder을 사용해 실시간으로 UI에 렌더링할 수 있다.

# Python 서버 side: LLM 청크를 받아 StreamingResponse로 변환
from fastapi.responses import StreamingResponse

def stream_chat_response():
    def generate():
        # LLM으로부터 토큰(chunk) 단위로 yield
        for token in llm.stream_tokens():
            yield token  # FastAPI가 이 제너레이터를 감싸서 HTTP 스트리밍으로 변환

    return StreamingResponse(generate(), media_type="text/event-stream")

총평#

오늘 오전 전체에서 배운 것#

LangChain Agent는 LLM이 질문의 의도를 파악해 도구를 선택하고 인자를 구성하는 ‘판단력 있는 실행자’ 역할을 수행하며, 실제 연산이나 검색은 Tool이 담당하는 책임 분담 구조를 통해 협업한다. 또한, FastAPI 웹 서비스를 구축할 때 LLM에게 직접 계산을 맡기기보다는 LLM의 판단과 Tool의 실제 작업 수행으로 역할이 분리되어야 한다는 점을 명확히 이해했다. 마지막으로 ChatOllama와 같은 Provider 교체를 통해 LangChain 프레임워크 자체를 수정하지 않고 local LLM 환경을 유연하게 적용할 수 있다는 확신을 얻었다.

다음에 조심할 것#

LLM이 도구 선택에 실패하거나 인자가 잘못 구성되었을 때, 즉시 에러를 확인하고 프롬프트 엔지니어링을 통해 의도를 명확히 재지정하는 습관을 들일 것이다. 또한 Tool 실행 전후의 상태를 로그로 남겨, LLM과 Tool 간 데이터 흐름이 예상대로 진행되는지 디버깅하며 점검하는 과정을 반드시 거칠 것이다. 마지막으로 Provider 교체 시 전체 코드를 수정하는 수고로움을 피하기 위해, ChatOllama와 같은 래퍼 클래스를 활용해 인터페이스만 교체하면 된다는 원칙을 기억하고 실전 적용에 임할 것이다.

다음 복습 주제#

LangChain Agent에서 LLM이 도구를 선택하고 인자를 구성하는 ‘판단력’과 Tool이 실제 작업을 수행하는 ‘역할 분리의 핵심’을 확실히 이해했다.

FastAPI 웹 서비스 구축 시, LLM 판단 흐름과 Tool 실행 흐름이 어떻게 연결되는지 전체적인 orchestration 과정을 직관적으로 파악했다는 점에 집중했다.

ChatOllama에서 ChatOpenAI로 Provider를 교체해도 LangChain 구조 자체를 수정하지 않고 유연하게 적용할 수 있다는 점, 그리고 LLM 스트리밍과 HTTP 스트리밍을 연결하는 yield와 StreamingResponse의 기술적 원리를 다음 단계 복습 대상으로 삼았다.
