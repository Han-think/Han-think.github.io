1. 기준 테이블 선택의 중요성: employees vs titles#

무엇을 배웠나#

SQL 작성에서 가장 중요한 것은 어떤 집합을 시작점으로 삼느냐이다. 문제 해결 과정에서 기준 테이블을 옮기며 쿼리가 달라지는 것을 경험하며, 단순히 문법에 집중하는 것보다 먼저 ‘내가 원하는 대상이 누구인가’를 정하고 기준 테이블을 잡는 것이 훨씬 중요하다는 점을 깨달았다. 특히 NULL 값이 발생하는 문제를 해결하기 위해 titles 테이블로 기준을 이동시킨 과정은, 결과의 정확성을 확보하기 위한 필수적인 선택이었다.

헷갈렸던 점#

JOIN 작성의 핵심은 ‘어떤 집합을 시작점으로 삼는가’에 있다. 처음에는 employees를 기준으로 했으나, 퇴사자 포함으로 인해 NULL 값이 발생해 쿼리가 꼬였다. 이를 해결하기 위해 기준 테이블을 titles로 이동시켜 현재 직책이 있는 사람만 조회하는 방식으로 전환했다. 또한, ‘현재 관리자’ 조건을 정확히 만족시키기 위해서는 dm.to_date = '9999-01-01' 필터를 반드시 붙여야 한다는 점을 간과하지 않아야 한다.

정리된 이해#

SQL 작성에서 가장 중요한 것은 문법이 아니라 **‘어떤 집합을 시작점으로 삼는가’**라는 점이다. 처음에는 employees 테이블을 기준으로 했으나, 퇴사자까지 포함돼 NULL 값이 발생해 기준을 titles로 이동시켰다. 이는 기준 테이블의 선택이 결과의 정확성을 결정짓는 핵심 요소임을 보여준다.

🟢 SQL JOIN 확장 및 기준 테이블 선택 고찰 (학습 요약)#

🔍 핵심 통찰: “기준 테이블의 선택이 쿼리의 성패를 가른다”#

SQL 작성에서 가장 중요한 것은 **‘어떤 집합을 시작점으로 삼는가’**입니다. 문제 해결 과정에서 employees 테이블을 기준으로 시작했다가 NULL 값 문제가 발생하고, 이를 해결하기 위해 titles 테이블로 기준을 이동시킨 경험은 SQL 작성의 로직보다 문법에만 집중했던 제 접근 방식의 한계를 보여주었습니다.

📊 기준 테이블 비교#

접근 방식 기준 테이블 특징
employees 기준 employees 퇴사자까지 포함돼 NULL 발생 가능
titles 현재값 기준 titles 현재 직책이 있는 사람으로 시작해 결과가 명확함

핵심 통찰: JOIN 문법도 중요하지만, 먼저 “내가 원하는 대상이 누구인가?“를 정하고 기준 테이블을 잡는 것이 훨씬 중요했습니다. 기준이 잘못잡이면 이후 JOIN이 정확해도 결과 의미가 틀어질 수 있습니다.

🛠️ 실습 예시#

문제 3: JOIN으로 부서·사원 조회#

SELECT e.emp_no, d.dept_name
FROM employees e
JOIN dept_emp de ON e.emp_no = de.emp_no
JOIN departments d ON de.dept_no = d.dept_no;

문제 4: 현재 관리자 정보 조회 (수정된 쿼리)#

SELECT e.emp_no, dm.dept_no, d.dept_name, dm.from_date, dm.to_date
FROM employees e
JOIN dept_manager dm ON e.emp_no = dm.emp_no
JOIN departments d ON dm.dept_no = d.dept_no
WHERE dm.to_date = '9999-01-01';

문제 5: 현재 직책 정보 조회 (서브쿼리 활용)#

SELECT e.emp_no, t.title, t.from_date, t.to_date
FROM employees e
JOIN titles t ON e.emp_no = t.emp_no
WHERE t.to_date = '9999-01-01';

2. FastAPI와 SQLAlchemy 데이터베이스 연결 이해하기#

무엇을 배웠나#

SQLAlchemy에서 engine, sessionmaker, session은 각각 DB 접속 관리, 세션 생성, 실제 데이터 작업 담당이라는 명확한 역할을 수행한다. engine은 항상 열려있는 ‘관리실장’ 역할이고, sessionmaker는 필요할 때마다 새 세션을 만들어주는 ‘공장’이며, session()은 데이터를 실제로 조회하거나 수정하는 ‘현장’이다. 이러한 계층 구조를 이해하면 DBeaver와 같은 GUI 툴과 코드 간의 연결 과정이 왜 복잡한지 합리적으로 설명할 수 있게 되었다.

헷갈렸던 점#

DBeaver 같은 GUI 툴에서는 아이디와 비밀번호만 입력하면 바로 연결되는 것과 달리, SQLAlchemy 코드에서 engine, sessionmaker, session 등 낯선 단어가 등장하고 각각의 역할이 겹쳐 혼란스러웠다.

가장 큰 난점은 왜 엔진 하나만으로 충분하지 않고 세션이 따로 필요한지 이해하기 어려웠는데, 강사님의 비유대로 매니저에게 금고를 요청해 사용한 뒤 반납하는 개념으로 정리하니 각 컴포넌트의 역할이 명확해졌다.

정리된 이해#

SQLAlchemy에서 engine은 데이터베이스 접속을 관리하고 유지하는 ‘관리실장’ 역할을 하며, sessionmaker는 엔진을 기반으로 세션을 생성하는 ‘공장’, 그리고 session()은 실제 데이터를 조회하거나 수정하는 ‘현장’이다. 사용이 끝난 후에는 close()를 통해 연결을 정리하고 자원을 반환해야 한다.

# FastAPI + SQLAlchemy + PyMySQL + MariaDB 연결 기본 예시

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from sqlalchemy.ext.declarative import declarative_base

# 1. 데이터베이스 URL 설정 (MariaDB의 경우 pymysql 드라이버 사용)
# 예: mysql+pymysql://사용자명:비밀번호@호스트명/데이터베이스명
SQLALCHEMY_DATABASE_URL = "mysql+pymysql://root:@localhost/mydatabase"

# 2. Engine 생성 (DB 접속 관리 및 유지)
engine = create_engine(
    SQLALCHEMY_DATABASE_URL,
    echo=True  # SQL 로그 출력 여부 (디버깅 시 유용)
)

# 3. SessionLocal 클래스 생성 (세션 팩토리/공장)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

# 4. Base 클래스 선언 (모델 기반 클래스)
Base = declarative_base()

# 5. DB 세션 의존성 함수 (FastAPI 등에서 사용)
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

3. 회원가입 화면 구조와 데이터 흐름#

무엇을 배웠나#

오늘은 HTML, JavaScript, FastAPI가 연동된 실제 서비스 구조를 처음으로 경험했다. 특히 jQuery로 값을 추출해 Axios에 전달하고, FastAPI가 이를 받아 DB에 저장하는 ‘데이터의 흐름’을 이해하는 데 집중했다. 무엇보다 echo=True 옵션으로 SQL 로그를 확인하고, 전체 과정이 ‘입력 → 전송 → 처리 → 저장 → 응답 → 표시’라는 하나의 루프 안에서 움직인다는 점이 가장 명확해졌다.

헷갈렸던 점#

가장 큰 혼란은 **‘값이 어떻게 서버로 전달되고 받아지는지’**에 대한 연결 고리였다. jQuery로 값을 가져와 Axios에 담아 전송하는데, 그 ‘param’이 FastAPI에서 어떤 형식으로 변환되어 DB에 저장되는지 알 수 없었다.

또 하나의 오해는 HTML, JavaScript, FastAPI의 역할 경계가 모호하다는 점이었다. HTML은 단순히 화면을 보여주는 것뿐만 아니라 JavaScript와 상호작용하며 데이터를 주고받는 주체였고, FastAPI는 이를 받아 비즈니스 로직을 처리하고 DB에 저장하는 ‘다리’ 역할을 한다는 사실을 구분하지 못해 전체 흐름이 어지러웠다.

정리된 이해#

오늘은 HTML, JavaScript, FastAPI, DB가 하나의 흐름으로 연결된 ‘실제 서비스’ 구조를 처음으로 경험했다. 특히 값이 브라우저에서 서버로, 그리고 DB로 어떻게 이동하는지 ‘연결 고리’를 파악하는 데 집중했으며, echo=True 옵션과 세션 관리 방식 등 구체적인 설정 포인트도 명확히 정리할 수 있었다.

🟢 초보자 시점, 학습자의 혼란#

오늘은 드디어 ‘실제 서비스’ 같은 구성을 보기 시작했다. HTML로 만든 화면에 자바스크립트가 값을 모아 Axios로 보내고, FastAPI가 그걸 받아 MariaDB에 저장한다. 각 파일이 제각각 역할을 하니 감이 안 잡혔다.

특히 jQuery로 값 가져오기, Axios로 parameter 전달하기, FastAPI의 StaticFiles와 RedirectResponse 조합 등등이 뒤죽박죽 섞여 있었다. “HTML은 화면이고, DB는 데이터고, 나머지는 무슨 역할이지?” 하는 질문이 꼬리에 꼬리를 물었다.

가장 혼란스러웠던 부분은 값이 어디서 오고 어디로 가는지의 연결 고리였다. jQuery로 뽑아온 값을 param에 담아 Axios.post를 날리는데, 그 ‘param’이 FastAPI에서 어떻게 받아서 DB에 넣는 거지? 하는 부분이었다.

📌 정리된 이해#

오늘 learned 가장 핵심적인 흐름은 **“브라우저 → API → DB → 응답”**이라는 선형적인 연결 고리였다.

  1. HTML: 사용자가 입력한 값을 화면에 표시하는 역할
  2. JavaScript (jQuery + Axios): 입력된 값을 서버로 전송하고, 서버의 응답을 받아 화면을 업데이트 하는 역할
  3. FastAPI: 클라이언트의 요청을 받아 비즈니스 로직을 처리하고 DB와 통신하는 ‘다리’ 역할
  4. MariaDB / SQLAlchemy: 실제 데이터를 저장하고 조회하는 저장소 역할

특히 echo=True 옵션이 SQL 로그를 출력한다는 점, 그리고 get_conn()으로 세션을 분리해 관리한다는 점이 인상 깊었다. 파일별로 보면 복잡하지만, 전체 흐름으로 보면 “입력 → 전송 → 처리 → 저장 → 응답 → 표시"라는 하나의 루프 안에서 움직인다는 생각이 들었다.

총평#

오늘 오후 전체에서 배운 것#

SQL 작성에서 가장 중요한 것은 어떤 집합을 시작점으로 삼느냐이며, 단순히 문법에 집중하기보다 먼저 ‘내가 원하는 대상이 누구인가’를 정하고 기준 테이블을 잡는 것이 핵심임을 깨달았다. FastAPI와 SQLAlchemy의 engine, sessionmaker, session이 각각 DB 접속 관리, 세션 생성, 실제 데이터 작업을 담당하는 명확한 역할을 수행한다는 계층 구조를 이해하여 코드의 흐름을 합리적으로 설명할 수 있게 되었다. HTML, JavaScript, FastAPI가 연동된 서비스에서 jQuery로 값을 추출해 Axios에 전달하고 FastAPI가 DB에 저장하는 ‘입력 → 전송 → 처리 → 저장 → 응답 → 표시’라는 데이터의 흐름을 경험하며, 실제 서비스 개발에서의 연결 과정의 복잡성을 이해하게 되었다.

다음에 조심할 것#

오늘 배운 핵심은 ‘기준 테이블 선택’과 ‘데이터 흐름 구조’였다. 기준을 잘못 잡으면 결과가 달라지므로, 원하는 대상을 먼저 정하고 테이블을 결정하는 것이 무엇보다 중요하다. 또한 HTML에서 FastAPI로 데이터를 전송할 때 jQuery와 Axios의 역할을 정확히 구분하여 연결하지 않으면 데이터가 제대로 전달되지 않으니, 요청 파라미터 매핑에 신중을 기해야 한다.

다음 복습 주제#

  1. SQL 쿼리 작성 시 단순히 문법이나 JOIN 순서에 앞서, ‘내가 정확히 무엇을 원하는 데이터인가’를 먼저 정의하고 그에 맞는 기준 테이블을 선정하는 전략적 사고가 무엇보다 중요하다는 점을 재확인해야 한다.

  2. FastAPI와 SQLAlchemy의 engine, sessionmaker, session 역할 분담을 명확히 이해한 뒤, 실제 서비스에서 HTML과 JavaScript가 어떻게 이 구조를 타고 데이터를 주고받는지 전체적인 흐름을 복습하여 디버깅 능력을 높여야 한다.

  3. 회원가입 화면 구현 과정에서 경험한 ‘입력 → 전송 → 처리 → 저장 → 응답 → 표시’의 데이터 루프가 왜 발생하는지, 그리고 echo=True 옵션을 통해 확인한 SQL 로그가 쿼리 성능 최적화에 어떻게 기여하는지 점검해 보아야 한다.
