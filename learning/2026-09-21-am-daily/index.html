1. PRIMARY KEY와 UPSERT의 연결 고리#

무엇을 배웠나#

PRIMARY KEY는 테이블당 하나라는 제약조건을 가지며, 컬럼이 하나뿐일 필요는 없고 여러 컬럼을 조합해 복합키로 설정할 수 있음을 깨달았다. ALTER TABLE 문을 사용해 기존 테이블에 키를 추가하는 과정은 DB 구조에 기능을 부착하는 듯한 낯설음이 있었지만, 문법 자체는 간단했다. UPSERT에서 ON DUPLICATE KEY UPDATE가 PRIMARY KEY가 실제로 설정되어 있어야만 중복 판정과 업데이트가 작동한다는 점을 실감하며, 키가 스위치 역할을 한다는 것을 체감할 수 있었다.

헷갈렸던 점#

  1. PRIMARY KEY가 테이블 생성 시점에 자동으로 생기는 줄 알았는데, ALTER TABLE을 통해 나중에 추가하는 과정을 겪으며 DB 구조를 수정하는 개념이 낯설었습니다.
  2. “테이블당 PK는 하나"라는 표현이 컬럼이 한 개여야 한다는 뜻으로 잘못 해석될 여지가 있어, 복합키가 존재한다는 사실을 모르고 있으면 오해하기 쉽습니다.
  3. ON DUPLICATE KEY UPDATE가 PRIMARY KEY가 실제로 설정되어 있어야만 작동한다는 점을 오늘 체감했으며, PK가 생기니 suddenly 동작하는 모습을 통해 이 키가 스위치 역할을 한다는 것을 실감했습니다.

정리된 이해#

PRIMARY KEY는 테이블당 단 하나 존재하지만, 그 구성은 단일 컬럼이든 여러 컬럼의 조합(복합키)이 될 수 있다. 키가 설정되어 있어야만 ON DUPLICATE KEY UPDATE와 같은 UPSERT 문법이 실제 중복 판정과 업데이트 기능을 수행할 수 있다. 테이블 구조를 변경할 때 ALTER TABLE 문을 사용해 기존 그릇에 제약조건을 부착하는 과정이 익숙하지 않을 수 있지만, 이는 DB 설계의 유연성을 높이는 중요한 과정이다.

-- 테이블 생성 시 PRIMARY KEY (단일 컬럼)
CREATE TABLE users (
    user_id INT PRIMARY KEY,
    username VARCHAR(50) NOT NULL
);

-- 테이블 생성 시 복합키 (Composite Key, 여러 컬럼 합쳐서 하나의 PK)
CREATE TABLE orders (
    order_id INT,
    user_id INT,
    product_name VARCHAR(100),
    PRIMARY KEY (order_id, user_id) -- 두 컬럼의 조합이 하나의 키가 됨
);

-- 기존 테이블에 PRIMARY KEY 추가 (ALTER TABLE)
ALTER TABLE products
ADD PRIMARY KEY (product_code);

-- UPSERT 연결 예시: PK가 있어야 ON DUPLICATE KEY UPDATE가 작동함
INSERT INTO users (user_id, username) VALUES (1, 'alice')
ON DUPLICATE KEY UPDATE username = 'alice_updated';

2. RDBMS 관계와 참조 무결성 이해하기#

무엇을 배웠나#

테이블 간의 관계는 단순히 그림상의 선이 아니라, SQL 문법으로 enforce되는 제약 조건임을 명확히 이해하게 되었다. 특히 참조 무결성이 자식 테이블이 부모 테이블을 바라볼 때, 실제 존재하는 값만 입력하도록 강제하여 데이터의 일관성을 지키는 ‘안전장치’ 역할을 한다는 점을 실감했다. 또한 ON DELETE CASCADE와 같은 삭제 옵션은 비즈니스 로직에 맞춰 신중하게 결정해야 하는 위험한 선택임을 깨닫게 되었다. 마지막으로 ERD의 식별/비식별 관계는 FK의 존재 여부가 아니라, 부모의 PK가 자식의 PK에 포함되는 구조적 차이임을 정확히 구분할 수 있게 되었다.

헷갈렸던 점#

테이블이 동시에 등장하면 어느 쪽이 부모인지, 자식인지 직관적으로 가늠하기 어려웠다.

부모를 삭제하면 자식이 자동으로 삭제된다는 개념은 이해했지만, 왜 기본적으로 부모 삭제가 차단되는지 ‘참조 무결성’의 논리를 실시간로 연결 짓기 힘들었다. “부모가 없는데 자식만 지워도 되는 거 아닌가?“라는 반문이 들었다.

자식 테이블이 부모를 바라볼 때, 부모에 실제로 존재하는 값만 입력하도록 강제하는 규칙임을 명확히 했다. FK는 단순한 주소가 아니라 무결성을 검사하는 제약 조건이며, ON DELETE CASCADE 같은 옵션은 비즈니스 로직에 맞춰 신중하게 결정해야 한다는 점을 이해했다.

정리된 이해#

RDBMS에서의 관계는 단순히 테이블 간의 연결 고리가 아니라, SQL 문법에 의해 enforce되는 참조 무결성 규칙이다. 부모 키를 참조하는 외래키(FK)는 자식 테이블이 존재하지 않는 부모 데이터를 삽입하거나 수정하는 것을 차단하여 데이터의 일관성을 보장한다. 또한, ON DELETE CASCADE와 같은 옵션은 비즈니스 로직에 맞춰 신중하게 선택해야 하며, 단순히 부모 삭제 시 자식도 자동 삭제되는 기능으로만 접근해서는 안 된다.

-- 참조 무결성 예시: 부모 테이블과 자식 테이블 생성
CREATE TABLE departments (
    department_id INT PRIMARY KEY,
    department_name VARCHAR(50)
);

CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    employee_name VARCHAR(50),
    department_id INT,
    -- 외래키(FK) 제약조건: departments 테이블의 department_id를 참조
    FOREIGN KEY (department_id) REFERENCES departments(department_id)
);

-- ON DELETE CASCADE 예시: 부모 행 삭제 시 자식 행도 자동 삭제
ALTER TABLE employees
ADD CONSTRAINT fk_dept_delete_cascade
FOREIGN KEY (department_id) REFERENCES departments(department_id)
ON DELETE CASCADE;

3. dept/emp 관계에서 서브쿼리의 핵심: PK-FK 연결 흐름#

무엇을 배웠나#

서브쿼리 실습을 위해 dept와 emp 테이블을 생성하고 데이터를 입력하는 과정은, 단순한 데이터 입력이 아니라 PK와 FK 관계를 통해 식별자를 이동시키는 ‘준비 운동’이었습니다. 직원 정보를 조회해 deptno를 추출한 뒤, 이를 이용해 dept 테이블에서 부서 이름을 확인하는 흐름이 서브쿼리의 핵심 구조임을 깨달았습니다. 특히 WHERE deptno = (서브쿼리)와 같은 구문이 가능한 이유는 두 테이블이 deptno라는 공통 열을 통해 참조 관계를 맺고 있기 때문입니다.

헷갈렸던 점#

처음에는 CREATE TABLE과 INSERT 같은 기초 데이터 입력 과정이 서브쿼리와 무슨 연관이 있는지 의아해했습니다. 하지만 deptno라는 식별자 열이 두 테이블에 모두 존재하고 한쪽이 다른쪽을 참조하는 관계(PK-FK)가 형성되어야만, 직원 정보를 통해 부서 이름을 조회할 수 있다는 사실을 깨닫고 이해가 되었습니다. 즉, 서브쿼리는 단순히 쿼리 안에 또 다른 쿼리가 들어가는 구조가 아니라, 테이블 간의 관계를 활용해 단계를 거쳐 원하는 데이터를 추출하는 과정 itself라는 점이 핵심적으로 와닿았습니다.

정리된 이해#

서브쿼리는 emp 테이블에서 직원 정보를 조회해 deptno를 추출한 뒤, 이를 통해 dept 테이블을 검색하여 부서 이름을 확인하는 식별자 이동 과정입니다. 이 과정에서 두 테이블 간의 PK-FK 관계가 선행되어야만 단계적인 데이터 참조가 가능하며, 이것이 서브쿼리의 핵심 구조가 됩니다. 또한, 문자형 날짜 데이터를 실제 날짜 형식으로 변환하는 STR_TO_DATE() 함수를 활용해 정확한 조건 검색을 수행할 수 있습니다.

-- 서브쿼리를 활용한 부서명 조회 예시
SELECT e.ename, d.dname
FROM emp e,
     dept d
WHERE e.deptno = d.deptno;

4. 한 번에 이해하는 서브쿼리의 논리#

무엇을 배웠나#

처음에는 괄호 안에 SELECT가 들어간 복잡한 문법에 압도되었지만, 안쪽 쿼리가 반환하는 결과값이 바깥 쿼리의 조건으로 사용된다는 핵심 원리를 이해하면서부터 서브쿼리의 역할을 명확히 할 수 있었다. JOIN은 두 테이블을 한 번에 연결해 데이터를 가져오는 방식인 반면, 서브쿼리는 ‘먼저 값을 구해서 다음 단계의 조건으로 던져주는’ 도구라는 구분감이 들었다. 이를 통해 문법적 차이뿐만 아니라 목적과 흐름이 다른 두 개념을 명확히 분리할 수 있게 되었다.

헷갈렸던 점#

처음에는 괄호 안에 SELECT가 포함된 문법을 한 줄로 읽기 어려워했으며, JOIN과의 차이점을 명확히 구분하지 못해 개념이 섞여 혼란스러웠다. 하지만 서브쿼리가 “안쪽 쿼리 결과를 바깥 쿼리의 조건으로 던져주는 도구"라는 점에 집중하니 문법의 차이가 목적이 다른 도구의 차이임을 이해할 수 있었다.

정리된 이해#

서브쿼리는 안쪽 쿼리의 결과가 바깥 쿼리의 조건으로 사용되는 구조이며, JOIN이 두 테이블을 동시에 연결해 데이터를 가져오는 방식과 달리 ‘먼저 값을 구해서 다음 단계에 전달하는 도구’로 이해하면 된다. 이번 예제에서 han의 부서 번호를 먼저 조회한 뒤, 그 결과를 이용해 부서 이름을 찾는 식으로 서브쿼리는 순차적인 데이터 추출 과정을 가능하게 한다.

-- 1) han의 부서 번호 찾기 (안쪽 SELECT)
SELECT deptno FROM emp WHERE ename = 'han';

-- 2) 부서 이름으로 조회 (바깥 SELECT + 서브쿼리)
SELECT deptname FROM dept WHERE deptno = (
    SELECT deptno FROM emp WHERE ename = 'han'
);

-- 참고: JOIN 방식으로 같은 결과 얻기
SELECT emp.ename, dept.deptname
FROM emp JOIN dept ON emp.deptno = dept.deptno
WHERE emp.ename = 'han';

총평#

오늘 오전 전체에서 배운 것#

PRIMARY KEY가 UPSERT의 스위치 역할을 하며, 복합키 설정을 통해 테이블 구조를 유연하게 설계할 수 있다는 점을 깨달았다. 또한 RDBMS에서 참조 무결성은 단순한 관계를 넘어 데이터 일관성을 보장하는 안전장치이며, ON DELETE CASCADE와 같은 옵션은 비즈니스 로직에 따라 신중히 결정해야 함을 이해했다. 마지막으로 서브쿼리는 바깥 쿼리의 조건으로 값을 던져주는 도구라는 논리를 파악해 JOIN과의 명확한 구분감을 갖게 되었다.

다음에 조심할 것#

  • UPSERT 시 PRIMARY KEY 누락 시 의도치 않은 레코드 생성이나 에러가 발생할 수 있으므로, INSERT 전 반드시 키 제약 조건이 정상 적용되었는지 확인하는 습관을 들일 것이다.
  • 서브쿼리 작성 시 JOIN과 혼동되지 않도록 ‘먼저 값을 구해 조건으로 던지는 흐름’을 머릿속에 그린 뒤, 실제 SQL을 작성하여 참조 무결성이 유지되는지 검증할 계획이다.

다음 복습 주제#

서브쿼리 실전 적용 및 최적화 전략 서브쿼리의 기본 논리를 익혔으니, 이제 실제 비즈니스 현장에서 효율적으로 활용하는 방법을 고민해 봐야 한다. 단순히 값을 추출하는 것을 넘어, 인덱스 활용과 성능 저하를 막기 위한 쿼리 튜닝 관점에서 서브쿼리와 JOIN의 차이를 명확히 구분하고, 상황에 맞는 최적의 방식을 선택하는 연습이 필요하다.

참조 무결성과 트랜잭션 관리 심화 ON DELETE CASCADE와 같은 옵션이 데이터 일관성을 어떻게 해치는지, 그리고 비즈니스 로직상 어떤 영향을 미치는지에 대한 깊은 이해가 필요하다. 단순히 제약 조건을 거는 것을 넘어, 삭제 시 연쇄 반응이 발생하는 파급 효과를 예측하고, 필요한 경우 애플리케이션 레인에서 적절히 처리해야 할 책임과 한계를 명확히 하는 트랜잭션 관리 능력을 기를 필요가 있다.

복합키와 인덱스 전략 수립 PRIMARY KEY와 UPSERT의 연결 고리를 통해 키의 중요성을 확인했지만, 실제 테이블 설계 시 복합키가 성능에 미치는 영향을 검증해 봐야 한다. 컬럼 조합에 따른 인덱스 생성 전략과 쿼리 최적화 기법을 공부하여, 키 설정이 단순히 제약 조건을 넘어 검색 속도와 데이터 무결성에 어떻게 기여하는지 실전 감각을 익혀야겠다.
