1. JWT 로그인 흐름과 sessionStorage 활용#

무엇을 배웠나#

로그인 과정에서 토큰을 sessionStorage에 저장하는 것이 단순히 데이터를 보관하는 것을 넘어, 인증된 요청으로 넘어가는 관문이라는 점을 명확히 이해할 수 있었다. 또한, 입력값 관리부터 서버 통신, 그리고 상태 이동까지 연계된 흐름을 한 번에 파악하는 것이 처음에는 혼란스러웠으나, 단계별로 나누어 정리하니 로그인의 전체적인 윤곽이 잡혔다. 앞으로는 토큰 저장 여부가 다음 단계 인증 가능 여부를 결정한다는 점을 기준으로 코드를 점검할 계획이다.

헷갈렸던 점#

처음에는 토큰이 단순히 ‘로그인 완료’ 신호 정도로만 생각해서, 서버 응답 후 어떤 행동을 해야 할지 막막했습니다. 특히 sessionStorage에 저장하는 과정이 로그인의 목적이 아니라, 이후 인증된 요청을 위한 준비 과정이라는 점을 구분하기 어려웠습니다. 결국 로그인이 단순히 아이디와 비밀번호를 보내는 행위가 아니라, 토큰을 보관하며 다음 단계로 넘어가는 ‘관문’임을 깨닫는 데 시간이 걸렸습니다.

정리된 이해#

로그인은 단순히 아이디와 비밀번호를 서버에 전송하는 과정을 넘어, 토큰을 sessionStorage에 저장하여 인증된 상태를 유지하는 관문입니다. 따라서 로그인 성공은 입력과 전송의 종료가 아니라, 다음 단계로 넘어가는 시작점이 됩니다.

// 1. 상태 관리 (입력값)
const [info, setInfo] = useState({id:'', pw:''});

// 2. 입력 처리
const inputVal = function(e){
    setInfo({
        ...info,
        [e.target.name]: e.target.value
    });
}

// 3. 로그인 함수 (핵심 흐름)
const handleLogin = async () => {
    const response = await axios.post('/login', info); // 서버에 전송

    if(response.success) { // 성공 시
        // 4. 토큰 저장 (sessionStorage)
        sessionStorage.setItem('token', response.data.token);
        sessionStorage.setItem('id', response.data.id);
    }
}

2. 게시판 목록 렌더링 논리 분리#

무엇을 배웠나#

복잡한 삼항연산자와 map이 섞여 있어 코드 흐름을 파악하기 어려웠지만, ‘빈 목록 여부’와 ‘데이터 렌더링’을 분리해서 생각하니 논리가 단순해졌습니다. 데이터가 없으면 메시지를 출력하고, 있으면 반복문을 통해 각 항목을 테이블에 채워주는 방식으로 접근하니 가독성이 크게 향상되었습니다. 앞으로는 조건문과 반복문을 별개로 먼저 확인한 뒤 최종적으로 결합하여 코드를 작성할 계획입니다.

헷갈렸던 점#

처음에는 코드가 촘촘히 들어차 있어 전체적인 흐름을 읽기 어려웠습니다. 특히 data.list.length === 0이라는 조건과 그 바로 뒤에 오는 .map()이 어떻게 연결되는지 감이 안 잡혔습니다.

핵심은 “데이터가 있는지 없는지"와 “있다면 어떻게 보여줄지"를 분리해서 생각하는 것입니다. 복잡한 식을 한 번에 풀려고 하지 말고, 조건문과 반복문을 쪼개서 읽으면 논리가 단순해집니다.

정리된 이해#

핵심은 데이터 존재 여부를 먼저 확인한 뒤, 조건에 따라 빈 목록 메시지나 리스트 렌더링 로직을 분리하여 처리하는 것입니다. data.list.length === 0이라는 조건과 .map() 함수는 서로 다른 단계(빈 체크 vs 반복 처리)로 구분하면 논리가 단순해집니다.

// 1. 먼저 조건 확인 (빈 목록 여부)
let row;
if (data.list.length === 0) {
  row = <tr><th colSpan={6}>작성된 글이 없습니다.</th></tr>;
} else {
  // 2. 데이터가 있다면 map으로 반복 처리
  row = data.list.map(item => (
    <tr key={item.idx}>
        <td>제목: {item.title}</td>
        <td>작성자: {item.author}</td>
        {/* 기타 td 채우기... */}
    </tr>
  ));
}

// 최종 렌더링
return <tbody>{row}</tbody>;

3. URL 파라미터로 전달되는 동적 라우팅의 원리#

무엇을 배웠나#

URL 경로에 포함된 [idx]는 단순한 화면 번호가 아니라, 서버에서 특정 데이터를 조회하는 고유 식별자 역할을 한다는 점을 깨달았습니다. Next.js의 동적 라우팅이 URL 변동을 감지해 params 객체로 값을 전달하고, 이를 기반으로 서버 측에서 데이터 조회를 수행한다는 흐름을 이해하게 되었습니다. 무엇보다 URL 경로 자체가 데이터 요청의 트리거가 된다는 개념 정리가 가장 큰 도움이 되었습니다.

헷갈렸던 점#

URL에 포함된 [idx]는 단순히 화면상의 순번이 아니라, 서버가 특정 데이터를 조회하는 데 사용되는 고유 식별자 역할을 한다는 점이 가장 혼란스러웠습니다.

특히 URL 경로의 변동이 서버에서 어떤 데이터를 가져올지 결정한다는 흐름이 복잡하게 느껴졌는데, URL path 변동 → params 추출 → server lookup이라는 중간 과정 없이 바로 데이터가 넘어오는 것으로 생각했던 것이 큰 오해였습니다.

정리된 이해#

URL 경로에 포함된 [idx]는 특정 게시물을 식별하는 고유 값이며, 사용자가 클릭하면 Next.js가 이 값을 추출해 서버에 전달하여 해당 데이터만을 조회한다.

// 1. 리스트 페이지에서 상세 페이지 이동 (링크 혹은 이동)
location.href = '/detail/' + data

총평#

오늘 오전 전체에서 배운 것#

JWT 로그인 흐름에서 sessionStorage가 단순한 데이터 보관을 넘어 인증 관문의 역할을 한다는 점을 명확히 이해했으며, 단계별로 나누어 코드의 전체적인 윤곽을 파악하는 중요성을 깨달았다. 또한 게시판 목록 렌더링 논리를 ‘빈 목록 여부’와 ‘데이터 렌더링’으로 분리하여 삼항연산자의 복잡함을 해소하고 가독성을 높이는 방법을 학습했다. 마지막으로 URL 파라미터를 통한 동적 라우팅이 고유 식별자를 서버에 전달하여 데이터 조회의 트리거가 된다는 원리를 이해하였다.

다음에 조심할 것#

오늘 학습한 내용을 바탕으로 다음에 코드를 작성할 때 유의해야 할 점은 다음과 같습니다.

먼저, JWT 인증 흐름에서 sessionStorage에 토큰을 저장하는 것은 단순히 보관하는 행위가 아니라, 이후 인증된 요청이 가능하게 하는 핵심 관문임을 명심하고 코드 검증을 진행해야 합니다. 또한, 게시판 목록과 같은 복잡한 화면 구성 시 ‘빈 목록 여부’와 ‘데이터 렌더링’ 논리를 분리하여 먼저 확인한 뒤 결합하는 방식으로 접근하면 코드의 가독성을 크게 높일 수 있습니다. 마지막으로 URL 파라미터를 활용한 동적 라우팅에서는 경로에 포함된 값이 단순히 화면 전환을 넘어 서버 측 데이터 조회의 필수 식별자 역할을 한다는 점을 항상 인지하여 실수를 방지해야 합니다.

다음 복습 주제#

다음에 복습할 주제#

JWT 인증 시스템에서 토큰 관리 전략을 재점검해야 한다. 현재 sessionStorage 활용이 인증 상태 유지와 요청 인터셉터 연결 고리로서 기능하는지, 혹은 보안 이슈가 있는지는 별도 검토가 필요하다. 또한, 조건부 렌더링 로직을 작성 시 ‘데이터 존재 여부’와 ‘UI 출력 방식’을 명확히 분리하여 삼항 연산자의 중첩을 최소화하는 연습을 이어갈 계획이다.

동적 라우팅에서 params 객체가 실제로 서버 요청 파라미터로 어떻게 매핑되는지, 그리고 경로 변환 시 데이터 페칭 로직이 올바르게 작동하는지 실제 API 호출 흐름을 통해 검증해 볼 필요가 있다.
