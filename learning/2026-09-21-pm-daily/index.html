1. 상관 서브쿼리의 핵심 이해#

무엇을 배웠나#

오늘은 dept와 emp 테이블 구조에 익숙해지는 데 집중했다. 특히 문제 5처럼 안쪽 쿼리가 바깥 행의 값을 참조하는 상관 서브쿼리 패턴을 이해하는 것이 가장 중요하다고 느꼈다. ‘값 하나면 =, 여러 개면 IN’이라는 단순한 규칙을 넘어, 쿼리의 의존 관계를 파악하는 사고가 필요하다는 점을 깨달았다.

헷갈렸던 점#

오전에 이어 오후에 sub_query.sql 문제 1~5를 풀었다. 전반적으로 “SELECT로 중간 결과를 먼저 뽑아보는 습관"은 잡혀 있었는데, 테이블이 dept와 emp로 바뀌니 컬럼 이름과 테이블 관계도 다시 머릿속에 그렸다는 점이 가장 큰 혼란이었다.

특히 문제 5(부서별 직원 수)가 앞선 문제들과 결이 달랐다. 이전 문제들은 “안쪽 쿼리가 값 하나를 반환하면 =를 쓰고, 여러 개면 IN을 쓴다"는 식의 패턴 매칭이었는데, 문제 5는 안쪽 쿼리가 바깥쪽 행의 값을 참조하는 구조가 되어버렸다. 어디서부터 손을 대야 할지 막막함을 느꼈다.

오늘 강사님의 피드백과 직접 실행해보며 확실히 잡힌 키워드들이다. 단일값 서브쿼리는 안쪽 쿼리가 하나의 값만 반환할 때 =를 쓰고, 다중행 서브쿼리는 여러 개의 값을 반환할 때 IN을 사용한다. 상관 서브쿼리의 핵심은 “안쪽 SELECT가 바깥 SELECT의 컬럼을 참조한다"는 점이며, 이는 매 행마다 다시 실행된다는 생각이 가장 중요하다.

정리된 이해#

서브쿼리는 반환되는 값의 개수에 따라 =나 IN을 사용하며, 안쪽 쿼리가 바깥 쿼리의 컬럼을 참조하는 ‘상관 서브쿼리’는 행마다 재실행된다는 점을 이해해야 한다.

-- 문제 1: 단일값 서브쿼리 패턴 (안쪽 쿼리가 하나의 값 반환)
SELECT empno, ename, sal
FROM emp
WHERE deptno = (
    SELECT deptno
    FROM dept
    WHERE dname = 'RESEARCH'
);

-- 문제 2: 다중행 서브쿼리 패턴 (안쪽 쿼리가 여러 값 반환)
SELECT empno, ename, sal
FROM emp
WHERE deptno IN (
    SELECT deptno
    FROM dept
    WHERE loc = 'DALLAS'
);

-- 문제 3: 단일값 서브쿼리 패턴 (급여 등급 비교)
SELECT empno, ename, sal, grade
FROM emp e, salgrade s
WHERE e.sal BETWEEN s.losal AND s.hisal
AND s.grade = (
    SELECT grade
    FROM salgrade
    WHERE losal <= 2000 AND hisal >= 2000
);

-- 문제 5: 상관 서브쿼리 패턴 (안쪽 쿼리가 바깥 행의 값을 참조)
SELECT e.ename, e.deptno, (
    SELECT COUNT(*)
    FROM emp mgr
    WHERE mgr.mgr = e.empno
) as sub_staff_count
FROM emp e;

2. JOIN 종류별 데이터 유지 전략: INNER·OUTER·CROSS 구분하기#

무엇을 배웠나#

JOIN을 이해할 때 가장 중요한 첫 단계는 연결 고리(Join Condition)를 먼저 확정하는 것이다. 이 한 줄이 정해지면, 이후 JOIN 종류는 “일치하지 않는 행을 어떻게 처리할 것인가"의 문제로 단순화된다. 특히 LEFT와 RIGHT OUTER JOIN은 이름만 보고 직관적으로 어떤 데이터가 남는지 파악하기 어려우나, ‘어느 쪽 데이터를 끝까지 유지할 것인가’라는 관점으로 전환하면 이해가 쉬워진다. CROSS JOIN은 조건 없이 모든 조합을 생성하는 Cartesian Product이므로, 실무에서는 자동 연결되는 컬럼이 의도치 않게 늘어나지 않을까 봐 USING이나 NATURAL JOIN 사용에 주의를 기울여야 한다.

헷갈렸던 점#

처음 JOIN을 배울 때와 비슷하게, 새로운 테이블 구조를 마주하니 ‘왼쪽’과 ‘오른쪽’의 기준이 다시 설렜다. 특히 LEFT와 RIGHT OUTER JOIN은 이름만 보고 직관적으로 어떤 데이터가 남는지 파악하기 어려웠다.

가장 중요한 첫 단계는 **연결 고리(Join Condition)**를 먼저 확정하는 것이다. 이 한 줄이 정해지면, 이후 JOIN 종류는 **“일치하지 않는 행을 어떻게 처리할 것인가”**의 문제로 단순화된다.

정리된 이해#

JOIN 연산은 연결 고리(Join Condition)를 먼저 확정한 뒤, 일치하지 않는 행을 어떻게 처리할 것인가에 따라 종류가 단순화된다. INNER JOIN은 양쪽 테이블에 모두 존재하는 행만 반환하고, LEFT·RIGHT OUTER JOIN은 각각 왼쪽 또는 오른쪽 테이블의 모든 행을 유지한다. CROSS JOIN은 조건 없이 두 테이블의 모든 경우의 수를 조합해 Cartesian Product를 생성한다.

SELECT e.ename, d.dname
FROM emp e JOIN dept d ON e.deptno = d.deptno;

SELECT e.ename, d.dname
FROM emp e LEFT OUTER JOIN dept d ON e.deptno = d.deptno;

SELECT e.ename, d.dname
FROM emp e RIGHT OUTER JOIN dept d ON e.deptno = d.deptno;

SELECT e.ename, d.dname
FROM emp e CROSS JOIN dept d;

3. SQL 합집합과 차집합 개념 정리#

무엇을 배웠나#

UNION은 SELECT문의 결과를 행 방향으로 이어 붙이는 합집합 연산이며, UNION ALL은 중복을 포함해 더 빠르게 처리할 수 있다. INTERSECT는 두 쿼리 결과에 공통으로 존재하는 값만 추출하는 교집합 연산이다. NOT IN은 첫 번째 결과에서 두 번째 결과에 포함되지 않는 값을 제거하여 차집합을 만드는 방식이다.

헷갈렸던 점#

UNION은 행을 이어 붙이는 수직 결합이고, JOIN은 열을 확장하는 가로 결합이라는 점이 가장 큰 차이였다.

INTERSECT는 두 결과에 모두 존재하는 값만 남기는 ‘교집합’ 개념이지만, 일반적인 JOIN의 등가조인과 목적이나 구조가 다르다는 점을 명확히 구분해야 했다.

정리된 이해#

UNION은 SELECT문의 결과를 행 방향으로 이어 붙여 세로로 긴 표를 만드는 반면, INTERSECT는 두 결과 집합에 공통으로 존재하는 값만 추출하고, NOT IN은 첫 번째 결과에서 두 번째 결과에 포함되지 않는 값을 제외하여 차집합을 만든다.

-- UNION: 중복 제거된 합집합 (행 추가)
SELECT deptno FROM dept
UNION
SELECT deptno FROM emp;

-- UNION ALL: 중복 포함된 합집합 (빠름)
SELECT deptno FROM dept
UNION ALL
SELECT deptno FROM emp;

-- INTERSECT: 교집합 (공통된 값만 남김)
SELECT deptno FROM dept
INTERSECT
SELECT deptno FROM emp;

-- NOT IN: 차집합 (첫 번째에서 두 번째에 없는 값 추출)
SELECT * FROM emp WHERE deptno NOT IN (SELECT deptno FROM dept);

4. auto_increment_primary_key의_연관성#

무엇을 배웠나#

AUTO_INCREMENT는 단순히 번호를 자동 생성하는 기능이 아니라, 반드시 PRIMARY KEY와 결합하여 식별자와 자동 증가 기능을 동시에 수행하는 속성입니다. MariaDB에서는 AUTO_INCREMENT 컬럼이 key/index로 지정되어 있어야 정상적으로 작동한다는 점이 초보자에게 반직관적으로 느껴질 수 있습니다. 이를 통해 데이터베이스 구조상 PK와 AI 속성이 결합해야 비로소 자동 번호 생성이 가능하다는 것을 명확히 이해할 수 있었습니다.

헷갈렸던 점#

AUTO_INCREMENT는 단순히 번호를 자동 생성하는 기능이 아니라, PRIMARY KEY와 결합하여 행을 식별하고 값을 자동으로 증가시키는 속성입니다.

MariaDB에서는 AUTO_INCREMENT 컬럼이 반드시 key/index로 지정되어야 정상적으로 작동하며, 이는 ‘식별자 역할’과 ‘자동 증가 속성’이 동시에 필요하기 때문입니다.

정리된 이해#

AUTO_INCREMENT는 PRIMARY KEY와 결합하여 행을 식별하는 동시에 자동으로 숫자를 생성하는 속성입니다. MariaDB에서는 이 컬럼이 반드시 key/index로 지정되어야 정상적으로 작동합니다. 따라서 테이블 생성 시 PRIMARY KEY AUTO_INCREMENT를 함께 정의하면, 새 데이터가 삽입될 때마다 고유하고 증가하는 번호가 자동으로 할당됩니다.

-- 1. 테이블 생성 시 AUTO_INCLUDE 설정 (코드에 맞게 수정)
CREATE TABLE auto_inc(
    no INT(10) PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(50)
);

-- 2. 데이터 삽입 (자동 번호 할당)
INSERT INTO auto_inc(name) VALUES('철수');
INSERT INTO auto_inc(name) VALUES('영희');

-- 3. 조회
SELECT * FROM auto_inc;

총평#

오늘 오후 전체에서 배운 것#

관계형 데이터베이스의 핵심은 단순히 문법을 외우는 것이 아니라, 쿼리 간의 의존 관계와 테이블 구조를 이해하는 사고력에 있음을 깨달았다. JOIN을 배울 때는 연결 조건 하나만 명확히 정해도 종류별 동작 원리가 ‘일치 여부 처리’로 단순화되어 훨씬 직관적으로 다가왔다. 마지막으로 AUTO_INCREMENT가 PRIMARY KEY와 반드시 결합해야 작동한다는 점은, 데이터베이스 설계에서 속성 간의 필수적인 연관성을 다시 한번 확인하게 되는 계기가 되었다.

다음에 조심할 것#

오늘 배운 상관 서브쿼리와 JOIN 전략을 실무에 적용할 때는 ‘값의 개수’와 ‘데이터 유지 방향’을 반드시 확인하는 습관을 들일 것이다. 특히 LEFT OUTER JOIN과 RIGHT OUTER JOIN은 직관적으로 파악하기 어려우니, ‘어느 쪽 데이터를 끝까지 유지할 것인가’를 기준으로 조건을 설정해 실수를 방지해야 한다. 마지막으로 UNION이나 NOT IN 등 집합 연산을 사용할 때는 중복 처리와 포함 여부를 정확히 검증하여 의도치 않은 데이터 누락이 없도록 주의하겠다.

다음 복습 주제#

관련 서브쿼리에서 바깥 행과 안쪽 쿼리의 값 참조 관계를 명확히 파악하는 연습을 더 해야겠다. JOIN 종류별로 ‘어떤 데이터를 유지할 것인가’를 결정하는 Join Condition의 역할과, LEFT/RIGHT OUTER JOIN의 데이터 유지 방향을 시각화하는 훈련이 필요하다. UNION·INTERSECT·NOT IN 등 집합 연산자의 동작 원리와 중복 제거 여부에 따른 성능 차이를 정확히 구분하는 복습이 필요해 보인다.
