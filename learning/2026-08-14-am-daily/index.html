1. Next.js 서버-클라이언트 경계 이해하기#

무엇을 배웠나#

Next.js는 React 위에 라우팅과 서버-클라이언트 실행 경계라는 새로운 개념을 추가한 프레임워크입니다. App Router 구조에서 폴더와 URL 경로가 직접 연결되며, 기본적으로 서버 컴포넌트가 작동합니다. 필요한 경우에만 'use client'를 선언하여 클라이언트 측 상호작용을 제어할 수 있습니다.

헷갈렸던 점#

React를 배울 때는 “브라우저에서 실행되는 것"이라는 인식이 강했지만, Next.js에서는 기본적으로 서버가 렌더링을 시작한다는 점이 가장 큰 전환점이었습니다. 특히 page.js와 URL이 어떻게 연결되는지, 그리고 서버와 클라이언트의 경계가 어디인지 감 잡기 어려웠습니다.

정리된 이해#

Next.js는 React 위에 라우팅, 서버-클라이언트 경계, 데이터 페칭 등 프레임워크 특화 기능을 덧씌운 것이다. 핵심은 컴포넌트 모델을 유지하면서도 “코드가 어디서 실행되는지(Server vs Client)“를 명확히 구분하는 것이다. App Router 구조에서 폴더 경로가 URL과 직접 연결되며, 기본적으로 서버 컴포넌트가 작동하므로 필요한 경우에만 'use client'로 클라이언트 경계선을 긋는다.

// app/layout.js - 전체 페이지의 공통 레이아웃
import './globals.css';

export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="ko">
      <body>{children}</body>
    </html>
  );
}

// app/page.jsx - 루트 페이지 (서버 컴포넌트 기본)
export default function HomePage() {
  return <h1>Welcome to Next.js</h1>;
}

// components/counter.jsx - 클라이언트 컴포넌트 예시
'use client';

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>카운트: {count}</p>
      <button onClick={() => setCount(count + 1)}>증가</button>
    </div>
  );
}

2. URL Query를 Object 변환하여 화면에 출력하기#

무엇을 배웠나#

URL query string을 다룰 때 key라는 단어가 React 고유 값과 데이터 속성명으로 동시에 쓰여 혼란스러웠지만, 데이터 구조에 맞춰 접근 방법을 선택하면 된다는 점을 깨달았다. Object에는 기본적으로 map 메서드가 없으므로 Object.keys()나 Object.entries()를 활용해 배열 형태로 변환한 뒤 반복 처리를 해야 한다. 이를 통해 URL 파라미터를 쉽게 꺼내어 화면에 출력하는 로직을 이해할 수 있었다.

헷갈렸던 점#

React의 key와 Object의 key가 같은 단어지만 다른 의미를 가지는 점이 가장 큰 혼란 요소였다. 또한, object에는 기본적으로 map 메서드가 없기 때문에 데이터를 꺼내오는 방법에 막막함을 느꼈다. 데이터 구조에 맞춰 접근 방법을 선택하고, Object.keys()나 Object.entries()를 활용해 배열 형태로 변환한 뒤 반복 처리해야 한다는 점을 이해하게 되었다.

정리된 이해#

URL query string을 다룰 때 가장 중요한 것은 데이터 구조에 맞는 메서드를 선택하는 것이다. Object 형태의 검색 파라미터는 기본적으로 map 메서드가 제공되지 않으므로, Object.keys()나 Object.entries()를 활용해 배열로 변환한 뒤 반복 처리를 해야 한다. 이를 통해 키와 값을 명확히 구분하여 화면에 출력할 수 있다.

Object.keys(search).map(function(key){
    console.log(key, search[key]);
});

3. 동적 라우팅과 캐치올 슬러그의 이해#

무엇을 배웠나#

Dynamic Route를 통해 URL을 데이터 구조로 변환하여 활용할 수 있다는 점을 이해하게 되었다. 특히 Catch-all Route([...slug])는 URL의 깊이에 따라 자동으로 배열에 담기며, 이를 분해하면 코드의 가독성을 높일 수 있다. 실습을 통해 params.slug가 어떻게 경로 조각들을 배열 형태로 반환하는지 직접 확인할 수 있었다.

헷갈렸던 점#

[slug]는 URL에서 경로 조각 하나를만 가져오는 반면, [...slug]는 남은 모든 조각을 배열에 담아온다는 점이 가장 헷갈렸다. 특히 React의 key prop에서 인덱스 대신 고유 ID를 사용하는 것이 중요한 이유를 감 잡지 못했는데, 이는 데이터가 추가되거나 삭제될 때 화면이 꼬이는 부작용 때문이었다. 결국 Dynamic Route는 URL을 데이터 구조로 변환해주는 기능이며, 배열을 해체하여 각 자리에 의미 있는 이름을 붙여 사용하면 코드의 가독성이 높아진다는 점을 명확히 했다.

정리된 이해#

Dynamic Route는 URL을 데이터 구조로 변환하여, 경로의 각 조각을 배열 형태로 받아올 수 있게 해준다. 특히 [...slug]를 사용하면 URL의 깊이가 깊어지더라도 모든 경로 조각을 하나의 배열에 담아 처리할 수 있다. 이를 통해 const [category, region, id] = params.slug;와 같이 변수를 분해하여 의미 있는 이름으로 해석함으로써 코드의 가독성과 유지보수성을 높일 수 있다.

export default async function Page(props) {
    let params = await props.params;
    console.log("params", params.slug);

    // [...slug] 일 경우 blog/11 -> slug:['11']
    // [...slug] 일 경우 blog/food/11 -> slug:['food','11']
    // [...slug] 일 경우 blog/food/korea/11 -> slug:['food','korea','11']

4. URL 설계의 3가지 역할: 이동·분류·추적#

무엇을 배웠나#

URL은 단순히 페이지로 이동하는 주소가 아니라, 목차와 분류, 추적 정보를 포함할 수 있는 구조적 도구라는 점을 이해하게 되었다. 특히 params를 통해 동적으로 전달되는 경로가 트리 구조로 시각화될 수 있다는 사실을 통해, URL 설계가 시스템이 문서를 자연스럽게 따라갈 수 있게 한다는 것을 배웠다. 이를 통해 URL 규칙을 일관되게 설계하는 것이 검색 엔진이나 자동화 시스템에게 콘텐츠의 구조를 쉽게 파악하게 하는 핵심임을 깨달았다.

헷갈렸던 점#

처음에는 URL이 단순히 페이지 이동 주소나 데이터 파라미터 정도로만 생각하여, 그 안에 담긴 구조적 의미(목차·분류·추적 가능성)가 잘 보이지 않았습니다. 특히 params.slug 같은 코드가 화면에 어떻게 출력되는지에 집중하다 보니, URL이 단순한 경로가 아니라 콘텐츠를 분류하고 시스템이 문서를 찾고 정리할 수 있게 하는 ‘용기’라는 점을 구분하지 못해 혼란스러웠습니다.

정리된 이해#

URL은 단순한 이동 경로가 아니라, 콘텐츠를 분류하고 시스템이 구조를 파악할 수 있게 설계된 ‘용기’다. params와 같은 동적 요소를 규칙적으로 구성하면, 별도의 크롤링 없이도 계층적인 목차와 고유 식별 정보가 자연스럽게 전달된다. 따라서 URL 설계는 페이지 연결을 넘어 데이터의 조직화와 추적 가능성을 보장하는 핵심 구조가 된다.

총평#

오늘 오전 전체에서 배운 것#

Next.js의 App Router 구조에서 서버-클라이언트 경계와 URL 파라미터 처리 방법을 정리했다. 기본적으로 서버 컴포넌트가 작동하며, 'use client'를 선언하여 클라이언트 상호작용을 제어하는 방식을 이해했다. 또한 Object.entries() 등을 활용해 쿼리 스트링을 배열로 변환하고, 동적 라우팅과 catch-all 슬러그를 통해 URL의 깊이를 데이터 구조로 활용하는 방법을 학습했다.

다음에 조심할 것#

  1. key와 같은 용어가 데이터 구조명과 React 고유 속성명으로 중복될 경우, 변환 로직을 통해 명확히 구분하여 혼동을 피해야 한다.
  2. Object 형태의 query string은 기본적으로 map이 제공되지 않으므로, Object.keys()나 Object.entries()를 활용해 배열로 전처리하는 습관을 들여야 한다.

다음 복습 주제#

Next.js의 서버 컴포넌트 기본 동작과 'use client' 선언 위치에 대한 개념을 확실히 다져야 합니다. 특히 클라이언트와 서버 간의 데이터 페칭 시점과 경계 처리가 애플리케이션 성능에 미치는 영향을 깊이 이해해야 할 것입니다.

동적 라우팅에서 슬러그 배열 처리 방식과 캐치올 라우트의 구조적 특성에 대한 복습이 필요합니다. [...slug] 패턴이 URL 깊이에 따라 어떻게 자동으로 배열로 변환되는지, 그리고 이를 분해하여 활용하는 연습을 통해 실제 라우팅 로직의 흐름을 정확히 파악해야 합니다.

URL이 단순한 이동 경로를 넘어 데이터 구조와 추적 기능을 수행한다는 점을 재정립해야 합니다. params를 통한 동적 전달이 어떻게 트리 구조로 시각화되는지 이해하고, 일관된 URL 설계가 검색 엔진과 자동화 시스템에 콘텐츠 구조를 효과적으로 전달하는 핵심 요소임을 다시 한번 점검해야 합니다.
