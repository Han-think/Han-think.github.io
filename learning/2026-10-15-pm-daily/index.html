1. LangChain·Opik 기본 호출과 추적 흐름 (초보자 워킹 노트)#

무엇을 배웠나#

처음에는 HAKSA.txt가 포함된 코드를 보고 RAG 프로그램인 줄 알았지만, 실제로는 LLM 기본 호출에 트레이서를 붙이는 예제였습니다. 01_start.py는 문서를 검색하는 기능이 아니라 단순히 질문을 던지고 결과를 Opik으로 추적하는 것이 핵심입니다. 따라서 실제 문서 기반 답변은 02_rag.py에서 다루며, 두 단계는 확실히 구분해야 합니다.

헷갈렸던 점#

가장 큰 혼란은 01_start.py 코드에서 HAKSA.txt 파일이 언급된 점입니다. 단순히 LLM에게 질문을 던지는 기본 예제임에도 불구하고 문서가 등장하자, 이것이 RAG(검색 증강 생성) 프로그램인 줄 알았습니다. 또한 Opik이라는 추적 도구를 사용했다는 사실과 웹 화면에서 trace를 확인한다는 사실이 같은 과정인 것처럼 여겨져, 코드 실행과 대시보드 시각화가 별개라는 점을 구분하는 데 시간이 걸렸습니다.

정리된 이해#

01_start.py는 문서 검색 기능이 없는 순수 LLM 호출 실습이며, Opik 트레이서를 통해 질문과 답변을 추적하는 것이 주된 목적입니다. 실제 RAG(검색 증강 생성) 기능은 02_rag.py에서 다루며, 두 예제는 목적이 명확히 구분됩니다.

tracer = OpikTracer(project_name=PROJECT_NAME, tags=['langchain', 'ollama'])
llm = ChatOllama(model=LLM_MODEL, base_url=OLLAMA_URL, temperature=0)
chain = prompt | llm

2. CallbackManager 인스턴스 생성과 속성 대입#

무엇을 배웠나#

Settings.callback_manager는 함수 호출이 아니라 값을 대입하는 속성(attribute)이라는 점을 명확히 이해하게 되었다. CallbackManager 클래스를 인스턴스로 생성한 뒤, 그 객체를 = 연산자를 통해 Settings에 할당해야만 정상적으로 작동한다는 사실을 깨달았다. 이러한 타입의 의미를 정확히 파악함으로써 발생했던 TypeError를 해결할 수 있었다.

헷갈렸던 점#

Settings.callback_manager()를 함수 호출로 오해하여 괄호(())가 붙은 형태를 함수 실행처럼 생각하다가, 실제로는 속성(attribute)에 값을 대입하는 것임을 깨닫고 TypeError가 발생했다. 특히 CallbackManager라는 클래스 이름이 붙어 있어 객체 자체가 callable한 존재인 줄 알았으나, 인스턴스를 생성한 후 = 연산자로 Settings에 할당해야만 정상적으로 작동한다.

정리된 이해#

Settings.callback_manager는 괄호를 붙여 실행하는 함수가 아니라, 값을 대입하는 속성(attribute)이다. CallbackManager 클래스를 import해 인스턴스를 생성한 뒤, 그 객체를 = 연산자를 통해 해당 속성에 할당해야 정상적으로 작동한다. 이러한 타입의 의미를 정확히 파악하면 TypeError: 'CallbackManager' object is not callable 오류를 해결할 수 있다.

# 수정된 이해
from llama_index.core import Settings
from llama_index.core.callbacks import CallbackManager
from opik.integrations.llama_index import LlamaIndexCallbackHandler

# 1. CallbackManager 인스턴스 생성 (괄호로 감싸서 객체 생성)
callback_manager = CallbackManager([
    LlamaIndexCallbackHandler(
        project_name=PROJECT_NAME,
        skip_index_construction_trace=True,
    )
])

# 2. Settings의 속성에 대입 (등호로 값 할당)
Settings.callback_manager = callback_manager

3. Docker Ollama 포트와 호스트 주소 구분하기#

무엇을 배웠나#

Docker 컨테이너 내에서 Python 코드가 실행될 경우, localhost는 컨테이너 자체를 의미하므로 호스트 측 포트 매핑을 별도로 지정해야 한다. 반면, Windows 호스트에서 직접 실행되는 코드라면 localhost는 자신의 컴퓨터 주소를 뜻하며, Docker가 게시한 포트의 왼쪽 값인 호스트 측 포트를 사용해야 연결된다. 또한, ConnectionError 발생 시 모델 미설치 여부와 함께 네트워크 포트 설정이나 host.docker.internal 같은 특수 주소가 원인일 가능성을 반드시 확인해야 한다.

헷갈렸던 점#

Docker가 호스트와 컨테이너 사이에서 포트를 매핑할 때, ’localhost’는 호스트(내 컴퓨터)의 자기 자신을 의미한다는 점을 명확히 구분하지 못해 헷갈렸다.

강의 예시에서 언급된 172.17.0.1 같은 네트워크 주소가 환경에 따라 변동된다는 점과, Python이 컨테이너 내부에서 실행될 경우 ’localhost’가 자기 자신을 가리키는 것인지 외부 접속을 의미하는 것인지 확신할 수 없어 혼란스러웠다.

연결 오류가 났을 때 모델 파일이 없는 것으로 착각하기보다, 먼저 포트 매핑 설정이나 네트워크 주소 접근 방식 자체를 점검해야 한다는 점을 구분하지 못해 실제 문제 해결에 시간을 지체한 적이 있다.

정리된 이해#

Docker 환경에서 호스트와 컨테이너는 각각 고유한 localhost를 가지므로, Python 실행 위치에 따라 접속 주소가 달라진다. Windows 호스트에서는 Docker가 매핑해준 포트(예: 11435)를 직접 사용해야 하며, 컨테이너 내부에서는 host.docker.internal을 통해 외부 호스트의 서비스에 접근할 수 있다.

# Docker Ollama 포트 매핑 및 접속 주소 정리

1. Windows 호스트에서의 실행 (Python 외부)#

  • Python이 Docker 컨테이너 밖(Windows 자체)에서 실행되는 경우:
  • localhost는 Windows 자신의 localhost를 의미한다.
  • Docker가 게시한 포트의 호스트 측(left) 값을 사용해야 한다.
# Windows 호스트에서 OLLAMA_URL 설정 예시
OLLAMA_URL = 'http://localhost:11435'  # 호측측 포트 매핑

2. Docker 컨테이너 내부에서의 실행 (Python 내)#

  • Python 코드가 Docker 컨테이너 내부에서 실행되는 경우:
  • localhost는 컨테이너 자체의 localhost(자기 자신을 의미)다.
  • 호스트 측 포트 매핑은 적용되지 않으며, 컨테이너 내부 네트워크 환경을 사용해야 한다.
# Docker 컨테이너 내부에서 OLLAMA_URL 설정 예시
OLLAMA_URL = 'http://localhost:11434'  # 컨테이너 내부 포트

3. 다른 Docker 컨테이너에서 실행 시 (연결용)#

  • FastAPI 등 다른 Docker 컨테이너에서 Ollama에 접속해야 할 때:
  • host.docker.internal을 사용하여 호스트 측 포트에 접근할 수 있다.
# 다른 Docker 컨테이너에서 OLLAMA_URL 설정 예시
OLLAMA_URL = 'http://host.docker.internal:11435'

4. RAG 파이프라인 단계별 이해 정리#

무엇을 배웠나#

RAG 파이프라인은 문서 로딩, 임베딩 및 색인 생성, 질문 기반 검색, LLM 답변 생성 등 명확한 단계로 나뉘며, 각 단계가 순차적으로 의존한다는 점을 배웠습니다. 특히 similarity_top_k는 최종 답안의 개수를 결정하는 것이 아니라, 답변 생성을 위한 참고 문서 후보를 제한하는 검색 단계의 파라미터임을 명확히 이해했습니다. 또한 LLM이 답을 생성하기 전에도 문서를 벡터화하여 색인 구축할 때 외부 API가 필요하다는 점은 간과하기 쉬운 중요한 시스템 설계 요소였습니다. 마지막으로 코드 실행 흐름과 학습 로그를 구분하는 연습을 통해, 실제 RAG 동작 원리와 한계를 더 객관적으로 파악할 수 있게 되었습니다.

헷갈렸던 점#

가장 큰 오해는 similarity_top_k=2를 최종 답변 개수를 결정하는 설정으로 착각했던 점입니다. 실제로는 검색 단계에서 상위 2개 문서만 추출할 뿐, LLM이 생성하는 최종 답변의 수는 이 설정과 무관합니다. 또 다른 혼란점은 RAG 파이프라인 전체가 LLM 답변 생성 전후로 외부 API(임베딩 모델 등)를 필수적으로 사용한다는 점입니다. 문서 색인 구축 단계에서도 API 호출이 발생하므로, 이 연결 고리가 끊어지면 나중에 “답이 안 나온다"는 문제를 추적하기 매우 어렵습니다. finally

정리된 이해#

RAG 파이프라인은 문서 로딩, 임베딩 및 색인 생성, 질문 기반 유사 문서 검색, LLM을 통한 답변 생성, 그리고 결과 추적의 5단계로 구성되며, 각 단계는 독립적인 API 호출과 데이터 흐름을 가집니다. 특히 similarity_top_k 설정은 검색 단계에서 반환할 최대 문서 수를 제어하는 파라미터일 뿐, 최종 사용자에게 제공되는 답변의 개수를 직접 결정하지는 않습니다. 마지막으로 시스템 전체의 동작을 정확히 파악하고 디버깅하기 위해서는 각 단계별 API 호출 시점과 데이터 흐름을 명확히 구분하여 추적하는 것이 필수적입니다.

from llama_index.core import SimpleDirectoryReader, VectorStoreIndex, Settings
from llama_index.embeddings.huggingface import HuggingFaceEmbedding
from llama_index.llms.ollama import OllamaLLM

# 1. 데이터 로딩 (문서 인덱싱 전 단계)
documents = SimpleDirectoryReader("data").load_data()

# 2. 임베딩 모델 설정 (색인 생성 시 사용)
Settings.embed_model = HuggingFaceEmbedding(model_name="BAAI/bge-m3")

# 3. 벡터 스토어 인덱스 구축 (임베딩 + 색인 생성, 이때 외부 API 호출 발생)
index = VectorStoreIndex.from_documents(documents)

# 4. 쿼리 엔진 설정 (검색 시 similarity_top_k=2 적용)
query_engine = index.as_query_engine(similarity_top_k=2)

# 5. LLM 설정 (답변 생성 시 사용)
Settings.llm = OllamaLLM(model="gemma4:e4b")

# 6. 질문 및 답변 실행
response = query_engine.query("기숙사 신청 방법")
print(response)

총평#

오늘 오후 전체에서 배운 것#

RAG 파이프라인의 각 단계(로딩, 임베딩, 검색, 답변 생성)가 순차적으로 의존하며, similarity_top_k는 최종 답안 개수가 아니라 검색 후보를 제한하는 파라미터임을 명확히 이해했습니다. 또한 Docker 환경에서는 localhost가 컨테이너 자체를 의미하므로 호스트 포트 매핑이나 host.docker.internal을 정확히 구분해야 연결 오류를 해결할 수 있었습니다. 마지막으로 CallbackManager 인스턴스를 생성해 Settings.callback_manager에 할당하는 방식이 함수 호출이 아닌 속성 대입임을 깨닫고, 타입 이해 부족으로 발생했던 TypeError를 해결할 수 있게 되었습니다.

다음에 조심할 것#

Docker 환경에서는 localhost가 컨테이너 내부 주소를 의미한다는 점을 반드시 확인하고, 호스트 포트 매핑을 정확히 지정해야 합니다. 또한 CallbackManager는 속성 할당 형태임을 잊지 말고, 실제 RAG 파이프라인 구축 시에는 문서 로딩부터 답변 생성까지 각 단계의 의존 관계를 명확히 파악하는 습관을 들입니다.

다음 복습 주제#

다음에는 Settings 객체에 콜백 매니저를 할당하는 구체적인 코드 패턴을 직접 작성해보며, 실제 RAG 파이프라인에서 임베딩 모델과 LLM 호출 시 발생할 수 있는 네트워크 설정(특히 Docker 환경에서의 포트 매핑) 문제를 해결하는 방법을 심층적으로 점검할 예정입니다. 특히 similarity_top_k와 같은 검색 파라미터가 답변 품질에 미치는 영향을 실험해보며, 시스템 전체 흐름에서 각 단계의 의존 관계를 시각화할 수 있는 다이어그램을 그려보는 시간을 가집니다.
