1. LangGraph 핵심 구조와 기존 지식 연결하기#

무엇을 배웠나#

LangGraph는 ‘어떤 모델을 쓸지’가 아니라 ‘작업 순서를 어떻게 흐르게 할 것인가’에 초점을 맞춘 프레임워크다. 핵심 요소인 State, Node, Edge는 기존의 pipeline이나 state 개념과 구조적으로 매우 유사해 빠르게 적응할 수 있었다. 특히 환경 설정 차이에도 불구하고 모델 백엔드가 바뀌어도 기본 구조가 동일하다는 사실은 큰 안도감이 되었다. 이러한 이해를 바탕으로 실제 워크플로우를 코드로 설계하는 데 자신감을 갖게 되었다.

헷갈렸던 점#

LangGraph를 처음 접했을 때 가장 큰 혼란은 환경 설정 차이였다. 시연된 Ollama 예제와 내 LM Studio 환경이 달라 코드 수정에 애를 먹었지만, 결국 모델 백엔드가 달라도 기본 구조는 동일하다는 사실을 깨닫고 안도했다.

가장 중요한 깨달음은 LangGraph의 핵심 that **“어디에 어떤 모델을 쓸지”**가 아니라 **“어떤 순서로 작업을 흐르게 할 것인가”**에 있다는 점이다. 기존에 쓰던 pipeline, state, gate 개념과 매우 비슷해 새롭고 어려운 기술로 느껴졌지만, 워크플로우를 코드로 명시적으로 설계하는 방식이라는 점에서 익숙한 사고방식과 크게 다르지 않아 빠르게 적응할 수 있었다.

정리된 이해#

LangGraph는 기존 파이프라인 개념과 크게 다르지 않은 ‘노드와 엣지로 흐름을 설계하는 프레임워크’다. 핵심은 모델 선택이 아니라 데이터가 어떤 순서로 이동할지를 정의하는 데 있다. 특히 State, Node, Edge는 기존의 상태 관리, 작업 함수, 연결 고리 개념과 직접적으로 대응되어 학습 곡선이 완만했다.

# State 정의: 세 단계의 데이터를 담는 그릇
from typing import TypedDict

class SimpleState(TypedDict):
    ori_query: str

# Node (작업 함수): 실제 일을 처리하는 함수
def refiner(state: SimpleState) -> SimpleState:
    """입력된 질문을 정제하는 노드"""
    print(f"정제 전 질문: {state['ori_query']}")
    # 가공 로직 예시
    refined = state['ori_query'].strip().upper()
    return {"refined_query": refined}

def generator(state: SimpleState) -> SimpleState:
    """정제된 질문을 바탕으로 답변을 생성하는 노드"""
    print(f"생성 중... 질문: {state['refined_query']}")
    # 가공 로직 예시
    response = f"답변: {state['refined_query']}에 대한 처리 완료"
    return {"response": response}

# Edge (이동 경로): 노드 사이의 연결 고리
from langgraph.graph import StateGraph, START, END

# 그래프 객체 생성
workflow = StateGraph(SimpleState)

# 노드 추가
workflow.add_node("refiner", refiner)
workflow.add_node("generator", generator)

# Edge 정의: 흐름 순서 설정
# START → refiner → generator → END
workflow.add_edge(START, "refiner")
workflow.add_edge("refiner", "generator")
workflow.add_edge("generator", END)

# 그래프 컴파일 (실행 가능 상태로 변환)
app = workflow.compile()

2. LangGraph 업데이트 스트리밍 이해하기 (초보자 워킹 노트)#

무엇을 배웠나#

LangGraph의 stream() 메서드는 LLM 토큰 생성 속도와는 무관하게, 그래프 내 각 노드별 State 변화를 단계별로 추적하는 기능임을 명확히 이해했습니다. 특히 stream_mode="updates"를 사용하면 전체 흐름을 한눈에 파악할 수 있으며, 최종 결과뿐만 아니라 중간 과정의 데이터 변동까지 실시간으로 확인할 수 있어 디버깅과 학습에 매우 유용하다는 점을 깨달았습니다.

헷갈렸던 점#

stream() 메서드를 보고 즉시 LLM이 토큰을 실시간으로 내보내는 과정으로 착각했습니다.

결국 stream()과 LLM의 토큰 스트리밍은 완전히 별개의 개념이며, LangGraph에서는 State 업데이트를 단계별로 관찰하는 것이 주된 목적입니다.

정리된 이해#

LangGraph에서 stream()은 LLM이 토큰을 실시간으로 내보내는 과정과 완전히 별개의 개념입니다.

stream_mode="updates"는 그래프 전체 흐름(입력 → 리파이너 → 제너레이터 → 종료)을 한 눈에 파악할 수 있게 해주며, 최종 결과물만 확인하는 invoke()와 달리 각 노드에서의 State 변화를 실시간으로 추적할 수 있다는 점이 가장 큰 장점입니다.

# stream_mode="updates"를 사용한 실행
for node in app.stream({"ori_query": query}, stream_mode="updates"):
    for name, val in node.items():
        print(f"{name}: {val}")

실행된 흐름은 다음과 같았습니다.

입력
→ refiner 실행
→ refined_query 갱신
→ generator 실행
→ response 갱

총평#

오늘 오전 전체에서 배운 것#

LangGraph는 모델 선택보다는 작업 흐름(State, Node, Edge)을 정의하는 프레임워크라는 점을 깨닫고, 기존 pipeline 개념과 구조적 유사성을 빠르게 익힐 수 있었다. 또한 stream() 메서드를 통해 LLM 토큰 생성 속도와 무관하게 각 노드의 State 변화를 단계별로 실시간으로 추적할 수 있으며, updates 모드를 사용하면 중간 과정까지 파악하여 디버깅에 큰 도움이 된다는 점을 학습했다.

다음에 조심할 것#

LangGraph의 핵심 구조를 이해하는 과정에서 State와 Node, Edge가 기존 pipeline과 유사하다는 점을 확인했지만, 실제 코드 작성 시 환경 설정이나 데이터 흐름 세부 사항에서 미세한 차이로 인해 시행착오를 겪을 수 있으므로 꼼꼼히 검증해야겠다.

특히 stream() 메서드의 업데이트 모드를 활용할 때, 토큰 생성 속도와 무관하게 노드별 State 변화만을 정확히 추적하는 것이 중요하며, 이를 통해 중간 과정의 데이터 변동까지 실시간으로 확인하지 않으면 디버깅이 어려워질 수 있으니 흐름을 놓치지 않도록 주의해야겠다.

다음 복습 주제#

LangGraph의 핵심 구조(State, Node, Edge)를 활용해 실무 워크플로우를 직접 설계해보고 싶다. stream() 메서드의 업데이트 모드 기능을 통해 중간 과정 데이터를 추적하는 방법을 실제 프로젝트에 적용해 보고 싶다.
