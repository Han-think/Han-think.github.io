1. 적응형 RAG 경로 결정 과정#

무엇을 배웠나#

Adaptive RAG는 검색 기술을 단순히 많이 붙이는 것이 아니라, 질문과 근거 상태에 따라 어떤 정보원을 선택할지 결정하는 제어 흐름을 만든다는 점을 배웠습니다. 특히 router가 JSON 형식으로 경로를 판단하고, plain, rag, web 중 하나를 선택해 실행한다는 구조를 이해했습니다. 또한 last_answer와 같은 공통 노드를 두면 source 선택과 답변 생성을 분리할 수 있는 유연성이 있다는 점도 인상 깊었습니다.

헷갈렸던 점#

처음 Adaptive RAG를 접했을 때 가장 큰 혼란은 **“그래프에 web node가 있으면 웹 검색이 이미 다 된 것 아닌가?”**라는 기대였습니다. 또한, 세 경로(rag, plain, web)가 모두 실행되어 답을 비교하는 구조인지, 아니면 router가 하나를 선택해 그 하나만 실행하는 구조인지에 대한 명확한 이해가 필요했습니다.

핵심은 **“모든 source를 다 쓰는 구조가 아니라, 판단에 따라 하나의 경로만 선택한다”**는 점입니다.

정리된 이해#

Adaptive RAG는 검색 기술을 단순히 많이 붙이는 것이 아니라, 질문과 근거 상태에 따라 가장 적합한 정보원(rag, plain, web)을 선택하는 제어 흐름을 만드는 것이다. 핵심은 라우터가 JSON 형식으로 경로를 판단하고, 선택된 단일 경로만 실행하여 최종 답변을 도출한다는 점이다. 이를 통해 모델의 기본 지식과 외부 정보를 유연하게 결합할 수 있다.

# Adaptive RAG 핵심 로직 요약 (노트 기반)

def adaptive_rag_pipeline(question):
    # 1. 초기 답변 생성 (근거 검색)
    init_answer = search_and_generate(question)

    # 2. 라우터에 의해 경로 선택 (JSON 형식 결정)
    route = router.decide_route(question, init_answer)
    # 예: {"route": "web"} 또는 {"route": "rag"} 등

    # 3. 선택된 경로만 실행
    if route == "web":
        final_answer = web_search_and_generate(question)
    elif route == "plain":
        final_answer = use_internal_knowledge(question)
    else: # route == "rag"
        final_answer = rag_search_and_generate(question)

    return final_answer

2. Adaptive RAG 구현 흐름과 출처 추적 이해하기#

무엇을 배웠나#

수업 중에는 웹 검색 기능이 동작하지 않아 혼란스러웠지만, 최신 Commit을 확인해 보니 실제 구현된 상태였습니다. 이러한 시간 차이로 인해 ‘안 된 건가?’ 혹은 ‘된 건가?‘라는 판단이 수시로 바뀌어 집중력이 흐트러지는 문제가 있었습니다. 핵심은 실행 흐름의 우선순위에 있으며, 강사님은 먼저 RAG 검색 → route 판단 → plain/rag/web → 공통 답변이라는 최소 구조를 완성하는 데 초점을 두셨습니다. 특히 evidence와 source metadata의 중요성을 다시금 느꼈는데, 답변은 가능해도 나중에 근거를 검증하기 어렵다는 점은 RAG 시스템을 운영할 때 치명적인 약점이 될 수 있습니다.

PDF evidence에는 filename, page, content가 포함되며, 저는 이 노트에서 배운 점을 2~4문장으로 요약하여 마크다운 헤딩 없이 출력합니다.

헷갈렸던 점#

1. 무엇이 헷갈렸나 (Confusion)#

수업을 듣는 내내 가장 큰 혼란은 **“지금 이 코드가 동작하는가, 안 되는가”**에 대한 시점의 차이였습니다.

강사님의 최신 코드(11_adaptive_rag)를 보면 Tavily 검색까지 실제로 연결되어 있어 “아, 웹 검색이구나” 하고 이해하게 됩니다. 그런데 수업 중간중간 Git을 확인하면 “웹 노드 골격만 있음"이라고 느꼈던 상태와 딴판이죠.

수업 중: "웹 검색 안 됨"
최신 Commit: "웬 검색 구현됨"

이런 시간 차이 때문에 “아직 안 했나?” 혹은 “이미 된 건가?“라는 판단이 수시로 바뀌어 집중력이 흐트러지곤 했습니다. 또한 similarity_top_k 같은 옵션 이름의 오타나, insert_data()가 주석 처리된 상태에서 기존 store가 있어야 한다는 점 등 **“기능이 동작한다"와 “서비스가 검증 가능하다”**는 다른 단계에 대한 이해도 부족했습니다.

2. 정리된 이해 (Organized Understanding)#

핵심은 실행 흐름의 우선순위였습니다.

강사님은 먼저 다음 최소 구조를 완성하는 데 초점을 둡니다.

RAG 검색 → route 판단 → plain / rag / web → 공통 답변

provenance, fallback, document lifecycle 같은 고급 문제는 일단 접어두고, **“코드가 어떻게 연결되는가”**부터 파악하라는 조언이 인상적이었습니다. 로컬에서는 같은 구조를 더 명시적으로 나누어 추적할 수 있었지만, 강사님의 방식은 “빨리 개념을 학습"하는 데 초점이 맞춰져 있었습니다.

특히 evidence와 source metadata의 중요성을 다시금 느꼈습니다. 답변은 가능해도 나중에 근거를 검증하기 어렵다는 점은 RAG 시스템을 운영할 때 치명적인 약점이 될 수 있습니다.

3. RAG 청킹과 데이터 운영의 현실#

무엇을 배웠나#

RAG 파이프라인 코드가 동작한다고 해서 서비스가 완성된 것이 아니라는 점을 깨닫게 되었다. 실제 서비스에서는 데이터 업데이트, 권한 관리, 출처 추적 등 인프라적인 운영 문제가 가장 먼저 대두된다. 청크 크기와 문서 구조 보존을 통해 검색 정밀도를 높이고, 메타데이터를 필수적으로 관리해야 신뢰할 수 있는 시스템을 구축할 수 있다.

헷갈렸던 점#

처음 RAG 파이프라인을 접했을 때 코드가 단순히 돌아가면 서비스가 완성된 것처럼 느껴져 큰 착각에 빠졌습니다. 하지만 실제 서비스 관점에서 보면 데이터가 업데이트되거나 삭제될 때의 처리, 사용자별 권한 관리, 답변 출처 추적과 같은 운영 문제가 가장 먼저 대두됩니다. 이러한 현실적인 딜레마는 단순한 코드 연결 단계에서는 자연스럽게 드러나지 않아 서비스의 완성도를 가늠하기 어렵습니다.

청크 설계에서 가장 중요한 원칙은 검색의 단위가 된다는 점입니다. 청크가 너무 작으면 문맥이 단절되고, 너무 크면 여러 주제가 섞여 검색 정밀도가 떨어지기 때문에 적절한 크기 조절이 필수적입니다. 또한 문서의 제목이나 섹션 구조를 보존하고, 길이 초과 시 문장 단위로 나누는 것이 시스템 전체의 안정적인 출발점이 됩니다.

특히 메타데이터는 단순한 부가 정보를 넘어 검색 근거 추적과 문서 갱신·삭제 관리에 필수적입니다. 파일명, 페이지 번호, 제목 경로, 문서 ID 같은 정보가 있어야 사용자는 답변의 출처를 신뢰할 수 있고 시스템 관리자 입장에서 데이터 운영이 가능해집니다. 이러한 메타데이터 전략은 검색 정확도를 높이는 동시에 실제 서비스에서의 유지보수 편의성을 크게 좌우합니다.

정리된 이해#

청크는 검색 단위로, 문서 구조를 보존하고 메타데이터를 필수적으로 관리해야 실제 서비스에서 데이터 운영과 추적 가능성을 확보할 수 있다.

# 청킹 및 메타데이터 부착 예시 (노트 기반 핵심 로직)

def chunk_document(document, chunk_size=512, overlap=50):
    """
    문서를 청크로 분할하고 필수 메타데이터를 부착합니다.

    Args:
        document: 파싱된 문서 객체 (langchain Document 등)
        chunk_size: 한 청크의 최대 토큰 수
        overlap: 인접 청크 간의 토큰 오버랩 수

    Returns:
        청크 리스트 (각 청크는 내용과 메타데이터를 가짐)
    """
    chunks = []

    # 1. 문서 구조 보존 (제목/섹션 유지 전제)
    # 실제 서비스에서는 document.metadata에 'source', 'page', 'section_path' 등이 있어야 함

    # 간단한 문장 단위 청킹 로직 (실제로는 langchain의 RecursiveCharacterTextSplitter 등 사용)
    sentences = document.page_content.split('. ')

    current_chunk_text = ""
    current_meta = dict(document.metadata)  # 원본 메타데이터 복사

    for sentence in sentences:
        # 청크 크기 초과 시 저장 후 초기화
        if len(current_chunk_text) + len(sentence) > chunk_size:
            if current_chunk_text:
                chunks.append({
                    "content": current_chunk_text.strip(),
                    "metadata": current_meta  # 메타데이터 필수 부착
                })
            current_chunk_text = sentence
            # 필요 시 메타데이터 갱신 (예: 페이지 번호 재설정 등)
        else:
            current_chunk_text += sentence + ". "

    # 마지막 청크 처리
    if current_chunk_text:
        chunks.append({
            "content": current_chunk_text.strip(),
            "metadata": current_meta
        })

    return chunks

4. RAG 검색 기법 미리보기: BM25, 하이브리드, 쿼리 변환#

무엇을 배웠나#

BM25는 단어 단위의 정확한 일치에 강하고, 벡터 검색은 의미가 비슷한 문서를 찾는 데 특화되어 있다는 점을 명확히 이해할 수 있었다. 특히 한국어 검색에서는 형태소 분석이 필수적이라는 점을 깨닫고, 단순한 공백 분리가 아닌 언어학적 전처리의 중요성을 새롭게 인식했다. 하이브리드 검색이나 RRF 같은 기법을 통해 두 방식의 장점을 결합하면 검색 결과의 정밀도와 재현율을 동시에 높일 수 있다는 점도 인상 깊었다.

헷갈렸던 점#

BM25는 단어 단위의 정확한 일치에 의존하는 반면, 벡터 검색은 의미적 유사성을 기반으로 문서를 찾기 때문에, 같은 의미를 담고 있어도 표현이 다르면 검색이 되지 않는 간극이 존재한다. 이러한 한계를 보완하고자 BM25와 벡터 검색 결과를 점수 통합 방식으로 결합해 두 방식의 장점을 모두 활용하는 하이브리드 접근 방식을 고려하게 되었다. 특히 한국어 특성상 형태소 분석 없이 단순 공백 분리를 하면 의미가 왜곡될 수 있어, 검색 정확도를 높이기 위해 전처리 단계에서 형태소 분석기가 반드시 필요하다는 점을 명확히 했다.
