1. Docker Desktop 이미지·컨테이너 개념 정리 (Windows PowerShell 활용)#

무엇을 배웠나#

처음 Docker를 접할 때 이미지 유무가 엔진 작동과 연관된다고 잘못 생각했지만, 실제로는 PowerShell에서도 명령어를 직접 실행할 수 있었습니다. 가장 중요한 점은 docker search, pull, run이 각각 다른 대상을 대상으로 하며, 로컬에 이미지가 있어도 컨테이너 실행과 서비스 연결은 별도의 과정이라는 것입니다.

헷갈렸던 점#

처음에는 이미지가 없으면 Docker 엔진에 문제가 있는 줄 알았고, Windows 환경에서 Linux 터미널을 따로 열어야 하는지 혼란스러웠습니다. 또한 이미지가 로컬에 있어도 컨테이너 실행과 서비스 연결은 별도의 과정이라는 점을 나중에야 명확히 이해했습니다.

정리된 이해#

Docker Desktop 설치 후 PowerShell에서 바로 Docker CLI를 사용할 수 있으며, 로컬에 이미지가 존재하는 것과 컨테이너가 정상적으로 서비스하는 것은 별개의 개념이다. 따라서 docker search는 원격 레지스트리 이름을 찾는 것이고, docker pull은 이를 로컬에 다운로드한 뒤 docker run으로 실제 서비스를 시작해야 한다.

Docker Hub 검색 ≠ 다운로드
이미지 다운로드 ≠ 컨테이너 시작
컨테이너 Up ≠ 웹/API 및 DB 연결 검증

2. FastAPI Dockerfile 빌드 vs 런타임 이해하기#

무엇을 배웠나#

Dockerfile은 ‘계약서’와 같아 FROM으로 기반 이미지를 선택하고, WORKDIR로 디렉터리를 설정한 뒤 CMD로 컨테이너 시작 시 실행되는 명령을 정의한다. 빌드 시점과 실행 시점을 분리하면 pip install이 매번 수행되어도 캐시를 활용해 효율적으로 동작하며, docker build로 생성된 이미지 이름은 별개로 docker ps는 기반 이미지를 기준으로 컨테이너를 식별한다는 점을 이해했다.

헷갈렸던 점#

Dockerfile에 의존성 설치 명령이 없어도 컨테이너 실행 시점에 pip install이 자동으로 수행된다는 점, 그리고 이미지를 새로 빌드해도 기존 컨테이너는 베이스 이미지인 python:3.14-slim을 계속 사용한다는 점이 가장 큰 혼란점이었습니다.

정리된 이해#

Dockerfile은 이미지 빌드 시점과 컨테이너 실행 시점을 명확히 분리하는 ‘계약서’ 역할을 한다. CMD는 컨테이너 시작 시점에 실행되어 requirements.txt를 설치하고 서버를 구동한다. 반면 docker build로 생성된 이미지는 기존 기반 이미지를 기반으로 하므로, docker ps에서 확인되는 IMAGE 칼럼은 최신 빌드 결과와 무관하게 기준이 되는 베이스 이미지가 표시된다.

FROM python:3.14-slim

WORKDIR /app

CMD ["sh", "-c", "pip install -r requirements.txt && uvicorn main:app --workers 4 --host 0.0.0.0"]

오늘 오전 전체에서 배운 것#

Dockerfile은 ‘계약서’와 같아 FROM으로 기반 이미지를 선택하고, WORKDIR로 디렉터리를 설정한 뒤 CMD로 컨테이너 시작 시 실행되는 명령을 정의한다. 빌드 시점과 실행 시점을 분리하면 pip install이 매번 수행되어도 캐시를 활용해 효율적으로 동작하며, docker build로 생성된 이미지 이름은 별개로 docker ps는 기반 이미지를 기준으로 컨테이너를 식별한다는 점을 이해했다. Docker Desktop을 통해 이미지와 컨테이너의 개념을 정리하면서, 로컬에 이미지가 있어도 컨테이너 실행과 서비스 연결은 별도의 과정이며 PowerShell에서 직접 명령어를 실행할 수 있다는 사실에 주목했다.

다음에 조심할 것#

Dockerfile 작성 시 FROM 기반 이미지 선택과 CMD 명령어 정의에 더욱 신중을 기하겠다. 이미지 빌드와 컨테이너 실행은 별개의 과정임을 명확히 인지하여 불필요한 재빌드를 피하고, docker ps로 실제 동작 중인 컨테이너를 정확히 확인하겠다. 특히 Windows PowerShell에서 직접 명령어를 실행할 수 있다는 점을 활용해 로컬 환경과 Docker 환경의 차이를 최소화하는 연습을 하겠다.

다음 복습 주제#

Dockerfile에서 CMD와 ENTRYPOINT의 차이점을 명확히 이해하지 못해, 컨테이너 실행 시 어떤 명령어가 실제로 수행되는지 헷갈리는 경우가 많다.

빌드 과정에서 발생하는 레이어 캐시의 동작 원리를 정확히 파악하지 못하면, 불필요한 이미지 크기 증가나 예상치 못한 빌드 오류에 직면할 수 있어 심화 학습이 필요하다.

docker ps 명령어로 확인되는 컨테이너 상태가 docker build로 생성된 이미지의 메타데이터와 어떻게 매핑되는지, 그리고 실제 실행 중인 프로세스와의 관계를 정확히 구분하는 연습이 필요해 보인다.
