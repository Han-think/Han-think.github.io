1. pm-01-join-advanced-types#

무엇을 배웠나#

SQL JOIN 종류에 대한 혼란을 해결하고 각 유형의 동작 방식을 명확하게 이해하게 되었다. USING과 NATURAL JOIN의 문법적 차이점과 CROSS JOIN의 활용 시나리오를 파악했고, RIGHT JOIN과 FULL OUTER JOIN의 버전 호환성 문제도 숙지하게 되었다. 이제 다양한 JOIN 유형을 상황에 맞게 적용할 수 있을 것 같다.

헷갈렸던 점#

JOIN 종류가 너무 많아서 각각의 차이점을 명확하게 구분하기 어려웠고, 특히 JOIN 조건을 설정하는 방식인 ON, USING, NATURAL JOIN의 문법적 차이가 헷갈렸습니다. CROSS JOIN이 언제 사용해야 하는지, 그리고 RIGHT JOIN과 FULL OUTER JOIN의 지원 여부가 SQLite 버전에 따라 달라지는 점도 이해하기 어려웠습니다.

정리된 이해#

JOIN은 양쪽 테이블의 데이터를 결합하는 방식으로, INNER JOIN은 일치하는 데이터만, LEFT JOIN은 왼쪽 테이블의 모든 데이터를 보존합니다. USING과 NATURAL JOIN은 JOIN 조건을 간결하게 표현하는 방식이고, CROSS JOIN은 두 테이블의 모든 조합을 생성합니다. 각 JOIN 유형의 차이점을 명확히 이해하고, 상황에 맞는 적절한 JOIN을 선택하는 것이 중요합니다.

SELECT t.Name AS TrackName, g.Name AS GenreName
FROM tracks t
INNER JOIN genres g ON t.GenreId = g.GenreId;

SELECT artists.Name AS ArtistName, albums.Title AS AlbumTitle
FROM artists
LEFT JOIN albums ON artists.ArtistId = albums.ArtistId;

SELECT albums.Title, artists.Name
FROM albums
INNER JOIN artists USING (ArtistId);

SELECT albums.Title, artists.Name
FROM albums NATURAL JOIN artists;

2. pm-02-self-join-patterns#

무엇을 배웠나#

SELF JOIN은 같은 테이블을 여러 번 사용하여 계층 구조를 표현하거나 특정 조건을 만족하는 쌍을 찾는데 사용될 수 있다는 것을 알게 되었습니다. 계층형 SELF JOIN은 상위 관리자와 하위 직원의 관계를 파악하는 데 도움이 되고, 비교형 SELF JOIN은 데이터 쌍을 비교하여 원하는 결과를 얻는 데 사용됩니다. 특히 tracks 테이블 예시를 통해 비교형 SELF JOIN이 단순히 데이터 비교를 위한 것임을 이해하게 되었습니다.

헷갈렸던 점#

처음에는 같은 테이블을 여러 번 사용해야 하는 SELF JOIN의 목적 자체가 잘 이해가 안 갔습니다. 특히 계층 구조를 표현하는 문제에서, 어떤 기준으로 테이블을 연결해야 하는지, 그리고 차상위 관리자까지 포함해야 하는지 감이 잘 잡히지 않았습니다. 또한 비교형 SELF JOIN에서는 어떤 조건을 사용해야 원하는 결과를 얻을 수 있는지 파악하는 데 어려움이 있었습니다.

정리된 이해#

SELF JOIN은 같은 테이블을 여러 번 사용하여 관계를 표현하는 기법인데, 계층 구조를 나타내는 경우도 있고 단순히 데이터를 비교하는 경우도 있습니다. 계층형 SELF JOIN은 상하 관계를 연결하여 계층 구조를 보여주고, 비교형 SELF JOIN은 특정 조건을 만족하는 데이터 쌍을 찾는데 사용됩니다. 예를 들어, 직원과 관리자 관계나 트랙 ID를 비교하여 중복을 제거하는 데 활용될 수 있습니다.

  SELECT e.FirstName || ' ' || e.LastName

3. pm-03-subquery-classification#

무엇을 배웠나#

서브쿼리 분류에 대한 혼란을 줄이고자 노력했으며, 비연관 서브쿼리는 독립적으로 실행 가능한 쿼리이고, 연관 서브쿼리는 바깥 쿼리의 컬럼을 참조한다는 점을 명확히 이해하게 되었습니다. 연관 서브쿼리를 구분할 때 특정 컬럼의 사용 여부보다는 바깥 쿼리의 컬럼을 참조하는지 여부가 중요하다는 것을 깨달았습니다. 이 지식을 바탕으로 앞으로 서브쿼리를 더 효율적으로 활용하고 분석할 수 있을 것 같습니다.

헷갈렸던 점#

서브쿼리의 다양한 분류(단일행, 다중행, 연관, 비연관)를 동시에 고려하려다 보니 각각의 특징을 명확히 구분하기 어려웠습니다. 특히 연관 서브쿼리에서 바깥 쿼리의 컬럼을 참조하는 부분이 어떻게 연관성을 만드는지 이해하는 데 어려움이 있었습니다. 단순히 t2.Milliseconds와 같은 컬럼을 참조하는 것인지, 아니면 다른 메커니즘이 작용하는지 혼란스러웠습니다.

정리된 이해#

서브쿼리를 이해하는 데 어려움을 겪었지만, 비연관 서브쿼리는 독립적으로 실행 가능하고, 연관 서브쿼리는 바깥 쿼리의 컬럼을 참조한다는 점을 명확히 했습니다. 따라서 서브쿼리의 종류를 구분할 때, 안쪽 쿼리와 바깥 쿼리의 관계를 파악하는 것이 중요하며, 이를 통해 각 서브쿼리가 어떻게 작동하는지 더 명확하게 이해할 수 있습니다.

SELECT Name, UnitPrice
FROM tracks
WHERE UnitPrice > (
    SELECT AVG(UnitPrice)
    FROM tracks
);

SELECT t.Name, t.Milliseconds, t.AlbumId
FROM tracks t
WHERE t.Milliseconds > (
    SELECT AVG(t2.Milliseconds)
    FROM tracks t2
    WHERE t2.AlbumId = t.AlbumId
)
ORDER BY t.AlbumId, t.Milliseconds DESC
LIMIT 20;

4. pm-04-multicolumn-subquery-and-group-max#

무엇을 배웠나#

다중 컬럼 서브쿼리가 여러 행이 아닌 특정 컬럼의 조합을 비교하는 방식이라는 점을 이해하게 되었다. 각 앨범별로 가장 긴 트랙을 찾기 위해 AlbumId가 필요하며, GROUP BY는 단순 정렬이 아닌 그룹화 역할을 한다는 것을 명확히 알게 되었다. 특히 (AlbumId, Milliseconds)와 같은 컬럼 조합을 사용하여 각 앨범 내에서 최대 재생시간을 가진 트랙을 찾는 방법을 익혔다.

헷갈렸던 점#

다중 컬럼이라는 용어가 여러 행을 의미하는지, 아니면 여러 컬럼을 함께 고려하는 것인지 처음에는 헷갈렸고, 특정 앨범 내에서 가장 긴 트랙을 찾기 위해 AlbumId가 왜 필요한지 이해하는 데 어려움을 겪었다. GROUP BY와 ORDER BY의 역할을 명확히 구분하지 못해 결과가 어떻게 도출되는지 파악하는 데 시간이 걸렸다.

정리된 이해#

다중 컬럼 서브쿼리는 단순히 여러 행이나 컬럼을 비교하는 것이 아니라, 특정 컬럼의 조합 (예: 앨범 ID와 재생 시간)을 비교하여 각 그룹 내에서 최대값을 찾는 데 사용됩니다. 각 앨범별로 가장 긴 트랙을 찾기 위해 앨범 ID를 함께 고려하는 것이 중요하며, GROUP BY 절은 데이터를 그룹화하고, ORDER BY 절은 정렬을 담당합니다. 이 쿼리는 특정 그룹 내에서 최대값을 찾는 데 유용한 방법입니다.

SELECT Name,
         AlbumId,
         Milliseconds
  FROM tracks
  WHERE (AlbumId, Milliseconds) IN (
      SELECT AlbumId, MAX(Milliseconds)
      FROM tracks
      GROUP BY AlbumId
  )
  ORDER BY AlbumId
  LIMIT 15;

5. pm-05-view-and-plsql-overview#

무엇을 배웠나#

SQL VIEW는 실제 데이터 복사본이 아니라, 특정 쿼리를 저장한 가상 창이라는 점을 명확히 이해하게 되었다. VIEW는 데이터를 복사하지 않고 원본 테이블을 참조하기 때문에, 원본 테이블의 데이터가 변경되면 VIEW에 반영된다. 또한 PL/SQL은 Oracle 데이터베이스 내에서 SQL을 확장하여 프로그래밍적인 기능을 사용할 수 있게 해주는 언어라는 것을 알게 되었다.

헷갈렸던 점#

VIEW가 테이블 복사본인지 가상 창인지, 그리고 WebView2와 혼동되었었어. PL/SQL을 다른 프로그래밍 언어와 비슷하게 생각하며 그 역할이 무엇인지 제대로 이해하지 못했어.

정리된 이해#

VIEW는 실제 데이터를 복사하는 것이 아니라, SELECT 쿼리를 저장하여 데이터를 보여주는 가상의 테이블이라고 이해했다. 따라서 VIEW를 통해 데이터를 조회하면 원본 테이블의 데이터가 실시간으로 반영되지만, 데이터 수정은 제한적이다. PL/SQL은 Oracle 데이터베이스 내에서 SQL의 기능을 확장하여 조건문이나 반복문과 같은 프로그래밍 구조를 사용할 수 있게 해주는 언어라는 것을 알게 되었다.

CREATE VIEW view_track_full AS
SELECT t.TrackId, t.Name AS TrackName, t.Milliseconds, t.UnitPrice,
           al.Title AS AlbumTitle, ar.Name AS ArtistName, g.Name AS GenreName
    FROM tracks t
    INNER JOIN albums al ON t.AlbumId = al.AlbumId
    INNER JOIN artists ar ON al.ArtistId = ar.ArtistId
    INNER JOIN genres g ON t.GenreId = g.GenreId;

6. pm-06-window-function-preview#

무엇을 배웠나#

윈도우 함수는 데이터를 그룹화하여 요약하는 GROUP BY와 달리 원본 행을 유지하며 계산 결과를 각 행 옆에 추가하는 기능이라는 것을 알게 되었습니다. PARTITION BY와 ORDER BY를 활용하여 그룹화와 정렬을 제어하며, MAX()나 SUM()과 같은 함수와 함께 사용하면 그룹 내의 최대값이나 누적 합계를 각 행에 표시할 수 있습니다. 코드 복잡성이 증가할 수 있다는 부담감을 느끼지만, 이제는 윈도우 함수가 기존 SQL 쿼리를 더 효율적으로 만드는 강력한 도구라는 것을 이해하게 되었습니다.

헷갈렸던 점#

처음에는 윈도우 함수가 JOIN이나 서브쿼리처럼 데이터 결과 집합을 변형하는 줄 알았습니다. 코드 복잡성이 증가할까 봐 걱정했는데, 실제로 사용해보니 GROUP BY와 달리 행을 제거하지 않고 정보를 추가하는 방식이라서 오히려 유연하게 활용할 수 있다는 것을 알게 되었습니다. PARTITION BY와 ORDER BY가 어떻게 작동하는지 이해하는 데 집중해야겠다는 생각이 들었습니다.

정리된 이해#

윈도우 함수는 GROUP BY와 달리 데이터를 그룹화하여 요약하는 대신, 원본 행을 유지하면서 각 행에 대한 계산 결과를 추가하는 기능입니다. PARTITION BY를 통해 그룹을 나누고 ORDER BY로 정렬하여 그룹 내에서 특정 값(최대값, 누적 합계 등)을 계산할 수 있으며, 이를 통해 복잡한 분석을 수행할 수 있습니다. 코드가 길어질 수 있지만, 원본 데이터를 유지하면서 분석 결과를 얻을 수 있다는 장점이 있습니다.

SELECT Name,
       AlbumId,
       Milliseconds,
       MAX(Milliseconds) OVER (PARTITION BY AlbumId) AS MaxMsInAlbum
FROM tracks;

SELECT Name,
       AlbumId,
       Milliseconds
FROM (
    SELECT Name,
           AlbumId,
           Milliseconds,
           MAX(Milliseconds) OVER (PARTITION BY AlbumId) AS MaxMsInAlbum
    FROM tracks
) AS subquery
WHERE Milliseconds

총평#

오늘 오후 전체에서 배운 것#

SQL JOIN 유형과 서브쿼리 분류, 그리고 윈도우 함수에 대한 이해도를 높여 데이터 분석 역량을 강화했다. 특히 서브쿼리 활용법과 다중 컬럼 서브쿼리, 윈도우 함수의 개념을 명확히 익혀 실제 데이터 분석에 적용할 수 있게 되었다. VIEW와 PL/SQL 개요를 통해 데이터베이스 프로그래밍적인 지식도 쌓았다.

다음에 조심할 것#

JOIN 유형별 시나리오 적용 연습을 꾸준히 해야 실전에서 유연하게 활용할 수 있을 것 같다. 서브쿼리의 연관성 판단 기준을 계속 상기하며 분석에 활용하고, 복잡한 쿼리 작성 시 윈도우 함수 사용을 신중하게 고려해야 할 것 같다.

다음 복습 주제#

윈도우 함수는 코드 복잡성 증가에 대한 부담감도 있지만, 실제 활용 예제를 통해 익숙해져야 할 것 같습니다. 특히 PARTITION BY와 ORDER BY의 활용법을 더 숙달하고 다양한 시나리오에 적용해 보면서 이해도를 높여야겠습니다. 마지막으로 PL/SQL의 구체적인 활용법을 학습하여 SQL 쿼리 작성 능력을 향상시키고 싶습니다.
