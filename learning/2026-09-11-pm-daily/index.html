1. stream_mode 변경 시 chunk 구조와 파서 재구성 필요#

무엇을 배웠나#

stream_mode 옵션을 변경하면 데이터의 청크 구조가 완전히 달라지므로, 단순히 옵션 하나만 바꾸는 것이 아니라 그에 맞는 파서 로직도 함께 재구성해야 한다.

mode를 선택할 때 중요한 것은 ‘어떤 모드를 쓸 것인가’가 아니라, 해당 mode에 맞춰 데이터를 어떻게 정규화하고 변환할 것인지가 핵심 설계 포인트가 된다. raw event를 UI로 전달하기 전, 일관된 형태(text/tool_call 등)로 정제하는 normalization layer를 두는 것이 유지보수에 훨씬 유리하다.

헷갈렸던 점#

stream_mode 옵션을 변경하면 데이터 구조가 완전히 달라져서 파싱 로직까지 재구성해야 한다는 점이 가장 큰 혼란이었습니다. 단순히 streaming 기능 제공 여부가 아니라, mode에 따라 chunk의 포맷과 내부가 다르기 때문에 코드 전체를 다시 짜야 했습니다. 따라서 프로젝트에서는 옵션 선택 자체보다, 각 mode에 맞춰 데이터를 정규화하는 설계가 핵심입니다.

정리된 이해#

stream_mode 옵션을 변경하면 데이터 구조가 완전히 달라지므로, 단순히 옵션 하나만 바꾸는 것이 아니라 그에 맞는 chunk parser와 정규화 로직도 함께 재구성해야 한다. mode에 맞춰 데이터를 통일된 형태로 변환해주는 normalization layer를 두는 것이 유지보수에 훨씬 유리하다.

# stream_mode="updates" 모드에서 반환되는 chunk 구조 예시
# 주요 단계 종료 시점마다 결과가 반환되며, model.messages 형태로 중첩됨
chunk = {
    "model": {
        "messages": [...]  # message 리스트가 모델 내부 상태와 함께 묶림
    }
}

# stream_mode="messages" 모드에서 반환되는 chunk 구조 예시
# message 단위로 세밀하게 스트리밍되며, chunk[0] 형태로 직접 접근 가능
chunk = [
    {"role": "assistant", "content": "안녕하세요..."},
    {"role": "assistant", "content": "어떻게 도와드릴까요?"}
]

2. 에이전트 툴 인터페이스와 모듈성: 일관된 구조와 내부 구현 교체ability#

무엇을 배웠나#

오늘은 툴 인터페이스의 일관성과 내부 구현의 교체 가능성을 중심으로 배웠습니다. 어떤 툴 이름이 실시간성을 암시하더라도, 모든 도구는 Agent → tool 선택 → Python 함수 실행이라는 동일한 흐름을 따른다는 점이 핵심입니다. 또한, 툴 인터페이스는 유지하면서 내부 구현을 더미에서 실제 API로 교체하는 방식이 이상적인 모듈 구조라고 판단했습니다.

헷갈렸던 점#

함수명만 보고 실제 API가 연결된 줄 알았는데, 날씨와 주식 툴은 가짜 문자열을 반환하는 mock이어서 ‘보이는 것과 다른 실체’에 혼란을 느꼈다. 또한 툴 인터페이스는 유지하면서 내부 구현을 교체할 수 있다는 점에서, “보는 사람은 실시간 데이터처럼 느끼게 하되 안에서는 더미를 쓰는 것"이 이상적인 구조라는 점을 이해하게 되었다.

정리된 이해#

툴 인터페이스의 일관성을 유지하면서 내부 구현을 mock에서 실제 API로 교체하는 것이 모듈성의 핵심이며, 툴 이름은 실시간성을 암시하지만 실제 동작은 내부 로직에 따라 달라질 수 있음을 이해해야 한다.

# Tool Interface Consistency Example
def check_weather(city: str) -> str:
    """날씨 조회 툴 (내부 구현은 mock 또는 실제 API 연동 가능)"""
    # 실제 서비스에서는 requests 라이브러리로 외부 API 호출
    # 여기서는 예시를 위해 더미 데이터 반환
    return f"{city}의 날씨: 맑음, 25도"

def check_stock(ticker: str) -> str:
    """주식 조회 툴"""
    # 실제 서비스에서는 yfinance 또는 키움증권 API 호출
    return f"{ticker} 현재가: 10,000원"

def now_date() -> str:
    """현재 날짜/시간 툴 (실제 datetime.now() 직접 호출)"""
    from datetime import datetime
    return datetime.now().strftime("%Y-%m-%d %H:%M:%S")

# 사용 예시
if __name__ == "__main__":
    print(check_weather("서울"))
    print(check_stock("005930"))
    print(now_date())

3. Transformers Pipeline과 ViT 이미지 분류 실습 정리#

무엇을 배웠나#

Transformers Pipeline은 모델 로드와 전처리 과정을 자동화해주는 하이레벨 API라는 점을 명확히 이해하게 되었다. LangChain과 달리 이미지 분류 자체는 Pipeline이 담당하며, LangChain은 복잡한 워크플로우를 구성할 때 사용되는 오케스트레이션 툴이라는 구분도 잡혔다. 또한 CUDA 명령어가 자신의 Intel Arc 환경과 맞지 않아 환경 설정에 신중을 기해야 한다는 점을 깨닫고 실습에 임했다. 이러한 이해를 바탕으로 실제 코드 실행 시 전처리 과정과 모델 입력 형태에 더 집중할 수 있게 되었다.

헷갈렸던 점#

가장 큰 혼란은 ‘CUDA 환경 설정’과 ‘도구 사용법’이 뒤섞여 있었다는 점입니다. Intel Arc를 사용하는 제 환경에서는 제공된 CUDA 명령어가 맞지 않아 “반드시 따라 해야 하는 건가?“라는 불안감이 들었고, 폴더 경로가 LangChain이었기에 LangChain을 이용한 이미지 분류를 배우는 줄 알았으나 실제로는 transformers.pipeline()을 직접 사용하는 순수 실습이었다는 점이 initially 이해되지 않았습니다.

정리된 이해#

Transformers Pipeline은 모델 추론을 위한 하이레벨 API로, 전처리와 후처리를 자동화해 빠르게 결과를 얻는 데 적합하다. LangChain Agent는 복잡한 워크플로우를 조율하는 오케스트레이션 툴이며, 이미지 분류 자체는 Pipeline이 담당한다. 하드웨어 환경에 따라 CUDA 대신 XPU나 다른 백엔드를 사용해야 하므로, 설치 명령어는 자신의 그래픽 카드 사양에 맞게 조정해야 한다.

# Transformers Pipeline을 이용한 간단한 Image Classification 예시
from transformers import pipeline

# 비전 모델 로드 (자동으로 전처리 및 후처리 수행)
classifier = pipeline("image-classification", model="google/vit-base-patch16-224")

# 이미지 파일 경로 또는 URL 입력
image_path = "example.jpg"

# 분류 실행 (결과 자동 정렬 및 확률 반환)
results = classifier(image_path)

# 상위 5개 결과 출력
for result in results[:5]:
    print(f"Label: {result['label']}, Score: {result['score']:.4f}")

4. 업로드 후 분류와 정리: 임시 파일 관리 전략#

무엇을 배웠나#

업로드된 파일을 임시 저장했다가 분석 후 삭제하는 방식은, AI 인퍼런스 서비스에서 메모리나 디스크 자원을 효율적으로 관리하고 사용자 업로드 이미지가 영구히 남지 않도록 보안성을 확보하기 위한 필수 과정이다. 단순히 파일을 지우는 것을 넘어, shutil.copyfileobj()를 활용해 메모리 버퍼에 임시로 저장한 뒤 os.remove()로 정리하는 코드 흐름을 이해하여 ‘일시적 처리’와 ‘영구 보관’의 개념을 명확히 구분할 수 있게 되었다. 특히 분류 결과를 보존하면서도 원본 파일을 즉시 삭제하는 구조가, 분석 목적이 달성된 후 시스템을 깨끗이 정비하는 핵심 로직임을 깨닫았다.

헷갈렸던 점#

업로드된 파일을 바로 지우는 행위가 ‘저장했다가 지우는’ 것처럼 느껴져서, 왜 굳이 임시 파일 생성 과정을 거치는지 의아했습니다. 또한 분류 결과를 보존하면서 원본 파일은 삭제하는 방식이, 결과물과 입력 데이터의 관리 주체가 달라 혼란스러웠습니다.

정리된 이해#

업로드된 파일을 영구 보관하는 것이 목적이 아니라, AI 분석을 위한 일시적인 처리 수단으로 사용한다는 점이 핵심입니다. 분석이 완료된 후에는 디스크 점유를 막고 민감한 정보가 남지 않도록 즉시 삭제하는 것이 필수적입니다. 따라서 파일 관리는 ‘저장’이 아닌 ‘자원 회수와 보안’의 과정으로 접근해야 합니다.

# FastAPI 이미지 업로드 → 분류 → 임시파일 삭제 (핵심 로직)

from fastapi import FastAPI, UploadFile, File
import shutil
import os

app = FastAPI()

@app.post("/upload-and-classify/")
async def upload_and_classify(file: UploadFile = File(...)):
    # 1. 업로드된 파일을 임시 경로에 저장 (디스크 I/O 발생)
    # 'temp_image.jpg' 같은 고유한 파일명으로 저장해야 충돌 방지
    temp_file_path = f"temp_{file.filename}"

    with open(temp_file_path, "wb") as buffer:
        shutil.copyfileobj(file.file, buffer)

    # 2. 분류 모델 추론 실행 (여기서 AI 처리가 일어남)
    # classify_result = model.predict(temp_file_path)
    # result_label = "cat" # 예시 결과

    # [학습 포인트] 분류 결과를 보존하거나 화면에 표시한 후,
    # 원본 업로드 파일을 즉시 삭제하여 메모리/디스크 자원 회수 및 보안 유지

    # 3. 임시 파일 삭제 (핵심 단계)
    if os.path.exists(temp_file_path):
        os.remove(temp_file_path)

    return {"filename": file.filename, "status": "processed and deleted"}

5. Intel Arc/XPU 환경으로 이어가는 오후 수업 요약#

무엇을 배웠나#

오늘 수업은 ‘환경 이식’에 대한 이해를 높여주는 계기가 되었습니다. 단순히 코드를 따라 치는 것이 아니라, 애플리케이션 로직과 프레임워크 어댑터, 런타임을 구분하여 교체해야 한다는 점이 핵심 insight였습니다. 특히 ChatOllama나 CUDA 코드를 내 환경에 맞게 수정하는 과정 자체가 학습의 일부가 된다는 점을 깨닫고 실무 적용에 대한 자신감이 생겼습니다.

헷갈렸던 점#

강의에서 제시한 ChatOllama나 CUDA 코드를 내 환경에 그대로 적용하려다 보니, 어떤 부분을 수정해야 할지 막막하고 시행착오가 많았다.

핵심은 ‘애플리케이션 로직’은 수업의 의도를 따라가는 것이 빠르지만, ‘프레임워크 어댑터’와 ‘런타임/하드웨어’ 부분은 내 환경에 맞게 교체해야 한다는 점이었다. 특히 ChatOllama 같은 인터페이스를 다른 것으로 대체하는 것이 단순히 코드를 고치는 것을 넘어, 어떤 레이어를 건드려야 하는지 구분하는 안목이 필요하다는 점이 가장 큰 혼란 포인트였다.

정리된 이해#

오늘은 ‘환경 이식’이라는 주제로 수업을 들었습니다. 핵심은 애플리케이션 로직을 그대로 유지하면서, 프레임워크 어댑터와 런타임/하드웨어 레이어만 내 환경에 맞게 교체하면 된다는 점이었습니다. 특히 ChatOllama 같은 인터페이스를 교체하는 것이 중요한 중간 다리 역할을 한다는 점을 깨닫고 실습 예시를 통해 3층 구조를 머릿속에 그렸습니다.

[오전: Ollama → LM Studio]
    ↓ (환경 교체)
[오후: CUDA 예제 → Intel Arc/XPU 관점]

    ↓ (3층 구조 적용)
[내 프로젝트: Application logic 고정]
        ↑
[내 프로젝트: Framework adapter 교체 (ChatOllama 등)]
        ↑
[내 프로젝트: Runtime Adapter 교체 (XPU/CUDA)]

총평#

오늘 오후 전체에서 배운 것#

오늘은 stream_mode 변경 시 청크 구조와 파서 로직이 함께 재구성되어야 한다는 점, 그리고 mode 선택보다는 그에 맞는 데이터 정규화 설계가 핵심임을 배웠습니다. 또한 툴 인터페이스의 일관성을 유지하면서 내부 구현을 교체 가능한 모듈 구조로 설계하는 것이 중요하다는 점을 명확히 했습니다. 마지막으로 Transformers Pipeline의 자동화 기능과 Intel Arc 환경에서 CUDA 호환성 문제를 해결하기 위한 환경 설정의 필요성을 실감했습니다.

다음에 조심할 것#

오늘은 stream_mode 변경 시 chunk 구조와 파서 로직이 함께 재구성돼야 한다는 점을 뼈저리게 느꼈다. mode 선택 자체보다 해당 모드에 맞춰 데이터를 어떻게 정규화하고 변환할지가 핵심 설계 포인트라는 사실도 새롭게 정리했다.

특히 툴 인터페이스의 일관성과 내부 구현의 교체 가능성을 중점적으로 학습했는데, 모든 도구가 동일한 흐름(agent → tool 선택 → python 함수 실행)을 따른다는 점과, 인터페이스는 유지하면서 실제 API로 교체하는 모듈 구조가 이상적이라는 점을 명확히 했다.

다음 복습 주제#

오늘 배운 핵심 내용은 다음과 같습니다.

stream_mode 옵션을 변경할 때는 단순히 설정값 하나만 수정하는 것이 아니라, 그에 맞는 청크 구조와 파서 로직을 함께 재구성해야 한다는 점입니다. mode 선택의 핵심은 ‘어떤 모드를 쓸 것인가’가 아니라, 해당 모드에 맞춰 데이터를 어떻게 정규화하고 변환할 것인지가 설계의 핵심 포인트가 되어야 합니다.

툴 인터페이스의 일관성과 내부 구현의 교체 가능성에 대해 배웠습니다. 어떤 툴 이름이 실시간성을 암시하더라도, 모든 도구는 Agent → tool 선택 → Python 함수 실행이라는 동일한 흐름을 따른다는 점이 핵심이며, 툴 인터페이스는 유지하면서 내부 구현을 더미에서 실제 API로 교체하는 방식이 이상적인 모듈 구조라고 판단했습니다.

Transformers Pipeline은 모델 로드와 전처리 과정을 자동화해주는 하이레벨 API라는 점을 명확히 이해하게 되었습니다. LangChain과 달리 이미지 분류 자체는 Pipeline이 담당하며, LangChain은 복잡한 워크플로우를 구성할 때 사용되는 오케스트레이션 툴이라는 구분도 잡았습니다. 또한 CUDA 명령어가 Intel Arc 환경과 맞지 않아 환경 설정에 신중을 기해야 한다는 점을 깨닫고 실습에 임했습니다.

업로드된 파일을 임시 저장했다가 분석 후 삭제하는 방식은 AI 인퍼런스 서비스에서 메모리나 디스크 자원을 효율적으로 관리하고 보안성을 확보하기 위한 필수 과정입니다. 단순히 파일을 지우는 것을 넘어, shutil.copyfileobj()를 활용해 메모리 버퍼에 임시로 저장한 뒤 os.remove()로 정리하는 코드 흐름을 이해하여 ‘일시적 처리’와 ‘영구 보관’의 개념을 명확히 구분할 수 있게 되었습니다.

오늘 수업은 ‘환경 이식’에 대한 이해를 높여주는 계기가 되었습니다. 단순히 코드를 따라 치는 것이 아니라, 애플리케이션 로직과 프레임워크 어댑터, 런타임을 구분하여 교체해야 한다는 점이 핵심 insight였습니다. ChatOllama나 CUDA 코드를 내 환경에 맞게 수정하는 과정 자체가 학습의 일부가 된다는 점을 깨닫고 실무 적용에 대한 자신감이 생겼습니다.
