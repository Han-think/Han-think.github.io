1. SELECT 기본기 실습#

무엇을 배웠나#

오후에는 chinook.db를 기준으로 SELECT 기본 문법을 직접 타이핑했다. 실습 범위는 SELECT, DISTINCT, WHERE, AND/OR/NOT, BETWEEN, IN/NOT IN, LIKE, ORDER BY, LIMIT였다.

SELECT 컬럼명
FROM 테이블명
WHERE 조건
ORDER BY 정렬기준
LIMIT 개수;

헷갈렸던 점#

같은 컬럼에 여러 후보 값을 비교할 때 OR을 계속 붙이려 했는데, 이럴 땐 IN이 더 짧고 읽기 좋다. 또 LIKE의 % 위치 감각이 헷갈렸다.

'K%'     = K로 시작
'%Live'  = Live로 끝남
'%Love%' = 중간 어디든 Love 포함

정리된 이해#

문제별 핵심 답안을 모으면 SELECT의 기본기가 한눈에 들어온다.

-- 고객 국가 중복 제거
SELECT DISTINCT Country
FROM customers;

-- 미국 또는 캐나다 고객
SELECT *
FROM customers
WHERE Country IN ('USA', 'Canada');

-- 금액 5~10 사이 인보이스
SELECT *
FROM invoices
WHERE Total BETWEEN 5 AND 10;

-- 가장 비싼 곡 10개
SELECT
    Name AS "곡 이름",
    UnitPrice AS "단가"
FROM tracks
ORDER BY UnitPrice DESC
LIMIT 10;

2. SELECT에서 자주 한 실수와 교정#

무엇을 배웠나#

SQL은 문법이 짧아 보이지만 작은 오타와 패턴 차이가 결과를 크게 바꾼다. 오늘 실습에서 세 가지 교정 포인트가 있었다.

헷갈렸던 점#

첫째, 숫자 비교에 따옴표를 붙였다. 둘째, LIKE 'K%'(시작)와 LIKE '%K%'(포함)를 혼동했다. 셋째, “가장 비싼 곡부터"인데 가격이 아니라 이름 기준으로 정렬했다.

-- (잘못) 숫자에 따옴표
SELECT * FROM tracks WHERE UnitPrice > '0.99' LIMIT 10;

-- (교정) 숫자는 따옴표 없이
SELECT * FROM tracks WHERE UnitPrice > 0.99 LIMIT 10;

정리된 이해#

실수 방지 공식을 한 덩어리로 외워 두면 같은 함정을 덜 밟는다.

숫자 비교 = 따옴표 없이
문자 비교 = 작은따옴표 사용
시작 검색 = '문자%'
끝 검색   = '%문자'
포함 검색 = '%문자%'
정렬 기준 = 문제에서 요구한 기준 컬럼
상위 N개  = ORDER BY + LIMIT

응애 단계에서 이런 실수를 밟는 것은 정상이고, 기록해 두면 나중에 쿼리 검증 규칙으로도 쓸 수 있다.

3. DML 실습: INSERT, UPDATE, DELETE#

무엇을 배웠나#

오후 후반에는 book 테이블로 DML을 실습했다. DML은 데이터를 실제로 바꾸는 명령이다. SELECT가 조회라면 DML은 장부를 직접 고치는 행위다.

INSERT = 새 줄 추가
UPDATE = 기존 줄 수정
DELETE = 줄 삭제

헷갈렸던 점#

INSERT에서 컬럼 순서와 값 순서가 헷갈렸고, 문자열 안의 작은따옴표 처리도 주의가 필요했다(It's → 'It''s'). DELETE에 SET을 쓰는 실수도 했다.

INSERT INTO book (title, category, price, rating, stock)
VALUES ('It''s Only the Himalayas', 'Travel', 45.17, 2, 19);

-- (잘못) DELETE 에 SET
-- DELETE book SET rating = 1;

-- (맞음)
DELETE FROM book
WHERE rating = 1;

정리된 이해#

DML에서 가장 중요한 것은 WHERE다. WHERE를 빠뜨리면 전체가 수정되거나 삭제된다. 그래서 삭제·수정 전에는 항상 SELECT로 대상을 먼저 조준한다.

-- 먼저 조준
SELECT * FROM book WHERE stock < 16;

-- 확인 후 실행
DELETE FROM book WHERE stock < 16;

실제 프로젝트에서는 DELETE 대신 status = 'archived' 같은 소프트 삭제가 더 안전할 수 있다.

4. book 테이블로 SELECT 복습#

무엇을 배웠나#

DML로 데이터를 바꾼 뒤 book 테이블로 SELECT를 다시 복습했다. 복습 범위는 DISTINCT, 비교 연산자, LIKE, ORDER BY였다.

헷갈렸던 점#

DML 이후에는 데이터 상태가 바뀐다. 그래서 DELETE를 실행한 뒤에는 같은 SELECT라도 결과가 달라진다. “같은 질문이라도 실행 시점에 따라 답이 바뀐다"는 점이 새삼 와닿았다.

정리된 이해#

컬럼의 성격에 따라 쓰는 연산자가 달라진다는 감각이 잡혔다.

SELECT DISTINCT category FROM book;          -- 분류 컬럼 → DISTINCT
SELECT * FROM book WHERE price >= 40;        -- 숫자 컬럼 → 비교 연산
SELECT * FROM book WHERE title LIKE '%the%'; -- 문자열 컬럼 → LIKE
SELECT * FROM book ORDER BY price DESC;      -- 정렬 기준 → ORDER BY

SQLite의 LIKE는 기본적으로 영문 대소문자를 크게 구분하지 않아 '%the%'로도 The를 찾을 수 있다.

5. ERD를 보고 쿼리를 만드는 훈련#

무엇을 배웠나#

ERD는 단순 그림이 아니라 어느 테이블에서 어떤 데이터를 가져올지 찾는 지도다. 보는 순서가 있다.

1. 테이블 이름을 본다.
2. 각 테이블의 Primary Key를 찾는다.
3. Foreign Key가 어디를 가리키는지 본다.
4. 1:N 관계인지 확인한다.
5. 원하는 데이터가 어느 테이블에 있는지 찾는다.
6. 필요한 테이블을 JOIN으로 연결한다.

헷갈렸던 점#

ERD를 처음 보면 트리처럼 보이지만 실제로는 회로도에 가깝다. 테이블은 부품, PK는 고유 단자, FK는 다른 부품으로 가는 선, JOIN은 그 선을 따라 데이터를 결합하는 작업이다.

정리된 이해#

원하는 정보가 한 테이블에 없으면 ERD에서 연결 키를 찾아 JOIN한다. 예를 들어 아티스트 이름과 앨범 제목을 함께 보려면 두 테이블을 잇는다.

SELECT
    artists.Name,
    albums.Title
FROM artists
JOIN albums
    ON artists.ArtistId = albums.ArtistId;

ERD는 데이터베이스 던전의 미니맵이다. 처음엔 무섭지만 계속 보면 길이 보인다.

총평#

오늘 오후 전체에서 배운 것#

SELECT 기본기(DISTINCT/WHERE/IN/LIKE/ORDER BY)를 직접 타이핑하며 익히고, 자주 하는 실수를 교정 규칙으로 정리했다. 이어서 INSERT/UPDATE/DELETE로 데이터를 직접 바꾸는 DML을 다루고, ERD를 보고 어떤 테이블을 연결할지 읽는 훈련까지 했다. 조회에서 조작, 그리고 관계 읽기로 이어지는 하루였다.

다음에 조심할 것#

DML에서 WHERE를 빠뜨리지 않기. 삭제·수정 전에는 반드시 SELECT로 대상을 먼저 확인한다. 숫자/문자 리터럴과 LIKE 패턴 위치도 계속 의식한다.
