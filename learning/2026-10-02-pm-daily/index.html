1. 검색-먼저 접근, 라우팅과 트레이드오프#

무엇을 배웠나#

PDF와 무관한 질문에도 검색을 먼저 수행하는 이유는, 라우터가 실제 문서 내용을 보고 판단해야 정확한 경로(RAG/Plain/Web)를 선택할 수 있기 때문이다. 이 ‘검색-먼저’ 접근 방식은 PDF 관련 질문에 강하지만, 비용이 발생한다는 trade-off가 있다. ultimately, 핵심은 검색을 먼저 수행함으로써 분류 오류를 방지하고 품질을 보장하는 대신, 비용 효율성을 희생한다는 점이다.

헷갈렸던 점#

처음에는 질문 유형을 먼저 판단하여 검색을 최소화하는 ‘Route First’ 방식이 더 효율적일 것이라 생각했으나, 시스템은 질문을 먼저 PDF에 노출시켜 근거를 확인한 뒤 라우팅함으로써 분류 오류로 인한 증거 부족 위험을 줄이는 ‘Retrieve-First’ 방식을 선택한다는 점을 이해하게 되었다.

특히 Router가 질문의 의도뿐만 아니라 실제로 검색된 데이터 내용까지 종합적으로 판단하여 RAG, Plain, Web 경로 중 최적의 답변 경로를 분기시킨다는 점이 핵심이었다. 이는 단순히 비용 절감보다는, 불필요한 지식 누락 없이 정확한 답변을 제공하기 위한 시스템의 설계 철학이 담겨 있었다.

정리된 이해#

검색-먼저(Retrieve-First) 방식은 PDF 관련 질문에 강력한 근거를 제공하지만 검색 비용이 발생하며, 라우팅(질문 분류) 전에 실제 문서 내용을 확인하여 최적의 답변 경로(RAG/Plain/Web)를 선택하는 장점이 있다. 반면 질문-먼저(Route-First) 방식은 검색 비용을 절감할 수 있지만 분류 오류 시 관련 증거를 놓칠 위험이 있어 품질과 비용 사이에서 균형을 잡아야 한다.

# Adaptive Search Path Selection Logic (Conceptual)

def select_answer_path(question: str, retrieved_data: list) -> str:
    """
    질문과 검색된 데이터를 기반으로 최적의 답변 경로(RAG, Plain, Web)를 선택합니다.
    """

    # 1. Router 판단: 질문의 성격과 실제 검색 결과 평가
    # (이 부분은 실제 시스템에서는 LLM이나 분류 모델에 의해 수행됩니다)
    need_rag = any(keyword in question.lower() for keyword in ['pdf', '문서', '보고서', '내용'])
    need_web = any(keyword in question.lower() for keyword in ['최근', '오늘', '날씨', '시세'])

    # 2. 경로 선택 로직
    if need_rag and retrieved_data:
        # PDF 내용이 필수적이고 검색 결과가 유효할 경우 RAG 경로 선택
        return "RAG"
    elif need_web:
        # 최신/실시간 정보가 필요할 경우 Web Search 경로 선택
        return "Web Search"
    else:
        # 일반 지식 질문의 경우 Plain Text 답변 생성
        return "Plain"

# 실행 예시 시뮬레이션
question = "오늘의 주식 시세는 어떻게 되나요?"
retrieved_docs = []  # PDF 검색 결과 (빈 리스트)

path = select_answer_path(question, retrieved_docs)
print(f"선택된 경로: {path}")
# 출력 예시: 선택된 경로: Web Search

2. State 구조와 Source Selection 통합#

무엇을 배웠나#

State 구조를 통해 RAG, 웹 검색, 빈 문자열 등 다양한 소스를 하나의 data 필드에 통합할 수 있다는 점을 배웠습니다. 다만 data라는 필드명이 너무 포괄적이어서 현재 source가 무엇인지 즉시 파악하기 어렵다는 점을 인지했습니다. 이를 해결하기 위해 source_type을 별도 관리하거나 evidence를 구조화하는 방식이 필요하다고 느꼈습니다.

헷갈렸던 점#

data 필드 하나에 RAG 문서, 웹 검색 결과, 빈 문자열이 모두 들어간다는 점에 가장 큰 혼란을 느꼈습니다. data라는 필드명이 너무 포괄적이어서, 안에는 무엇이 들어있는지 코드를 읽어보지 않으면 알 수 없었기 때문입니다. 특히 URL 같은 출처 정보가 data 문자열에 포함되지 않는다는 점이 아쉬웠습니다.

정리된 이해#

State 구조에서 data 필드가 RAG, 웹 검색, 빈 문자열 등 다양한 형태를 수용하면서도 일관된 답변 생성을 가능하게 한다는 점이 핵심입니다. 특히 Source Selection과 Evidence Normalization 과정을 통해 각 worker의 로직을 통합하고, 통일된 형식으로 데이터를 정규화함으로써 최종 답변 노드에서 복잡한 분기 처리를 피할 수 있다는 점이 인상적이었습니다.

3. 적응형 검색 설계 검토: 코드와 서비스의 간극#

무엇을 배웠나#

강사님의 시연을 통해 ‘기능 구현’과 ‘서비스 품질’ 사이의 간극을 실감했습니다. 단순히 코드가 동작하는지 확인하는 것을 넘어, 사용자가 의문을 가졌을 때 어떤 경로가 열려 있는지, 정보가 부족할 경우 어떻게 대응해야 하는지가 중요하다는 점을 깨달았습니다. 특히 clarify와 no_evidence 라우트가 설계에 포함된 이유를 통해, 신뢰성 있는 시스템을 위해서는 예외 처리와 추적 로직이 필수적임을 배웠습니다.

헷갈렸던 점#

처음에는 코드가 정상적으로 동작하는 모습을 보고 기능 구성이 완료된 것으로 착각하기 쉽습니다. 하지만 실제 서비스에서는 사용자가 경로 선택의 근거를 묻거나 정보가 부족할 때 어떻게 대처하는지가 중요하다는 점을 간과하고 있었습니다. 특히 clarify와 no_evidence 라우트가 설계에는 있지만 구현에는 없어 ‘왜 이 답변이 나왔는지’에 대한 투명성이 결여된 것처럼 느껴졌습니다.

정리된 이해#

작동하는 코드와 실제 서비스의 품질 요소는 별개라는 점을 깨달았다. 현재 구현은 rag → plain → web 세 경로를 최소 동작 단위로 연결한 학습용 프로토타입이지만, 실제 서비스 관점에서는 ‘근거의 충분성’, ‘출처 추적’, ‘폴백 행동’ 같은 요소가 동등하게 중요하다. 특히 정보가 부족할 때 사용자에게 물어주거나 없다고 인정하는 과정은 신뢰성을 위한 필수 요소이다.

def adaptive_search_router(query: str, context: dict) -> str:

총평#

오늘 오후 전체에서 배운 것#

검색-먼저 접근 방식은 라우터가 문서 내용을 정확히 판단하기 위해 필수적이지만, 비용 발생이라는 트레이드오프를 동반한다는 점을 명확히 이해했습니다. State 구조와 Source Selection을 통합하면서 data 필드의 포괄성으로 인해 소스 식별이 어렵다는 한계를 느껴, source_type 관리나 evidence 구조화의 필요성을 절실히 느꼈습니다. 마지막으로 코드 구현과 서비스 품질 사이의 간극을 실감했으며, clarify와 no_evidence 라우트 설계가 신뢰할 수 있는 시스템을 위한 필수적인 예외 처리와 추적 로직임을 깨달았습니다.

다음에 조심할 것#

검색-먼저 접근 방식은 분류 정확도를 보장하지만 비용이 발생한다는 trade-off를 명확히 인지하고, 불필요한 검색을 최소화하기 위해 라우터의 판단 기준을 정교하게 설계해야겠다.

State 구조 통합 시 data 필드의 포괄성으로 인해 source 식별에 혼선이 올 수 있으므로, source_type이나 evidence 구조화를 별도로 관리하여 시스템의 추적 가능성을 높이는 방향으로 개선하겠다.

기능 구현에만 집중하기보다 사용자의 의문 처리와 예외 상황(clarify, no_evidence 등)에 대한 로직을 설계에 반드시 포함시켜, 신뢰성 있는 서비스 품질을 보장하는 데 주력해야겠다.

다음 복습 주제#

오늘은 검색-먼저(Retrieve-first) 접근 방식의 장단점을 깊이 있게 이해할 수 있었다. 라우터가 문서 내용을 파악한 후 최적의 경로(RAG, Plain, Web)를 선택할 수 있다는 점에서 분류 오류를 방지하고 품질을 보장하는 효과가 있지만, 검색 비용이 발생한다는 트레이드오프가 있음을 명확히 했다.

State 구조와 Source Selection 통합에 대한 고민도 이어졌다. 다양한 소스를 하나의 data 필드에 통합할 수는 있으나, 필드명이 너무 포괄적이라 현재 소스의 출처를 즉시 파악하기 어렵다는 한계를 느꼈다. 이에 source_type을 별도로 관리하거나 evidence를 구조화하는 방안이 필요하다고 생각했으며, 이는 시스템의 투명성을 높이는 중요한 과제가 될 것이다.

마지막으로 적응형 검색 설계와 코드-서비스 간극에 대한 통찰을 얻었다. 단순히 기능이 동작하는지 확인하는 것을 넘어, 사용자가 의문을 가졌을 때 어떤 경로가 열려 있는지와 정보 부족 시의 대응 로직이 중요하다는 점을 깨달았다. clarify와 no_evidence 라우트의 존재는 신뢰성 있는 시스템 구축을 위한 예외 처리와 추적 로직의 필수성을 보여주었다.
