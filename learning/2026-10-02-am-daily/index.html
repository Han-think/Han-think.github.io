1. LLM 정보 경로 분리하기: Ollama, ChromaDB, Tavily#

무엇을 배웠나#

오늘은 LLM이 답을 생성하는 과정과 정보를 가져오는 과정을 분리하여 생각해야 한다는 점을 명확히 이해했습니다. 특히 Ollama가 ‘두뇌’ 역할을 하고, ChromaDB와 Tavily는 각각 개인 지식과 외부 최신 정보를 담당한다는 구분이 중요하다고 느꼈습니다. LangGraph 같은 도구를 통해 이 세 가지를 순서대로 연결하는 구조를 파악하게 되어 실무 적용 시 어떤 도구를 활용해야 할지 기준이 생겼습니다.

헷갈렸던 점#

처음에는 Ollama, ChromaDB, Tavily가 모두 “AI가 무언가를 하는 도구"라는 점에서 기능이 비슷하게 느껴져 구분하기 어려웠습니다. 특히 강사님의 설명으로 Ollama가 단순히 모델을 실행하는 툴이라는 사실보다 ‘내부 지식’의 대명사로 받아들여지면서 다른 도구의 역할이 더 혼동되었습니다. 이러한 혼란을 해소하기 위해 LLM이 답을 생성하는 과정과 정보를 가져오는 과정을 분리하여 생각해야 한다는 점을 가장중요하게 정리했습니다.

정리된 이해#

LLM은 답변을 생성하는 두뇌 역할을 수행하며, ChromaDB는 사내 자료와 같은 개인 맞춤형 지식 저장소로서 RAG를 지원하고 Tavily는 실시간 인터넷 정보를 제공하는 외부 검색 도구이다. 이 세 가지는 LangGraph 등 오케스트레이션 도구를 통해 질문의 목적에 따라 적절히 연계되어 활용된다.

# LLM 정보 경로 분리: Ollama, ChromaDB, Tavily 역할 시뮬레이션

def answer_question(query_type, data_source):
    """
    질문에 따라 적절한 '정보 경로'를 선택하는 함수.

    :param query_type: 'internal', 'external', 'custom'
    :param data_source: 사용자 제공 데이터 (RAG용) 또는 None
    :return: 답변 문자열
    """
    # 1. LLM (Ollama): 답변 생성의 '두뇌'
    #    내부 지식이나 외부 정보를 받아 텍스트를 완성함.

    if query_type == "internal":
        # 자체 학습 데이터 활용 (예: 수학, 코드, 일반적인 상식)
        # Ollama가 모델 가중치를 이용해 확률적으로 다음 토큰 예측
        return f"LLM(Ollama) 내부 지식으로 답변: '{query_type}' 질문에 대한 표준적 답변."

    elif query_type == "external":
        # 실시간 인터넷 정보 활용 (Tavily 경로)
        # 검색 후 LLM에 전달하여 최신성 보장
        return f"LLM(Ollama) + Tavily 외부 검색: '{query_type}' 질문에 대한 최신 정보 통합 답변."

    elif query_type == "custom":
        # 사용자 지정 지식 (ChromaDB 경로 - RAG)
        # ChromaDB에서 유사한 문서 검색 후 프롬프트에 주입
        if data_source:
            return f"LLM(Ollama) + ChromaDB RAG: '{query_type}' 질문에 맞춰 '{data_source}' 지식 기반 답변."
        else:
            return "오류: ChromaDB에 저장된 커스텀 데이터가 필요합니다."

    # 기본 경우
    return "알 수 없는 경로입니다."

2. Tavily 검색의 핵심 차이점: 로컬 vs 웹 검색#

무엇을 배웠나#

Tavily 웹 검색과 RAG(로컬 데이터베이스)의 핵심 차이는 ‘검색 대상’과 ‘통제 범위’에 있다. ChromaDB는 미리 저장된 지식 기반 내에서 검색하는 반면, Tavily는 실시간으로 인터넷상의 외부 정보를 가져오는 점이 다르다. 특히 Tavily는 단순히 답을 제공하는 도구가 아니라 LLM이 답변을 구성할 수 있는 외부 증거를 공급하는 역할을 한다는 점에서 중요했다. 실습을 통해 search_depth나 time_range 같은 옵션이 결과의 최신성과 구체성에 어떻게 영향을 주는지 확인할 수 있었다.

헷갈렸던 점#

처음에는 RAG와 Tavily 웹 검색이 단순히 ‘검색’이라는 행위만으로 비슷하게 느껴져 헷갈렸다. 하지만 검색 대상(로컬 데이터베이스 vs 외부 인터넷)의 차이와 최신성, 비용 및 통제 범위의 차이가 핵심임을 깨달았다. 특히 Tavily가 답을 직접 주는 도구가 아니라 LLM 답변을 구성하는 외부 증거를 공급한다는 점이 중요했다.

정리된 이해#

RAG는 기존 지식 기반 내에서 검색하는 반면, Tavily 웹 검색은 인터넷상에서 최신 정보를 실시간으로 확보하는 점에서 결정적인 차이가 있다. 특히 Tavily는 LLM이 답변을 구성하는 데 활용할 외부 증거를 공급하는 역할을 한다는 점이 중요하다. 따라서 두 방식은 검색 대상의 범위와 최신성, 비용 및 신뢰도 면에서 명확히 구분된다.

# 기본 검색 (일반적인 정보 조회)
search = TavilySearch(
    max_results=3,
    search_depth="basic",
    topic="general"
)

# 고급 검색 (최근성, 제외 도메인 등 활용)
TavilySearch(
    include_answer=True,
    include_raw_content=True,
    time_range="week",  # 최근 일주일 내의 정보
    exclude_domains=["example.com"]  # 특정 도메인 제외
)

3. .env와 .gitignore로 API Key 분리하기#

무엇을 배웠나#

오늘은 코드와 API 키를 분리하는 것이 왜 중요한지 실감했습니다. 이전에는 단순히 ‘키를 어딘가에 적으라’는 지시를 따라 했을 뿐이었지만, 이제는 소스 코드는 공유해도 되고 비밀키는 비밀로 해야 한다는 구분이 생겼습니다. 특히 .gitignore를 통해 의도치 않게 키가 Git에 업로드되는 것을 막고, 과거의 실수로 인해 이미 history에 노출된 키는 사라지지 않는다는 점을 반드시 기억해야 합니다.

헷갈렸던 점#

코드와 실제 키를 같은 선상에서 생각했던 것이 가장 큰 오류였습니다. .env 파일에 값을 넣는다고 해서 코드가 끝나는 줄 알았는데, .gitignore를 통해 업로드를 막아야 한다는 안전장치의 존재를 몰랐습니다. 이미 Git 히스토리에 시크릿이 commit된 경우, 나중에 .gitignore를 추가해도 과거의 비밀키가 사라지지 않는다는 점을 반드시 주의해야 합니다.

정리된 이해#

코드와 실제 키는 분리해야 하며, .env 파일은 Git에 업로드되지 않도록 .gitignore로 관리해야 한다. 이미 Git history에 키가 포함된 경우, .gitignore 추가만으로는 과거의 유출을 막을 수 없으므로 키 교체가 필수적이다.

1) .env 파일 생성 및 키 입력

# .env 파일 (Gitignore 적용 전용)
OPENAI_API_KEY=sk-abcdefghijklmnopqrstuvwxyz123456

2) 코드에서 변수 사용하기

import os

# .env 파일의 값을 자동으로 로드하여 환경 변수로 만듦 (dotenv 라이브러리 가정)
from dotenv import load_dotenv
load_dotenv()

# 실제 키 값은 몰라도 되고, 변수명만 알면 됨
api_key = os.getenv("OPENAI_API_KEY")

print(f"API Key loaded: {api_key}")

3) .gitignore 설정

# .gitignore 파일 내용
.env

오늘 오전 전체에서 배운 것#

LLM의 답변 생성과 정보 검색 과정을 분리하여, Ollama가 ‘두뇌’ 역할을 하고 ChromaDB와 Tavily가 각각 개인 지식과 외부 정보를 담당한다는 구조를 명확히 이해했습니다. 또한, .env와 .gitignore를 활용해 API 키를 코드에서 분리 관리하는 것이 보안 유지의 필수적임을 깨닫고, 실무 적용 시 도구 선택의 기준을 세웠습니다.

다음에 조심할 것#

  1. .gitignore를 통해 API 키가 코드와 함께 Git에 업로드되지 않도록 철저히 관리하여 보안 사고를 예방한다.
  2. ChromaDB(내부 지식)와 Tavily(외부 실시간 정보)의 역할을 명확히 구분하여, 상황에 맞는 도구를 선택해 LLM의 답변 품질을 높인다.
  3. search_depth 등 검색 옵션을 조정하여 결과의 최신성과 구체성을 세밀하게 제어하는 습관을 들인다.

  2. 실제 프로젝트에서 API 키 관리의 실수를 방지하기 위해 .env 파일 구성과 .gitignore 설정 전략을 직접 구현해보고, 과거 이력에 노출된 민감한 정보의 위험성을 재확인하는 시간을 갖겠습니다.
