1. RAG 웹 서비스 완성: 파일·DB·검색 통합 흐름#

무엇을 배웠나#

오늘은 RAG 알고리즘 자체를 새로 배우는 것이 아니라, 기존 구성 요소를 웹 서비스 구조로 연결하고 분리하는 과정에 집중했습니다. file_service, rag_service, llm_service 등의 역할 분담을 통해 ‘기존 코드를 이동시킨 것인가?‘라는 경계가 모호했던 부분을 명확히 정리할 수 있었습니다. 특히 PDF 업로드 후 청크 분할과 메타데이터를 활용한 검색 범위 제한이 실제 애플리케이션 구조에서 어떻게 작동하는지 이해하는 것이 핵심이었습니다.

헷갈렸던 점#

RAG 알고리즘 자체를 새로 배우는 것이 아니라, 기존 구성 요소를 웹 서비스 구조로 연결하고 분리하는 과정에서 파일 이동처럼 보여 개념 학습이 혼동되었다.

특히 main.py, file_service.py, rag_service.py 등 각 파일의 역할 분담과 메타데이터 필터링 방식, 그리고 LLM 출력을 실시간으로 전달하는 스트리밍 응답의 메커니즘이 어떻게 작동하는지 감 잡기 어려웠다.

정리된 이해#

오늘은 RAG 알고리즘 자체를 새로 배우는 것이 아니라, 기존 구성 요소를 FastAPI 웹 서비스 구조에 맞게 연결하고 분리하는 과정이었습니다. 핵심은 PDF 업로드를 통해 청크와 메타데이터를 Chroma 벡터 DB에 저장하고, 사용자 질의 시 subject 메타데이터를 활용해 검색 범위를 제한하는 흐름을 완성한 점이었습니다. 특히 StreamingResponse를 활용한 LLM 출력의 실시간 전송 메커니즘을 이해하며, 계층적 서비스 구조 내에서 각 모듈의 역할이 어떻게 상호작용하는지 명확히 정리할 수 있었습니다.

# 1. 파일 업로드 및 Chroma DB 저장 (file_service.py 등)
def ingest_pdf(file_content, subject):
    # PDF를 청크(chunk)로 분할하고 메타데이터(subject)와 함께 Chroma에 저장
    chunks = split_text(file_content)
    metadatas = [{"subject": subject}] * len(chunks)
    vectorstore.add_documents(chunks, metadatas=metadatas)

# 2. 주제 기반 검색 (rag_service.py 등)
def retrieve_docs(query, subject):
    # subject 메타데이터를 필터로 적용하여 검색 범위 제한
    filters = {"subject": subject}
    results = vectorstore.similarity_search(query, filter=filters)
    return results

# 3. 스트리밍 LLM 응답 (llm_service.py 등)
def stream_llm_response(messages):
    # LLM의 출력을 토큰 단위로 실시간 전달
    response = llm.stream(messages)
    for token in response:
        yield token.content

2. LLM을 ‘코드 생성기’로 재정의하기#

무엇을 배웠나#

LLM을 단순히 정보를 제공하는 답변기로가 아니라, 데이터 분석을 위한 실행 가능한 Python 코드를 설계하는 프로그램러로 재정의하는 것이 핵심이었다. 특히 질문→코드 생성→Python 실행이라는 새로운 흐름에 적응하면서, LLM이 직접 데이터를 처리하는 것이 아니라 코드를 ‘설계’하는 보조자의 역할을 한다는 점이 가장 크게 와닿았다.

헷갈렸던 점#

LLM이 단순히 질문에 답변하는 ‘지식 전달자’에서, 사용자의 의도를 Python 코드로 번역해주는 ‘프로그램러’로 역할이 전환된 점이 가장 낯설었습니다. 특히 LLM이 생성한 코드를 실행하기 위해 별도의 파서와 실행 환경이 필요하다는 점은, LLM의 출력을 단순히 텍스트로 끝나는 것이 아니라 실제 동작하는 프로그램으로 가공해야 한다는 사실에 적응하는 데 시간이 걸렸습니다.

정리된 이해#

LLM을 ‘답변 생성기’에서 ‘코드 생성기’로 재정의하는 것이 핵심입니다. LLM은 데이터를 직접 분석하는 것이 아니라, Pandas나 Python 문법을 활용해 데이터를 조작할 방법을 설계하는 역할을 수행합니다. 또한, LLM이 반환한 코드를 안전하게 실행하기 위한 경계 설정과 후처리가 필수적임을 명확히 했습니다.

📌 핵심 요약: LLM을 데이터 분석 ‘코드 생성기’로 재정의#

1. 역할 전환의 핵심#

  • 기존 RAG 방식: 질문 → LLM → 자연어 답변 (사용자가 직접 읽음)
  • 데이터 분석 워크플로우: 질문 → LLM → Python code → Python 실행 → 결과 (시스템이 처리)

LLM은 데이터를 직접 조작하는 것이 아니라, Pandas/python 문법을 활용해 데이터를 조작할 ‘방법(코드)‘을 설계하는 역할을 수행합니다.

2. 실습 흐름 (강사 예시)#

  1. CSV 파일을 Pandas DataFrame으로 미리 읽어옵니다.
  2. DataFrame의 컬럼 목록과 스키마를 프롬프트에 포함합니다.
  3. 사용자의 자연어 질문을 LLM에게 전달하여 Python 코드를 생성하게 합니다.
  4. LLM 출력을 마크다운 코드 블록(```python ... ```) 내의 실제 실행 코드로 제한하여 추출 후 실행합니다.

3. 출력 규약 (중요)#

강사님의 지시에 따라, LLM이 생성한 코드는 반드시 백틱 3개(```)로 둘러싸인 Python 코드 블록 형태로만 출력해야 합니다. 노트에 코드 근거가 없으면 아무것도 쓰지 않습니다.

💡 실습 예시 (구조화된 흐름)#

전제 조건#

  • CSV 파일이 Pandas DataFrame으로 미리 로드되어 있습니다.
  • DataFrame의 컬럼명과 데이터 타입(스키마)가 프롬프트에 포함됩니다.

1. 프롬프트 구성 (Prompt Engineering)#

사용자의 질문은 LLM이 코드를 생성할 수 있도록 구조화된 컨텍스트와 함께 전달되어야 합니다.

예시 프롬프트:

You are a Python data analyst. Your task is to generate Pandas code to answer the user's question based on the provided DataFrame schema and head.

DataFrame Schema:
- col_a: int
- col_b: str
- col_c: float

User Question: {user_query}

2. 코드 생성 및 출력 규약#

LLM은 사용자의 질문에 대응하는 Python 코드를 생성합니다. 출력은 반드시 아래 형식을 따릅니다.

# LLM이 생성한 실제 실행 코드만 포함
import pandas as pd

# 예시 필터링 로직 (실제 질문 내용에 따라 변동)
result = df[df['col_a'] > 10]

print(result)

3. 후처리 및 실행#

  • LLM의 출력을 StrOutputParser 등을 통해 문자열로 추출합니다.
  • 문자열에서 python 와 사이의 내용을 식별하여 Python 환경에 전달합니다.
  • 추출된 코드를 안전하게 실행(사용자 정의 함수 제한 등)하고 결과를 사용자에게 반환합니다.

3. 파이썬 코드 파이프라인 단계 구분: 질문-원시텍스트-코드-실행결과#

무엇을 배웠나#

LLM이 생성한 텍스트를 실제 Python 코드로 변환하고 실행하여 결과를 받아오는 파이프라인의 핵심은 문자열 형태가 같더라도 그 안에 담긴 의미와 목적에 따라 단계별 역할이 구분된다는 점입니다. 특히 question, raw_llm_output, python_code, tool_output 같은 중간 단계는 형식적으로는 모두 문자열이지만, 코드 포함 여부와 실행 상태에 따라 그 기능이 완전히 다르다는 점을 명확히 이해하는 것이 중요합니다.

헷갈렸던 점#

처음에는 LLM이 생성한 모든 출력이 문자열로 보여서, 현재 단계가 코드 작성 단계인지 결과 확인 단계인지 구분하기 어려웠습니다. 특히 raw_llm_output와 python_code가 모두 텍스트 형태라서, “지금 이 문자열은 실행 가능한 코드인가, 아니면 그냥 설명인가?“라는 혼란이 들곤 했습니다. 하지만 파이프라인 구조를 이해한 후에는, 각 단계가 문자열이라는 동일한 포맷을 공유하면서도 그 안의 의미와 목적(코드 작성 여부, 실행 결과 등)이 완전히 다르다는 점을 명확히 인식할 수 있게 되었습니다.

정리된 이해#

LLM이 생성한 텍스트를 실제 Python 코드로 실행하고, 그 결과를 다시 텍스트로 받아오는 일련의 과정이며, LangChain의 pipe 연산자를 사용해 LLM뿐만 아니라 일반 파이썬 함수도 처리 단계에 연결할 수 있습니다. 질문에서 시작해 원시 텍스트, 추출된 코드, 그리고 실행 결과까지 이어지는 각 단계는 형식은 문자열이지만 그 안의 의미와 목적은 완전히 다르다는 점을 명확히 하는 것이 중요합니다.

📌 Python Code Extraction & Execution Pipeline (LLM + LangChain)#

🔰 초보자 시점, 학습자의 혼란#

처음 이 파이프라인을 마주했을 때 가장 든 생각은 **“모든 게 문자열로 보여서 무슨 단계가 진행되고 있는지 구별이 안 된다”**는 것이었습니다. LLM이 내놓은 답변, 실제 Python 코드, 실행된 결과물까지 모두 str 타입으로 보이니, 현재 어떤 단계의 데이터가 흐르고 있는지 감을 잡기 힘들었죠. 특히 question에서 시작해 raw_llm_output, python_code, tool_output까지 이어지는 흐름을 눈으로 추적하다 보면, “지금 이 문자열은 코드야? 아니면 실행된 결과야?“라는 혼란이 들곤 했습니다.

📌 정리된 이해#

이 pipeline의 핵심은 **“LLM이 생성한 텍스트를 실제 Python 코드로 실행하고, 그 결과를 다시 텍스트로 받아오는 일련의 과정”**입니다. LangChain의 pipe(|) 연산자를 사용하면 LLM뿐만 아니라 일반 파이썬 함수도 processing stage로 연결할 수 있다는 점이 핵심입니다.

중간 단계들의 역할 구분은 다음과 같습니다.

  1. question: 사용자의 질문이나 프롬프트
  2. raw_llm_output: LLM이 생성한 원시 텍스트 (여기서 코드가 포함될 수 있음)
  3. python_code: LLM으로부터 추출된 실제 실행 가능한 Python 코드 문자열
  4. tool_output: exec()를 통해 실행된 후 나오는 결과 (print문의 출력 등)

형식은 모두 문자열이지만, 그 안의 의미와 목적은 완전히 다르다는 점을 명확히 하는 것이 중요합니다.

💻 실습 예시#

가장 기본적인 흐름을 코드로 표현하면 이렇습니다.

from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
import io
import contextlib

# 1. LLM이 코드를 생성한다고 가정
def code_gen(question):
    # 실제로는 LLM 호출, 여기서는 더미 반환
    return f"print('Hello from AI')"

# 2. Python 코드 파싱 (문자열 그대로 통과하거나 추출하는 과정)
parsed_code = code_gen("test question")

# 3. 실행 전용 네임스페이스 및 출력 스트림 설정
namespace = {}
output_capture = io.StringIO()

# 4. 실제 exec()를 통한 코드 실행
with contextlib.redirect_stdout(output_capture):
    exec(parsed_code, namespace)

# 5. 실행 결과 텍스트 추출
tool_output = output_capture.getvalue()

print(f"📤 최종 출력: {tool_output}")

💡 핵심 요약#

  • question: 사용자 입력
  • raw_llm_output: LLM이 뱉은 원시 텍스트 (코드 포함 가능)
  • python_code: 실제 실행 가능한 코드 문자열로 추출된 상태
  • tool_output: exec() 실행을 통해 얻은 결과 텍스트

모든 단계가 str 타입이지만, **“의도된 역할”**에 따라 다음 단계로 넘어가는 전이 과정이 달라진다는 점을 기억해야 합니다.

총평#

오늘 오전 전체에서 배운 것#

RAG 웹 서비스 구축 과정에서 기존 코드를 기능별로 재정비하고, PDF 업로드부터 검색까지의 데이터 흐름을 명확히 정리했습니다. 또한 LLM을 단순한 답변 제공자가 아닌, 데이터를 처리하는 Python 코드를 설계하는 ‘프로그래머’로 재정의하며 질문→코드 생성→실행이라는 새로운 파이프라인 구조를 이해하게 되었습니다.

다음에 조심할 것#

RAG 서비스 통합 과정에서 느꼈던 코드 역할의 모호함을 경계 삼아, 앞으로는 file_service, rag_service 등 각 컴포넌트의 책임을 명확히 정의하고 분리하는 습관을 들일 것이다.

LLM을 단순한 답변기가 아닌 ‘코드 설계자’로 재정의한 만큼, 다음 단계에서는 LLM이 생성한 텍스트가 실제 Python 코드로 실행될 수 있도록 프롬프트와 파이프라인 구조를 더욱 정교하게 검증하는 데 집중할 것이다.
