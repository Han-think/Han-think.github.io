1. SQL 프롬프트 경계 확인하기#

무엇을 배웠나#

명령을 입력하기 전 현재 프롬프트가 어디인지 확인하는 습관의 중요성을 깨달았다. Linux Shell과 MariaDB Shell의 구분 없이 섞여 있으면 SQL 문법 오류와 파일 경로 오류가 발생한다. 이를 통해 SQL 문법과 운영체제 명령어의 경계를 명확히 구분할 수 있게 되었다.

헷갈렸던 점#

수업 초반, ec2-user@...$와 MariaDB> 프롬프트가 섞여 나오면 무의식적으로 SQL 문법을 리눅스 Shell에 입력하거나 반대로 복원 명령을 DB 내부에서 실행하려 했던 것이 가장 큰 혼란이었습니다. 특히 dump 파일을 찾을 수 없다는 에러와 데이터베이스가 없다는 에러가 교차하면서, 문제 발생 단계를 추적하기 어려웠습니다. 핵심은 명령어를 입력하기 전 반드시 현재 프롬프트가 리눅스 Shell인지 DB Shell인지를 먼저 확인하는 습관을 들이는 것입니다.

정리된 이해#

명령을 입력하기 전 현재 프롬프트가 Linux Shell인지 MariaDB Shell인지 반드시 확인하는 습관이 가장 중요합니다. SQL 문법과 운영체제 명령어는 엄연히 다른 영역이므로, 혼동되지 않도록 환경 경계를 명확히 구분해야 합니다. dump 복원 시에는 Linux Shell에서 파일 경로를 지정해 MariaDB 서버에 전달하는 구조를 이해하면 오류 추적이 쉬워집니다.

# Linux/PuTTY 환경 (Shell)
ec2-user@ip-address$ mysql -u root -p employees < test_data/employees.sql

# MariaDB Shell 환경 (SQL)
MariaDB [(none)]> USE employees;
MariaDB [employees]> SOURCE test_data/employees.sql;

2. employees DB 현재값과 이력값 구분하기#

무엇을 배웠나#

SQL JOIN 시 결과 행이 중복되는 것은 데이터 구조상 자연스러운 현상으로, 직원 한 명이 여러 직책을 가질 수 있는 1:N 관계 때문입니다. to_date = '9999-01-01' 조건은 현재 유효한 이력을 조회하는 기준이 되며, 이를 통해 과거의 변경 이력도 보존하면서 현재 상태를 정확히 확인할 수 있습니다. 데이터베이스를 분리 관리함으로써 직책이나 부서 변동 등 이력을 추적하고 저장할 수 있는 구조적 장점이 있음을 이해했습니다.

헷갈렸던 점#

JOIN을 처음 배울 때, 같은 이름의 행이 여러 번 반복되는 현상을 데이터 오류로 직관적으로 해석했습니다. 특히 to_date = '9999-01-01' 조건이 왜 필요한지 감 잡기 어려웠습니다. 이번 학습을 통해 결과 행의 중복은 1:N 관계의 정상적인 산물이며, 특정 날짜 조건을 붙여야 현재 상태를 조회할 수 있다는 점을 명확히 이해하게 되었습니다.

정리된 이해#

JOIN 연산은 테이블 간의 1:N 관계에서 자연스럽게 행이 중복되는 것이 데이터 구조의 정상적인 산물이며, 이는 오류가 아닙니다. 현재값과 이력값을 구분하기 위해서는 to_date = '9999-01-01'와 같은 조건을 통해 ‘현재 상태’를 나타내는 특정 기준을 적용해야 합니다. 이러한 테이블 분리 및 날짜 관리 방식은 직책 변경 등 이력을 정확하게 추적하고 보존하기 위한 데이터베이스의 설계 의도입니다.

SELECT e.first_name, t.title, t.from_date, t.to_date
FROM employees e
JOIN titles t ON e.emp_no = t.emp_no
WHERE t.to_date = '9999-01-01';

3. 팀 이동 사원 ID 추출하기#

무엇을 배웠나#

GROUP BY와 HAVING를 사용해 조건을 걸고, 그 결과를 IN 절에 넣는 방식으로 서브쿼리의 흐름을 파악할 수 있었다. 처음에는 전체 쿼리를 한 번에 이해하려 했지만, ‘사번 추출’과 ‘정보 조회’라는 두 단계로 나누니 데이터가 어떻게 움직이는지 명확해졌다. 특히 상관 서브쿼리는 안쪽에서 바깥쪽으로 데이터가 흐른다는 점을 인식하니 이전보다 훨씬 직관적으로 느껴졌다.

헷갈렸던 점#

처음 이 문제를 마주했을 때, SQL 문장 전체가 하나의 거대한 퍼즐처럼 느껴졌다. GROUP BY, HAVING, IN, 그리고 서브쿼리가 뒤섞여 있어 “이게 무슨 순서로 돌아가는 거지?“라는 막막함이 들었다. 특히 문제 3에서 이름과 팀명을 한 번에 가져오는 상관 서브쿼리를 볼 때는, DB 안쪽에서 바깥쪽으로 어떻게 데이터가 흐르는지 감조차 잡기 힘들었다. “완성된 쿼리를 외워야 하나?“라는 생각도 들었지만, 막상 실행해 보니 이해하는 데 훨씬 시간이 걸렸다.

이번 학습의 핵심은 **‘조건이 있는 테이블에서 ID를 찾는다 → 그 ID로 필요한 정보를 가져온다’**는 흐름이었다. 1단계: dept_emp 테이블에서 사원 번호(emp_no)를 기준으로 그룹화하고, 부서 기록이 2개 이상인(Having cnt > 1) 사번을 추출한다. 2단계: 추출한 사번을 가지고 employees 테이블에서 이름이나 departments 테이블에서 팀명을 조회한다.

dept_emp → emp_no → employees/department

이렇게 중간 결과물(사번 리스트)을 두어두니, 복잡한 쿼리도 “어떤 사번을 찾았지?“만 생각하면 돼서 훨씬 수월했다.

정리된 이해#

이번 학습의 핵심은 ‘조건이 있는 테이블에서 ID를 찾는다 → 그 ID로 필요한 정보를 가져온다’는 흐름이었다. 먼저 dept_emp 테이블에서 부서 기록이 2개 이상인 사원 번호를 추출한 뒤, 이를 기준으로 employees 또는 departments 테이블에서 이름과 팀명을 조회하는 방식이었다. 이렇게 중간 결과물(사번 리스트)을 두어두니 복잡한 쿼리도 ‘어떤 사번을 찾았나’에 집중할 수 있어 이해가 용이했다.

-- 문제 2: 팀 이동이 있었던 사원의 이름
-- 1단계: 부서 기록이 2개 이상인(팀 이동) 사원 번호 추출
SELECT emp_no
FROM dept_emp
GROUP BY emp_no
HAVING COUNT(*) > 1;

-- 2단계: 추출한 사번으로 employees 테이블에서 이름 조회
SELECT first_name, last_name
FROM employees
WHERE emp_no IN (
    SELECT emp_no
    FROM dept_emp
    GROUP BY emp_no
    HAVING COUNT(*) > 1
);

총평#

오늘 오전 전체에서 배운 것#

SQL 프롬프트 경계 확인 습관의 중요성을 깨닫고, Linux Shell과 MariaDB Shell 구분 없이 섞이면 문법 오류가 발생한다는 점을 명확히 했다.

employees DB에서 JOIN 시 행이 중복되는 것은 1:N 관계 구조상 자연스러운 현상으로, to_date = '9999-01-01' 조건을 통해 현재 유효한 이력을 조회하면서 과거의 변경 이력도 보존할 수 있음을 이해했다.

GROUP BY와 HAVING를 사용해 사번을 추출하고 IN 절에 넣는 방식으로 서브쿼리의 흐름을 파악했으며, 데이터가 안쪽에서 바깥쪽으로 흐른다는 상관 서브쿼리의 특성을 인식하니 쿼리 작성 직관성이 크게 향상되었다.

다음에 조심할 것#

SQL 문법과 쉘 명령어를 혼동하지 않도록 프롬프트 경계를 항상 확인하는 습관을 들일 것이다. JOIN 시 발생할 수 있는 결과 행의 중복을 단순히 오류로 여기지 않고, 데이터 구조상 자연스러운 현상으로 받아들이며 to_date 조건을 통해 현재 이력을 정확히 조회하는 방법을 적용할 것이다. 복잡한 쿼리는 한 번에 이해하려 하기보다 ‘사번 추출’과 ‘정보 조회’라는 두 단계로 나누어 데이터를 추적하는 흐름을 명확히 파악하도록 노력할 것이다.

다음 복습 주제#

다음 학습에서는 JOIN을 활용한 테이블 간의 데이터 연결 방법을 심화적으로 다뤄보고 싶습니다. 특히, 여러 테이블이 어떻게 관계를 맺고 있는지 시각화하고, 각 조인의 차이점(내부조인, 외부조인 등)을 정확히 이해하여 의도하지 않은 데이터 누락이나 중복을 방지하는 연습을 하고자 합니다. 또한, 앞서 learned한 서브쿼리의 흐름을 응용해 복잡한 조건을 한 번에 해결하는 대신, 단계별로 쿼리를 분해하여 논리적으로 풀어내는 습관을 further 강화하고 싶습니다.
