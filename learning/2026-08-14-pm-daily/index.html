1. Next.js App Router에서 Server Component와 Client Component의 경계 이해하기#

무엇을 배웠나#

Next.js App Router에서는 컴포넌트의 기본 실행 위치가 서버이며, 브라우저 상태 관리나 이벤트 처리가 필요할 때 최상단에 'use client'를 선언하여 클라이언트 컴포넌트로 명확히 구분해야 한다. function Component() 자체는 자동으로 서버와 클라이를 구분하지 않으며, 실행 위치는 UI의 모양뿐만 아니라 코드가 어디서 실행되는지를 결정하는 중요한 설계 요소이다.

헷갈렸던 점#

Next.js App Router에서는 컴포넌트의 기본 실행 위치가 서버이므로, 브라우저 상태 관리나 이벤트 처리가 필요할 때 'use client' 선언을 반드시 붙여야 한다는 점이 가장 큰 혼란 포인트였다.

특히 React에서 useState 같은 훅을 아무 곳에든 쓸 수 있었던 익숙함과 달리, Next.js에서는 컴포넌트의 위치가 ‘코드가 실행되는 곳’을 결정하는 핵심 요소가 되어 기존의 직관적인 사용 패턴이 깨진 느낌을 받았다.

정리된 이해#

Next.js App Router는 기본적으로 Server Component이며, 브라우저 상태 관리나 이벤트 처리가 필요할 때 최상단에 'use client'를 선언하여 Client Component로 전환해야 한다. 컴포넌트의 위치가 단순히 UI의 모양을 결정하는 것을 넘어, 코드가 실행되는 환경(서버 또는 클라이언트)을 가르는 중요한 설계 요소가 된다.

// 1. 기본적으로 Server Component (별도 선언 없음)
export default function Profile() {
  return <div>서버에서 렌더링된 프로필</div>;
}

'use client';
import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>카운트: {count}</p>
      <button onClick={() => setCount(count + 1)}>증가</button>
    </div>
  );
}

2. Axios 상태 관리와 조건부 렌더링#

무엇을 배웠나#

React와 Axios를 활용한 데이터 흐름에서 가장 중요한 점은 API 요청 후 useState로 상태를 관리하고, 이를 자식 컴포넌트에 전달하여 화면에 렌더링하는 것입니다. 특히 데이터를 보여줄 때 조건문을 어디에 배치해야 할지 고민했지만, 결국 목록을 구성하는 Post 컴포넌트 내에서 list.length를 확인해 데이터가 없을 경우 빈 화면을 방지하는 것이 가장 자연스럽다는 것을 배웠습니다. 또한 useState의 초기값이 비어있는 배열 []인 것은 ‘데이터가 아직 없는 상태’를 의미하며, Axios 요청 완료 후 State가 업데이트되면 React가 자동으로 화면을 갱신해 최신의 목록을 보여준다는 사실도 핵심적으로 익혔습니다.

헷갈렸던 점#

Axios 요청 후 setList를 호출해도 화면이 바로 갱신되지 않는 것처럼 느껴져, State 업데이트 시점이 언제인지 혼란스러웠습니다. 리액트의 비동기 처리와 리렌더링 주기가 맞물려 있어, 데이터가 실제로 화면에 반영되기까지의 시차를 예측하기 어려웠습니다. 특히 useEffect 내부에서 상태를 관리할 때, dependency 배열에 API 호출 함수가 포함되지 않아 무한 루프가 발생하거나 데이터가 업데이트되지 않는 등 타이밍 조절에 시행착오를 겪었습니다.

정리된 이해#

Axios로 API 데이터를 받아 useState에 저장하면 React가 자동으로 화면을 갱신해 최신의 목록을 보여준다. 데이터가 없을 때는 빈 배열([]) 상태를 활용해 조건부 렌더링을 수행하는 것이 자연스럽다. 핵심은 State 업데이트 후 컴포넌트 내 map() 함수를 통해 리스트를 출력하고, 화면 표시 여부는 해당 컴포넌트에서 판단하는 것이다.

// Page.jsx: API 주소 전달 및 컴포넌트 렌더링
import SendList from "@/app/SendList";

function Page() {
  return (
    <div>
      {/* SendList 컴포넌트에 API 주소를 props로 전달 */}
      <SendList apiUrl="https://jsonplaceholder.typicode.com/posts" />
    </div>
  );
}

export default Page;

// SendList: Axios 요청 후 State에 저장하고 Post에 전달
import { useEffect, useState } from "react";
import Post from "@/app/Post";

function SendList({ apiUrl }) {
  const [list, setList] = useState([]); // 초기값은 빈 배열

  useEffect(() => {
    // Axios를 사용하여 API 데이터 요청
    axios.get(apiUrl).then((response) => {
      // 받아온 데이터를 State에 저장하여 리렌더링 유도
      setList(response.data);
    });
  }, [apiUrl]);

  // list prop을 Post 컴포넌트에 전달
  return <Post list={list} />;
}

export default SendList;

// Post: received list를 조건부 매핑하여 출력
import { useEffect, useState } from "react";

function Post({ list }) {
  // 데이터가 없을 경우를 대비한 조건부 렌더링
  if (!list.length) {
    return <div>로딩중...</div>;
  }

  // map으로 목록 구성 (두 번째 인자 idx는 key 용도로 사용하므로 실제로는 안 씀)
  return (
    <ul>
      {list.map((item, idx) => (
        <li key={idx}>{item.title}</li>
      ))}
    </ul>
  );
}

export default Post;

3. 네트워크 주소 체계의 모든 것#

무엇을 배웠나#

처음에는 localhost:3000 같은 주소가 하나의 덩어리로 보여서 각 요소가 어떤 역할을 하는지 구분하기 어려웠습니다. 하지만 host, port, path, query가 각각 네트워크 상의 대상, 서비스 지정, 구체적인 자원 탐색, 추가 조건 전달이라는 서로 다른 계층을 담당한다는 사실을 이해하면서 주소 구조가 명확해졌습니다. 이제 포트 번호는 특정 프로그램에 데이터를 보내는 입구고, 경로와 쿼리는 그 안쪽으로 들어가는 세부 지침 정도로 인식하게 되었습니다.

헷갈렸던 점#

localhost 뒤에 붙는 숫자가 포트인지 경로인지 구별할 수 없었고, 같은 포트를 두 프로그램이 쓰면 안 되는 이유도 이해하지 못했다. 도메인 이름을 실제 IP 주소로 변환하는 DNS의 작동 원리가 막연하게만 느껴졌다. URL 구성 요소들이 각기 다른 역할을 하는 것이 아니라 하나의 문자열처럼 보여서 구분하기 힘들었다.

정리된 이해#

네트워크 상에서 데이터를 전송할 때는 host가 목적지 컴퓨터를, port가 내부 서비스를 지정하고, path와 query는 각각 구체적인 자원과 추가 조건을 의미한다. 이를 통해 localhost:3000/blog?idx=11 같은 URL은 host, port, path, query가 각기 다른 역할을 수행하는 복합 주소임을 명확히 이해할 수 있다.

# URL 구조 요약 (학습 노트 기반)

📍 기본 구조#

[protocol]://[host]:[port]/[path]?[query]

🔢 포트 번호의 의미#

  • localhost:3000에서 3000은 **포트(Port)**이며, 특정 서비스(앱)가 listening하고 있는 통신 endpoint를 지정합니다.
  • 같은 컴퓨터 내에서도 포트가 다르면 서로 다른 프로그램에 데이터가 전달됩니다.

🛤️ 경로와 쿼리의 구분#

  • /blog와 같이 URL의 중간 부분은 path이며, 서비스 내부에서 특정 페이지나 자원을 탐색하는 역할을 합니다.
  • ?idx=11과 같이 물음표(?) 뒤는 query이며, 서버에 전달할 추가 조건이나 파라미터(예: 게시글 ID 등)를 의미합니다.

🏠 호스트와 포트의 관계#

  • host (IP/도메인): 데이터를 보낼 ‘대상 컴퓨터’를 찾습니다.
  • port: 대상 컴퓨터 내부에서 데이터를 받을 ‘특정 서비스(앱)‘를 지정합니다.

4. Next.js 오후 흐름, Server와 Client의 경계#

무엇을 배웠나#

오늘은 React에서 이미 익숙했던 문법들이 Next.js에서는 Server Component와 Client Component라는 새로운 컨텍스트 안에서 어떻게 재구성되는지 확인하는 시간이었습니다. 특히 use client 디렉터리와 실행 위치의 경계가 명확하지 않아, 기존 지식과 새 지식이 어디서 끝나는지 파악하는 데 집중했습니다. 결국 Next.js는 개별 문법이 아니라 웹 애플리케이션 전체를 관통하는 하나의 흐름으로 이해해야 한다는 점이 오늘의 핵심 통찰이었습니다.

헷갈렸던 점#

React에서 이미 익숙한 문법들이 Next.js에서는 Server Component와 Client Component라는 새로운 컨텍스트 안에서 다시 등장하여, 기존 지식과 새 지식의 경계가 모호하게 느껴졌습니다. 특히 use client 디렉터리나 해커가 단순히 ‘Client Component’를 지칭하는 것인지, 실제 브라우저에서 실행되는지에 대한 개념이 확실히 잡히지 않았습니다. 또한, 버튼 클릭부터 화면 업데이트까지의 흐름은 알지만, 그 뒤에 도메인, DNS, IP, 포트 등 네트워크 인프라가 어떻게 자연스럽게 연결되는지는 여전히 추상적으로 느껴졌습니다.

정리된 이해#

Next.js는 React의 익숙한 문법들이 Server Component와 Client Component라는 새로운 컨텍스트 안에서 웹 애플리케이션 전체를 관통하는 하나의 흐름으로 재구성된 프레임워크다. 핵심은 기존 지식의 반복이 아니라, UI 표현과 상태 통신 그리고 실제 네트워크 인프라가 어떻게 연결되는지 그 경계를 명확히 이해하는 것이다. 따라서 개발자는 문법의 위치와 실행 환경에 집중하여, 조각난 지식이 아닌 하나의 통합된 흐름으로 사고의 전환을 해야 한다.

"use client";

import { useState } from "react";
import axios from "axios";

// UI Layer: 화면 구성 요소 (Image, Component 등)
// State/Communication Layer: 데이터 흐름 및 통신

export default function ExampleComponent() {
  const [data, setData] = useState(null);

  const handleClick = async () => {
    // 실제 네트워크 요청 예시
    const response = await axios.get("/api/data");
    setData(response.data);
  };

  return (
    <div>
      {/* UI 표현 */}
      {data ? <p>{data.title}</p> : <p>로딩 중...</p>}

      {/* 상태 변화에 따른 버튼 */}
      <button onClick={handleClick}>데이터 요청</button>
    </div>
  );
}

총평#

오늘 오후 전체에서 배운 것#

Next.js App Router에서는 컴포넌트의 기본 실행 위치가 서버이며, 클라이언트 상태 관리가 필요할 때 최상단에 'use client'를 선언해 명확히 경계를 나누는 것이 핵심이다. API 데이터 fetch 후 useState로 상태를 관리하고 자식 컴포넌트에 전달하면 React가 자동으로 화면을 갱신해 최신의 목록을 보여준다. 네트워크 주소 체계에서 호스트, 포트, 경로, 쿼리는 각각 대상, 서비스 지정, 자원 탐색, 조건 전달이라는 서로 다른 역할을 수행한다는 사실을 이해했다.

다음에 조심할 것#

  1. 'use client' 선언 위치를 신중히 확인하여 컴포넌트가 의도치 않게 클라이언트 사이드에서 실행되지 않도록 경계해야 한다.
  2. 상태 업데이트 시점과 렌더링 순서를 정확히 파악하여, 데이터 로딩 중이나 에러 발생 시 사용자가 빈 화면이나 오류 메시지를 보게 되지 않도록 처리해야 한다.
  3. **네트워크 주소 구성 요소(호스트, 포트, 경로, 쿼리)**가 각각 어떤 역할을 하는지 명확히 구분하여, API 요청 URL을 구성할 때 실수가 없도록 주의해야 한다.

다음 복습 주제#

Next.js에서 컴포넌트 실행 위치 결정하기#

Next.js App Router 환경에서는 컴포넌트의 기본값이 서버 측이라는 점을 명확히 이해해야 한다. 단순히 function Component()의 형태만 보고 클라이언트와 서버 중 어디에서 실행되는지 판단하려 하면 안 되며, 반드시 최상단에 'use client' 디렉터리나 주석을 선언하여 의도적으로 클라이언트 컴포넌트로 구분해야 한다. 이 경계가 모호하면 데이터 페칭이나 이벤트 핸들링 시 예상치 못한 렌더링 오류나 성능 문제가 발생할 수 있으므로, UI 구성뿐만 아니라 코드의 실행 주체까지 고려한 설계가 필수적이다.

상태 관리와 조건부 렌더링의 실제 적용#

React와 Axios를 활용한 데이터 흐름에서 핵심은 useState를 통해 API 응답 결과를 관리하고, 이를 자식 컴포넌트에 내려주는 것이다. 특히 목록이 비어있는 경우를 대비해 데이터를 화면에 표시하기 전 list.length 체크를 Post 컴포넌트 내부에서 수행하는 것이 가장 자연스러운 흐름이었다. 또한 초기 상태를 빈 배열 []로 설정한다는 것은 ‘데이터가 아직 로드되지 않은 상태’임을 의미하며, Axios 요청이 완료되어 State가 업데이트되면 React가 자동으로 화면을 갱신하여 최신의 목록을 보여준다는 점은 데이터 바인딩의 기본 원리로 확실히 익힐 필요가 있다.

네트워크 주소 체계의 구조적 이해#

처음에는 localhost:3000 형태의 주소가 전체적으로 뭉쳐 보여 요소별 역할을 구분하기 어려웠으나, host, port, path, query가 각각 다른 계층을 담당한다는 사실을 파악하면서 구조가 명확해졌다. 포트 번호는 특정 프로그램에 데이터를 전달하는 입구이며, 경로와 쿼리는 그 안쪽으로 들어가는 세부적인 탐색 지침 정도로 인식하게 되어 네트워크 주소 체계의 전체적인 흐름을 이해하는 데 큰 도움이 되었다.
