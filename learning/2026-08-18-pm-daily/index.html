1. form 상태 관리의 핵심 원리#

무엇을 배웠나#

Controlled Component 패턴을 통해 input의 value를 state에 바인딩하고 onChange로 업데이트하는 방식의 핵심 원리를 파악했습니다. input의 name 속성이 state의 key를 식별하여, 동일한 handler 함수로 여러 input을 효율적으로 관리할 수 있다는 점을 이해했습니다. 또한 type="password"는 브라우저가 문자를 마스킹해 표시할 뿐 실제 보안은 서버 측에서 이루어지는 기능임을 명확히 했습니다.

헷갈렸던 점#

처음에는 type="password"가 비밀번호를 암호화해줄 것이라 생각했었다. 하지만 실제로는 브라우저가 화면에 표시하는 방식만 바꿔줄 뿐, 보안은 서버에서 이루어지는 것이었다. 또한 input의 name 속성이 state의 key를 결정한다는 점을 간과하고 있었다.

정리된 이해#

controlled component 패턴을 통해 input의 value를 state에 바인딩하고 onChange로 상태를 업데이트하는 방식이 핵심입니다. input의 name 속성이 state의 key를 결정하여, 하나의 handler 함수로 여러 input을 효율적으로 관리할 수 있습니다. 또한, type="password"는 브라우저가 화면에 문자를 가려주는 기능일 뿐 실제 보안은 서버 측에서 이루어지는 점을 명확히 했습니다.

// 상태 초기화: id와 pw를 담고 있는 객체 생성
const [info, setInfo] = useState({id:'',pw:''})

<input type="text" name="id" value={info.id} onChange={(e) => setInfo({...info, [e.target.name]: e.target.value})} placeholder="아이디"/>
<input type="password" name="pw" value={info.pw} onChange={(e) => setInfo({...info, [e.target.name]: e.target.value})} placeholder="비밀번호"/>

2. axios 로그인 토큰 sessionStorage 저장하기#

무엇을 배웠나#

오늘은 로그인 흐름의 입문을 배우며, 서버로부터 받은 success 값이 true일 때만 id와 token을 sessionStorage에 저장하는 방법을 익혔습니다. 단순히 토큰을 저장하는 단계를 넘어, 인증 성공 여부를 검증한 후 다음 단계로 넘어가는 게이트 역할을 한다는 점을 이해했습니다. 아직 JWT의 내부 구조는 이번 범위 밖이므로, 토큰을 서버가 발급한 인증 증명서 정도로 받아들이고 실제 요청 시 헤더 실어주는 부분은 다음 단계로 미뤄두었습니다.

헷갈렸던 점#

  1. sessionStorage에 token을 저장한다는 문구를 그대로 따라 치기 전에, 토큰이 단순히 문자열인지 JWT 구조를 가진 것인지, 그리고 서버가 어떻게 이 값을 검증하는지까지 한 번에 이해하려다 머리가 복잡해졌습니다.
  2. 강의 코드 폴더명이 06_jwt라서 JWT에 대해 깊게 배우는 줄 알았는데, 실제 코드 안에는 token이라는 단어만 덩그러니 있을 뿐 헤더나 페이로드 같은 JWT 핵심 구조가 보이지 않아 “왜 이걸 jwt라고 부르는 거지?“라는 의문이 들었습니다.
  3. 로그인 성공 시 토큰을 저장하는 ‘공식’은 외워지는데, 그 뒤에 숨겨진 원리(검증 과정 등)는 아직 불투명하여 다음 단계가 어떻게 이어질지 기대가 되면서도 막막한 마음이 듭니다.

정리된 이해#

오늘 로그인 기능을 구현하며 서버로부터 전달받은 token을 믿고 바로 저장하는 것이 아니라, success가 true인지 확인한 뒤 유효한 경우에만 id와 token을 sessionStorage에 보관한다는 점을 핵심으로 삼았습니다. 이는 단순히 데이터를 저장하는 단계를 넘어, 인증이 성공했는지 검증된 후 다음 단계로 넘어가는 게이트 역할을 한다고 이해했습니다. 아직 JWT의 내부 구조는 이번 코드 범위 밖이므로, 토큰을 서버가 발급한 인증 증명서 정도로만 받아들이고 실제 요청 시 헤더에 실어주는 부분은 현재로서는 미루어두었습니다.

// 로그인 요청 및 토큰 저장 (axios + sessionStorage)
import axios from 'axios';

async function login(username, password) {
  try {
    const response = await axios.post('/api/auth/login', { username, password });

    // 📌 핵심: 서버로부터 success 여부를 먼저 확인
    if (response.data.success) {
      // 인증 성공 시 token과 id를 sessionStorage에 저장
      sessionStorage.setItem('token', response.data.token);
      sessionStorage.setItem('id', response.data.id);

      console.log('로그인 성공, 토큰이 세션 스토리지에 저장되었습니다.');
    } else {
      console.error('로그인 실패: 서버에서 success가 false를 반환했습니다.');
    }
  } catch (error) {
    console.error('네트워크 오류 또는 서버 응답 오류:', error);
  }
}

3. Next.js App Router에서 브라우저 상태 관리의 경계#

무엇을 배웠나#

Next.js App Router에서는 기본적으로 서버 컴포넌트가 사용되므로, useState나 sessionStorage 같은 브라우저 전용 기능을 사용할 때는 파일의 최상단에 'use client' 선언을 반드시 해야 한다. 이 선언은 단순히 오류를 방지하는 문구가 아니라, 컴포넌트가 브라우저에서 상호작용과 상태 관리를 담당한다는 명확한 경계 표시 역할을 한다는 점을 이해했다.

헷갈렸던 점#

Next.js App Router에서 기본적으로 Server Component로 간주되는 컴포넌트에 useState나 sessionStorage 같은 브라우저 전용 기능을 사용하려면 'use client' 선언이 반드시 필요하다는 점이었다.

오전에는 단순히 useState가 있으면 Client Component가 되는 공식처럼 받아들여 혼동했으나, 오후에는 브라우저 기능(상태 관리, 스토리지 접근)이 필요한 경우 컴포넌트의 성격이 Client Component로 전환되어야 한다는 개념 정리가 필요했다.

정리된 이해#

Next.js App Router에서 기본적으로 서버 컴포넌트이며, 브라우저 고유 기능인 useState나 sessionStorage를 사용하려면 파일 최상단에 'use client' 선언을 반드시 해야 한다. 이 선언은 단순히 오류를 방지하는 것이 아니라, 컴포넌트가 브라우저에서 상호작용과 상태 관리를 담당한다는 명확한 경계 표시이다. 따라서 브라우저 기능이 필요한 경우 무조건 클라이언트 컴포넌트로 전환해야 한다.

'use client';

import { useEffect } from 'react';
import { useRouter } from 'next/navigation';

export default function PageLoginInitializer() {
  const router = useRouter();

  useEffect(() => {
    // 브라우저 스토리지에서 세션 확인 및 초기화 로직
    const handleSessionInit = () => {
      console.log('세션 초기화 수행');
      // 예: sessionStorage.clear(); 또는 토큰 검증 로직
    };

    handleSessionInit();
  }, []); // 의존성 배열이 비어있으므로 첫 마운트 시 한 번만 실행

  return null; // 실제 UI는 생략하거나 로딩 상태 표시
}

총평#

오늘 오후 전체에서 배운 것#

Controlled Component 패턴을 통해 input의 value를 state에 바인딩하고 onChange로 업데이트하는 핵심 원리를 파악했으며, input의 name 속성을 활용해 동일한 handler 함수로 여러 input을 효율적으로 관리할 수 있다는 점을 이해했습니다. 또한 Next.js App Router에서 브라우저 전용 기능을 사용하기 위해서는 파일의 최상단에 ‘use client’ 선언을 반드시 해야 하며, 이는 컴포넌트가 브라우저에서 상호작용과 상태 관리를 담당한다는 명확한 경계 표시 역할을 한다는 점을 학습했습니다.

다음에 조심할 것#

  • use client 선언 누락 시 발생하는 오류를 방지하기 위해, 브라우저 전용 훅이나 스토리지를 사용할 때마다 파일 최상단에 반드시 'use client' 주석을 추가해야 한다.
  • 서버 컴포넌트와 클라이언트 컴포넌트의 경계를 명확히 하여, 불필요한 리렌더링이나 상태 동기화 문제를 사전에 차단하는 습관을 들인다.

다음 복습 주제#

  • Next.js에서 인증 상태 지속성 확보: sessionStorage에 저장된 토큰을 활용해 로그인 상태를 유지하는 방법을 학습하고, 이를 통해 protected route 접근 제어 및 UI 상태 반영의 기초를 다지는 것이 목표입니다.
  • JWT 기반 인증 흐름 완성: 서버로부터 받은 토큰을 요청 헤더에 실어주는 실제 API 호출 메커니즘과, 토큰 만료 시 리프레시 토큰이나 로그아웃 처리의 로직을 이해하여 보안이 완전한 인증 시스템으로 확장하는 단계를 준비합니다.
  • Next.js 데이터 페칭 최적화: 서버 컴포넌트에서 fetch를 직접 사용하거나 swr, react-query 같은 라이브러리를 활용해 데이터를 캐싱하고 동기화하는 패턴을 익혀, 클라이언트 상태 관리와 서버 상태 관리의 경계를 명확히 하는 능력을 기릅니다.
