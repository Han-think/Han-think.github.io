1. metadata로 ChromaDB 조건 검색 복습#

무엇을 배웠나#

오늘은 metadata를 활용한 검색 조건(where) 사용법을 정리했습니다. 특히 $and, $or 같은 논리 연산자의 차이를 명확히 이해하는 데 집중했습니다. 반복되는 학습 패턴 속에서 ‘넣기’와 ‘찾아내기’ 단계의 목적 차이를 인식할 수 있었습니다.

헷갈렸던 점#

처음에는 metadata를 문서에 붙이는 ‘넣기’ 단계와, 조건을 걸어 검색하는 ‘찾아내기’ 단계를 같은 도구로 사용한다는 점이 직관적이지 않았습니다. 특히 $and와 $or의 차이를 머릿속으로 그리기가 어려웠고, 두 연산자가 단순히 True/False를 판별하는 것이 아니라 문서 전체를 걸러내는 필터 역할을 한다는 점을 명확히 구분하지 못해 혼란스러웠습니다.

정리된 이해#

metadata는 문서에 붙이는 속성이고, where 절은 그 속성을 이용해 검색 범위를 제한하는 필터입니다. $and 연산자는 모든 조건을 동시에 만족해야만 결과가 반환되며, $or 연산자는 조건 중 하나만 충족해도 결과를 포함합니다. 오늘 배운 이 두 가지 개념을 통해 metadata를 활용한 정밀한 데이터 탐색이 가능해졌습니다.

# 1. 단일 조건 검색 (year >= 2023)
res = coll.query(
    query_texts=["공부할 자료"],
    n_results=2,
    where={"year": {"$gte": 2023}}
)

# 2. AND 연산자: 모든 조건을 만족해야 함
# official이면서 python인 문서만 조회
res = coll.query(
    query_texts=["공부할 자료"],
    n_results=2,
    where={"$and": [{"official": True}, {"lang": "python"}]}
)

# 3. OR 연산자: 어느 하나만 만족하면 됨
# official이 아니거나 beginner 레벨이면 모두 조회
res = coll.query(
    query_texts=["공부할 자료"],
    n_results=2,
    where={"$or": [{"official": False}, {"level": "beginner"}]}
)

2. PDF RAG 파이프라인 전처리 과정#

무엇을 배웠나#

PDF RAG 구현 과정에서 가장 큰 변화는 단순한 텍스트 입력에서 문서 전처리 파이프라인으로의 전환이었다. 특히 tiktoken을 활용한 토큰 길이 측정과 RecursiveCharacterTextSplitter를 통한 청크 분할 과정이 필수적임을 깨달았다. 단순히 DB에 저장하는 것보다, 검색 가능한 적절한 크기로 문서를 쪼개는 전처리 과정이 핵심이었다.

헷갈렸던 점#

가장 큰 혼란은 **“ChromaDB에 저장하는 과정이 반복된다”**는 점이었습니다. 어제는 단순한 문장을 DB에 넣었다면, 오늘은 PDF 전체를 읽고 전처리를 거친 후 저장하게 되었기 때문에, “어제 했던 작업과 오늘 하는 작업이 무엇이 다른가?“라는 의문이 들었습니다.

특히 PersistentClient와 get_or_create_collection을 사용하는 코드 구조가 반복되어 보여, DB 조작 자체에 익숙해져 있는지, 아니면 문서 전처리 파이프라인에 집중해야 하는지 구분이 안 되었던 순간이 있었습니다. PDF라는 ‘큰 덩어리’를 다루다 보니, chunking 과정까지 포함된 전체 흐름이 한 번에 들어오기엔 양이 많았습니다.

오늘의 핵심은 **ChromaDB 사용법 자체보다, “긴 문서를 검색 가능한 단위로 쪼개는 전처리 과정”**에 있습니다. PDF라는 큰 덩어리를 다루다 보니, 단순히 DB에 넣는 것을 넘어 텍스트를 적절한 크기로 가공하는 과정이 새로 추가된 것이 중요합니다.

정리된 이해#

오늘의 핵심은 PDF라는 큰 덩어리를 검색 가능한 단위로 가공하는 전처리 과정에 있었습니다. 단순히 DB에 저장하는 것보다, 텍스트를 추출한 뒤 토큰 길이를 측정하고 적절한 크기로 쪼개는 ‘청킹’ 과정이 필수적입니다. 이 과정을 거치지 않으면 LLM이 감당하기 너무 큰 텍스트가 되어 검색 성능이 저하됩니다.

PDF RAG 실습: 전처리 및 ChromaDB 저장 핵심 코드#

오늘 학습한 핵심 흐름은 PDF 텍스트 추출 → 토큰 길이 측정(Chunking) → DB 저장입니다. 아래는 해당 과정의 핵심 코드 예시입니다.

import fitz  # PyMuPDF
import tiktoken
from langchain.text_splitter import RecursiveCharacterTextSplitter
from langchain.vectorstores import Chroma
from langchain.schema import Document

# 1. PDF 읽기 및 텍스트 추출
def extract_text_from_pdf(pdf_path):
    doc = fitz.open(pdf_path)
    full_text = ""
    for page_num in range(len(doc)):
        page = doc.load_page(page_num)
        text = page.get_text("text")
        full_text += text
    return full_text

# 2. 토큰 길이 측정용 함수 정의 (tiktoken 사용)
def num_tokens_from_string(string: str, encoding_name: str = "cl100k_base") -> int:
    """텍스트의 토큰 수를 계산합니다."""
    encoding = tiktoken.get_encoding(encoding_name)
    return len(encoding.encode(string))

# 3. 청킹 (Chunking) 설정 및 실행
def chunk_documents(text, chunk_size=800, chunk_overlap=50):
    """
    RecursiveCharacterTextSplitter를 사용하여 문서를 적절한 크기로 쪼갭니다.
    chunk_size: 한 청크의 최대 토큰 수 (예: 800)
    chunk_overlap: 인접 청크 사이의 겹치는 토큰 수 (예: 50)
    """
    text_splitter = RecursiveCharacterTextSplitter(
        chunk_size=chunk_size,
        chunk_overlap=chunk_overlap,
        length_function=num_tokens_from_string, # 위에서 정의한 토큰 세는 함수 사용
        is_separator_regex=False,
    )

    # Document 객체로 변환 (메타데이터 포함)
    documents = [Document(page_content=text)]

    chunks = text_splitter.split_documents(documents)
    return chunks

# 4. ChromaDB에 저장
def save_to_chroma(chunks, persist_directory="./chroma_db"):
    """
    쪼개진 청크를 ChromaDB에 업서트(Upsert)합니다.
    """
    # PersistentClient를 사용하여 기존 DB가 있다면 로드, 없다면 생성
    vectordb = Chroma(
        persist_directory=persist_directory,
        embedding_function=None, # 실제 프로젝트에서는 HuggingFaceEmbeddings 등 사용
    )

    # 청크를 DB에 추가 (이미 존재하면 업데이트)
    # addDocuments는 LangChain의 표준 인터페이스입니다.
    vectordb.add_documents(chunks)
    vectordb.persist()
    print(f"총 {len(chunks)}개의 청크가 ChromaDB에 저장되었습니다.")
    return vectordb

# --- 실행 예시 ---
if __name__ == "__main__":
    pdf_file = "example.pdf"

    # 1. 텍스트 추출
    raw_text = extract_text_from_pdf(pdf_file)

    # 2. 청킹 수행 (800 토큰 크기, 50 토큰 겹침)
    document_chunks = chunk_documents(raw_text, chunk_size=800, chunk_overlap=50)

    # 3. DB 저장
    db = save_to_chroma(document_chunks)

3. RAG 단계별 이해: 검색·증강·생성#

무엇을 배웠나#

RAG 개념을 접하며 검색과 생성의 경계가 모호하다는 점이 가장 어려웠다. ChromaDB에서 검색한 chunk를 프롬프트에 넣는 과정이 ‘검색’인지 ‘문맥 추가’인지 구분하기 힘들었다. 오늘은 Retrieval, Augmentation, Generation의 3단계 구조와 각 단계의 역할을 명확히 이해했다. 특히 num_ctx와 num_predict 옵션을 조정하는 실습을 통해 LLM이 문맥을 얼마나 활용하는지 확인할 수 있었다.

RAG의 핵심은 검색된 결과를 단순히 붙이는 것이 아니라, 모델이 답변을 생성할 수 있는 ‘유용한 문맥’으로 가공하는 Augmentation 과정에 있다. 이를 통해 LLM의 환각 현상을 줄이고 정확한 답변을 도출할 수 있다는 점이 인상 깊었다.

헷갈렸던 점#

처음 RAG 개념을 접했을 때 가장 막막했던 부분은 ‘검색’과 ‘생성’의 경계가 모호하다는 점이었습니다. 코드 흐름상 query → retrieval → context → prompt → LLL이 반복되다 보니, 이것이 정말 RAG인지 단순한 LLM 질의인지 구분이 안 갔습니다. 특히 ChromaDB에서 검색해온 chunk를 그대로 프롬프트에 넣는 과정이 ‘검색’인지 ‘문맥 추가’인지, 그리고 LLM이 그 문맥을 얼마나 활용하는지가 헷갈렸습니다.

오늘 학습한 핵심은 RAG의 3단계 구조였습니다. 이전에는 코드 흐름에만 집중했다면, 이제는 각 단계의 역할과 목적을 명확히 구분했습니다. Retrieval는 ChromaDB 같은 벡터 데이터베이스에서 사용자의 질문에 의미적으로 관련된 chunk를 찾아내는 과정이며, Augmentation는 검색된 결과를 LLM이 답변을 생성할 수 있는 유용한 문맥으로 가공하는 과정입니다. Generation은 Retrieval와 Augmentation된 정보를 바탕으로 환각을 줄이고 정확한 답변을 생성해내는 단계입니다.

정리된 이해#

RAG는 검색, 문맥 가공, 답변 생성을 아우르는 3단계 과정입니다. Retrieval 단계에서 ChromaDB를 통해 의미적으로 관련된 청크를 찾고, Augmentation 단계에서 이를 프롬프트에 유용한 문맥으로 추가한 뒤, Generation 단계에서 LLM이 해당 정보를 바탕으로 환각을 최소화한 정확한 답변을 생성합니다.

📝 학습 요약#

  1. Retrieval (검색): ChromaDB 등 벡터 DB에서 질문의 의미를 파악해 관련 청크를 검색하는 과정입니다.
  2. Augmentation (증강): 검색된 결과를 LLM이 답변을 생성할 수 있도록 프롬프트에 문맥으로 추가하는 과정입니다.
  3. Generation (생성): LLM이 retrieved와 augmented된 정보를 바탕으로 질문에 답변하는 최종 단계입니다.

🛠️ 실습 코드#

# 1. 검색 (Retrieval)
query = "RAG의 기본 원리는 무엇인가?"
results = chroma_collection.query(
    query_texts=[query],
    n_results=3  # 상위 3개 청크 retrieval
)

# 2. 증강 (Augmentation)
contexts = results['documents'][0]
prompt_template = f"""질문: {query}

참고 문맥:
{contexts}

답변:"""

# 3. 생성 (Generation)
response = ollama.generate(
    model='llama3',
    prompt=prompt_template,
    options={
        'num_ctx': 4096,   # 컨텍스트 창 크기 조정
        'num_predict': 256 # 최대 토큰 수 제한
    }
)

print(response['response'])

# 1. 검색 (Retrieval)
query = "RAG의 핵심 원리는 무엇인가요?"
results = chroma_collection.query(
    query_texts=[query],
    n_results=3  # 상위 3개 chunk 검색
)

# results에는 document, metadatas, ids가 포함됨

# 2. 증강 (Augmentation)
contexts = results['documents'][0]  # 검색된 문서들 추출
prompt_template = f"""질문: {query}

참고 문맥:
{contexts[0]}

위 참고 문맥을 바탕으로 질문에 답해주세요."""

# 3. 생성 (Generation)
response = ollama.generate(
    model='llama2',
    prompt=prompt_template,
    options={
        'num_ctx': 4096,   # 컨텍스트 윈도우 크기 조절
        'num_predict': 512 # 최대 토큰 수 제한
    }
)
print(response['response'])

오늘 오전 전체에서 배운 것#

오늘은 ChromaDB의 metadata 검색 조건과 $and, $or 같은 논리 연산자의 차이를 명확히 이해하는 데 집중했습니다. 또한 PDF RAG 파이프라인에서 텍스트를 적절한 크기로 쪼개는 전처리 과정, 특히 tiktoken을 통한 토큰 길이 측정과 RecursiveCharacterTextSplitter의 중요성을 깨닫았습니다. 마지막으로 Retrieval, Augmentation, Generation으로 구성된 RAG의 3단계 구조를 이해하며, 검색된 chunk가 단순히 프롬프트에 입력되는 것이 아니라 모델이 답변을 생성할 수 있는 ‘유용한 문맥’으로 가공되는 Augmentation 과정이 LLM의 환각 현상을 줄이는 핵심임을 확인했습니다.

다음에 조심할 것#

오늘은 metadata 검색 조건과 PDF RAG 전처리 파이프라인, 그리고 Retrieval-Augmentation-Generation 단계별 구조를 정리했습니다.

특히 $and, $or 같은 논리 연산자의 차이를 명확히 이해하고, 단순한 텍스트 입력이 아닌 문서 전처리 과정의 중요성을 깨닫는 좋은 기회였습니다. 다음 학습에는 metadata 검색과 전처리 과정을 실제 적용해보며, 검색된 chunk가 모델에 유용한 문맥으로 전달될 수 있도록 세부 설정을 점검하는 데 집중하겠습니다.

다음 복습 주제#

다음 학습에서는 metadata 검색 시 $and, $or 등 논리 연산자의 조합 패턴을 다양하게 적용해보며, 조건에 맞는 문서를 정확히 필터링하는 실전 감각을 기를 계획이다. 또한 PDF 파이프라인에서 사용한 RecursiveCharacterTextSplitter의 분할 전략이 검색 성능에 미치는 영향을 분석하고, 청크 크기 조정이 Retrieval 단계의 정확도에 어떻게 영향을 주는지 구체적인 실험 결과를 통해 확인해보고자 한다. 마지막으로 RAG 전체 흐름에서 Augmentation 과정의 중요성을 재확인한 뒤, 실제 LLM에게 문맥을 제공할 때 프롬프트 구조를 어떻게 설계하면 모델이 정보를 가장 효율적으로 활용하는지 프롬프트 엔지니어링 관점에서 심화 학습하겠다.
