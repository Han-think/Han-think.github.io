1. 상태 공유와 렌더링 흐름의 분리#

무엇을 배웠나#

React Context는 상태를 멀리 있는 컴포넌트까지 전달하는 ‘통로’ 역할을 하며, useMemo는 의존값이 바뀔 때만 계산을 재실행하여 렌더링 성능을 최적화하는 도구다. 이 두 기능은 각각 상태 공유 경로와 재계산 시점을 제어한다는 점에서 별개의 개념으로 분리되어 이해해야 한다.

헷갈렸던 점#

Context는 상태를 공유하는 통로일 뿐, 상태 자체를 생성하거나 관리하는 기능이 아니라는 점이 가장 혼란스러웠습니다. 또한 useMemo가 단순히 값을 저장하는 것이 아니라, 의존값에 따라 렌더링 시점을 제어하는 성능 최적화 도구라는 점도 명확히 구분하지 못해 애를 먹었습니다. 결국 두 기능은 ‘상태 공유 경로(Context)‘와 ‘재계산 시점 제어(useMemo)‘라는 완전히 다른 목적을 가지고 있다는 점을 이해하는 데 시간이 걸렸습니다.

정리된 이해#

Context는 상태 자체를 생성하는 기능이 아니라, 부모 컴포넌트에서 자식 컴포넌트로 깊숙한 곳까지 상태를 전달할 수 있는 ‘공유 경로’를 만들어주는 역할을 한다. 반면 useMemo는 단순히 값을 저장하는 것이 아니라, 특정 의존값이 변경될 때만 계산을 다시 수행하도록 렌더링 시점을 제어하여 성능을 최적화하는 도구다. 즉, Context는 상태의 전달 경로를 담당하고, useMemo는 계산의 재실행 시점을 관리하는 독립적인 개념이다.

// Context를 통한 상태 공유 예시
const ThemeContext = React.createContext();

function Parent() {
  const [theme, setTheme] = useState('light');

  return (
    <ThemeContext.Provider value={theme}>
      <Child />
    </ThemeContext.Provider>
  );
}

function Child() {
  // Context에서 상태를 꺼내 씀 (공유 경로)
  const theme = useContext(ThemeContext);

  return <div style={{ color: theme === 'dark' ? '#fff' : '#000' }}>내용</div>;
}

// useMemo에 의한 렌더링 제어 예시
function ExpensiveComponent({ value }) {
  // dependency array에 따라 계산 재실행 제어
  const processed = useMemo(() => heavyComputation(value), [value]);

  return <div>{processed}</div>;
}

2. Redux 핵심 회로도: dispatch → reducer → store → useSelector → 화면갱신#

무엇을 배웠나#

처음 Redux를 접했을 때 ‘store’, ‘slice’, ‘dispatch’ 등 다양한 용어가 섞여 혼란스러웠지만, 핵심은 단순히 값을 저장하는 기술이 아니라 공용 상태의 변경과 조회를 규칙화하는 구조라는 점을 이해하게 되었다. 특히 dispatch로 요청하고 reducer가 규칙을 적용해 store에 반영한 뒤, useSelector로 화면에 출력하는 일련의 흐름을 파악하니 각 API의 존재 이유를 명확히 할 수 있었다. now I understand that Redux is not just a value storage technology but a structure that systematizes common state changes and lookups. The process of requesting via dispatch, applying rules through reducer, storing in store, and reading with useSelector finally made the purpose of each API clear.

헷갈렸던 점#

처음 Redux를 접했을 때 가장 큰 문제는 **“용어의 홍수”**였습니다. store, slice, state, reducer, action, dispatch, selector가 한꺼번에 등장해서, 하나의 단순한 숫자(카운터 값)를 위해 너무 많은 이름이 필요하다는 느낌이 들었습니다.

특히 강의가 “API를 하나씩 연결하는 순서 설명"부터 시작하다 보니, **“왜 이렇게 복잡한 구조를 써야 하지?”**라는 목적성보다 “연결 규칙을 외우는 것"에 집중하게 되는 느낌이 들었습니다. 최종 목적인 “상태 업데이트 → 화면 갱신"이라는 큰 그림이 보이지 않으면, 각 API의 존재 이유를 이해하기 어렵죠.

핵심 회로를 단순화하면 Redux는 **“값을 저장하는 기술"보다는 “공용 상태의 변경과 조회를 규칙화하는 구조”**로 이해하는 편이 맞습니다. 오늘 학습한 내용을 내 방식으로 압축하면 다음과 같습니다: 버튼 클릭 → dispatch(변경 요청) → reducer(규칙 적용) → store/state(저장) → useSelector(읽기) → 화면 갱신(출력).

정리된 이해#

Redux는 단순히 값을 저장하는 기술이 아니라, **‘상태 변경 요청 → 규칙 적용 → 저장 → 조회 → 화면 반영’**이라는 순환 구조를 통해 공용 상태를 일관되게 관리하는 시스템입니다. 핵심은 dispatch로 변화를 요청하고 reducer가 그 규칙을 적용해 store에 반영한 뒤, useSelector로 값을 읽어 화면에 전달한다는 점이며, 각 API 이름은 이 흐름 속에서 ‘위치’와 ‘역할’을 구분하는 용도에 불과합니다.

// Redux Store & Slice 연결 예시 (초보자 관점)

import { configureStore } from '@reduxjs/toolkit';
import { createSlice, useSelector, useDispatch } from 'react-redux';

// 1. slice: 변경 규칙 정의
const counterSlice = createSlice({
  name: 'counter',
  initialState: { value: 0 },
  reducers: {
    increment: (state) => { state.value += 1 }, // reducer: 저장 규칙
    decrement: (state) => { state.value -= 1 }
  }
});

// 2. store: 상태를 보관하는 곳
const store = configureStore({
  reducer: counterSlice.reducer
});

// 3. 컴포넌트에서 사용
function Counter() {
  // useSelector: 저장된 값 조회 (화면 갱신)
  const value = useSelector(state => state.counter.value);

  // useDispatch: 변경 요청 발사
  const dispatch = useDispatch();

  return (
    <div>
      <h2>카운터: {value}</h2>
      <button onClick(() => dispatch(increment()))>
        +
      </button>
      <button onClick(() => dispatch(decrement()))>
        -
      </button>
    </div>
  );
}

3. 비동기 통신과 상태 관리의 분리#

무엇을 배웠나#

Redux 적용 과정에서 가장 큰 혼란은 비동기 서버 통신과 동기 상태 변경이 reducer 안에서 동시에 발생하려 했던 점입니다. 저는 결국 서버 요청을 Component가 담당하고, reducer는 받은 데이터를 단순히 저장하는 역할로 분리해야 한다는 것을 깨달았습니다. 이를 통해 Redux의 핵심 목적인 ‘데이터 관리’에 집중할 수 있었고, 코드의 흐름이 명확해졌습니다.

헷갈렸던 점#

핵심은 비동기 서버 통신과 동기 상태 변경의 위치 분담이었습니다.

처음에는 reducer가 axios 요청까지 담당하려 했으나, 이는 동기 규칙과 충돌했습니다. 결국 Component가 통신을 담당하고 Redux는 저장 관리만 맡기로 방향을 전환했습니다.

정리된 이해#

Redux는 비동기 서버 통신보다는 동기적인 상태 관리에 집중해야 합니다. 실제 데이터 fetching은 컴포넌트에서 담당하고, reducer는 받아온 데이터를 단순히 저장하는 역할로 분리해야 합니다.

// [변경 전 - 헷갈리던 구조]
// Component에서 dispatch를 호출하면 reducer 내부에 axios 요청이 포함되어
// 비동기 처리가 불확실해지는 문제 발생

/*
Component
  └── dispatch(page)
      ↓
    board reducer (async 시도)
      ↓ (Promise 반환 문제)
    axios 요청 및 state 변경 ❌
*/

// [변경 후 - 명확한 구조]
// 서버 통신은 Component가 담당하고, Reducer는 상태 변화만 관리

const fetchPosts = async () => {
  const response = await axios.get('/api/posts');
  dispatch({ type: 'FETCH_SUCCESS', payload: response.data });
};

// Reducer는 순수 함수로 동기적 상태 변경만 책임짐
const boardReducer = (state = initialState, action) => {
  switch (action.type) {
    case 'FETCH_SUCCESS':
      return { ...state, list: action.payload };
    default:
      return state;
  }
};

총평#

오늘 오전 전체에서 배운 것#

React Context와 useMemo는 상태 전달 경로와 재실행 시점을 제어하는 별개의 개념이며, Redux는 store·dispatch·reducer·useSelector를 통해 공용 상태의 변경과 조회를 규칙화하는 구조임을 이해했다. 특히 비동기 통신과 동기 상태 변경을 분리하여 reducer가 데이터 관리에 집중하도록 설계한 점을 명확히 했다.

다음에 조심할 것#

Redux에서 비동기 작업은 Component가 담당하고 reducer는 데이터 저장에만 집중해야 한다는 분리 원칙을 명확히 했다.

Context와 useMemo는 각각 상태 전달 경로와 재계산 시점을 제어하는 별개의 개념으로 접근하여 혼동을 피해야 한다.

Reducer 내부에 서버 통신 로직이 섞이지 않도록 하여, ‘데이터 관리’라는 Redux의 핵심 목적에 집중할 수 있는 코드 구조를 유지해야 한다.

다음 복습 주제#

Redux에서 비동기 로직을 처리하는 구체적인 패턴(예: thunk나 saga 등)을 이해하고, 컴포넌트와 reducer 사이의 데이터 흐름을 더욱 명확히 구분할 수 있어야 한다.

이전 학습에서 확인한 Redux의 핵심 흐름(dispatch → reducer → store → useSelector)을 기반으로, 상태 업데이트가 화면에 어떻게 반영되는지 디버깅하는 연습을 통해 실제 프로젝트 적용 시 발생할 수 있는 부수 효과를 최소화해야 한다.
