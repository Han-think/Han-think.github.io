1. SA 관점 UI 설계서 이해하기#

무엇을 배웠나#

UI 설계서를 단순한 화면 배치도가 아닌 기획·구현·테스트 사이의 공통 언어로 이해하게 되었다. 특히 ‘검증 방법’과 ‘상태별 테스트 케이스’를 명시하는 것이 실제 개발 현장에서의 추적성을 높이는 핵심임을 깨달았다. AGV 현황 화면을 분석하며, 캡처 구성요소와 실제 업무 정책이 다른 층위의 데이터라는 점을 구분하는 법을 배웠다. 마지막으로 화면 요소 하나하나에 ‘ID/표시데이터/사용자동작/이동대상/성공·빈결과/오류상태/검증방법’이 연결될 때 비로소 완성되는 설계임을 확인했다.

헷갈렸던 점#

처음 UI 설계서를 마주했을 때, 단순히 화면 구성을 나열하는 수준을 넘어 각 버튼이 어떤 데이터를 바꾸고 어디서 오는지를 정확히 파악해야 한다는 점이 가장 큰 혼란이었습니다.

특히 강의 캡처에 포함되지 않은 권한 설정, 데이터 갱신 주기, 에러 처리 정책 같은 부분은 실제 업무와 비슷하게 작성하려다 보니 헷갈리기 쉽더군요. 화면 요소 하나하나를 단순히 나열하는 수준을 넘어, 그 이면에 있는 데이터 흐름과 상태 관리를 이해하는 것이 첫걸음이었습니다.

정리된 이해#

화면 설계 문서는 기획, 구현, 테스트가 공통으로 사용하는 언어이며, 단순한 화면 배치보다는 요소 ID와 데이터 흐름, 상태별 검증 방법을 명시해야 실제 개발이 가능해진다. 특히 ‘검증 방법’과 ‘상태별 테스트 케이스’를 명확히 정의하는 것이 현장에서의 추적성을 높이는 핵심이다.

2. SNS 요구사항을 화면·동작·데이터로 변환하기: 핵심 개념 재정리#

무엇을 배웠나#

처음에는 게시글에 좋아요 숫자만 세는 줄 알았지만, 실제로는 누가 눌렀는지 기록하는 별도 테이블이 필요하다는 점을 깨달았다. 친구 목록은 같은 회원 테이블을 두 번 참조하는 관계형 구조가 필요해 처음에는 설계 감이 안 잡혔다. 또한 화면에 보이는 기능이 곧 서버 API나 DB 기능을 의미하지 않는다는 경계가 중요하다고 느꼈다.

헷갈렸던 점#

처음에는 게시글 테이블에 likes_count 컬럼 하나면 충분할 것이라 생각했으나, 요구사항을 자세히 보니 ‘누가 언제 어떤 글에 눌렀는지’를 추적하기 위해 별도의 기록 테이블이 필수적임을 깨달았다. 또한 친구 목록은 단순한 문자열 저장이 아니라 같은 회원 테이블을 서로 참조하는 관계형 구조로 설계해야 한다는 점과, 화면에 보이는 기능이 실제 서버 API나 DB 기능을 직접 대입하면 안 된다는 경계가 필요했다.

정리된 이해#

좋아요 시스템은 게시글 테이블에 숫자를 세는 것이 아니라, ‘누가 언제 어떤 글에 눌렀는지’를 기록하는 별도의 테이블을 만들어야 하며, 표시되는 수는 이 기록의 개수로 계산한다. 친구 목록은 같은 회원 테이블을 두 컬럼으로 참조하여 회원 간 연결 관계를 구현해야 하며, 선택 프로필은 가입 필수 항목과 분리되어 1:0..1 관계로 표현할 수 있다.

-- 1. 좋아요 시스템: 게시물FK + 회원FK로 구성된 별도 기록 테이블
CREATE TABLE likes (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT NOT NULL,
    post_id BIGINT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (member_id) REFERENCES members(id),
    FOREIGN KEY (post_id) REFERENCES posts(id)
);

-- 2. 친구 목록: 같은 회원 테이블을 두 컬럼으로 참조하는 관계형 테이블
CREATE TABLE friendships (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT NOT NULL,           -- 요청한 사람(A)
    friend_member_id BIGINT NOT NULL,     -- 수락한 사람(B)
    status ENUM('pending', 'accepted') DEFAULT 'pending',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (member_id) REFERENCES members(id),
    FOREIGN KEY (friend_member_id) REFERENCES members(id),
    UNIQUE KEY unique_friendship (member_id, friend_member_id)
);

-- 3. 선택 프로필: 회원 1 : 프로필 0..1의 관계
CREATE TABLE profiles (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT UNIQUE NOT NULL,
    nickname VARCHAR(50),
    bio TEXT,
    profile_image_url VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (member_id) REFERENCES members(id)
);

3. PK·FK 관계와 6개 테이블 SNS 논리 ERD#

무엇을 배웠나#

PK는 해당 행을 고유하게 식별하는 값이며, 다른 테이블 참조를 목적으로 하지 않는다. FK는 관계를 맺기 위해 자식 테이블에 존재하는 컬럼으로, 선 자체를 FK가 아닌 양 끝에 있는 컬럼 중 하나로 구분해야 한다. 친구관계 테이블처럼 두 개의 FK가 같은 부모 테이블을 바라보는 구조는 양쪽 모두 해당 테이블의 PK와 매핑된다는 점을 이해하는 것이 중요하다. JSON 스키마 파일을 ERDCloud에 바로 import할 경우 내부 구조 불일치로 인해 오류가 발생하므로, 전용 변환 과정을 거치는 것이 필요하다.

헷갈렸던 점#

PK는 다른 테이블에서 참조해야 하는 필수 요건이 아니라, 해당 행을 고유하게 식별하는 값이라는 점입니다.

ERD상의 선 자체가 FK가 아니라, 선의 양 끝에 있는 컬럼 중 하나가 FK이며, 친구관계와 같이 두 개의 FK가 같은 테이블을 바라보는 구조에서는 컬럼 레벨에서의 관계 파악이 중요하다는 점을 명확히 했습니다.

정리된 이해#

PK는 해당 행을 고유하게 식별하는 값이며, 다른 테이블 참조 목적이 아니다. FK는 관계를 맺기 위해 자식 테이블에 존재하는 컬럼으로, 선 자체를 FK가 아니라 선의 양 끝 컬럼 중 하나로 구분해야 한다. 특히 두 개 이상의 FK가 같은 부모 테이블을 바라보는 구조에서는 컬럼 명세에 집중하여 혼동을 피해야 한다.

4. 정규화·복합 UQ·데이터 정합성 이해하기#

무엇을 배웠나#

정규화는 표를 쪼개는 기술이 아니라, 한 사실을 한 곳에서 책임지게 설계하는 방식이라는 점을 깨달았습니다. 또한 복합 고유 제약은 각 컬럼을 따로 설정하면 요구사항과 맞지 않게 동작하므로, 의미 있는 조합으로 묶어야 한다는 것을 이해했습니다. 친구 관계에서 (A,B)와 (B,A)는 서로 다른 튜플이며, 정책에 따라 방향성을 두거나 대칭 설계가 필요하다는 점을 명확히 했습니다.

헷갈렸던 점#

처음에는 ‘정규화’가 테이블을 쪼개는 기술로만 이해되어, 데이터 중복을 막는 진정한 목적보다는 설계 복잡함에 초점을 두게 되었습니다. 또한 ‘복합 UQ’에 대해 각 컬럼을 따로 유일하게 설정하면 요구사항이 깨진다는 점을 직관적으로 파악하지 못해, 조합의 의미를 간과하기 쉬웠습니다. 마지막으로 ‘친구 관계’에서 방향성이 있다는 사실을 모르고 (A,B)만으로 양방향 관계를 모두 커버된다고 오해하다가, 정책에 따라 추가 설계가 필요하다는 점을 구분하는 데 시간이 걸렸습니다.

정리된 이해#

정규화는 표를 쪼개는 기술이 아니라, 한 사실을 한 곳에서 책임지게 하여 데이터 중복을 방지하는 설계 방식이다. 복합 UQ는 의미 있는 컬럼 조합으로 묶어야 실제 요구사항인 ‘한 회원 한 글 중복 좋아요 금지’가 성립하며, 각 컬럼을 따로 설정하면 의도와 다른 동작이 발생한다. 친구 관계에서 (A,B)와 (B,A)는 서로 다른 튜플이며, 정책에 따라 방향성을 명확히 설정하거나 대칭 관계를 구현해야 한다.

-- 복합 UQ(Unique Constraint) 예시: 좋아요 테이블
CREATE TABLE likes (
    post_id   INT NOT NULL,
    member_id INT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    -- 한 회원이 같은 글에 중복으로 좋아요를 누르지 못하게 함
    CONSTRAINT uq_post_member UNIQUE (post_id, member_id)
);

-- 친구 관계 예시: 방향성 있는 UQ
CREATE TABLE relationships (
    follower_id INT NOT NULL,
    followee_id INT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

-- (A,B)와 (B,A)는 서로 다른 튜플이므로 각각 독립적인 UQ가 필요하거나,
-- 정책에 따라 복합 UQ로 중복 방지 여부를 결정함
  CONSTRAINT uq_follower_followee UNIQUE (follower_id, followee_id)
);

총평#

오늘 오후 전체에서 배운 것#

UI 설계서는 단순한 화면 배치도를 넘어 기획, 구현, 테스트 사이의 공통 언어이며, 각 요소(ID, 데이터, 검증 방법 등)의 연결이 완성된 설계를 의미한다. SNS 요구사항 변환 과정에서 좋아요 기록을 위한 별도 테이블 필요 관계형 구조와 API·DB 기능의 경계를 명확히 이해했으며, PK·FK 관계를 통해 테이블 간의 참조 논리와 복합 UQ를 통한 데이터 정합성 유지를 정확히 파악했다.

다음에 조심할 것#

  1. UI 설계서에서 ‘검증 방법’과 ‘상태별 테스트 케이스’를 누락하지 않도록 하여 개발 현장의 추적성을 높이는 습관을 들일 것이다.
  2. SNS 기능 구현 시 화면상의 버튼이 곧 DB 테이블이나 API가 아님을 인지하고, 실제 데이터 구조(예: 좋아요 별도 테이블, 관계형 친구 목록)를 정확히 설계하는 데 집중할 것이다.
  3. 정규화와 복합 UQ 적용 시 ‘한 사실 한 곳 책임’ 원칙을 준수하여, 방향성 있는 친구 관계 설계를 위해 (A,B)와 (B,A) 튜플의 차이를 명확히 구분하도록 하겠다.

다음 복습 주제#

다음에는 SNS 서비스 설계 시 실제 DB 구조 구축 전, 테이블 간의 관계와 제약 조건을 시각화하고 검증하는 연습을 해보고 싶다. 특히 ERD 툴을 활용해 PK·FK 설정을 직접 구성하고, 친구 관계와 같은 대칭/비대칭 정책에 따른 데이터 모델링의 차이점을 비교 분석하여 설계 오류를 사전에 방지하는 방법을 익히길 바란다. 또한 JSON 스키마와 ERD 간의 변환 과정에서 발생할 수 있는 구조 불일치를 해결하기 위한 구체적인 매핑 전략을 연구하여, 이론과 실제 구현 사이의 간극을 메우는 역량을 키우고자 한다.
