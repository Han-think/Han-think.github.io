1. LangGraph로 연결한 질문 분기 그래프#

무엇을 배웠나#

오늘은 기존에 따로 공부해왔던 RAG, DataFrame, Python Worker 기능들이 LangGraph 워크플로우 안에서 하나의 흐름으로 연결된 것을 확인했습니다. 특히 router가 답변을 생성하는 것이 아니라, 어떤 worker를 호출할지 결정하는 가이드 역할이라는 점이 핵심 이해점으로 다가왔습니다. State와 Edge를 통해 데이터가 노드 사이에서 자연스럽게 전달되는 과정을 보니 LangGraph의 구조가 명확해졌습니다.

헷갈렸던 점#

처음에는 router가 답변을 생성하는 역할을 한다고 오해하여, LLM이 스스로 라우팅을 한다는 개념이 직관적이지 않았습니다. 또한 각 기능(Data Retrieval, DataFrame, Python Worker)이 독립적인 기술로 느껴져, LangGraph라는 컨테이너 안에서 어떻게 제어 흐름이 연결되는지 이해하는 데 시간이 걸렸습니다. 하지만 State와 Edge가 노드 사이에서 데이터를 전달하는 통로 역할을 한다는 사실을 깨닫고, 실제 코드로 연결되는 과정을 보니 ‘아, 이렇게 이어지는구나’ 하는 실감나는 이해가 되었습니다.

정리된 이해#

오늘은 그동안 따로 공부해왔던 RAG, DataFrame, Python Worker 기능들이 LangGraph라는 하나의 워크플로우 안에서 어떻게 통합되는지 실감할 수 있었습니다. 특히 router가 답변을 생성하는 것이 아니라, 어떤 worker를 호출할지를 결정하는 가이드 역할이라는 점이 핵심적인 전환점이 되었습니다. 이를 통해 State와 Edge가 어떻게 데이터를 매개체 삼아 노드 사이에서 흐르는지 이해하게 되어, 개념만 익히던 것과 실제 코드로 연결되는 실감나는 차이가 있었습니다.

from langgraph.graph import StateGraph, END

# 1. 공통 상태 정의 (State)
class GraphState(dict):
    question: str = ""
    answer: str = ""
    route: str = ""  # plain, excel, vector 중 하나

# 2. 라우팅 결정 노드 (Router)
def router(state: GraphState) -> dict:
    """
    질문의 의도를 분석하여 어떤 worker를 호출할지 결정합니다.
    실제 구현에서는 LLM 프롬프트나 키워드 매칭을 사용합니다.
    """
    q = state.get("question", "")

    # 간단한 예시 로직: 키워드에 따라 라우팅
    if "엑셀" in q or "데이터" in q:
        route = "excel"
    elif "검색" in q or "관련" in q:
        route = "vector"
    else:
        route = "plain"

    return {"route": route}

# 3. 워커 노드들 (Workers)
def plain_answer(state: GraphState) -> dict:
    """일반적인 질문에 대한 답변 생성"""
    # 실제로는 LLM 호출 또는 지식베이스 조회
    answer = f"일반 답변: '{state['question']}'에 대해 일반적인 정보를 제공합니다."
    return {"answer": answer, "route": state["route"]}

def excel_worker(state: GraphState) -> dict:
    """엑셀 데이터 처리 워커"""
    # 실제로는 pandas 등을 사용해 엑셀 파일 읽기/처리
    answer = f"엑셀 처리 결과: '{state['question']}' 관련 데이터를 분석했습니다."
    return {"answer": answer, "route": state["route"]}

def vector_worker(state: GraphState) -> dict:
    """벡터 DB 검색 워커"""
    # 실제로는 임베딩 후 유사도 검색
    answer = f"검색 결과: '{state['question']}'와 관련된 벡터 DB 검색 완료."
    return {"answer": answer, "route": state["route"]}

# 4. 그래프 구성 (Graph Construction)
workflow = StateGraph(GraphState)

# 노드 추가
workflow.add_node("router", router)
workflow.add_node("plain_answer", plain_answer)
workflow.add_node("excel_worker", excel_worker)
workflow.add_node("vector_worker", vector_worker)

# 진입점 설정 (질문 입력 후 라우팅 노드로 이동)
workflow.set_entry_point("router")

# 조건부 엣지 추가 (라우터 결과에 따라 분기)
# router가 반환한 'route' 값에 따라 해당 워커로 이동
workflow.add_conditional_edges(
    "router",
    # 경로 함수: state의 route 값을 확인하여 노드 이름 반환
    lambda state: state["route"],
    {
        "plain": "plain_answer",
        "excel": "excel_worker",
        "vector": "vector_worker"
    }
)

# 워커 종료 후 END로 연결 (또는 다음 단계로)
for worker_name in ["plain_answer", "excel_worker", "vector_worker"]:
    workflow.add_edge(worker_name, END)

# 그래프 컴파일
app = workflow.compile()

# 5. 실행 예시
if __name__ == "__main__":
    # 테스트 질문 1: 일반 질문
    input_question_1 = "오늘 날씨는 어때?"
    result_1 = app.invoke({"question": input_question_1})
    print(f"질문: {input_question_1}")
    print(f"라우팅: {result_1['route']} -> 답변: {result_1['answer']}\n")

    # 테스트 질문 2: 엑셀 관련 질문
    input_question_2 = "지난달 매출 엑셀 데이터 보여줘"
    result_2 = app.invoke({"question": input_question_2})
    print(f"질문: {input_question_2}")
    print(f"라우팅: {result_2['route']} -> 답변: {result_2['answer']}\n")

2. 라우팅 그래프와 워커 계약: plain과 RAG 구분하기#

무엇을 배웠나#

오늘은 LLM을 사용하더라도 context가 포함되는지에 따라 worker의 성격이 달라진다는 점을 명확히 이해했습니다. 특히 RAG를 전체 파이프라인이 아닌 하나의 ‘worker’로 재사용하는 graph 구조에 집중했으며, plain과 vector의 차이를 모델의 차이보다는 context 제공 여부로 구분하게 되었습니다. 이를 통해 기존 기능을 독립적인 worker로 쪼개 orchestration 안에서 선택 가능하게 만든 과정임을 깨닫게 되었습니다.

헷갈렸던 점#

오늘은 RAG를 독립적인 파이프라인 전체로 생각하다가, graph 내부에서 하나의 ‘worker’로 재사용되는 방식에 혼란을 느꼈습니다. 특히 plain과 vector의 차이가 모델 자체의 차이가 아니라 context 사용 여부라는 점이 코드 레벨에서 추상적으로 느껴졌습니다. 결국 기존 기능을 worker로 쪼개 orchestration 안에서 선택 가능하게 만든 과정이었음을 깨닫게 되었습니다.

정리된 이해#

오늘은 RAG가 독립적인 파이프라인 전체가 아니라, 그래프 내부의 ‘worker’로 재사용되는 방식임을 깨달았습니다. 같은 LLM을 사용하더라도 context를 주느냐 안 주느냐에 따라 답변의 성격이 달라진다는 점이 핵심 개념이었습니다. 결국 기존 기능을 worker로 쪼개 orchestration 안에서 선택 가능하게 만든 과정이었습니다.

# plain worker: LLM에게 질문만 전달하여 직접 생성하게 함
def plain_worker(question):
    # context 없이 모델에 프롬프트 전달
    response = ollama.generate(model='llama3', prompt=question)
    return response['response']

# RAG worker: retriever가 관련 증거를 찾은 뒤, 이를 prompt에 주입 후 LLM 답변 생성
def rag_worker(question):
    # 1. retriever로 관련 문서 검색 (context 확보)
    context = retriever.retrieve(question)

    # 2. context와 질문을 combined한 프롬프트 구성
    prompt = f"Context: {context}\n\nQuestion: {question}"

    # 3. LLM에 프롬프트 전달하여 답변 생성
    response = ollama.generate(model='llama3', prompt=prompt)
    return response['response']

# graph: worker를 호출하기 전후로 routing 로직 처리
def route_question(question):
    # 간단한 예시 라우팅 논리 (키워드 기반)
    if "최신" in question or "가격" in question:
        return rag_worker(question)  # RAG 경로 선택
    else:
        return plain_worker(question)  # Plain 경로 선택

3. 엑셀 파이프라인: 코드 생성에서 답변 도출까지#

무엇을 배웠나#

State를 worker 간의 데이터 버스처럼 활용해 하나의 큰 로직을 여러 node로 나눌 수 있다는 점을 배웠다. 각 단계에서 generation 필드가 코드인지 자연어 답변인지 구분해야 한다는 점이 핵심이었다. 중간 산출물인 code와 data는 각각 다른 의미를 가지며, 이전 단계의 결과가 다음 단계로 전달된다는 점도 확인했다.

헷갈렸던 점#

가장 큰 혼란은 generation 필드가 단계마다 다른 의미를 갖는다는 점이었습니다. LLM이 excel_data 과정에서는 Python 코드를 생성하고, excel_answer 과정에서는 자연어 답변을 생성하는데, 둘 다 같은 이름의 필드에 담기기 때문입니다. 이로 인해 State가 worker 사이에서 데이터를 어떻게 전달하는지, 그리고 데이터의 의미가 단계에 따라 어떻게 변하는지를 파악하는 데 시간이 걸렸습니다.

정리된 이해#

State는 worker 간 데이터 전달을 담당하는 ‘데이터 버스’ 역할을 수행하며, 각 단계별 산출물(코드, 결과, 답변)은 동일한 필드명이라도 그 내용이 달라질 수 있음을 의미한다. worker 내부의 로직을 node로 분할하여 중간 산출물을 다음 단계에 넘길 수 있으며, State 키 이름은 고정하되 시점에 따라 코드인지 텍스트인지를 구분해야 한다.

# Excel Worker Pipeline: Code Generation → Answer Generation

# Step 1: excel_data worker - Code Generation
state = {
    "question": "2024년도 분기별 매출액 평균은?",
    "generated_code": 'df.groupby("quarter")["sales"].mean()',  # LLM generates Python code
}

# Step 2: Excel execution (simulated)
exec_result = eval(state["generated_code"])  # Returns DataFrame or values

# Step 3: Update state with execution result for next step
state["data"] = exec_result  # Calculated result DataFrame/values

# Step 4: excel_answer worker - Answer Generation
final_prompt = f"""Based on the data {state["data"]}, answer the user's question: {state["question"]}"""
final_answer = llm.generate(final_prompt)  # LLM generates natural language response

state["final_answer"] = final_answer  # Final output

총평#

오늘 오전 전체에서 배운 것#

LangGraph 워크플로우 내에서 RAG, DataFrame, Python Worker 등 기존 기능을 독립적인 node로 분리하고 State를 통해 자연스럽게 데이터가 전달되는 흐름을 이해했습니다. 특히 라우팅 결정자(Router)가 답변을 직접 생성하는 것이 아니라, 어떤 worker를 호출할지 안내하는 가이드 역할임을 핵심적으로 파악했습니다. 이를 통해 context 제공 여부에 따라 worker의 성격이 달라지며, 하나의 큰 로직을 여러 node로 나누어 orchestration 하는 전체적인 구조가 명확해졌습니다.

다음에 조심할 것#

LangGraph 워크플로우에서 router는 답변을 생성하는 주체가 아니라, 적절한 worker를 선택하는 가이드 역할에 집중해야 한다.

State와 Edge를 통해 데이터가 노드 사이에서 자연스럽게 전달되도록 설계하여, 하나의 큰 로직을 여러 node로 분할해도 흐름이 끊기지 않도록 해야 한다. each 단계에서 generation 필드가 코드인지 자연어 답변인지 명확히 구분하여, 중간 산출물이 다음 단계에 올바르게 전달될 수 있도록 검증해야 한다.

다음 복습 주제#

LangGraph 워크플로우 내에서의 State 관리와 데이터 흐름에 대해 더 깊이 이해하고 싶습니다. 특히 각 노드에서 생성된 generation 필드가 다음 단계에 어떻게 영향을 주며, 데이터가 어떻게 누적되고 변환되는지 시뮬레이션해보는 연습이 필요합니다.

라우팅 로직을 단순화하기 위해 LLM의 출력 형태뿐만 아니라, worker별로 요구하는 구체적인 input schema와 output format을 정의하는 것이 중요하다고 느꼈습니다. plain과 RAG worker가 context를 어떻게 다른 방식으로 소비하고 생산하는지 명확히 구분하여, graph 구성 시 불필요한 데이터 전달을 방지하는 방법을 모색해보고 싶습니다.

엑셀 파이프라인에서 코드 생성 후 답변 도출까지의 전 과정을 end-to-end로 실행해보며, 각 단계에서의 State 업데이트 시점과 에러 발생 시 롤백 및 재시도 전략에 대해 고민해보고 싶습니다. 특히 code와 data가 분리된 상태에서 어떻게 안전하게 다음 단계로 넘겨주는지가 핵심 포인트입니다.
