1. 학습 안정성 디버깁: axis·dim 차이와 gradient 분석#

무엇을 배웠나#

axis와 dim이라는 용어 차이로 인한 코드 작성 시 혼란을 해소하고, loss 값만으로는 학습 상태를 판단하기 어렵다는 점을 깨닫게 되었다. 또한 gradient norm과 learning rate를 함께 살펴야 모델의 안정성을 정확히 진단할 수 있다는 탐정적인 접근법이 중요하다는 것을 이해했다.

헷갈렸던 점#

axis와 dim이라는 용어가 라이브러리마다 달라 헷갈렸고, loss 값 하나만 보고 학습 상태를 판단하려 했던 사고방식이 gradient norm 등 다른 지표를 봐야 한다는 내용으로 바뀌었습니다.

정리된 이해#

axis=-1과 dim=-1은 파이썬 리스트와 PyTorch 텐서에서 모두 ‘마지막 차원’을 의미하지만, 라이브러리별 표기법 차이를 반드시 확인해야 한다. loss 값만으로는 학습 원인을 규명하기 어렵으므로, gradient norm이나 learning rate 변화까지 함께 살펴야 안정적인 디버깅이 가능하다.

# PyTorch에서 텐서의 마지막 차원(argmax)을 찾는 예시
import torch

# [batch_size, num_classes] 형태의 가상 텐서
logits = torch.tensor([[0.1, 0.9], [0.8, 0.2]])

# dim=-1 (또는 axis=-1)은 '가장 높은 확률의 클래스 인덱스'를 반환
predicted_classes = torch.argmax(logits, dim=-1)

print(predicted_classes)
# tensor([1, 0])

2. 메모리 최적화 옵션별 병목 해결 포인트 정리#

무엇을 배웠나#

각 옵션이 해결하는 병목 위치가 다르다는 점이 명확해졌습니다. gradient_checkpointing는 중간 계산값을 다시 계산하여 메모리를 아끼고, fp16/bf16은 숫자의 정밀도를 낮춰 메모리 사용량을 줄입니다. 또한 gradient_accumulation_steps는 실제 배치 사이즈를 작게 가져가며 여러 번 나누어 학습함으로써 효과적으로 메모리를 절약하는 역할을 한다는 것을 이해했습니다.

헷갈렸던 점#

각 옵션이 모두 ‘메모리 절약’이라는 공통점이 있지만, 어디에 있는 메모리를 어떻게 줄이는지(activation 저장 여부, 숫자 정밀도, 실행 속도 등)의 차이가 명확하지 않았던 점이 가장 큰 혼란점이었다. 특히 gradient_accumulation_steps는 다른 옵션들이 ‘메모리 절약’을 목표로 한다면, 배치 사이즈를 키우는 것처럼 동작해 그 역할이 감 잡히지 않았다.

정리된 이해#

각 옵션이 해결하는 병목 위치가 다르다는 점이 핵심입니다.

gradient_checkpointing는 중간 계산값을 저장하지 않고 다시 계산해 메모리를 아끼고, fp16은 숫자의 정밀도를 낮춰 메모리 사용량을 줄이며, torch.compile은 파이썬 실행을 최적화된 C++ 코드로 변환해 속도를 높입니다. 반면 gradient_accumulation_steps는 실제 GPU에 들어가는 배치 사이즈를 작게 가져간 뒤 여러 번 나누어 연산함으로써, 메모리 부족 문제 없이 효과적으로 배치 사이즈를 키우는 역할을 합니다.

# gradient_accumulation_steps: 실제 배치 사이즈를 키우지 않고 메모리 효율화
# effective_batch_size = actual_batch_size * accumulation_steps

accumulation_steps = 4
actual_batch_size = 8

# GPU에 한 번에 올리는 데이터 양은 8로 유지하면서,
# 4번의 backward pass를 거쳐서 실제 효과적인 배치 사이즈는 32가 됨.

3. 양자화와 XPU 디버깅: 실패 원인 추적과 이해 정리#

무엇을 배웠나#

학습을 시작하며 가장 큰 혼란은 ‘실패 원인 추적’에 있었습니다. 모델 자체, 양자화 백엔드, 그리고 런타임 환경 사이의 경계가 모호해 어떤 요소에서 문제가 발생했는지 가려내기 어려웠습니다. 특히 4비트 양자화가 무조건 가볍고 잘 동작할 것이라 생각했으나, 인코딩 문제나 백엔드 호환성 여부에 따라 결과가 달라진다는 사실을 깨닫고 ‘가벼움’의 기준이 하드웨어 지원 여부에 달렸음을 이해하게 되었습니다. 이러한 혼란을 통해 모델 지원, 양자화 백엔드, 런타임 및 드라이버 지원, 그리고 메모리 할당자의 동작은 각각 독립적인 층(layer)으로 분리되어 있음을 명확히 인식할 수 있었습니다.

헷갈렸던 점#

모델 지원 여부와 양자화 백엔드, 런타임 및 드라이버 지원이 별개의 문제라는 점을 구분하지 못해 실패 원인을 파악하기 어려웠습니다. 또한 4비트 양자화가 무조건 가볍고 잘 동작할 것이라 생각했으나, 인코딩 문제나 백엔드 호환성에 따라 변환 자체가 실패할 수 있다는 사실을 간과했습니다. 마지막으로 XPU 메모리 부족 에러가 실제 사용 가능한 메모리 양의 문제가 아니라 시스템이 할당자를 초기화하는 과정에서 발생할 수 있는 오류임을 깨닫지 못했습니다.

정리된 이해#

양자화와 XPU 디버깅에서 가장 중요한 것은 모델 자체의 호환성 여부를 떠나, 양자화 백엔드, 런타임 환경, 메모리 할당기(allocator)의 상호작용을 정확히 파악하는 것이다. 특히 4비트 양자화가 ‘가볍다’는 인상만으로 끝나지 않고, Triton이나 Intel backend와의 조합 및 Windows의 인코딩 문제 등 구체적인 기술적 장벽을 검증해야 실제 사용이 가능한지를 판단할 수 있다. 마지막으로 XPU out of memory 에러는 단순히 메모리 부족을 의미하기보다, 시스템 allocator의 워밍업 과정이나 특정 백엔드와의 호환성 충돌일 가능성을 먼저 의심하고 체계적으로 원인을 추적하는 것이 핵심이다.

# 양자화 및 XPU 디버깅 핵심 개념 정리 (노트 기반)

# 1. 모델 지원 ≠ 런타임/백엔드 지원
# 모델 자체가 특정 하드웨어를 타는 것이 아니라,
# 양자화 백엔드와 allocator의 조합이 성능을 결정한다.
model_name = "Mistral-7B"
quantization_config = {"bits": 4, "backend": "intel"} # 예시 설정

# 2. XPU Allocator Warmup OOM 구분
# "XPU out of memory" 에러는 메모리 부족이 아닌,
# 시스템 초기화(Warmup) 과정에서 발생할 수 있다.
xpu_memory_status = "allocator warmup in progress" # 실제 상태 예시

# 3. 인코딩 호환성 체크 (Windows cp949 등)
# 4비트 경로라도 인코딩 문제로 변환이 실패할 수 있음.
encoding_check = "cp949 compatibility required for Windows"

4. LoRA·증류·양자화: 무엇을 줄이는가#

무엇을 배웠나#

LoRA는 전체 파라미터를 늘리지 않고, 작은 어댑터만 학습시켜 모델을 미세 조정하는 방식입니다. 증류는 교사의 연부 확률 분포를 학생이 학습하여 작은 모델이라도 큰 모델의 성능을 따라가게 하는 기법입니다. 양자화는 숫자의 표현 정밀도를 낮추어 저장 공간과 추론 비용을 크게 줄이는 방법입니다. 특히 LoRA는 ‘학습 가능한 파라미터 감소’, 증류는 ‘모델 크기 자체 축소’, 양자화는 ‘수치 정밀도 감소’로 구분하면 개념이 명확해집니다.

헷갈렸던 점#

LoRA는 전체 파라미터를 동결하는 방식이라, 모델 자체의 크기가 줄어드는 것이 아니라 학습 가능한 파라미터 수만 감소한다는 점이었다.

증류에서 Temperature 보정은 학생 모델이 teacher의 부드러운 확률 분포를 따라잡도록 돕는 역할을 하지만, 그 과정이 직관적으로 와닿지 않아 헷갈렸다.

양자화는 숫자의 표현 정밀도를 낮추는 것이므로, 모델의 학습 능력이나 파라미터 수가 줄어드는 것이 아니라 추론 속도와 메모리 사용량만 감소한다는 점이 명확하지 않았다.

정리된 이해#

LoRA는 전체 파라미터를 늘리지 않고 adapter만 학습시켜 미세 조정을 가능하게 하며, 증류는 교사의 연부 확률을 학생이 학습해 모델 자체 크기를 줄이는 기법이고, 양자화는 숫자의 표현 정밀도를 낮춰 저장 및 추론 비용을 감소시키는 방법이다.

# LoRA 구조 예시 (Adapter 추가 및 Base Weight 동결)
import torch.nn as nn

class LoRALayer(nn.Module):
    def __init__(self, base_layer, r=8, lora_alpha=16, lora_dropout=0.1):
        super().__init__()
        self.base_layer = base_layer
        # Base weight는 동결 (requires_grad=False)
        for param in self.base_layer.parameters():
            param.requires_grad = False

        # Low-rank adapter
        self.lora_a = nn.Linear(base_layer.in_features, r, bias=False)
        self.lora_b = nn.Linear(r, base_layer.out_features, bias=False)
        self.scaling = lora_alpha / r

        # Dropout (입력 정규화)
        self.dropout = nn.Dropout(lora_dropout)

        # Adapter 파라미터 초기화 (Zero initialization)
        nn.init.zeros_(self.lora_a.weight)
        nn.init.zeros_(self.lora_b.weight)

    def forward(self, x):
        # x → dropout → lora_a → lora_b → scaling → base_output에 더함
        result = self.base_layer(x)
        adapter_out = self.lora_b(self.dropout(self.lora_a(x))) * self.scaling
        return result + adapter_out

# Distillation 손실 함수 예시 (Temperature 보정 포함)
import torch.nn.functional as F

def distillation_loss(student_logits, teacher_logits, labels, temperature=2.0, alpha=0.5):
    # Teacher의 soft target을 위해 온도(Temperature) 스케일링 적용
    student_scaled_logits = student_logits / temperature
    teacher_scaled_logits = teacher_logits / temperature

    # Student 로그 확률 계산 (log_softmax)
    student_log_probs = F.log_softmax(student_scaled_logits, dim=-1)

    # Teacher 확률 분포 계산 (softmax)
    teacher_probs = F.softmax(teacher_scaled_logits, dim=-1)

    # Soft Loss: KL-divergence (Teacher의 부드러운 분포를 맞추는 용도)
    soft_loss = F.kl_div(student_log_probs, teacher_probs, reduction='batchmean') * (temperature ** 2)

    # Hard Loss: 정답 라벨에 대한 Cross Entropy
    hard_loss = F.cross_entropy(student_logits, labels)

    # 전체 손실은 Soft Loss와 Hard Loss의 가중합
    total_loss = alpha * soft_loss + (1 - alpha) * hard_loss

    return total_loss

# 양자화 예시 (INT8로 표현을 축소하는 개념)

from transformers import BitsAndBytesConfig

    load_in_4bit=True,

    bnb_4bit_compute_dtype=torch.float16,# 연산 시 float16 사용
    bnb_4bit_use_double_quant=False      # 2중 양자화 사용 여부

5. Hugging Face Hub 배포와 Gated 모델 운영 이해하기#

무엇을 배웠나#

Hub 배포는 단순히 파일을 올리는 행위가 아니라, 라이선스와 공개 범위 등 다양한 메타데이터를 함께 관리하는 시스템이라는 점을 깨달았다. 특히 게이트된 모델은 로그인 상태만으로는 접근이 불가능하며, 관리자의 승인이 필요한 approval_required 플래그가 핵심임을 이해했다. 코드 뒤에 숨겨진 사람과 조직의 승인 절차가 실제 운영의 핵심임을 깨닫고 개념 정리가 되었다.

헷갈렸던 점#

코드를 짜서 올리는 행위 자체가 목적이 아니라, 라이선스와 공개 범위 등 다양한 메타데이터를 함께 관리하는 시스템이라는 점이 가장 컸습니다.

특히 is_gated 같은 boolean 값 이면에 실제 사람과 조직의 승인 절차가 개입된다는 점이 초보자에겐 낯설게 느껴졌습니다. 단순히 로그인한 상태에서는 접근이 불가능하며, 관리자가 approval_required와 is_approved 플래그를 통해 승인해야만 모델을 다운로드할 수 있다는 점을 이해하는 데 시간이 걸렸습니다.

정리된 이해#

Hub 배포는 단순히 파일을 올리는 행위가 아니라, 라이선스와 공개 범위 등 다양한 메타데이터를 함께 관리하는 시스템이다. 게이트된 모델은 로그인 상태라 해도 승인이 필요하며, approval_required와 is_approved 같은 플래그가 실제 접근을 제어한다. 따라서 코드 작성뿐만 아니라 정책 파일과 토큰 스코프 설정이 모델의 공개 범위를 결정하는 핵심 요소이다.

총평#

오늘 오전 전체에서 배운 것#

오늘은 axis와 dim 같은 용어 차이에서 오는 혼란을 해소하고, loss 값만으로는 판단하기 어려운 학습 안정성을 gradient norm과 learning rate를 함께 살펴야 정확히 진단할 수 있다는 점을 배웠다. 또한 gradient checkpointing, fp16/bf16, gradient accumulation steps 등 각 메모리 최적화 옵션이 해결하는 병목 위치가 다르다는 점과, 양자화나 XPU 디버깅 시 모델, 백엔드, 런타임 환경 사이의 경계를 명확히 구분하여 실패 원인을 추적하는 것이 중요하다는 것을 깨달았다.

다음에 조심할 것#
