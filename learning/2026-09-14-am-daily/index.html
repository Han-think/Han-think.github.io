1. LLM 스트리밍 구조 핵심 개념 정리#

무엇을 배웠나#

비동기 함수와 제너레이터가 결합된 형태를 이해하는 데 집중했다. async와 await는 I/O 대기 중 흐름을 양보하는 장치이며, yield는 함수를 종료하지 않고 값을 한 조각 뱉고 일시 정지하는 기능이다. 이를 통해 StreamingResponse가 제너레이터가 뿜어낸 조각들을 HTTP 응답으로 감싸주는 구조임을 명확히 파악했다.

헷갈렸던 점#

async, await, yield가 단순히 비동기나 반복과 관련된 키워드인지, 실제로는 I/O 흐름을 양보하고 값을 일시 정지했다가 이어주는 제너레이터의 핵심 기능인지 구분이 안 갔다.

StreamingResponse와 yield가 별개의 개념인지 하나로 묶여 있는 것인지, 조각을 내는 행위와 HTTP 응답으로 감싸주는 행위가 어떻게 연결되는지 명확히 구분하지 못했다.

Python 코드 내에 Path("server.py").write_text(...) 같은 파일이 존재했는데, 이것이 단순한 터미널 명령어처럼 보여서 Python 코드 내부의 파일 I/O 기능인지, 별도의 실행 명령인지 혼동했다.

정리된 이해#

비동기 함수는 I/O 대기 중 흐름을 양보해 다른 작업을 수행하게 하며, yield를 사용한 제너레이터는 값을 한 조각씩 뱉으며 일시 정지했다가 이어간다. 이를 StreamingResponse가 감싸 HTTP 응답으로 전송하는 구조다.

from fastapi.responses import StreamingResponse

async def generate_chunks():
    # 비동기 제너레이터: 값을 하나씩 뱉고 일시 정지
    yield "첫 번째 조각"
    await asyncio.sleep(0.5)  # I/O 대기 시뮬레이션
    yield "두 번째 조각"

# StreamingResponse는 제너레이터가 뱉어낸 조각들을 HTTP 응답으로 감쌈
streaming_response = StreamingResponse(generate_chunks())

2. GPU 스택 차이와 실행 경로의 오해#

무엇을 배웠나#

Intel Arc GPU를 사용한다고 해서 모두 torch.xpu가 동작하는 것은 아니었다는 점이 가장 큰 깨달음이었다. 특히 07-1 프로젝트에서 Python이 LM Studio에 API 요청을 보내는 구조임을 깨닫고, ‘소프트웨어 실행 경로’의 차이를 명확히 구분할 수 있게 되었다. 이로써 하드웨어 이름은 같지만 실제 명령을 내리는 주체가 PyTorch인지, LM Studio인지에 따라 성능과 로그가 완전히 달라진다는 사실을 이해하게 되었다.

헷갈렸던 점#

처음에는 Python 코드가 GPU를 직접 제어하는 것으로 착각하기 쉽습니다. 특히 torch.xpu가 언급될 때, 그것이 하드웨어를 제어하는 주체라고 생각하기 쉬웠습니다. 하지만 실제로는 프로젝트마다 추론을 담당하는 소프트웨어 스택이 완전히 달라, 하드웨어 이름은 같지만 명령의 주체가 다르다는 점이 핵심적인 혼점이었습니다.

정리된 이해#

Intel Arc GPU는 프로젝트마다 하드웨어 이름은 같지만, 실제 명령을 내리는 소프트웨어 스택이 완전히 다르다. 07 프로젝트는 Python이 직접 torch.xpu를 통해 모델을 제어하는 반면, 07-1 프로젝트는 Python이 LM Studio의 HTTP API에 요청을 보내고 Vulkan 기반 엔진이 추론을 담당한다. 따라서 하드웨어가 같더라도 실행 주체와 경로가 달라지므로 torch.xpu 사용 여부를 반드시 확인해야 한다.

# 07 프로젝트 (PyTorch XPU) 경로 예시
import torch

device = "xpu" if torch.xpu.is_available() else "cpu"
model = AutoModelForCausalLM.from_pretrained("path/to/model", device_map=device)

# 07-1 프로젝트 (LM Studio/Vulkan) 경로 예시
import requests

response = requests.post(
    url="http://localhost:1234/v1/completions",
    json={"model": "local-model", "prompt": "Hello, world!"}
)
print(response.json()["choices"][0]["text"])

3. FastAPI와 Hugging Face 모델 통합 구조 정리#

무엇을 배웠나#

FastAPI와 Hugging Face Transformers를 활용한 멀티모달 모델 구현 과정에서, 파일 업로드 함수들이 HTTP 요청 수신, 임시 저장, 모델 추론 등 서로 다른 역할을 수행한다는 점을 명확히 구분할 수 있었습니다. 또한 장치 선택 코드가 모델 로드 시점에 실행되며, HTTP 응답 성공 여부와 무관하게 실제 가속기 사용 여부는 환경에 따라 달라진다는 사실을 확인했습니다. 이러한 계층적 구조 분리를 통해 웹 서버의 안정성과 모델 실행의 유연성을 동시에 확보할 수 있다는 점을 실감했습니다.

헷갈렸던 점#

처음에는 /upload, fileUpload(), class_img() 같은 함수 이름이 모두 ‘파일 처리’ 역할을 한다고 직관적으로 생각했지만, 실제로는 HTTP 요청 수신, 임시 저장, 모델 추론이라는 완전히 다른 책임이 섞여 있었습니다. 또한 “XPU로 실행된다"는 문구를 보고 자동으로 Intel Arc GPU가 활성화된 것으로 착각했는데, 코드를 보니 torch.xpu.is_available()이 False면 CPU로 폴백되는 구조라 실제 가속기 작동 여부는 startup log와 장치 확인 상태에 달려 있다는 점이 가장 핵심이었습니다.

정리된 이해#

이 프로젝트는 FastAPI로 웹 요청을 받고, Hugging Face Transformers 멀티모달 모델(Qwen3-VL)을 Intel XPU 또는 CPU에서 추론하는 파이프라인입니다. 핵심은 HTTP 엔드포인트와 파일 경로 관리를 담당하는 main.py와, 실제 이미지 전처리부터 모델 생성까지 수행하는 image_service.py의 책임 분리입니다. 장치 선택(torch.xpu.is_available())은 모델 로드 시점에 이루어지며, HTTP 응답 성공 여부와 무관하게 실제 가속기 사용 여부는 실행 환경에 따라 달라집니다.

@app.post("/upload")
def upload(files: UploadFile = File(...), query: str = Form(...)):
    # 1) UUID로 파일명 충돌 방지
    filename = f"{uuid4().hex}_{files.filename}"
    file_path = UPLOAD_DIR / filename

    # 2) 임시 저장 (바이트 단위 스트리밍)
    with open(file_path, "wb") as f:
        shutil.copyfileobj(files.file, f)

    # 3) 모델 서비스에 전달하여 추론 수행
    result = image_service.process_image(str(file_path), query)

    # 4) 응답 정리 및 파일 삭제
    return {"filename": filename, "result": result}

총평#

오늘 오전 전체에서 배운 것#

LLM 스트리밍 구조는 비동기와 제너레이터가 결합된 형태로, yield를 통해 함수를 멈추지 않고 조각을 뱉으며 HTTP 응답으로 전송하는 방식이다. GPU 환경에서는 하드웨어 이름이 같더라도 PyTorch와 LM Studio 등 실행 주체에 따라 실제 명령 경로와 성능이 완전히 달라질 수 있음을 명확히 구분할 필요가 있다. FastAPI와 Hugging Face 모델 통합에서 파일 업로드 및 장치 선택 코드는 서로 다른 계층을 담당하며, 환경에 따라 실제 가속기 사용 여부가 달라지는 유연성을 확보할 수 있었다.

다음에 조심할 것#

  1. 명시적 동기화와 경로 구분: 비동기 함수와 제너레이터의 흐름을 혼동하지 않도록, await가 I/O 양보인지 yield가 일시정지인지 명확히 구분하여 코드 구조를 설계해야 한다.
  2. 하드웨어 vs 실행 주체 인식: ‘Intel Arc’ 같은 하드웨어 이름이 붙었다고 해서 자동으로 가속화가 되는 것이 아니라, 요청이 PyTorch로 가는 것인지 LM Studio API로 가는 것인지 반드시 확인해야 성능과 로그 해석에 오류가 없다.
  3. 계층적 구조의 독립성: FastAPI와 모델 추론 코드를 rigid하게 결합하기보다, 장치 선택 및 파일 처리 부분을 별도로 관리하여 웹 서버 안정성과 모델 실행 유연성을 동시에 확보하는 설계 습관을 들여야 한다.

다음 복습 주제#

LLM 스트리밍 구현 시 async와 yield가 비동기 흐름을 어떻게 제어하는지, 그리고 실제 실행 경로가 하드웨어 스택이 아닌 요청 주체(PyTorch vs LM Studio)에 의해 결정된다는 점을 명확히 구분하는 연습을 해야 한다. 또한 FastAPI 기반 멀티모달 시스템에서 모델 로드 시점의 장치 선택과 HTTP 응답과는 무관하게 가속기 사용 여부가 환경에 따라 달라지는 계층적 구조를 정확히 이해하고 적용할 수 있도록 복습한다.
