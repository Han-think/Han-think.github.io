1. Redux 상태 흐름 이해하기: 컴포넌트→요청→dispatch→reducer→store→렌더링#

무엇을 배웠나#

Redux를 처음 접할 때 가장 큰 혼란은 ‘데이터 흐름’을 이해하지 못해 각 라이브러리의 역할이 겹치는 것처럼 보였던 점입니다. 핵심적으로 Reducer는 HTTP 요청을 실행하는 곳이 아니라, 이미 도착한 데이터를 State에 반영하는 규칙이라는 점을 깨닫고 구조가 명확해졌습니다. 특히 페이지네이션 같은 경우 page 번호 변경이 트리거가 되어 결과가 Store에 반영되어 UI가 업데이트되는 흐름으로 이해했습니다.

헷갈렸던 점#

처음 Redux를 접했을 때, 가장 큰 혼란은 ‘도구들의 집합’이 아니라 ‘데이터가 흐르는 구조’로 받아들이지 못했던 점입니다. 특히 reducer 코드 안에서 axios 호출이나 async/await 같은 비동기 관련 코드가 섞여 보여서 “Reducer가 직접 통신을 하는 건가?“라는 오해를 하게 되었고, state를 업데이트하는 시점과 데이터가 화면에 그려지는 시점을 구분하지 못했습니다.

강사님의 피드백을 통해 ‘Redux = 상태 저장소’라는 본질을 되찾았습니다. 핵심은 Reducer는 HTTP 요청을 실행하는 곳이 아니라, 이미 도착한 데이터를 State에 반영하는 ‘규칙’이라는 점입니다.Reducer는 state를 업데이트하는 규칙이며, 비동기 통신은 액션 생성자나 미들웨어가 담당한다는 점을 명확히 이해하게 되었습니다.

정리된 이해#

Redux는 상태를 저장하는 공간이며, Reducer는 비동기 통신 결과물을 단순히 State에 반영하는 규칙일 뿐 직접 HTTP 요청을 수행하지 않는다. 데이터 흐름은 컴포넌트에서 Axios로 외부 요청을 보낸 뒤, 그 응답을 dispatch하여 Reducer가 Store에 업데이트하고, 최종적으로 useSelector로 화면에 렌더링되도록 연결된다.

// 1. 액션 생성 (변경 요청)
const setPosts = (posts) => {
  return { type: 'posts/setPosts', payload: posts };
};

// 2. 리듀서 (상태 변경 규칙)
// Reducer 안에는 axios 코드를 넣지 않으며, 오직 state를 업데이트하는 규칙만 정의합니다.
const postsReducer = (state = initialState, action) => {
  switch (action.type) {
    case 'posts/setPosts':
      return { ...state, list: action.payload };
    default:
      return state;
  }
};

2. Git의 핵심 흐름과 개념을 정리한 글입니다.#

무엇을 배웠나#

Git은 Working Tree, Staging Area, Commit으로 이어지는 명확한 상태 전이를 통해 파일 변경을 관리한다. git add 명령어를 통해 파일을 스테이징 영역에 올리는 과정은 단순히 저장하는 것이 아니라, 다음 커밋에 포함시킬 후보를 선별하는 역할을 한다. 또한, git commit -a와 같은 옵션을 사용하면 tracked된 파일만 자동으로 처리되어 전체 파일을 수동으로 추가할 필요 없이 효율적으로 작업할 수 있다.

헷갈렸던 점#

git add는 단순히 파일을 저장하는 것이 아니라, ‘다음 커밋에 포함시킬 파일’을 스테이징 영역에 올리는 별도 과정이라는 점이 가장 혼란스러웠다.

또한 git commit -a가 tracked 파일만 자동으로 처리한다는 사실로 인해, untracked 파일이 포함되지 않을까 걱정하며 실수할 뻔했던 경험이 있다.

정리된 이해#

Git은 **Working Tree(작업 트리)**에서 파일을 수정하고, git add 명령어로 변경된 내용을 **Staging Area(스테이징 영역)**에 올린 뒤, commit을 통해 영구적으로 저장하는 명확한 상태 전이를 기반으로 동작한다. 이 과정에서 git status로 현재 위치를 확인하고, git commit -a와 같은 옵션은 tracked 파일만 자동으로 처리한다는 점을 구분하여 사용하는 것이 중요하다. ultimately, 이러한 흐름을 Redux와 유사한 ‘변화하는 상태를 추적한다’는 관점에서 이해하면 명령어의 목적과 순서가 더 명확해진다.

# 1. 현재 상태 확인 (Working Tree 위치 파악)
git status

# 2. 파일을 스테이징 영역에 올리기 (커밋 후보 등록)
git add readme.md

총평#

오늘 오전 전체에서 배운 것#

Redux는 상태 업데이트를 위한 ‘규칙’과 ‘저장소’로 구성되며, 컴포넌트에서 발생한 액션이 리듀서를 거쳐 스토어에 반영되어 UI가 갱신되는 흐름을 이해했다. 또한 Git은 Working Tree와 Staging Area를 거치는 명확한 상태 전이를 통해 파일 변경을 관리하며, git add는 다음 커밋 후보를 선별하는 역할을 한다는 점을 정리했다.

다음에 조심할 것#

Redux는 상태 업데이트를 위해 불필요한 HTTP 요청을 실행하지 않으며, 오직 도착한 데이터를 State에 반영하는 순수 함수임을 기억해야 합니다.

Git에서는 add가 단순히 저장하는 것이 아니라 다음 커밋 후보를 선별하는 과정이므로, 명령어 옵션의 동작 원리를 정확히 파악해 실수를 줄여야 합니다.

다음 복습 주제#

Redux에서 미들웨어(예: thunk)의 역할과 비동기 액션 처리 흐름을 확실히 이해해야겠다. 단순히 동기적인 상태 업데이트를 넘어, API 통신 후 받아온 데이터를 어떻게 디스패치하고 리듀서에 전달할지 전체 파이프라인을 머릿속에 그릴 수 있어야 한다.

Git에서 브랜치 전략(Feature Branch, Git Flow 등)과 충돌 해결(CONFLICT) 과정에 대해 심화 학습해야 한다. add와 commit의 기본 개념은 알았지만, 실제 팀 프로젝트에서 여러 명이 동시에 수정했을 때 발생하는 복잡한 상황과 해결 방법을 체계적으로 익혀야 실전 역량이 될 것이다.

Redux와 Git의 기초 흐름을 확실히 잡았으니, 다음 단계로는 각 라이브러리/도구의 고급 기능이나 실제 프로젝트 적용 사례에 집중해야겠다. 특히 Redux Toolkit을 활용한 효율적인 상태 관리 패턴과, Git에서 리베이스(Rebase)나 머지 전략(Merge Strategy)을 정확히 이해하여 이력 관리를 깔끔하게 하는 방법을 공부하고 싶다.
