1. 쇼핑몰 요구사항 엔터티 구조 이해하기#

무엇을 배웠나#

처음에는 엔터티와 관계 구분을 혼동했지만, ‘한 행의 의미’를 명확히 적는 과정을 통해 어떤 데이터가 테이블이 되어야 하는지 구분할 수 있게 되었습니다. 특히 ‘기능의 개수와 테이블의 개수는 다르다’는 원칙을 이해하면서, 주문 내역이나 후기와 같이 시간에 따라 변하거나 연결되는 데이터를 어떻게 구조화해야 할지 실무적인 안목을 갖게 되었습니다.

헷갈렸던 점#

처음에는 화면에 여러 개의 테이블이 동시에 보였을 때, ‘왜 이렇게 많은 테이블로 쪼개져 있지?‘라는 의문이 가장 컸습니다. 특히 ‘구매’ 기능이 왜 구매 테이블 하나로 끝나지 않고 구매상품 같은 별도 테이블이 필요한지 이해하는 데 시간이 걸렸습니다.

또 엔터티(테블) 후보가 되는 ‘명사’와, 관계를 결정하는 ‘동사·규칙’을 구분하는 일도 처음에는 혼동되었습니다. 단순히 그림을 그리는 것과 실제 업무 규칙을 데이터 구조로 표현하는 일은 다른 차원의 고민이 필요하다는 점을 직관적으로 파악하기 어려웠습니다.

학습 후 가장 중요하게 바뀐 생각은 **“모든 명사가 테이블이 되는 것은 아니다”**라는 점입니다. 요구사항에 나오는 명사는 엔터티 후보가 될 수 있지만, 먼저 그 ‘한 행(row)‘이 실제로 무엇을 의미하는지 정확한 문장으로 적어보는 과정이 필수적이었습니다. 특히 **‘기능의 개수 ≠ 테이블의 개수’**라는 원칙이 가장 와닿았습니다. 주문 한 번에 여러 상품을 산다거나, 구매 후기가 나중에 달리는 등 데이터가 시간에 따라 어떻게 변하는지, 누가 정보를 소유하고 있는지 등을 고려해 테이블을 나누어야 합니다.

2. 회원·일반회원·판매자회원 분리와 민감정보#

무엇을 배웠나#

테이블 설계 시 로그인에 필요한 공통 속성은 최상위 테이블에, 역할별 고유 속성은 상세 테이블로 분리하는 것이 일반적이다. 이를 통해 회원번호(PK)를 외래키(FK)로 설정해 1:0..1 관계를 구축하면 데이터 중복을 방지하고 역할을 명확히 구분할 수 있다. 또한 민감정보인 정산계좌와 같은 경우, 암호화 및 접근 권한 관리 등 별도의 보안 통제가 반드시 필요하다는 점을 확인했다.

헷갈렸던 점#

처음에는 단순히 테이블을 어떻게 나누는가에만 집중해 아이디와 비밀번호 중복 여부, 배송지와 정산계좌의 위치에 대해 명확한 기준이 없어 혼란스러웠다. 특히 회원이면서 동시에 판매자가 될 수 있는지에 대한 역할 관계설정이 가장 큰 걸림돌이었다.

정리된 이해#

공통 속성(아이디, 비밀번호)은 최상위 회원 테이블에 두고, 역할별 특화 속성(배송지, 정산계좌 등)은 상세 테이블로 분리하는 것이 일반적이다. 1:0..1 관계를 활용해 상세 테이블의 회원번호를 기본키와 외래키로 설정하면 데이터 중복을 방지하고 역할당 최대 한 행만 소유하게 할 수 있다. 판매자 정산계좌처럼 민감정보는 최소화된 수집과 암호화, 접근 권한 관리 등 별도의 보안 통제가 반드시 필요하다.

-- 공통 속성(아이디, 비밀번호 등)을 가진 최상위 회원 테이블
CREATE TABLE member (
    member_id INT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    password VARCHAR(255) NOT NULL,
    email VARCHAR(100),
    create_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 역할에 따라 확장되는 상세 테이블 (예: 일반회원, 판매자)
-- 회원 번호를 기본키이자 외래키로 설정하여 1:0..1 관계 형성
CREATE TABLE member_detail (
    member_id INT PRIMARY KEY,
    -- 역할별 고유 속성 (일반회원의 경우 배송지, 판매자의 경우 정산계좌 등)
    address VARCHAR(255),
    bank_account VARCHAR(50), -- 민감정보 예시
    FOREIGN KEY (member_id) REFERENCES member(member_id) ON DELETE CASCADE
);

3. 대분류·중분류·소분류와 키의 구분#

무엇을 배웠나#

PK는 행을 고유하게 식별하는 제약 조건이며, FK는 다른 테이블의 PK를 참조해 관계를 맺고 상위 데이터를 조회할 수 있는 연결 고리다. INDEX는 쿼리의 실행 속도를 높이기 위한 성능 최적화 도구로, 반드시 제약 사항은 아니지만 자동으로 생성되기도 한다. 따라서 컬럼 설계 시 PK와 FK의 관계 설정이 우선이며, 이후 조회 빈도에 따라 INDEX를 추가하는 것이 좋다.

헷갈렸던 점#

PK는 행을 식별하는 고유 제약 조건이고, FK는 다른 테이블과의 관계를 맺기 위한 참조 값이다. 인덱스는 조회 성능을 위해 만든 보조 구조이며, PK나 FK가 자동으로 생성되기도 하지만 필수적인 설계 요소는 아니다.

정리된 이해#

PK는 테이블 내 행을 고유하게 식별하는 제약 조건이며, FK는 다른 테이블의 PK를 참조하여 관계를 맺고 상위 데이터를 조회할 수 있게 한다. INDEX는 쿼리 성능을 최적화하기 위한 보조 구조로, PK나 FK가 자동으로 생성되기도 하지만 무조건적인 관계는 아니다.

-- PK(Primary Key) 예시: 각 행을 고유하게 식별하는 컬럼
CREATE TABLE Category (
    category_id INT PRIMARY KEY,  -- PK: 중복 불가, 자동 인덱스 생성
    name VARCHAR(50)
);

-- FK(Foreign Key) 예시: 다른 테이블의 PK를 참조하여 관계 맺기
CREATE TABLE Product (
    product_id INT PRIMARY KEY,
    product_name VARCHAR(100),
    category_id INT,              -- FK: 부모 테이블(category)의 PK를 참조
    FOREIGN KEY (category_id) REFERENCES Category(category_id)
);

-- INDEX 예시: 조회 성능을 위해 별도로 생성한 인덱스
CREATE INDEX idx_product_category ON Product(category_id); -- FK에 자동 인덱스가 붙어있지만, 상황에 따라 추가 생성 가능

4. 주문 상품 이력 관리하기#

무엇을 배웠나#

구매 당시 가격을 보존하는 것이 정규화 위반이 아니라, 현재 가격과 구별되는 ‘역사적 스냅샷’을 유지하기 위한 필수 요소라는 점이 가장 명확해졌습니다. 또한, 주문상품을 독립적인 거래 사실로 보고 구매번호와 상품번호를 외래키로 활용하면 테이블 간의 관계를 자연스럽게 연결할 수 있음을 이해했습니다. 마지막으로 후기가 실제 구매자임을 보장하려면 구매상품 ID까지 참조해야 한다는 점에서, 단순한 회원 식별만으로는 권한을 검증하기 부족하다는 사실을 배웠습니다.

헷갈렸던 점#

정규화 원칙과 데이터 중복의 경계가 모호해, 구매 당시 가격을 저장하는 것이 위반인지 아닌지 혼란스러웠다.

한 행이 ‘특정 주문에서 특정 상품을 몇 개 얼마에 샀는가’라는 단일 거래 사실을 의미한다는 점을 이해하고 나니, 가격 보존이 정규화 위반이 아니라 ‘역사적 사실의 스냅샷’을 보존하는 것이라는 명확함이 생겼다.

후기가 실제 구매 경험과 연결되도록 하려면 구매상품 ID까지 참조해야 한다는 점에서, 단순히 회원 아이디만으로는 권한 확인이 불충분하다는 사실을 깨닫고 데이터 모델링의 필수 요소를 재정리했다.

정리된 이해#

데이터 모델링에서 ‘구매상품’은 특정 주문 내의 개별 상품을 의미하며, 여기서 가격과 수량은 역사적 스냅샷으로 보존하는 것이 시스템 정확성을 위한 필수 요소입니다. 또한, 후기가 실제 구매 경험에 기반했음을 보장하기 위해서는 구매상품 ID를 연결 고리로 활용해야 합니다.

-- 주문 상세 내역을 보존하는 테이블 구조 예시
CREATE TABLE purchase_items (
    purchase_id VARCHAR(50),      -- 주문번호 (외래키)
    product_id VARCHAR(50),       -- 상품번호 (외래키)
    quantity INT,                 -- 구매 수량
    unit_price DECIMAL(10, 2),    -- 구매 당시 단가 (역사적 스냅샷 보존)
    PRIMARY KEY (purchase_id, product_id) -- 복합 기본키: 주문+상품 조합의 고유 식별자
);

-- 후기가 실제 구매와 연결되는 예시
CREATE TABLE reviews (
    review_id INT AUTO_INCREMENT PRIMARY KEY,
    purchase_id VARCHAR(50),      -- 어떤 구매건에 대한 후기인지 보장
    user_id VARCHAR(50),           -- 작성자
    rating INT,                    -- 별점
    content TEXT,                  -- 후기 내용
    FOREIGN KEY (purchase_id) REFERENCES purchase_items(purchase_id) -- 권한 보장 FK
);

5. ERDCloud 관계선과 실제 제약 조건의 차이 (초보자 워킹 노트)#

무엇을 배웠나#

ERDCloud 사용 시 시각적 요소에 과신하면 실제 데이터베이스 제약 조건과 동떨어진 그림만 남을 수 있음을 깨달았다. PK가 자식 테이블 PK에 포함되면 식별 관계, 그렇지 않으면 비식별 관계라는 규칙을 단순히 외우는 것을 넘어 컬럼 구조를 직접 검증해야 한다는 점을 명확히 했다. 이를 통해 관계선 그리기 행위 자체를 목적으로 하기보다, 논리적인 제약 조건이 제대로 반영되었는지 확인하는 과정이 중요하다는 교훈을 얻었다.

헷갈렸던 점#

ERDCloud에서 선이나 색상 등 시각적 요소에 의존하다 보니, 실제 테이블 간의 제약 조건(PK/FK 포함 여부)을 확인하는 과정을 소홀히 했던 점이 가장 큰 혼란의 원인였습니다.

특히 ‘PK가 자식 PK에 포함되면 식별 관계’라는 규칙은 외웠지만, 컬럼 구조를 보고 이것이 맞는지 검증하는 실무적인 과정이 부족해 단순히 선을 긋는 행위만으로 관계를 확정하려 했던 점이 문제였습니다.

정리된 이해#

식별 관계는 자식 테이블의 기본키에 부모 테이블의 기본키가 포함되어 있어, 부모 키 없이는 존재할 수 없는 강한 종속성을 의미한다. 반면 비식별 관계는 자식 테이블이 부모 키를 기본키에 포함하지 않으면서도 외래키로 참조하여 관련성을 유지하는 약한 종속성이다. 이러한 구분은 데이터베이스 설계 시 단순히 선을 긋는 것을 넘어, 실제 제약 조건과 테이블 구조를 정확히 검증하는 과정이 필수적임을 이해하게 되었다.

-- 식별 관계 (Identifying Relationship)
-- 자식 테이블의 PK에 부모 테이블의 PK가 포함된 경우
CREATE TABLE parent_table (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE child_table (
    parent_id INT,      -- FK이자 PK
    child_name VARCHAR(50),
    PRIMARY KEY (parent_id)  -- 부모 PK가 자식 PK에 포함됨
);

-- 비식별 관계 (Non-Identifying Relationship)
-- 자식 테이블의 PK에는 부모 키가 포함되지 않음
CREATE TABLE parent_table (
    id INT PRIMARY KEY,
    name VARCHAR(50)
);

CREATE TABLE child_table (
    id INT AUTO_INCREMENT PRIMARY KEY, -- 고유한 자식 PK
    parent_id INT,                     -- FK (부모 참조)
    child_name VARCHAR(50),
    FOREIGN KEY (parent_id) REFERENCES parent_table(id)
);

총평#

오늘 오전 전체에서 배운 것#

오늘은 엔터티와 관계의 개념적 차이를 명확히 이해하고, 회원 구분과 민감정보 보안 필요성을 실무적으로 적용하는 방법을 학습했습니다. 특히 구매 당시 가격을 보존하는 것이 정규화 위반이 아니라 역사적 데이터 유지에 필수적임을 깨닫고, ERD 작성 시 시각적 요소보다는 실제 제약 조건을 검증하는 과정을 중요하게 생각하게 되었습니다.

다음에 조심할 것#

  • ERD 설계 시 시각적 도구에 의존하기보다, PK와 FK의 제약 조건 논리를 직접 검증하여 실제 DB 구조와 일치하는지 확인해야 한다.
  • 민감정보(예: 정산계좌) 처리 시 암호화 및 접근 권한 관리 등 별도의 보안 통제를 반드시 수반해야 함을 인지하고 설계에 반영해야 한다.
  • 컬럼 설계는 PK와 FK 관계를 우선으로 한 뒤, 조회 빈도에 따라 INDEX를 추가하여 성능을 최적화하는 순서로 진행해야 한다.

다음 복습 주제#

정규화와 성능 최적화의 균형 역사적 데이터 보존(가격 스냅샷)의 필요성과 테이블 분리 전략을 이해했습니다. 앞으로는 PK/FK 관계를 먼저 확정한 후, 조회 패턴에 따라 INDEX를 추가하는 순서로 컬럼 설계를 진행해야 합니다. 또한 ERD 툴 사용 시 시각적 편의성에 의존하기보다, 실제 DB 제약 조건(식별/비식별 관계)을 검증하는 습관을 들여야 합니다.

민감정보와 보안 설계 회원 등급에 따른 속성 분리 구조는 명확히 익혔지만, 민감정보(정산계좌 등) 처리에 대한 구체적인 보안 통제가 필수라는 점을 새겼습니다. 앞으로는 역할별 테이블 분리와 함께 암호화 및 접근 권한 관리 방안을 병행하여 설계해야 합니다.

관계 모델링의 실제 적용 ERDCloud를 활용한 그림 그리기만으로는 부족하다는 교훈을 얻었습니다. 관계선(식별/비식별)은 컬럼 구조가 PK를 공유하는지 여부에 따라 결정되므로, 직접 테이블 스키마를 검증하며 관계를 설정하는 연습을 해야 합니다.
