1. Redux 데이터 흐름과 비동기 처리 위치 수정 (pm-01-redux-data-flow-refactor)#

무엇을 배웠나#

Redux는 상태 변경 경로와 조회 경로를 분리하여 관리하는 것이 핵심이며, reducer는 단순히 데이터를 state에 넣는 단순 저장 전용 역할임을 깨달았다. 서버 요청 후 dispatch를 통해 reducer가 state를 업데이트하고, useSelector로 값을 꺼내 화면에 렌더링하는 전체 흐름을 이해하게 되어 혼란이 해소되었다.

헷갈렸던 점#

dispatch와 reducer가 단순히 데이터를 넣는 통로라고 생각하다 보니, 비동기 처리가 어떻게 맞물리는지 감이 안 잡혔습니다. 실제로는 서버 요청 후 받아온 데이터를 dispatch해야 reducer가 실행되므로, 흐름을 분리해서 이해하는 것이 중요했습니다.

정리된 이해#

Redux는 상태 변경 경로와 조회 통로를 분리하여 데이터 흐름을 일관되게 관리하는 도구다. 핵심은 dispatch를 통해 reducer가 state를 업데이트하고, useSelector로 화면에 값을 전달하는 구조를 이해하는 것이다. 복잡한 비동기 처리는 미들웨어나 thunk를 사용하더라도 이 기본적인 흐름만 명확히 하면 코드의 의도가 쉽게 파악된다.

// boardSlicer.jsx - reducer (단순 저장 전용)
reducers: {
    setList(state, action) {
        state['list'] = action.payload.list;
        state['pages'] = action.payload.pages;
        return state;
    },
    setDetail(state, action) {
        state['detail'] = action.payload.detail;
        return state;
    }
}

2. 게시판 목록 데이터 흐름 이해하기#

무엇을 배웠나#

처음에는 파일 구조와 Redux 흐름이 복잡하게 느껴졌지만, 핵심은 ‘데이터 담당’과 ‘화면 담당’으로 나뉘는 것이었다. 목록 기능은 URL을 확인해 데이터를 요청하고, Redux를 통해 전역 상태를 관리하며, ListComp가 그 데이터를 화면에 뿌리는 식으로 동작한다. 또한 Pagination은 새로운 데이터 요청을 트리거하는 스위치 역할을 한다는 점을 명확히 이해할 수 있었다.

헷갈렸던 점#

처음에는 파일 구조가 복잡하게 느껴져 각 파일의 역할이 겹치는 것 같아 혼란스러웠습니다. 특히 Redux를 기존 코드에 적용할 때 데이터가 어디서 오고 가는지 감이 안 잡혀 ‘목록 기능이 어디에 있는지’를 파악하는 데 어려움이 있었습니다.

핵심은 목록 기능이 **데이터 요청(ListPage)**과 **화면 출력(ListComp)**으로 나뉘어 있다는 점입니다. Pagination은 새로운 시스템이 아니라 데이터 흐름 회로에 ‘스위치’를 켜는 역할이며, 특정 페이지 번호를 누르면 onSubmit(page) 함수를 호출해 다시 데이터를 요청하는 트리거가 된다는 점을 명확히 했습니다.

정리된 이해#

핵심은 데이터 담당과 화면 담당으로 나뉘어 있다는 점이다. 목록 기능은 URL slug를 확인해 axios로 데이터를 요청하고, Redux store에 저장한다. 이후 ListComp는 stored된 데이터를 읽어 화면에 뿌리고, 페이지 변경 시 부모에게 알리는 역할을 한다. Pagination은 새로운 시스템이 아니라 데이터 흐름 회로에 ‘스위치’를 켜는 역할이다.

🔰 초보자 시점: 내가 헷갈렸던 점#

처음에는 파일 구조가 너무 복잡하게 느껴졌다. page.jsx, ListComp.jsx, boardSlicer.jsx, store.jsx까지 네 개의 파일이 연관되어 있는데, “왜 이렇게 쪼개져 있지?“라는 의문이 들었다.

특히 Redux라는 새로운 개념을 기존 게시판 코드에 끼워 넣으려니 감이 안 왔다. 각 파일의 역할이 겹치는 것 같으면서도 어디서 데이터가 오고 가는지 감이 잡히지 않았다. “이게 다 무슨 역할을 하는 거지?” 하며 코드를 line-by-line로 따라가야만 겨우 이해되는 수준이었다.

가장 혼란스러웠던 지점은 **‘목록 기능이 어디에 있는지’**였다. 페이지 이동(Pagination) 버튼을 누르면 데이터가 다시 오는 건 알겠는데, 그 과정이 page.jsx에서 시작되는지, ListComp에서 시작되는지, 아니면 Redux store를 경유하는지 구분이 안 갔다. “Pagination이 새로 데이터를 요청하는 주체인가, 아니면 그냥 화면을 넘어가는 역할만 하는 건가?“라는 질문이 끊임없이 들었다.

📌 정리된 이해#

핵심은 **“목록 기능은 데이터 담당과 화면 담당으로 나뉘어 있다”**는 점이다.

  1. 데이터 요청 및 관리 (ListPage): URL의 slug를 확인하고, axios로 서버에 목록을 요청한 뒤, Redux store에 데이터를 저장한다.
  2. 상태 공유 (Redux): 요청된 데이터와 전체 페이지 수(pages)를 전역 상태에 저장해 모든 컴포넌트가 접근할 수 있게 한다.
  3. 화면 출력 (ListComp): stored된 데이터를 읽어와 화면에 뿌리고, 페이지가 변경되면 부모에게 알리는 역할을 한다.

Pagination은 새로운 시스템이 아니라, 이 데이터 흐름 회로에 ‘스위치’를 켜는 역할이다. 특정 페이지 번호를 누르면 onSubmit(page) 함수를 호출해 다시 데이터를 요청하는 트리거가 된다.

💻 실습 예시 (코드 흐름)#

// ListPage.jsx
import { useEffect } from 'react';
import { useDispatch, useSelector } from 'react-redux';
import { fetchBoardList } from './store'; // 액션 생성자 import
import ListComp from './ListComp';       // 화면 컴포넌트 import

const ListPage = ({ match }) => {
  const dispatch = useDispatch();
  const { data, pages } = useSelector(state => state.board); // Redux에서 데이터 가져오기
  const slug = match.params.slug; // URL 파라미터 추출

  // 컴포넌트 마운트 시 한 번 데이터 요청
  useEffect(() => {
    dispatch(fetchBoardList(slug)); // store에 데이터 저장
  }, [dispatch, slug]);

  return (
    <div>
      {/* ListComp는 Redux에 저장된 data와 pages를 props로 받음 */}
      <ListComp data={data} pages={pages} onPageChange={page => dispatch(fetchBoardList(slug, page))} />
    </div>
  );
};

export default ListPage;

// ListComp.jsx

          <p>{item.content}</p>

        ))}

    </div>
  );
};

3. 상세보기 진행 상태와 사진·삭제 기능 다음 단계 미리보기#

무엇을 배웠나#

Redux를 처음 접할 때 기존 로컬 상태와 새로운 데이터 흐름이 겹치면서 “이 변수는 왜 필요한지”, “이미 Redux에서 관리하는데 굳이 또 쓰는지"라는 혼란이 들었다. 특히 사진과 삭제 기능은 단순히 코드를 추가하는 것을 넘어, 기존의 데이터 흐름(Redux state)과 연결되는 지점이 여러 곳이라 어디서 데이터를 가져오고 어떻게 화면에 반영해야 할지 동시에 추적해야 했다. 기능 자체보다 이전 구조와 새 구조 사이의 정합성 추적이 더 어려웠던 순간이었다.

현재까지 진행된 흐름은 다음과 같다. 목록에서 제목을 클릭하면 /detail/{idx}로 이동해 서버에서 데이터를 요청하고, Redux state에 board.info, board.photos를 저장한다. 글쓰기 단계에서는 텍스트 입력, 사진 선택(FileReader을 통한 미리보기), FormData를 활용한 전송이 상당 부분 구현된 상태다. 상세보기에서의 사진 출력은 서버가 준 data.photos를 화면에 연결하는 작업이 남아 있으며, 삭제는 DELETE URL 구조는 갖춰져 있지만 어떤 idx를 기준으로 요청할지가 현재 수정 포인트다.

헷갈렸던 점#

처음 Redux를 접했을 때, 기존 local state 방식과 새로운 데이터 흐름이 동시에 존재하다 보니 “이 변수는 뭘 위한 거지?“라는 혼란에 빠졌던 점이 가장 기억에 남습니다.

특히 사진과 삭제 기능은 단순히 코드를 추가하는 수준을 넘어, 기존의 Redux state와 연결되는 지점이 여러 곳이다 보니 “어디서 데이터를 가져오지?”, “이 함수 호출하면 화면에 어떻게 반영되지?“를 동시에 추적해야 했습니다. 기능 자체보다 이전 구조와 새 구조 사이의 정합성 추적이 더 어렵게 느껴졌던 순간이었습니다.

정리된 이해#

Redux로 전환하면서 가장 어려웠던 점은 기존 로컬 상태와 새로운 데이터 흐름 사이의 정합성 추적이었다. 특히 사진과 삭제 기능은 기존 구조와의 연결 고리 파악이 필수적이어서, “어디서 데이터를 가져오는지"를 동시에 확인해야 했다. 현재까지 상세보기 이동 및 글쓰기 단계는 완성되었으나, 서버로부터 받은 사진 데이터를 화면에 출력하고 삭제 시 어떤 idx를 기준으로 요청할지 정하는 작업이 남아 있다.

4. 리팩토링 시 인지 부하 관리: 기존 코드 이해부터 재구조화까지#

무엇을 배웠나#

오늘은 기존 완성된 코드에 새 구조를 입히는 마이그레이션 과정을 경험하며, 단순히 문법을 외우는 것을 넘어 ‘이전 코드를 이해하고 재구성하는 일’의 어려움을 실감했습니다. 특히 store, slice 등 용어와 구조가 주는 압박감 때문에 목적보다 세부 사항을 쫓게 되는 함정에 빠졌지만, 강사님의 단계적 리팩토링 방식에서 기존 코드의 정합성을 유지하며 점진적으로 개선하는 방법의 가치를 배웠습니다. 결국 기존 코드를 읽고 이해한 뒤 구조를 변경하고 작동 여부를 검증하는 일련의 과정이, 새로운 주입을 효율적으로 소화하는 핵심 학습 전략임을 깨닫게 되었습니다.

헷갈렸던 점#

오늘은 단순히 문법을 익히는 것이 아니라, 기존 코드에 새로운 구조를 입히는 ‘리팩토링’ 과정을 경험했습니다. 가장 큰 혼란은 **“목적 없이 세부 부품의 이름과 파일 구조부터 따라가다”**가 되어, 왜 이 구조가 필요한지보다는 코드가 어디에 무엇을 위한 것인지 쫓게 되었다는 점입니다. 또한 강사님의 단계적 추가 방식과 저의 접근 방식 사이에는 **“기존 코드를 복구하고 새 코드를 입력하는 연쇄 오류”**가 발생할 위험이 있어, 중간 목적을 보기 전에 구현을 시작했다가 방향을 잃기 쉽다는 점을 깨달았습니다.

정리된 이해#

기존 코드를 읽고 이해하는 것에서 시작해, 목적에 맞게 구조를 변경하고 검증하는 과정 자체가 리팩토링임을 깨달았다. 단순히 문법을 외우는 것이 아니라, 기존 시스템의 맥락을 파악한 뒤 안전하게 새로운 설계로 이관하는 ‘마이그레이션’의 중요성을 체험했다.

🟡 초보자 시점: 오늘의 혼란과 발견#

오늘은 단순히 Redux 문법을 배우는 것을 넘어, 이미 완성된 코드에 새 구조를 입히는 과정을 경험했습니다. 저는 학습자 입장에서 다음과 같은 지점에서 큰 혼란을 느꼈습니다.

무엇이 헷갈렸나#

가장 큰 문제는 **“목적 없이 세부 부품의 이름부터 따라갔다”**는 점이었습니다. store, slice, reducer, dispatch, selector라는 연속된 영어 용어와 파일 분리 구조에 압도되어, “왜 이 구조가 필요한가"라는 근본적인 질문보다 “이 코드는 어디에 무엇을 위한 것인가"를 쫓게 되었습니다.

특히 기존의 JWT 게시판 코드를 다시 가져와 Redux로 변환하는 과정은, **‘과거 프로젝트에서 정합성을 잡기 위해 연결을 추적했던 경험’**과 비슷했습니다. 중간중간 비동기 처리 문제로 구현 방향이 수정되면서, 현재 어떤 상태가 최종적인 것인지 추적하기 어려웠습니다.

강사님의 방식과 저의 한계#

강사님은 기존 완성 코드에 기능과 구조를 단계적으로 추가하며 실제 리팩토링 과정을 보여주셨습니다. 이 방식은 실전 흐름을 직접 볼 수 있다는 장점이 있지만, 오늘처럼 중간 구조 자체가 수정되는 상황에서는 **“완성 목적을 보기 전 구현을 시작했다가, 기존 코드를 복구하고 새 코드를 입력하는 연쇄 오류”**에 빠졌습니다.

오늘 배운 핵심#

오늘의 수업은 결과적으로 다음과 같은 경험을 포함했습니다.

  1. 기존 코드 읽기 (읽고 이해하기)
  2. 마이그레이션 (구조 변경하기)
  3. 리팩토링 (설계 변경하기)
  4. 회귀 확인 (작동 여부 검증하기)
  5. 최종 구조 재정리 (정리하기)

📌 정리된 이해: 효율적인 학습 전략#

오늘의 어려움은 **“새로운 주입이 많아서”**뿐만 아니라, **“기존 구조를 다시 불러와 실시간으로 구조를 바꾸는 migration 수업”**이라는 점에서 발생했습니다.

중요한 것은 **‘어떤 순서로 코드를 입력해야 하는가’**가 아니라, **“왜 이 구조 변화가 필요한가”**에 대한 명확한 목표 설정입니다. 다음 학습부터는 전체적인 설계도(아키텍처)를 먼저 파악한 후 세부 구현으로 들어가는 전략을 사용하겠습니다.

핵심을 보여주는 코드 예시’만’ 백틱3개 코드블록으로 출력하라. 노트에 코드 근거가 없으면 아무것도 쓰지 마라.

총평#

오늘 오후 전체에서 배운 것#

Redux는 상태 변경 경로와 조회 경로를 분리하여 관리해야 하며, reducer는 단순히 데이터를 저장하는 전용 역할임을 명확히 이해했다. 기존 코드를 읽고 재구성하는 마이그레이션 과정에서 ‘이전 구조와의 정합성 추적’이 핵심이며, 세부 용어에 매몰되기보다 단계적으로 리팩토링하며 목적과 흐름을 파악하는 전략을 배웠다.

다음에 조심할 것#

  • 기존 코드 흐름을 온전히 이해한 뒤 리팩토링에 착수해야, 목적에서 벗어나 세부 사항을 쫓는 실수를 막을 수 있다.
  • Redux state와 로컬 상태의 중복 및 연결 지점을 명확히 파악하지 않으면 사진·삭제 기능 등 복합 기능 구현 시 데이터 흐름 추적이 어려워진다.

다음 복습 주제#

Redux 상태 관리와 비동기 흐름에서 ‘데이터 담당’과 ‘화면 담당’의 역할을 명확히 구분하는 것이 핵심임을 재확인했다. 특히 상세보기 기능 구현 시 기존 로컬 상태와 Redux state 간의 정합성 추적은 코드 추가보다 구조 이해가 우선이라는 점을 뼈저리게 느꼈다.

다음 복습 주제는 Redux를 활용한 비동기 데이터 흐름에서 dispatch와 useSelector의 정확한 호출 시점과 순서이며, 삭제 및 사진 기능 구현 시 어떤 idx를 기준으로 API 요청을 보내야 할지 데이터 참조 경로를 명확히 하는 것이다.
