1. Docker 이미지와 컨테이너의 핵심 개념과 명령어 정리#

무엇을 배웠나#

Docker를 처음 접할 때 ‘이미지 다운로드’와 ‘컨테이너 실행’을 혼동했던 점이 가장 큰 실수였습니다. docker pull만으로는 프로그램이 실행되지 않으며, 실제 서비스를 위해서는 별도의 run 명령어가 필수적입니다. 또한, 삭제 명령어의 구조가 생각보다 복잡해 docker rm image와 같은 직관적인 표기가 아닌 docker image rm과 같이 정확한 구문을 외워야 한다는 점을 뼈저리게 느꼈습니다.

헷갈렸던 점#

처음 Docker를 접했을 때 docker pull만으로 이미지를 다운로드한 줄 알았지만, 실제로는 별도로 컨테이너를 실행해야 한다는 점이 가장 큰 혼란이었습니다. 또한 docker rm image와 같이 직관적으로 생각하다가 docker rmi나 docker container rm과 같은 정확한 명령어 구조를 구분하지 못해 삭제에 실패했던 경험이 있습니다.

정리된 이해#

Docker는 이미지를 기반으로 실제 실행 인스턴스인 컨테이너를 별도로 생성하고 관리하는 구조입니다. docker pull 명령어는 이미지만 다운로드할 뿐 자동으로 실행되지 않으므로, 반드시 run 명령을 통해 컨테이너를 시작해야 합니다. 특히 docker ps는 현재 실행 중인 컨테이너의 상태를 확인하는 데 집중해야 하며, 종료된 컨테이너까지 포함해 전체 목록을 보고 싶을 때는 -a 옵션을 사용하는 것이 중요합니다.

# 이미지 다운로드 (Pull)
docker pull mariadb:latest

# 컨테이너 실행 (Run) - MariaDB 예시
docker run -d \
  --name my_mariadb \
  -e MARIADB_ROOT_PASSWORD=rootpass \
  -p 3306:3306 \
  mariadb:latest

# 이미지 목록 확인
docker images

# 실행 중인 컨테이너 확인 (ps)
docker ps

# 종료된 컨테이너 포함 전체 목록 조회
docker ps -a

# 컨테이너 삭제
docker rm my_mariadb

# 이미지 삭제
docker rmi mariadb:latest

2. MariaDB 볼륨과 영속 데이터·SQL 실습의 경계#

무엇을 배웠나#

Docker 컨테이너와 데이터의 생명주기를 분리하여 이해하는 것이 핵심이며, 볼륨 마운트를 통해 로컬 폴더와 컨테이너 데이터를 연결하면 삭제 후 재생성 시에도 데이터가 보존됩니다. MariaDB 실습에서는 SQL 명령어의 순서뿐만 아니라 .sh 스크립트 실행 시 주의해야 할 점과 CREATE DATABASE 등 기본적인 DB 생성 절차를 이해하는 것이 무엇보다 중요합니다.

헷갈렸던 점#

처음 Docker와 DB를 연동할 때 가장 헷갈렸던 지점은 “컨테이너를 지워도 데이터가 남는가?“라는 질문에 대한 답을 찾기 어려웠습니다. 강사님의 수업 방식은 볼륨 마운트를 통해 로컬 폴더와 컨테이너의 데이터를 연결하지만, 실제 docker container rm 명령을 실행했을 때 데이터가 어떻게 되는지 감이 잡히지 않았습니다. SQL 명령어의 순서도 중요했지만, 그보다 더 기본적인 “데이터가 실제로 어디에 저장되고 어떻게 보존되는지"에 대한 이해가 선행되지 않아 혼란이 컸습니다.

정리된 이해#

Docker 컨테이너와 데이터 스토리지를 분리하여 이해하는 것이 핵심입니다. image는 프로그램 틀, container는 실행 상태, volume/bind mount는 데이터를 저장하는 공간으로 구분해야 합니다. 볼륨 마운트만으로는 DB 데이터가 자동 보존되지 않으며, 컨테이너 재생성 후 실제 DB를 조회하여 확인해야 합니다.

# 볼륨 마운트 예시 (Windows 경로와 컨테이너 내부 연결)
docker run -d -p 3306:3306 --name mariadb \
  -v C:/mysql_data:/var/lib/mysql \
  -e MARIADB_ROOT_PASSWORD=secure_password \
  mariadb:latest

3. Docker와 Ollama, 그리고 나의 첫 수업 경험#

무엇을 배웠나#

Docker와 Ollama를 결합할 때 포트 번호 매핑과 컨테이너 이름은 필수적으로 숙지해야 할 기본 설정 사항입니다. 특히 -p 옵션은 호스트 포트와 컨테이너 내부 포트의 관계를 정의하며, 임의로 이름을 붙인 컨테이너는 명령어 입력 시 혼동을 줄 수 있습니다. 또한 GPU 가속 옵션의 유무와 상관없이 Docker 자체는 CPU 환경에서도 정상적으로 동작할 수 있음을 확인했습니다.

헷갈렸던 점#

Docker와 Ollama를 결합할 때 포트 번호 매핑 방식과 컨테이너 이름 지정법에 대한 이해 부족으로 인해 접속 오류와 명령어 실수를 경험했습니다.

특히 호스트 포트와 컨테이너 내부 포트의 관계, 그리고 임의로 지정한 컨테이너 이름을 사용할 경우 docker exec 등 명령어 입력 시 기존 예시와 혼동되어 당황했던 점이 가장 큰 혼란이었습니다.

정리된 이해#

Docker와 Ollama는 호스트 포트와 컨테이너 내부 포트를 -p 옵션으로 매핑하며, 이때 localhost:호스트포트로 접속해야 합니다. 또한 컨테이너 이름은 임의 지정 가능하지만, 명령어 실행 시 반드시 해당 이름을 정확히 입력해야 합니다. GPU 환경 여부와 상관없이 Docker의 네트워크 구조를 이해하는 것이 핵심입니다.

docker run -d -p 11435:11434 --gpus all ollama/ollama

4. Intel Arc, Docker·Vulkan 미인식과 CPU 수업의 괴리#

무엇을 배웠나#

오늘 수업은 GPU 가속 여부를 확인하는 과정이었으며, Intel Arc 환경에서 ollama ps가 보여주는 CPU 표시와 실제 실행 속도 사이의 차이를 명확히 인식하게 되었다. 특히 llamacpp라는 엔진 이름이 GPU 가속을 연상케 했지만, 실제로는 추론 전용 엔진일 뿐 하드웨어 백엔드의 활성화 여부를 판단하는 지표가 되지 않는다는 점을 깨닫고 혼란을 겪었다. 이러한 경험을 통해 ‘속도 체감’과 ‘하드웨어 프로세서 표시’는 별개의 문제이며, Docker 환경 내에서의 그래픽 카드 인식 여부가 RAG 파이프라인 구축의 핵심 열쇠임을 이해하게 되었다.

헷갈렸던 점#

강사님의 NVIDIA CUDA 기준 예시와 제 Intel Arc 환경 사이의 차이로 인해, GPU 가속 여부를 속도 체감만으로 판단하다가 실제 프로세서 표시를 보고 충격을 받았습니다. 특히 llamacpp라는 실행 엔진 이름이 GPU 가속과 연관된 것으로 오해하게 되었고, bge-m3 모델이 Docker 환경에서 정상적으로 목록에 뜨지 않아 RAG 파이프라인에서의 동작을 확신할 수 없었습니다.

정리된 이해#

Docker 환경 내 Ollama는 Intel Arc 그래픽 카드가 인식되지 않아 CPU 전적으로 추론이 이루어지며, llamacpp 실행 엔진은 GPU 가속 여부와 무관하게 모델 처리를 담당한다는 점을 확인했다.

🟡 초보자 시점, 학습자의 혼란#

오늘 수업은 “GPU 가속이 되는가 안 되는가"에 대한 확인 작업처럼 느껴졌다. 강사님은 NVIDIA CUDA 환경을 기준으로 예시를 들었지만, 저는 Intel Arc를 쓰고 있어 모든 과정이 낯설었다. 특히 ollama ps로 모델이 돌아가는 모습을 보고도, 그게 realmente GPU에서 돌고 있는지 CPU에서 돌고 있는지 구별하기가 어려웠다. “모델 응답이 꽤 빠르니 GPU를 쓰는구나"라고 직관적으로 생각했던 제게, PROCESSOR가 100% CPU라고 표시된 것은 큰 충격이었다. ‘Docker 안에서도 내 그래픽 카드가 인식되지 않는다’는 사실은, 그동안 내가 상상해온 것과 다른 현실을 마주하게 했다.

📌 무엇이 헷갈렸나#

가장 혼란스러웠던 지점은 llamacpp라는 실행 엔진의 정체성이다. 러너 이름이 llamacpp라고 되어 있으니, 이것이 Vulkan이나 CUDA와 연동된 가속 엔진인 줄 알았다. 실제로 모델이 빠르게 답변을 주니 “아, GPU가 잘 작동하는구나"라고 안심했던 기억이 있다. 하지만 ollama ps에 표시된 RUNNER llamacpp는 단순히 추론을 담당하는 엔진일 뿐, GPU 백엔드가 활성화된 증거는 아니었다. ‘속도 체감’과 ‘하드웨어 프로세서 표시’는 별개의 문제였고, 이 부분을 구분하지 못하고 있었다.

또 하나의 헷갈림은 bge-m3 모델에 대한 부분이었다. 임베딩 모델이 대화형으로 쓰이면 예상한 응답이 나오지 않을 수 있다는 강사님의 주석을 보고, 실제로 실행해보았으나 Docker 내에서는 모델 목록 확인이 되지 않았다. “다운로드와 실행 성공 여부는 불확실하다"는 판단 하에, 저는 이 부분을 보류했지만, 이것이 실제 RAG 파이프라인에서 어떻게 작용할지 감이 안 잡혔다.

총평#

오늘 오전 전체에서 배운 것#

Docker 이미지와 컨테이너의 생명주기 차이를 명확히 이해하고, docker pull과 run 명령어의 필수적 구분 및 정확한 삭제 구문을 숙지했습니다. 또한 MariaDB 볼륨을 통한 데이터 영속화와 SQL 실습의 기본 절차를 학습했으며, Docker 환경에서 포트 매핑과 컨테이너명 관리가 핵심임을 확인하고 GPU 인식 여부와 속도 체감 사이의 차이를 이해하게 되었습니다.

다음에 조심할 것#

Docker 명령어는 pull과 run을 반드시 구분하여 사용하고, 컨테이너 이름과 포트 매핑 옵션은 임의로 지정하지 않도록 꼼꼼히 확인해야 한다.

특히 MariaDB와 같은 데이터베이스 실습 시에는 볼륨 마운트를 통해 데이터를 영구 보존하는 구조를 명확히 이해하고, GPU 가속 여부와 상관없이 Docker 환경 자체는 CPU에서도 정상 동작한다는 점에 유의하여 속도 차이를 정확히 판단해야 한다.

다음 복습 주제#

Docker 이미지와 컨테이너의 생명주기 관리와 docker rm과 같은 명령어 구문의 정확한 외우기가 가장 시급합니다. 또한, Ollama와 같은 AI 모델 실행 시 GPU 가속 여부 확인을 위해 하드웨어 프로세서 표시보다는 실제 속도 체감에 집중하는 연습이 필요합니다. 마지막으로, Docker 환경에서 볼륨 마운트를 통한 데이터 영속화 전략과 포트 매핑 설정의 중요성을 재확인하여 실전 적용 능력을 키워야 합니다.
