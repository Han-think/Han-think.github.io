1. DDL 변경 및 테이블 구조 변경 가이드#

무엇을 배웠나#

DDL 명령어, 특히 ALTER TABLE의 복잡성과 SQLite의 제한 사항을 명확히 이해하게 되었다. 테이블 생성 및 삭제 시 외래키 관계를 고려한 정확한 순서가 중요하다는 점을 깨달았고, SQLite에서는 원하는 변경을 위해 테이블 재구성을 고려해야 할 수 있다는 것을 알게 되었다. 앞으로 테이블 구조 변경 시 이러한 점들을 유념하여 오류를 방지하고 효율적으로 작업하도록 노력해야겠다.

헷갈렸던 점#

테이블 구조를 변경하는 것이 단순히 컬럼을 추가하는 것 이상으로 복잡하게 생각했고, SQLite에서 ALTER TABLE 명령어의 모든 기능을 사용할 수 없다는 점이 당황스러웠습니다. 테이블 생성 및 삭제 순서를 제대로 지키지 않으면 테이블이 삭제되는 상황이 발생할 수 있다는 사실을 뒤늦게 깨달았습니다.

정리된 이해#

테이블 구조를 변경할 때는 기존 데이터나 외래키 제약 조건 등 여러 요소를 고려해야 하며, SQLite에서는 ALTER TABLE 명령어의 기능 제한으로 인해 테이블 재생성이 필요할 수 있습니다. 테이블 생성 및 삭제 순서는 외래키 관계를 고려하여 자식 테이블부터 생성하고, 삭제할 때는 자식 테이블부터 삭제해야 합니다.

ALTER TABLE customer ADD COLUMN birthday DATE NULL;

2. 데이터 무결성 확보를 위한 제약 조건과 키 이해#

무엇을 배웠나#

비즈니스 로직과 DB 제약조건의 역할을 구분하고, 데이터가 저장되기 전에 여러 단계의 검증이 이루어진다는 것을 알게 되었다. 제약조건의 종류별 역할(NOT NULL, UNIQUE, CHECK, FOREIGN KEY 등)과 개체, 참조, 도메인 무결성, 고유성 등 데이터 무결성의 종류에 대한 이해가 깊어졌다. 이를 통해 데이터베이스 설계 시 더욱 신중하게 제약조건을 적용하여 데이터의 정확성과 일관성을 확보할 수 있음을 깨달았다.

헷갈렸던 점#

처음에는 비즈니스 로직과 데이터베이스 제약조건이 각각 어떤 역할을 하는지 명확하게 구분하기 어려웠고, 어떤 단계에서 어떤 검증이 이루어져야 하는지에 대한 그림이 부족했습니다. 특히 데이터 무결성을 보장하기 위한 제약조건과 키의 관계에 대한 이해가 부족했습니다.

정리된 이해#

비즈니스 로직은 서비스 레벨에서 검증을 수행하고, DB 제약조건은 데이터베이스에 잘못된 데이터가 저장되는 것을 막는 최종적인 안전망 역할을 한다는 것을 이해하게 되었습니다. 제약 조건과 키는 데이터 무결성을 유지하는 데 핵심적인 역할을 하며, 특히 PRIMARY KEY, FOREIGN KEY, CHECK 제약 조건은 데이터의 정확성과 일관성을 보장하는 데 중요합니다.

-- NOT NULL 제약조건 예시: 'email' 필드는 필수 입력
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  email TEXT
);

-- UNIQUE 제약조건 예시: 'username' 필드는 중복 불허
CREATE TABLE users (
  id INTEGER PRIMARY KEY,
  username TEXT UNIQUE
);

-- CHECK 제약조건 예시: 'status'는 'active' 또는 'inactive'만 허용
CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  status TEXT CHECK (status IN ('active', 'inactive'))
);

-- FOREIGN KEY 제약조건 예시: 'order_id'는 'orders' 테이블의 'id'를 참조
CREATE TABLE order_items (
  id INTEGER PRIMARY KEY,
  order_id INTEGER,
  product_id INTEGER,
  FOREIGN KEY (order_id) REFERENCES orders(id)
);

3. 초보자를 위한 학교 데이터베이스 ERD 이해 및 실습#

무엇을 배웠나#

ERD는 데이터베이스 구조를 시각적으로 보여주는 지도이지만, 실제 관계는 PRAGMA foreign_key_list 명령어를 통해 확인해야 한다는 점을 배웠습니다. 테이블 생성 및 삭제 시 순서가 중요하며, ERD 에디터의 캐시 문제나 파일 불일치 가능성도 고려해야 합니다. 특히 데이터 손실을 막기 위해 테이블 삭제 순서를 정확히 파악하고 실행하는 것이 중요합니다.

헷갈렸던 점#

ERD 에디터 화면과 실제 SQL 쿼리 결과가 불일치해서 데이터베이스 구조를 파악하는 데 어려움이 있었습니다. 테이블 생성 및 삭제 순서, 캐시 문제, 그리고 SQL 실행 범위에 대한 이해 부족으로 인해 혼란스러웠습니다. PRAGMA 명령어를 통해 실제 관계를 확인하는 것이 중요하다는 점을 깨달았습니다.

정리된 이해#

ERD는 데이터베이스 구조를 시각적으로 보여주는 지도이지만, 실제 관계는 PRAGMA foreign_key_list 명령어로 확인해야 정확합니다. 테이블 생성 및 삭제 순서, 그리고 캐시 문제로 인해 ERD와 실제 DB 스키마가 다를 수 있으므로 주의해야 합니다. 문제 발생 시 PRAGMA foreign_key_list를 통해 관계를 재확인하는 것이 중요합니다.

PRAGMA foreign_keys = OFF;

PRAGMA foreign_keys = OFF;

4. 온라인 서점 ERD 설계 초보 학습 노트#

무엇을 배웠나#

온라인 서점 ERD 구성 과정에서 테이블 간 관계, 특히 N:M 관계 설정과 외래 키 설정의 우선순위를 혼동했습니다. N:M 관계는 중간 테이블을 통해 해결해야 하며, 실제 데이터 흐름을 반영하여 ERD를 설계해야 한다는 점을 배웠습니다. 또한, SQL 오류를 해결하면서 외래 키 연결 과정을 명확히 이해하게 되었습니다.

헷갈렸던 점#

처음에는 테이블 간의 관계를 어떻게 표현해야 할지 몰라서 선을 먼저 그릴지, 외래키를 먼저 정의할지 계속 고민했습니다. N:M 관계를 중간 테이블로 해결해야 한다는 개념도 왜 필요한지 바로 이해되지 않았고, ERD 에디터가 만들어주는 SQL 코드가 제대로 작동하지 않아서 답답했습니다.

정리된 이해#

온라인 서점 ERD를 구성하면서 테이블 간의 관계, 특히 N:M 관계를 이해하는 데 어려움을 겪었지만, 중간 테이블의 필요성과 외래 키 설정의 중요성을 명확히 알게 되었습니다. ERD는 단순히 테이블을 연결하는 것이 아니라 실제 데이터 흐름을 반영해야 한다는 점을 깨달았고, 이를 통해 더 정확하고 효율적인 데이터베이스 구조를 설계할 수 있을 것 같습니다. 앞으로는 ERD 설계 시 데이터의 흐름과 참조 관계를 더욱 주의 깊게 고려하여 오류를 줄이고 데이터 일관성을 확보하도록 노력하겠습니다.

CREATE TABLE ShoppingBasket_Book (
    ShoppingBasketID INTEGER,
    BookID INTEGER,
    count INTEGER,
    PRIMARY KEY (ShoppingBasketID, BookID),
    FOREIGN KEY (ShoppingBasketID) REFERENCES ShoppingBasket(ShoppingBasketID),
    FOREIGN KEY (BookID) REFERENCES Book(BookID)
);

총평#

오늘 오후 전체에서 배운 것#

DDL 변경 시 SQLite의 제한 사항과 데이터 무결성을 위한 제약 조건의 중요성을 다시 한번 깨달았고, ERD를 통해 데이터베이스 구조를 설계할 때 실제 관계와 데이터 흐름을 정확히 반영해야 한다는 점을 알게 되었습니다. 특히 N:M 관계 해결 및 테이블 삭제 순서 등 실습을 통해 데이터베이스 설계의 복잡성을 이해하고, 오류 방지를 위해 주의해야 할 점들을 확인했습니다.

다음에 조심할 것#

테이블 구조 변경 시 SQLite의 제한 사항과 외래 키 관계를 고려하여, 필요하다면 테이블 재구성을 신중하게 검토해야겠다고 생각합니다. 또한 ERD 설계 시 테이블 간 관계를 실제 데이터 흐름에 맞춰 정확하게 반영하고, 외래 키 설정 순서를 혼동하지 않도록 주의해야겠습니다.

다음 복습 주제#

DDL 변경 및 테이블 구조 변경 시 SQLite의 제약사항을 다시 한번 살펴보고, 실제 테이블 변경 작업에서 적용해 보면서 숙달해야겠다. 특히 N:M 관계를 포함한 복잡한 ERD 설계를 진행할 때 데이터 흐름을 정확히 파악하고, 외래 키 설정 순서를 꼼꼼히 확인하는 연습이 필요하다.
