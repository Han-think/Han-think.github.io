1. FastAPI 백그라운드 실행 시 주의사항#

무엇을 배웠나#

nohup, --workers, 로그 리다이렉션 등 각 옵션의 역할과 순서를 명확히 이해할 수 있었다. 특히 nohup 뒤에 오는 [1]이 PID가 아니라 작업 번호임을 구분하지 못해 발생할 수 있는 위험성을 깨닫고, 실제 서비스 시작 여부를 확인하는 과정을 소홀히 하면 안 된다는 점을 중요하게 느꼈다.

헷갈렸던 점#

nohup 뒤에 오는 [1]은 프로세스 ID가 아니라 작업 번호라는 점, 그리고 이 숫자를 기준으로 다른 프로세스를 제어하려다 실수로 중단시킬 위험이 있다는 점이 가장 큰 혼란이었다.

터미널에 [1] PID가 뜨는 순간을 ‘서버 실행 완료’로 오해하기 쉽지만, 실제로는 로그 파일 확인이 필요한 다음 단계가 남아있으며, 이 시점에서 안일하게 넘어가면 실행 실패를 나중에야 발견할 수 있다.

--workers 옵션 앞에 반드시 -- 기호를 붙여야 하며, 이를 생생히 실수했던 경험을 통해 옵션 서식의 중요성을 뼈저리게 느꼈다.

정리된 이해#

nohup, --workers, 로그 리다이렉션, 그리고 &는 각각 서버 안정성, 처리량, 오류 확인, 백그라운드 실행이라는 명확한 목적을 가진 옵션이며, [1] PID가 뜨는 것은 프로세스 생성일 뿐 실제 서비스 시작 여부를 보장하지 않는다. 따라서 명령어 실행 직후 로그를 반드시 확인하여 성공 여부를 검증하는 과정이 필수적이다.

nohup uvicorn app:app --workers 2 > uvicorn.log 2>&1 &

2. ollama 모델 저장소 디스크 관리하기#

무엇을 배웠나#

ollama 모델을 설치하면서 단순히 용량 부족이 아니라 인ode 제한까지 확인해야 한다는 점을 깨달았다. manifest와 blob, partial 파일이 분리되어 관리된다는 사실을 이해하고 시스템 관리의 핵심을 배웠다. 특히 digest 값으로 다운로드 완료 여부를 검증하는 과정이 중요하다고 느꼈다. 이러한 파일 시스템 지식은 LLM 운영에 필수적인 기초가 되었다.

헷갈렸던 점#

ollama list 명령어로 모델이 보이지 않아서 데이터도 사라진 줄 알았는데, 실제로는 수 기가바이트 규모의 blob 파일이 시스템에 남아 있어 당황했다. 또한 no space left on device 에러가 뜰 때 단순히 디스크 용량 부족으로만 생각하다가, df -i 명령어를 통해 인ode(파일 개수 제한)까지 확인해야 한다는 사실을 깨닫고 복합적인 관리 방법을 배워야 했다.

정리된 이해#

Linux 기반 LLM 운영에서 모델 관리는 파일 시스템 관리와 불가분의 관계에 있다. ollama list 명령어로 모델이 보이지 않더라도, 실제 데이터인 blob 파일이 남아 있는 것은 매니페스트가 삭제되지 않았거나 임시 파트가 정리되지 않아서다. 특히 디스크 용량과 인ode는 별개의 자원이므로 한쪽이 꽉 차도 다른 쪽에 여유가 있을 수 있어, df -i 명령어를 통해 파일 개수 제한까지 꼼꼼히 확인하는 것이 중요하다.

# ollama 모델 목록 확인 (매니페스트 확인)
ollama list

# 남아있는 blob 파일 강제 삭제 (디스크 공간 확보)
docker system prune -a --volumes

# 인ode(파일 수) 확인 후 정리
df -i

3. Ollama 네트워크 설정과 LangChain 연결: 0.0.0.0의 의미와 보안 이해#

무엇을 배웠나#

OLLAMA_HOST 설정은 네트워크 바인딩 범위를 결정하며, 실제 보안은 별도의 Security Group이 담당한다는 사실을 명확히 이해했습니다. localhost와 0.0.0.0의 차이를 구분하고, 같은 인스턴스 내에서는 localhost만으로도 충분하다는 점을 깨닫게 되었습니다. 모델 서버와 앱 코드가 독립된 레이어에 존재하므로 서비스를 교체하거나 재구성할 때 유연하게 대처할 수 있다는 점도 중요한 깨달음이었습니다.

헷갈렸던 점#

0.0.0.0 설정이 서버 전체를 외부에 노출하는 것처럼 보여 불안했지만, 실제로는 네트워크 인터페이스의 범위만을 결정할 뿐 보안은 별도의 방화벽인 Security Group이 담당한다는 점을 이해했습니다. 또한 localhost와 0.0.0.0, 그리고 Security Group이 각각 독립된 역할을 수행하며 앱의 접근을 제어한다는 사실에 큰 깨달음을 얻었습니다.

정리된 이해#

네트워크 바인딩(0.0.0.0 vs localhost)과 보안(Security Group)의 역할을 명확히 구분하는 것이 핵심입니다. OLLAMA_HOST 설정은 통신 범위를 결정하며, 실제 외부 접근을 제어하는 것은 별도의 방화벽 시스템입니다. 이를 통해 앱 코드 삭제 시 모델 서버가 독립적으로 유지될 수 있음을 이해했습니다.

# Ollama 네트워크 설정 예시 (초보자 워킹 노트 기준)

import os

# 127.0.0.1: 로컬 호스트만 허용 (보안성 높음, 외부 접속 차단)
# OLLAMA_HOST=127.0.0.1

# 0.0.0.0: 모든 네트워크 인터페이스에서 요청 수신 (외부 접근 가능)
# OLLAMA_HOST=0.0.0.0

4. MariaDB 서버 관리와 데이터 조작의 경계, 그리고 ‘%‘의 의미#

무엇을 배웠나#

오늘은 데이터 조작 명령어와 서버 관리 명령어가 섞여 있어 어떤 영역을 다루고 있는지 구분하는 데 혼란이 있었다. 특히 'web_user'@'%'에서 %가 모든 호스트를 의미한다는 점을 이해했지만, 실무에서는 보안 위험을 고려해 구체적인 IP 제한이 필요하다고 생각했다. 이를 통해 데이터 조작과 사용자 권한 관리는 완전히 다른 영역이며, 안전한 설정을 위해 세부적인 제어가 중요하다는 점을 새겼다.

헷갈렸던 점#

SELECT/INSERT/UPDATE/DELETE는 테이블 내 데이터를 조작하는 것이고, CREATE USER/GRANT는 DB 서버 자체를 관리하는 명령어라는 점이었다.

특히 'web_user'@'%'에서 %가 모든 호스트에서의 접속을 의미한다는 사실은 이해했지만, 실무에서는 보안 위험이 있으므로 구체적인 IP 제한으로 수정해야 한다는 점을 새롭게 인식했다.

정리된 이해#

오늘은 데이터 조작 명령어와 서버 관리 명령어가 섞여 있어 DB 다루는 영역과 시스템 관리하는 영역을 구분하는 것이 무엇보다 중요하다는 것을 깨달았다. 특히 CREATE USER와 GRANT는 DB 자체를 제어하는 권한 부여 과정이며, 'web_user'@'%'의 %는 모든 호스트에서 접속을 허용한다는 의미이지만 보안상 위험할 수 있어 구체적인 IP 제한이 필요하다고 생각했다.

-- 1. 데이터 조작 (DML)
SELECT * FROM users;
INSERT INTO users (name, email) VALUES ('홍길동', 'hong@example.com');
UPDATE users SET status = 'active' WHERE id = 1;
DELETE FROM users WHERE id = 2;

-- 2. 사용자 및 권한 관리 (DDL/권한 부여)
CREATE USER 'web_user'@'%' IDENTIFIED BY 'password';
GRANT ALL PRIVILEGES ON database_name.* TO 'web_user'@'%';
FLUSH PRIVILEGES;

5. EC2 라이프사이클과 DBeaver 원격 접속 이해하기#

무엇을 배웠나#

EC2 인스턴스에 Uvicorn, Ollama, MariaDB 등 다양한 서비스가 동시에 실행될 때, 각 프로그램이 서버·런타임·DB 프로그램이라는 역할 분담을 명확히 이해하는 것이 중요합니다. 또한 EC2의 Stop과 Terminate는 단순히 전원을 끄거나 지우는 것을 넘어, EBS 저장소와 Public IPv4 주소에 미치는 영향을 정확히 인지해야 합니다. Stop 시에는 EBS와 설정 환경이 보존되지만 IP가 재부팅될 때마다 변경될 수 있어 접속 주소를 다시 확인해야 하는 번거로움이 있습니다.

헷갈렸던 점#

EC2 인스턴스에 FastAPI, Ollama, MariaDB 등 다양한 서비스가 동시에 설치될 때, 각 프로그램이 ‘서버’ 개념으로 겹쳐 보여 어떤 역할을 하는지 감이 잡히지 않았다.

또 Stop과 Terminate의 차이를 단순히 ‘끄기/지우기’로만 생각하다가, EBS 저장소와 Public IPv4 주소가 어떻게 보존되거나 소멸되는지 이해하지 못해 접속 주소를 다시 설정해야 하는 번거로움을 예측할 수 없었다.

정리된 이해#

EC2 인스턴스 중지 시 EBS 스토리지와 설정 환경은 보존되지만 공용 IP가 재할당되어 접속 주소가 변경될 수 있음을 이해해야 한다. FastAPI의 Uvicorn, LLM 실행용 Ollama, 데이터베이스 서버인 MariaDB는 각각 독립적인 역할을 수행하며, DBeaver 같은 GUI 툴을 사용해 원격 DB에 접속하는 것이 일반적이다.

# EC2 lifecycle 핵심 정리 (노트 기반)

1. Stop vs Terminate#

구분 Stop (일시 중지) Terminate (종료/삭제)
인스턴스 상태 일시 정지 (중지된 상태로 유지) 영구 삭제 (실제 서버 종료)
EBS(디스크) 유지 (데이터 보존) 삭제 (데이터 소멸 가능성)
Public IPv4 주소 해제/재할당 가능 (중지 후 재시작 시 IP가 바뀔 수 있음) 영구 소실
비용 스토리지 비용만 발생 비용 정지

2. 서비스 역할 분담#

  • Uvicorn: FastAPI 애플리케이션을 구동하는 서버 프로그램
  • Ollama: LLM(대형 언어 모델)을 실행하고 관리하는 런타임 환경
  • MariaDB: 데이터를 저장하고 관리하는 DB 서버 프로그램
  • DBeaver: 사용자가 원격 DB에 접속하기 위한 GUI 클라이언트 툴

3. EC2 접속 시 고려사항#

Stop 후 IP가 변경될 수 있으므로, DBeaver 등 GUI 툴로 DB에 접속할 때는 Host 주소를 다시 확인해야 함.

총평#

오늘 오후 전체에서 배운 것#

오늘은 시스템 구성 요소별 역할 분담과 설정 파라미터의 의미를 정확히 이해하는 것이 중요함을 느꼈다. 특히 네트워크 바인딩, 디스크 인ode 관리, 그리고 서비스 종료 시 데이터 보존 여부 등 세부적인 옵션들이 실제 운영 환경에 미치는 영향을 구분하는 데 집중했다. 이러한 기초 지식은 서비스의 안정성과 보안을 확보하기 위한 필수적인 판단 기준이 되었다.

다음에 조심할 것#

오늘 학습한 내용을 바탕으로 다음에 주의할 점은 다음과 같다.

  1. FastAPI 배포 시 nohup 뒤에 붙는 [1]이 PID가 아닌 작업 번호임을 반드시 확인하여, 실수로 프로세스를 종료하거나 충돌이 발생하지 않도록 해야 한다.
  2. Ollama 모델 관리는 디스크 용량뿐만 아니라 inode 제한을 사전에 체크하고, digest 값을 통해 데이터 무결성을 검증하는 등 파일 시스템 관리에 신경 써야 한다.
  3. 네트워크 설정 시 0.0.0.0과 localhost의 차이를 명확히 구분하고, 실제 서비스 보안은 Security Group 설정을 통해 관리해야 하며, 접속 주소 변경 가능성에 대비해 주기적으로 확인하는 습관을 들여야 한다.

다음 복습 주제#

  1. 서비스 배포 시 네트워크 보안과 접속 주소 관리: 0.0.0.0 바인딩 시 발생할 수 있는 외부 노출 위험을 인지하고, 실제 서비스 접근에 필요한 Security Group 설정과 EC2 재부팅 시 변동될 수 있는 Public IPv4 주소를 주기적으로 확인하는 습관을 들인다.

  2. 데이터베이스 권한 설계와 시스템 관리 경계: '%' 와일드카드의 편의성과 보안 위험 사이의 균형을 이해하고, 실제 운영 환경에서는 구체적인 IP 제한을 적용한 사용자 계정을 생성하는 등 세밀한 권한 관리의 중요성을 재확인한다.

  3. 컨테이너 및 가상화 환경에서의 파일 시스템과 스토리지 관리: Ollama 모델 파일의 구조(manifest, blob 등)와 Inode 제한 문제를 통해, 서비스 운영 시 디스크 용량뿐만 아니라 인ode 사용량을 모니터링하고, EBS 스냅샷이나 스토리지 정책이 서비스의 재구성 및 복구에 미치는 영향을 파악한다.
