1. [워킹노트] 앙상블과 멀티태스크 Loss의 구분#

무엇을 배웠나#

멀티태스크 학습에서 Loss는 각 태스크의 오차를 가중합한 최종 신호이며, Checkpoint는 훈련된 모델 상태를 저장하는 스냅샷이라는 점을 명확히 구분했습니다. 앙상블이 여러 모델의 결과를 모아 최종 답을 도출하는 방식인 반면, 멀티태스크는 하나의 모델 내에서 여러 태스크의 Loss를 합쳐 가중치를 업데이트한다는 점에서 본질적인 차이가 있습니다.

헷갈렸던 점#

멀티태스크 합산 Loss가 단순히 여러 손실을 더한 것인지, 체크포인트와 연관된 것인지 처음에 구분하기 어려웠습니다. 또한 앙상블과 멀티태스크가 모두 ‘여러 모델이나 결과물을 다룬다’는 점에서 비슷하게 느껴져 개념 혼동이 있었습니다.

정리된 이해#

Loss는 모델 가중치를 업데이트하는 오차 신호이며, checkpoint는 훈련된 모델 상태를 저장한 파일입니다. 앙상블은 여러 모델의 결과를 결합해 정확도를 높이는 기법이고, 멀티태스크는 하나의 모델에 여러 Loss를 합쳐 동시에 다양한 태스크를 학습시키는 방식입니다.

# 앙상블: 여러 모델의 예측을 결합 (Loss는 각 모델별로 독립적)
import numpy as np

# 모델 1, 2, 3의 개별 예측 확률 (예: 분류 작업)
pred_1 = np.array([0.7, 0.3])  # 클래스 A에 대한 confidence
pred_2 = np.array([0.4, 0.6])
pred_3 = np.array([0.8, 0.2])

# Soft Voting: 평균값을 통해 최종 예측 결정
ensemble_pred = (pred_1 + pred_2 + pred_3) / 3
print("앙상블 최종 예측:", ensemble_pred)
# 출력: [0.63333334 0.36666666] -> 클래스 A 선택

# 멀티태스크: 하나의 모델이 여러 Loss를 합쳐서 업데이트
# 각 태스크의 Loss와 가중치 (위 노트에서 언급한 공식과 유사)
loss_cls = 0.5  # 분류 손실
loss_reg = 0.3  # 회귀 손실
loss_tok = 0.2  # 토큰화/정규화 손실

alpha, beta, gamma = 1.0, 1.0, 1.0  # 가중치

# 최종 합산 Loss (Backward Pass를 위한 오차 신호)
total_loss = alpha * loss_cls + beta * loss_reg + gamma * loss_tok
print("멀티태스크 최종 Loss:", total_loss)
# 출력: 1.0

2. CPU와 XPU의 역할 분리: 전처리와 모델 연산#

무엇을 배웠나#

num_proc=4는 CPU 기반의 병렬 프로세스 수를 의미하며, XPU 모델 연산과는 별개로 데이터 전처리 단계에서 역할을 분담한다. 단순히 숫자를 늘려도 성능이 비례해서 향상되지 않으며, 프로세스 생성 오버헤드와 I/O 병목 등 실제 환경 요소를 신중히 고려해야 한다.

헷갈렸던 점#

처음에는 num_proc 숫자를 단순히 “작업자 수"로만 생각하여, 숫자를 늘리면 무조건 속도가 빨라질 것이라 기대했습니다. 또한 XPU라는 용어가 등장하면서 전처리 단계까지 하드웨어가 자동으로 담당하는 것으로 오해했던 것이 가장 큰 혼란이었습니다. 특히 num_proc 설정과 XPU 모델 연산이 별개의 영역이라는 점을 구분하지 못해 Dataset 처리 범위를 잘못 이해하고 있었습니다.

정리된 이해#

num_proc는 CPU 기반의 병렬 프로세스 생성이며, XPU 모델 연산과는 별개로 Dataset 전처리 단계에서 데이터 변환과 토크나이저 실행을 담당한다. 단순히 숫자를 키운다고 성능이 비례해서 좋아지지는 않으며, 프로세스 생성 오버헤드와 I/O 병목 등을 고려해 실제 환경에 맞게 신중하게 설정해야 한다.

from datasets import load_dataset

ds = load_dataset("imdb")

# num_proc=4로 CPU 병렬 처리 활성화 (전처리 전용)
ds = ds.map(lambda x: {"length": len(x["text"])}, num_proc=4)

print(ds)

3. IMDB 데이터 전처리 길이에 대한 오해와 수정#

무엇을 배웠나#

토큰화 과정에서 max_length=128이 기본 적용되어 있어, 긴 리뷰는 모두 128토큰으로 잘린 상태에서 길이가 측정된다는 점을 명확히 이해하게 되었다. 또한 remove_columns=["text"]를 사용하면 토큰화된 결과에는 원본 텍스트가 필요 없으므로 메모리 절약을 위해 컬럼을 삭제할 수 있다는 사실을 확인했다. 마지막으로 필터링 후 Top 10개의 길이가 모두 128로 일치하는 것은 데이터의 길이 때문이 아니라 모델 입력 제한에 의해 잘린 결과임을 깨닫고 코드의 동작 원리를 정확히 파악할 수 있었다.

헷갈렸던 점#

remove_columns를 적용했을 때 텍스트가 사라져 데이터가 비어있는 것처럼 보여 혼란스러웠습니다.

토큰화 과정에서 max_length=128이 기본값으로 적용되어 있어, 실제 리뷰의 길이가 200~500토큰 이상이라도 모두 128로 잘린 상태에서 길이를 재고 있었습니다.

길이(Len)가 모두 128로 일치하는 이유를 처음에는 코드 오류로 의심했으나, 이는 토크나이저의 최대 길이 제한에 의해 강제로 통일된 결과였습니다.

정리된 이해#

토큰화 과정에서 max_length=128이 기본 적용되어 있어, 실제 리뷰 길이가 길어도 모두 128로 잘린 ‘입력 길이’가 측정되므로 이를 ‘원문의 전체 길이’라고 오해하기 쉽다. 또한 remove_columns=["text"]는 토큰화된 데이터에 원본 텍스트가 더 이상 필요 없어 삭제하는 것이지, 데이터 자체가 사라지는 것은 아니며 필터링 후 길이가 일정하게 나오는 것은 truncation 설정 때문임을 명확히 이해해야 한다.

# 토큰화 전처리 흐름 (map + remove_columns)
dataset = dataset.map(token_func, batched=True)
dataset = dataset.remove_columns(["text"])

# 긍정 리뷰만 필터링
dataset = dataset.filter(lambda example: example["label"] == 1)

# 길이 측정 (truncated length)
dataset = dataset.map(lambda item: {"length": len(item["input_ids"])})

4. 오늘의 혼란 포인트: 권한 인증#

무엇을 배웠나#

오늘 push_to_hub 실습을 통해 가장 크게 당황했던 부분은 ‘권한 인증’이었습니다. 영상이나 교재에서는 REPO_ID만 지정하면 되는 것처럼 보여서 간단하다고 생각했는데, 실제 실행해 보니 Permission denied 에러가 발생하여 hf auth login --force 명령어를 직접 터미널에 쳐야 로그인이 된다는 사실을 알게 되었습니다.

배운 흐름은 크게 4단계로 요약할 수 있습니다. 첫째, 원본 데이터를 확보하고 둘째, 컬럼명 변경이나 라벨 변환 등 Schema를 가공하여 모델 학습에 적합한 형태로 만드는 과정입니다. 셋째, push_to_hub() 메서드를 사용해 클라우드에 등록할 때 REPO_ID와 Write 권한을 가진 토큰이 반드시 필요합니다. 마지막으로, 정리된 데이터는 load_dataset() 함수를 통해 다른 사람이나 프로젝트에서 쉽게 재사용할 수 있다는 점이 가장 중요했습니다.

헷갈렸던 점#

push_to_hub() 실행 시 Permission denied 에러가 발생하여, Python 코드 내부에서 자동으로 토큰을 인식하지 못하고 터미널 명령어(hf auth login)를 별도로 입력해야 한다는 사실에 당황했다.

특히 Write Token이라는 개념과 권한 관리가 필요하다는 점을 처음 알았으며, 데이터 업로드가 목적이 아니라 schema와 split 정보를 명확히 하여 재현성 있는 데이터 자산으로 만드는 과정이 중요하다고 느꼈다.

정리된 이해#

오늘 push_to_hub 실습 중 가장 큰 혼란은 ‘권한 인증’이었습니다. 영상이나 교재에서는 REPO_ID만 지정하면 되는 것처럼 보여서 간단해 보였지만, 실제 실행하니 Permission denied 에러가 발생했습니다. 결국 터미널에 hf auth login --force를 입력하고 Write Token을 발급받아 로그인해야 했습니다.

배운 흐름은 크게 4단계로 요약할 수 있습니다. 원본 데이터를 확보한 뒤, 컬럼명 변경이나 라벨 추가 등 Schema 가공을 통해 모델 학습에 적합한 형태로 만든 후, push_to_hub()를 사용해 클라우드에 등록합니다. 이때 반드시 Write 권한을 가진 토큰이 필요하며, 업로드가 완료되면 load_dataset() 함수를 통해 다른 사람이나 프로젝트에서 데이터를 쉽게 재사용할 수 있습니다. 가장 중요한 점은 데이터를 올리는 것 자체가 목적이 아니라, schema와 split 정보를 명확히 하여 재현성 있는 데이터 자산으로 만드는 과정이라는 것입니다.

from datasets import load_dataset

# 1. 데이터 로드 (예: Rotten Tomatoes)
dataset = load_dataset(
    "cornell-movie-review-data/rotten_tomatoes",
    split="train[:200]"
)

# 2. Schema 가공: 컬럼명 변경 및 라벨 텍스트 추가
dataset = dataset.rename_column("label", "sentiment")
dataset = dataset.map(lambda x: {"label_text": ["positive" if l == 1 else "negative" for l in x["sentiment"]]})

# 3. Hub 업로드 (Write Token 필요)
# REPO_ID에 Write 권한이 있는 토큰으로 로그인된 상태여야 함
dataset.push_to_hub("my-username/custom-movie-reviews")

5. SQuAD 평가 메트릭: Exact Match와 F1의 차이#

무엇을 배웠나#

SQuAD 평가 메트릭에서 answer와 answers 키명의 차이로 인해 코드 작성 중 혼란을 겪었지만, references 리스트 안에 answers가 존재한다는 사실을 파악해 해결할 수 있었다. Exact Match는 예측 답안과 정답이 문자열 전체로 완벽히 일일 때만 점수를 주지만, F1 Score는 토큰 단위의 겹침 정도를 측정해 부분 일치도 인정해준다는 점을 명확히 이해했다. 특히 EM이 “전부 아니면 Nothing"인 반면 F1은 일부라도 맞으면 점수가 부여된다는 점이 두 지표의 핵심적인 차이점이었다.

헷갈렸던 점#

처음에는 ‘정답’과 ‘정답들’이 헷갈려 schema 구조를 파악하는 데 시간이 걸렸습니다. Exact Match와 F1 점수의 차이를 처음 들었을 때는, 둘 다 정답과의 일치도를 재는 지표인데 왜 두 가지가 필요한지 감이 잡히지 않았습니다. 특히 F1 점수가 토큰 단위로 겹치는 정도를 측정한다는 점이, EM의 ‘전부 아니면 nothing’ 방식과는 어떻게 다른지 이해하는 데 시간이 걸렸습니다.

정리된 이해#

Exact Match는 정답과 예측값이 문자열 전체가 완벽히 일치해야 점수가 주어지지만, F1 Score는 토큰 단위의 겹침 정도를 측정해 부분적인 일치도 인정한다는 점이 핵심입니다. Exact Match는 ‘전부 아니면 Nothing’인 반면, F1은 얼마나 많은 정답 요소를 예측했는지 수치화하여 엄격함과 유연함의 차이를 보입니다.

# SQuAD 평가 메트릭 (Exact Match, F1) 비교

# 정답과 예측값 예시
ground_truth = "Tokyo Japan"
prediction = "Tokyo"

# 1. Exact Match (EM)
# 문자열 전체가 완벽하게 일치해야 1점, 아니면 0점
em_score = int(ground_truth == prediction)  # 결과: 0

# 2. F1 Score
# 토큰(token) 간의 겹침 정도를 측정
from collections import Counter

def compute_f1(ground_truth, prediction):
    ground_truth_tokens = ground_truth.split()
    prediction_tokens = prediction.split()

    common_tokens = Counter(ground_truth_tokens) & Counter(prediction_tokens)
    num_same = sum(common_tokens.values())

    if len(ground_truth_tokens) == 0 or len(prediction_tokens) == 0:
        return 0.0

    precision = num_same / len(prediction_tokens)
    recall = num_same / len(ground_truth_tokens)

    if precision + recall == 0:
        return 0.0

    f1_score = 2 * (precision * recall) / (precision + recall)
    return f1_score

f1_result = compute_f1(ground_truth, prediction)  # 결과: 0.5 (토큰 하나 일치 인정)

print(f"Exact Match Score: {em_score}")
print(f"F1 Score: {f1_result:.4f}")

6. PM_06 메트릭 오케스트레이션 프로젝트 연결#

무엇을 배웠나#

오늘 수업을 통해 기존에 만들어둔 코드들이 ‘Ensemble’, ‘Routing’, ‘Orchestration’과 같은 전문적인 구조를 갖추고 있었음을 깨닫고, 개념 용어를 붙이는 과정의 중요성을 체감했습니다. 특히 Datasets가 단순한 데이터 모음 도구가 아니라 모델 실패 원인 분석과 경로 설정을 개선하는 핵심 기반이라는 점을 이해하게 되었고, 결과값만 저장하는 것이 아니라 raw metrics를 보존해야 나중에 모델 비교와 개선이 가능하다는 사실을 새롭게 배웠습니다.

헷갈렸던 점#

오늘 수업을 들으며 드는 가장 큰 생각은 **“나는 개념 용어보다 구조를 먼저 만들어왔고, 이제 그 구조에 정식 용어를 붙이는 과정”**이라는 점이었습니다. 기존에 해오던 일들이 ML(머신러닝) 전문 용어와 맞아떨어지는 것을 확인하면서, 동시에 내가 모르고 있던 ‘전문적인 구조’가 내 코드 안에 숨어 있었다는 사실이 새삼 부끄러웠습니다.

특히 Datasets가 단순히 데이터를 모으는 도구가 아니라, 모델의 실패 원인을 분석하고 routing(경로 설정)을 개선하는 핵심 기반이 된다는 점을 깨닫고 나서야 비로소 이전 프로젝트들이 왜 그렇게 동작했는지 이해하게 되었습니다. “별점만 저장하면 끝"이라는 단순한 생각에서 벗어나, raw metrics를 보존해야 나중에 모델 비교와 개선이 가능하다는 점이 가장 크게 와닿았습니다.

  1. 용어의 부재 vs 구조의 존재: 정식 용어를 잘 모른 채 만들어둔 내 프로그램들이 실제로 ‘Ensemble’, ‘Routing’, ‘Orchestration’과 같은 전문적인 구조를 가지고 있는지 의문이 들었다. 기능은 작동하는데, 그 안에 깔린 이론적 토대가 빈약하다고 느껴졌습니다.
  2. Datasets의 역할 불명확함: Datasets가 실제 수익이나 시스템 발전에 어떻게 직접적으로 연결되는지 처음에는 명확하지 않았습니다. 단순히 데이터를 모으는 도구인지, 아니면 분석을 위한 자산인지가 애매했습니다.
  3. 측정의 중요성 간과: “별점만 저장하면 원인을 재분석하기 어렵다"는 말은 저에게 큰 충격이었습니다. 지금까지는 결과값(별점)만 남겼지, 그 결과를 만든 과정(raw metrics)의 세부 내역은 놓치고 있었습니다.

정리된 이해#

나는 개념 용어보다 구조를 먼저 만들어왔고, 이제 그 구조에 정식 용어를 붙이는 과정이었다. 기존에 해오던 일들이 ML 전문 용어와 맞아떨어지는 것을 확인하면서, 내가 모르고 있던 ‘전문적인 구조’가 내 코드 안에 숨어 있었다는 사실을 새롭게 인식했다. 특히 Datasets가 단순히 데이터를 모으는 도구가 아니라, 모델의 실패 원인을 분석하고 routing을 개선하는 핵심 기반이 된다는 점을 깨닫고 비로소 이전 프로젝트들이 왜 그렇게 동작했는지 이해하게 되었다.

# Ensemble 패턴: 여러 모델의 예측을 결합하여 성능 향상
def ensemble_predictions(model_outputs):
    """
    여러 모델의 출력을 받아 가중 평균으로 최종 예측값을 반환합니다.
    이는 'Routing' 및 'Orchestration'의 기본 구조입니다.
    """
    # 각 모델의 confidence(신뢰도) 기반 가중치 계산
    weights = [model['confidence'] for model in model_outputs]
    total_weight = sum(weights)

    if total_weight == 0:
        return None

    # 가중 평균 계산 (Routing 논리)
    weighted_sum = sum(out['prediction'] * w for out, w in zip(model_outputs, weights))
    final_prediction = weighted_sum / total_weight

    return final_prediction

# Datasets 구조: raw metrics 보존을 위한 데이터 클래스
class MetricsDataset:
    """
    모델의 실패 원인 분석을 위해 raw metrics를 보존하는 Dataset 구조.
    단순히 별점(score)만 저장하지 않고, 예측 과정의 상세 내역을 유지합니다.
    """
    def __init__(self):
        self.records = []  # raw metrics 리스트

    def add_record(self, prediction, actual, confidence):
        """
        원본 메트릭(raw metric)을 보존하여 나중에 모델 비교가 가능하게 함.
        """
        self.records.append({
            'prediction': prediction,
            'actual': actual,
            'confidence': confidence
        })

    def get_failure_analysis(self):
        """
        raw metrics를 기반으로 실패 패턴을 분석합니다.
        """
        failures = [r for r in self.records if r['prediction'] != r['actual']]
        return len(failures), len(self.records)
