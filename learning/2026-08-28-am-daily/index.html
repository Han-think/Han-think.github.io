1. HTTP 요청이 MongoDB에 저장되는 전층 연결 구조#

무엇을 배웠나#

오늘은 MongoDB와 Express가 데이터를 주고받는 연결 흐름을 이해하는 데 집중했습니다. 데이터가 즉시 보이지 않는 현상은 DB 연결 자체가 아닌, Schema나 Model 설정 단계가 완료되지 않아서 발생한다는 점을 명확히 했습니다. 특히 HTTP 요청이 Router를 거쳐 Mongoose 모델을 호출한 뒤 create() 메서드로 실제 document가 저장되는 전층 구조를 파악하는 것이 중요했습니다.

헷갈렸던 점#

가장 큰 혼란은 **‘데이터가 즉시 보이지 않는다’**는 점이었습니다. MongoDB Compass를 켜고 데이터를 확인했는데 화면에 아무것도 없으면, “아, DB 연결이 안 된 거구나"라고 직관적으로 생각하기 쉽습니다. 하지만 실제로는 DB 연결 자체가 정상인데도, Schema 정의나 Model 생성 단계가 아직 완료되지 않아 document가 저장되지 않은 경우였죠.

또 하나의 혼란 요소는 파일 간의 역할 분담이었습니다. db.js, app.js, model.js, router.js 등 여러 파일이 짧은 시간 안에 등장하고 변하면서, “지금 우리는 어떤 단계에 있는지”, “다음 단계는 무엇인지"를 놓치기 쉽웠습니다. 특히 강사님의 빠른 진행 속도 속에서 현재 어느 층(level)에 있는지 파악하는 것이 어려웠습니다.

오늘의 핵심은 **‘HTTP 요청이 어떻게 MongoDB에 데이터로 저장되는지’**의 전층 연결 구조였습니다. 단순히 DB를 연결하는 것을 넘어, Express라는 웹 서버 프레임워크와 Mongoose라는 ODM(Object Data Modeling) 라이브러리가 어떻게 협업하는지를 이해하는 것이 중요했습니다.

정리된 흐름은 이렇습니다.

  1. HTTP 요청 도착 (Client → Browser/Postman 등)
  2. Express 처리 (app.js에서 라우팅 설정)
  3. Router 분기 (member_router.js에서 API 경로 담당)
  4. Mongoose 모델 호출 (Schema에 따라 데이터 구조 정의)
  5. MongoDB 저장 (Model.create() 메서드 실행 후 실제 document 생성)

특히 “Schema를 정의했다고 곧바로 document가 저장되는 것은 아니다"라는 점이 중요했습니다. Schema는 ‘규칙(Blueprint)‘이고, 실제로 데이터를 넣는 행위는 Model.create()를 호출했을 때 일어나는 일입니다.

정리된 이해#

HTTP 요청을 통해 Express와 Mongoose가 협업하여 MongoDB에 데이터를 저장하는 과정은, Schema 정의 후 Model.create()를 호출해야 비로소 document가 생성된다는 점에서 단순한 연결이 아닌 구조적 이해가 필요합니다. 특히 라우터와 모델 단계를 거치며 데이터가 어떻게 흐르는지 파악하는 것이 중요하며, DB 접속 성공 여부와 관계없이 Schema 및 Model 설정 완료 여부가 데이터 저장의 핵심 열쇠가 됩니다.

// db.js - MongoDB 연결 설정
const mongoose = require('mongoose');

mongoose.connect('mongodb://localhost:27017/yeardream')
  .then(() => console.log('MongoDB connected...'))
  .catch(err => console.log(err));

// 연결 이벤트 리스너
const db = mongoose.connection;
db.once('open', () => console.log('DB connected'));
db.on('error', (err) => console.log('DB error:', err));

2. Mongoose Schema와 Model 옵션 이해하기#

무엇을 배웠나#

Mongoose Schema는 MongoDB 위에 놓인 애플리케이션 규칙이며, 데이터베이스의 유연함과 스키마 정의의 목적을 명확히 구분할 수 있었다. 특히 required, trim 같은 옵션들이 DB 레벨에서 적용되는 것이 아니라 Mongoose가 데이터를 관리하는 방식임을 이해하는 데 집중했다. 이를 통해 Model이 CRUD 메서드를 제공하며 실제 DB 작업을 수행하는 인터페이스 역할을 한다는 점도 확실히 grasp하게 되었다.

헷갈렸던 점#

Mongoose Schema는 MongoDB 자체의 유연함을 유지하면서, 애플리케이션 레벨에서 데이터의 구조와 규칙을 정의하는 ‘계약서’ 역할을 한다는 점이 가장 명확해졌다. 특히 required, type 같은 옵션들이 DB 강제력이 아닌 Mongoose가 데이터를 검증하고 변환하는 로직임을 깨닫고 이해하는 데 시간이 걸렸다. 결국 Schema는 MongoDB라는 ‘통’ 안에 들어갈 데이터의 규격을 정해주는 규칙 책이며, Model은 그 규격에 따라 실제 CRUD 작업을 수행하는 인터페이스라는 구분이 무엇보다 중요했다.

정리된 이해#

Mongoose Schema는 MongoDB라는 유연한 데이터베이스 위에 애플리케이션 레벨에서 데이터를 관리하기 위한 규칙과 인터페이스를 정의하는 것이다. MongoDB가 문서 저장 기반을 제공한다면, Mongoose는 스키마를 통해 필드 타입, 필수 여부, 기본값 등 비즈니스 로직을 제어한다. 결국 Schema는 DB 자체의 유연성을 해치지 않으면서도 개발자가 데이터 구조와 동작을 체계적으로 통제할 수 있게 해주는 도구다.

const mongoose = require('mongoose');

const userSchema = new mongoose.Schema({
  username: {
    type: String,
    required: true,
    trim: true,
    minlength: 2,
    maxlength: 10
  },
  email: {
    type: String,
    required: true,
    unique: true
  }
});

const User = mongoose.model('User', userSchema);

3. 회원가입 POST와 라우팅 오류 해결하기#

무엇을 배웠나#

핵심은 HTTP 메서드와 라우팅 경로의 조합이었으며, 404 에러는 DB 코드가 실행되기 전 라우팅 단계에서 발생한다는 사실을 깨닫고 트러블슈팅 효율을 높였습니다.

헷갈렸던 점#

가장 큰 혼란은 “DB 문제인가, 라우팅 문제인가” 하는 점이었습니다. 데이터가 안 보인다고 MongoDB나 Mongoose Schema 쪽에 문제가 있다고 의심했지만, 실제 발생한 에러는 404 Cannot POST /member/였습니다.

핵심은 HTTP Method와 Route의 조합이었습니다. 단순히 /member/만 호출하거나 라우팅 구조를 정확히 파악하지 못해 404 에러가 발생한 줄 알았던 것이 가장 큰 오점이었습니다.

정리된 이해#

HTTP 요청이 Router에 도달하지 못해 발생한 404 에러는, DB 코드 실행 전 단계에서 라우팅 구조를 점검해야 함을 의미한다. 실제 endpoint는 /member/join로 조합되어야 하므로, app.js와 member_router.js의 경로 설정이 정확히 일치하는지 확인하는 것이 가장 효율적인 트러블슈팅 방법이다.

// member_router.js
const express = require('express');
const router = express.Router();
const Member = require('../model');

router.post('/join', async (req, res) => {
  try {
    const { id, pw, name, phone } = req.body;

    // DB에 회원 정보 저장
    await Member.create({ id, pw, name, phone });

    res.status(201).json({ message: '가입 성공', user: { id, name } });
  } catch (error) {
    console.error('회원 가입 오류:', error);
    res.status(500).json({ message: '서버 내부 오류' });
  }
});

module.exports = router;

4. HTTP 라우트와 테스트 파일 조합 이해하기#

무엇을 배웠나#

POST 요청을 보낼 때 app.use의 prefix와 router.post의 path가 합쳐져 최종 URL이 결정된다는 점을 명확히 이해하게 되었습니다. 서버가 죽었다고 생각했던 ‘Cannot POST’ 에러는 실제로는 해당 경로에 POST 메서드를 처리하는 라우트가 정의되지 않아 발생한 ‘길 찾기 실패’ 상황이었음을 깨닫았습니다. 404 에러가 나면 HTTP Method, app.use prefix, router path 세 가지를 순차적으로 확인하여 원인을 파악해야 한다는 점도 중요한 정리 포인트로 남겼습니다.

헷갈렸던 점#

처음에는 에러 메시지 자체에만 집중하다가, 그 의미를 제대로 해석하지 못했습니다.

Cannot POST /member/

이 문구를 보고 저는 서버가 죽거나 DB 연결에 문제가 생긴 줄 알았습니다. ‘POST 요청을 처리할 수 없다’는 말이니 인프라 문제인 줄 알고 panic 상태였죠. 하지만 실제로는 “해당 경로에서 POST 메서드를 처리하는 라우트가 정의되어 있지 않다"는 뜻이었습니다. 서버는 살아있는데, 요청한 조합(메서드 + URL)이 맞지 않아서 생긴 ‘길 찾기 실패’ 상황이었던 거죠.

또 하나의 헷갈림 포인트는 app.use('/member', router)와 router.post('/join')가 합쳐지는 과정이었습니다. prefix와 path가 어떻게 합쳐져 최종 URL이 되는지, 그리고 test.http 파일에서 실제로 어떤 요청을 보내야 하는지 감이 안 잡혔습니다.

가장 중요한 공식은 이겁니다.

app.use(prefix, router) + router.METHOD(path) = METHOD prefix+path

쉽게 말해, 앱 전체의 접두사(예: /member)와 라우터 안쪽의 구체적인 경로(예: /join)가 합쳐져 최종 URL이 만들어집니다.

그래서 다음과 같은 매칭이 성립합니다.

  • POST /member/join ✅ (성공)
  • POST /member/ ❌ (실패 - router에 /join이 없음)

404 에러가 나면 우선순위로 비교해봐야 할 세 가지가 있습니다.

  1. HTTP Method (GET인지 POST인지 확인)
  2. app.use prefix (URL의 시작 부분이 맞는가?)
  3. router path (나머지 경로가 라우터 안에 정의되어 있는가?)

정리된 이해#

핵심은 app.use(prefix, router)와 router.METHOD(path)가 합쳐져 최종 URL이 만들어지는 공식입니다. 서버 에러가 아니라 ‘경로 조합 불일치’ 문제임을 먼저 확인해야 합니다. 404 에러 발생 시 HTTP Method, app.use prefix, router path 세 가지를 순서대로 검증해야 합니다.

핵심 정리: 라우트 조합 공식#

app.use(prefix, router) + router.METHOD(path) = METHOD prefix+path

매칭 예시:

  • POST /member/join ✅ (성공)
  • POST /member/ ❌ (실패 - router에 /join이 없음)

404 에러 시 확인 순서:

  1. HTTP Method (GET인지 POST인지 확인)
  2. app.use prefix (URL의 시작 부분이 맞는가?)
  3. router path (나머지 경로가 라우터 안에 정의되어 있는가?)

총평#

오늘 오전 전체에서 배운 것#

오늘은 MongoDB와 Express 간의 데이터 연결 흐름을 이해하는 데 집중했습니다. 특히 HTTP 요청이 Router를 거쳐 Mongoose 모델을 호출해 데이터를 저장하는 전층 구조를 파악하여, Schema나 Model 설정 누락으로 인한 데이터 미보임 현상을 해결할 수 있게 되었습니다. 또한 라우팅 경로와 HTTP 메서드의 조합이 중요하다는 점을 깨닫고, ‘Cannot POST’ 에러가 실제 DB 오류가 아닌 경로 정의 부족에서 비롯된 것임을 정확히 이해하게 되어 트러블슈팅 효율이 크게 높아졌습니다.

다음에 조심할 것#

Mongoose 스키마 옵션은 DB 레벨에서 적용되는 것이 아니라 Mongoose가 데이터를 관리하는 방식임을 기억해야 한다.

HTTP 요청이 Router를 거쳐 Model을 호출하는 전층 구조를 정확히 이해하고, 라우팅 경로와 메서드 조합에 오류가 없는지 꼼꼼히 확인해야 한다.

다음 복습 주제#

  1. Mongoose 모델 생성 시기와 데이터 저장 메서드에 대해 다시 정리한다. create() 메서드를 사용하기 전에 반드시 model 객체가 유효하게 초기화되어 있는지 확인하고, 스키마 옵션이 실제 DB 레벨에서 적용되는 것이 아님을 명확히 하여 불필요한 디버깅을 줄이는 방법을 익힐 것이다.

  2. 라우팅 경로와 HTTP 메서드의 조합에 대한 이해를 심화시킨다. app.use()의 prefix와 router.post()의 path가 어떻게 최종 URL을 결정하는지, 그리고 404 에러 발생 시 Method, Prefix, Path 세 가지 요소를 체계적으로 점검하여 라우트 설정을 검증하는 습관을 들일 것이다.

  3. 데이터베이스 연결 상태와 실제 데이터 저장의 차이에 대해 복습한다. DB 연결 자체가 끊어지지 않았음에도 데이터가 저장되지 않는 현상의 원인을 Schema/Model 설정 미완료에서 찾았듯, 모델 생성 과정의 필수 단계를 거치지 않았을 때 발생하는 오류를 예방하고, 요청 흐름을 정확히 추적하는 능력을 키울 것이다.
