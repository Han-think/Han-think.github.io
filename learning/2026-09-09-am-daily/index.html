1. URL 경로와 실제 폴더의 연결 (mapping)#

무엇을 배웠나#

FastAPI에서 URL 요청이 어떻게 처리되는지, 그리고 mount가 어떤 역할을 하는지 정립했습니다. Route는 특정 URL 경로에 접속했을 때 실행될 Python 함수를 연결하는 논리적 연결고리이고, Mount는 URL 공간과 서버 내부의 리소스를 매핑해주는 물리적/공간적 연결 고리입니다. 특히 mount는 브라우저가 폴더로 이동한다는 직관적인 표현보다, URL 공간과 실제 파일 시스템을 연결한다는 개념이 구조를 바꿀 때도 덜 헷갈리는 정확한 이해를 돕습니다.

헷갈렸던 점#

URL 경로와 실제 폴더 구조가 자동으로 연결된다고 오해했습니다. /view라는 주소를 치면 view 폴더로 이동하는 마법 같은 동작이 일어날 것이라 생각했습니다. 하지만 핵심은 URL 문자열과 실제 디렉터리 경로를 개발자가 직접 매핑(mapping)해야 한다는 점이었습니다.

정리된 이해#

FastAPI에서 URL 요청은 @app.get() 같은 라우팅을 통해 특정 경로에 연결된 Python 함수를 실행하는 방식으로 처리되며, mount는 브라우저가 실제 폴더로 이동하는 것이 아니라 URL 공간과 서버 내부의 리소스를 직접 매핑해주는 역할을 한다. 즉, 라우팅은 논리적인 주소-함수 연결이고 마운트는 물리적인 URL 접두사와 디렉터리 경로를 연결하는 작업이다.

from fastapi import FastAPI
from fastapi.staticfiles import StaticFiles

app = FastAPI()

# 1. Route: URL 경로와 Python 함수를 연결
@app.get("/")
def read_root():
    return {"message": "Hello World"}

# 2. Mount: URL prefix와 실제 폴더 경로를 연결 (매핑)
# /static URL로 접속 시, 서버 내부의 'view' 폴더 파일을 제공함
app.mount("/static", StaticFiles(directory="view"), name="static")

2. FastAPI 파라미터와 계산기 실습 (초보자 워킹 노트)#

무엇을 배웠나#

URL 경로와 API 기능은 별개이며, 쿼리 파라미터는 같은 키를 여러 번 전달할 수 있다. FastAPI에서 함수 인자 이름과 타입 힌트만으로도 요청값을 직접 받을 수 있다는 점이 핵심이었다. 또한 /calc가 HTML 화면이 아니라 계산 로직을 처리하는 API 기능임을 구분하는 것이 중요하다.

헷갈렸던 점#

처음 /calc라는 단어를 보았을 때, 이것이 endpoint 이름인지 전체 프로그램 폴더명인지 구분하는 데 시간이 걸렸습니다. 또한 Query parameter가 URL에 그대로 노출된다는 점과 같은 key를 여러 번 전달할 수 있다는 사실이 초보자에게는 낯설었습니다. FastAPI에서 함수 파라미터의 이름과 타입 힌트만으로 쿼리 파라미터를 직접 받을 수 있다는 점이 인상 깊었으며, /calc가 HTML 화면이 아니라 계산 로직을 처리하는 API 기능이라는 점을 구분하는 것이 중요했습니다.

정리된 이해#

FastAPI에서 Request는 클라이언트가 보낸 요청 전체를 의미하며, Parameter는 URL에 포함된 Path parameter와 Query string으로 구분됩니다. 특히 함수 파라미터 이름과 타입 힌트만으로 쿼리 파라미터를 직접 받을 수 있어 라우팅 설계 시 ‘URL = 페이지’라는 개념을 넘어 API 기능의 분리 필요성을 명확히 인식하게 되었습니다.

@app.get("/items")
def read_name(skip: int, limit: int):
    return {"skip": skip, "limit": limit}

URL: /items?skip=10&limit=20

@app.get("/items/id/{item_id}")
def read_id(item_id: str):
    return {"item_id": item_id}

URL: /items/id/10

3. AJAX와 비동기 통신의 핵심 차이점#

무엇을 배웠나#

오늘은 ‘동기’와 ‘비동기’가 단순히 기술 용어로만 느껴졌던 제 인식을 완전히 바꿔놓았습니다. 특히 계산기 예제에서 time.sleep(5) 동안 브라우저가 멈추는 경험을 통해, 비동기가 사용자 경험을 지키는 핵심 기술임을 직관적으로 체감할 수 있었습니다. 그리고 AJAX와 Axios를 통해 페이지 새로고침 없이 서버와 데이터를 주고받을 수 있다는 점, 그리고 Python의 async def가 서버 내부 효율성을 높이는 것과는 별개로 Client-side 통신과는 다른 개념임을 명확히 구분하게 되었습니다.

헷갈렸던 점#

오늘 ‘비동기’라는 용어가 Python 서버 내부 처리 모델과 JavaScript 클라이언트 통신 방식을 뒤섞여 이해하기 어려웠습니다. 특히 계산기 예제에서 time.sleep(5)가 실행되었을 때 브라우저가 얼어붙는 경험을 통해, 동기가 사용자에게 미치는 직접적인 차단 효과를 실감할 수 있었습니다. 결국 AJAX와 Axios는 서버 응답을 기다리는 동안 화면이 멈추지 않게 해주는 Client-side 기술이며, Python의 async def는 서버가 요청을 효율적으로 처리하게 해주는 Server-side 모델이라는 점을 명확히 구분해야 한다는 점이 가장 중요했습니다.

정리된 이해#

AJAX와 Axios는 서버 응답을 기다리는 동안 화면이 멈추지 않게 해주는 클라이언트 측 통신 기술이며, Python의 async def는 서버 내부에서 여러 요청을 효율적으로 처리하는 모델이다. 이 둘은 연결되어 있지만 목적이 다르므로 혼동해서는 안 된다.

function ajaxSend() {
    let val = $('input[name="msg"]').val();

    axios.get('/send?msg=' + val)
        .then(function(res) {
            console.log(res.data);
        });
}

4. Cookie와 Session, 서버와 클라이언트 사이의 신뢰할러운 상태 유지 전략#

무엇을 배웠나#

처음에는 Cookie와 Session이 왜 따로 존재하는지 의아해했지만, 실제로는 Session ID를 전달하는 통로로서 Cookie가 작동한다는 사실을 깨닫고 이해가 깊어졌다. 특히 서버 측에서 세션 데이터를 관리하면서 클라이언트에는 식별자만 남기는 구조임을 명확히 했다. 이를 통해 HTTP의 비연결성 특성을 유지하면서 사용자 상태를 지속적으로 관리할 수 있다는 점이 인상적이었다.

헷갈렸던 점#

처음에는 SessionMiddleware 코드 속에서 세션 정보가 클라이언트와 서버 양쪽에 동시에 존재하는 것처럼 보여서, 정확히 어디에 데이터가 저장되는지 구분이 안 되었습니다. 또한 강의에서는 “Cookie는 Client, Session은 Server"라고 하지만, 실제로는 세션을 식별하는 ID가 Cookie에 담겨 전달된다는 점에서 두 개념이 완전히 분리되어 있지 않고 상호 연관되어 있다는 점이 가장 큰 혼란 포인트였습니다.

정리된 이해#

Cookie는 브라우저에 저장되어 요청 시 자동으로 서버로 전달되며, Session은 서버 측에서 사용자의 연속된 요청을 하나의 덩어리로 묶어 관리하는 방식이다. 실제 구현에서는 세션을 식별하기 위한 키인 Session ID가 Cookie에 담겨 브라우저를 이동하며, 서버는 이 ID를 통해 해당 세션 데이터를 조회한다. 따라서 Cookie와 Session은 독립적인 개념이 아니라, Session ID를 전달하는 통로로서 Cookie가 Session과 밀접하게 연관되어 작동한다는 점을 이해해야 한다.

from fastapi import FastAPI, Request, Response
from fastapi.responses import HTMLResponse
from starlette.middleware.sessions import SessionMiddleware

app = FastAPI()

# 세션 미들웨어 설정 (세션 ID를 쿠키에 저장하도록 함)
app.add_middleware(SessionMiddleware, secret_key="super-secret-key")

@app.get("/")
async def home(request: Request):
    # 현재 세션에 loginId가 있으면 로그인된 상태로 간주
    login_id = request.session.get("loginId", None)

    if login_id:
        message = f"안녕하세요, {login_id}님!"
    else:
        message = "로그인이 필요합니다."
        # 로그인 페이지로 리디렉션하거나 로그인 폼 제공 (생략)

    # HTMLResponse를 통해 간단한 화면 반환
    return HTMLResponse(content=f"<h1>{message}</h1>", status_code=200)

@app.get("/login/{user_id}")
async def login(user_id: str, request: Request):
    # 로그인 처리: 세션에 user_id 저장
    request.session["loginId"] = user_id

    # 응답 헤더에 Set-Cookie가 자동으로 포함되어 브라우저에 Session ID 쿠키 저장됨
    return {"msg": f"{user_id}님 환영합니다!"}

5. mount와 redirect의 역할 구분#

무엇을 배웠나#

mount는 서버가 URL 경로를 실제 파일 폴더에 연결하는 역할을 하고, redirect는 브라우저가 새로운 주소를 요청하도록 유도하는 동작이라는 점을 명확히 구분했다. 특히 ‘누가 다음 행동을 수행하느냐’에 초점을 맞추면 mount는 서버, redirect는 브라우저라는 주체가 뚜렷해져 헷갈림을 줄일 수 있었다. 이를 통해 URL 매핑과 실제 이동 요청의 차이를 정확하게 이해할 수 있게 되었다.

헷갈렸던 점#

처음에는 mount와 redirect가 모두 ‘이동’이라는 단어 때문에 역할이 비슷하게 느껴졌다. 특히 강사님의 설명에서 /view를 폴더 이동 명령어처럼 들으며 두 개념을 혼동했다. 하지만 코드를 직접 보며 동작 주체를 명확히 나누니, mount는 서버가 연결 관계를 맺는 것이고 redirect는 브라우저가 다시 요청하는 것임을 정확히 구분할 수 있게 되었다.

정리된 이해#

mount는 서버가 URL 경로를 실제 파일 시스템 폴더에 연결하는 역할을 하고, redirect는 브라우저가 새로운 주소를 요청하도록 응답 헤드를 보내는 동작이다. 즉, mount는 서버 측의 ‘연결 설정’이고 redirect는 클라이언트 측의 ‘재요청 유도’다.

# mount: URL 네임스페이스를 리소스에 연결 (서버 내부 동작)
app.mount('/view', StaticFiles(directory='view'))

# redirect: 브라우저에게 새로운 Location 요청을 보내는 응답 (브라우저 동작)
@app.get("/")
def main():
    return RedirectResponse('/view/index.html')

총평#

오늘 오전 전체에서 배운 것#

URL 경로와 실제 폴더를 연결하는 mount는 서버 내부의 리소스를 URL 공간에 매핑해주는 물리적 연결고리이며, Route는 특정 URL에 실행될 Python 함수를 논리적으로 연결하는 역할을 한다. 쿼리 파라미터 전달과 함수 인자 타입 힌트만으로 값을 받을 수 있는 FastAPI의 특징을 통해, API 기능과 HTML 화면 처리를 명확히 구분하는 것이 중요하다. 또한 동기 통신 중 브라우저가 멈추는 경험을 통해 비동기가 사용자 경험을 보호하는 핵심 기술임을 직관적으로 체감했으며, Cookie가 Session ID를 전달하는 통로 역할을 하여 서버가 세션 데이터를 관리하면서 HTTP의 비연결성 특성을 유지할 수 있다는 점도 핵심 정리다.

다음에 조심할 것#

  • URL 경로와 실제 폴더 연결 시 mount가 단순히 ‘이동’ 개념이 아니라 ‘매핑’임을 명확히 인식하고, redirect와의 역할 주체 차이를 재확인해야 한다.
  • 비동기 통신에서 브라우저가 멈추지 않도록 하는 것이 핵심 목표임을 기억하며, async def의 서버 효율화 효과와 클라이언트 통신 목적구를 분리해서 공부해야 한다.
  • Cookie가 Session ID를 전달하는 통로 역할을 한다는 점을 기반으로, 서버 측 세션 관리 전략이 HTTP 비연결성의 한계를 어떻게 극복하는지 지속적으로 점검해야 한다.

다음 복습 주제#

오늘 학습한 핵심 개념들이 머릿속에 정리가 되었지만, 아직 실전 적용이 불안정한 부분들이 있습니다.

첫째, mount와 redirect의 역할 구분이 여전히 헷갈릴 때가 있는데, URL 경로 매핑과 브라우저 이동 요청이라는 기술적 차이는 알겠으나, 실제 프로젝트에서 어떤 상황에서 어떤 기능을 써야 하는지 감이 안 잡힙니다. 특히 라우팅 설정 시 mount를 쓸지, redirect를 쓸지 결정하는 기준가 구체적으로 연습해보고 싶습니다.

둘째, 비동기 통신(AJAX/Axios)과 서버 측 async/await의 경계가 아직 명확하지 않습니다. 클라이언트에서 페이지 새로고침 없이 데이터를 주고받는 것과 서버 내부 효율성을 높이는 것은 별개라는 점은 이해했지만, 이 두 가지를 프로젝트 코드에서 어떻게 조합하고 관리해야 하는지 감이 안 잡힙니다.

셋째, 계산기 API 실습 때 쿼리 파라미터 전달 방식과 path parameter의 차이를 확실히 구분하는 연습이 필요합니다. 같은 키를 여러 번 보낼 수 있다는 점이나, 인자 이름만으로 값을 받는 FastAPI의 특징을 실제 함수 설계에 적용했을 때 어떤 이득이 있는지 시나리오별로 정리해보고 싶습니다.
