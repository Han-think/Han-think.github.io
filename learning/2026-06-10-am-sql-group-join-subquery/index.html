1. 어제 SQL 복습: 함수와 JOIN이 서브쿼리로 이어지는 흐름#

무엇을 배웠나#

오전 수업은 전날 배운 SQL 함수와 다수 테이블 제어 복습에서 시작했다. 함수는 단순 계산용으로 끝나는 것이 아니라, 이후 서브쿼리 안에서 기준값을 만드는 재료가 된다.

COUNT = 데이터 개수 세기
LIMIT = 출력 개수 제한
SUM = 총합
AVG = 평균
MAX = 최댓값
MIN = 최솟값

예를 들어 평균 결제 금액보다 작은 인보이스를 찾을 때는 먼저 AVG(Total)로 기준값을 만든다.

SELECT InvoiceId, Total
FROM invoices
WHERE Total < (
    SELECT AVG(Total)
    FROM invoices
);

JOIN 복습에서는 ON이 핵심이었다. JOIN은 테이블을 그냥 붙이는 것이 아니라, 어떤 컬럼끼리 연결할지 지정해야 한다.

SELECT *
FROM rental
INNER JOIN user
    ON user.id = rental.user_id;

헷갈렸던 점#

복습 카드만 보면 함수와 JOIN은 각각 따로 떨어진 문법처럼 보였다. 하지만 실제 문제에서는 AVG, MAX, COUNT 같은 함수가 서브쿼리 안으로 들어가고, JOIN은 테이블 간 경로를 찾는 도구로 다시 등장했다.

또 LEFT JOIN과 RIGHT JOIN은 어느 쪽 테이블이 살아남는지 자주 헷갈릴 수 있다.

FROM A LEFT JOIN B  = A 생존
FROM A RIGHT JOIN B = B 생존

정리된 이해#

전날 배운 3장 함수와 4장 JOIN은 오늘 배운 서브쿼리의 재료였다.

3장 함수
→ 평균/최대/최소 기준값 만들기

4장 GROUP BY / HAVING / JOIN
→ 묶기, 조건 걸기, 테이블 연결하기

5장 서브쿼리
→ 앞에서 만든 기준값과 연결 감각을 안쪽 SELECT로 접어 넣기

2. GROUP BY와 HAVING: 묶고 나서 조건 걸기#

무엇을 배웠나#

GROUP BY는 같은 값끼리 묶는 기준이고, 집계 함수는 묶인 그룹 안에서 개수·합계·평균·최댓값을 계산한다.

기본 공식은 다음과 같다.

SELECT 그룹기준컬럼, COUNT(*) AS count_name
FROM 테이블
GROUP BY 그룹기준컬럼
ORDER BY count_name DESC;

미디어 타입별 트랙 수는 다음처럼 쓸 수 있다.

SELECT MediaTypeId, COUNT(*) AS track_count
FROM tracks
GROUP BY MediaTypeId;

도시별 인보이스 건수를 많은 순서로 정렬하려면 ORDER BY의 기준은 원본 금액이 아니라 집계 결과여야 한다.

SELECT BillingCity, COUNT(*) AS invoices_count
FROM invoices
GROUP BY BillingCity
ORDER BY invoices_count DESC;

담당 직원별 고객 수에서 10명 이상만 보려면 HAVING을 쓴다.

SELECT SupportRepId, COUNT(*) AS customer_count
FROM customers
GROUP BY SupportRepId
HAVING COUNT(*) >= 10;

장르별 최대 재생시간은 MAX와 GROUP BY를 함께 사용한다.

SELECT GenreId, MAX(Milliseconds) AS max_ms
FROM tracks
GROUP BY GenreId
ORDER BY max_ms DESC;

헷갈렸던 점#

DESC를 GROUP BY에 붙이려고 했던 부분이 핵심 오류였다. GROUP BY는 묶는 기준이고, DESC는 정렬 방향이므로 ORDER BY에 붙어야 한다.

GROUP BY = 묶기
ORDER BY = 정렬
DESC = 정렬 방향

또 문제에서 요구하는 정렬 기준이 “건수”인지 “금액”인지 분리해서 봐야 한다. 도시별 주문 건수를 묻는 문제에서 ORDER BY Total DESC를 쓰면 문제 목적과 어긋난다.

정리된 이해#

WHERE와 HAVING의 차이를 이렇게 고정했다.

WHERE = 그룹 짓기 전 원본 행 조건
HAVING = GROUP BY 이후 집계 결과 조건

즉 원본 행을 필터링할 때는 WHERE, 묶은 뒤 계산된 결과를 필터링할 때는 HAVING이다.

3. JOIN과 서브쿼리: ERD보다 연결표를 먼저 보기#

무엇을 배웠나#

Chinook DB 문제에서는 ERD 전체를 한 번에 보려고 하기보다, 문제마다 필요한 테이블과 연결 컬럼을 표처럼 정리하는 방식이 더 유용했다.

트랙 이름과 미디어 타입 이름을 함께 보려면 tracks와 media_types를 연결한다.

SELECT
    t.Name AS track_name,
    mt.Name AS media_type
FROM tracks AS t
INNER JOIN media_types AS mt
    ON t.MediaTypeId = mt.MediaTypeId;

인보이스와 고객 정보를 함께 보려면 invoices.CustomerId = customers.CustomerId 경로를 사용한다.

SELECT
    i.InvoiceId,
    i.Total,
    i.BillingCountry,
    c.LastName,
    c.FirstName
FROM invoices AS i
INNER JOIN customers AS c
    ON i.CustomerId = c.CustomerId;

플레이리스트와 트랙은 직접 연결되지 않고, playlist_track이라는 중간 테이블을 거친다.

SELECT
    p.Name AS playlist_name,
    t.Name AS track_name
FROM playlists AS p
INNER JOIN playlist_track AS pt
    ON p.PlaylistId = pt.PlaylistId
INNER JOIN tracks AS t
    ON pt.TrackId = t.TrackId;

헷갈렸던 점#

세 테이블 JOIN에서는 중간 테이블이 왜 필요한지 바로 보이지 않았다. playlists와 tracks가 직접 연결되지 않기 때문에 playlist_track이 다리 역할을 한다.

playlists → playlist_track → tracks

또 같은 결과를 JOIN으로도, 서브쿼리로도 만들 수 있어서 무엇이 필수인지 혼동됐다.

정리된 이해#

JOIN 문제는 ERD 전체보다 연결표를 믿는 것이 낫다.

tracks.MediaTypeId = media_types.MediaTypeId
invoices.CustomerId = customers.CustomerId
playlists.PlaylistId = playlist_track.PlaylistId
playlist_track.TrackId = tracks.TrackId

서브쿼리는 결과 형태에 따라 구분한다.

단일 행 서브쿼리 = AVG, MAX, MIN처럼 값 하나 → =, >, <
다중 행 서브쿼리 = 목록 → IN, NOT IN
FROM 절 서브쿼리 = 안쪽에서 임시표를 만들고 바깥에서 조회

4. 스칼라 서브쿼리와 FROM 절 서브쿼리: 값과 임시표 만들기#

무엇을 배웠나#

스칼라 서브쿼리는 SQL에 SCALAR라는 키워드를 쓰는 것이 아니다. 서브쿼리 결과가 한 칸짜리 값처럼 쓰일 때 스칼라 서브쿼리라고 부른다.

스칼라 = 한 칸짜리 값
스칼라 서브쿼리 = 값 하나처럼 쓰이는 괄호 안 SELECT

각 고객의 총 결제 금액을 옆 칸에 붙이는 예시는 다음과 같다.

SELECT
    c.FirstName,
    c.LastName,
    (
        SELECT SUM(i.Total)
        FROM invoices AS i
        WHERE i.CustomerId = c.CustomerId
    ) AS total_spent
FROM customers AS c;

FROM 절 서브쿼리는 안쪽 SELECT로 임시표를 만들고, 바깥 SELECT가 그 임시표를 다시 조회하는 방식이다.

SELECT
    country_sales.BillingCountry,
    country_sales.total_sales
FROM (
    SELECT
        BillingCountry,
        SUM(Total) AS total_sales
    FROM invoices
    GROUP BY BillingCountry
) AS country_sales
ORDER BY country_sales.total_sales DESC
LIMIT 5;

헷갈렸던 점#

FROM invoices는 원본 테이블을 바로 쓰는 것이지만, FROM (SELECT ...) AS sub는 원본을 가공한 임시표를 쓰는 것이다. 이 차이가 처음에는 갑자기 난이도를 올리는 부분이었다.

FROM invoices
= 원본 테이블 사용

FROM (SELECT ... FROM invoices GROUP BY ...) AS sub
= 원본을 가공한 임시표 사용

정리된 이해#

SELECT와 FROM의 역할을 다시 정리했다.

FROM = 작업할 데이터 덩어리 / 판 / 임시 테이블을 정함
SELECT = 그 데이터 덩어리에서 최종으로 보여줄 컬럼을 고름

스칼라 서브쿼리는 행마다 값 하나를 붙이고, FROM 절 서브쿼리는 새로운 데이터판을 만든다.

총평#

오늘 오전 전체에서 배운 것#

오전 수업은 함수 복습에서 시작해 GROUP BY, HAVING, JOIN, 서브쿼리, 스칼라 서브쿼리, FROM 절 서브쿼리까지 이어졌다. 처음에는 각각의 문법이 따로 떨어져 보였지만, 실제로는 “기준값 만들기 → 묶기 → 연결하기 → 임시표 만들기 → 최종 결과표 만들기”라는 하나의 데이터 흐름으로 연결된다.

가장 중요한 전환은 SQL을 단순 조회문이 아니라 데이터 파이프라인으로 보는 관점이었다. 원본 테이블을 바로 조회하는 수준을 넘어, 안쪽 SELECT로 요약표를 만들고, 그 결과를 바깥 쿼리에서 다시 정렬하거나 JOIN하는 흐름이 보이기 시작했다.

다음에 조심할 것#

DESC는 GROUP BY가 아니라 ORDER BY에 붙인다. 정렬 기준은 문제에서 요구하는 값이 건수인지 금액인지 먼저 확인해야 한다. JOIN 문제에서는 테이블을 먼저 외우려고 하기보다 중심 테이블과 연결 경로를 찾는 편이 안전하다.

서브쿼리는 괄호 안 SELECT가 무엇을 반환하는지부터 봐야 한다. 값 하나인지, 목록인지, 임시표인지 구분하지 않으면 메인쿼리까지 같이 흔들린다.
