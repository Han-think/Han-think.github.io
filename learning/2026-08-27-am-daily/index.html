1. RTL UI Test Refactoring with Helper Function#

무엇을 배웠나#

오늘은 반복되는 UI 테스트 흐름을 함수로 캡슐화하는 방법을 배웠습니다. test.each()가 데이터 통합에 유리한 반면, helper function을 사용하면 각 테스트 케이스의 고유 이름을 유지하면서 ‘어떻게 테스트하는か’를 추상화할 수 있다는 점을 이해했습니다. 무엇보다도 고정되는 동작과 바뀌는 데이터를 분리하여 인자로 전달하는 것이 코드의 가독성과 유지보수성을 높이는 핵심이라는 점을 명확히 했습니다.

헷갈렸던 점#

test.each() 방식이 코드 양을 줄여주는 것처럼 보여도, 실제 UI 동작 흐름 자체를 캡슐화하는 것과는 목적이 달랐습니다.

helper function을 만들면 테스트 케이스마다 코드를 다시 짜야 해서 번거로워 보였지만, 이는 ‘어떻게 테스트하는가(UI 조작 흐름)‘를 함수로 추상화한 것이고, test.each()는 단순히 데이터만 통합한 것에 불과했습니다.

정리된 이해#

반복되는 UI 테스트 흐름을 하나의 함수로 캡슐화하여, 공통된 동작은 숨기고 변하는 데이터(값과 연산자)만 인자로 전달함으로써 코드의 중복을 효과적으로 제거할 수 있다. test.each()가 테스트 데이터를 통합하는 반면, 헬퍼 함수는 ‘어떻게 테스트하는か(UI 조작 흐름)’ 자체를 추상화하여 테스트 케이스 이름을 유지하면서 구조를 간소화한다는 점에서 두 접근 방식은 서로 다른 단계의 추상화를 제공한다.

1. 무엇이 헷갈렸나#

어제는 test.each()를 사용해 테스트 데이터만 행으로 묶고, 반복되는 render와 userEvent 같은 코드는 그대로 두는 방식으로 학습했습니다. 그런데 오늘은 아예 그 반복되는 UI 동작 자체를 함수로 뽑아버리셨죠.

“어차피 test.each()로 데이터를 통합하면 더 깔끔한데, 왜 굳이 helper function을 만들어서 각 테스트마다 코드를 다시 짜야 하지?“라는 의문이 들었습니다. 특히 test.each() 방식이 코드 양도 적고 추가하기도 편해 보여서, 강사님의 방식이 오히려 ‘원시적’인 느낌까지 들었습니다.

또 하나 혼란스러웠던 점은 **“어디까지가 추상화이고, 어디부터가 중복 제거인가”**였습니다. helper function을 만들면 분명 코드 양은 줄어들지만, 정작 테스트 코드를 읽었을 때 ‘이게 무슨 테스트지?‘를 파악하는 데 더 시간이 걸리는 것 같았습니다.

2. Express 서버 구동과 라우팅의 원리 이해하기#

무엇을 배웠나#

코드 강조 색상이 실제 실행 여부를 보장하지 않는다는 점을 깨닫고, 문법적 시각적 효과에 의존하면 안 된다는 교훈을 얻었다. Express 서버는 app.listen() 이후 요청을 지속적으로 대기하는 ‘유지 상태’가 핵심 개념임을 이해했다. 이러한 혼란을 해소함으로써 서버와 일반 스크립트의 실행 차이점을 명확히 구분할 수 있게 되었다.

헷갈렸던 점#

코드 색깔이 예쁘게 보여도 문법 강조는 실행 보장이 아니므로 실제 동작 여부를 반드시 확인해야 한다. Express 서버는 app.listen() 이후 요청을 계속 기다리는 ‘대기 상태’가 되는데, 이는 일반 스크립트 종료와 달라 진입장벽으로 느껴졌다. 이러한 혼란을 해소하니 서버는 끝나는 것이 아니라 지속적으로 동작하며 클라이언트의 신호를 감시하는 과정이라는 사실이 명확해졌다.

정리된 이해#

Express 서버는 요청을 지속적으로 기다리는 ‘대기 상태’의 프로세스이며, 문법 강조 기능은 코드의 실행 여부를 보장하지 않는다는 점을 명확히 인지해야 한다.

const express = require('express');
const app = express();

app.get('/', (req, res) => {
  res.send('Hello World!');
});

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});

3. Express 경로와 HTTP 메서드의 조합 이해하기#

무엇을 배웠나#

Express 라우팅은 URL 경로와 HTTP 메서드의 조합으로 결정됩니다. app.get()는 GET 요청, app.post()는 POST 요청에만 해당 경로를 매칭시킵니다. 404 에러는 서버가 꺼진 것이 아니라, 요청한 method와 path를 조합한 라우트를 찾지 못해 발생하는 것입니다. Router 분리는 처리 로직을 분리하여 파일 구조를 깔끔하게 유지하는 방법입니다.

헷갈렸던 점#

브라우저에 주소를 입력했을 때 서버가 꺼진 줄 알았지만, 실제로는 정의된 경로가 없어서 404 에러가 뜬 것이었습니다. Express에서 라우팅은 URL 경로와 HTTP 메서드(GET, POST 등)의 조합으로 결정되며, 브라우저는 기본적으로 GET 요청을 보내지만 서버 측에서는 해당 메서드를 explicit하게 선언해주어야 route가 매칭된다는 점이 처음에는 직관적이지 않았습니다. 404 에러는 서버 자체가 죽은 것이 아니라, 요청한 method와 path를 조합한 라우트를 찾지 못해 발생하는 것이니 안심하고 디버깅할 수 있습니다.

정리된 이해#

Express 라우팅은 URL 경로와 HTTP 메서드의 조합으로 결정된다. 브라우저는 기본적으로 GET 요청을 보내지만, 서버 측에서 해당 메서드를 명시적으로 선언해야 route가 매칭된다. 404 에러는 서버가 죽은 것이 아니라, 요청한 method와 path를 조합한 라우트를 찾지 못해 발생하는 것이다.

const express = require('express');
const app = express();

// GET 요청일 때 '/hello' 경로 매칭
app.get('/hello', (req, res) => {
  res.send('Hello, this is a GET request!');
});

// POST 요청일 때 '/hello' 경로 매칭
app.post('/hello', (req, res) => {
  res.send('Hello, this is a POST request!');
});

Express 서버 구동에 있어 app.listen() 이후 요청을 지속적으로 대기하는 ‘유지 상태’가 핵심임을 이해했으며, 라우팅은 URL 경로와 HTTP 메서드의 조합으로 결정된다는 점을 명확히 했습니다.

다음에 조심할 것#

  • UI 테스트 시 고정된 동작과 변하는 데이터를 명확히 분리하여 인자로 전달해야 코드 유지보수가 용이하다.
  • Express 서버는 app.listen() 이후 요청을 지속적으로 대기하는 ‘유지 상태’가 핵심 개념이며, 문법 강조 색상에 현혹되지 말고 실제 실행 흐름을 이해해야 한다.
