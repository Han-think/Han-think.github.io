1. ERD 구조#

왜 이걸 보게 됐나#

데이터베이스 모델링을 통해 효율적인 데이터 저장 및 관리를 할 수 있도록 ERD는 필수적인 도구인데, 실제 서비스에서 데이터를 어떻게 연결하고 표현해야 할지 몰라서 처음에는 감이 잘 안 잡혔어. 특히 다양한 테이블 간의 관계를 시각적으로 보여주는 ERD 구조를 이해해야 데이터를 정확하게 표현하고 쿼리할 수 있다는 것을 깨달았어. 그래서 ERD를 제대로 익히고 Crow’s Foot 표기법을 통해 관계를 명확하게 표현할 수 있게 되었어.

내가 헷갈린 지점#

처음에는 ERD를 트리처럼 단순하게 테이블 간의 연결을 보여주는 구조라고 생각했는데, 실제로는 테이블 간의 양방향 관계를 시각화하는 복잡한 회로도라는 것을 깨달았습니다. 특히 playlists 테이블과 tracks 테이블이 직접 연결되지 않고 playlist_track이라는 중간 테이블을 거쳐 연결되는 부분이 이해하기 어려웠습니다. 테이블 간의 관계가 여러 단계로 이어질 수 있다는 점이 낯설었습니다.

시도한 코드 / 예시#

-- playlists 테이블과 tracks 테이블 간의 연결을 위한 중간 테이블 playlist_track 예시:
-- playlists 테이블: playlist_id (PK), name
-- tracks 테이블: track_id (PK), title
-- playlist_track 테이블: playlist_id (FK referencing playlists), track_id (FK referencing tracks)

결과와 해석#

playlists와 tracks 테이블 간의 관계를 표현하기 위해 playlist_track 테이블이 사용된 것을 보면서, N:M 관계는 직접적인 연결이 아닌 중간 테이블을 통해 관계를 정의해야 한다는 것을 깨달았습니다. 이 중간 테이블은 playlists와 tracks 각각의 기본 키를 외래 키로 참조하여, 하나의 재생 목록에 여러 트랙이 연결될 수 있고, 하나의 트랙이 여러 재생 목록에 포함될 수 있는 관계를 나타냅니다. 이러한 구조는 데이터의 유연성과 무결성을 유지하는 데 중요한 역할을 합니다.

정리된 이해#

처음에는 ERD를 트리처럼 단순하게 이해했지만, 테이블 간의 복잡한 양방향 관계를 보여주는 회로도처럼 파악해야 한다는 것을 알게 되었다. 특히 playlists와 tracks 관계처럼 중간 테이블이 존재하는 복잡한 연결 방식을 이해하는 데 집중해야 했음을 깨달았다. 이제는 ERD를 통해 데이터베이스 테이블 간의 관계를 시각적으로 표현하고 분석할 수 있을 것 같다.

2. 카디널리티#

왜 이걸 보게 됐나#

데이터베이스 설계 과정에서 테이블 간의 관계를 명확하게 정의하고 표현해야 했는데, 단순히 테이블을 만들어서는 데이터의 정확성과 무결성을 보장할 수 없다는 것을 깨달았습니다. 카디널리티를 이해해야 테이블 간의 연결 관계를 정확하게 모델링하고, 데이터베이스의 효율적인 구조를 설계할 수 있다는 것을 알게 되었습니다. 예를 들어, 플레이리스트와 트랙 간의 관계를 1:N으로 정의하는 것이 아니라 N:M으로 정확하게 모델링해야 하는 이유를 알게 되었습니다.

내가 헷갈린 지점#

처음에는 카디널리티를 단순히 테이블의 행 수나 컬럼 수를 의미한다고 생각했어요. 그래서 1:N이나 N:M 같은 관계를 그림으로 표현할 때, 실제 데이터의 양을 나타내는 지표라고 착각했었죠. 다대다 관계에서 중간 테이블이 왜 필요한지, 그리고 카디널리티가 이 중간 테이블의 존재를 어떻게 반영하는지도 잘 이해하지 못했어요.

시도한 코드 / 예시#

# 카디널리티 예시 (N:M 관계)
# playlists 테이블과 tracks 테이블의 다대다 관계를 나타냅니다.
# playlist_track 테이블은 중간 테이블 역할을 합니다.

# playlists 테이블
# CREATE TABLE playlists (
#   playlist_id INT PRIMARY KEY,
#   playlist_name VARCHAR(255)
# );

# tracks 테이블
# CREATE TABLE tracks (
#   track_id INT PRIMARY KEY,
#   track_name VARCHAR(255)
# );

# playlist_track 테이블 (중간 테이블)
# CREATE TABLE playlist_track (
#   playlist_id INT,
#   track_id INT,
#   PRIMARY KEY (playlist_id, track_id),
#   FOREIGN KEY (playlist_id) REFERENCES playlists(playlist_id),
#   FOREIGN KEY (track_id) REFERENCES tracks(track_id)
# );

결과와 해석#

카디널리티는 테이블 간 관계의 최소/최대 개수를 나타내는 핵심 개념인데, 예를 들어 N:M 관계는 중간 테이블을 통해 구현되고, 이 중간 테이블의 존재 자체가 카디널리티를 반영하는 것 같아. 강의에서 제공된 다이어그램과 실제 DB 스키마를 비교하면서 카디널리티를 적용해 보니, 데이터 모델링의 설계 의도를 더 명확하게 이해할 수 있었다. 특히, playlist_track 테이블을 통해 playlists와 tracks의 N:M 관계가 표현되는 것을 보면서 카디널리티가 단순한 기호 이상의 의미를 가지는 것을 알게 되었다.

정리된 이해#

카디널리티는 테이블 간의 관계에서, 특정 엔티티가 다른 엔티티와 얼마나 많은 개수를 연결하는지를 나타내는 중요한 개념이야. 예를 들어, ‘일대다’ 관계는 하나의 엔티티가 여러 엔티티와 연결될 수 있다는 의미고, ‘다대다’ 관계는 중간 테이블을 통해 연결을 표현해야 한다는 것을 알려주지. 이 개념을 이해하면 ERD를 그릴 때 테이블 간의 연결을 정확하게 표현할 수 있어.

3. Crow’s Foot 표기법#

왜 이걸 보게 됐나#

데이터베이스 설계 과정에서 테이블 간의 관계를 시각적으로 표현하고 이해하기 위해 ERD와 Crow’s Foot 표기법을 배우게 되었어. 특히, 복잡한 관계를 명확하게 파악하고 설계 오류를 줄이기 위해 이 표기법이 필수적이라는 것을 알게 되었지. 이제는 이 표기법을 통해 데이터베이스 설계를 좀 더 효율적으로 할 수 있을 것 같아.

내가 헷갈린 지점#

처음에는 Crow’s Foot 표기법을 그냥 단순한 그림 기호 정도로 생각했는데, 각 기호가 관계의 cardinality를 나타내는 엄격한 의미를 가지고 있다는 것을 몰랐어요. 특히 < 와 O< 기호의 미묘한 차이를 파악하는 데 어려움을 겪었고, 여러 관계가 얽혀 있을 때 어떻게 해석해야 할지 헷갈렸습니다.

시도한 코드 / 예시#

-- Crow's Foot 표기법 예시 (가정)
-- playlists 테이블과 tracks 테이블 간의 관계를 나타내는 ERD 조각
-- playlist_track 테이블을 사용한 N:M 관계 표현

-- playlists 1개는 playlist_track 0개 또는 그 이상 가질 수 있음 (O<)
-- tracks 1개는 playlist_track 0개 또는 그 이상 포함될 수 있음 (O<)
-- playlist_track 테이블은 playlists 테이블의 ID를 외래키로 참조 (||)
-- playlist_track 테이블은 tracks 테이블의 ID를 외래키로 참조 (||)

결과와 해석#

Crow’s Foot 표기법을 사용해서 테이블 간의 관계를 그림으로 표현하는 연습을 했는데, 특히 O와 < 기호가 어디에 쓰이는지를 파악하는 게 중요했습니다. 강의 자료에 있는 예시 다이어그램을 따라 직접 그려보면서 테이블 간의 연결 방식과 카디널리티를 시각적으로 이해하는 데 도움이 됐습니다.

정리된 이해#

Crow’s Foot 표기법은 테이블 간의 관계를 시각적으로 표현하는 방법인데, 각 기호는 관계의 카디널리티를 나타내서 필수적인 연결 여부나 연결될 수 있는 개수를 명확하게 보여줍니다. 처음에는 다양한 기호가 혼란스러웠지만, 각 기호가 의미하는 바를 이해하고 예시를 통해 연습하면서 테이블 간의 연결 방식을 정확하게 파악할 수 있게 되었습니다. 이제는 ERD를 통해 데이터베이스 설계를 더 효과적으로 진행할 수 있을 것 같습니다.

4. 외래키#

왜 이걸 보게 됐나#

테이블 간의 관계를 제대로 표현하려면, 다른 테이블의 정보를 참조하는 외래키라는 개념이 꼭 필요했어요. 예를 들어, 여러 노래가 여러 플레이리스트에 속할 수 있는데, 이 관계를 나타내려면 노래 테이블과 플레이리스트 테이블 외에 중간 테이블을 만들고, 그 테이블에 외래키를 설정해야만 정확한 연결을 표현할 수 있거든요. 그래서 데이터베이스 설계에서 외래키는 테이블 간의 연결고리를 만들고 데이터의 무결성을 유지하는 핵심적인 역할을 한다는 것을 알게 됐습니다.

내가 헷갈린 지점#

처음에는 외래키가 단순히 테이블 간의 연결 고리라는 생각만 했지, 왜 ‘다른 테이블의 기본키를 참조’해야 하는지에 대한 필요성을 명확히 이해하지 못했습니다. 또한, 외래키가 데이터 무결성을 어떻게 보장하는지에 대한 개념이 부족하여, 단순히 연결해주는 역할만 한다고 생각했습니다. 외래키가 테이블 간의 관계를 ‘강제’하는 역할을 한다는 것을 이해하는 데 시간이 걸렸습니다.

시도한 코드 / 예시#

-- playlists 테이블
CREATE TABLE playlists (
    playlist_id INTEGER PRIMARY KEY,
    name VARCHAR(255) NOT NULL
);

-- tracks 테이블
CREATE TABLE tracks (
    track_id INTEGER PRIMARY KEY,
    title VARCHAR(255) NOT NULL
);

-- playlist_track 테이블 (중간 테이블)
CREATE TABLE playlist_track (
    playlist_id INTEGER,
    track_id INTEGER,
    PRIMARY KEY (playlist_id, track_id),
    FOREIGN KEY (playlist_id) REFERENCES playlists(playlist_id),
    FOREIGN KEY (track_id) REFERENCES tracks(track_id)
);

결과와 해석#

외래키는 playlists 테이블의 playlist_id 컬럼이 playlists 테이블의 기본키를 참조하는 방식으로, 플레이리스트와 트랙 간의 다대다 관계를 연결하는 핵심 역할을 합니다. 이를 통해 특정 트랙이 어떤 플레이리스트에 속하는지, 그리고 플레이리스트에 어떤 트랙들이 포함되는지를 효율적으로 관리할 수 있습니다. 코드 실행 결과는 조인 쿼리를 통해 플레이리스트 정보와 연결된 트랙 정보를 함께 가져오는 것을 확인할 수 있었습니다.

정리된 이해#

외래키는 다른 테이블의 기본키를 참조하여 두 테이블 간의 관계를 설정하는 컬럼이야. 이를 통해 관련된 데이터를 연결하고, 데이터의 무결성을 유지할 수 있어. 예를 들어, playlist_track 테이블의 외래키는 playlists 테이블과 tracks 테이블의 기본키를 참조하여 플레이리스트와 트랙 간의 연결을 나타내지.

총평#

오늘 전체에서 배운 것#

ERD는 테이블 간의 관계를 시각적으로 표현하는 회로도와 같다는 것을 이해했고, Crow’s Foot 표기법을 통해 관계의 종류와 수를 정확히 파악할 수 있게 되었습니다. 특히, 다대다 관계를 해결하기 위한 중간 테이블의 역할을 명확히 이해하게 되었습니다.

다음에 조심할 것#

다음에는 ERD를 그릴 때 테이블 간의 관계를 단순한 연결선이 아닌, 데이터 흐름의 경로로 생각해야겠다. 특히 중간 테이블을 사용하는 N:M 관계를 그릴 때, 각 테이블의 카디널리티를 정확히 파악하는 데 집중해야겠다. Crow’s Foot 표기법의 다양한 기호들의 의미를 암기하는 것뿐 아니라, 실제 ERD에 적용하는 연습을 꾸준히 해야겠다.

다음 복습 주제#

Crow’s Foot 표기법에서 다양한 조합의 Cardinality를 적용한 복잡한 ERD를 그려보고, 실제 데이터베이스 스키마 설계에 어떻게 활용되는지 예제를 찾아봐야겠다. 특히, O< 기호의 활용법과, 중간 테이블이 필요한 N:M 관계의 설계 원리를 더 깊이 파고들어야 할 것 같다.
