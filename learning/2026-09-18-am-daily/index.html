1. MariaDB DDL 기본 구조와 실습 정리#

무엇을 배웠나#

데이터베이스 구조를 이해하는 핵심은 ‘Database’와 ‘Table’의 관계, 그리고 DESC 명령어로 Column을 확인하는 것입니다. 또한 데이터 타입 선택 시 비즈니스 로직(예: 앞자리 0 유지 등)을 고려해야 한다는 점이 중요했습니다.

헷갈렸던 점#

처음에는 명령어가 너무 많아 각각 외워야 하는 것처럼 느껴졌습니다. 특히 SHOW TABLES와 DESC employees가 비슷하게 보여서 무슨 차이인지 감을 잡기 어려웠습니다. 또 mobile 같은 경우 숫자처럼 보인데 왜 VARCHAR로 저장해야 하는지 처음에는 이해가 안 갔습니다.

정리된 이해#

DB는 여러 테이블을 모아둔 저장 단위이며, 실제 데이터는 테이블에 저장된다. 명령어는 SHOW DATABASES로 목록을 확인하고, DESC로 테이블 구조를 파악한 뒤 CREATE, ALTER, DROP 등으로 구조를 관리한다. 데이터 타입은 용도와 특성에 맞게 선택해야 하며, 특히 숫자처럼 보이지만 계산이 아닌 식별이나 보존이 필요한 경우 VARCHAR가 적합하다.

-- Database 생성 및 선택
CREATE DATABASE mydb;
USE mydb;

-- Table 생성
CREATE TABLE test_table(
    user_name VARCHAR(40),
    age INT(3),
    mobile VARCHAR(20),
    reg_date DATE DEFAULT CURDATE()
);

-- 구조 확인
DESC test_table;

-- Table 수정 (컬럼 이름 변경)
ALTER TABLE employees
RENAME COLUMN last_name TO family_name;

-- 컬럼 추가
ALTER TABLE employees
ADD (depart_no VARCHAR(10));

-- 속성 변경
ALTER TABLE employees
MODIFY COLUMN commission FLOAT(4,2);

-- 삭제
DROP TABLE test_table;

2. MariaDB utf8mb4 문자셋 설정과 한글 저장 오류 해결하기#

무엇을 배웠나#

MariaDB는 문자셋을 명시하지 않으면 서버 기본값이 테이블에 상속된다는 점을 깨닫고, latin1가 한글 저장을 막는 주원인임을 이해했습니다. 또한 설정 계층 구조를 통해 서버 레벨과 기존 객체 레벨의 수정 방법을 명확히 구분했습니다. 앞으로는 테이블 생성 시 반드시 utf8mb4를 명시적으로 지정하여 한글 저장 문제를 예방할 것입니다.

헷갈렸던 점#

SQL 문을 작성하지 않았음에도 테이블이 latin1로 생성된 이유는 MariaDB가 ‘서버 기본 설정’을 물려받기 때문입니다.

한글 저장이 실패한 원인은 latin1 문자셋이 한글(UTF-8 등)을 지원하지 않기 때문에 데이터 저장 도중 오류가 발생했기 때문입니다.

정리된 이해#

MariaDB는 문자셋을 명시하지 않으면 서버 기본값을 상속받아 latin1가 적용될 수 있어, 한글 저장에 실패하는 경우가 있다. 문자셋 설정은 서버→데이터베이스→테이블 순으로 계층 구조를 가지며, 기존 객체는 ALTER 문을 통해 개별적으로 수정해야 한다.

SHOW CREATE TABLE employees;
-- 결과: DEFAULT CHARSET=latin1 COLLATE=latin1_swedish_ci

ALTER DATABASE mydb
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

ALTER TABLE employees
CONVERT TO CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;

3. 데이터 입력과 중복 처리: INSERT와 UPSERT#

무엇을 배웠나#

INSERT 문을 통해 실제 데이터를 테이블에 채우는 방법을 배웠습니다. 여러 행을 한 번에 삽입하는 문법과, 중복된 키가 생겼을 때 기존 데이터를 수정하는 UPSERT 구문을 익혔습니다. 특히 WHERE 절 없이 UPDATE나 DELETE를 실행하면 모든 행이 영향을 받을 수 있다는 점에 주의를 기울였습니다. NULL이 ‘값 없음’을 의미하며, INSERT 시 컬럼 생략 시 기본적으로 NULL로 처리된다는 점을 명확히 이해했습니다.

헷갈렸던 점#

INSERT 시 중복 허용 여부는 제약조건(PRIMARY KEY 등)에 따라 달라지며, 조건이 없으면 동일한 데이터가 여러 번 입력됩니다. NULL은 ‘값이 없다’는 의미이며, 문자열 ‘NULL’로 저장되는 것이 아니므로 INSERT 시 생략된 컬럼은 기본적으로 NULL로 처리됩니다.

정리된 이해#

INSERT 시 PRIMARY KEY 등 제약조건이 없으면 중복 데이터가 자유롭게 삽입되며, NULL은 ‘값이 없다’는 의미이며 문자열로 저장되는 것이 아니다. DML에서 WHERE 절 없이 UPDATE나 DELETE를 실행하면 테이블 전체 행에 영향을 미칠 위험이 있으므로 주의해야 한다.

INSERT INTO employees(
    emp_no,
    first_name,
    family_name
)
VALUES
(117, '상민', '전'),
(118, '준', '유');

INSERT INTO employees(
    emp_no,
    first_name
)
VALUES (123, '홍길동')
ON DUPLICATE KEY UPDATE first_name = VALUES(first_name);

4. EC2 MariaDB 설정과 접속 흐름: 두 영역의 구분#

무엇을 배웠나#

MariaDB 설정 파일(/etc/my.cnf)은 EC2 리눅스 서버 내부에서 관리하는 것이지, 내 PC(DBeaver)에서는 직접 수정할 수 없다는 사실을 깨달았다.

SQL 쿼리 작성과 데이터 조작은 DBeaver 등 SQL 클라이언트 툴을 통해 수행되며, 서버의 설정 변경이나 재시작 명령어(systemctl restart mariadb)는 EC2 리눅스 Shell(SSH/PuTTY)을 통해 실행해야 한다는 점도 명확히 구분했다.

헷갈렸던 점#

EC2 리눅스 서버 접속과 SQL 공부가 동시에 진행된다는 점에 혼란이 있었다. 리눅스 Shell(EC2 내부)과 SQL Client(내 PC)는 별개의 영역이며, 설정 파일(/etc/my.cnf)은 EC2 안에서 열어야 한다는 점을 구분하지 못했다.

정리된 이해#

리눅스 서버(EC2)와 내 PC는 별개의 영역으로 구분된다. EC2 내부에서는 sudo vim /etc/my.cnf와 같은 명령어로 MariaDB 설정을 관리하고, 실제 SQL 쿼리는 DBeaver 등 클라이언트 툴을 통해 실행한다. 두 공간을 명확히 분리하면 작업 흐름이 자연스럽게 이해된다.

[수업/학습의 흐름]
내 PC (DBeaver)       →      EC2 Linux (PuTTY/SSH)
SQL 쿼리 실행         →      MariaDB 설정 및 서비스 관리

총평#

오늘 오전 전체에서 배운 것#

오늘은 MariaDB의 기본 구조와 문자셋 설정, 데이터 입력 및 UPSERT 문법을 정리했습니다. 특히 테이블 생성 시 반드시 utf8mb4를 명시하여 한글 저장 문제를 예방해야 한다는 점을 명확히 이해했습니다. 또한 EC2 환경에서 MariaDB 설정을 변경하려면 서버 내부 Shell을 통해 접속하고 재시작 명령어를 실행해야 한다는 점도 구분해서 학습했습니다.

다음에 조심할 것#

  1. DBeaver 등 클라이언트 툴에서는 보이지 않는 서버 설정 파일(/etc/my.cnf)은 EC2 리눅스 Shell을 통해 직접 수정하고 재시작해야 하므로, 실수 방지를 위해 항상 SSH 접속 후 변경 사항을 확인하는 습관을 들일 것이다.
  2. INSERT 시 컬럼 생략으로 인해 의도치 않은 NULL 값이 삽입되지 않도록, 반드시 대상 컬럼을 명시하거나 기본값 설정을 검토하여 데이터 무결성을 유지할 것이다.
  3. WHERE 절 없이 UPDATE나 DELETE 문을 실행하면 모든 행에 영향을 미칠 수 있으므로, 항상 조건절을 꼼꼼히 검증한 후 실행하는 안전한 쿼리 작성 습관을 기를 것이다.

다음 복습 주제#

다음 학습에서는 UPDATE와 DELETE 문에서 WHERE 절을 반드시 확인하여 의도치 않은 전체 행 삭제나 수정을 방지하는 연습을 해야겠다. 또한, EC2 환경에서 MariaDB 설정을 변경한 후에는 반드시 systemctl restart mariadb 명령어를 통해 서비스를 재시작해야 반영되는지 검증해보는 것이 중요할 것이다.
